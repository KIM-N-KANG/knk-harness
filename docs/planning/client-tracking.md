계약의 승인·적용, 구현·검증·배포 증거와 Jira 연결을 관리합니다. 제품 계약은 스펙, 구조는 설계, 선택 이유는 ADR이 정본입니다. Phase·일정은 [로드맵](roadmap.md)만 소유하며 이 문서에 복사하지 않습니다.

## 사용·갱신 규칙

- 승인 상태는 `미정 / 방향 합의 / 승인`으로 구분합니다. 승인된 목표라도 적용을 유예했다면 현재 플랫폼 계약과 구분하고 적용 조건·목표 문서 링크를 남깁니다.
- 플랫폼별로 `미착수 / 진행 중 / 코드 반영 / 검증 / 배포`를 구분합니다. 코드 반영에는 기준 커밋, 검증에는 실행 환경·결과, 배포에는 릴리스 근거가 필요합니다. 이번 문서 이관으로 제품 검증·출시를 새로 완료 처리하지 않습니다.
- Jira는 작업 담당·일정·진행의 정본입니다. 여기는 티켓·계약·계획·PR·검증·릴리스를 연결합니다. Jira 상태를 수동 복제하지 않습니다.
- 새 행의 최소 항목은 `기능 / 승인·적용 범위 / 플랫폼별 코드·검증·배포 근거 / Jira·계획·PR 링크 / 남은 확인`입니다. 새 확인이 생기면 갱신하고 완료 시 결과 링크로 닫습니다.
- 구현 계획은 해당 저장소의 기존 계획 경로에 둡니다. 논의 중 목표·승인된 변경 계약·실행 단계를 별도 절로 구분하고 현재 스펙으로 오인되지 않게 합니다. 착수 직전에 순서·검증·복구 방법을 확정합니다.
- 구현 후 유효한 계약·설계와 ADR을 먼저 반영하고 계획에는 결과·검증·정본 링크만 보충해 보관합니다. 과거 계획 본문을 현재 지침으로 계속 고치지 않습니다. 완료 행에는 필요한 링크만 남기며 세부 실행 일지는 계획·PR이 소유합니다.

## 이번 문서 이관

- 작업: [KNK-1236](https://kimandkang.atlassian.net/browse/KNK-1236). 세 저장소 브랜치: `docs/KNK-1236-split-client-spec-and-adr`.
- 조사 기준: harness `2d77abce078b75e168d8f924e3759e3bb624515a`, web `a11538dc3d22a6a543875986abffeb6959a533d3`, Android `6bccf25adc531dfc8254a0dad3076bef0a72958a`.
- 현재 체크아웃에서 확인: 웹은 단일 제작 슬롯과 자동 채팅 생성, Android는 ownerId가 있는 편집·완성 요청 두 테이블과 루트 알림 진입의 SavedStateHandle을 사용합니다. 문서의 전체 기능 상태를 코드·기기로 재검증한 작업은 아닙니다.
- 기존 본문에서 문서 전체가 Android 미착수라는 설명과 개별 기능 반영 기록이 충돌했습니다. 아래 과거 상태표는 당시 문서 기록이며 현재 상태로 재인용하지 않습니다. 최신 확인은 기능별 증거를 추가합니다.

### 제품 문서 경로·번호 정리

- 2026-09-09: 역할별 폴더, 배경의 spec 배치, 폴더별 독립 번호를 적용했습니다. 당시에는 각 폴더에 같은 클라이언트 번호를 사용했으며, 이후 파일명 변경·통합에 따라 [C-007](../adr/1-1-client-adr.md#c-007)로 대체했습니다. [C-006](../adr/1-1-client-adr.md#c-006), [개정 계획·검증/복구](product-document-reorganization.md)를 참조합니다.
- 이번 단계는 경로·번호·참조 정리입니다. 제품 본문의 책임 분리와 이 문서의 제품 전체 추적 확장은 후속 계획입니다. 기능 검증·배포 상태는 변경하지 않았습니다.
- 같은 날 후속 경로 정리: `spec/`·`design/`·`adr/`를 `docs/` 바로 아래로 옮기고 중간 `product-specs/` 폴더를 제거했습니다. 폴더별 번호와 본문 분리 범위는 유지합니다.

### PWA 푸시 후속 범위

[KNK-1271](https://kimandkang.atlassian.net/browse/KNK-1271)의 후속 설계 범위입니다. 일정은 로드맵·Jira를 따르며 현재 웹 제공 계약에 포함하지 않습니다.

- 로그인과 브라우저 알림 권한을 모두 확인한 뒤 FCM 토큰을 `PUT /users/me/push-tokens`의 `platform: "WEB"`으로 등록하고 삭제는 기존 DELETE의 `token` 계약을 사용합니다.
- `GET·PUT /users/me/push-settings`의 광고 수신 동의 UI를 별도로 설계합니다. 브라우저 권한으로 광고 수신 동의를 대체하지 않습니다.
- data `recipientId`가 없거나 현재 로그인 회원 ID와 다르면 표시·클릭을 차단해야 합니다. 서비스 워커·브라우저 자동 표시 경로까지 검증이 필요합니다.
- 같은 Firebase 프로젝트, VAPID·서비스 워커 구성이 선행 조건입니다. 지원 브라우저·UI는 후속 확정하며 [서버 API](../spec/4-backend-server-spec.md#4-3-api-계약)를 따릅니다.
