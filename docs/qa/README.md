이 디렉터리는 **수동 QA와 E2E 테스트 설계의 기준이 되는 화면·기능별 QA 케이스**를 담습니다. 유저 스토리([`2-user-stories.md`](../spec/2-user-stories.md))와 화면 스펙의 검수 기준([`3-1-client-spec.md`](../spec/3-1-client-spec.md))을 씨앗으로 삼아, 플랫폼별 [웹 계약](../spec/3-2-web-spec.md)을 함께 적용해 케이스를 작성합니다. 실제 코드와 기대 계약의 차이는 [추적 문서](../planning/client-tracking.md)에 남기며 관측된 코드만으로 기대 결과를 바꾸지 않습니다. 별도 유스케이스 문서는 만들지 않으며, 각 케이스가 US-x-y ID를 직접 참조합니다.

QA는 검수 절차·자동화 연결을 소유하고 제품 규칙·Jira 진행의 정본을 대신하지 않습니다. 구현·릴리스 증거는 추적 문서에서 연결합니다.

여러 문서에 걸치는 기능은 한 문서가 케이스를 소유하고 나머지는 참조 스텁을 둡니다(예: 신규 가입 초대 코드 다이얼로그 → `onboarding.md`).

## 케이스 표 읽는 법

각 케이스는 다음 컬럼으로 구성합니다.

| 컬럼      | 의미                                                                                                             |
| --------- | ---------------------------------------------------------------------------------------------------------------- |
| ID        | `{도메인}-{섹션}-{번호}` 형식의 고유 ID. 섹션 내 추가는 뒤 번호를 이어 붙이고, 삭제된 번호는 재사용하지 않습니다 |
| P         | 우선순위. 아래 기준 참고                                                                                         |
| 사전조건  | 케이스 실행 전 준비 상태(세션·로컬 데이터·서버 응답 등)                                                          |
| 절차      | 사용자가 수행하는 행동                                                                                           |
| 기대 결과 | 확인해야 하는 화면·데이터 동작                                                                                   |
| 자동화    | `✅ e2e {스펙 경로}` = 자동화됨, `◐` = 일부만 자동화, `수동` = 사람 확인 필요                                    |
| 근거      | 참조 유저 스토리(US-x-y)·스펙 섹션(§)                                                                            |

### 우선순위 기준

| P   | 기준                                                        | 릴리스 전             |
| --- | ----------------------------------------------------------- | --------------------- |
| P0  | 핵심 플레이 경로가 끊기거나 사용자 데이터가 손실되는 케이스 | 반드시 확인           |
| P1  | 주요 기능·에러 안내가 어긋나 사용성이 크게 떨어지는 케이스  | 시간이 허락하면 확인  |
| P2  | 엣지 케이스·표시 품질. 어긋나도 우회 가능한 케이스          | 회귀 의심 영역만 확인 |

### 크로스커팅 항목

| 항목 | 검수 수단·기준 |
| --- | --- |
| 브라우저 핵심 진입 | Pixel 5 전체 E2E, Desktop Chrome·iPhone 13은 `e2e/smoke/`. Safari 에뮬레이션 통과를 iOS 실기기 통과로 읽지 않음 |
| iOS Safari·키보드 | 최신 실기기에서 주소창·툴바 변화, 안전 영역, CTA·컴포저·마지막 메시지 가림, 이중 스크롤·러버밴드·위치 튐 확인 |
| 입력·스트리밍 | IME Enter 오전송, 전송 후 포커스, 잠금, 토큰·이미지 누적의 깜빡임·잔상·앵커 확인 |
| 모션·접근성 | 동작 줄이기에서 장식 모션 정지, 전환 중 입력 차단 없음. 키보드·포커스·오류 연결·상태 읽기 확인 |
| 다크 모드 | 비주얼 회귀의 대표 화면(채팅방·목록·상세·마이 회원), 나머지는 수동 검수 |
| 인앱 로그인 | 카카오톡·Instagram·Threads × iOS·Android 실기기. provider별 전환·자동 실패 시 수동 대체 경로는 AUTH-HANDOFF |

준비: API fixture의 정책값을 기대값으로 사용합니다. 홈 SSR과 브라우저 mock이 섞이지 않도록 Playwright 설정의 `API_BASE_URL`·서버 재사용 여부를 확인합니다. 실제 환경에서는 서버 응답과 화면을 비교합니다.

### ⚠️ 확인 필요

계약·구현의 미결 사항은 [클라이언트 추적](../planning/client-tracking.md#qa-확인-항목)이 소유합니다. QA에서는 관련 ID·검증 절차를 연결하며 현재 코드만으로 제품 기대값을 바꾸지 않습니다.

## 유지보수 규칙

- 화면 동작을 바꾸는 PR은 해당 도메인 QA 문서의 케이스를 함께 갱신합니다(추가·수정·삭제).
- E2E 스펙을 추가하면 대응 케이스의 자동화 컬럼을 갱신합니다.
- 실행 대상 커밋·환경·결과를 추적 문서 또는 연결된 실행 기록에 남깁니다. 자동화 열은 기존 테스트 연결이며 이번 통과·배포를 뜻하지 않습니다.
- `skip`은 코드에 테스트가 있어도 실행하지 않는 케이스입니다. 좋아요 재노출 케이스처럼 적용 보류 범위를 명시하고 일반 실행 케이스와 표를 분리합니다.
- 중복 케이스는 소유 문서로 통합하고 이전 ID → 유지 ID를 남깁니다. 분리한 중복 번호와 폐기한 ID는 재사용하지 않습니다.
