# QA 문서 작업 지침

이 지침은 이 디렉터리의 웹 QA 문서를 작성·수정·검증할 때 적용합니다. `CLAUDE.md`는 이 파일을 가리키는 상대경로 심볼릭 링크로 유지합니다.

## 작업 기준

- 수동 QA와 E2E 테스트 설계에 사용할 화면·기능별 케이스를 작성합니다. [유저 스토리](../spec/2-user-stories.md), [공통 Spec](../spec/3-1-client-spec.md), [웹 Spec](../spec/3-2-web-spec.md)의 관련 절을 먼저 읽습니다.
- 제품 규칙은 Spec, 작업 진행은 Jira를 따릅니다. QA에는 검수 절차와 자동화 연결을 기록하고 구현·릴리스 증거는 [추적 문서](../planning/client-tracking.md)에서 연결합니다.
- 코드와 계약이 다르면 차이와 관련 QA ID를 [확인 항목](../planning/client-tracking.md#qa-확인-항목)에 남깁니다. 관측된 코드만으로 기대 결과를 바꾸지 않습니다.
- 여러 문서에 걸치는 기능은 한 문서가 케이스를 소유하고 나머지는 참조만 둡니다. 신규 가입 초대 코드 다이얼로그는 `onboarding.md`가 소유합니다.

## 케이스 작성 규칙

- 컬럼은 `ID | P | 사전조건 | 절차 | 기대 결과 | 자동화 | 근거` 순서로 작성합니다.
- ID는 `{도메인}-{섹션}-{번호}` 형식으로 고유하게 부여합니다. 새 케이스는 해당 섹션의 마지막 번호 뒤에 추가하고 삭제·폐기한 번호는 재사용하지 않습니다.
- 사전조건에는 세션·로컬 데이터·서버 응답을, 절차에는 사용자 행동을, 기대 결과에는 확인할 화면·데이터 동작을 씁니다.
- 근거에는 `US-x-y` ID와 Spec 절을 직접 연결합니다. 별도 유스케이스 문서는 만들지 않습니다.
- 자동화는 `✅ e2e {스펙 경로}`(자동화됨), `◐`(일부 자동화), `수동`으로 표기합니다.

### 우선순위 기준

| P   | 기준                                                        | 릴리스 전             |
| --- | ----------------------------------------------------------- | --------------------- |
| P0  | 핵심 플레이 경로가 끊기거나 사용자 데이터가 손실되는 케이스 | 반드시 확인           |
| P1  | 주요 기능·에러 안내가 어긋나 사용성이 크게 떨어지는 케이스  | 시간이 허락하면 확인  |
| P2  | 엣지 케이스·표시 품질. 어긋나도 우회 가능한 케이스          | 회귀 의심 영역만 확인 |

## 유지보수 규칙

- 화면 동작을 바꾸는 PR은 해당 도메인 QA 문서의 케이스를 함께 갱신합니다(추가·수정·삭제).
- E2E 스펙을 추가하면 대응 케이스의 자동화 컬럼을 갱신합니다.
- `skip`은 코드에 테스트가 있어도 실행하지 않는 케이스입니다. 좋아요 재노출 케이스처럼 적용 보류 범위를 명시하고 일반 실행 케이스와 표를 분리합니다.
- 중복 케이스는 소유 문서로 통합하고 이전 ID → 유지 ID를 남깁니다. 분리한 중복 번호와 폐기한 ID는 재사용하지 않습니다.

## 검증과 결과 기록

- 자동화 검증은 API fixture의 정책값을 기대값으로 사용합니다. 홈 SSR과 브라우저 mock이 섞이지 않도록 Playwright 설정의 `API_BASE_URL`·서버 재사용 여부를 확인합니다. 실제 환경에서는 서버 응답과 화면을 비교합니다.
- 문서 변경 후 링크·앵커·QA ID 중복과 자동화 경로를 확인하고 하네스에서 `git diff --check`를 실행합니다.
- 실행 대상 커밋·환경·결과를 추적 문서 또는 연결된 실행 기록에 남깁니다. 자동화 열은 기존 테스트 연결이며 이번 통과·배포를 뜻하지 않습니다. 문서 검사와 제품 실행 검증을 구분합니다.
