# 3-1-CLIENT

이 문서는 **마냑 서비스의 모든 클라이언트(웹·모바일)가 공통으로 구현하고 QA가 검수해야 할 계약**을 정의합니다. 화면, 사용자 흐름, 화면 상태, API 연동, 오류 처리, 검수 기준을 다룹니다.

각 항목은 조건, 입력, 출력, 화면 상태, 예외 처리, 완료 기준을 구체값으로 적습니다. 플랫폼별 기술 환경·라우팅·구현 세부는 플랫폼 문서([`3-2-web-app.md`](./3-2-web-app.md)·[`3-3-android-app.md`](./3-3-android-app.md))가 소유합니다.

```text
§3-1-1  문서 목적·범위와 관련 문서
§3-1-2  핵심 아키텍처
§3-1-3  화면별 스펙
§3-1-4  스토리 생성 퍼널
§3-1-5  채팅 플레이와 SSE 스트리밍
§3-1-6  게스트 데이터 모델
§3-1-7  API 연동·에러 처리 계약
§3-1-8  입력·폼 검증 규칙
§3-1-9  MVP 제외 범위와 스펙-구현 간극
```

### 읽는 순서

- **처음 보는 사람** — §3-1-1(경계)과 §3-1-2(아키텍처 큰 그림)를 먼저 보고, §3-1-3 도입의 흐름 인덱스로 전체 표면을 잡습니다.
- **구현자** — 담당 화면의 §3-1-3 스펙 → 관련 상세 절(§3-1-4~§3-1-8) → §3-1-7 API 연동·에러 처리 순서로 보고, 담당 플랫폼 문서([`3-2-web-app.md`](./3-2-web-app.md)·[`3-3-android-app.md`](./3-3-android-app.md))로 구현 세부를 확인합니다. 각 결정 지점의 "결정 기록"(배경·대안·영향)이 왜 이 계약인지의 근거입니다.
- **리뷰·QA** — 각 화면·절의 검수 기준과 §3-1-9 간극 표(G2~G7), 플랫폼 문서의 테스트 절에서 시작해 본문을 역참조합니다.

### 플랫폼 표기 원칙

이 문서는 웹 구현을 기준으로 검증된 계약을 서술하므로, 본문에 웹 메커니즘(경로·`localStorage`·`replace`/`push` 히스토리·`beforeunload` 등)이 예시로 등장합니다. 이때 **계약(무엇을 보장해야 하는가)은 플랫폼 공통**이고, 그 메커니즘 자체는 웹 구현([`3-2-web-app.md`](./3-2-web-app.md))의 소유입니다. 모바일 앱은 같은 계약을 플랫폼 수단(내비게이션 스택·로컬 저장소·라이프사이클 콜백 등)으로 충족하며, 대응 규칙은 [`3-3-android-app.md`](./3-3-android-app.md)가 정의합니다.

## 3-1-1. 문서 목적·범위와 관련 문서

### 목적

이 문서는 마냑의 모든 클라이언트(웹·안드로이드) 구현자와 QA가 화면, 사용자 흐름, API 연동, 검수 기준을 판단하는 기준입니다. 각 플랫폼은 이 문서의 계약을 기준으로 구현하고, QA는 이 문서와 담당 플랫폼 문서를 함께 기준으로 검수합니다.

### 범위

플랫폼과 무관하게 보장해야 하는 제품·클라이언트 계약만 소유합니다.

- 화면의 목적·구성과 사용자에게 보여야 하는 정보, 화면 상태(로딩·빈 상태·오류·성공)
- 사용자 흐름과 화면 전환의 의도, 뒤로가기 시 보장해야 하는 결과
- 스토리 생성 퍼널·채팅 SSE 스트리밍·로그인·이관 흐름
- 게스트(익명) 데이터의 논리적 구조와 정리 규칙
- API 호출 시점과 응답별 사용자 처리(헤더, 상태 코드 분기, 에러 처리)
- 입력·폼 검증, 플랫폼 공통 검수 기준, 보안·개인정보 관점의 공통 보장

MVP 본문은 로그인 없는 전원 게스트 기준입니다. Phase 1 로그인·마이 페이지·회원 서재·이프 잔액과 출석·체험 한도 처리는 `Phase 1 · 구현`, 소모량 사전 고지는 `Phase 1 · 부분 구현`입니다(라벨은 웹 구현 상태만 뜻하며, 공통 계약 상태는 아래 상태 정본 표가 소유합니다). 일반 제작·스토리 수정 흐름은 `Phase 1 · 계획` 라벨로 본문에 포함됩니다(FE-SCREEN-008·009, 웹 토큰 세션은 [3-2-web-app.md §3-2-4](./3-2-web-app.md#3-2-4-bff-프록시토큰-세션)).

### 제외 범위

- 웹 라우팅·URL·레이아웃·공통 셸, BFF 프록시·토큰 세션, 브라우저 지원·반응형, 웹 관측 배선, 웹 테스트·Definition of Done (담당: [`3-2-web-app.md`](./3-2-web-app.md))
- 안드로이드 내비게이션·로컬 저장소 기술·인증 세션·디바이스 지원, Android 관측 배선·테스트 (담당: [`3-3-android-app.md`](./3-3-android-app.md))
- 백엔드 내부 구현과 API 상세 스키마 (담당: [`4-backend.md`](./4-backend.md))
- AI 요청·응답 계약과 프롬프트 (담당: [`5-ai-server.md`](./5-ai-server.md))
- 이벤트 카탈로그, 식별자 정책, 지표 (원천: [`6-analytics.md`](./6-analytics.md))

- 코드 구조, 컴포넌트 래퍼 목록, 환경 변수, 배포 런북 (각 플랫폼 개발 문서·README가 소유)

### 작성 원칙

- 구현된 동작을 기준으로 씁니다. 배경·유저스토리 문서와 코드가 다르면 코드를 기준으로 하고 차이는 [§3-1-9](#3-1-9-mvp-제외-범위와-스펙-구현-간극)에 기록합니다.
- `적절히`, `필요 시` 같은 모호한 표현 대신 상수와 조건을 적습니다.
- 이벤트·API 스키마·식별자는 원천 문서를 교차 참조하고 중복 서술하지 않습니다.
- 화면과 흐름에 US ID와 e2e 스펙을 연결합니다.
- 갈림길이 있었던 결정은 해당 결정 지점에 "결정 기록"(배경·대안·영향)으로 근거를 남깁니다([`4-backend.md`](./4-backend.md)와 동일한 형식).
- API 경로는 `/api/v1` prefix를 생략해 표기합니다. 백엔드 호출 창구는 플랫폼 소유입니다 — 웹에서는 실제 요청이 BFF 프록시(`/api/*`)를 거쳐 백엔드로 전달되고([3-2-web-app.md §3-2-4](./3-2-web-app.md#3-2-4-bff-프록시토큰-세션)), 앱의 호출 창구는 [`3-3-android-app.md §3-3-4`](./3-3-android-app.md#3-3-4-api-연동인증-세션--작성-예정)에서 확정합니다.

### 구현 상태 라벨과 상태 정본

이 문서는 항목의 상태를 서로 **독립인 세 축**으로 관리합니다. 세 축의 용어·판정 기준과 아래 상태 정본 표의 값은 이 문서가 소유하며, 플랫폼 문서([`3-3-android-app.md §3-3-3`](./3-3-android-app.md) 매트릭스 포함)는 이 값을 재해석 없이 참조합니다.

- **로드맵 Phase** — [`roadmap.md`](../planning/roadmap.md)가 기능을 배정한 단계입니다(`MVP`(= Phase 0)·`Phase 1`·`Phase 2`).
- **공통 계약 상태** — 플랫폼과 무관한 제품 계약의 상태입니다. `확정`(계약이 합의되어 본문·검수 기준이 규범으로 유효) / `방향 합의`(방향만 합의, 세부 계약은 확정 전) / `미정`(계약 자체가 결정 전) 3종입니다.
- **웹 구현 상태** — 기준 코드 `manyak-web`의 실제 구현 상태입니다. `구현` / `부분 구현`(하위 기능의 상태가 갈림) / `미구현` 3종입니다.

**본문 라벨 `{로드맵 Phase} · {구현 상태}`는 로드맵 Phase와 웹 구현 상태만 인코딩하는 관례 단축형입니다**(`구현`·`부분 구현`·`계획`(= 미구현)). `MVP`는 `Phase 0 · 구현`의 단축형이고, 라벨이 없는 항목은 모두 `MVP`입니다. **공통 계약 상태는 라벨로 표현하지 않습니다** — 라벨이 `계획`이어도 공통 계약은 이미 `확정`일 수 있으므로(예: 채팅 이미지·게스트 본 엔딩 합산은 계약 확정 + 웹 미구현), 계약 상태는 라벨에서 추론하지 말고 반드시 아래 상태 정본 표에서 읽습니다.

웹 구현 상태 축은 기준 코드 `manyak-web` 기준이며 **Android 구현 완료를 뜻하지 않습니다** — 안드로이드 앱은 Phase 2 범위로 현재 전 화면 미착수이고, 화면·흐름별 Android 목표 범위와 현재 상태는 [`3-3-android-app.md §3-3-3`](./3-3-android-app.md) 매트릭스가 소유합니다. 서버 구현 상태는 [`4-backend.md §4-1`](./4-backend.md)의 라벨이 정본입니다.

#### 상태 정본 표

화면·흐름과 주요 하위 기능의 정본값입니다. **세 축 모두 한 셀에 정의된 값 하나만 쓰고**(로드맵 Phase = `MVP`·`Phase 1`·`Phase 2` 중 하나), Phase나 상태가 갈리는 기능은 행을 나눕니다. **흐름(FLOW-001~009)은 이 표에 행을 두지 않습니다** — 여러 화면에 걸친 흐름의 Phase·계약·구현 상태를 단일값으로 합성하면 정의되지 않은 파생값이 생기므로, 흐름을 볼 때는 그 흐름을 구성하는 화면 행을 각각 확인합니다(구성 화면 매핑은 [§3-1-3](#3-1-3-화면별-스펙) 흐름 인덱스). ### FE-SCREEN-001. 홈 — 오리지널 스토리 목록

| 항목     | 값                                             |
| -------- | ---------------------------------------------- |
| 경로     | `/`                                            |
| 관련 API | `GET /stories/originals`                       |
| 관련 US  | US-2-2, US-2-7·2-8 `Phase 1 · 구현`            |

**목적** — 마냑 공식 계정의 오리지널 스토리를 탐색하고 상세로 진입합니다. 내가 만든 스토리 관리와 제작 진입은 FE-SCREEN-013 제작 탭이 담당합니다(KNK-988).

**진입 조건** — 앱의 기본 진입 화면입니다. 최초 방문자는 온보딩 페이지(FE-SCREEN-007)로 이동합니다.

**화면 구성** — 별도 상단 패딩 없이 시작하는 굵은 "오리지널 스토리" 제목과 2열 카드 그리드로 구성합니다. 카드는 3:4 썸네일(없으면 placeholder), 좌상단 ORIGINAL 태그, 우하단 누적 턴 수 뱃지, 제목 1줄, 제작자 닉네임(응답 `author.nickname` 앞에 `@`를 붙여 "@마냑") 1줄을 표시합니다. `@`는 핸들임을 드러내는 표기이므로 카드에만 붙이고, 상세의 제작자 값에는 붙이지 않습니다(KNK-1079). 카드의 모든 텍스트가 1줄 고정이라 제목 길이와 무관하게 카드 높이가 같고, 같은 행의 제작자 줄이 같은 높이에 놓입니다. 내 스토리 목록·이어 만들기 배너·생성 버튼은 홈에 표시하지 않습니다.

**ORIGINAL 태그**는 스크롤로 섹션 제목이 화면 밖으로 밀려도 공식 스토리임이 카드 자체로 드러나게 하는 표시입니다(KNK-983). 표지가 비치는 반투명이라 그림을 가리지 않으며, 우하단 턴 수 뱃지와 같은 질감(반투명 + 블러)으로 통일합니다. 제작 탭의 내 스토리 카드에는 붙이지 않습니다. 웹의 태그 이미지 정본과 색 변형 교체 방법은 [`3-2-web-app.md §3-2-3`](./3-2-web-app.md#3-2-3-라우팅레이아웃공통-셸)이 소유합니다.

**결정 기록 — 오리지널 카드 메타는 두 줄** (2026-08-24, KNK-983)

- **배경.** 오리지널 카드에 "얼마나 플레이됐는지"를 보여 주는 셋째 줄을 검토했습니다. 그러나 `StorySummaryResponse`에는 채팅 수 필드가 없고, 있는 것은 누적 턴 수(`turnCount`)와 좋아요 수(`likeCount`)뿐입니다.
- **결정.** 셋째 줄을 두지 않고 **제목·제작자 두 줄로 확정**합니다. 턴 수를 셋째 줄로 쓰는 안은 구현까지 갔다가 되돌렸습니다 — 같은 값이 이미 썸네일 우하단 뱃지로 보여 한 카드에 두 번 노출되기 때문입니다. "채팅 횟수"라는 새 용어를 만드는 안은 용어 정본의 "턴"과 어긋나 채택하지 않았습니다([`0-glossary.md §0-3-3`](./0-glossary.md#0-3-3-플레이채팅-단위)).
- **영향.** 플레이 지표를 별도 줄로 보여 주려면 서버에 채팅 수 필드 신설이 선행해야 합니다.

**데이터 소스** — 인증 없이 `GET /stories/originals`를 조회하며 게스트·회원 모두 서버 등록순을 그대로 유지합니다. 공식 계정이 설정되지 않은 환경은 빈 목록입니다.

| 관련 API | `POST /stories/batch`(게스트), `GET /users/me/stories`(회원)                |
| 관련 US  | US-2-1·2-3·2-4·2-6·2-8 `Phase 1 · 구현`                                    |

**목적** — 내가 만든 스토리를 확인·관리하고 새 제작 또는 진행 중 제작을 이어갑니다.

**진입 조건** — 하단 "제작" 탭으로 진입합니다. 최초 방문자의 온보딩 게이트는 다른 메인 탭과 동일하게 적용합니다. 웹 정식 URL은 `/studio`이고 생성 퍼널은 `/studio/story/simple`이며, 기존 `/create` 계열 URL의 호환 규칙은 [3-2-web-app.md §3-2-3](./3-2-web-app.md#3-2-3-라우팅레이아웃공통-셸)이 소유합니다(KNK-994).

**화면 구성** — 제작 헤더 바로 아래에서 별도 섹션 제목 없이 시작하는 내 스토리 1열 가로 카드 목록과, 미정리 제작 레코드가 있을 때의 이어 만들기 배너로 구성합니다. 스토리가 하나 이상이면 콘텐츠 오른쪽 아래에 primary FAB를 표시하고, 빈 상태·로딩·에러에서는 숨깁니다. FAB는 스크롤 전에는 plus 아이콘과 "만들기"를 함께 표시하고 스크롤 후에는 아이콘만 남기며, 접근 가능한 이름은 "스토리 만들기"입니다. 마우스 호버에서는 배경 불투명도를 낮추지 않고 3% 확대해 primary 동작을 강조하며, 모션 감소 환경에서는 확대하지 않습니다(KNK-994).

내 스토리 목록은 콘텐츠 폭을 모두 사용하고, 각 카드 행이 가로 16px·세로 8px 내부 패딩과 16px 열 간격을 소유합니다. 카드 전체 링크는 행의 패딩 영역까지 덮습니다. 카드의 왼쪽에는 폭 128px 고정 3:4 썸네일(없으면 placeholder)을 두고, 오른쪽 정보 영역은 썸네일 높이를 최소 높이로 사용합니다. 정보 영역 위쪽에는 제목 최대 2줄과 첫 줄 오른쪽의 옵션 버튼, 한 줄 소개 최대 2줄, 한 줄 장르 배지(초과 시 `+N`)를 순서대로 표시합니다. 아래쪽에는 누적 턴 수와 제작일(`createdAt`의 KST 기준 `YYYY-MM-DD` — [§3-1-7 날짜 표시 기준](#날짜-표시-기준))을 오른쪽 정렬합니다. 옵션 버튼은 공용 `icon-xs` 변형(현재 24×24px, 내부 더보기 아이콘 16px)을 사용합니다. 오리지널 카드는 기존 2열 카드와 ORIGINAL 태그를 유지합니다. 카드 전환의 이유는 표지를 첫 식별 단서로 충분히 크게 유지하면서 제목·소개와 메타 정보를 잘리지 않게 읽도록 하기 위함이며, 각 플랫폼의 기존 아이콘 자산과 시맨틱 글자색은 유지합니다(KNK-1012·1043, 2026-08-30 결정). 로딩 스켈레톤도 같은 전체 폭 행, 가로 16px·세로 8px 패딩, 128px 표지, 제목·소개·장르·하단 메타 순서를 사용해 실제 목록으로 바뀔 때 위치가 튀지 않게 합니다(KNK-1043).

**데이터 소스** — 게스트는 로컬 저장소의 스토리 ID를 `POST /stories/batch`로 조회해 로컬 저장 순서(최신순)로 재정렬하고, 회원은 `GET /users/me/stories`의 서버 목록을 사용합니다([§3-1-6](#3-1-6-게스트-데이터-모델)). 게스트 목록은 최대 100개를 한 번에 조회합니다.

**사용자 액션**

| 액션      | 트리거                              | 결과                      |
| --------- | ----------------------------------- | ------------------------- |
| 상세 이동 | 카드 탭                             | `/stories/[id]`로 이동    |
| 생성 시작 | FAB 또는 빈 상태 CTA                | `/studio/story/simple`로 이동    |

| 삭제      | 내가 만든 카드의 옵션 메뉴 → 확인   | 낙관적으로 카드를 제거하고 현재 `/studio` 화면 유지 |

스토리 삭제는 내가 만든 카드의 옵션 메뉴에서만 제공합니다. 상세와 오리지널 카드에는 삭제 메뉴를 표시하지 않으며, 낙관적 삭제 규칙은 [§3-1-6](#3-1-6-게스트-데이터-모델)을 따릅니다(KNK-1012).

**검수 기준**

- 제작 탭에는 별도 섹션 제목을 표시하지 않고, 제작 헤더 바로 아래에 내가 만든 스토리만 표시해야 합니다. 카드 행과 카드 전체 링크는 목록의 전체 폭을 사용해야 합니다. (US-2-1·2-8, KNK-988·1043, e2e `stories/story-list`)
- 빈 상태·에러·로딩·회원/게스트 목록과 상세 이동이 기존 목록 계약대로 동작해야 합니다. (US-2-1·2-2·2-6)
- 목록이 있으면 오른쪽 아래 FAB를 표시하고, 빈 상태에서는 이를 숨긴 채 기존 빈 상태 CTA만 표시해야 합니다. 두 CTA는 `/studio/story/simple`로 이동하고, 이어 만들기 배너는 이 화면에서만 표시되어야 합니다. (US-2-3, KNK-988)
- FAB는 마우스 호버 중에도 primary 배경 불투명도를 유지하면서 3% 확대하고, 모션 감소 환경에서는 확대하지 않아야 합니다. (KNK-994)
- 스토리 삭제 성공 후 현재 `/studio`에서 삭제된 카드가 사라져야 합니다. (US-2-4, KNK-1012)

**검수 기준**

- 제목·소개·설명·시작 설정과 턴 수·생성일을 표시해야 합니다. (US-4-1, e2e `stories/story-detail`)
- 본문 제목이 헤더 아래로 사라지면 응답 속도와 무관하게 헤더 제목을 표시해야 합니다. (US-4-1, e2e `stories/story-detail`, KNK-1039)
- `thumbnailUrl`이 있으면 썸네일 이미지가, 없으면 placeholder가 표시돼야 합니다. 썸네일을 누르면 이미지 뷰어가 열리고 X·뒤로가기로 페이지 이동 없이 닫혀야 합니다. (US-4-1)
- 시작 설정이 여러 개면 Select로 상황을 바꿀 수 있고, 선택한 상황 설명이 표시돼야 합니다. (US-4-1)

**진입점** — 하단 탭 "마이"(`/my`). 게스트는 로그인 버튼(→ `/login`)을, 회원은 프로필·로그아웃·회원 탈퇴를 표시합니다. 게스트/회원 판정은 [3-2-web-app.md §3-2-4](./3-2-web-app.md#3-2-4-bff-프록시토큰-세션) 토큰 세션의 모드 판정 소스를 따릅니다.

**마이 페이지 회원 상태 구성** — 게스트는 로그인 버튼을 표시합니다. 회원은 닉네임·프로필 이미지·연동된 계정(아래 계정 연동 문단)·이프 잔액·친구 초대·로그아웃·회원 탈퇴를 표시합니다. 이프 카드에는 잔액 오른쪽에 이프 충전(`/my/credits`)으로 가는 강조색 버튼 "충전" 하나만 둡니다 — 이프를 얻는 수단은 모두 이프 충전 화면이 소유하므로 마이에는 그 화면으로 가는 입구만 남깁니다(KNK-1092). 출석 체크 버튼도 이때 이프 충전으로 옮겼습니다. 친구 초대 메뉴는 라벨 아래에 작은 강조색 보조 문구 "하고 N 이프 받기"를 붙여 보상을 라벨과 이어 읽게 합니다(N은 서버 정책의 초대 보상 — [§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시)). 계정 섹션은 기본 전경색의 로그아웃 아래에 위험색 회원 탈퇴를 둬 비가역 동작만 강조합니다. 화면 섹션의 테마 변경과 기타 섹션의 피드백·서비스 안내(FE-SCREEN-011)는 게스트와 회원 모두 사용할 수 있습니다.

**이프 충전** (`Phase 2 · 구현`, KNK-1081 — 앱 KNK-1082·웹 KNK-1083, 화면 개편 KNK-1091 — 웹 KNK-1092) — 마이 이프 카드의 "충전" 버튼으로 `/my/credits`에 진입합니다. 게스트 진입은 친구 초대와 같이 `/login`으로 보냅니다. 화면 성격이 내역 열람에서 충전으로 넓어졌지만 **경로는 그대로 둡니다** — 같은 자리의 같은 관심사이고, 이미 배포된 링크를 깨지 않기 위해서입니다.

- **화면 골격** — 뒤로가기 헤더("이프 충전") 아래에 잔액 상자와 탭 줄을 **셸에 고정**하고 탭 패널만 스크롤합니다. 잔액은 어느 탭에서 무엇을 하든 계속 보여야 하는 값이라 스크롤을 따라 사라지지 않습니다. 탭은 무료 충전 · 내역 두 개이고 기본값은 무료 충전이며, 스토리 생성 퍼널(FE-SCREEN-002)과 같은 밑줄 탭 모양을 씁니다. 선택한 탭은 URL에 남기지 않습니다 — 진입 경로가 마이의 "충전" 하나뿐이라 탭 자체를 공유·북마크할 일이 없습니다.
- **잔액 박스** — 화면 최상단에 중립 배경·카드 모서리·안쪽 여백 16px 상자를 두고, "내 이프" 라벨을 위에, 잔액을 그 아래 오른쪽에 한 단계 큰 글자와 천 단위 콤마로 표시합니다. 값의 정본은 마이와 같은 `GET /auth/me`의 `creditBalance`이며 진입할 때 다시 읽습니다. **내역 항목의 금액을 합산해 잔액을 만들지 않습니다** — 구매는 내역에서 제외되고 만료 회수는 실제 만료보다 늦게 기록돼 합계가 잔액과 어긋납니다([`4-backend.md §4-3-7`](./4-backend.md) 이용내역 조회).
- **무료 충전 탭** — 결제 없이 이프를 얻는 수단만 모읍니다. 위에는 중립 배경 상자에 "매일 출석하고 / 매일 N 이프 받으세요"를 두 줄 제목으로 두고, 그 아래 가로 전폭 강조색 버튼 "출석 하기"를 둡니다. 버튼 아래에는 작은 보조색 문구 "매일 오전 00시에 초기화돼요"와 "보상으로 받은 이프는 적립일로부터 30일 동안 사용할 수 있어요"를 오른쪽 정렬로 붙입니다. 상자에서 32px 아래에는 마이와 **같은** 친구 초대 메뉴 줄(라벨 + 강조색 보조 문구)을 둬 무료 수단 두 가지를 한 화면에 모읍니다. 제목의 N은 서버 정책의 출석 보상이며 출처는 [§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시)입니다(KNK-1095). 출시 이벤트처럼 값을 올리는 운영은 서버 정책만 바꾸면 화면이 따라가므로 이벤트 전용 문구를 따로 두지 않습니다.
- **출석 체크** — 마이에 있던 계약을 화면만 바꿔 그대로 옮겼습니다. 오늘 이미 출석했으면(`attendedToday: true`) 진입 시점부터 "출석 완료" 비활성이고, 요청 중에는 버튼 문구 자리에 스피너를 띄워 중복 요청을 막습니다. 성공(`rewarded: true`)은 적립 안내 토스트와 함께 `GET /auth/me`를 무효화해 잔액 상자를 갱신하고, 200 `rewarded: false`(서버 중복 판정)는 적립 없이 "오늘은 이미 출석 체크했어요"로 안내하며, 실패는 실패 토스트 후 버튼을 다시 활성화합니다.
- **내역 탭** — 내가 쓰거나 받은 이프를 최신순으로 나열합니다. `GET /users/me/credits/transactions`를 기본값(`type=ALL`)으로 호출하며, 분류 필터 UI는 두지 않습니다 — 지금은 전체 목록만 보여줍니다.
- **항목 구성** — 한 항목은 사유 라벨·대상 스토리 제목·날짜와 오른쪽 금액입니다. 서버는 `reason` enum 원문만 내려주고 **한국어 라벨은 클라이언트가 붙입니다**(문구 변경에 서버 배포를 걸지 않기 위해서입니다 — 402 `code` 계약과 같은 원칙).

| `reason` | 라벨 |
| --- | --- |
| `SIGNUP_REWARD` | 가입 보상 |
| `ATTENDANCE_REWARD` | 출석 체크 보상 |
| `INVITE_REWARD` | 친구 초대 보상 |
| `REFUND` | 사용 취소 |
| `STORY_CREATION` | 스토리 완성 |
| `CHAT_TURN` | 채팅 전송 |
| `EXPIRE` | 기간 만료 |

- **금액 표기** — 부호는 `type`이 정합니다. `EARN`은 `+`, `SPEND`·`EXPIRE`는 `-`를 붙이고 값은 절대값에 천 단위 콤마를 씁니다. 응답의 `amount`는 원장 부호가 실린 값(소모·소멸은 음수)이지만 그 부호를 그대로 옮기지 않고 절대값을 취합니다 — 표시 규칙을 분류 하나로 모읍니다.
- **제목·날짜** — `title`이 있으면 라벨 아래 한 줄로 표시하고, 소모·사용 취소인데 `title`이 없으면(삭제된 스토리) "삭제된 스토리"로 대체합니다. 보상·소멸 항목은 제목 줄을 그리지 않습니다. 날짜는 `createdAt`(KST 기준 YYYY-MM-DD — [§3-1-7 날짜 표시 기준](#날짜-표시-기준))이며, `expiresAt`이 있으면 "YYYY-MM-DD 만료"를 함께 표시합니다 — 획득은 만료 예정일, 소멸은 회수된 로트의 실제 만료일입니다. **소멸 항목의 `createdAt`을 만료일로 읽지 않습니다**(지연 정리라 실제 만료보다 늦습니다).
- **페이징** — 목록 끝에 닿으면 응답의 `nextCursor`를 그대로 실어 다음 페이지를 이어 붙입니다. 커서는 불투명 문자열이라 파싱하거나 조립하지 않고 받은 값을 되돌려 줍니다. `nextCursor`가 없으면 마지막 페이지입니다.
- **화면 상태** — 첫 조회 중에는 잔액 상자와 내역 목록 자리에 각각 골격을 표시합니다. 항목이 하나도 없으면 "아직 이프 내역이 없어요"를 표시하고, 첫 조회 실패는 "이프 내역을 불러오지 못했어요"와 다시 시도하기를 목록 자리에 둡니다(친구 초대 코드 카드와 같은 처리). 다음 페이지 조회 실패는 **이미 그린 목록을 지우지 않고** 재시도만 제공합니다.

**테마 변경** — 화면 섹션의 테마 변경 메뉴는 탭할 때마다 시스템 설정 → 라이트 모드 → 다크 모드 순으로 순환합니다. 왼쪽 아이콘(모니터·해·달)과 오른쪽 현재 값 문구가 함께 바뀌고 테마는 즉시 적용됩니다. 선택값은 기기 단위로 저장됩니다.

**친구 초대** (`Phase 1 · 구현`, KNK-567) — 마이의 친구 초대 메뉴는 `/my/invite`로 이동하며, 게스트 진입 시 `/login`으로 보냅니다.

- **보상 안내** — 화면 상단에는 "친구가 내 초대 코드를 등록하면 모두 N 이프를 받아요"를 표시합니다(N은 서버 정책의 `inviteReward` — [§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시), KNK-1045·1095).
- **초대 코드 카드** — `GET /users/me/invite`로 내 코드와 월 보상 횟수를 조회합니다. 코드는 불필요한 최소 높이 없이 압축된 별도 카드에 표시하고, 기본 크기의 코드 복사와 카카오톡 공유 버튼을 나란히 둡니다. 카카오톡 공유가 불가능한 상태면 공유 버튼을 비활성화합니다(판정 수단은 플랫폼 소유 — 웹: 카카오 JS SDK 키 부재·초기화 전 / 앱: 공유 방식·SDK 선택이 미정이라 판정 기준도 [`3-3-android-app.md`](./3-3-android-app.md)에서 결정 필요).
- **코드 복사·공유** — 코드 복사는 초대 코드 문자열만 클립보드에 저장합니다. 카카오 메시지 제목은 "초대 코드 등록하고 N 이프 받기 🎁"(N은 서버 정책의 초대 보상)이며, 본문에는 초대 코드를 싣고 버튼은 서비스 홈으로 이동합니다.
- **코드 입력** — 입력값을 trim·자동 대문자 변환한 뒤 `POST /users/me/invite/redeem`으로 제출합니다. 빈 값은 "코드를 입력해주세요", 404는 "코드를 다시 확인해주세요", 409 `INVITE_SELF_CODE`는 "내 코드는 입력할 수 없어요", 409 `INVITE_ALREADY_REDEEMED`는 "이미 초대 코드를 입력했어요"로 안내합니다. 성공 시 "친구 초대 보상으로 N 이프를 받았어요" 토스트를 표시합니다.
- **등록 중 상태** — 입력창과 등록 버튼을 비활성화하고 버튼 문구 공간을 유지한 중앙 스피너를 표시합니다. 신규 가입 온보딩에서는 등록·"닫기" 버튼을 모두 잠급니다.
- **이용 안내** — 초대 보상은 월 최대 10회이며 매월 1일(한국 시간) 초기화되고, 초대 코드는 계정당 한 번 입력할 수 있으며, 보상 이프는 적립일부터 30일간 유효함을 안내합니다.

**소모량 사전 고지** `Phase 1 · 부분 구현` (US-10-3) — 하위 항목별 웹 구현 상태가 갈립니다. 정책 수치의 정본은 [`4-backend.md §4-3-7`](./4-backend.md)입니다.

- **서비스 안내의 정책 수치 고지 — 구현.** 서비스 안내(FE-SCREEN-011)가 이프 차감 기준(스토리 완성 200, 채팅 전송·재생성 20, 스토리라인 무료)과 게스트 체험 한도를 고지합니다.
- **각 소모 지점의 사전 고지 — 부분 구현.** 스토리 완성 CTA 위에는 `스토리 완성 비용`과 `N 이프`(`storyCreationCost`)를 표시하고, 채팅 입력 컴포저의 전송 버튼 왼쪽에는 회원에게만 `N 이프`(`chatTurnCost`) 비용을 표시합니다. 두 수치 모두 서버 정책을 렌더합니다([§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시), KNK-1045·1068·1095). 게스트는 이프가 아니라 모든 채팅방 합산 5회 체험 한도를 사용하므로 이 비용 문구를 표시하지 않습니다. 스토리라인 남은 횟수와 응답 재생성 버튼 주변의 사전 고지는 아직 미구현(`계획`)입니다.

**이프 부족·체험 한도 처리** `Phase 1 · 구현` (KNK-1045) — 클라이언트는 게스트 누적 사용량을 먼저 확인해 한도 도달 요청을 보내지 않습니다. 로컬 카운터가 없거나 우회돼도 서버 402를 최종 판정으로 처리합니다.

- **회원(잔액 부족)** — 현재 화면에 "이프가 부족해요" 오류 토스트만 표시합니다. 별도 다이얼로그·보상 CTA·화면 이동은 없습니다. 스토리 완성·채팅 턴처럼 실제 이프를 소모하는 요청에만 적용하며, 무료인 채팅방 생성(`POST /chats`)은 잔액과 관계없이 진행합니다. (US-10-4)
- **게스트(체험 한도 소진)** — 제목 "게스트 체험 한도를 모두 사용했어요"와 기존 한도 설명을 담은 모달 바텀 시트를 표시합니다. 설명 아래 32px 뒤에 카카오·Google 로그인 버튼을 8px 간격으로 세로 배치하고, Google 버튼과 로그인 약관 고지는 16px 간격을 둡니다. 로그인 진행 중에는 닫기를 막고, 바깥 탭·ESC로 닫을 수 있습니다. (US-10-5) **앱 비적용** — 앱 사용자는 전원 회원이라 게스트 분기가 없습니다([`3-3-android-app.md §3-3-1`](./3-3-android-app.md)).
- **상태 복구** — 스토리라인 402는 키워드 단계, 스토리 완성 402는 추가 정보 단계의 입력·선택을 유지합니다. 채팅 턴 402는 실패한 낙관적 사용자 버블을 제거하고 기존 대화는 유지합니다.

**화면 구성·동작** (`Phase 1 · 구현`) — `/login`은 카카오·Google 로그인 버튼을 세로(column)로 두고(카카오가 위 — 아래 카카오 로그인 버튼 문단), 이관 안내는 중앙 로그인 콘텐츠에, 약관 동의 고지는 화면 최하단에 표시합니다:

- **이관 1회 안내** — "계정마다 처음 로그인할 때 / 한 번만 이 기기의 스토리와 채팅을 그 계정에 저장해요"를 두 줄로 표시합니다. 게스트에게만 실질적 의미가 있으나 `/login`은 로그인 전 화면이므로 상시 노출합니다. 근거는 이관 1회 잠금 계약([`4-backend.md §4-3-5`](./4-backend.md) B15 — 최초 성공 이관 시 `users.migrated_at`을 기록해 이후 호출은 `migrationClosed: true`로 닫힘)입니다.
- **약관 동의 고지** — 로그인 화면의 중앙 콘텐츠와 분리된 화면 최하단에 "로그인하면 <u>서비스 이용약관</u>과 <u>개인정보 처리방침</u>에 / 동의하는 것으로 간주해요"를 두 줄로 표시하고, 밑줄 링크로 각각 `/terms`·`/privacy`(FE-SCREEN-010)를 **새 브라우저 탭**에서 엽니다. 별도 동의 체크박스는 없으며 로그인 버튼 클릭을 동의로 간주합니다(묵시적 동의). 외부 로그인 랜딩과 게스트 한도 바텀 시트에서도 같은 문구·링크명·새 탭 동작을 사용합니다(KNK-1037).

**카카오 로그인 버튼** (`Phase 1 · 구현`, KNK-721·KNK-728) — Google 버튼 위에 카카오 로그인 버튼("카카오로 시작하기")을 세로로 둡니다. 두 버튼은 같은 공통 시작 함수를 provider 인자만 달리해 호출하며, 각 플랫폼 안에서 로그인 성공 이후 처리는 provider와 무관하게 동일합니다. 웹은 토큰 보관·자동 마이그레이션·완료 피드백·신규 가입 온보딩을, Android는 토큰 보관·회원 그래프 전환·신규 가입 초대 코드 안내를 수행합니다. 버튼 시각 사양은 카카오 디자인 가이드를 따릅니다.

- **계정 연동 정적 안내** — Google과 Kakao는 처음 로그인할 때 별개 계정이 될 수 있으므로([`4-backend.md §4-5`](./4-backend.md) 결정 기록), 버튼 아래에 먼저 하나의 소셜 계정으로 로그인한 뒤 다른 계정을 연동하도록 안내합니다. 문구는 모든 플랫폼이 동일하게 쓰며 **이 문서가 정본을 소유합니다** — "소셜 계정 하나로 먼저 로그인한 뒤 다른 계정을 연동하면, / 어느 계정으로 로그인해도 똑같이 이용할 수 있어요"(웹 구현 위치: `src/features/auth/login/components/login-screen.tsx`, KNK-1037). 웹은 이 안내를 보조 문구 중 강조되는 14px(`text-sm`) 크기로 표시하며 별도 반응형 분기를 두지 않습니다. 이미 별도 회원으로 만들어진 두 계정은 연동이 409로 막히고 통합도 제공하지 않으므로, 안내는 계정이 갈라지기 전의 예방 흐름만 설명합니다. **가입 여부를 조회해 안내를 분기하지 않습니다** — 특정 계정의 가입 여부를 알려주는 열거 오라클이 되기 때문입니다.

**로그인 진행 중 상태** (`Phase 1 · 구현`, KNK-760) — 소셜 로그인 CTA(로그인 화면·게스트 한도 바텀 시트 등 모든 진입점 공통)는 버튼 탭 직후 탭한 버튼을 문구 공간을 유지한 중앙 스피너로 바꾸고 두 provider 버튼을 모두 비활성화합니다. 인증 화면으로 전환되기 전 공백에서의 중복 탭(클릭 계측 중복 적재 등)과 provider 교차 탭을 막기 위해서입니다. 화면 이탈 없이 실패하면 실패 토스트와 함께 잠금을 풀어 재시도를 허용합니다. 게스트 한도 바텀 시트는 진행 중 바깥 터치·Escape 닫기를 막습니다(진행 중 이탈로 상태가 꼬이지 않게 — 계정 연동 확인 다이얼로그와 같은 규칙). 웹 구현 상세(OAuth 리다이렉트 공백, bfcache 복원 시 잠금 리셋)는 [`3-2-web-app.md §3-2-4` 소셜 로그인·계정 연동 웹 구현](./3-2-web-app.md#소셜-로그인계정-연동-웹-구현)이 소유합니다.

로그인 성공 시 순서대로:

1. **토큰 보관** — access·refresh 토큰을 앱 코드에 노출되지 않는 플랫폼별 안전 보관소에 저장합니다(웹: BFF httpOnly 쿠키 — [`3-2-web-app.md §3-2-4`](./3-2-web-app.md#3-2-4-bff-프록시토큰-세션) 토큰 세션 / 앱: [`3-3-android-app.md §3-3-4`](./3-3-android-app.md)에서 확정). 초대 URL 라우트(`/invite/[code]`)·초대 코드 httpOnly 쿠키·로그인 요청의 `inviteCode` 전송은 폐기했고, 초대 보상 적립은 `/my/invite`의 코드 입력이 소유합니다([`4-backend.md §4-3-7`](./4-backend.md) 결정 기록).
2. **자동 마이그레이션(웹 전용, Android 비적용)** — 로컬 저장소의 스토리·채팅 ID 배열([§3-1-6](#3-1-6-게스트-데이터-모델))을 `POST /auth/migrate`로 제출합니다. 사용자 확인 없이 실행합니다.
3. **이관 결과 처리(웹 전용, Android 비적용)** — 결과 `status`와 무관하게(`MIGRATED` · `ALREADY_OWNED` · `CONFLICT` · `NOT_FOUND`) 제출한 ID를 로컬 저장소에서 제거합니다. 회원 서재는 서버 정본으로 전환되므로 로컬 목록은 게스트 전용이 됩니다.
4. **완료 피드백** — 웹은 홈으로 이동하고 이관 성공(`MIGRATED`) 수를 토스트로 알립니다("스토리 N개, 채팅 M개를 계정으로 옮겼어요"). 성공 0건이면 토스트를 생략하고 `CONFLICT`·`NOT_FOUND`는 별도 안내하지 않습니다. Android는 이관 없이 회원 그래프로 전환합니다.

**신규 가입 온보딩(초대 코드 입력)** (`Phase 1 · 구현`, KNK-1045) — 신규 가입의 첫 로그인 완료 직후 화면 아래에서 올라오는 모달 바텀 시트를 표시합니다. 제목은 "초대 코드를 등록하면 / N 이프를 받을 수 있어요" 두 줄(N은 서버 정책의 `inviteReward`), 설명은 "지금은 건너뛰고 나중에 등록해도 돼요"이며, 초대 코드 입력란 아래에 "등록하기" 주 버튼과 "닫기" 고스트 버튼을 세로로 둡니다. 제목·설명 사이는 8px, 설명과 폼 사이는 32px입니다. 제출·피드백 규칙은 `/my/invite` 입력란과 동일합니다. 열릴 때 초점은 입력란이 아니라 시트 자체에 두어 모바일 키보드가 자동으로 올라오지 않게 합니다. "닫기"는 배경 탭·ESC와 같은 처리(세션 플래그 소비 후 닫기)이며, 건너뛰어도 자격(계정당 평생 1회)은 유지되어 이후 `/my/invite`에서 입력할 수 있습니다. 입력 성공 후 세션 플래그 저장이 끝날 때까지 등록 스피너와 입력 잠금을 유지하며, 저장 실패 시 보상은 다시 요청하지 않고 "N 이프는 정상 지급되었지만, 창을 닫는 데 실패했어요"를 표시한 뒤 플래그 저장만 재시도합니다.

**계정 연동** (`Phase 1 · 구현`, KNK-740) — 로그인된 계정에 다른 provider를 추가해 어느 쪽으로 로그인해도 같은 계정으로 들어오게 합니다. 백엔드 계약과 2단계 프로토콜(재인증 → 연동)의 정본은 [`4-backend.md §4-5`](./4-backend.md) 계정 연동 절입니다. **연동 해제는 제공하지 않으며**, 이미 갈라진 계정은 연동할 수 없습니다(예방책).

- **연동된 계정 표시** — 마이 페이지 닉네임 아래에 Chip 행을 둡니다. 연동된 provider는 로고 + 이름("Google" · "카카오") Chip으로, 미연동 provider는 같은 모양의 점선 테두리 버튼("카카오 연동하기" · "Google 연동하기")으로 표시합니다. 둘 다 연동되면 버튼은 사라지고 Chip 2개만 남습니다. 상태 정본은 `GET /auth/me`의 `linkedProviders`(소문자, `google` → `kakao` 정렬)이며, 전용 조회 API는 두지 않습니다. `GET /auth/me` 응답 전(로딩 중)에는 칩 크기의 스켈레톤 2개로 자리를 잡아 레이아웃 시프트를 막고, 응답이 왔는데 `linkedProviders`가 비어 있으면(미제공) 섹션 자체를 렌더하지 않습니다 — 실데이터 전에 칩·버튼을 그리지 않으므로 연동 버튼 2개가 잠깐 보이는 오해도 막힙니다(KNK-740).
- **연동 시작 확인 다이얼로그** — 연동 버튼을 누르면 곧바로 OAuth로 보내지 않고 확인 다이얼로그를 먼저 띄웁니다. 재인증이 선행되므로 **대상 provider가 아니라 현재 로그인한 provider의 인증 창이 먼저** 뜨는데, 예고가 없으면 사용자가 흐름을 오해합니다. 또 연동은 해제할 수 없어 비가역 확인이 필요합니다. 다이얼로그는 혜택(어느 쪽으로 로그인해도 같은 마냑 계정)·재인증 순서 예고(현재 provider를 다시 인증한 뒤 대상 provider를 연동)·해제 불가 고지를 각각 한 줄로 나눠 담고, "나중에 하기"/"연동하기" 2버튼을 둡니다. 명시적 이탈 버튼이 있으므로 닫기(X) 버튼은 두지 않습니다(KNK-715).
- **플로우** — 확인 → 현재 provider 재인증 → `POST /auth/links/reauth`로 링크 코드 발급(클라이언트 코드에 노출되지 않게 보관) → 대상 provider 인증 → `POST /auth/links/{provider}`(`X-Manyak-Link-Code` 헤더) → 성공 시 `GET /auth/me` 재조회로 Chip 갱신 + 성공 토스트. 연동 인증이 로그인 경로(백엔드 로그인 호출·세션 교체)를 타지 않아야 하고, 단계 판정은 클라이언트 상태가 아니라 콜백 provider의 `linkedProviders` 포함 여부로 서버가 하므로 중단된 이전 시도의 잔여 상태에도 자기 교정됩니다. 재인증 요구 자체(2단계 프로토콜)는 백엔드 계약이므로 유지합니다. 웹 구현 상세(NextAuth 연동 전용 프로바이더 변형, 중계 화면, `login_hint`)는 [`3-2-web-app.md §3-2-4` 소셜 로그인·계정 연동 웹 구현](./3-2-web-app.md#소셜-로그인계정-연동-웹-구현)이 소유합니다.
- **에러 처리** — 409 두 종류는 안내를 구분합니다([`4-backend.md §4-5`](./4-backend.md) 결정 기록이 요구). `PROVIDER_ALREADY_LINKED`(이미 내 계정에 연동)는 "이미 연동된 계정이에요" 토스트 + 상태 재조회, `SOCIAL_ACCOUNT_LINKED_TO_OTHER_USER`(다른 마냑 계정에 연동 = 갈라진 계정)는 **다이얼로그**로 상황과 대처(로그아웃 후 해당 계정으로 로그인)를 안내합니다 — 사라지는 토스트로는 "그럼 어떻게 하나"에 답할 수 없기 때문입니다. 이 다이얼로그에 "기존 계정으로 로그인하기" 버튼은 두지 않습니다(현재 세션 로그아웃이라는 큰 부수효과를 한 번의 탭에 묶지 않음). 403(`REAUTH_FAILED`·`SOCIAL_TOKEN_INVALID`)은 실패 토스트만 띄우고, 링크 코드가 소비되지 않아 만료 전 재시도가 가능합니다. **연동 경로의 403·409를 세션 만료로 처리하지 않습니다**(로그아웃·토큰 재발급을 트리거하지 않음).
- **인앱 브라우저 차단 (웹 전용)** — 연동은 재인증·연동 두 단계 모두 OAuth라 Google 인증이 반드시 끼는데 인앱 WebView는 Google이 막습니다. 인앱에서 연동 버튼을 누르면 플로우를 시작하지 않고 "계정 연동은 외부 브라우저에서만 할 수 있어요" 토스트로 안내합니다(로그인의 핸드오프 경로는 재사용하지 않습니다 — 연동은 기존 세션 유지가 전제). 앱에는 인앱 브라우저 개념이 없어 이 항목이 적용되지 않습니다.
- **운영 요건·구현 결정** — 연동 전용 프로바이더의 콘솔 콜백 URL 등록 등 웹 구현·운영 요건과 결정 기록(NextAuth 프로바이더 변형)은 [`3-2-web-app.md §3-2-4` 소셜 로그인·계정 연동 웹 구현](./3-2-web-app.md#소셜-로그인계정-연동-웹-구현)이 소유합니다.

**예외 처리** (`Phase 1 · 구현`)

- **마이그레이션 요청 실패(400·네트워크)** — 로그인 완료를 막지 않습니다. `400`은 손상 ID가 섞인 경우이므로 무한 재시도를 피하기 위해 제출 배열을 그대로 재시도하지 않습니다. 클라이언트가 UUID 형식이 유효한 ID만 골라 1회 재제출하고, 형식이 깨진 ID는 폐기합니다(원본은 접근 불가 상태이므로 손실 없음).
- **로그인 실패** — 실패 토스트 후 화면 유지입니다. 인증 제공자 단계의 실패(토큰 교환 오류·콘솔 설정 오류 등)도 로그인 화면으로 복귀시켜 같은 실패 토스트로 처리하고, 관측 이벤트 `client_login_oauthError_shown`을 발행합니다([`6-analytics.md §6-4-3`](./6-analytics.md) — 서버 이벤트가 못 잡는 콜백 단계 사각지대 커버, `Phase 1 · 계획` KNK-721). 복귀 수단(웹: NextAuth `pages.error`의 `error` 쿼리)은 플랫폼 소유입니다.

**결정 기록 — 이관 후 로컬 ID 일괄 제거(결과 무관)**

- **배경.** 이관 제출 후 로컬 배열을 어떻게 정리할지의 갈림길입니다. 회원 서재는 서버가 정본이므로 로컬 목록은 게스트 전용이어야 합니다.

| 대안                                                     | 채택 안 한 이유                                                                                         |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 실패 항목(`CONFLICT` · `NOT_FOUND`)만 로컬에 남겨 재시도 | 두 상태 모두 사용자 행동으로 해소할 수 없어, 남겨 두면 로그인할 때마다 같은 실패를 반복 제출하게 됩니다 |

- **영향.** `MIGRATED` 성공 수만 토스트로 안내하고 실패는 별도 안내하지 않습니다. 로그아웃 후에는 빈 서재에서 새로 시작합니다.

**회원 모드 데이터 소스** `Phase 1 · 구현` — 회원의 스토리·채팅 목록은 `GET /users/me/stories` · `GET /users/me/chats`를 서버 정본으로 사용합니다. 생성·삭제 후 서버 목록 쿼리를 무효화해 재조회합니다. 게스트 배치 조회([§3-1-6](#3-1-6-게스트-데이터-모델))와 로컬 ID 배열은 게스트 전용입니다.

**로그아웃** (`Phase 1 · 구현`) — 마이 페이지의 로그아웃은 `POST /auth/logout` 후 플랫폼 세션 보관소를 폐기합니다(웹: 세션 쿠키 — [3-2-web-app.md §3-2-4](./3-2-web-app.md#3-2-4-bff-프록시토큰-세션) / 앱: [`3-3-android-app.md §3-3-4`](./3-3-android-app.md)). 웹은 게스트 모드의 빈 서재로, Android는 모든 로컬·공급자 정리를 마친 뒤 인증 그래프로 복귀합니다. 진행 중에는 메뉴 오른쪽에 스피너를 표시하고 항목을 잠가 중복 탭을 막습니다. 분석 식별자는 [`6-analytics.md §6-2`](./6-analytics.md)에 따라 재설정합니다(공용 기기 보호).

**회원 탈퇴** (`웹 Phase 1 · 구현`, KNK-1052) — 회원은 마이 페이지 계정 섹션의 "회원 탈퇴"에서 `/my/account-deletion`으로 이동합니다. 게스트가 경로에 직접 진입하면 `/login`으로 보냅니다. 화면은 뒤로가기 헤더("회원 탈퇴")와 확인 목록, 하단 위험색 CTA로 구성합니다.

- **사전 확인** — 제목은 "탈퇴하기 전에 / 아래 내용을 모두 확인해주세요", 설명은 "모든 항목을 확인해야 탈퇴할 수 있어요"입니다. 사용자는 잔여 이프 소멸, 기존 서재 복구·이전 불가, 공개 콘텐츠 잔존 가능성, 같은 소셜 계정으로 재로그인해도 기존 계정이 복구되지 않음을 각각 체크해야 합니다. 현재 카피의 코드 정본은 `manyak-web/src/features/my/account-deletion/constants.ts`입니다.
- **CTA 상태** — 네 항목을 모두 체크하기 전에는 "회원 탈퇴하기"를 비활성화합니다. 요청 중에는 "회원 탈퇴 중" 스피너를 표시하고 버튼을 잠가 중복 요청을 막습니다.
- **성공** — `DELETE /users/me`가 `204`를 반환하면 계정은 탈퇴 상태가 되고 소셜 연결·프로필이 제거되며 닉네임이 익명화됩니다. 잔여 이프와 비공개 서재는 복구하거나 새 계정으로 옮길 수 없습니다. 공개 스토리는 익명화된 작성자로 남고 공유 채팅은 기존 링크로 계속 열람할 수 있습니다. 클라이언트는 사용자 쿼리 캐시·진행 중인 생성 복구 슬롯·분석 사용자 식별자를 정리하고 플랫폼 세션을 종료한 뒤 게스트 마이 화면으로 이동합니다.
- **실패** — 5xx·네트워크 오류면 "회원 탈퇴에 실패했어요" 토스트를 표시하고 체크 상태와 현재 화면을 유지해 재시도를 허용합니다. 401로 세션 만료가 확정되면 플랫폼의 전역 세션 만료 흐름을 따릅니다. 탈퇴 성공 뒤 세션 종료 과정에서 이미 무효화된 refresh 토큰의 백엔드 로그아웃이 실패해도 플랫폼 로컬 세션 정리는 계속합니다.

**검수 기준**

- 게스트가 스토리 2개를 만들고 로그인하면 회원 서재에 같은 2개가 보여야 합니다. (US-9-3)
- 같은 계정으로 다른 기기·클라이언트에서 로그인하면 같은 서재가 보여야 합니다. (US-9-4)
- 로그아웃 후 재로그인해도 서재가 유지돼야 합니다. (US-9-5)
- 마이그레이션 API 실패가 로그인 완료를 막지 않아야 합니다.
- 손상된 로컬 ID가 있어도 유효 ID는 이관되고, 손상 ID로 인한 매 진입 반복 실패가 없어야 합니다.
- 회원 상태에서 만든 스토리·채팅은 로컬 목록이 아니라 서버 목록에 나타나야 합니다.
- 회원 서재 조회가 401이면 재발급 후 성공하거나, 재발급 실패 시 재로그인을 안내해야 합니다.
- 회원의 마이 페이지에 현재 연동된 provider가 Chip으로, 미연동 provider가 연동 버튼으로 보여야 합니다. 둘 다 연동한 계정에는 연동 버튼이 없어야 합니다.
- 연동 버튼을 누르면 확인 다이얼로그가 먼저 뜨고, 재인증이 현재 provider로 진행된다는 것과 해제할 수 없다는 것을 알려야 합니다.
- 다른 마냑 계정에 이미 연결된 소셜 계정을 연동하면 토스트가 아니라 다이얼로그로 상황과 대처를 안내해야 합니다.
- 연동에 실패해도 로그인 세션이 풀리지 않아야 합니다.
- 회원 탈퇴 확인 네 항목을 모두 체크하기 전에는 CTA가 비활성화되고, 모두 체크하면 활성화돼야 합니다. (US-9-11)
- 회원 탈퇴 성공 뒤 계정 캐시와 세션이 남지 않고 `/my`의 게스트 상태로 복귀해야 합니다. 실패하면 확인 화면과 체크 상태를 유지해 재시도할 수 있어야 합니다. (US-9-11)
- 잔액 부족 회원의 소모 요청은 이프 부족 토스트를, 한도 소진 게스트는 로그인 바텀 시트를 봐야 합니다. 스토리 제작 입력은 유지하고 실패한 채팅의 낙관적 버블은 제거해야 합니다. (US-10-4, US-10-5)
- 이프 충전의 무료 충전 탭에서 출석체크를 같은 날 두 번 누르면 두 번째는 적립 없이 비활성 상태가 보여야 합니다. (US-10-2)
- 이프 충전에서 탭 패널을 끝까지 스크롤해도 잔액 상자와 탭 줄이 화면에 남아야 합니다. (KNK-1092)
- `/login`에 이관 1회 안내와 약관·개인정보 처리방침 동의 고지가 표시되고, 밑줄 링크가 각각 `/terms`·`/privacy`(FE-SCREEN-010)를 새 브라우저 탭에서 열어야 합니다.
- 마이 페이지 헤더와 하단 네비게이션은 `마이`라는 접근 가능한 이름을 사용해야 합니다.
- 초대 코드 등록 중에는 버튼 문구 대신 중앙 스피너가 표시되고 입력이 잠겨야 합니다. 신규 가입 온보딩에서는 등록·"닫기" 버튼이 함께 잠겨야 합니다.

### FE-SCREEN-009. 일반 제작·스토리 수정 — `Phase 1 · 계획`

| 항목    | 값                                                          |
| ------- | ----------------------------------------------------------- |
| 라우트  | `/studio/story/general` (제작) · `/stories/[id]/edit` (수정) |
| 관련 US | US-3-15, US-3-16, US-4-5                                    |

**목적** — 제작 폼에 스토리 구성 항목을 직접 입력해 등록하고(일반 제작), 같은 폼으로 기존 스토리를 수정합니다.

**진입점** — 제작 화면의 간편 제작 진입점은 `/studio/story/simple`, 일반 제작 진입점은 `/studio/story/general`로 역할별 URL을 분리합니다. 일반 제작 진입점은 이 기능을 구현할 때 추가합니다(US-3-16). 수정: 스토리 상세의 옵션 메뉴에 "수정" 항목을 추가합니다. 회원 소유 스토리는 소유자에게만, 게스트 스토리는 로컬 서재에 해당 `storyId`가 있을 때만 표시합니다.

**폼 구성** — 섹션 아코디언 구조. 필수: 기본 정보(제목·한 줄 소개·장르), 스토리 설정(세계관·등장인물·주인공·규칙 — 섹션별 텍스트 입력을 통글 마크다운으로 조립해 전송), 시작 설정(이름·프롤로그·시작 상황), 추천 입력 3개. 선택: 주요 사건(최대 10 — 이름·설명·키 문장), 엔딩(시작 설정당 최대 10 — 각 이름·조건(`minTurns`+달성 조건)·에필로그). 주요 사건·엔딩은 저장 후 채팅 런타임(목표 진행·엔딩 판정·선택지 구성)에 반영됩니다([`4-backend.md §4-3-10`](./4-backend.md)) — 런타임 동작 자체는 채팅 화면([§3-1-5](#3-1-5-채팅-플레이와-sse-스트리밍))의 검수 대상입니다.

- **이미지 입력은 없습니다**(B10 — [`4-backend.md §4-3-9`](./4-backend.md)). 스토리 이미지는 전부 팀이 사전 제작해 서버가 자동 연결하며, 사용자가 업로드하거나 선택하는 폼 섹션·업로드 API를 두지 않습니다.
- `Phase 1 · 계획`(B14) — 시작 설정은 여러 개(`startSettings[]`, 1개 이상) 등록할 수 있고, 엔딩은 시작 설정별로 입력합니다([`4-backend.md §4-3-8`](./4-backend.md)).

**작성 중 보관** — 임시 저장(서버 초안) API는 없습니다. 등록은 전부를 한 번에 보내는 단발 `POST`이며([`4-backend.md §4-3-8`](./4-backend.md) 결정 기록), 작성 중 유실 방지는 클라이언트가 담당합니다 — 폼 상태를 로컬 저장소(웹: `localStorage`)에 자동 보관해 이탈·복귀 시 복원하고, 등록 성공 시 보관분을 지웁니다.

**동작** — 등록: `POST /stories/general` → 성공 시 스토리 상세로 이동("스토리가 등록됐어요" 토스트). 수정: 진입 시 `GET /stories/{storyId}/edit`로 편집 가능 필드 전체를 조회해 폼을 채우고, 변경 필드만 `PATCH /stories/{storyId}`로 전송 → 성공 시 상세로 복귀. 검증 실패(400)는 `details`의 필드별 사유를 해당 섹션에 인라인 표시합니다.

**검수 기준**

- 일반 제작으로 등록한 스토리가 기본 메타·스토리 설정·시작 설정 기준으로 상세·채팅 시작에서 간편 제작 산출물과 동일하게 동작해야 합니다. (US-3-15)
- 제작 화면에서 간편 제작은 `/studio/story/simple`, 일반 제작은 `/studio/story/general`로 진입할 수 있어야 합니다. (US-3-16)

- 폼 작성 중 이탈 후 복귀하면 작성 내용이 복원돼야 합니다.
- 타인 소유 스토리와 로컬 서재에 없는 게스트 스토리에는 수정 진입점이 보이지 않아야 합니다.

**진입점** — `/login` 화면 최하단 동의 고지의 밑줄 링크(서비스 이용약관 → `/terms`, 개인정보 처리방침 → `/privacy` — [FE-SCREEN-008](#3-1-3-화면별-스펙))와 서비스 안내 페이지(FE-SCREEN-011)의 약관 및 정책 링크에서 진입합니다. **로그인 여부와 무관하게 접근**할 수 있습니다. 웹의 두 진입점은 원래 화면을 유지한 채 문서를 새 브라우저 탭에서 열고, 문서 헤더의 마냑 로고로 홈(`/`)에 이동합니다. 웹은 라우트 가드를 두지 않으며([3-2-web-app.md §3-2-3](./3-2-web-app.md#3-2-3-라우팅레이아웃공통-셸)), Android는 인증·메인 그래프 밖의 공용 법적 문서 목적지로 둡니다([`3-3-android-app.md §3-3-3`](./3-3-android-app.md)). **콘텐츠 동일성 계약** — 서비스 이용약관·개인정보 처리방침은 법적 고지이므로 **모든 플랫폼이 같은 시행일·버전·본문 내용을 표시해야 합니다**. 콘텐츠 정본은 웹 레포의 TypeScript 모듈이며(경로는 [`3-2-web-app.md §3-2-3` 법적 콘텐츠 소스](./3-2-web-app.md#법적-콘텐츠-소스-웹)가 소유), Android의 `LegalDocumentScreen`은 `WEB_BASE_URL/terms`·`WEB_BASE_URL/privacy`를 WebView로 직접 열어 별도 사본 없이 같은 정본을 표시합니다. 2026-09-01 시행본은 약관 v1.2·처리방침 v1.3입니다. 약관은 개인 운영 주체·만 14세 이상 이용 조건·Google/Kakao 로그인과 연동·게스트 이관·무상 이프·콘텐츠 공개·AI 평가 데이터·책임 범위를, 처리방침은 웹·Android 실제 수집 항목·1년 보유 정책·위탁·국외 이전·권리 행사·쿠키·Meta 픽셀·Sentry 리플레이·AI 제공자별 처리 조건·만 14세 미만 비대상을 포함합니다. 운영자는 원문을 품질 점검·평가 데이터·평가 지표 생성에 사용하지만 자체 AI 모델은 훈련하지 않으며, Langfuse 원문은 1년 보유합니다([`6-analytics.md §6-7`](./6-analytics.md)). 개정 시 시행일·버전과 부칙의 개정 이력을 함께 갱신합니다. **개인 운영자 연락처, 국외 이전 근거·동의 방식, 1년 파기 운영 등은 법률·운영 검토가 필요합니다.**

**동의 모델** — 별도 동의 화면·체크박스 없이 `/login` 로그인 버튼 클릭을 동의로 간주합니다(묵시적 동의 — [FE-SCREEN-008](#3-1-3-화면별-스펙)). 약관 개정 시 재동의 흐름은 이 스펙의 범위 밖입니다.

**검수 기준**

- 웹 `/login`의 동의 고지 밑줄 링크로 `/terms`·`/privacy`를 각각 새 브라우저 탭에서 열고, 원래 로그인 탭은 유지돼야 합니다.
- 두 페이지 모두 본문 상단에 시행일·버전이 보여야 합니다.
- 로그인하지 않은 사용자도 두 페이지를 열람할 수 있어야 합니다(웹 게스트·Android 미로그인 상태 모두).
- 웹 문서 헤더에는 뒤로가기·문서 제목 없이 마냑 로고 홈 링크가 보여야 하며, 로고로 홈(`/`)에 이동할 수 있어야 합니다.
- Android WebView에서도 웹과 같은 시행일·버전·본문 내용이 표시되어야 합니다(위 콘텐츠 동일성 계약).

### FE-SCREEN-011. 서비스 안내 — `Phase 1 · 구현`

| 항목    | 값                                                   |

**목적** — 서비스 이용에 필요한 정책 정보(웹 게스트 데이터, AI 콘텐츠 특성, 문의)를 약관보다 쉬운 말로 모아 보여주고, 서비스 이용약관·개인정보 처리방침(FE-SCREEN-010)으로의 상시 진입점을 제공합니다. 현재 두 문서의 진입점이 로그인 화면뿐이라 로그인 후에는 다시 볼 경로가 없습니다 — 개인정보 처리방침은 이용자가 쉽게 확인할 수 있는 곳에 상시 공개해야 하므로 마이에 상시 진입점을 마련합니다.

**화면 구성** — 웹은 서비스 이용약관·개인정보 처리방침과 같은 마냑 로고 홈 링크 헤더와 정적 본문(세로 스크롤)으로 구성합니다. 뒤로가기 버튼은 표시하지 않으며 로고를 누르면 홈(`/`)으로 이동합니다. 본문 최상단에는 20px 굵기의 `h1` "서비스 안내"를 표시하고, 그 아래에 기존 안내 섹션을 둡니다. 웹 브라우저 탭 제목은 본문 제목과 같은 정본을 루트 제목 템플릿에 적용한 "서비스 안내 - 마냑"입니다. 별도 API·상태 없이 클라이언트 정적 렌더입니다. 본문은 다음 섹션으로 구성합니다.

1. **게스트 이용 안내(웹 전용)** — 로그인 없이 체험 한도 내에서 이용 가능하며, 게스트 콘텐츠는 브라우저 로컬 저장소 기반이라 저장소 삭제·기기 변경 시 접근이 어려울 수 있고, 최초 로그인 시 1회에 한해 계정으로 이관됨을 안내합니다(서비스 이용약관 제6조와 동일 정책의 요약). **Android는 게스트 모드가 없으므로 이 섹션 전체를 렌더하지 않습니다**([`3-3-android-app.md §3-3-1`](./3-3-android-app.md)).
2. **AI 콘텐츠 안내** — 스토리·채팅 응답은 AI가 생성한 허구이며, 부정확하거나 부적절한 내용이 포함될 수 있음을 고지.
3. **문의** — 서비스 개선 의견은 피드백(`/my/feedback`)으로 유도. 회원 탈퇴 관련 내용과 이메일 탈퇴 요청 경로는 이 화면에 표시하지 않습니다(KNK-1068).
4. **약관 및 정책** — "서비스 이용약관"(`/terms`)·"개인정보 처리방침"(`/privacy`) 링크(FE-SCREEN-010). 웹은 각 링크 뒤에 새 창 아이콘(`LinkSquare01Icon`)을 표시하고 두 링크를 새 브라우저 탭에서 엽니다.

**콘텐츠 규칙** — **이프 수치는 이 화면에서 고지하지 않습니다**(KNK-1095, 2026-09-01). 수치는 서버 정책이 정본이라 운영 중에 바뀌고, 안내 화면에 복제해 두면 서버만 바꿔도 이 화면이 거짓말을 합니다. 수치가 필요한 자리(스토리 완성 비용·채팅 턴 비용·출석·초대 보상)는 각 화면이 서버 값을 직접 렌더합니다([§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시)). 게스트 체험 한도는 서버 정본이 백엔드 정책([`4-backend.md §4-3-7`](./4-backend.md))이며 이 화면 표기와 일치해야 합니다. 약관·개인정보 처리방침 본문과 상충하는 서술을 두지 않습니다 — 요약은 허용하되 다르게 말하지 않습니다.

**분석** — 진입 시 `client_serviceInfo_viewed`(P2)를 기록합니다([`6-analytics.md §6-4`](./6-analytics.md)).

**검수 기준**

- 마이 기타 섹션의 서비스 안내 메뉴로 진입할 수 있어야 합니다(웹은 게스트·회원, Android는 회원). 웹은 새 창 아이콘을 표시하고 서비스 안내를 새 브라우저 탭에서 열어 원래 마이 탭을 유지해야 합니다.
- 웹 헤더에는 뒤로가기 없이 마냑 로고 홈 링크가 보여야 하며, 로고로 홈(`/`)에 이동할 수 있어야 합니다.
- 서비스 안내 본문 최상단에는 `h1` "서비스 안내"가 있고, 기존 안내 섹션은 그 아래에 표시되어야 합니다.
- 웹 브라우저 탭 제목은 "서비스 안내 - 마냑"이어야 합니다.
- 이프 수치를 고지하는 섹션이 없어야 합니다(KNK-1095). 게스트 체험 한도 수치는 백엔드 정책과 일치해야 합니다.

## 3-1-4. 스토리 생성 퍼널

FE-SCREEN-002의 상세입니다. `/studio/story/simple` 단일 라우트에서 로컬 상태로 4단계를 전환합니다. URL 쿼리로 단계를 표현하지 않습니다.

### 단계 구성

단계 순서는 `키워드 선택 → 스토리라인 선택 → 추가 정보 → 완료`입니다. 진행 표시기는 앞의 3단계만 동일 너비의 둥근 막대로 노출하고 완료는 종료 로딩 상태입니다. 완료한 막대는 현재 단계보다 조금 진하게, 현재 단계는 중간 회색으로, 미도달 단계는 경계색으로 표시합니다. 진행 상태는 다음 행동을 뜻하지 않으므로 CTA에 쓰는 브랜드 초록은 사용하지 않습니다(Android 화면 패리티, 2026-08-27).

| #   | 단계            | 목적                                            | 진행(다음) 조건                          |
| --- | --------------- | ----------------------------------------------- | ---------------------------------------- |
| 1   | 키워드 선택     | 장르·주인공·주변 인물 키워드 수집               | 장르 1개 이상 **그리고** 주인공 1개 이상 |
| 2   | 스토리라인 선택 | AI 생성 스토리라인 3개 중 택1(선택·재생성·평가) | 활성 스토리라인 선택 완료                |
| 3   | 추가 정보       | 추천 태그·자유 텍스트로 디테일 보강             | 생성 ID와 선택 스토리라인 ID 존재        |
| 4   | 완료            | 스토리·채팅 생성                                | (종료) 성공 시 채팅 화면으로 `replace`   |

**모바일 키보드** — 키워드 단계의 이름·직접 추가 키워드와 추가 정보 단계의 자유 텍스트처럼 사용자가 직접 입력하는 동안 가상 키보드가 열리면, 화면을 가리지 않도록 하단 단계 CTA 푸터를 숨깁니다. 키보드가 닫히면 같은 푸터를 다시 표시하고 입력값은 유지합니다(KNK-999).

| 주인공 특징    | 주인공 (나)    | 예     | 인물 1명, 특징 3개          | 가능      |
| 주변 인물 특징 | 주변 인물      | 아니오 | 인물 5명, 인물마다 특징 3개 | 가능      |

- 카테고리 탭은 화면 가로폭을 3등분하는 라인 탭입니다. 탭 행 컨테이너의 위·아래에 별도 내부 여백을 두지 않고, 선택 탭의 검은 선은 미선택 탭의 회색 기준선과 같은 높이에서 기준선을 덮습니다. 탭 아래 별도 설명 문구는 두지 않습니다(Android 화면 패리티, 2026-08-27).
- 각 카테고리 콘텐츠에는 칩 목록 위에 섹션 라벨을 둡니다(장르 탭 "장르 (최대 3개)", 인물 탭 "특징 (최대 3개)"). 장르·주인공 콘텐츠는 탭 기준선 아래 16px에서 시작하고, 모든 탭 패널 하단은 32px를 확보합니다. 필수 카테고리(장르·주인공)의 라벨에는 `*`를 붙입니다(KNK-1012).
- 태그 목록은 API로 조회하며, 로딩 시 스켈레톤 칩을 표시합니다.
- 상한에 도달하면 미선택 칩과 "키워드 추가" 트리거를 비활성화합니다(제공 태그·직접 추가 합산). 주변 인물이 5명이면 "인물 추가"도 비활성화합니다.
- 필수 카테고리의 "다음" 버튼은 선택 전에도 활성화합니다. 선택 없이 누르면 이동하지 않고 버튼 위 푸터에 "키워드를 하나 이상 선택해주세요"를 표시합니다. 오류가 생길 때만 푸터가 메시지 높이만큼 늘어나며, 해당 카테고리에서 키워드를 선택하면 오류를 제거합니다.
- 커스텀 키워드는 "키워드 추가" 다이얼로그로 입력합니다. "추가하기" 버튼은 빈 입력에서도 활성화하고, 빈 값으로 누르면 입력창 아래에 "키워드를 입력해주세요"를 표시합니다. 유효한 값을 입력하거나 다이얼로그를 닫으면 오류를 제거합니다. 클라이언트 최대 15자(서버 스키마 30자), IME 조합 중 Enter는 제출하지 않습니다. 세 카테고리 모두 직접 추가할 수 있으며, 요청에서 장르는 `customGenreTags`, 인물은 각 인물의 `customTags`로 나갑니다([`4-backend.md §4-3-2`](./4-backend.md)).
- 카테고리 탭은 앞선 필수 카테고리가 완료되어야 잠금 해제됩니다.

#### 인물 단위 입력 — `Phase 2 · 구현`(KNK-834·858)

주인공과 주변 인물을 특징 태그 묶음이 아니라 인물 단위로 입력받습니다. 두 탭은 같은 폼을 씁니다.

- **폼 구성** — 세로로 `기본 정보`(이름 인풋 + 성별 셀렉트를 3:2 비율로 배치) → `특징`(제공 태그 칩 + "키워드 추가") 순입니다. 기본 정보 아래에 "비워두면 랜덤으로 설정해요"를 두어 선택 항목임을 알립니다. 특징 라벨의 `*`는 주인공 탭에만 붙고, 특징이 선택 항목인 주변 인물은 칩 아래에 "선택하지 않으면 랜덤으로 설정해요"를 둡니다.
- **이름** — 직접 입력이며 클라이언트·서버 모두 30자 상한입니다. 인풋 오른쪽에 입력 글자 수를 표시합니다.
- **성별** — 셀렉트이고 기본값은 "랜덤 성별"입니다. 랜덤은 고르지 않은 상태와 같아 요청에 `null`로 나가고 AI가 정합니다.
- **주변 인물 목록** — 퍼널 진입 시 빈 인물 1명이 놓여 있고, 각 인물은 전체 폭의 중립색 헤더와 좌우 16px 여백의 폼으로 구성합니다. 헤더에는 14px의 입력 이름(비어 있으면 "주변 인물 N"), 현재 순번을 나타내는 12px `N/5` 필, 14px의 텍스트형 "삭제"를 표시합니다. 순번 필은 헤더보다 한 단계 진한 중립색 배경으로 구분합니다. 카드 테두리는 두지 않습니다. 삭제로 0명까지 줄일 수 있고, 목록 아래 가운데의 "인물 추가"로 5명까지 늘립니다. 추가 직후 새 이름 인풋이 화면 중앙에 오도록 부드럽게 스크롤하되 자동으로 초점을 옮기지 않아 모바일 키보드는 열지 않습니다(KNK-999). 항목을 채우지 않은 폼도 인원으로 집계됩니다(빈 폼 3개 = 주변 인물 3명). Android 화면 패리티에 따른 구성입니다(2026-08-27).
- **이름 중복 금지** — 한 스토리 안에서 주인공과 주변 인물의 이름은 겹칠 수 없습니다. AI가 이름 글자로 인물의 등장 여부를 확인하기 때문입니다. 판정 키는 서버와 같습니다 — NFC 정규화 → 공백 제거 → 소문자([`4-backend.md §4-3-2`](./4-backend.md)). 먼저 쓴 이름을 남기고 뒤에 겹친 인물의 이름 인풋에 "이미 사용한 이름이에요"를 즉시 표시하고, 그 상태에서 "스토리라인 만들기"를 누르면 요청을 보내지 않고 푸터에 "인물 이름이 겹치지 않게 해주세요"를 표시합니다. 비워 둔 이름은 AI가 각각 지어 주므로 판정 대상이 아닙니다. 서버도 400으로 막습니다([`4-backend.md §4-3-2`](./4-backend.md)).

#### 세계관 탭 개편 — `Phase 2 · 계획`(KNK-621)

2026-07-20 팀 결정의 남은 부분입니다. 인물 관련 개편(주변 인물 세트·주인공 이름·성별)은 위 인물 단위 입력으로 구현됐고, 세계관 탭은 배경 태그를 서버가 아직 제공하지 않아 미구현입니다. 구현 전까지는 위 현행 규칙이 유효합니다.

- **탭 구조** — 첫 탭 "장르"를 "세계관"으로 바꾸고, 세계관 탭 안을 "장르"와 "배경" 두 키워드 그룹으로 나눕니다. 두 번째 탭의 현행 라벨 "주인공 (나)"는 유지하고 제공 태그 목록을 새 체계에 맞춰 갱신합니다. 탭 순서는 세계관 → 주인공 (나) → 주변 인물입니다.
- **장르·배경 선택 규칙** — 각 그룹에서 1~2개를 선택하며 각 최소 1개 필수입니다(기존 장르 최대 3 대체). 세계관 탭 완료 조건은 장르 1개 이상 **그리고** 배경 1개 이상이고, 스토리라인 생성 가능 조건도 장르·배경 각 1개 이상 그리고 주인공 1개 이상으로 바뀝니다([§3-1-8](#3-1-8-입력폼-검증-규칙)). 두 그룹 모두 커스텀 키워드를 추가할 수 없게 바꾸며(서비스 제공 키워드만 선택) "키워드 추가" 트리거를 감춥니다 — 현재 장르는 직접 추가를 허용하므로 이 시점에 걷어냅니다. 제공 키워드 목록은 [`4-backend.md §4-3-2`](./4-backend.md)가 소유합니다.
- 서버·AI 계약 영향분은 [`4-backend.md §4-3-2`](./4-backend.md)·[`5-ai-server.md §5-3-2`](./5-ai-server.md)가 소유합니다.

### 스토리라인 생성·평가

- **선택 UI** — 생성된 3개 결과는 키워드 단계와 같은 전체 폭 3등분 라인 탭("첫 번째"·"두 번째"·"세 번째")으로 전환합니다. 탭 컨테이너에는 위·아래 내부 여백을 두지 않고 선택선은 회색 기준선과 같은 높이에서 덮습니다. 본문은 탭 기준선 아래 16px에서 시작하고 패널 하단은 32px를 확보합니다. 스토리라인 본문과 추가 정보 단계의 선택 스토리라인 요약은 16px MaruBuri, 자간 -2%, 행간 175%(28px)를 함께 사용합니다(KNK-1029). 하단 푸터에는 위·좌·우 여백 없이 앱 프레임 전체 폭을 채우는 높이 40px의 각진 중립색 "선택한 키워드 보기" 버튼을 두고, "다시 만들기"·"선택하기" 행과는 8px 간격으로 구분합니다. 라벨은 보조 전경색으로 표시합니다. 누르면 기존 선택 키워드 드로어를 열며 장르·주인공·주변 인물 등 키워드 그룹 사이는 24px로 구분합니다(Android 탭 패리티, 2026-08-27; 여백 KNK-1012).
- **생성** — `POST /stories/simple/storylines {genreTagIds, customGenreTags, protagonist, supportingCharacters}`. 인물 객체는 `{name, gender, featureTagIds, customTags}`이고 비워 둔 이름·성별은 `null`로 보냅니다. 클릭 직후 "스토리라인 만들기" 버튼을 비활성화하고 문구 공간을 유지한 중앙 스피너를 표시하며, 동시에 스토리라인 선택 단계로 전환해 로딩 화면을 렌더합니다. 응답은 스토리라인 3개와 생성 ID(`simpleCreationId`)를 포함합니다. 로딩 중에는 타자기형 문구와 15·30초 시점 힌트를 표시합니다. `Phase 1 · 구현` — 회원은 무료이고, 게스트는 디바이스 ID별 스토리라인 생성·재생성 합산 5회 한도를 사용합니다. 201 성공 시에만 로컬 누적 카운터를 1 증가시킵니다.
- **재생성** — "다시 만들기"는 저장된 생성 요청을 재호출합니다. 생성 요청 이벤트는 최초 1회만 발화합니다. `Phase 1 · 구현` — 로컬 카운터가 5회에 도달한 게스트 요청은 API 호출 전에 차단합니다.
- **평가** — 스토리라인별 좋아요·별로예요를 토글합니다. 300ms 디바운스 후 설정(`PUT`)·해제(`DELETE`)로 동기화합니다. 동일 평가를 다시 누르면 해제되고, 실패 시 상태를 되돌리고 실패 토스트를 표시합니다. **평가는 보조 신호이며 완성 페이로드에 포함되지 않고 진행을 막지 않습니다.**

### 추가 정보 진입·스토리라인 재선택

- 추가 정보 단계의 선택 스토리라인은 첫 렌더부터 한 줄로 접고 **더보기/접기 토글을 항상 렌더링**합니다. 내용 길이를 측정한 뒤 토글을 제거하지 않아 짧은 스토리라인에서도 첫 렌더 레이아웃이 움직이지 않아야 합니다(KNK-994, Android PR #5 패리티).
- 추천 추가 정보 목록과 자유 입력 영역 사이는 32px로 구분하고 자유 입력 패널 하단도 32px를 확보합니다. 자유 입력 영역의 제목 행은 기본 전경색의 `추가 정보 (최대 10개)`로 표시하고, `입력`이라는 중복 설명은 붙이지 않습니다. "정보 추가" 직후 새 입력 행이 화면 중앙에 오도록 부드럽게 스크롤하되 자동으로 초점을 옮기지 않아 모바일 키보드는 열지 않습니다. 각 행의 X 삭제 버튼은 Tab 순서에서 제외해 입력 중 Tab을 누르면 다음 입력 행으로 바로 이동합니다(KNK-999·1012). Android 화면 패리티에 따른 구성입니다(2026-08-28).
- 추가 정보 단계 하단 푸터에는 CTA 행 바로 위에 앱 프레임 전체 폭을 채우는 높이 40px의 각진 중립색 비용 행을 둡니다. 왼쪽에는 보조 전경색으로 `스토리 완성 비용`, 오른쪽에는 기본 전경색의 굵은 `N 이프`를 표시하고 CTA 행과는 8px 간격으로 구분합니다. N은 서버 정책의 `storyCreationCost`이며([§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시)), 문구 정본은 `manyak-web/src/features/stories/new/constants.ts`입니다(KNK-1045·1068·1095, 2026-09-01).
- 추가 정보나 추천을 아직 고르지 않은 상태에서 "다시 선택하기"를 누르면 경고 없이 스토리라인 선택 단계로 돌아갑니다. 공백만 있는 자유 입력과 처음부터 놓인 빈 입력 행은 작성한 정보로 보지 않습니다.
- 공백이 아닌 자유 입력 또는 선택한 추천이 하나라도 있으면 `스토리라인을 바꿀까요? / 입력한 추가 정보는 모두 사라져요` 경고를 표시합니다. `닫기`는 단계·스토리라인·입력·추천을 모두 유지합니다. 파괴적 스타일의 `다시 선택하기`를 확정하면 선택 스토리라인, 자유 입력 전부, 추천 선택 전부를 초기화하고 스토리라인 선택 단계로 돌아갑니다.

### 완성(finalize)

추가 정보(`additionalInfos`)는 `[선택한 추천 추가 정보 텍스트, ...공백 제거한 자유 텍스트]`로 구성합니다. 전송 상한은 총 13개(추천 추가 정보 최대 3개 + 자유 텍스트 최대 10개), 각 100자입니다. 완성은 두 경로로 나뉩니다.

1. **최초 완성** — `POST /stories/simple {simpleCreationId, storylineId, additionalInfos}` → 성공 시 스토리 ID를 로컬에 저장 → `POST /chats {storyId}` → 성공 시 채팅 ID 저장·완료 이벤트·상세 prefetch·완료 토스트 후 채팅 화면으로 `replace`.
2. **재시도** — 스토리가 이미 생성된 경우 스토리 생성을 건너뛰고 저장된 `storyId`로 채팅 생성만 재호출합니다. 채팅 생성이 실패하거나 그 사이 앱·페이지가 종료돼도 완성 진행 레코드는 채팅 성공 전까지 유지합니다.

이 분기로 같은 화면에서의 재시도와 재진입 후 재시도 모두 스토리가 중복 생성되지 않습니다. 채팅 생성 성공 뒤에만 완성 진행 레코드를 제거합니다.

- 헤더는 뒤로가기 화살표가 아니라 **X 닫기 버튼**을 사용합니다. 헤더 X와 플랫폼 뒤로가기는 모든 단계에서 퍼널을 이탈시키며, 웹은 제작(`/studio`)으로 돌아갑니다. 키워드 단계는 경고 없이 이탈합니다.
- 이탈 처리는 내용이 남는지로 갈립니다. 자동 저장본이나 진행 중 요청이 복구 대상으로 남으면 묻지 않고 즉시 이탈하고, 복원할 결과가 없으면(스토리라인 생성 실패 등) 소실 경고 다이얼로그를 표시합니다. 자동 저장 상태는 헤더 뱃지로 이미 알리므로 이탈 시 임시 저장 토스트를 중복 표시하지 않습니다(KNK-994, Android PR #5 패리티). 웹 전용 — `beforeunload` 경로는 브라우저 기본 확인창이라 문구를 제어하지 않으며 그대로 유지합니다([`3-2-web-app.md`](./3-2-web-app.md) 소유).
- 이탈 감지 수단은 플랫폼 소유입니다 — 웹은 새로고침·탭 닫기·URL 이동을 `beforeunload`로, 브라우저·모바일 웹 뒤로가기를 더미 히스토리 트래핑으로 잡아 커스텀 다이얼로그를 띄우고, 앱은 백 버튼·제스처 인터셉트와 라이프사이클 콜백으로 같은 계약(경고 또는 임시 저장 후 이탈)을 충족합니다([`3-3-android-app.md §3-3-5`](./3-3-android-app.md)). 확정 시 진입 이력과 관계없이 제작 화면으로 이동합니다(KNK-988).

### 백그라운드 생성 복귀 — `Phase 1 · 구현`(KNK-623·KNK-637)

모바일에서 스토리라인 생성·완성(스토리 생성) 대기 중 다른 앱으로 전환했다가 돌아와도 진행 상태를 이어서 확인할 수 있어야 합니다(2026-07-20 팀 결정). 서버는 연결이 끊겨도 생성·저장을 끝까지 진행하므로([`4-backend.md §4-3-2`](./4-backend.md) 복구 계약), 프론트엔드는 복구 조회로 결과를 되찾습니다. 생성 요청 전에 UUID `requestId`를 만들어 요청 본문에 싣고 단계·퍼널 컨텍스트와 함께 로컬 저장소에 저장합니다(웹 키: `manyak:pending-creation-request` — 저장 수단·키는 플랫폼 소유, [§3-1-6](#3-1-6-게스트-데이터-모델) 저장 구조와 동일 원칙). 원 요청이 진행 중이지 않은데 미정리 레코드가 남아 있으면(퍼널 재진입, 응답 유실 복귀) `GET /stories/simple/creation-requests/{requestId}`를 **3초 주기**로 폴링해 `PENDING`이면 해당 단계 로딩 화면을 복원하고, `COMPLETED`면 결과 화면을 복원하며(원 성공 경로의 부수효과 — 게스트 카운터·로컬 ID 저장·쿼리 무효화 — 를 함께 수행), `FAILED`·404는 기존 실패 처리로 합류합니다. 폴링은 탭이 백그라운드인 동안 멈췄다가 복귀 시 즉시 재개됩니다.

- **정리 규칙** — 서버가 상태 코드로 응답한 실패(HTTP 오류)는 레코드를 즉시 제거하고, 응답 자체를 받지 못한 네트워크 오류(백그라운드 전환·타임아웃)만 보존해 복구 대상으로 남깁니다. 원 응답과 복구 조회가 경합하면 저장된 `requestId`와 레코드 선점으로 한쪽만 결과를 반영해 부수효과(카운터 증가·채팅 생성)가 이중 실행되지 않습니다. 단, 퍼널 이탈 후(언마운트 상태) 도착한 원 응답은 성공·실패 모두 레코드를 소비하지 않고 남깁니다 — 화면에 반영할 곳이 없는 상태에서 레코드만 지우면 제작 탭의 이어서 만들기 배너가 사라지고 결과 접근 경로를 잃기 때문이며, 성공 부수효과와 결과 반영은 재진입 시 복구 조회가 수행합니다. 스토리라인 성공은 즉시 편집 자동 저장본으로 바꾸고, 완성 성공은 채팅 성공 전까지 진행 레코드를 유지합니다.
- **재시도 멱등·409 복구** — 실패한 같은 스토리라인 생성 또는 같은 페이로드의 완성 재시도는 저장된 `requestId`를 재사용해 서버 멱등 계약([`4-backend.md §4-3-2`](./4-backend.md))으로 중복 생성·중복 과금을 막습니다. 재사용 요청이 409(`PENDING` 재POST)로 거절되면 실패로 처리하지 않고 같은 레코드의 복구 폴링으로 결과를 되찾습니다.
- **이탈 가드 상호작용** — 복구로 복원된 단계에서도 이탈 가드([§3-1-4](#3-1-4-스토리-생성-퍼널))는 동일하게 활성입니다(키워드 단계 제외 규칙 그대로).
- **재진입 복원 범위** — 완성 단계 레코드는 스토리라인 결과·선택 스토리라인·활성 순번·자유 입력·추천 선택을 함께 보관해, 재진입 후 실패 합류 시에도 추가 정보 화면을 토글 상태까지 그대로 복원합니다. 완성 결과가 이미 생겼다면 저장된 `storyId`로 채팅 생성만 이어갑니다.
- **이어서 만들기 배너** — 미정리 레코드(진행 중 요청 또는 임시 저장본)가 있으면 제작(`/studio`) 콘텐츠 상단에 추가 여백 없이 배너를 표시합니다. 배너 패딩은 위·아래 12px, 왼쪽 16px, 오른쪽 2px이고 안내 문구는 보통 굵기입니다. 홈에는 표시하지 않습니다(KNK-988). 문구는 완성 진행 중이면 "완성 중인 스토리가 있어요", 그 외(스토리라인 생성 중·임시 저장본)는 "만들고 있는 스토리가 있어요"입니다. 레코드 존재만 확인하며(서버 조회 없음), 닫기(X) 없이 primary 색상 텍스트의 기본 크기 ghost "이어서 만들기" CTA만 제공합니다. CTA 탭 시 퍼널로 이동해 복구 또는 임시 저장 재개 흐름에 합류합니다(KNK-994). 배너가 나타나고 사라질 때는 주변 레이아웃을 접지 않고 200ms 투명도 페이드만 적용하며, 모션 감소 환경에서는 즉시 전환합니다(KNK-999).

### 제작 자동 저장 — `Phase 1 · 구현`(KNK-648·994)

사용자가 이탈·새로고침·백그라운드 전환을 해도 마지막 편집을 잃지 않게, 퍼널 입력을 백그라운드 복구와 **같은 단일 슬롯**에 자동 저장합니다(Android PR #5 결과 패리티). 편집이 바뀌면 즉시 헤더에 `임시 저장중` 뱃지를 표시하고 마지막 변경 뒤 **300ms**가 지난 시점에 영속합니다. 299ms까지는 쓰지 않고 300ms 경계부터 쓰며, 성공하면 `임시 저장됨`으로 바꿉니다. 쓰기가 실패하면 완료로 오인시키지 않고 뱃지를 숨깁니다. 이탈·백그라운드 전환 직전에는 남은 디바운스를 즉시 flush합니다.

- **키워드 저장 범위** — `KEYWORD_DRAFT`에 제공 장르 선택, 직접 추가 장르(선택 해제된 항목 포함), 주인공·주변 인물의 이름·성별·제공 특징 선택·직접 추가 특징(선택 해제 포함)을 보관합니다. 처음부터 놓인 빈 주변 인물 한 장만 있는 상태는 입력으로 보지 않습니다. 현재 열어 둔 카테고리 탭은 저장하지 않고 재개 시 첫 탭에서 시작합니다.
- **생성 이후 저장 범위** — 스토리라인 생성 성공 결과는 응답 직후 `STORY_DRAFT`로 즉시 저장합니다. 이후 활성 스토리라인 순번, 선택 스토리라인, 자유 입력 행의 원형(빈 행 포함), 추천 선택, 이미 생성된 `storyId`, 마지막 완성 요청(`requestId` 포함)을 편집마다 300ms 자동 저장합니다. 추천 선택은 자유 텍스트와 분리해 토글 상태 그대로 복원합니다.
- **단일 슬롯 우선순위** — 서버 작업이 실제로 돌 수 있는 진행 레코드(`STORYLINE_GENERATION`·`STORY_COMPLETION`)가 모든 자동 저장본보다 우선합니다. 진행 레코드는 지연 도착한 draft 쓰기로 덮지 않습니다. 생성 결과가 있는 `STORY_DRAFT`는 키워드 단계에서 예약됐다가 늦게 도착한 `KEYWORD_DRAFT`보다 우선합니다. 요청 시작·성공·실패 전환과 자동 저장 쓰기는 이 순서를 깨지 않게 직렬화합니다.
- **완성 멱등 승계** — 스토리는 생성됐지만 채팅 생성 전에 실패·이탈한 경우 `storyId`와 마지막 완성 요청을 유지합니다. 같은 화면 또는 재진입 후 재시도는 스토리를 다시 만들지 않고 채팅만 생성합니다.
- **재개** — 제작 탭 배너의 "이어서 만들기"는 재개 의도를 일시 저장소에 남기고(웹: 세션스토리지 `manyak:story-draft-resume-intent`) 퍼널로 이동해, 묻지 않고 저장된 단계를 복원합니다. draft가 있는 제작 화면에서 FAB·빈 상태 CTA를 누르면 이동하기 전에 현재 화면에서 "만들고 있는 스토리가 있어요 / 새로 만들면 임시 저장된 내용은 사라져요" 다이얼로그를 열어 이어서 만들기·새로 만들기를 고릅니다. 이 다이얼로그는 바깥 영역 또는 Escape로 닫을 수 있고, 닫아도 현재 경로와 저장본을 유지합니다. 딥링크로 퍼널에 바로 진입한 경우에는 같은 다이얼로그를 퍼널에서 표시하되 빈 편집 상태가 저장본을 덮지 않도록 선택 전에는 닫히지 않습니다. 선택 전에 불필요한 화면 전환을 만들지 않기 위한 흐름입니다(KNK-994, 2026-08-27 결정). 다이얼로그는 기존 작업을 보존하는 `이어서 만들기`를 오른쪽 primary 버튼으로, 저장본을 폐기하는 `새로 만들기`를 왼쪽 secondary 버튼으로 표시합니다. `이어서 만들기`는 레코드를 **소비하지 않고** 복원하므로 새 편집이 저장되기 전에도 새로고침 복원이 유지됩니다. `새로 만들기`는 기존 레코드를 먼저 폐기한 뒤 빈 키워드 단계에서 시작합니다.
- **재개 의도를 URL이 아닌 스토리지에 두는 이유(웹 구현 사유)** — 쿼리 파라미터(`?resume=1`)로 먼저 구현했으나, 라우터 캐시가 있는 재진입에서는 컴포넌트 마운트가 히스토리 URL 반영보다 먼저 일어나 파라미터를 놓칩니다. 스토리지 쓰기는 이동 전에 동기적으로 끝나 전환 타이밍과 무관합니다.
- **로그아웃 정리** — 로그아웃(명시적 로그아웃·세션 만료 자동 로그아웃)하면 슬롯을 전량 삭제합니다. 로그아웃 시 분석 디바이스 ID가 재발급되어 진행 중 레코드는 복구 조회 소유 판정([`4-backend.md §4-3-2`](./4-backend.md))을 통과할 수 없고, 공용 기기에서 다음 사용자에게 제작 내용이 노출되는 것도 막습니다. 반대로 **로그인 시에는 유지**합니다 — 같은 기기의 게스트 진행·임시 저장본은 로그인 후에도 서버가 디바이스 해시·귀속(claim) 계약으로 이어가기를 지원하므로, 체험 한도 로그인 유도 직후 흐름이 끊기지 않습니다.
- **정리·범위 밖** — 자동 저장본은 `새로 만들기`, 새 요청에 따른 우선 레코드 교체, 생성 완료 뒤 채팅 성공, 로그아웃으로 정리합니다. 제작 배너에서는 저장본을 폐기하지 않습니다. 서버 저장·기기 간 동기화·만료(TTL)는 범위 밖입니다.

### 검수 기준

- 키워드 → 스토리라인 → 추가정보 → 완성 시 채팅 화면으로 이동해야 합니다. (US-3, e2e `stories/story-create`)
- 필수 카테고리 미충족 상태에서도 다음 버튼은 활성화되어야 하며, 누르면 푸터 오류를 표시하고 현재 카테고리를 유지해야 합니다. 키워드를 선택하면 오류가 사라져야 합니다.
- 빈 커스텀 키워드로 "추가하기"를 누르면 입력창 아래에 오류가 표시되고, 유효한 값을 입력하면 오류가 사라져야 합니다.
- 스토리라인 생성 요청 중에는 버튼 크기를 유지한 스피너와 다음 단계의 로딩 화면이 연속으로 표시돼야 합니다.
- 완성 실패 시 입력을 유지한 채 재시도할 수 있어야 하며, 재시도가 스토리를 중복 생성하지 않아야 합니다.
- 로컬 게스트 카운터가 한도에 도달하면 스토리라인·스토리 요청을 보내지 않아야 합니다. 서버 402를 받으면 사유에 맞는 다이얼로그를 표시하고 현재 단계의 입력·선택을 유지해야 합니다. (US-10-4·5, e2e `stories/story-create-limit`)
- 키워드 편집은 299ms까지 영속되지 않고 300ms에 영속돼야 하며, 새로고침·백그라운드 전환 직전에는 예약된 저장을 flush해 재진입 시 복원해야 합니다. 저장 중/완료 뱃지는 실제 쓰기 상태와 일치해야 합니다. (KNK-994, unit `draft-autosave`, e2e `stories/story-create-draft`)
- 생성·완성 대기 중 응답을 못 받고 퍼널을 재진입하면 3초 복구 조회로 진행 상태·결과를 되찾아야 하며, 백그라운드에서는 폴링을 멈추고 복귀 시 재개해야 합니다. 네트워크 오류와 같은 요청의 409는 레코드·`requestId`를 유지하고 복구 흐름에 합류해야 합니다. (e2e `stories/story-create-recovery`)
- 헤더 X로 나가면 별도 임시 저장 토스트 없이 제작 화면으로 이동하고, 제작 탭 배너의 "이어서 만들기"로 저장된 단계가 복원돼야 합니다. (KNK-988·994, e2e `stories/story-create-draft`)
- 임시 저장본이 있는 제작 화면에서 FAB·빈 상태 CTA를 누르면 경로를 바꾸기 전에 이어서/새로 만들기를 묻고, 딥링크 진입은 퍼널에서 같은 다이얼로그를 표시해야 합니다. "새로 만들기"는 저장본을 폐기하고 키워드 단계부터 시작해야 합니다. (e2e `stories/story-create-draft`)
- 추가 정보가 있는 상태에서 재선택 취소는 입력을 유지하고, 파괴적 확정은 선택·입력·추천을 모두 초기화해야 합니다. 추가 정보 첫 렌더에서는 스토리라인 길이와 무관하게 레이아웃 점프가 없어야 합니다. (e2e `stories/story-create`)
- 채팅 생성 실패 뒤 같은 화면과 재진입에서 재시도해도 스토리 생성은 한 번뿐이어야 합니다. (e2e `stories/story-create`)

## 3-1-5. 채팅 플레이와 SSE 스트리밍

FE-SCREEN-005의 상세입니다. 실시간 AI 출력이 이 앱에서 가장 복잡한 경로이므로 스트리밍 계약과 렌더 규칙을 명확히 정의합니다.

### 턴 모델

- 채팅은 스토리 상세 또는 퍼널 완료에서 `POST /chats {storyId, startSettingId}`로 생성됩니다(`startSettingId`는 상세에서 선택한 시작 설정, 생략 시 첫 번째). 채팅 목록에서는 생성하지 않습니다.
- **턴** = 사용자 입력 + AI 출력 + 다음 선택지입니다. 사용자 입력과 AI 출력은 응답이 완료될 때 한 턴으로 저장됩니다.
- 채팅 화면은 `GET /chats/{id}`로 스토리 제목·프롤로그·턴 목록·추천 입력을 조회합니다.
- 렌더 순서: 프롤로그 버블 → 각 턴(사용자 버블 → AI 버블) → 진행 중 스트리밍 블록.
- 선택지는 **마지막 턴에만** 표시합니다. 턴이 0개면 시작 화면의 추천 입력을 선택지로 표시합니다.

### SSE 스트리밍 계약

채팅 턴은 사용자 입력을 본문에 실은 `POST` 요청의 응답을 SSE로 받는 계약입니다([`4-backend.md §4-3-3`](./4-backend.md)). 표준 SSE 클라이언트 다수가 GET 전용이라 각 플랫폼은 POST 본문을 실을 수 있는 SSE 수신을 직접 구현해야 하며(웹: `fetch`+`ReadableStream` — 결정 기록은 [`3-2-web-app.md §3-2-2` SSE 클라이언트 구현](./3-2-web-app.md#sse-클라이언트-구현-웹) / 앱: [`3-3-android-app.md §3-3-2`](./3-3-android-app.md)에서 확정), 그 귀결로 **이벤트 파싱과 스트림 종료 감지는 클라이언트 책임**입니다. `completed`·`error` 없이 EOF로 끝나는 종료도 클라이언트가 처리합니다 — 전송·재생성 두 경로 모두 실패로 확정하고 상세 refetch로 서버 확정본을 반영합니다(`Phase 1 · 구현` KNK-741).

- **요청** — `POST /chats/{id}/turns/stream`, 헤더 `Accept: text/event-stream` + `X-Manyak-*` 식별자, 본문 `{userInput}`(서버 검증 상한 3000자, 프론트는 별도 차단 없음).
- **이벤트 계약** (원천: [`4-backend.md §4-3-3`](./4-backend.md))

| 이벤트          | 데이터 필드          | 프론트 처리                                                                                                                                   |
| --------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `started`       | —                    | 수신만(무동작)                                                                                                                                |
| `token`         | `text`               | 현재 위치의 텍스트 조각에 누적해 부분 렌더                                                                                                    |
| `character_image` | `name`, `imageUrl` | `Phase 2 · 구현`(KNK-1013). 이벤트를 받은 즉시 현재 스트리밍 위치에 인물 이미지 조각을 추가. 같은 이벤트가 다시 오면 이미지도 다시 추가      |
| `completed`     | `chatId`, `turnId`, `aiOutput`, `choices`, `reachedEnding` | 상세 refetch로 확정 턴을 받은 뒤 진행 중 조각 목록과 한 번에 교체. 클라이언트는 `completed`의 별도 이미지 목록에 의존하지 않음 |
| `error`         | `message`            | 실패 토스트                                                                                                                                   |

- `token`은 `data: {"text":"..."}`(JSON) 또는 원문 텍스트를 모두 허용합니다.
- **스트리밍 순서의 정본은 이벤트 도착 순서입니다 — `Phase 2 · 구현`(KNK-1013·1015).** 진행 중 AI 출력은 하나의 문자열이 아니라 순서가 있는 `text | character_image` 조각 목록으로 관리합니다. `token`은 마지막 조각이 텍스트면 그 조각에 이어 붙이고, `character_image`는 현재 위치에 새 이미지 조각을 추가하며, 그다음 `token`은 이미지 뒤의 새 텍스트 조각으로 시작합니다. AI 서버는 이미지가 있는 인물의 `이름:` 토큰보다 `character_image`를 먼저 보내므로, 클라이언트는 이미지 → 인물명 → 대사 순서를 그대로 표시합니다. 이름 기준 정렬·중복 제거·`completed`까지 표시 지연은 금지합니다.
- **인물 이미지가 먼저 나온 뒤 턴이 실패한 경우 — `Phase 2 · 구현`(KNK-1013).** 이미지도 텍스트 토큰과 같은 미확정 스트리밍 결과입니다. `error` 이벤트가 오면 낙관적 사용자 버블과 진행 중 텍스트·이미지 조각을 함께 제거합니다. `completed`·`error` 없는 EOF는 서버 저장 여부를 알 수 없으므로 기존 EOF 규칙대로 상세를 refetch하고, 저장된 턴이 있으면 확정 `aiOutput`의 `[[URL]]` 마커로 복원하며 없으면 진행 중 조각을 제거합니다. 실패한 턴의 이미지만 화면에 남겨 확정 이력처럼 보이게 하지 않습니다.
- `completed` 수신 시 진행 중 조각을 즉시 지우지 않습니다. 상세 재조회가 성공한 프레임에 서버 확정 턴의 조각 목록으로 한 번에 교체해, 본문·이미지가 사라졌다 다시 나타나거나 URL 마커가 한 프레임 노출되지 않게 합니다. 완료 후 채팅 목록을 무효화해 미리보기·시각을 갱신합니다.
- 클라이언트와 백엔드 사이의 전달 계층은 SSE 청크를 버퍼링하지 않아야 합니다(웹: BFF 프록시 스트리밍 통과 — [`3-2-web-app.md §3-2-4`](./3-2-web-app.md#3-2-4-bff-프록시토큰-세션)).
- **타임아웃** — 백엔드 쪽 상한은 두 층이고 종료 모양이 다릅니다(값·근거의 정본은 [`4-backend.md §4-3-3`](./4-backend.md)): 클라이언트향 SSE **전체 상한**을 넘기면 `error` 이벤트 **없이** 스트림이 닫히고(클라이언트는 EOF로 관측 — 위 예외 처리), 백엔드→AI의 **이벤트 간 idle** 상한을 넘기면 `AI_STREAM_FAILED` `error` 이벤트가 옵니다. 클라이언트에는 자체 타임아웃이 없습니다(웹 사유: 채팅 스트림이 공용 요청 계층 `fetchWithTimeout`을 우회해 맨 `fetch`를 사용) — FIN 없이 끊긴 연결은 백엔드 상한에 기대 종료됩니다([§3-1-9](#3-1-9-mvp-제외-범위와-스펙-구현-간극) G5).

### 입력창과 선택지

- **입력 모드** — 일반 텍스트 모드와 블럭 모드(상황·대사)를 제공합니다. 두 모드는 같은 전송·추천 입력 규칙을 사용합니다. 블럭의 X(입력 삭제) 버튼은 탭 순서에서 제외해 키보드 포커스가 블럭 인풋 사이를 바로 오가게 합니다(터치·클릭으로는 계속 삭제 가능).
- **입력이 있을 때** — 전송 버튼에 위쪽 화살표 아이콘을 표시합니다. 공백 제거 후 1자 이상이고 스트리밍 중이 아닐 때 `Enter`(Shift 없이, IME 조합 아님)·폼 제출·버튼으로 전송합니다. 일반 모드 텍스트에어리어는 최대 `20dvh`까지 자동 확장합니다.
- **입력이 없을 때** — 현재 추천 입력이 1개 이상이면 전송 버튼을 filled 재생 아이콘으로 표시하고 활성화합니다. 누르면 현재 추천 입력 중 하나를 무작위로 골라 즉시 전송합니다. 추천 입력도 없으면 같은 아이콘을 유지한 채 버튼을 비활성화합니다.
- **채팅 턴 이프 비용** — 회원에게는 전송 버튼 바로 왼쪽 8px 위치에 `N 이프`(서버 정책의 `chatTurnCost` — [§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시))를 12px 보조 전경색으로 표시합니다. 블럭·일반 입력 모드와 위쪽 화살표·랜덤 전송·응답 대기 스피너 상태에서 같은 위치를 유지합니다. 게스트는 이프가 아니라 체험 턴 수를 사용하므로 이 문구를 표시하지 않습니다(KNK-1045·1095).
- **응답 대기 스피너 — `Phase 1 · 구현`(KNK-694)** — 스트리밍 중에는 전송 버튼의 아이콘(화살표·재생 공통)을 스피너로 바꿔 응답을 받는 중임을 알립니다(스크린 리더 라벨 "응답을 받는 중"). 두 입력 모드와 응답 재생성에 동일하게 적용하며, 완료·실패로 스트리밍이 끝나면 원래 아이콘으로 돌아옵니다. 버튼은 스피너 표시 중에도 전송 잠금 규칙대로 비활성 상태입니다. 2026-07-28 이전에는 "별도 스피너를 표시하지 않는다"였으나, 응답 대기 중 아무 피드백이 없어 이 규칙으로 대체했습니다.
- **추천 입력 소스** — 턴이 0개면 상세 응답의 `suggestedInputs`, 턴이 있으면 마지막 턴의 `choices`를 사용합니다.
- **선택지** — 각 선택지에 "채우기"(입력창에 채워 편집)와 "전송"(바로 제출) 버튼을 둡니다. 추천 입력 목록은 컨테이너 위에서 12px 띄우고 항목끼리는 8px 간격을 둡니다. 본문은 14px MaruBuri, 자간 -2%, 행간 175%(24.5px)를 사용합니다(KNK-1029). 바로 전송 시 상황(`*...*`)과 대사를 빈 줄로 구분해 정규화한 뒤 전송합니다(블럭 입력 전송과 동일한 포맷). **등장은 항목이 차례로 흐르는 모션입니다** — 각 항목이 8px 아래에서 300ms(ease-out) 동안 올라오며 나타나고 항목마다 80ms씩 늦게 출발하며, 1회성 인라인 힌트도 첫 항목으로 셉니다. 로딩 스켈레톤과 생성 실패 안내도 같은 모션을 씁니다(실패 안내는 한 덩이로). 같은 묶음은 한 번만 흐릅니다 — 목록이 길어 추천이 화면 밖으로 나갔다 돌아와도 다시 흐르지 않고, 스켈레톤 → 추천처럼 내용이 바뀐 때만 다시 흐릅니다.
- **블럭 순번과 개수 상한** — 블럭 모드의 각 입력 라벨에 종류별 순번을 붙입니다("상황 1", "대사 1"). 순번 자리는 두 자리 폭으로 미리 잡아 한 자리에서 두 자리로 넘어가도 입력 글자의 시작 위치가 밀리지 않습니다. 같은 종류가 여럿일 때 방금 늘어난 칸이 어느 것인지 라벨만 보고 알 수 있게 하는 표시이며, 순번은 화면 표시 전용이라 전송 본문에는 싣지 않습니다. 블럭은 상황·대사를 합쳐 **최대 50개**이고, 상한에 닿으면 두 추가 버튼을 비활성화합니다. 모드 전환·추천 채우기로 파싱된 블럭은 상한을 넘을 수 있습니다 — 문장을 잘라 버리지 않기 위해 파싱 결과는 그대로 두고 추가 버튼만 잠급니다. 칸을 더하면 아래에서 자라 오르고 지우면 같은 변을 붙잡은 채 접히며, **목록이 높이 상한에 걸려 스크롤 중이면 더한 칸이 보이도록 끝까지 따라 내려갑니다** — 접힌 자리에 생기면 추가가 일어났는지 보이지 않습니다. 모드 전환·추천 채우기·전송 뒤 초기화처럼 목록 전체가 갈리는 경로는 칸별 모션 없이 한 번에 교체합니다.
- **강조 삽입** — "상황 추가" 버튼이 선택 영역을 `*...*`로 감쌉니다.
- **전송 잠금** — 스트리밍 중에는 컴포저·입력창·버튼이 모두 비활성화됩니다(전송 버튼은 비활성 상태로 스피너를 표시).
- **추천 입력 토글 — `Phase 1 · 구현`(KNK-622·643)** — 선택지(추천 입력) 생성을 응답 스트림에서 분리합니다(2026-07-20 팀 합의 — [`4-backend.md §4-3-3`](./4-backend.md)). 인풋 애드온 줄(입력 모드 메뉴 왼쪽)에 추천 입력 on/off 드롭다운 메뉴(AI 말풍선 아이콘 트리거)를 둡니다 — 켬/끔 라디오 항목(라벨+설명)에서 선택하고, on이면 트리거 아이콘을 primary 색으로 표시합니다. 토글 on이면 `completed` 수신·상세 refetch(본문 확정) 후 선택지 생성 API(`POST /chats/{id}/turns/{turnId}/choices`)를 호출합니다(본문 확정과 선택지 도착 사이의 지연은 수용 — 본문이 먼저 확정되는 체감 개선이 목적). 응답 200은 저장 완료 신호이며 렌더 소스가 아닙니다 — 상세를 한 번 더 재조회해 마지막 턴 `turns[].choices`로 표시합니다(기존 경로 재사용 — 2026-07-20 프론트 합의, `completed`의 `choices`는 항상 빈 배열이라 렌더 소스로 쓰지 않음). 토글 off면 호출하지 않으며, 표시 중이던 마지막 턴 선택지도 숨깁니다(빈 입력의 무작위 추천 전송 대상에서도 제외 — 서버 데이터는 유지되므로 다시 켜면 재호출 없이 재표시). off 상태로 턴이 끝난 뒤 토글을 켜면 같은 API로 마지막 턴의 선택지만 생성합니다. flag 없이 "API를 부르는가"로 on/off를 처리합니다. 토글 기본값은 on이고 변경값은 로컬 저장소에 기기 단위로 기억합니다(저장 수단·키는 플랫폼 소유 — [§3-1-6](#3-1-6-게스트-데이터-모델) 저장 구조와 동일 원칙). 트리거 전환과 토글 UI는 KNK-643에서 함께 구현했습니다(2026-07-21). 백엔드 내부 호출 제거(stopgap, [`4-backend.md §4-8`](./4-backend.md) B23)는 후속입니다. 선택지 생성은 무료이며 마지막 턴만·턴당 1회 멱등 계약입니다([`4-backend.md §4-3-3`](./4-backend.md)). 선택지 로딩은 선택지 자리의 스켈레톤 칩 3개로 표시하고, 도착하면 교체합니다. 실패하면 선택지 자리에 에러 문구와 재시도 버튼을 표시하고, 재시도는 같은 API를 다시 호출합니다(선택지가 없어도 직접 입력으로 채팅은 계속 진행 가능).

### 첫 진입 안내 — `Phase 1 · 구현`(KNK-694)

처음 채팅을 시작한 사용자에게 입력 영역 사용법을 안내합니다. 안내 대상은 진입 경로와 무관하게 생애 첫 채팅방 진입 사용자 전원이며, 온보딩 경유 여부는 따지지 않습니다.

- **노출 조건** — 로컬 저장소(웹 키: `manyak:chat-tour-seen`)에 열람 기록이 없고, 턴 0개(프롤로그와 첫 추천만 있는 상태)이며 스트리밍 중이 아닐 때 짧은 지연 뒤 1회 자동 노출합니다. 노출 시점에 열람 기록을 남깁니다. 조건을 만족하지 않는 방(이미 대화가 진행된 방)에서는 노출하지 않고 기록도 남기지 않습니다. 기기 단위 1회이며 **재열람 진입점은 두지 않습니다**. 로컬 저장소 접근이 막힌 환경에서는 기록이 남지 않아 진입마다 다시 노출될 수 있으며, 이는 허용합니다.
- **형태** — body로 포털되는 오버레이(딤 + 대상 컷아웃 하이라이트 + 말풍선 카드)입니다. 앱 프레임 내부가 아니라 다이얼로그와 같은 층에 그리므로 앱 프레임 안의 `fixed` 사용 제약([3-2-web-app.md §3-2-3](./3-2-web-app.md#3-2-3-라우팅레이아웃공통-셸))에 걸리지 않습니다. 투어 중 뒤 화면 상호작용은 오버레이가 막고, "다음"으로 진행하며 언제든 "건너뛰기"로 닫을 수 있습니다.
- **카드 배치** — 카드는 뷰포트가 아니라 앱 프레임(`max-w-md`) 안에 둡니다. 기본은 하이라이트 중앙 정렬이고, 대상이 좌우 끝이라 중앙에 둘 수 없으면 그쪽 하이라이트 변에 카드 변을 맞춥니다(프레임 여백에만 맞추면 카드가 하이라이트보다 안쪽으로 들어가 어긋나 보이기 때문). 세로는 하이라이트 기준 남은 공간을 `max-height`로 걸어 문구가 길어져도 화면을 벗어나지 않습니다.
- **스텝(3개)** — ① 상황·대사 추가 버튼 ② 추천 입력 토글 + 입력 모드 메뉴 ③ 전송(랜덤) 버튼. 첫 스텝은 입력 모드에 따라 갈립니다 — 블럭 모드는 두 추가 버튼을 함께 잡아 "입력창이 하나 늘어난다"로, 일반 모드는 대사 추가 버튼이 없으므로 상황 추가 버튼만 잡고 강조 마커(`*...*`) 삽입 동작으로 안내합니다. 화면에 대상이 없는 스텝은 건너뛰고, 모든 스텝의 대상이 없으면 투어를 열지 않습니다.
- **추천 입력은 투어 대상이 아닙니다** — 추천 입력은 메시지 스크롤 영역 안에 있어 프롤로그가 길면 화면 밖으로 밀려나고, 그때 설명만 뜨고 대상이 보이지 않는 문제가 있었습니다. 대신 첫 추천 목록 바로 위에 **1회성 인라인 힌트**를 콘텐츠로 함께 렌더합니다(두 줄: "AI가 추천하는 입력이에요" / "탭하면 바로 전송되고, 연필 버튼으로 고쳐서 보낼 수 있어요"). 추천과 같이 스크롤되므로 위치가 어긋나지 않습니다. 노출 기록은 투어와 별도 플래그(웹 키: `manyak:chat-choices-hint-seen`)로 관리하며, 턴 0개 화면에서 노출된 순간 기록합니다(같은 방에 머무는 동안은 유지, 재진입부터 미노출).
- **계측** — 투어는 노출·스텝 도달·완주·건너뛰기 4종을 수집합니다([`6-analytics.md §6-4-2-6`](./6-analytics.md)). 인라인 힌트는 별도 이벤트를 두지 않습니다.

### 렌더와 스크롤

- **부분 렌더** — `token`이 누적되는 동안 AI 버블에 실시간 텍스트를 표시하고, `character_image`가 오면 같은 버블의 해당 위치에 이미지를 즉시 표시합니다. 첫 표시 가능 이벤트(`token` 또는 `character_image`) 전에는 "작성 중" shimmer 로딩(스크린 리더 라벨 "답변을 작성하고 있어요")을 표시하고, 이미지가 먼저 오면 첫 토큰을 기다리지 않고 로딩을 이미지로 교체합니다.
- **본문 타이포그래피·패딩** — 프롤로그·사용자 입력·AI 출력은 16px MaruBuri, 자간 -2%, 행간 175%(28px)를 사용합니다. MaruBuri 자간과 행간은 웹 공통 스타일 한 곳에서 관리해 스트리밍 로딩·스토리 제작 본문·추천 입력에도 같은 비율을 적용합니다. 사용자·AI 메시지 영역은 위·아래 20px, 좌우 16px을 확보합니다(KNK-1029).
- **강조 마크업** — `**볼드**`는 굵게, `*...*`는 서술·독백 강조로 렌더합니다.
- **진입 스크롤 위치** — 턴이 있는 방은 마지막 메시지 위치에서, 턴이 0개인 방은 프롤로그가 보이도록 상단에서 시작합니다.
- **새 턴 앵커** — 전송하면 새 턴(사용자 버블 + 스트리밍 블록)을 뷰포트 상단에 이전 메시지와의 여백 없이 밀착해 앵커하고, 텍스트·이미지 조각이 추가돼도 화면이 끌려 내려가지 않습니다. 스트리밍 중 사용자가 옮긴 스크롤 위치는 완료(상세 refetch) 후에도 유지됩니다.
- **하단 이동 버튼** — 스크롤이 하단에 있지 않으면 "맨 아래로 이동" 버튼을 표시합니다. 스트리밍 중에도 동일하게 동작합니다(진행 스피너 대체는 KNK-643에서 제거 — 2026-07-21).
- **헤더 show/hide** — 상단 근처·위로 스크롤 시 표시, 아래로 스크롤 시 숨깁니다. 스크롤된 위치로 진입하면(마지막 메시지 앵커) 등장 없이 처음부터 숨긴 채 시작합니다. 숨긴 헤더는 보조기술·포커스 대상에서도 제외합니다(웹: `aria-hidden`·`inert`). 헤더 back은 `/chats`로 이동합니다.

### 입력 설정 메뉴와 삭제

입력 모드·추천 입력 설정은 입력 툴바의 드롭다운 메뉴에 두고, 채팅 삭제는 헤더 우측 옵션 메뉴(⋮)에 둡니다. 헤더 우측은 공유 버튼 + 옵션 메뉴 두 개이며, 공유 발급은 위 [채팅 공유하기](#채팅-공유하기--phase-1--구현)가 정의합니다.

- **입력 설정** — 입력 툴바(추가 버튼들 오른쪽)에 추천 입력 on/off 메뉴와 입력 모드 메뉴를 나란히 둡니다. 둘 다 라디오 항목(라벨 + 설명)으로 고르는 드롭다운이며, 상세 계약은 위 [입력창과 선택지](#입력창과-선택지)의 "추천 입력 토글"을 따릅니다.
- **옵션 메뉴** — 헤더 우측 ⋮ 버튼이 드롭다운을 열고, 항목은 destructive "삭제하기" 하나입니다(KNK-715에서 "채팅 삭제하기"를 축약 — 공유 항목이 빠져 메뉴가 채팅 단일 대상이 되었으므로 목적어를 생략).
- **삭제 흐름** — "삭제하기" → 확인 다이얼로그("채팅을 삭제할까요?") 표시 → 확정 시 낙관적 삭제([§3-1-6](#3-1-6-게스트-데이터-모델)과 동일 규칙: 204 완료 토스트, 404 무음 성공) 후 `/chats`로 `replace`합니다. 확정 버튼은 요청 중 문구 공간을 유지한 중앙 스피너("삭제 중")로 잠깁니다.
- 채팅 목록(FE-SCREEN-004)에는 삭제 진입점이 없으며 이 옵션 메뉴가 유일한 삭제 경로입니다.
- 2026-07-16(KNK-611)에 우측 설정 드로어(입력 모드 선택 + 삭제 버튼)를 걷어내고 위 구조로 바꿨습니다. 이 절의 드로어 서술은 그때 갱신되지 않아 2026-07-28에 현재 구현으로 맞췄습니다.

### 응답 재생성과 채팅 이미지

응답 재생성은 `Phase 1 · 구현`, 배경 이미지는 `Phase 1 · 계획`, 인물 이미지는 `Phase 2 · 구현`입니다.

**재생성 버튼** — 마지막 턴의 AI 버블 하단에 "다시 생성" 버튼을 둡니다(US-6-10). 마지막 턴에만 표시하고, 스트리밍 중에는 전송 잠금과 같은 조건으로 비활성화합니다. 버튼 터치 영역 아래 20px과 추천 입력 목록 위 12px을 합쳐 첫 추천 입력까지 32px을 확보합니다(KNK-1029). 엔딩 도달 턴(`reachedEnding` 존재)에는 버튼을 표시하지 않습니다 — 서버도 동기 409로 거부합니다([`4-backend.md §4-3-9`](./4-backend.md)).

**재생성 흐름** — 클릭 → `POST /chats/{id}/turns/regenerate/stream {turnId}`(SSE 이벤트 계약은 턴 진행과 동일) → 기존 마지막 AI 버블·선택지를 스트리밍 블록으로 대체 → `completed` 수신 시 상세 refetch로 서버 확정본을 표시합니다. 사용자 입력 버블은 그대로 유지합니다. 서버는 이전 출력을 버전 이력으로 보존하지만([`4-backend.md §4-8`](./4-backend.md) B11) 상세 조회·SSE에는 활성본만 실리므로, 프론트엔드 화면 계약은 변하지 않습니다.

**재생성 실패 처리** — 실패 종류에 따라 다르게 처리합니다.

- **`error` 이벤트 수신** — 서버가 교체하지 않았음이 보장되므로([`4-backend.md §4-3-9`](./4-backend.md)) 기존 본문·선택지를 복원하고 실패 토스트를 표시합니다.
- **네트워크 실패·EOF(`completed`·`error` 없이 종료)** — 서버 교체 성공 후 전달만 끊겼을 수 있어 결과 불명입니다. 기존 본문을 임의로 복원하지 않고 상세 refetch로 서버 확정 상태를 표시합니다(교체됐으면 새 본문, 아니면 기존 본문).
- **402** — 턴 진행과 동일하게 이프 부족(회원)·로그인(게스트) 다이얼로그를 띄우고 기존 본문을 유지합니다.
- **409**(이미 새 턴이 추가된 낡은 화면) — 상세 refetch로 최신 상태를 반영합니다.

**배경 이미지 렌더** — 공통 계약은 `확정`이고 웹·백엔드·AI 서버 구현은 모두 `미구현`입니다(위 상태 정본 표). 배경 이미지는 별도 턴 필드가 아니라 **`aiOutput` 본문 안의 이미지 마커**로 옵니다(US-6-11). 어떤 장면에 어떤 이미지를 삽입할지는 AI가 응답 생성 중 결정하고 서버가 마커를 검증하며([`4-backend.md §4-3-9`](./4-backend.md) B10 — 이미지는 전부 팀 제작 자산), 클라이언트는 본문 렌더 시 마커 위치에 이미지를 표시하기만 합니다.

- **마커 포맷은 확정됐습니다**(2026-07-10 팀 합의) — 본문 인라인 `[[image:<imageKey>]]` 1종이고, 서버가 검증한 목록이 `completed`·상세 응답의 `images[]`(`{imageKey, type, url}`)로 동봉됩니다(정본: [`4-backend.md §4-3-9`](./4-backend.md)). 남은 선행 조건은 AI 서버 계약 정렬이며 [`4-backend.md §4-8`](./4-backend.md) B10이 추적합니다.
- **무효 마커는 마커 텍스트째 숨깁니다** — `images[]`에 없는 키의 마커는 이미지를 띄우지 않는 데 그치지 않고 `[[image:…]]` 문자열 자체를 출력하지 않습니다. 사용자에게 마커 원문이 보이는 것은 어떤 경우에도 계약 위반입니다.
- 이미지 로드 실패 시 이미지 영역을 제거하고 본문만 표시합니다.

**인물 이미지 렌더 — `Phase 2 · 구현`(KNK-1013·1015).** 위 배경 마커와 별개로, 인물 이미지는 스트리밍 중에는 `character_image` 이벤트로, 저장 뒤에는 `aiOutput` 본문 안의 저장 마커로 전달합니다(정본: [`4-backend.md §4-3-9`](./4-backend.md) · [`5-ai-server.md §5-3-4`](./5-ai-server.md)). AI·백엔드 중계·저장과 웹의 스트리밍·확정 턴 렌더까지 구현됐습니다. 클라이언트 렌더 규칙은 다음과 같습니다.

- **적용 경로** — 새 턴 이어쓰기, 마지막 응답 재생성, 채팅 상세와 공유 열람은 같은 조각 렌더 규칙을 사용합니다. 재생성 중에는 기존 AI 본문·이미지를 진행 중 조각 목록으로 대체하고, 완료 시 새 저장 마커 결과로 교체합니다. 명시적 `error`면 기존 확정 본문·이미지를 함께 복원합니다. 공유 열람도 저장 마커를 숨기는 데 그치지 않고 원본 채팅과 같은 위치의 이미지를 표시합니다.
- **진행 중 렌더** — `character_image`를 받는 즉시 AI 메시지의 현재 위치에 이미지 블록을 추가합니다. 이미지 이벤트 뒤에 해당 인물의 `이름:`과 대사가 `token`으로 이어지므로, 아직 오지 않은 글자를 기다리거나 완료 본문에서 위치를 다시 추측하지 않습니다. 같은 인물이 같은 턴에서 다시 말하면 새 이벤트마다 같은 이미지를 다시 표시합니다. 다만 웹 허용 목록(운영 `cdn.manyak.app`·개발 `dev-cdn.manyak.app`의 HTTPS `/characters/generated/**` 또는 `/characters/originals/**`) 밖의 URL은 이미지 조각에 추가하지 않습니다. 사용자 생성 스토리는 `generated`, 오리지널 스토리는 `originals` 경로를 사용합니다(KNK-1055).
- **저장 마커 `[[URL]]`** — `completed` 뒤 상세 refetch, 재진입, 공유 열람에서 받는 턴의 `aiOutput`에서 이미지가 표시된 대사(`인물명:` 줄) 바로 앞에 독립된 한 줄로 오고, 마커와 대사 사이에는 빈 줄 하나가 있습니다. 웹은 마커가 독립된 한 줄 전체이고, 뒤에 빈 줄 하나를 사이에 둔 다음 줄이 비어 있지 않은 `인물명:` 라벨로 시작하며, URL이 위 생성·오리지널 인물 이미지 허용 목록에 속할 때만 `text | character_image` 조각으로 바꿉니다. 이미지 대체 텍스트에 쓸 이름은 뒤 대사 라벨에서 가져옵니다. 세 조건 중 하나라도 어긋난 마커 모양 문자열은 제거하거나 이미지로 요청하지 않고 일반 본문으로 유지합니다. 유효한 마커의 글자와 URL 원문은 출력하지 않으며 그 위치에 이미지를 표시합니다. 위치는 마커가 알려 주므로 별도 이미지 목록에 의존하지 않습니다. 같은 인물이 여러 번 말하면 마커 횟수만큼 표시합니다. 웹 PR이 머지되기 전에 AI 계약이 이 형식으로 전환됐으므로 이전 `[[인물이름:URL]]` 형식은 지원하지 않습니다(KNK-1014, 2026-08-28).
- **스트리밍→확정 교체** — 진행 중 `character_image`와 확정 저장 마커는 같은 위치·순서·횟수를 표현합니다. 상세 refetch가 끝날 때 전체 조각 목록을 원자적으로 교체하며, 이벤트 이미지와 저장 마커 이미지를 동시에 렌더해 중복시키지 않습니다.
- **레이아웃·접근성** — 이미지는 AI 메시지 본문 안의 독립된 가로 4:3 블록으로 렌더합니다(현행 생성 자산 `1024×768`, 정본: AI 서버 `IMAGE_SIZE`). **이미지는 AI 메시지 양쪽에서 16px씩 띄우고, 20px 곡률과 전체 1px 시맨틱 보더를 적용합니다.** 앞 텍스트 조각과 이미지 사이는 40px, 이미지와 뒤 텍스트 조각 사이는 20px을 띄웁니다(KNK-1029). 이미지가 메시지의 첫 조각이면 별도 상단 여백을 추가하지 않습니다. 텍스트 조각과 엔딩 배지도 기존 좌우 16px 패딩을 유지해 이미지·본문의 좌우 기준선을 맞춥니다. 이벤트 수신 즉시 여백 안쪽의 가로 4:3 영역을 예약해 로드 완료로 본문이 크게 밀리지 않게 하고, 별도 등장 지연이나 완료 대기 애니메이션을 두지 않습니다. 원본 전체가 보이도록 비율을 유지하며 자르지 않습니다. 대체 텍스트는 `"{name} 인물 이미지"`로 제공합니다. 인물 이름 캡션은 바로 뒤의 대사 라벨과 중복되므로 추가하지 않습니다.
- **로드 실패** — 깨진 이미지 아이콘·대체 텍스트·URL 원문을 남기지 않고 해당 이미지 블록만 제거합니다. 앞뒤 텍스트와 이후 스트리밍은 계속 표시합니다.

**결정 기록 — 인물 이미지를 `completed`에서 일괄 표시하지 않음(KNK-1015)**

- **배경.** 완료 본문의 `[[URL]]` 마커만 해석하면 텍스트는 토큰 단위로 보이다가 응답이 끝나는 순간 이미지가 한꺼번에 나타납니다. 저장·재진입에는 충분하지만 실시간 응답이라는 사용자 기대(US-6-3·6-11)를 충족하지 못하고, 이미지가 본문의 어느 대사보다 먼저 등장했는지도 생성 중에는 알 수 없습니다.
- **결정.** 진행 중 화면은 `character_image`를 수신 즉시 이벤트 위치에 표시하고, 완료·재진입 화면만 저장 마커를 사용합니다. 두 경로는 공통 `text | character_image` 조각 렌더 모델을 사용합니다.
- **영향.** SSE 파서는 `character_image`를 버리지 않아야 하고 스트리밍 상태는 단일 `aiOutput` 문자열만으로 표현할 수 없습니다. 완료 후 상세 refetch는 복구·저장 정합성을 위한 것이며 이미지 최초 노출 시점을 늦추는 게이트가 아닙니다.

### 엔딩 도달 표시 — `Phase 1 · 구현`

엔딩 도달 여부는 서버가 판정하고([`4-backend.md §4-3-10`](./4-backend.md) KNK-522·523·527), 클라이언트는 값 유무로만 렌더합니다 — 채팅 이미지와 같은 원칙입니다.

- **도달 턴 배지 — `Phase 1 · 구현`.** 완료 후 상세 refetch의 턴 항목에 `reachedEnding`이 있으면 해당 AI 응답의 가장 위 왼쪽에 `엔딩 · {엔딩 이름}` 배지를 표시합니다(US-6-13). 스토리 제작의 "임시 저장됨" 배지와 같은 primary 10% 배경·primary 전경색·보조 배지 크기를 사용하고, 긴 이름은 버블 폭 안에서 줄바꿈합니다(KNK-1012). 스트리밍 중 임시 응답에는 표시하지 않고 서버가 확정한 턴에만 표시합니다.
- **도달 후 계속 진행 — `Phase 1 · 구현`.** 엔딩 도달이 입력을 잠그지 않습니다. 입력창·선택지는 일반 턴과 동일하게 동작하고(잠금 조건은 스트리밍 여부뿐 — [입력창과 선택지](#입력창과-선택지)의 전송 잠금), 이후 턴은 배지 없는 일반 턴으로 이어집니다(US-6-14). 서버도 도달 후 턴 진행을 계속 허용합니다. **재생성 버튼만 예외로 도달 턴에서 숨깁니다**(위 재생성 절 — 서버가 409로 거부).
- **본 엔딩 집계(게스트) — `Phase 1 · 계획`.** 스토리 상세의 본 엔딩 배지(FE-SCREEN-003)는 게스트의 경우 로컬 서재 채팅의 배치 조회 응답 `reachedEndings`를 스토리별로 합산해 구성해야 합니다. 현재 웹은 상세 응답 값만 렌더하므로 회원 표시는 구현됐지만, 항상 빈 배열을 받는 게스트 합산은 남아 있습니다. 로컬 서재가 비면 표시되지 않는 기기 종속 한계는 게스트 서재([§3-1-6](#3-1-6-게스트-데이터-모델))와 동일하게 수용합니다.

### 채팅 공유하기 — `Phase 1 · 구현`

공유 시점까지의 채팅을 읽기 전용 링크로 다른 사람에게 보여주는 기능입니다(US-6-17·6-18). 서버 계약은 [`4-backend.md §4-3-11`](./4-backend.md)이 정의합니다.

**발급** — 헤더 우측 옵션 메뉴(⋮) 왼쪽에 share 아이콘 버튼(접근 이름 "채팅 공유하기 버튼")을 둡니다. 클릭하면 바로 발급하지 않고 확인 다이얼로그를 먼저 엽니다 — 링크를 받은 사람은 누구나 대화를 볼 수 있으므로, 공개 범위를 알린 뒤 사용자가 확정하게 합니다(KNK-715).

- **다이얼로그 구성** — 제목 "이 채팅을 공유할까요?", 설명 "이 링크가 있으면 누구든지 내가 지금까지 이어온 채팅을 볼 수 있어요", 하단 버튼 두 개(왼쪽 "나중에 하기" 보조 스타일 · 오른쪽 "링크 복사하기" 주 스타일, 같은 폭). 타이틀은 의도(공유)를 묻고 확정 버튼은 실제 동작(링크 복사)을 예고합니다 — 버튼까지 "공유"라 하면 공유 시트 등 다른 결과를 기대하게 되기 때문입니다. 닫기(X) 버튼은 없고 "나중에 하기"·배경 탭·ESC로 발급 없이 닫습니다.
- **확정** — "링크 복사하기"를 누르면 `POST /chats/{id}/shares`로 공유를 발급하고, 응답의 공유 식별자로 `{서비스 origin}/share/{shareId}` URL을 만들어 클립보드에 복사한 뒤 "채팅 공개 링크가 복사되었어요" 토스트를 표시하고 다이얼로그를 닫습니다 — 문구는 모든 플랫폼 공통이며 이 문서가 정본입니다(웹 구현 위치: `src/constants/toast-message.ts`).
- **실패** — "공유 링크 생성에 실패했어요" 토스트를 표시하고 다이얼로그를 유지해 재시도할 수 있게 합니다.
- **진행 중** — 확정 버튼은 문구 공간을 유지한 중앙 스피너("복사 중")로 전환되고, 두 버튼과 배경 탭·ESC 닫기가 모두 잠깁니다.
- 턴이 0개인 채팅에서도 발급을 막지 않습니다(프롤로그만 보이는 공유).

**결정 기록 — 공유 진입점을 옵션 메뉴에서 헤더 버튼으로 (KNK-715)**

- **배경.** 최초 구현은 옵션 메뉴(⋮) 안의 "채팅 공유하기" 항목이었습니다. 공유는 이 화면에서 사용자가 자발적으로 하는 유일한 확산 행동인데 메뉴를 열어야 보여 발견되지 않았습니다. 헤더 우측에는 홈 버튼이 있었지만 하단 네비의 홈 탭과 목적지가 같아 중복이었습니다.
- **결정.** 홈 버튼을 걷어내고 그 자리에 share 아이콘 버튼을 둡니다. 옵션 메뉴에는 삭제 항목만 남습니다. 메뉴 항목처럼 문구로 의도를 말할 수 없으므로 의미는 아이콘과 접근 이름이 담습니다.
- **영향.** 옵션 메뉴 항목이 하나로 줄어 구분선이 없어집니다. 분석 이벤트(`client_chat_shareButton_clicked`)는 이름·프로퍼티 그대로 유지해 진입점 변경 전후의 발급 추이를 이어서 보고, 다이얼로그 도입에 맞춰 노출·이탈 이벤트(`client_chatShareDialog_shown`·`_dismissed`)를 추가해 노출 대비 확정 전환을 관찰합니다([`6-analytics.md §6-4-2-6`](./6-analytics.md)).

**열람 화면(FE-SCREEN-012)** — `GET /shares/{id}` 응답을 채팅 화면과 같은 렌더 규칙으로 표시하되, 상호작용 요소를 모두 제거합니다.

- **유지** — 프롤로그 버블 → 각 턴(사용자 버블 → AI 버블) 렌더 순서, 강조 마크업(`**볼드**`·`*...*`), 엔딩 배지(`reachedEnding`), 하단 이동 버튼, 헤더 show/hide. 배경 이미지 마커 렌더도 채팅 화면과 동일합니다(도입 시). 유효한 인물 이미지 저장 마커(`Phase 2 · 구현`, KNK-1013·1015)도 채팅 화면과 같은 위치의 이미지로 표시하고, 마커 글자와 URL은 숨깁니다.
- **제거** — 입력창(컴포저), 선택지·추천 입력, 재생성 버튼, 옵션 메뉴, 온보딩, 스트리밍 관련 UI 전부. 열람은 완결된 스냅샷이므로 SSE·refetch가 없습니다.
- **헤더** — 뒤로가기 대신 서비스 로고(홈 링크)와 스토리 제목을 표시합니다. 열람자는 앱 내 이력 없이 외부에서 진입하기 때문입니다. 인앱 브라우저 탈출 안내([3-2-web-app.md §3-2-5](./3-2-web-app.md#3-2-5-반응형접근성브라우저-지원))도 같은 로고 홈 링크 헤더를 씁니다.
- **안내 문구** — 대화 위에 "친구가 공유한 채팅을 보고 있어요"를 표시합니다. 외부 링크로 바로 진입한 사람은 자기가 무엇을 보고 있는지 알 단서가 없으므로, 읽기 전용 스냅샷이라는 맥락을 첫 화면에서 알려 줍니다.
- **하단 CTA** — "나만의 스토리 만들고 채팅하기" 버튼을 항상 고정해 스토리 생성 퍼널(`/studio/story/simple`)로 **직결**합니다. 제작 탭을 거치지 않는 이유는 공유 열람이 이미 서비스를 보여준 상태라 한 단계 더 두면 이탈만 늘기 때문입니다. 같은 이유로 클릭 시 온보딩을 본 것으로 기록해, 만들기 후 메인 탭에 돌아왔을 때 온보딩 게이트([3-2-web-app.md §3-2-3](./3-2-web-app.md#3-2-3-라우팅레이아웃공통-셸))를 다시 마주치지 않게 합니다.
- **진입 스크롤** — 처음부터 읽는 것이 목적이므로 항상 프롤로그가 보이는 상단에서 시작합니다.
- **진입 애니메이션** — 로딩 스피너가 열람 화면으로 교체될 때 헤더·대화·CTA를 포함한 화면 전체를 채팅 화면과 같은 150ms로 페이드인합니다. 메시지를 순차 등장시키는 연출은 두지 않습니다.
- **로드 실패** — 404(삭제된 채팅·잘못된 링크)를 포함한 로드 실패 시 "공유된 채팅을 찾을 수 없어요" 안내와 홈(`/`) 이동 링크를 표시합니다.

**링크 미리보기** — 서버가 공유본을 읽어 제목에 스토리 제목, 설명에 프롤로그 발췌, 이미지에 스토리 썸네일을 담은 오픈그래프 메타데이터를 만듭니다. 공유 열람 응답에는 썸네일이 없어 스토리 상세(`GET /stories/{storyId}`, 공개 식별자 접근)를 한 번 더 조회하며(KNK-713 — 카드가 스토리별로 구별돼야 공유 유입 전환에 유리합니다), 썸네일이 없거나 조회에 실패하면 루트의 브랜드 오픈그래프 이미지가 쓰입니다. 공유본 조회에 실패하면 제목·설명 없이 색인 차단만 담은 기본값을 돌려주고 페이지는 그대로 띄웁니다 — 미리보기가 비는 것이 페이지가 뜨지 않는 것보다 낫기 때문입니다. 이때 탭 제목은 기본 문서 제목으로 남으므로, 화면이 클라이언트에서 공유본을 받은 뒤 `제목 - 마냑`으로 덮어써 채팅방과 형식을 맞춥니다([3-2-web-app.md §3-2-3](./3-2-web-app.md#3-2-3-라우팅레이아웃공통-셸) 문서 제목).

공유 URL의 플랫폼 공통 계약은 세 가지입니다: ① 로그인·게스트 구분 없이 누구나 열람할 수 있고, ② 열람은 열람자의 로컬 서재([§3-1-6](#3-1-6-게스트-데이터-모델))에 아무것도 저장하지 않으며, ③ 분석 이벤트·Sentry에 공유 식별자를 싣지 않습니다([`6-analytics.md §6-4-2-14`](./6-analytics.md)). 검색 색인 정책(유효 공유본 색인 허용, 조회 불가 URL의 `noindex, nofollow`)은 웹 소유입니다([3-2-web-app.md §3-2-3](./3-2-web-app.md#3-2-3-라우팅레이아웃공통-셸) 색인 범위, KNK-713).

### 검수 기준

- 프롤로그와 추천 입력을 표시해야 합니다. (US-6-1)
- 메시지를 전송하면 응답이 스트리밍되어 누적되어야 합니다. (US-6-2·6-3)
- 전송한 턴은 뷰포트 상단에 앵커되어 토큰 누적이 화면을 끌어내리지 않아야 하고, 스트리밍 중 옮긴 스크롤 위치가 완료 후에도 유지돼야 합니다.
- 헤더 옵션 메뉴에서 채팅을 삭제하면 완료 안내 후 채팅 목록으로 돌아가야 합니다. (US-5-3, e2e `chats/chat-room`)
- 추천 입력의 수정 버튼은 입력창을 채우고, 본문 탭은 바로 전송해야 합니다. (US-6-4)
- 스트리밍이 실패하면 오류 안내가 떠야 합니다. (US-6-8, e2e `chats/chat-room`)
- 응답을 받는 동안 전송 버튼에 스피너가 표시되고, 완료되면 원래 아이콘으로 돌아와야 합니다. (KNK-694, e2e `chats/chat-room`)
- 투어 미열람 + 턴 0개 채팅에 진입하면 안내 투어가 1회 자동 노출되고, 완주·건너뛰기 후 재진입 시 다시 뜨지 않아야 합니다. 일반 입력 모드에서는 첫 스텝이 상황 추가 버튼만 안내해야 합니다. (KNK-694, e2e `chats/chat-tour`)
- 안내 카드는 앱 프레임 좌우 여백과 화면 위아래를 벗어나지 않아야 합니다. (KNK-694, e2e `chats/chat-tour`)
- 첫 추천 입력 위에 인라인 힌트가 1회 표시되고, 재진입 시에는 보이지 않아야 합니다. (KNK-694, e2e `chats/chat-tour`)
- 로컬 게스트 채팅 카운터가 5회에 도달하면 스트림 요청을 보내지 않아야 합니다. 서버 402를 받으면 실패한 낙관적 버블을 제거하고 사유에 맞는 다이얼로그를 표시해야 합니다. (US-10-4·5, e2e `chats/chat-guest-limit`)
- `Phase 1` 다시 생성 시 마지막 AI 응답이 새 본문으로 교체되고 사용자 입력 버블은 유지돼야 합니다. `error` 이벤트 시 기존 본문이 복원되고, `completed`·`error` 없는 종료 시에는 refetch 결과(서버 확정 상태)가 표시돼야 합니다. (US-6-10)
- `Phase 1` `aiOutput` 본문에 이미지 마커가 포함된 턴은 마커 위치에 이미지가 표시돼야 하고, 마커가 없는 턴에는 이미지가 없어야 합니다. (US-6-11)
- `Phase 2` 인물 이미지: 스트리밍 중 허용된 `character_image` 이벤트가 도착하면 `completed` 전에 그 위치에 이미지가 즉시 표시돼야 하고, 뒤따르는 인물명·대사는 이미지 다음에 토큰 단위로 계속 나타나야 합니다. 같은 인물의 이벤트가 다시 오면 다시 표시돼야 합니다. 완료·상세·공유 화면에서는 유효한 `[[URL]]` 마커 글자와 URL이 보이지 않고 같은 위치·순서·횟수의 이미지가 표시돼야 하며, 스트리밍→확정 교체 중 이미지가 사라지거나 중복되지 않아야 합니다. 허용 CDN·독립 줄·빈 줄 하나·뒤따르는 인물명 대사 라벨을 충족하지 않는 값은 이미지로 요청하지 않고 본문으로 유지해야 합니다. `error` 또는 저장되지 않은 EOF 뒤에는 미확정 텍스트·이미지를 함께 제거합니다. (KNK-1013·1015, e2e `chats/chat-room`·`share/shared-chat`)
- 엔딩에 도달한 뒤에도 입력·선택지가 정상 동작해 다음 턴을 이어갈 수 있어야 합니다. 단 엔딩 도달 턴에는 재생성 버튼이 표시되지 않아야 합니다. (US-6-14)
- `Phase 1` `reachedEnding`이 있는 확정 턴에는 AI 응답 최상단 왼쪽에 `엔딩 · {이름}` 배지가 표시돼야 합니다. (US-6-13, KNK-1012, e2e `chats/chat-room`·`visual/chats-visual`)
- `Phase 1` 선택지에 주요 사건 방향 제안이 포함돼야 합니다 — 구성 자체는 AI 계약이 담보하므로([`5-ai-server.md §5-3-5`](./5-ai-server.md)) 프론트엔드는 3개 렌더만 검수합니다. (US-6-12)
- 헤더 공유 버튼으로 공유 URL이 클립보드에 복사돼야 합니다. 헤더 우측에 홈 버튼은 없어야 합니다. (US-6-17, KNK-715, e2e `chats/chat-share`)
- 공유 열람 화면은 발급 시점까지의 턴만 표시하고, 입력창·선택지·재생성 등 상호작용 요소가 없어야 합니다. 로그인하지 않은 사용자도 열람할 수 있어야 합니다. (US-6-18, e2e `share/shared-chat`)
- 공유 열람의 하단 CTA는 스토리 생성 퍼널로 바로 이동하고, 이후 홈 진입에서 온보딩이 다시 뜨지 않아야 합니다. (e2e `share/shared-chat`)

## 3-1-6. 게스트 데이터 모델

> **앱 비적용** — 안드로이드 앱은 로그인 필수라 이 계약이 적용되지 않습니다. 예외 전체 목록은 [`3-3-android-app.md §3-3-1`](./3-3-android-app.md)입니다.

게스트 모드의 "내 스토리·채팅"은 서버의 사용자 소유 목록이 아니라 **클라이언트가 로컬에 보관한 공개 ID 배열**로 구성합니다. 회원 모드는 [FE-SCREEN-008](#3-1-3-화면별-스펙)의 서버 정본 목록을 사용합니다. 사용자가 보는 목록의 동작을 좌우하므로 게스트 저장 구조를 계약으로 정의합니다. 식별자 정책은 [`6-analytics.md §6-2`](./6-analytics.md)를 따릅니다.

### 저장 구조

데이터 항목·형식·정리 규칙은 플랫폼 공통 계약입니다. 저장 수단과 실제 키 이름은 플랫폼 소유입니다 — 웹 `localStorage` 키의 정본은 [`3-2-web-app.md §3-2-2` 게스트 저장소 키](./3-2-web-app.md#게스트-저장소-키-웹), 안드로이드 저장 기술·키는 [`3-3-android-app.md §3-3-4`](./3-3-android-app.md)에서 확정합니다.

| 데이터 항목             | 내용                                            | 형식(논리)                                       |
| ----------------------- | ----------------------------------------------- | ------------------------------------------------ |
| 생성 스토리 ID 목록     | 생성한 스토리의 공개 ID                         | 문자열 배열, 최신순                              |
| 생성 채팅 ID 목록       | 생성한 채팅의 공개 ID                           | 문자열 배열, 최신순                              |
| 게스트 사용량 카운터    | 스토리라인 생성·스토리 제작·채팅 성공 누적 횟수 | `{storylineCreate, storyCreate, chat}` 정수 객체 |
| 온보딩 열람 플래그      | 온보딩 열람 여부                                | 불리언성 플래그                                  |

- **상한 100개**. 저장 시 맨 앞에 추가하고 중복을 제거한 뒤 100개로 자릅니다. 101번째를 만들면 가장 오래된 ID가 로컬 목록에서 밀려납니다(서버 레코드는 유지).
- 저장 값은 공개 식별자만 담습니다. 민감 정보·토큰을 저장하지 않습니다.
- 손상된 값은 방어적으로 무시합니다(JSON·배열이 아니면 빈 목록).
- 게스트 사용량은 0 이상의 정수만 인정하고 누락·손상 값은 0으로 보정합니다. 카운터 도입 전에 만든 스토리가 있으면 저장된 스토리 ID 개수로 `storyCreate`를 보정합니다. 로그인·자동 이관이 끝나면 게스트 사용량을 삭제합니다.

### 상태 판정

저장소를 아직 읽지 못한 "알 수 없음"과 읽었더니 "비어 있음"을 구분해야 합니다 — 구분하지 않으면 데이터가 있는 사용자에게도 "빈 서재 → 목록" 깜빡임이 보입니다. 알 수 없음은 로딩으로, 빈 배열은 빈 상태로, 값이 있으면 배치 조회 후 목록으로 처리하고, 온보딩 노출 조건도 "알 수 없음"이 해소된 뒤에 판정합니다(FE-SCREEN-007). 웹은 SSR·하이드레이션 특성상 이 구분이 필수라 3-state(`null`/`[]`/`string[]`)로 구현합니다(결정 기록: [`3-2-web-app.md §3-2-2` 게스트 서재 상태 판정](./3-2-web-app.md#게스트-서재-상태-판정-웹)). 앱은 저장소 읽기 구조에 따라 같은 계약(깜빡임 없음)을 충족하는 방식을 [`3-3-android-app.md §3-3-4`](./3-3-android-app.md)에서 확정합니다.

### 배치 재조회

- 스토리: `POST /stories/batch {storyIds}`, 채팅: `POST /chats/batch {chatIds}`. ID가 비어 있으면 요청하지 않습니다.
- 배열이 커질 수 있어 `GET`이 아닌 `POST` 본문으로 전달합니다. 서버 상한도 100입니다.
- **정렬 기준이 목록마다 다릅니다.** 스토리 목록은 로컬 저장 순서(최신 생성순)로 재정렬하고, 채팅 목록은 서버 응답 순서(최근 활동순)를 유지합니다.
- 서버가 반환하지 않은 ID(삭제됨 등)는 목록에서 조용히 제외됩니다.

### 쓰기·삭제

- **쓰기** — 게스트는 스토리 생성 성공 시 스토리 ID, 채팅 생성 성공 시 채팅 ID를 저장합니다. `Phase 1 · 구현` — 회원 모드는 로컬에 저장하지 않습니다. 회원 생성분은 서버가 `user_id`로 귀속하고 서버 정본 목록([FE-SCREEN-008](#3-1-3-화면별-스펙))에 나타납니다.
- **삭제(낙관적)** — 현재 ID를 스냅샷한 뒤 로컬에서 먼저 제거하고 삭제 API를 호출합니다. 204 성공 시에만 완료 토스트를 띄우고, 404는 이미 삭제된 것으로 보아 토스트 없이 로컬 제거를 유지합니다. 그 외 오류는 로컬 목록을 롤백하고 실패 토스트를 표시합니다.
- **동기화** — 저장 변경 시 열려 있는 목록 화면이 즉시 갱신됩니다(웹은 같은 탭·다른 탭 모두 — 멀티 탭은 웹 전용 조건).

## 3-1-7. API 연동·에러 처리 계약

API 상세 명세는 [`4-backend.md`](./4-backend.md)가 소유합니다. 여기서는 클라이언트가 무엇을 호출하고 무엇에 의존하며 실패를 어떻게 처리하는지 정의합니다. API 경로는 `/api/v1` prefix를 생략해 표기합니다. 웹의 호출 창구(BFF 프록시)와 회원 토큰 세션은 [`3-2-web-app.md §3-2-4`](./3-2-web-app.md#3-2-4-bff-프록시토큰-세션)가 소유합니다.

### 요청 헤더

클라이언트는 익명 식별 헤더를 **best-effort**로 주입하고, 요청 상관관계(request id)는 백엔드가 완성합니다. 값·정책은 [`6-analytics.md §6-6`](./6-analytics.md), 백엔드 수용 계약은 [`4-backend.md §4-3` 요청·응답 헤더](./4-backend.md)를 따릅니다.

**클라이언트가 주입하는 헤더** — 논리 식별자 값이 있을 때만 싣습니다(웹은 Amplitude Browser SDK가 채운 값 — [`6-analytics.md §6-2`](./6-analytics.md), Android 매핑은 미정).

| 헤더                  | 값                     |
| --------------------- | ---------------------- |
| `X-Manyak-Device-Id`  | 논리 `device_id`       |
| `X-Manyak-Session-Id` | 논리 `session_id`      |

두 헤더가 없어도 일반 요청은 거부되지 않습니다(백엔드가 `unknown`으로 채움). 단 **`X-Manyak-Device-Id`가 정책상 필수인 경로**가 있습니다 — 게스트 체험 한도 대상 요청(누락 시 400 — [`4-backend.md §4-3-7`](./4-backend.md)), 로그인 핸드오프 생성(`POST /auth/handoffs`), 핸드오프 없는 첫 로그인의 회원 체험 시드([`4-backend.md §4-3-5`](./4-backend.md)). `X-Manyak-Session-Id`는 모든 경로에서 best-effort입니다.

- SDK 초기화 전(콜드 로드) 첫 요청은 폴백 소스에서 읽고(웹: SDK가 남긴 쿠키), 값이 없으면 해당 헤더를 생략합니다.
- 클라이언트 앱 코드는 `X-Manyak-Request-Id`를 생성·주입하지 않습니다. `Phase 1 · 구현` — 회원 인증 토큰은 앱 코드에 노출되지 않는 계층이 다룹니다. 웹에서는 브라우저 JS가 `Authorization`을 붙이지 않고 BFF 프록시가 httpOnly 쿠키의 access 토큰을 `Authorization` 헤더로 주입하며([3-2-web-app.md §3-2-4](./3-2-web-app.md#3-2-4-bff-프록시토큰-세션)), 앱의 토큰 주입 구조는 [`3-3-android-app.md §3-3-4`](./3-3-android-app.md)에서 확정합니다.

**백엔드가 처리하는 상관관계** — `X-Manyak-Request-Id`가 없으면 백엔드가 생성해 응답 헤더로 echo합니다(백엔드는 수신 헤더가 있으면 그 값을 우선하지만, 클라이언트 앱은 이 헤더를 만들지 않습니다 — [`4-backend.md §4-3` 요청·응답 헤더](./4-backend.md)). 퍼널의 생성 요청 **본문**에 싣는 `requestId`([§3-1-4](#3-1-4-스토리-생성-퍼널) 백그라운드 생성 복귀)는 멱등·복구용 별개 값이며 이 헤더와 무관합니다. device/session 헤더가 없어도 요청을 막지 않고 `unknown`으로 채운 뒤 경고 로그만 남깁니다.

**프론트가 채팅·스토리라인 요청에 추가로 싣는 값 — `Phase 1 · 구현`(KNK-707·KNK-751).** 백엔드가 AI 호출을 Langfuse 트레이스로 연결하는 데 쓰는 값으로, 값 자체는 백엔드가 헤더로 변환해 forward합니다([`4-backend.md §4-7`](./4-backend.md)).

- 채팅 턴 요청(`POST /chats/{chatId}/turns/stream`)에 `userSource`(선택, `"choice" | "edited_choice" | "typed"`)를 추가합니다 — 추천 선택지를 그대로 보낸 경우 `choice`, 고쳐서 보낸 경우 `edited_choice`, 직접 입력한 경우 `typed`입니다. 문자열만으로는 서버가 구분할 수 없어 프론트가 명시해야 하며, 허용값 밖의 값은 400입니다([`4-backend.md §4-3`](./4-backend.md)).
- 같은 채팅 턴 요청에 `sourceTurnId`(직전 턴의 `turnId` = 채팅 상세 `turns[].id`)와 `choiceOrder`(선택지 순번)를 함께 실으면 백엔드가 어느 선택지를 골랐는지, 원문 그대로 보냈는지를 DB에 기록합니다(`Phase 1 · 구현` — 서버 KNK-819·웹 KNK-822, [`4-backend.md §4-3-3`](./4-backend.md)). `choiceOrder`는 `turns[].choices` 배열의 **인덱스 + 1**입니다 — 0부터 보내면 400이 아니라 조용히 기록만 누락됩니다. 두 값 모두 선택 필드라 보내지 않아도 요청은 정상 처리되고, 값이 낡았거나(그새 턴이 진행됨) 범위 밖이어도 400·409가 아니라 기록만 생략되므로 프론트는 방어 없이 값을 그대로 보내면 됩니다. 시작 추천 입력과 직접 입력에는 원본 턴 선택지가 없으므로 두 값을 보내지 않습니다.
- 스토리라인 생성 재요청이 재생성(다시 만들기)일 때 **바로 직전** 시도의 `trace_creation_id`(AI 트레이스 연결 ID — 요청 필드 이름은 `parentCreationId`, 값은 스토리라인 요청 UUID)를 함께 보내면(체인 방식으로 확정 — 매번 최초 시도가 아니라 바로 이전 시도의 값, KNK-755) 백엔드가 검증 후 `X-Manyak-Parent-Creation-Id`로 AI에 forward합니다. 보내지 않으면 헤더가 생략되고 서버는 신규 진행으로 취급합니다 — 스토리라인 재생성은 전용 API가 없어 서버가 원본과의 연결을 스스로 알 수 없기 때문입니다. 백엔드가 검증에 실패해도(부모 미존재·소유 불연속 등) 400이 아니라 헤더만 조용히 생략되므로, 프론트엔드는 실패를 방어할 필요 없이 값을 그대로 보내기만 하면 됩니다([`4-backend.md §4-7`](./4-backend.md)). 요청 필드명은 `parentCreationId`(UUID, nullable)이며, 제품 분석 이벤트의 `analytics_creation_id`(`simpleCreationId`)와는 **다른 값**입니다([`6-analytics.md §6-2`](./6-analytics.md)).

**프론트가 값을 정하는 규칙 — `Phase 1 · 구현`(KNK-757).** 위 계약은 값의 의미만 정하고 어느 입력 경로가 어느 값인지는 정하지 않아, 구현에서 아래와 같이 확정했습니다. 판별 로직은 `resolve-user-source`가 소유하고 QA 케이스는 `qa/chats.md` CHAT-INPUT-17 · `qa/stories.md` STORY-LINE-11입니다.

- 선택지 본문 탭과 무작위 추천 전송(Play 버튼)은 대조 없이 `choice`입니다. 두 경로 모두 전송 전에 사용자가 문장에 손댈 기회가 없습니다.
- "채우기"로 입력창에 넣고 보내는 경로는 전송 시점의 텍스트를 채운 원문과 대조해 가릅니다 — 같으면 `choice`, 다르면 `edited_choice`입니다. 앞뒤 공백 차이는 같은 것으로 보고, **블럭 모드에서 채우면 블럭으로 파싱했다가 다시 직렬화되어 문자열이 달라지므로 그 왕복 결과도 "그대로"로 인정합니다** — 사용자가 손대지 않았는데 `edited_choice`가 되면 선호 신호가 오염됩니다.
- 채운 뒤 내용을 전부 지우고 새로 써도 `edited_choice`입니다. 추천을 본 뒤의 입력이라 순수 `typed`와 구분하는 편이 선호 분석에 유용하고, "고쳐 쓴 것"의 극단으로 두는 편이 규칙이 단순합니다. 이는 KNK-757의 현행 구현 기준이며, KNK-762 전환 뒤에는 아래 Langfuse 선호 행동 전달 계약대로 입력을 완전히 비운 시점에 선택지 연결을 지우고 이후 새 입력을 `typed`로 보냅니다.
- 채우기를 쓴 적이 없으면 `typed`입니다. 기억해 둔 원문은 전송에 성공하면 비워, 다음 턴 입력이 앞 턴에서 채운 선택지와 대조되지 않게 합니다.
- 스토리라인은 **최초 생성에도 `parentCreationId`를 `null`로 명시해** 보냅니다. 재생성이 직전 요청 본문을 그대로 재사용하는 구조라, 값을 비워두면 직전 요청의 `parentCreationId`가 딸려와 체인이 부모가 아닌 조부모를 가리킵니다.

### Langfuse 선호 행동 전달 — 연결 기반 `Phase 1 · 구현` · 상세 행동 `Phase 1 · 계획`(KNK-762)

- **무엇.** 클라이언트는 시작 추천 입력과 턴 선택지가 실제로 화면에 표시되고, 사용자가 채우기·바로 전송·무작위 전송·직접 입력 중 무엇을 선택했는지 백엔드에 전달합니다. 기존 `parentCreationId`와 `userSource` 전달은 구현됐고(KNK-755·KNK-757), 선택지 고유 ID와 노출·선택·반영 추적은 KNK-762 계획입니다.
- **왜.** 선택지가 생성됐다는 사실만으로는 사용자가 봤는지 알 수 없고, 문장만 비교하면 같은 문장의 다른 선택지를 구분할 수 없습니다. 다음 턴이 실패했다고 선택 행동까지 없던 것으로 처리하면 사용자가 실제로 누른 신호가 사라지고, 화면이 끊겼다는 이유만으로 실패를 기록하면 서버에 저장된 성공 턴을 실패로 오판할 수 있습니다.
- **어떻게.** 백엔드는 시작 추천 입력과 턴 선택지를 `{choiceId, choiceOrder, text}` 객체로 함께 제공합니다. 기존 `suggestedInputs: string[]`·`choices: string[]`는 클라이언트 전환이 끝날 때까지 유지합니다. 클라이언트는 시작 추천 입력을 `START_SUGGESTION`, 턴 선택지를 `TURN_CHOICE`로 상태에 보존하고 다음 규칙을 적용합니다.

  | 행동 | 클라이언트가 보내는 값 | 시점 |
  | --- | --- | --- |
  | 노출 | `interactionType=PRESENTED`, `choiceSource`, `choiceId` | 항목이 실제 화면 영역에 처음 들어왔을 때 한 번 |
  | 채우기 | `interactionType=SELECTED`, `selectionAction=FILL`, `selectionAttemptId` | 입력창에 채우는 즉시 |
  | 바로 전송 | `interactionType=SELECTED`, `selectionAction=SEND`, `selectionAttemptId` | 선택지를 눌러 전송하는 즉시 |
  | 무작위 전송 | `interactionType=SELECTED`, `selectionAction=RANDOM`, `selectionAttemptId` | 빈 입력에서 시스템이 항목 하나를 고르는 즉시 |

  노출·선택은 백엔드의 공통 선택지 상호작용 기록 API로 비동기 전송하며, API 경로는 백엔드 계약 티켓에서 확정합니다. 기록 성공을 기다리느라 렌더·입력·채팅 전송을 막지 않습니다. 토글로 숨겼거나 화면 밖에 있는 항목은 노출로 보내지 않습니다. `채우기` 뒤에는 `choiceId`·`choiceSource`·원문·`selectionAttemptId`를 입력 상태에 보존하고, 그대로 보내면 `userSource=choice`, 고치면 `edited_choice`를 보냅니다. 입력을 완전히 지운 뒤 새로 쓰면 선택지 연결을 지우고 `typed`로 보냅니다. 폐기된 선택지 때문에 백엔드가 409를 반환하면 최신 채팅 상세를 다시 읽고 과거 선택지 연결만 지우며, 사용자가 작성한 문장은 직접 입력으로 보존합니다. SSE `error`나 요청 거절은 같은 `selectionAttemptId`로 백엔드에 알립니다. `completed`·`error` 없이 연결만 끊기면 결과 미확정으로 두고 실패 행동을 추정하지 않습니다. 자동 테스트는 객체형 선택지 렌더, 실제 화면 노출, `FILL|SEND|RANDOM`, 편집·완전 삭제·직접 입력, 409 복구, 기록 API 장애의 비차단, 결과 미확정 단절을 각각 검증합니다.

  아직 정하지 않은 클라이언트 구현 세부사항은 담당 클라이언트 레포의 선택지 연동 티켓이 결정합니다. 대상은 `selectionAttemptId`의 생성 형식·수명, 노출 감지 방식, 비동기 기록 재시도와 화면 상태 보존 방식입니다. `inputAttemptId`의 생성 주체·형식·수명과 API 경로·필드 자료형·필수 여부·오류 응답은 manyak-server와 담당 클라이언트 레포의 계약 티켓에서 확정합니다. 이 구현 세부사항은 위에서 정한 행동 시점과 성공·실패 판정 규칙을 바꾸지 않습니다.
- **왜 이 방법.** 고유 ID는 문장 비교보다 정확하고, `PRESENTED`·`SELECTED`·다음 턴 저장 결과를 분리하면 “볼 수 있었음”, “눌렀음”, “실제로 반영됨”을 섞지 않습니다. 클라이언트는 화면과 클릭처럼 자신만 아는 사실만 보내고, 소유 관계·현재 활성 선택지·최종 저장 성공은 백엔드가 검증합니다. 행동 기록을 채팅 전송과 분리하면 관측 장애가 사용자 기능을 막지 않습니다. score 이름과 해석은 [`6-analytics.md §6-6-12`](./6-analytics.md), 서버 검증과 발행은 [`4-backend.md §4-7`](./4-backend.md)이 소유합니다.

### 이프 정책 수치 표시

`Phase 2 · 구현`(KNK-1089 — 서버 KNK-1088·웹 KNK-1095). 이프 적립·소모 수치는 **서버가 정본**이며 클라이언트는 화면에 박아 두지 않습니다. 운영 중 이벤트로 값이 바뀔 수 있는데 화면에 복제해 두면 서버만 바꿔도 안내가 거짓말을 하기 때문입니다.

- **출처는 `GET /credits/policies` 하나입니다.** 인증이 필요 없어 게스트 화면에서도 같은 값을 씁니다. 응답은 평평한 6개 필드입니다 — `signupReward` · `inviteReward` · `inviteMonthlyCap` · `attendanceReward` · `storyCreationCost` · `chatTurnCost`. `inviteMonthlyCap`만 이프가 아니라 **초대자 몫의 월 적립 횟수**입니다.
- **수치를 쓰는 자리** — 추가 정보 단계의 스토리 완성 비용(`storyCreationCost`), 회원 채팅 입력창의 턴 비용(`chatTurnCost`), 이프 충전 무료 충전 탭의 출석 제목(`attendanceReward`), 친구 초대 메뉴 보조 문구·초대 화면·초대 온보딩·등록 성공 토스트·카카오 공유 제목(`inviteReward`).
- **문구는 수치를 받아 만듭니다.** 문구 정본은 여전히 클라이언트 상수이되 값을 인자로 받는 빌더 형태이며, 리터럴로 굳은 문자열을 두지 않습니다.
- **응답 전·실패 시에는 자리표시 숫자를 쉬머와 함께 그립니다.** 클라이언트에 대체 수치를 두지 않습니다 — 화면이 들고 있는 값은 서버가 정책을 바꾸는 순간 거짓이 되기 때문입니다. 대신 자릿수만 채운 자리표시 숫자에 쉬머를 얹어 아직 확정되지 않은 값임을 드러내고, 응답이 오면 그 자리에 수치가 들어갑니다. 한 줄짜리 라벨을 비워 두거나 스켈레톤으로 바꾸지 않아 문구의 줄바꿈이 흔들리지 않습니다(웹 구현은 [`3-2-web-app.md`](./3-2-web-app.md) §3-2-2 이프 정책 수치 패칭).
- **토스트·공유 제목처럼 그 순간 문자열이 필요한 자리는 예외입니다.** 쉬머를 얹을 대상이 없으므로 사건이 일어난 시점의 값을 한 번만 읽습니다. 화면을 띄운 뒤 동작하는 흐름이라 그때는 수치가 이미 도착해 있습니다.
- **서비스 안내(FE-SCREEN-011)는 수치를 고지하지 않습니다.** 수치를 모아 보여주는 자리를 두면 각 사용 지점과 이중으로 관리해야 해서 절 자체를 없앴습니다(KNK-1095, 2026-09-01).
- **출시 이벤트처럼 값을 올리는 운영은 서버 정책만 바꿉니다.** 화면에 상시값·이벤트값을 나눠 적지 않습니다 — 서버 필드가 하나뿐이고, 이벤트 종료 시 문구를 되돌리는 작업이 남지 않습니다.

### 날짜 표시 기준

`Phase 2 · 구현`. 서버의 시각 필드(`createdAt` · `expiresAt` · `updatedAt`)는 **ISO 8601 UTC 문자열**입니다([`4-backend.md §4-3` 공통 규칙](./4-backend.md#4-3-api-계약)). 화면에 `YYYY-MM-DD`를 그릴 때는 **KST(`Asia/Seoul`)로 옮긴 뒤** 자릅니다.

- **문자열 앞 10자를 그대로 자르지 않습니다.** UTC 문자열을 자르면 KST 자정~오전 9시(UTC 15:00~24:00)에 벌어진 일이 하루 전으로 표시됩니다. 예: KST 09-02 00:10에 받은 출석 보상(`2026-09-01T15:10:00Z`)이 `2026-09-01`로 보이고, 만료일도 같이 하루 밀립니다.
- **기기 시간대가 아니라 KST로 고정합니다.** 서비스의 하루 경계가 KST로 못박혀 있어서입니다 — 출석 보상 멱등 키가 KST 날짜이고 초대 월 상한도 KST 월 귀속입니다([`4-backend.md §4-3-7`](./4-backend.md#4-3-api-계약)). 기기 시간대를 따르면 해외 접속자에게 "출석은 됐는데 날짜가 다른" 화면이 나옵니다. 서버 렌더 결과가 기기와 갈리지 않는 부수 효과도 있습니다.
- **적용 자리** — 이프 내역의 발생일·만료일(FE-SCREEN-008), 스토리 상세의 생성일(FE-SCREEN-003), 내 스토리 카드의 제작일(FE-SCREEN-013).
- **상대 시간 표기(채팅 목록의 "n시간 전"·"오늘"·"어제")는 이 규칙 밖입니다.** 경과 시간은 시간대와 무관하고, 날짜 경계 판정은 사용자의 체감 시각(기기 시간대)을 따르는 편이 자연스럽습니다.

### 응답·에러 처리 정책

- 읽기 응답은 HTTP 상태로 분기합니다. 정상 상태(200)가 아니면 목록은 빈 배열로, 상세는 에러 상태로 처리합니다.
- 백엔드 에러는 `ApiErrorResponse {timestamp, status, code, message, path, details[]}` 형태이며 `details`는 `{field, message}[]`입니다.
- 읽기 요청은 자동 재시도·화면 복귀 자동 재조회 없이 오류를 예외가 아닌 상태로 반환해, 화면이 인라인으로 처리합니다. 웹 TanStack Query 기본 옵션 값의 정본은 [`3-2-web-app.md §3-2-2` 데이터 패칭 기본 옵션](./3-2-web-app.md#데이터-패칭-기본-옵션-웹)입니다.
- 서버 원본 메시지·스택은 사용자에게 그대로 노출하지 않습니다. MVP는 인증 만료 개념이 없어 401 전용 리다이렉트를 두지 않습니다. `Phase 1 · 구현` — 회원 세션의 401은 토큰 세션 규칙([3-2-web-app.md §3-2-4](./3-2-web-app.md#3-2-4-bff-프록시토큰-세션) — BFF 선제 재발급)이 처리하므로 화면 레벨 리다이렉트는 여전히 두지 않습니다. 재발급까지 실패하면 게스트 모드로 되돌리고 재로그인을 안내합니다.

### 화면 상태 처리 (로딩·빈·에러)

화면별 상태는 각 화면 스펙([§3-1-3](#3-1-3-화면별-스펙))에 정의하며, 공통 규칙은 다음과 같습니다.

| 상황                 | 처리                                                                                |
| -------------------- | ----------------------------------------------------------------------------------- |
| 목록·상세 최초 로딩  | 지연 로딩(빠른 응답 시 스켈레톤 깜빡임 방지). 지연 전에는 아무것도 표시하지 않음    |
| 버튼 클릭 후 요청 중 | 버튼 비활성화 + 기존 문구 공간을 유지한 중앙 스피너. 버튼의 접근 가능한 이름은 유지 |
| 목록 조회 실패       | 재시도 가능한 에러 안내                                                             |
| 뮤테이션 실패        | 실패 토스트                                                                         |
| 라우트·렌더 오류     | "문제가 발생했어요" + 재시도(루트 오류는 Sentry 보고)                               |
| 존재하지 않는 경로   | "페이지를 찾을 수 없어요" + 홈 링크                                                 |

## 3-1-8. 입력·폼 검증 규칙

이 앱의 입력은 피드백·키워드·추가 정보·채팅 입력입니다. 로그인은 소셜 OAuth 버튼뿐이라 검증 대상 입력 폼이 없습니다(`Phase 1 · 구현`, FE-SCREEN-008).

### 일반 제작·수정 폼 — `Phase 1 · 계획`

서버 계약([`4-backend.md §4-3-8`](./4-backend.md))과 동일한 규칙을 클라이언트에서 선검증합니다: 제목 ≤ 100자, 한 줄 소개 ≤ 255자, 시작 설정 이름 ≤ 100자, 장르 1~8개(각 30자 이내), 스토리 설정 4필드·시작 설정 3필드·추천 입력 3개 필수. 주요 사건 ≤ 10개(각 이름·키 문장 필수), 엔딩은 시작 설정당 ≤ 10개(각 이름 필수). 이미지 입력은 없습니다(FE-SCREEN-009, B10). 필수 미충족 섹션은 아코디언 헤더에 상태 배지로 표시하고 등록 버튼을 비활성화합니다.

### 피드백 폼

| 필드  | 타입     | 필수   | 제약                                       | 비고                                                                                                                       |
| ----- | -------- | ------ | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| body  | textarea | 예     | 최대 500자(초과 입력 차단), 글자 수 카운터 | 서버 상한은 2,000자 — 의도된 여유이며 표시 상한은 프론트엔드가 유동 조정([§3-1-9](#3-1-9-mvp-제외-범위와-스펙-구현-간극) G6) |
| email | email    | 아니오 | 최대 320자                                 | 미입력 시 `null` 전송                                                                                                      |

- 제출 버튼은 `body`가 비어 있어도 활성화합니다. 빈 값으로 제출하면 버튼 위에 "피드백 내용을 입력해주세요"를 표시하고 요청하지 않습니다. 유효한 본문을 입력하면 오류를 제거합니다. 이메일은 필수가 아닙니다.
- `platform`은 UI에서 수집하지 않고 자기 플랫폼 값(웹 `WEB`, 안드로이드 `ANDROID`)으로 고정 전송합니다.
- 제출 중에는 입력·버튼을 비활성화하고 버튼 중앙에 `피드백 전송 중` 스피너를 표시합니다.

### 키워드·커스텀 키워드 (퍼널)

- 상한: 장르 키워드 3, 인물별 특징 3, 주변 인물 5명. 상한 도달 시 미선택 칩·추가 트리거 비활성화.
- 커스텀 키워드: 클라이언트 최대 15자(서버 스키마 30자). 빈 값에서도 추가 버튼은 활성화하고, 제출 시 입력창 아래에 오류를 표시합니다. IME 조합 중 Enter는 제출하지 않습니다. 세 카테고리 모두 사용할 수 있습니다.
- 인물 이름: 클라이언트·서버 모두 30자. 주인공과 주변 인물 사이에 겹치는 이름이 있으면 해당 인풋에 오류를 표시하고 생성 요청을 막습니다. 웹은 저장 인물 이미지 마커 충돌을 막기 위해 `]`가 포함된 이름도 인풋·푸터 오류로 막습니다([§3-1-4](#3-1-4-스토리-생성-퍼널) 인물 단위 입력).
- 생성 가능 조건: 장르 1개 이상 그리고 주인공 특징 1개 이상, 겹치는 인물 이름 없음, 웹에서는 `]`가 포함된 인물 이름 없음([§3-1-4](#3-1-4-스토리-생성-퍼널)). 미충족 상태에서 다음 또는 생성 버튼을 누르면 푸터 오류를 표시합니다.
- `Phase 2 · 계획`(KNK-621) — 세계관 탭 개편이 구현되면 장르·배경은 각 1~2개·각 최소 1개 필수가 되고, 생성 가능 조건에 배경 1개 이상이 더해집니다([§3-1-4](#3-1-4-스토리-생성-퍼널) 세계관 탭 개편).

### 추가 정보 (퍼널)

- 추천 추가 정보 토글 + 자유 텍스트 행(추천 추가 정보 최대 3개, 자유 텍스트 UI 최대 10개, 각 100자). 공백 제거 후 비어 있지 않은 값만 전송합니다.
- 전송 페이로드 `additionalInfos`(추천 추가 정보 + 자유 텍스트)의 서버 검증 상한은 총 13개입니다.

### 채팅 입력

- 서버 검증 상한 3000자. 프론트는 `maxLength`·길이 검사가 없어 초과 입력을 차단하지 않습니다.
- 입력이 있으면 위쪽 화살표 아이콘으로 전송하고, 입력이 없고 추천 입력이 있으면 filled 재생 아이콘으로 무작위 추천 입력을 즉시 전송합니다. 입력과 추천이 모두 없거나 스트리밍 중이면 버튼을 비활성화합니다.
- `Enter`(Shift 없이, IME 조합 아님) 또는 폼 제출로 전송합니다. "상황 추가"로 선택 영역을 `*...*` 강조로 감쌉니다.

### 검증 표시 원칙

- 필드 단위 오류는 해당 필드 근처에, 폼·요청 단위 오류는 토스트로 표시합니다.
- 오류는 해당 필드와 프로그램적으로 연결해 보조기술에 노출합니다. 구현 수단은 플랫폼 소유입니다(웹: `aria-invalid`·`role=alert` — [3-2-web-app.md §3-2-5](./3-2-web-app.md#3-2-5-반응형접근성브라우저-지원) / 앱: 접근성 시맨틱 — [`3-3-android-app.md §3-3-5`](./3-3-android-app.md)).
- 비밀번호·토큰 등 민감 입력은 없으며, 자유 입력 원문은 로그·이벤트에 수집하지 않습니다([`6-analytics.md §6-7`](./6-analytics.md)).
