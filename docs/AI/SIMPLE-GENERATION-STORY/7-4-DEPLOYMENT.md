# 7-4 배포

| 항목 | 값 |
|---|---|
| 적용 태스크 | 간편 제작 스토리 생성(스토리라인 생성, 컴파일, 인물 이미지와 썸네일 생성) |
| 버전 | 0.1 |

본 문서는 ([6-2 소프트웨어 구현](6-2-SOFTWARE-IMPLEMENTATION.md))에서 정의한 소프트웨어의 배포 단위와 절차, 운영 설정의 반영 방법을 정한다.

AI 서버의 배포 단위와 백엔드 의존 관계, 빌드 대상과 배포 경로를 설명한다. 환경 변수와 시크릿의 공급 방식, 설정 변경을 적용하는 절차를 정한다. 배포 전 검증, 배포 후 확인과 문제가 발생했을 때의 복구 기준을 명시한다.

<br>

### 7-4-1 단위와 의존성

AI 서버의 컨테이너 이미지 하나에 이 태스크와 채팅 태스크를 함께 담아 배포한다.

| 항목 | 값 |
|---|---|
| 형태 | FastAPI 서비스 <br> `uvicorn`으로 8000번 포트에서 실행 |
| 저장소 | `manyak-ai` |
| 이미지에 넣는 것 | `src/`, `prompt/`, `pyproject.toml`의 운영 의존성 |
| 이미지에 넣지 않는 것 | `tests/`, `experiment/`, `scripts/`, `.env`, 개발 의존성 |
| 실행 위치 | 백엔드와 같은 ECS 태스크 <br> 백엔드는 태스크 내부 주소로 호출 |

- AI 서버는 백엔드의 호출만 처리하며 외부 요청을 직접 받지 않는다. 인증, 이프 지불과 결과 저장은 모두 백엔드가 맡는다.

- 프롬프트는 이미지에 들어간다. 프롬프트만 바꿔도 이미지를 새로 빌드해 배포한다.
- 별도의 정책 파일은 없다. 작성 규칙은 템플릿 안에 있다.
- 백엔드가 정상이어도 AI 컨테이너는 실패할 수 있다. 백엔드 상태 검사만으로 AI 기능의 정상 동작을 확인할 수는 없다.
- 개발 환경에서 태스크를 교체하면 같은 태스크의 DB와 Redis도 다시 시작한다. 교체 중에는 서비스 중단을 허용한다.

| 연동 시스템 | 없을 때 |
|---|---|
| 백엔드 | 요청이 들어오지 않음 |
| 텍스트 모델 공급자 API | 서버 시작 검사에서 키가 없으면 시작하지 않음 <br> 호출이 실패하면 502 |
| 이미지 모델 공급자 API | 컴파일은 200을 반환하고 이미지 `error`에 실패 원인을 기록 |
| Sentry | 오류 보고 없이 동작 |
| Langfuse | 추적 없이 동작 |

### 7-4-2 배포 경로

| 단계 | 개발 | 운영 |
|---|---|---|
| 시작 조건 | `dev` 브랜치에 푸시 | `main` 브랜치에 푸시 |
| 워크플로 | `manyak-ai`의 `.github/workflows/docker-image.yml` | 같음 |
| 빌드 컨텍스트 | 저장소 루트와 `Dockerfile` <br> `.dockerignore`가 테스트와 로컬 파일을 제외 | 같음 |
| 이미지 저장소 | GHCR | ECR |
| 이미지 태그 | 커밋 SHA로 올린 뒤 `dev` 태그를 갱신 | 커밋 SHA로 올린 뒤 `latest` 태그를 갱신 |
| 적용 | ECS 서비스에 새 배포를 강제 실행해 갱신된 태그를 다시 받음 | 같음 |
| AWS 인증 | GitHub OIDC <br> 장기 키를 보관하지 않음 | 같음 |

워크플로는 테스트 → 이미지 상태 확인 → 빌드와 게시 → 배포 순서로 실행한다. 앞 단계가 실패하면 다음 단계를 실행하지 않는다.

- 환경 태그는 배포 작업에서만 갱신한다. 빌드 작업은 동시에 실행될 수 있다. 빌드 중 태그를 갱신하면 늦게 끝난 이전 커밋의 빌드가 최신 태그를 덮어쓸 수 있다.
- 배포할 커밋이 브랜치의 최신 커밋인지 먼저 확인한다. 최신이 아니면 배포를 건너뛴다.
- 백엔드와 AI 서버는 같은 태스크를 쓰지만 배포 워크플로는 저장소별로 실행한다. 두 워크플로가 동시에 배포할 수 있다.
- 배포 담당은 AI 담당자다. Terraform 변경은 정해진 배포 절차를 따른다. ([4-deployment.md](../../design/4-deployment.md#4-7-배포-절차))

| 위치 | 관리 항목 |
|---|---|
| `manyak-ai` | 코드, 프롬프트, `Dockerfile`, 배포 워크플로 |
| `manyak-terraform` | 태스크 정의, 환경 변수와 비밀 정보의 참조, 운영 모델 설정 |
| `manyak-infra` | 로컬 통합 실행용 Compose |

### 7-4-3 평가 도구 분리

- 실험 도구는 운영 코드의 함수를 그대로 호출한다. 실행 코드와 프롬프트를 따로 복제하지 않는다. 평가에서 검증한 코드가 배포되는 코드와 같아야 하기 때문이다.
- 운영 코드와 프롬프트만 배포한다. 평가 도구, 입력 세트와 채점 기준은 배포하지 않는다.
- 평가 실행 코드의 기준은 AI 평가 구현에서 정한다. ([6-5 AI 평가 구현](6-5-AI-EVALUATION-IMPLEMENTATION.md))

| 구분 | 위치 | 이미지 포함 | git 포함 |
|---|---|---|---|
| 운영 실행 코드와 프롬프트 | `src/`, `prompt/` | 포함 | 포함 |
| 테스트 | `tests/` | 제외 | 포함 |
| 실험과 평가 도구, 입력 세트, 실행 결과 | `experiment/` | 제외 | 제외 <br> 로컬 전용 |
| 보조 스크립트 | `scripts/` | 제외 | 포함 |
| 개발 의존성 | `pyproject.toml`의 `dev` 묶음 | 제외 | 포함 |

<br>

### 7-4-4 배포 조건

- 린트와 타입 검사는 워크플로에 없다. 병합 전에 자동으로 실행하는 검사는 테스트와 이미지 상태 확인뿐이다.
- 합격 판정의 절대 기준은 목표값이 미정이라 아직 배포 조건으로 쓸 수 없다. ([6-4-8 AI 평가 방법](6-4-AI-EVALUATION-METHOD.md#6-4-8-합격-판정))

  변경 전후 비교로 대신한다.
- 통합 테스트와 AI 평가를 실행하지 않아도 배포가 자동으로 차단되지는 않는다. 실행하지 않았다면 PR에 명시한다.

| 조건 | 기준 | 확인 방법 | 자동 여부 |
|---|---|---|---|
| 명세 | 계약이 바뀌면 계약 문서를 먼저 고침 ([5 계약](5-CONTRACT.md)) <br> 비호환 변경은 백엔드가 대응한 뒤 배포 | PR 검토 | 수동 |
| 테스트 | 전체 통과, 분기 커버리지 90% 이상 | 워크플로의 테스트 작업 | 자동 |
| 이미지 상태 확인 | 빌드한 이미지로 컨테이너를 실행했을 때 상태 확인 주소가 200을 반환 | 워크플로의 이미지 상태 확인 작업 | 자동 |
| Langfuse 활성 확인 | 더미 키와 운영 조건으로 실행했을 때 활성화 로그가 남음 | 같은 작업 | 자동 |
| 통합 테스트 | 프롬프트, 모델이나 호출 코드를 바꿨으면 통합 테스트를 실행 ([7-2-6 테스트 케이스](7-2-TEST-CASES.md#7-2-6-통합-테스트)) | 로컬에서 실행하고 결과를 PR에 기록 | 수동 |
| AI 평가 | 프롬프트나 모델을 바꿨으면 평가 결과로 채택 여부를 판정 ([6-3-6 AI 정렬](6-3-AI-ALIGNMENT.md#6-3-6-평가-데이터와-채택)) | 실험 보고서 | 수동 |
| 버전 일치 | 변경한 템플릿의 `version`과 `updated`를 갱신 | PR 검토 | 수동 |
| 승인 | PR 승인 뒤 병합 | GitHub | 수동 |

### 7-4-5 환경 변수와 비밀 정보

`src/core/config.py`에서 환경 변수를 읽는다. 변수 이름은 대소문자를 구분하지 않으며 정의되지 않은 이름은 무시한다. 서버 시작 시 한 번만 읽으므로 값을 바꾼 뒤에는 새 태스크를 시작해야 적용된다.

**비밀 정보**

| 이름 | 의미 | 필수 | 기본값 | 운영과 개발의 출처 |
|---|---|---|---|---|
| `DEEPSEEK_API_KEY` | DeepSeek 키 | 필수 | 없음 | Secrets Manager |
| `OPENAI_API_KEY` | OpenAI 키 <br> 텍스트와 이미지에 함께 씀 | 선택한 모델이 OpenAI이면 필수 | 빈 값 | Secrets Manager |
| `GEMINI_API_KEY` | Google 키 | 선택한 모델이 Gemini이면 필수 | 빈 값 | Secrets Manager |
| `ANTHROPIC_API_KEY` | Anthropic 키 | 선택한 모델이 Anthropic이면 필수 | 빈 값 | 주입하지 않음 |
| `SENTRY_DSN` | Sentry 주소 | 선택 | 빈 값 <br> 비면 보고하지 않음 | Secrets Manager |
| `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` | Langfuse 키 | 선택 | 빈 값 <br> 비어 있으면 비활성화 | Secrets Manager <br> 운영만 |
| `LANGFUSE_HOST` | Langfuse 주소 | 선택 | 일본 리전이 아닌 주소 | Secrets Manager <br> 운영만 <br> 일본 리전 주소를 넣어야 활성화 |

<br>

**설정값**

- 비밀값은 코드, 이미지와 문서에 넣지 않는다. 운영과 개발은 Secrets Manager에서 태스크가 시작할 때 주입한다. 로컬은 git에서 제외된 `.env`를 쓴다.
- 비밀값을 반영하려면 값을 등록하고 태스크에서 참조하도록 설정한 뒤 재배포해야 한다. 값만 바꾸면 실행 중인 컨테이너에는 반영되지 않는다.
- 배포 담당자는 `manyak-terraform`에서 비밀값의 참조와 주입을 설정한다. 비밀값은 AI 담당자가 등록한다.
- 문서 작성 시 운영 Parameter의 실제 값은 조회하지 않았다.
- 같은 이미지가 쓰는 채팅 태스크의 변수(`CHAT_MODEL`, 이미지 주소 허용 목록 등)는 이 표에 넣지 않았다.

| 이름 | 의미 | 타입 | 기본값 | 운영의 출처 | 개발의 출처 |
|---|---|---|---|---|---|
| `STORYLINES_MODEL` | 스토리라인 모델 | 문자열 | `deepseek-flash` | SSM Parameter Store | 태스크 정의의 환경 변수 |
| `STORY_COMPILE_MODEL` | 컴파일 모델 | 문자열 | `gpt-5.6-terra` | SSM Parameter Store | 태스크 정의의 환경 변수 |
| `IMAGE_MODEL` | 이미지 모델 | 문자열 | `gpt-image-2.5-flare` | 주입하지 않음 <br> 코드 기본값 | 같음 |
| `IMAGE_QUALITY` | 이미지 화질 | `low`, `medium`, `high` | `low` | 주입하지 않음 | 같음 |
| `IMAGE_SIZE` | 인물 이미지 크기 | `가로x세로` | `1024x768` | 주입하지 않음 | 같음 |
| `IMAGE_TIMEOUT` | 이미지 한 장의 제한 시간(초) | 실수 | `60.0` | 주입하지 않음 | 같음 |
| `DEEPSEEK_API_URL`, `OPENAI_API_URL`, `ANTHROPIC_API_URL`, `GEMINI_API_URL` | 공급자 주소 | 문자열 | DeepSeek만 공식 주소 <br> 나머지는 SDK 기본 | 주입하지 않음 | 같음 |
| `SENTRY_ENVIRONMENT` | 환경 이름 <br> Langfuse 활성화 조건에도 사용 | 문자열 | `local` | 태스크 정의 | 태스크 정의 |
| `SENTRY_TRACES_SAMPLE_RATE` | Sentry 성능 추적의 표본 비율 | 실수 | `0.0` | 주입하지 않음 | 같음 |

### 7-4-6 운영 설정

모델과 공급자 주소는 코드 밖에서 설정한다. 공급자 장애 등 긴급 상황에서 코드를 수정하지 않고 설정을 바꿔 재배포하기 위해서다. 변경 방법은 다음 세 가지로 나눈다.

- 설정의 우선순위는 환경 변수, `.env`, 코드 기본값 순서다.
- 서버는 시작할 때 설정을 검사한다. 등록부에 없는 모델이나 키가 없는 공급자를 선택하면 새 태스크는 시작하지 않는다. 이전 태스크가 계속 요청을 받는다. 검사 조건은 구현 규칙에 있다. ([6-2-5 소프트웨어 구현](6-2-SOFTWARE-IMPLEMENTATION.md#6-2-5-구현-규칙))
- 대체 모델이나 다른 공급자로 자동 전환하지 않는다. 모델을 바꾸려면 담당자가 설정을 수정해야 한다.
- 요청 한 건의 비용 한도는 설정하지 않았다.
- 설정 변경도 배포다. 모델을 바꾸면 배포 조건에 정한 통합 테스트와 AI 평가를 거친다.

  긴급 장애 대응으로 먼저 변경했다면 변경 후에 통합 테스트와 AI 평가를 실행하고 결과를 남긴다.
- 컴파일 모델의 공급자를 바꾸면 템플릿도 그 공급자용으로 바뀐다. 응답 `meta`의 `prompt_versions`에서 확인한다.
- Terraform은 운영 Parameter 값을 덮어쓰지 않는다. Terraform의 기본값을 고쳐도 이미 있는 운영 값은 바뀌지 않는다.

| 변경 유형 | 항목 | 바꾸는 방법 | 허용 범위 |
|---|---|---|---|
| 설정만 변경 | 텍스트 모델 | 운영은 SSM Parameter 값을 바꾸고 새 배포를 강제 실행 <br> 개발은 Terraform 값을 바꿔 적용 | 모델 등록부에 있는 모델 <br> 그 공급자의 키가 주입돼 있어야 함 |
| 인프라 선언 변경 | 이미지 모델, 화질, 크기, 제한 시간, 공급자 주소 | 현재 주입하지 않으므로 Terraform에 환경 변수를 추가해 적용 | 이미지 모델 등록부와 시작 검사를 통과하는 값 |
| 코드 변경 | 프롬프트, 모델별 추론 설정, 출력 토큰 한도, 온도, 보완 횟수, 텍스트 호출의 시간 한도 | 코드를 고쳐 이미지를 새로 배포 | 모델 호출의 실행 설정 ([6-1-5 AI 실행](6-1-AI-EXECUTION.md#6-1-5-모델-호출)) |

<br>

### 7-4-7 적용과 복구

**적용 순서**

1. 새 설정이 필요하면 먼저 준비한다. 비밀값 등록 여부, 태스크의 참조 설정, 공급자 모델의 호환성을 확인한다.
2. 백엔드와의 계약이 바뀌면 호환 여부에 따라 순서를 정한다. 필드 추가는 AI 서버를 먼저 배포할 수 있다. 필드를 삭제하거나 이름·타입을 바꾸면 백엔드가 대응한 뒤 배포한다.
3. 브랜치에 병합해 워크플로로 이미지를 배포한다.
4. 새 배포의 식별자, 실행 중인 태스크의 이미지 digest와 컨테이너 상태를 확인한다. 태그 이름이 같아도 실제 이미지는 다를 수 있다.
5. 실제 생성 요청으로 배포 후 확인 항목을 점검한다. ([7-4-8 배포](#7-4-8-배포-후-확인))
6. 실행 시각, 커밋 SHA, 이미지 digest, 설정 변경 범위와 확인 결과를 배포 기록에 남긴다.

<br>

**함께 바꿔야 하는 것**

| 변경 | 같은 시점에 바꿀 것 | 불일치 시 영향 |
|---|---|---|
| 공급자가 모델 이름을 바꿈 | 모델 등록부(이미지), 운영 모델 설정, Langfuse의 단가 등록 | 등록부와 설정이 어긋나면 서버 시작 실패 <br> 단가가 어긋나면 그 모델의 비용이 집계되지 않음 |
| 새 공급자의 모델을 고름 | 그 공급자의 키 주입 | 서버 시작 실패 |
| Langfuse의 단가 구간 이름 | 코드의 metadata 값과 Langfuse 등록 | 비용이 틀린 구간으로 집계됨 |

<br>

**진행 중인 요청**

- 새 태스크를 시작한 뒤 이전 태스크를 종료한다. 이전 태스크가 요청을 처리하던 중에 종료되면 해당 요청은 실패한다.
- AI 서버는 상태를 저장하지 않으므로 진행 중인 작업을 새 태스크로 넘기지 않는다. 실패한 요청은 최종 실패 규칙에 따라 백엔드가 환불하고 사용자가 다시 요청한다. ([7-1-5 오류 처리](7-1-ERROR-HANDLING.md#7-1-5-최종-실패))
- 개발 환경은 태스크가 하나이므로 교체 중에 요청을 받지 못한다.

<br>

**복구**

- 운영 배포 작업은 태그를 옮기기 전에 현재 `latest`의 digest를 보관한다. 배포가 실패하면 그 digest로 태그를 되돌린다.
- ECS의 자동 복구만으로 이전 이미지로 돌아간다고 보장할 수 없다. 태스크 정의가 같아도 태그가 가리키는 이미지는 바뀔 수 있기 때문이다.
- 모델 이름을 변경했다면 설정만 되돌릴 수 없다. 이전 이름이 새 등록부에 없으므로 이미지도 함께 되돌린다.
- 복구한 이미지와 설정의 조합을 배포 기록에 남긴다. 복구 담당은 AI 담당자다.
- 상세 복구 절차는 배포 설계의 롤백 기준을 따른다. ([4-deployment.md](../../design/4-deployment.md#4-9-검수-관측-롤백))

| 문제 | 되돌리는 것 | 방법 |
|---|---|---|
| 새 이미지의 결함 | 이미지 | 이전 정상 digest로 환경 태그를 되돌리고 새 배포를 강제 실행 <br> 배포 후 확인 절차를 다시 실행 |
| 모델 설정의 문제 | 설정과 이미지의 조합 | 이전 모델 설정과 그 설정에 맞는 이미지로 함께 되돌림 |
| 프롬프트의 품질 저하 | 이미지 | 프롬프트는 이미지에 들어 있으므로 이전 이미지로 되돌림 |
| 서버 시작 실패 | 없음 | 이전 태스크가 계속 요청을 받음 <br> 잘못된 설정을 고쳐 다시 배포 |

<br>

### 7-4-8 배포 후 확인

- 확인 기간과 지표별 기준값은 미정이다. 운영 요구사항의 목표값이 정해지면 그 값을 쓴다. ([2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md))
- 개발 환경에서는 Langfuse를 사용하지 않는다. 응답과 Sentry로만 확인한다.
- 개발 환경에서 확인한 결과만으로 운영 환경의 DB, 캐시와 배포 방식을 검증할 수는 없다.
- 프롬프트나 모델을 바꿨다면 실제 배포한 조합을 AI 성능 보고의 현재 상태에 반영한다. ([6-6 AI 성능 보고](6-6-AI-PERFORMANCE-REPORT.md))

  날짜, 모델, 프롬프트 버전과 측정한 품질, 시간, 비용을 적는다.

| 시점 | 확인 | 자료 | 기준 |
|---|---|---|---|
| 배포 직후 | 컨테이너 상태와 상태 확인 주소 | 워크플로의 확인 단계 | AI 컨테이너가 정상 |
| 배포 직후 | 스토리라인 생성과 컴파일을 실제로 한 건씩 실행 | 대상 환경의 앱이나 API | 둘 다 200 <br> 인물 이미지와 썸네일이 있음 |
| 배포 직후 | 응답 `meta`의 `model`과 `prompt_versions` | 응답, 운영은 Langfuse 추적 | 배포하려던 모델과 템플릿 버전 |
| 다음 날 | 새로 생기거나 늘어난 오류 분류 | Sentry 일일 요약 | 배포 전보다 늘지 않음 |
| 확인 기간 동안 | 재호출 분포, 인물 누락 빈도, 이미지 실패율, 시간, 비용 | ([7-3-4 관측](7-3-OBSERVABILITY.md#7-3-4-지표)) | 배포 전보다 나빠지지 않음 |
