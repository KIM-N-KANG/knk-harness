# 6-4 AI 평가 방법

| 항목 | 값 |
|---|---|
| 적용 태스크 | 간편 제작 스토리 생성(스토리라인 생성, 컴파일, 인물 이미지와 썸네일 생성) |
| 버전 | 0.1 |

본 문서는 ([2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md), [6-3 AI 개선](6-3-AI-ALIGNMENT.md))에서 정의한 요구 수준과 개선 목적을 달성했는지 판단할 평가 방법을 정한다.

평가할 출력에 맞춰 벤치마크의 구성, 정답과 데이터 분리 기준을 정한다. 코드 검사, 사람 검토와 LLM 채점이 각각 무엇을 평가하는지와 지표 계산 방법을 설명한다. 반복 실행의 변동과 실패를 처리하고, 운영 목표에 따라 통과 여부를 판정하는 기준을 정의한다.

<br>

### 6-4-1 평가 단위와 실행 방식

프롬프트 조립부터 모델 호출, 검증, 보완, 후처리까지 전체 실행 과정을 평가한다. 사용자가 받는 최종 결과의 품질을 확인하기 위해서다.

개선 실험은 스토리라인과 컴파일을 각각 평가하고, 최종 확인에서는 두 단계를 연결해 평가한다.

| 평가 단위 | 시작 | 종료 | 포함 | 제외 |
|---|---|---|---|---|
| 스토리라인 생성 | 스토리라인 요청 한 건 | 후보 3편과 추천 정보를 담은 응답 | 전체 재생성, 이름 보완 | 백엔드 저장, 화면 표시 |
| 컴파일 | 컴파일 요청 한 건 | 스토리 설정과 외형을 담은 응답 | 부분 보완, 엔딩 폴백, 입력값 덮어쓰기 | 백엔드 저장, 채팅 품질 |
| 이미지 | 컴파일이 만든 외형과 장르 태그 | 인물 이미지와 썸네일 | 이미지 프롬프트 조립, 이미지 호출 | 저장과 CDN 전달 |

연결 평가에서는 최초 입력, 생성 후보와 컴파일 결과를 사례 ID로 연결한다. 어떤 후보를 컴파일할지 정하는 선택 규칙은 미정이다. 비교 전에 이 규칙을 정하고 변경 전후에 동일하게 적용한다. 단계별 평가 결과는 각각 기록한다.

- 평가는 별도의 CLI에서 실행하되, 생성 과정은 운영 코드와 공유한다. ([6-1 AI 실행](6-1-AI-EXECUTION.md))

  평가용 CLI는 아직 구현되지 않았다.
- 컴파일 단독 평가에는 미리 정한 스토리라인을 사용한다. 스토리라인 생성 결과를 가져와도 비교 실험 중에는 같은 입력으로 고정한다.
- 이미지 평가는 비용이 많이 들어 텍스트 평가와 따로 실행할 수 있다. 이때 외형 입력은 동일하게 유지한다.
- 컴파일 결과로 채팅했을 때의 품질은 채팅 태스크의 평가 범위다.

| 실행 방식 | 입력과 비교 방법 | 목적 |
|---|---|---|
| 스토리라인 단독 | 같은 장르·인물 입력으로 변경 전후 후보를 비교 | 후보 생성 품질의 변화 확인 |
| 컴파일 단독 | 같은 스토리라인·추가 정보·인물·로어북을 고정해 변경 전후 결과를 비교 | 스토리라인 생성의 영향 없이 컴파일 품질 비교 |
| 연결 평가 | 같은 최초 입력으로 스토리라인을 생성하고, 선택한 후보를 컴파일에 전달 | 두 단계를 거친 최종 결과의 품질과 정보 전달 확인 |

### 6-4-2 벤치마크

**현재 상태**

확정된 벤치마크는 없다.

<br>

**구성 기준**

벤치마크는 태스크의 입력·출력과 출력별 정답 기준을 정한 뒤 만든다. 새 벤치마크는 다음 기준으로 구성한다.

| 항목 | 기준 |
|---|---|
| 입력 형식 | 계약의 요청 필드와 일치 ([5 계약](5-CONTRACT.md)) <br> 실행 코드에서 필드를 변환하지 않고 요청 객체로 만듦 |
| 사례 ID | 세트 안에서 중복되지 않는 짧은 식별자 |
| 세트 이름과 버전 | `산출물/성격-v버전` <br> 한 번 실험에 쓴 세트는 고치지 않고 새 버전을 만듦 |
| 분포 | 운영 추적의 장르 비율을 따름 <br> 요청 수가 매우 적은 장르는 필수 사례가 아니면 넣지 않음 |
| 제외 조건 | 입력 검증에서 거부되는 요청, 제품 요건에 맞지 않는 요청 |
| 필수 사례 | 아래 표의 입력 조건을 장르와 무관하게 포함함 |
| 표본 규모 | 미정 <br> 반복 실행에서 측정한 결과 변동을 바탕으로 지표 계산에 필요한 수를 정함 ([6-4-7 AI 평가 방법](#6-4-7-변동과-실패)) |
| 위치와 접근 권한 | 미정 |

- 입력은 합성 데이터를 원칙으로 한다. 분포만 운영 기록에서 가져온다.
- 운영 입력 원문으로 사례를 만들면 분석 명세의 보존, 접근과 삭제 조건을 그대로 적용하고 저장소에 올리지 않는다. ([6-analytics.md](../../spec/6-analytics.md#6-7-개인정보와-원문-수집-원칙))
- 세트에는 적용한 태스크 정의의 버전과 만든 날짜를 기록한다. 입력 형식이 바뀌면 세트를 새 버전으로 다시 만든다.

| 필수 사례 | 확인하려는 것 |
|---|---|
| 주인공과 주변 인물의 이름, 성별을 모두 입력 | 이름과 성별 보존, 인물 누락 |
| 인물 정보를 모두 비움 | AI가 인물을 정하는지 |
| 주변 인물 없음 | AI가 필요한 인물을 정하는지 |
| 주변 인물 5명, 인물별 특징 태그 3개 | 최대 입력에서 인물이 빠지는지와 소요 시간 |
| 추가 정보 없음 | 스토리라인만으로 설정을 확장하는지 |
| 추가 정보가 스토리라인과 어긋남 | 서로 어긋난 내용을 자연스럽게 조정하는지 |
| 로어북 있음 | 로어북과 모순되지 않는지 |

<br>

### 6-4-3 정답과 데이터 분리

**출력별 정답**

생성 결과에는 하나로 정해진 정답 문장이 없다. 대신 출력 항목마다 다음 기준으로 정답을 판단한다.

- LLM 채점 문항은 태스크 정의의 출력별 품질 기준과 유저 스토리의 기대에서 가져온다. ([3 태스크 정의](3-TASK-DEFINITION.md), [2-1 유저 스토리](2-1-USER-STORY.md))
- 기대에 없는 기준을 문항으로 만들지 않는다.
- 문항은 특정 내용의 유무나 정해진 방법으로 센 개수가 맞는지 묻도록 작성한다. 단순히 “잘 썼는가”를 물으면 채점자마다 판단이 달라진다.
- AI 담당자는 채점 결과의 일부를 뽑아 검토한다. 판단이 다르면 문항을 명확하게 고치고 버전을 올린다.
- 제품의 기대가 바뀌면 유저 스토리와 태스크 정의를 먼저 고친 뒤 문항을 고친다.
- 문항이 바뀌면 이전 점수와 직접 비교하지 않는다.

| 평가 주체 | 대상 | 판단 방법 |
|---|---|---|
| 코드 | 개수, 필수값, 입력한 이름과 성별의 보존 | 입력과 계약을 기준으로 계산함 <br> 사람이 정답을 표시할 필요는 없음 |
| LLM-as-a-judge | 장르 반영, 인물 특징 반영, 후보 간 차이, 설정 간 모순 없음, 추가 정보 반영 | 출력별로 참·거짓 문항을 만들고 채점자가 판단함 |
| 사람 | 재미, 이미지의 외형 일치 | 미정 <br> 기준이 정해지기 전에는 점수로 집계하지 않음 |

<br>

**데이터 분리**

- 개발 세트와 검증 세트는 사례가 겹치지 않아야 한다. 같은 세트로 수정과 최종 판단을 반복하면 해당 세트에만 잘 맞는 프롬프트가 될 수 있다.
- 두 세트는 같은 분포 기준으로 만든다.
- 현재는 구분이 없다. 새 벤치마크를 만들 때 함께 나눈다.

| 구분 | 용도 | 현재 상태 |
|---|---|---|
| 개발 세트 | 프롬프트를 고치며 반복해서 확인 | 구분 없음 |
| 검증 세트 | 채택 여부와 합격을 판정 | 구분 없음 |
| 통합 테스트 사례 | 파이프라인이 끝까지 동작하는지 확인 | 합격 판정의 사례 선정 기준 참고 ([6-4-8 AI 평가 방법](#6-4-8-합격-판정)) |

<br>

### 6-4-4 코드 기반 평가

계산 가능한 항목은 코드로 채점한다. 사용자에게는 운영 코드의 검증을 통과한 응답만 전달된다. 따라서 아래 지표는 최종 응답뿐 아니라 실행 기록도 함께 확인해 계산한다.

- 필수 항목과 개수는 운영 코드의 검증 기준을 그대로 쓴다. ([6-1-6 AI 실행](6-1-AI-EXECUTION.md#6-1-6-검증과-복구))

  평가에서 기준을 따로 정의하지 않는다.
- 스토리라인의 주인공 이름은 세지 않는다. 줄거리가 1인칭이기 때문이다.
- 컴파일에서는 코드가 이름과 성별을 입력값으로 덮어쓴다. 따라서 보존율은 이 코드가 제대로 동작하는지 확인하는 지표다.
- 백엔드 응답 시간은 백엔드가 AI 서버에 요청을 보낸 시점부터 응답을 받은 시점까지 측정한다. 현재 백엔드의 대기 제한은 [5-6 계약](5-CONTRACT.md#5-6-시간과-복구)를 따른다.
- 평가는 백엔드를 거치지 않으므로 AI 서버 내부 실행 시간만 잰다. 소요 시간을 비교하는 실험은 한 번에 요청 하나만 실행한다.
- 비용은 실험 설정에 기록된 모델별 단가로 계산한다. 단가가 없는 모델은 비용을 빈 값으로 두고, 단가를 추가한 뒤 다시 계산한다.

| 단위 | 지표 | 계산 |
|---|---|---|
| 스토리라인 | 요청 성공률 | 응답을 받은 요청 수 / 전체 요청 수 |
| 스토리라인 | 재호출 분포 | 요청별 `retry_count`의 분포 |
| 스토리라인 | 인물 등장률 | 이름을 입력한 주변 인물이 모두 등장한 후보 수 / 전체 후보 수 |
| 컴파일 | 요청 성공률 | 응답을 받은 요청 수 / 전체 요청 수 |
| 컴파일 | 필수 설정 충족률 | 보완 없이 필수 항목을 모두 갖춘 요청 수 / 전체 요청 수 |
| 컴파일 | 엔딩 폴백률 | 엔딩이 빈 배열인 응답 수 / 응답 수 |
| 컴파일 | 이름과 성별 보존 | 입력한 이름과 성별이 결과의 인물 설정과 같은 인물 수 / 입력한 인물 수 |
| 컴파일 | 외형 완성률 | 외형 값 6개를 모두 갖춘 인물 수 / 전체 인물 수 |
| 이미지 | 생성 성공률 | 성공한 이미지 수 / 시도한 이미지 수 <br> 인물 이미지와 썸네일을 따로 셈 |
| 공통 | 시간 | 요청 시작부터 응답까지 <br> 중앙값과 최댓값, 제한 시간 초과 건수 |
| 공통 | 비용 | 요청 한 건의 토큰과 이미지 비용의 합 <br> 재호출과 보완을 포함함 |

<br>

### 6-4-5 사람 평가

사람이 결과의 품질을 직접 평가하는 일과 LLM의 채점이 타당한지 확인하는 일을 구분한다.

LLM이 틀리게 채점한 사례는 채점 기준을 검토하는 데 사용한다. 생성 결과의 문제와 채점의 문제를 구분하며, 문항을 바꾸면 버전을 올리고 같은 기준으로 다시 비교한다.

| 역할 | 확인할 내용 | 기준과 현재 상태 |
|---|---|---|
| 결과 직접 평가 | 이야기의 재미와 매력, 이미지가 인물의 외형·성별에 맞는지 | 세부 평가 기준과 점수 척도는 미정 <br> 확정 전에는 점수로 집계하지 않음 |
| LLM 채점 검토 | 같은 결과에 대한 사람과 LLM의 판단이 일치하는지 | 비교 기록 없음 <br> 표본 수와 비교 방법은 미정 |
| 컴파일 결과 확인 | LLM이 뽑은 주인공의 목표 문장이 비었거나 관련 문항이 거짓인 결과 | 해당 결과를 사람이 직접 확인함 |
| 최종 채택 검토 | 코드·LLM 평가 결과와 결과 원문 표본 | AI 담당자가 검토한 뒤 채택 여부를 결정함 |

<br>

### 6-4-6 LLM-as-a-judge 평가

LLM-as-a-judge는 생성 결과를 다른 LLM이 채점하는 방식이다. 문항마다 참·거짓을 판단하고, 참인 문항 수를 점수로 삼는다.

재미와 이미지 적합성은 사람 평가에서 다룬다. LLM 채점 결과를 사람 평가 점수로 대신하지 않는다.

| 평가 단위 | 채점할 내용 | 미정 항목 |
|---|---|---|
| 스토리라인 | 장르 반영, 인물 특징 반영, 후보 간 차이 | 구체적인 문항, 채점 모델과 호출 단위 |
| 컴파일 | 선택한 스토리라인·추가 정보 반영, 설정 간 모순 | 구체적인 문항과 채점 모델 |

컴파일 채점 방법은 다음과 같다.

- 생성과 채점에는 서로 다른 모델을 사용한다.
- LLM 채점의 타당성은 사람 평가에서 확인한다.
- 채점 프롬프트와 생성 결과의 원문은 이 문서에 싣지 않는다.

| 항목 | 값 |
|---|---|
| 채점 단위 | 결과 한 건당 채점자별로 한 번 호출해 모든 문항을 평가 |
| 채점자 | 서로 다른 공급자의 모델 2개 <br> 각 모델의 점수는 따로 집계하며 합산하지 않음 |
| 기록 | 문항별 판정, 근거 인용, 채점자 이름과 모델 |
| 채점 제외 | 엔딩이 빈 배열인 결과는 채점하지 않음 <br> 평가의 실패 처리 규칙에 따라 다시 생성하고 횟수를 따로 보고함 ([6-4-7 AI 평가 방법](#6-4-7-변동과-실패)) |
| 기준 버전 | 문항의 판단 기준을 바꾸면 `rubric_version`을 올림 <br> 저장된 채점 결과는 이 버전으로 구분함 |

<br>

### 6-4-7 변동과 실패

생성 결과는 같은 입력으로 실행해도 달라질 수 있다. 평소 변동 폭을 측정해야 변경 전후의 차이가 의미 있는지 판단할 수 있다.

| 항목 | 기준 |
|---|---|
| 반복 실행 | 입력마다 같은 조건으로 여러 번 생성함 <br> 횟수는 실험 정의에 적음 |
| 집계 | 입력별 평균을 구한 뒤 전체 평균을 계산함 <br> 문항별 통과율도 계산함 |
| 무승부 | 컴파일 총점의 평균 차이가 1점 미만이면 우열을 정하지 않음 |
| 채점자 불일치 | 두 채점자가 서로 다른 조건을 더 높게 평가하면 판정을 보류함 |
| 채점 일관성 | 같은 결과를 다시 채점해 점수 차이를 측정함 |

실패는 다음 세 가지로 나누어 모두 기록한다.

- 형식이 잘못된 결과는 최대 5회 다시 생성해 보충한다. 재생성 횟수는 품질 점수와 함께 보고한다. 실패한 결과를 제외하기만 하면 실패가 잦은 조건의 평균 점수가 실제보다 좋아 보일 수 있다.
- 비교하는 두 조건에서 채점을 완료한 표본의 비율이 5%p 이상 차이 나면 평균 비교를 보류한다.
- 입력 한 건만 비교한 결과로 결론을 내리지 않는다.

| 구분 | 뜻 | 처리 |
|---|---|---|
| 실행 실패 | 운영 코드가 요청을 실패로 끝냈음 | 성공률 계산에서 실패 건수에 포함함 |
| 채점 실패 | 생성은 완료했지만 채점 호출이 실패하거나 채점 결과를 해석하지 못했음 | 다시 채점함 <br> 끝내 실패하면 채점 누락으로 기록함 |
| 평가 누락 | 실행하지 않았거나 결과 파일이 없음 | 누락된 표본 수를 보고함 |

<br>

### 6-4-8 합격 판정

코드 평가 지표, LLM 채점 점수, 사람 검토 결과를 구분해 기록한다. 서로 다른 평가 결과를 하나의 총점으로 합치지 않는다. 단독 평가와 연결 평가도 구분한다.

합격 기준은 운영 요구사항의 목표값이다. ([2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md))

목표를 충족해야 새 모델이나 프롬프트를 배포한다.

- 현재 운영 요구사항의 품질·시간·비용 목표값이 모두 미정이므로 목표 달성 여부는 판단할 수 없다.

  목표값이 정해질 때까지는 변경 전후를 비교해 채택을 판단한다. ([6-3-6 AI 정렬](6-3-AI-ALIGNMENT.md#6-3-6-평가-데이터와-채택))
- 현재 백엔드 대기 제한을 넘는 건수와 비율은 운영상 제약을 확인하는 자료로 기록한다. 내부 실행 시간만 측정한 결과로 백엔드 응답 시간이나 사용자 대기 시간 목표의 충족 여부를 판정하지 않는다. 시간 목표 달성 여부는 운영 요구사항의 목표값이 확정된 뒤 판단한다.
- 채점 기준을 통과해도 자동으로 채택하지 않는다. AI 담당자가 결과 원문 중 일부를 직접 검토한 뒤 결정한다.
- 판정 결과는 모델, 프롬프트 버전, 세트 버전, 채점 기준 버전과 함께 AI 성능 보고에 기록한다. ([6-6 AI 성능 보고](6-6-AI-PERFORMANCE-REPORT.md))

| 판정 | 조건 |
|---|---|
| 통과 | 검증 세트에서 운영 요구사항의 품질·시간·비용 목표를 모두 충족함 |
| 미달 | 목표 중 하나라도 충족하지 못함 |
| 판정 불가 | 목표값이 미정임 <br> 실행 실패, 채점 실패와 평가 누락으로 표본이 부족함 <br> 반복 평가 결과가 무승부나 보류에 해당함 ([6-4-7 AI 평가 방법](#6-4-7-변동과-실패)) |

<br>

**통합 테스트 사례**

벤치마크에서 5건 안팎을 골라 통합 테스트에 쓴다. ([7-2 테스트 케이스](7-2-TEST-CASES.md))

이 사례로는 외부 모델을 실제로 호출했을 때 전체 실행 과정이 끝까지 동작하는지 확인한다. 품질 평가는 하지 않는다. 연결 평가는 최종 결과의 품질도 확인하므로 이 통합 테스트와 구분한다.

현재 `manyak-ai`의 `tests/integration/`에 있는 라이브 테스트는 벤치마크와 연결돼 있지 않다. 새 벤치마크를 만들 때 사례 ID로 연결한다.

| 선정 기준 | 이유 |
|---|---|
| 요청이 가장 많은 장르의 일반 입력 | 가장 흔한 경로 |
| 인물 정보를 모두 비운 입력 | 입력이 가장 적은 경로 |
| 주변 인물 5명의 입력 | 출력과 이미지 호출이 가장 많은 경로 |
| 추가 정보와 로어북이 있는 컴파일 입력 | 선택 입력을 모두 쓰는 경로 |
| 스토리라인 생성 결과를 컴파일에 전달하는 입력 | 두 단위의 연결 |
