# 7-3 관측

| 항목 | 값 |
|---|---|
| 적용 태스크 | 간편 제작 스토리 생성(스토리라인 생성, 컴파일, 인물 이미지와 썸네일 생성) |
| 버전 | 0.1 |

이 문서는 운영 요청을 추적하고 품질, 소요 시간과 비용의 변화를 확인하는 기준을 정한다. 기록은 다음과 같이 나눈다.

- Langfuse: 모델 호출의 입력·출력, 토큰 사용량과 비용
- Sentry: 오류
- 백엔드: AI 서버가 응답 `meta`로 전달한 요청별 실행 정보

AI 서버는 상태를 저장하지 않으며 자체 저장소에도 기록을 남기지 않는다.

기록 항목은 AI 서버와 분석 명세의 운영, 관측과 원문 수집 규칙을 따른다. ([AI 서버 명세 5-6](../../spec/5-ai-server-spec.md#5-6-운영과-관측), [분석 명세 6-7](../../spec/6-analytics.md#6-7-개인정보와-원문-수집-원칙))

<br>

### 7-3-1 추적 단위

요청마다 추적 기록을 하나씩 만든다. 어느 요청에서 실패와 재시도가 발생했는지 구분할 수 있도록 서로 다른 요청의 기록은 합치지 않는다.

| 단위 | Langfuse 기록 | 이름 |
|---|---|---|
| 요청 | 추적 1건 | `스토리라인 생성`, `스토리 컴파일` |
| 텍스트 모델 호출 | 추적 아래의 호출 기록. 최초 생성, 전체 재생성과 보완이 각각 1건 | SDK가 자동으로 지정 |
| 이미지 모델 호출 | 컴파일 추적 아래의 호출 기록. 이미지 한 장마다 1건 | `이미지 생성:인물`, `이미지 생성:썸네일` |

백엔드가 헤더로 보낸 식별자로 요청과 제품 데이터를 연결한다. ([5-5 식별과 전달](5-CONTRACT.md#5-5-식별과-전달))

| 식별자 | 기록 위치 | 연결 대상 |
|---|---|---|
| `request_id` | 추적 metadata, 로그 | 백엔드 로그, 백엔드의 AI 호출 기록과 추적 |
| `session_id` | 추적의 세션 | 같은 접속 세션의 요청들 |
| 기기 식별자의 해시 | 추적의 사용자 | 같은 기기의 요청들. 원본 식별자는 받지 않음 |
| `creation_id` | 추적 metadata | 스토리라인 생성부터 컴파일까지의 제작 과정 |
| `parent_creation_id` | 스토리라인 추적 metadata | 다시 생성하기 전의 제작 요청 |
| `storyline_id`, `storyline_order` | 컴파일 추적 metadata | 컴파일에 쓴 후보 |

- 헤더가 없거나 값이 `unknown`이면 해당 식별자를 기록하지 않는다. 임의의 값을 만들어 넣지 않는다.
- AI 서버는 추적 식별자를 응답하지 않는다. 백엔드는 `request_id`로 추적을 찾는다.
- 여기서 쓰는 `creation_id`는 분석 이벤트의 `creation_id`와 다른 값이다. 두 식별자를 같은 값으로 취급하지 않는다.
- Anthropic과 Google 모델의 텍스트 호출은 자동 계측이 완성되지 않았다. 컴파일 모델을 바꾸면 호출 기록이 빠질 수 있다.

<br>

### 7-3-2 단계별 기록

| 기록 | 시점 | 내용 |
|---|---|---|
| 요청 추적 | 요청마다 1건 | 요청 입력, 장르 태그, 프롬프트 버전, 재호출 횟수, 제작 과정 식별자 <br> 보완과 이미지 호출은 같은 추적의 하위 기록 |
| 텍스트 호출 로그 | 호출마다 | 호출 종류, 소요 시간, 입출력 토큰, 캐시 적중 토큰 |
| 이미지 호출 기록 | 호출마다 | 모델, 크기, 화질, 형식, 토큰 사용량, 결과 크기 <br> 이미지 바이너리는 제외 |
| 오류 보고 | 실패한 시도마다 | 기능, 공급자, 모델, 프롬프트 버전, 오류 분류, 재호출 횟수, 소요 시간 <br> 최종 성공 전의 실패도 포함 |
| 경고 보고 | 인물 누락이 남은 채 반환할 때 | 인물이 빠진 후보 번호 <br> 이름과 본문은 제외 |

### 7-3-3 실행 정보

| 정보 | 응답 `meta` | Langfuse | Sentry |
|---|---|---|---|
| 환경과 코드 버전 | 없음 | 환경, 릴리스 | 환경. 릴리스는 코드에서 지정하지 않음 |
| 기능 | 없음 | 추적 이름 | `feature` 태그 |
| 공급자와 모델 | `provider`, `model` | 호출 기록의 모델 | `provider`, `model` 태그 |
| 프롬프트 버전 | `prompt_versions` | 추적 metadata | `ai` 컨텍스트 |
| 재호출 횟수 | `retry_count` | 추적 metadata | `ai` 컨텍스트 |
| 토큰 수 | `input_token_count`, `output_token_count` | 호출 기록의 사용량 | 없음 |
| 소요 시간 | 없음 | 추적과 호출 기록의 시작·종료 시각 | `ai` 컨텍스트의 `latency_ms` |
| 오류 분류 | 없음 | 호출 기록의 오류 수준과 예외 타입 이름 | `error_code` 태그 |
| 장르 | 없음 | `genre:` 태그 | 없음 |
| 단가 구간 | 없음 | DeepSeek 호출 기록의 `pricing_window` | 없음 |

`feature` 태그의 값은 `storyline_generation`, `story_completion`, `character_image_generation`, `thumbnail_image_generation`이다. `error_code`의 값은 실패 계약의 Sentry 분류를 따른다. ([5-4 실패 계약](5-CONTRACT.md#5-4-실패-계약))

- `prompt_versions`는 호출 전에 추적에 기록한다. 요청이 실패해도 프롬프트 버전을 확인할 수 있다.
- `retry_count`는 처음에 0으로 기록하고 결과가 나오면 실제 횟수로 바꾼다. 502로 끝난 요청에도 실제 값을 남긴다.
- `retry_count`에는 SDK 재시도 횟수를 포함하지 않는다. SDK 재시도 횟수는 어디에도 기록하지 않는다.
- 컴파일의 `prompt_versions`에는 컴파일, 인물 이미지와 썸네일 템플릿 버전을 모두 기록한다. 컴파일 모델이 Gemini이면 Gemini용 템플릿 버전을 기록한다.
- 모델 폴백은 없으므로 기록하지 않는다. 엔딩을 빈 배열로 대체한 경우에는 로그에만 남기고 추적과 `meta`에는 기록하지 않는다.
- 호출 옵션(온도, 토큰 한도)과 응답 스키마의 버전은 따로 기록하지 않는다. 코드 버전인 릴리스로 구분한다.

<br>

### 7-3-4 지표

| 지표 | 계산 | 자료 |
|---|---|---|
| 요청 수 | 기능별 추적 수. 장르별로 나눌 수 있음 | Langfuse |
| 요청 실패율 | 502와 500으로 끝난 요청 수 / 전체 요청 수 | 백엔드의 AI 호출 기록 |
| 오류 분류의 분포 | `error_code`별 보고 수. 복구된 실패도 포함 | Sentry |
| 재호출 분포 | 요청별 `retry_count`의 분포 | 백엔드의 AI 호출 기록, Langfuse |
| 인물 누락 빈도 | 경고 수준의 `invalid_ai_response` 보고 수 / 스토리라인 요청 수 | Sentry, Langfuse |
| 이미지 실패율 | 실패한 이미지 호출 수 / 이미지 호출 수. 인물 이미지와 썸네일을 따로 계산 | Langfuse의 이미지 호출 기록 |
| 시간 | 요청별 추적의 소요 시간. 중앙값과 최댓값, 백엔드 제한 시간을 넘은 건수 | Langfuse |
| 텍스트 비용 | 요청별 텍스트 모델 호출 비용의 합 | Langfuse의 텍스트 호출 기록 |
| 이미지 비용 | 요청별 인물 이미지와 썸네일 생성 비용의 합 | Langfuse의 이미지 호출 기록 |

- 비용은 Langfuse 프로젝트에 등록한 모델 단가로 계산한다. AI 서버 코드에서는 계산하지 않는다. 모델 이름이 바뀌면 단가 등록도 같은 시점에 바꾼다.
- 이미지 비용은 세부 사용량별로 계산한다. 전체 사용량에는 단가를 적용하지 않아 같은 비용이 두 번 더해지는 것을 막는다.
- 응답을 받지 못한 호출은 사용량이 없어 비용에서 빠진다. 집계한 비용은 실제 청구액보다 작을 수 있다.
- 응답 `meta`의 토큰 수에는 이미지 호출의 사용량을 포함하지 않는다. 컴파일 한 건의 텍스트 비용과 이미지 비용은 Langfuse에서 각각 확인한다.
- Langfuse는 운영 환경에서만 활성화한다. 위 지표는 운영 요청만 집계한다.
- 각 지표의 목표값은 운영 요구사항을 따르며 현재 대부분 미정이다. ([2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md))

  대시보드는 만들지 않았다.

<br>

### 7-3-5 품질 피드백

실패 기록으로 유효하지 않은 응답이 얼마나 자주 나오는지 확인한다. 이 기록을 프롬프트와 모델 개선에 사용한다. ([6-3 AI 정렬](6-3-AI-ALIGNMENT.md))

| 신호 | 기록 대상 | 연결 방법 | 상태 |
|---|---|---|---|
| 스토리라인 평가 `GOOD`, `BAD` | 후보 3편을 만든 스토리라인 추적 | 백엔드가 `request_id`로 추적을 찾아 점수를 기록. 후보는 `storyline_id`, `storyline_order`로 구분 | 계획 |
| 다시 생성함 | 새 추적이 아니라 버려진 이전 스토리라인 추적 | 백엔드가 점수를 기록 | 계획 |
| 시작 추천 입력의 노출과 선택 | 컴파일 추적 | 백엔드가 점수를 기록 | 계획 |

- 점수는 백엔드가 기록한다. 사용자 반응은 며칠 뒤에도 올 수 있지만 AI 서버는 상태를 저장하지 않기 때문이다. 점수의 의미와 기록 시점은 분석 명세를 따른다. ([분석 명세 6-6-12](../../spec/6-analytics.md))
- 점수의 metadata에는 식별자만 넣는다. 사용자 입력과 생성 결과의 원문은 넣지 않는다.
- `GOOD`의 비율을 품질 점수로 쓰지 않는다. 평가를 남긴 사용자의 반응만 반영하며 결과가 정답인지는 검증하지 않기 때문이다. 원문을 검토한 뒤 쓴다. ([6-3-2 피드백과 검수](6-3-AI-ALIGNMENT.md#6-3-2-피드백과-검수))
- 컴파일 결과와 이미지에는 사용자 평가가 없다.

<br>

### 7-3-6 알림과 대응

| 항목 | 값 |
|---|---|
| 알림 수단 | Sentry 오류의 일일 요약. 매일 오전 10시(KST)에 지난 24시간의 오류를 슬랙 채널에 올림 |
| 범위 | AI 서버, 백엔드와 웹의 Sentry 프로젝트 전체 |
| 오류가 없는 날 | 요약을 보냄. 오류가 없는 날과 요약 전송이 실패한 날을 구분하기 위함 |
| 조회 실패 | 오류 없음으로 적지 않고 조회가 실패했다고 보냄 |
| 실시간 알림 | 없음 |
| 기준값, 측정 기간과 최소 건수 | 미정 |
| 담당 | AI 담당자. 정해진 대응 시간은 없음 |

요약을 확인한 뒤 오류 분류에 따라 대응한다.

| 오류 분류 | 먼저 볼 곳 | 대응 |
|---|---|---|
| `provider_timeout`, `provider_unavailable`, `provider_rate_limited`가 늘어남 | 공급자의 장애 공지, 호출량 한도 | 공급자 문제면 복구를 기다림. 장애가 계속되면 허용 수단에 따라 모델 변경을 검토 [6-3-5 허용 수단](6-3-AI-ALIGNMENT.md#6-3-5-허용-수단) |
| `provider_bad_request` | Sentry의 공급자 오류 원문 | 요청 인자나 모델 설정을 고침 |
| `invalid_ai_response`가 갑자기 늘어남 | Langfuse의 모델 응답 원문과 검증 코드 | 원인 구분에 따라 구현 결함인지 먼저 확인 [6-3-3 원인 구분](6-3-AI-ALIGNMENT.md#6-3-3-원인-구분) |
| `schema_validation_failed`, `unexpected_error` | Sentry의 스택 | 코드 결함으로 보고 고침 |

요약에 쓰는 조회식과 메시지 형식은 `manyak-ai`의 `.agents/skills/daily-sentry-report/`를 따른다.

### 7-3-7 데이터와 수집 실패

**기록하는 것과 하지 않는 것**

| 데이터 | Langfuse | Sentry | 로그 | 응답 `meta` |
|---|---|---|---|---|
| 요청 입력(장르, 인물 정보, 선택한 스토리라인, 추가 정보) | 기록 | 기록하지 않음 | 기록하지 않음 | 없음 |
| 프롬프트와 모델 응답 원문 | 기록 | 기록하지 않음 | 기록하지 않음 | 없음 |
| 이미지 프롬프트 | 기록 | 기록하지 않음 | 기록하지 않음 | 없음 |
| 이미지 데이터 | 기록하지 않음. 형식과 바이트 수만 | 기록하지 않음 | 기록하지 않음 | 없음 |
| 공급자 오류 원문 | 기록하지 않음. 예외 타입 이름만 | 기록 | 기록하지 않음 | 없음 |
| 인물 이름 | 요청 입력 안에만 | 기록하지 않음. 빠진 후보 번호만 | 기록하지 않음 | 없음 |
| 기기 식별자 | 해시만 | 없음 | 없음 | 없음 |
| API 키 | 기록하지 않음 | 기록하지 않음 | 기록하지 않음 | 없음 |

- 사용자가 직접 쓴 값은 태그와 metadata에 넣지 않는다. 장르만 임시로 예외를 둔다. 직접 입력한 장르도 `genre:` 태그로 기록한다.
- 인물의 특징 태그에는 사용자 입력이 섞이므로 관측용 태그에 넣지 않는다.

<br>

**Langfuse 원문 수집 조건**

| 항목 | 값 |
|---|---|
| 활성화 조건 | 키가 있고, 주소가 일본 리전이며, 환경이 `prod`일 때만 활성화. 하나라도 맞지 않으면 비활성화 |
| 저장 리전 | 일본 |
| 접근, 삭제와 권한 | AI 담당자로 한정 |
| 보존 | 수집일부터 1년 |
| 환경 분리 | 운영만 기록. 로컬, 테스트와 실험은 기록하지 않음. 실험 기록은 별도로 관리 |
| 용도 | 결과 점검, 실패 원인 분석, 평가 데이터 구성. 자체 모델의 훈련에는 쓰지 않음 |
| 제외와 삭제 요청 | 해당 추적을 삭제하고 평가 자료에서 뺌 |

**수집 실패**

| 상황 | 처리 |
|---|---|
| Langfuse 초기화 실패 | 관측 없이 서버를 시작 |
| 추적 시작이나 기록 실패 | 경고 로그만 남기고 요청을 그대로 처리. 응답에 영향 없음 |
| 서버 종료 | 남은 기록을 전송. 전송에 실패하면 아직 보내지 못한 추적 기록이 유실됨 |
| 재전송 | 코드에서 직접 재전송하지 않음. SDK의 배치 전송에 맡김 |
| 표본 추출 | 하지 않음. 운영 요청을 모두 기록 |

- 관측 실패의 경고 로그에 사용자 입력이나 모델 응답 원문이 들어가지 않게 한다.
- 관측에 실패해도 요청은 계속 처리한다. 요청 처리 중 발생한 예외는 관측 코드에서 무시하지 않고 호출한 쪽으로 전달한다.
- 관측 실패가 요청 처리에 영향을 주지 않는지는 `tests/unit/test_langfuse.py`에서 확인한다. 해당 테스트는 FL-14다. ([7-2-5 실패와 반복](7-2-TEST-CASES.md#7-2-5-실패와-반복))
