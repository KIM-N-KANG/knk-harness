# 6-3 AI 정렬

| 항목 | 값 |
|---|---|
| 적용 태스크 | 간편 제작 스토리 생성(스토리라인 생성, 컴파일, 인물 이미지와 썸네일 생성) |
| 버전 | 0.1 |

이 문서는 사용자의 기대에 맞게 AI 결과를 개선하는 데 쓸 자료와 방법을 정한다. 배포 후에도 프롬프트와 모델이 바뀌므로 품질을 계속 확인한다. 개선에는 이 문서에서 허용한 방법만 쓰고, 제외한 방법은 제안하지 않는다. 채점 기준과 계산 방법은 AI 평가 방법에서 정한다. ([6-4 AI 평가 방법](6-4-AI-EVALUATION-METHOD.md))

<br>

### 6-3-1 개선 대상

개선 대상은 유저 스토리의 기대와 운영 요구사항의 품질 기준이다. ([2-1 유저 스토리](2-1-USER-STORY.md), [2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md#2-2-1-품질))

코드는 결과의 형식을 검사하고, 프롬프트와 모델은 내용을 만든다. 이 역할에 따라 개선 대상을 나눈다.

| 구분 | 개선 대상 | 현재 확인 방법 |
|---|---|---|
| 형식 | 스토리라인 3편과 추천 정보 3개가 채워진다 <br> 컴파일 결과가 채팅에 필요한 설정을 모두 갖춘다 | 응답 검증 기준, 재호출 횟수와 실패 코드 [6-1-6 검증과 복구](6-1-AI-EXECUTION.md#6-1-6-검증과-복구) |
| 형식 | 입력한 인물의 이름이 후보마다 등장한다 | 이름 누락 경고 |
| 형식 | 인물 이미지와 썸네일이 생성된다 | 이미지 호출의 실패 기록 |
| 내용 | 태그의 장르와 분위기가 이야기에 드러난다 <br> 인물의 특징이 행동에 드러난다 <br> 후보끼리 전개가 뚜렷하게 다르다 | 스토리라인 평가와 재생성 여부, 사람의 원문 검토 |
| 내용 | 고른 스토리라인과 추가 정보가 컴파일 결과에 반영된다 <br> 인물마다 성격과 말투가 구분된다 | 사람의 원문 검토 |
| 내용 | 인물 이미지가 설정의 외형과 성별에 맞는다 | 사람의 이미지 검토 |

운영 요구사항의 품질 목표값은 아직 정하지 않았다. ([2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md))

그전까지는 변경 전후를 비교해 품질이 나빠지지 않았는지 판단한다. 시간과 비용은 개선 과정에서 지켜야 할 한도다. 품질을 높이는 변경이 제한 시간을 넘기면 채택하지 않는다. ([2-2-2 시간](2-2-OPERATION-REQUIREMENTS.md#2-2-2-시간))

<br>

### 6-3-2 피드백과 검수

| 자료 | 수집 위치 | 내용 | 용도 |
|---|---|---|---|
| 스토리라인 평가 | 백엔드 DB의 스토리라인 평가 | 후보별 `GOOD`, `BAD` | 사용자가 마음에 들지 않아 한 후보 파악 |
| 재생성 여부 | Langfuse 추적의 이전 제작 요청 식별자 | 어느 제작 요청의 후보를 버리고 다시 생성했는지 <br> 백엔드가 계약에 정한 헤더로 전달 [5-5 식별과 전달](5-CONTRACT.md#5-5-식별과-전달) | 고를 만한 후보가 없었는지 검토 |
| 운영 추적 | Langfuse | 요청 입력, 프롬프트와 응답 원문, 장르 태그, 프롬프트 버전, 재호출 횟수 | 사례 검토, 원인 분석, 평가 데이터 구성 |
| 오류와 경고 | Sentry | 실패한 시도의 공급자, 모델, 오류 분류, 이름 누락 경고 | 형식 실패의 빈도와 추세 확인 |
| 호출 기록 | 백엔드의 AI 호출 기록 | 응답 `meta`의 모델, 토큰, 재호출 횟수, 실패 코드 | 실패율과 비용 추세 확인 |

결과를 사용자에게 보내기 전에 검수하는 사람은 없다. 결과를 받은 사용자의 반응과 운영 기록을 개선에 활용한다.

평가값과 재생성 여부를 Langfuse 추적에 점수로 기록하는 기능은 아직 계획 단계다. ([분석 명세 6-6-12](../../spec/6-analytics.md))

구현 전까지는 제작 과정 식별자로 평가값과 원문을 직접 연결해 확인한다. 기록 항목은 관측에서 정한다. ([7-3 관측](7-3-OBSERVABILITY.md))

자료를 쓸 때 다음을 지킨다.

- 사용자 평가를 그대로 정답으로 쓰지 않는다. `BAD`에는 평가 이유가 없으므로 AI 담당자가 원문을 검토한다. 어떤 기대를 충족하지 못했는지 유저 스토리의 항목으로 분류한 뒤 사용한다. ([2-1 유저 스토리](2-1-USER-STORY.md))
- 운영 원문은 Langfuse에서만 확인한다. Langfuse는 일본 리전의 운영 환경에서만 켠다. AI 담당자만 접근할 수 있고, 원문은 1년간 보존한다. 세부 조건은 분석 명세의 원문 수집 규칙을 따른다. ([분석 명세 6-7](../../spec/6-analytics.md#6-7-개인정보와-원문-수집-원칙))
- 운영 원문을 문서, 저장소, 로그와 Sentry에 옮기지 않는다. 사례는 식별자와 분류로만 기록한다.
- 사용자가 평가 활용 제외나 삭제를 요청하면 해당 사례를 평가 자료에서 뺀다.
- 컴파일 결과와 이미지에는 사용자 평가가 없다. 내용의 품질은 사람이 직접 검토해 확인한다.

### 6-3-3 원인 구분

수정에 앞서 결과가 기대와 달라진 원인을 찾는다. 원인에 따라 고칠 곳이 다르다.

| 원인 | 판단 기준 | 고칠 곳 |
|---|---|---|
| 프롬프트의 모호함 | 같은 입력의 결과가 실행마다 달라지거나, 규칙을 두 가지로 해석할 수 있다 | 템플릿의 작성 규칙 |
| 맥락 부족 | 모델이 판단에 필요한 입력을 받지 못했다 | 프롬프트 조립의 입력 구성 [6-1-4 프롬프트 조립](6-1-AI-EXECUTION.md#6-1-4-프롬프트-조립) |
| 모델 판단 | 규칙과 입력이 분명한데도 같은 오류를 반복한다 | 모델과 호출 옵션 |
| 구현 결함 | 유효한 모델 응답을 검증 코드가 거부하거나 후처리에서 잘못 바꾼다 | 구현 코드 [6-2 소프트웨어 구현](6-2-SOFTWARE-IMPLEMENTATION.md) |
| 기대의 모호함 | 결과가 기대에 맞는지 사람마다 판단이 다르다 | 사용자 기대와 운영 품질 기준 [2-1 유저 스토리](2-1-USER-STORY.md), [2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md) |
| 평가 오류 | 원문을 읽어 보면 결과는 기대에 맞는데 평가나 채점이 틀렸다 | 평가 자료의 분류와 채점 기준 [6-4 AI 평가 방법](6-4-AI-EVALUATION-METHOD.md) |

2026-09-10 스토리라인 전체 실패는 검증 코드의 결함 때문이었다. 모델이 후보의 `id`를 빼고 응답하자, 코드가 이를 필수값 누락으로 판단해 재호출한 뒤 502를 반환했다. `id`는 코드가 순서대로 덮어쓰는 값이므로 검증 코드를 수정했다.

실패가 갑자기 늘면 프롬프트를 수정하기 전에 모델 응답 원문과 검증 코드를 먼저 확인한다.

작성 규칙은 별도 정책 문서 없이 템플릿의 시스템 블록에서 관리한다. 따라서 정책을 바꾸려면 프롬프트를 수정한다.

<br>

### 6-3-4 개선 과정

| 순서 | 하는 일 | 산출물 |
|---|---|---|
| 1 | 피드백과 검수 자료에서 기대를 충족하지 못한 사례를 모은다 [6-3-2 피드백과 검수](#6-3-2-피드백과-검수) | 사례 식별자와 충족하지 못한 기대 |
| 2 | 원인 분류에 따라 가설을 하나 세운다 [6-3-3 원인 구분](#6-3-3-원인-구분) | 가설과 고칠 곳 |
| 3 | 프롬프트·모델·호출 옵션·파이프라인 중 한 번에 하나만 바꾼다 | 변경안 |
| 4 | 같은 입력 세트로 변경 전후를 실행해 비교한다 | 품질, 시간, 비용의 비교 결과 |
| 5 | 다른 품질 항목, 형식 실패율, 시간과 비용이 나빠지지 않았는지 확인한다 | 확인 결과 |
| 6 | 채택하면 버전을 올리고 배포한다 | 프롬프트 버전 또는 설정값 |
| 7 | 배포 뒤 운영 기록에서 같은 지표를 다시 확인한다 | 성능 보고 기록 [6-6 AI 성능 보고](6-6-AI-PERFORMANCE-REPORT.md) |

개선 과정에서는 다음 규칙을 지킨다.

- 프롬프트를 고치면 템플릿 frontmatter의 `version`을 1 올리고 `updated`를 그날 날짜로 바꾼다. 응답 `meta`와 추적에 이 버전을 기록해 변경 전후를 구분한다.
- 모델과 호출 옵션은 모델 호출의 설정값으로 바꾼다. ([6-1-5 모델 호출](6-1-AI-EXECUTION.md#6-1-5-모델-호출))
- 비교 실험에는 모델 호출 비용이 든다. 예상 호출 수와 비용을 확인하고 승인받은 뒤 실행한다.
- 스토리라인 템플릿에는 고정된 예시 이야기 대신 다양한 이야기를 만들기 위한 원칙을 적는다. 예시를 추가하면 후보의 다양성이 줄지 않았는지도 확인한다.
- 채택하거나 기각한 중요한 변경은 결정 기록에 남긴다. ([DECISIONS.md](DECISIONS.md))

  제안 전에 이 기록을 확인해 같은 안을 반복하지 않는다.

### 6-3-5 허용 수단

| 수단 | 허용 여부 | 조건 |
|---|---|---|
| 프롬프트 수정 | 허용 | 변경 전후 결과를 비교 평가 |
| 공급자와 모델 변경 | 허용 | 평가 방법에 따라 품질과 비용을 검증 [6-4 평가 방법](6-4-AI-EVALUATION-METHOD.md) <br> 등록부에 있는 모델만 사용 |
| 호출 옵션 변경 | 허용 | 온도, 출력 토큰 한도, 추론 강도가 대상 <br> 제한 시간은 계약에서 허용한 범위 안에서만 변경 [5-CONTRACT.md](5-CONTRACT.md) |
| 파이프라인 변경 | 허용 | 요구사항과 계약에 미치는 영향을 검토하고 비교 평가 <br> 인지 구조를 먼저 고친 뒤 구현 [4-1 인지 구조](4-1-DESIGN-COGNITIVE-ARCHITECTURE.md) |
| 모델 미세 조정 | 사용하지 않음 | 프롬프트 수정과 모델 변경으로 품질을 먼저 조정 |
| 선호 학습(DPO, GRPO 등) | 사용하지 않음 | 모델 미세 조정과 같음 |
| 자체 모델 서빙 | 사용하지 않음 | 외부 공급자 API만 사용 |

사용하지 않는 수단의 이유는 다음과 같다.

- 개인정보 처리방침은 운영 원문을 운영자 자체 AI 모델의 훈련에 쓰지 않는다고 정한다. 학습에 쓸 수 있는 운영 데이터가 없다.
- 정답이 표시된 데이터와 확정된 벤치마크가 없어 학습 효과를 검증할 수 없다.
- 현재는 외부 공급자 API만 호출한다. 자체 모델을 실행할 서버는 설계·배포 구성에 없다.
- 공급자의 모델 교체 주기가 짧다. 특정 모델에 맞춘 학습 결과는 모델이 바뀌면 다시 만들어야 한다.

다음 조건이 모두 충족되면 제외한 수단을 다시 검토한다. 검토 결과는 결정 기록에 남긴다. ([DECISIONS.md](DECISIONS.md))

- 허용 수단을 모두 시도해도 운영 요구사항의 품질 목표에 미달한다. ([2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md))

  목표값이 미정이면 이 조건은 충족된 것으로 보지 않는다.
- 학습에 쓸 수 있는 데이터를 방침에 맞게 확보했다.
- 학습 전후를 비교할 벤치마크가 확정돼 있다. ([6-4 AI 평가 방법](6-4-AI-EVALUATION-METHOD.md))

이 제한은 간편 제작 스토리 생성에만 적용한다. 다른 태스크까지 금지하는 것은 아니다.

### 6-3-6 평가 데이터와 채택

**실험 도구**

비교 실험은 `manyak-ai`의 `experiment/`에서 실행한다. 이 디렉터리는 Git 추적 대상에서 제외한다. 사용법은 `experiment/README.md`를 따른다.

실험 도구는 운영 코드의 함수를 그대로 호출한다. 실험용 실행 경로를 별도로 구현하지 않는다. 평가 실행 코드의 기준은 AI 평가 구현에서 정한다. ([6-5 AI 평가 구현](6-5-AI-EVALUATION-IMPLEMENTATION.md))

| 항목 | 위치 | 현재 상태 |
|---|---|---|
| 입력 세트 | `experiment/datasets/inputs/storylines/`, `experiment/datasets/inputs/compile/` | 합성 입력. 한 번 쓴 세트는 고치지 않고 새 버전으로 만든다 <br> 기존 세트는 태그 입력 형식이라 현재 입력과 맞지 않는다. [6-4-2 벤치마크](6-4-AI-EVALUATION-METHOD.md#6-4-2-벤치마크) |
| 실험 정의 | `experiment/plans/` | 실험마다 바꾸는 변수 하나와 고정할 조건을 기록 |
| 실행 결과 | `experiment/runs/` | 실험별 결과와 보고서 |
| 채점 기준 | `experiment/evaluation/rubrics/` | 컴파일만 체크리스트 채점 가능. 스토리라인은 채점 기준이 없어 시간, 비용, 실패율만 비교 |

**데이터 구분**

- 프롬프트 수정에 쓰는 입력과 최종 채택을 판단하는 입력은 분리한다. 같은 입력을 계속 쓰면 해당 입력에만 잘 맞는 프롬프트가 될 수 있다.
- 현재는 입력을 분리하지 않아 같은 세트를 개발과 최종 판단에 함께 쓴다. 분리 방법은 미정이며 정답과 데이터 분리에서 정한다. ([6-4-3 정답과 데이터 분리](6-4-AI-EVALUATION-METHOD.md#6-4-3-정답과-데이터-분리))
- 입력 세트는 합성 데이터를 원칙으로 한다. 운영 원문으로 평가 자료를 만들면 보존, 접근과 삭제 조건을 그대로 적용한다. ([6-3-2 피드백과 검수](#6-3-2-피드백과-검수))

**기준 변경**

- 제품 요구사항이 바뀌면 정답이나 채점 기준을 수정할 수 있다. 이때 유저 스토리나 운영 요구사항을 먼저 고친다. ([2-1 유저 스토리](2-1-USER-STORY.md), [2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md))
- 점수를 올리려고 채점 기준을 낮추거나 실패한 사례를 입력 세트에서 빼지 않는다.
- 기준을 바꾸면 이전 점수와 직접 비교하지 않는다. 같은 기준으로 변경 전 결과를 다시 채점한다.

**채택**

| 판정 | 조건 |
|---|---|
| 채택 | 개선 대상이 나아지고, 개선 과정의 5번에서 확인한 다른 항목도 나빠지지 않았다 [6-3-4 개선 과정](#6-3-4-개선-과정) |
| 기각 | 개선 대상이 나아지지 않았거나, 다른 항목·시간·비용이 허용 범위를 벗어났다 |
| 판정 불가 | 실행 실패나 채점 실패로 비교할 결과가 부족하다. 실패한 사례를 빼고 판정하지 않는다 |

채택한 변경은 프롬프트 버전, 모델과 설정값을 AI 성능 보고에 결과와 함께 기록한다. ([6-6 AI 성능 보고](6-6-AI-PERFORMANCE-REPORT.md))

채택 여부는 평가의 합격 기준에 따라 판단한다. ([6-4-8 합격 판정](6-4-AI-EVALUATION-METHOD.md#6-4-8-합격-판정))
