# DECISIONS.md

간편 제작 스토리 생성에 해당하는 기존 AI 서버 ADR을 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 두고 여기에는 결정 당시의 이유와 변경 이력을 남긴다. ([AI 서버 ADR](../../adr/3-ai-server-adr.md))

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다. 기존 D, A ID와 근거 티켓을 유지한다.
- 상태는 원본 기록 기준이다. 과거의 모델 선택, 적용 대기와 해결 여부를 현재 상태로 단정하지 않는다.
- 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.
- 채팅 전용 결정은 제외한다. 공통 결정은 간편 제작에 적용되는 범위와 필요한 배경을 옮긴다.

<br>

### 2. 구조 결정

**D1. AI 기능을 독립 서버로 분리**

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 배경 | LLM 호출은 제작과 채팅에 공통으로 쓰인다. 프롬프트는 자주 바뀌고 공급자 키도 별도로 관리해야 한다. |
| 채택 | 프롬프트 조립, 생성과 형식 보정을 AI 서버가 맡는다. 저장, 인증과 프록시는 백엔드가 맡는다. |
| 대안 | 백엔드가 LLM을 직접 호출하는 안. 프롬프트 변경이 백엔드 배포 주기에 묶이고 서로 다른 책임이 섞여 채택하지 않았다. |
| 영향 | 운영할 서비스가 하나 늘고 백엔드에 AI 프록시가 필요하다. |

<br>

**D2. AI 서버에 요청 사이의 상태를 저장하지 않음**

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 배경 | 채팅 상태를 AI 서버에 저장하면 재시작 시 유실, 워커 간 동기화와 만료 관리를 해결해야 한다. |
| 채택 | 백엔드가 요청마다 필요한 재료를 보내고 AI 서버는 받은 값으로 조립하고 응답한다. 이력과 요약은 백엔드가 저장한다. |
| 대안 | AI 서버에 세션 저장소와 초기화 단계를 두는 안. 프롬프트 치환 비용이 작고 공급자 캐시도 있어 별도 상태 관리의 부담을 택하지 않았다. |
| 영향 | 요청 크기가 커진다. 간편 제작도 이 서버의 상태 비저장 원칙을 따른다. |

<br>

**D3. 컴파일과 채팅 실행을 분리**

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 배경 | 태그, 스토리라인과 추가 정보만으로는 채팅에 필요한 세계관과 인물 설정이 부족하다. |
| 채택 | 스토리당 한 번 컴파일해 설정을 확장하고 저장한다. 채팅에서는 저장한 설정을 프롬프트에 끼워 넣는다. 세션 초기화 단계 A-2는 D2 결정으로 폐기하고 채팅 실행 단계에 합쳤다. |
| 대안 | 매 턴 LLM으로 확장하면 비용과 지연이 반복된다. 입력을 확장 없이 그대로 쓰면 설정이 빈약해져 두 안을 채택하지 않았다. |
| 영향 | 설정 확장과 검증은 제작 때 끝낸다. 채팅은 저장된 설정을 사용한다. |

**D4. 프롬프트를 파일로 관리**

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 배경 | 프롬프트를 코드 상수로 두면 문구 변경 이력과 코드 변경이 섞인다. |
| 채택 | `prompt/`의 Markdown 파일로 분리한다. 파일명은 고정하고 frontmatter의 `version` 정수로 버전을 관리한다. 변경 이력은 Git에 남긴다. |
| 대안 | 코드 상수로 관리하는 안. 문구 변경이 코드 수정과 묶여 채택하지 않았다. |
| 영향 | frontmatter 파싱이 필요하다. LF를 기준으로 쓰되 CRLF도 허용해 메타데이터가 프롬프트 본문에 섞이지 않게 한다. |

**D7. 출력 형식은 코드로 보장**

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 배경 | 모델에 개수와 필수 필드를 지시해도 형식 위반이 반복됐다. |
| 채택 | 개수, 형식과 필수 필드는 코드로 검증하고 내용, 다양성과 문체는 프롬프트로 개선한다. 스토리라인은 3편과 편별 추천 3개, 비어 있지 않은 본문을 검증한다. 컴파일은 필수 블록을 최대 2회 보완하고 남은 누락은 실패로 처리한다. 장르는 입력값으로, 스토리라인 id는 순서대로 보정한다. |
| 대안 | 프롬프트 지시만으로 형식을 보장하는 안. 반복 실측에서 위반을 막지 못했다. |
| 영향 | 재호출 비용이 생긴다. 스토리라인 id 누락 검증은 뒤의 KNK-1246 기록으로 변경됐다. |

**D8. 세분 JSON을 검증한 뒤 통글로 변환**

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 배경 | 누락 필드를 검사하고 보완하기에는 세분 JSON이 편하지만 저장, 프롬프트 치환과 사람의 수정에는 Markdown 통글이 편하다. |

| 영향 | 변환 규칙을 유지해야 한다. 통글을 세분 JSON으로 되돌리는 기능은 없고 통글 수정은 재컴파일 대상이 아니다. |

**D9. 모델과 파라미터는 실측으로 결정**

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 배경 | 모델과 파라미터가 품질, 시간과 비용을 바꾸므로 기본값이나 직관만으로 선택 근거를 설명하기 어렵다. |

| 영향 | 공급자나 모델을 다시 바꾸면 같은 기준으로 검증해야 한다. 당시 모델별 선택은 아래 스토리라인과 컴파일 결정에 남긴다. |

**D13. LLM 호출을 세 층으로 분리**

**A18. 이미지 전체 시간 예산**

| 항목 | 내용 |
| --- | --- |
| 상태 | 전체 시간 예산 미구현(원본 기준) |
| 배경 | `IMAGE_TIMEOUT=60`은 SDK 시도당 제한이다. 재시도로 한 장이 약 180초 이상 걸릴 수 있고 컴파일은 가장 늦은 이미지와 표지를 기다린다. |
| 채택 | 현재 동작은 바꾸지 않고 시도당 제한이라는 의미를 문서와 환경 변수 설명에 명시했다. 전체 시간 예산은 아직 적용하지 않았다. |
| 대안 | 인물 이미지와 표지를 같은 전체 시간 예산에 묶고 남은 SDK 재시도를 취소하는 안을 후속 작업으로 남겼다. |
| 영향 | 이미지 실패를 200으로 처리해도 응답 지연은 남는다. 구체적인 전체 제한값은 미정이다. |
