# DECISIONS.md

현재 적용 기준은 각 명세에 두고 결정 당시의 이유와 대체 관계는 이 문서에 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다. 기존 ID, 날짜, 당시 상태와 근거를 유지한다.
- 상태와 구현 설명은 원본의 기록 시점을 기준으로 해석한다. 현재 적용 여부나 배포 완료를 과거 기록만으로 단정하지 않는다.
- 결정이 바뀌면 새 ID로 기록하고 대체하는 결정과 적용 범위를 명시한다.
- 원문에 구분되지 않은 배경, 대안과 영향은 추측해서 보충하지 않는다.

**W-035. 겹치는 operationId는 메서드와 경로로 생성 이름을 고정**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-15 |
| 상태 | Accepted (원문 기록 기준) |
| 배경 | 백엔드(Springdoc)는 Java 메서드 이름으로 operationId를 만들고, 이름이 겹치면 스캔 순서대로 `get`, `get_1`, `get_2`처럼 순번을 붙인다. Orval은 이 값으로 훅 이름(`useGet1`)을 만든다. 임시 저장 API(`story-draft-controller`)가 추가되자 순번이 하나씩 밀려 `useList1` 같은 import가 깨졌고, `useGet3`은 이름이 남은 채 화풍 목록 대신 장르 목록을 가리켰다. |
| 채택 | Orval 입력 변환기(`input.override.transformer`)로 스펙을 생성 전에 고친다. 순번 접미사(`_숫자`)를 뗀 기본 이름이 둘 이상인 operationId는 모두 HTTP 메서드와 경로 이름으로 바꾸고(`GET /api/v1/stories/submissions/{id}` → `getStoriesSubmissionsById`), 겹치지 않는 이름은 그대로 둔다. API와 Zod 생성에 같은 변환기를 쓴다. |
| 대안 | 원문에 별도 항목으로 구분하지 않음 |
| 이유 | 메서드와 경로는 API 계약 자체라 백엔드 메서드가 늘거나 스캔 순서가 바뀌어도 변하지 않는다. 같은 이름이 다른 API를 가리키는 일은 없어진다. 모든 이름을 경로로 바꾸면 이미 쓰는 고유 이름(`getStoryDetail` 등)까지 바뀌어, 겹치는 이름만 바꾼다. 근본 해결은 백엔드가 `@Operation(operationId = ...)`로 고유 이름을 다는 것이지만 백엔드 코드라 웹에서 정하지 않는다. |
| 영향 | 지금 고유한 이름도 나중에 백엔드에 같은 이름의 메서드가 생기면 경로 이름으로 바뀌어 import가 깨진다. 다만 다른 API를 가리키지 않고 typecheck에서 드러난다. 경로가 바뀌면 이름도 바뀐다. 생성 훅 이름은 길어진다. |
