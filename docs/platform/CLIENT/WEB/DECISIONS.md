# DECISIONS.md

현재 적용 기준은 각 명세에 두고 결정 당시의 이유와 대체 관계는 이 문서에 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다. 기존 ID, 날짜, 당시 상태와 근거를 유지한다.
- 상태와 구현 설명은 원본의 기록 시점을 기준으로 해석한다. 현재 적용 여부나 배포 완료를 과거 기록만으로 단정하지 않는다.
- 결정이 바뀌면 새 ID로 기록하고 대체하는 결정과 적용 범위를 명시한다.
- 원문에 구분되지 않은 배경, 대안과 영향은 추측해서 보충하지 않는다.

<br>

**W-035. 겹치는 operationId는 메서드와 경로로 생성 이름을 고정**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-15 |
| 상태 | Accepted (원문 기록 기준) |
| 배경 | 백엔드(Springdoc)는 Java 메서드 이름으로 operationId를 만들고, 이름이 겹치면 스캔 순서대로 `get`, `get_1`, `get_2`처럼 순번을 붙인다. Orval은 이 값으로 훅 이름(`useGet1`)을 만든다. 임시 저장 API(`story-draft-controller`)가 추가되자 순번이 하나씩 밀려 `useList1` 같은 import가 깨졌고, `useGet3`은 이름이 남은 채 화풍 목록 대신 장르 목록을 가리켰다. |
| 채택 | Orval 입력 변환기(`input.override.transformer`)로 스펙을 생성 전에 고친다. 순번 접미사(`_숫자`)를 뗀 기본 이름이 둘 이상인 operationId는 모두 HTTP 메서드와 경로 이름으로 바꾸고(`GET /api/v1/stories/submissions/{id}` → `getStoriesSubmissionsById`), 겹치지 않는 이름은 그대로 둔다. API와 Zod 생성에 같은 변환기를 쓴다. |
| 대안 | 원문에 별도 항목으로 구분하지 않음 |
| 이유 | 메서드와 경로는 API 계약 자체라 백엔드 메서드가 늘거나 스캔 순서가 바뀌어도 변하지 않는다. 같은 이름이 다른 API를 가리키는 일은 없어진다. 모든 이름을 경로로 바꾸면 이미 쓰는 고유 이름(`getStoryDetail` 등)까지 바뀌어, 겹치는 이름만 바꾼다. 근본 해결은 백엔드가 `@Operation(operationId = ...)`로 고유 이름을 다는 것이지만 백엔드 코드라 웹에서 정하지 않는다. |
| 영향 | 지금 고유한 이름도 나중에 백엔드에 같은 이름의 메서드가 생기면 경로 이름으로 바뀌어 import가 깨진다. 다만 다른 API를 가리키지 않고 typecheck에서 드러난다. 경로가 바뀌면 이름도 바뀐다. 생성 훅 이름은 길어진다. |
| 근거 | [요청 흐름](2-COMPONENT-ARCHITECTURE.md#2-1-구성과-의존), [KNK-1655](https://kimandkang.atlassian.net/browse/KNK-1655) |

**W-046. 비주얼 회귀 테스트를 PR 전 UI 검사로 바꿈**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-23 |
| 상태 | Accepted |
| 배경 | 비주얼 회귀는 스펙 9개, 기준 이미지 59장을 CI에서 Linux 기준으로 비교했다. 2026-08 이후 `dev`에서 기준 이미지를 바꾼 커밋이 71개였고, 직전 실패한 PR CI 9건 중 7건에 비주얼 스펙이 포함됐다. 모두 UI를 의도적으로 바꾼 PR이었다. UI를 바꿀 때마다 Docker로 기준 이미지를 다시 만들어야 했고 채팅방 스냅샷은 실행마다 달라졌다. 실패 로그만으로는 의도하지 않은 회귀를 잡은 경우와 기준 갱신이 늦은 경우를 구분할 수 없었다. |
| 채택 | 비교 기준 이미지와 CI 비교를 없앤다. 기존 스펙의 화면 상태 설정은 `e2e/ui-capture`의 캡처 전용 스펙으로 옮겨 `pnpm ui:capture`(덮어쓰기)와 `pnpm ui:compare`(직전 캡처와 비교)로만 실행한다. UI를 바꾼 PR은 만들기 전에 ui-review 스킬로 캡처를 직접 보고 agent-browser로 개발 서버를 확인해 결과를 PR 화면 절에 남긴다. 레이아웃 규칙과 React 패턴 같은 코드 점검은 모든 PR 전에 도는 pr-review 스킬이 diff로 맡는다. |
| 대안 | 핵심 화면 몇 개만 비주얼 회귀로 유지: 기준 이미지 갱신과 Docker 의존이 그대로 남음<br>Playwright CLI: E2E와 같은 엔진과 WebKit을 쓰지만 React 렌더 기록, Web Vitals, 스크린샷 비교가 내장되지 않음<br>Playwright MCP: 도구 정의와 접근성 트리가 컨텍스트를 많이 차지하고 에이전트마다 MCP 설정이 필요함 |
| 이유 | 기준 이미지 유지 비용에 비해 확인된 효과가 작았다. agent-browser는 셸 명령이라 Claude Code와 Codex에서 같은 스킬로 쓸 수 있고 `react renders`, `vitals`, `a11y`, `diff screenshot`이 내장돼 화면을 실행해서 보는 점검을 한 절차로 묶을 수 있다. diff를 읽는 코드 리뷰는 브라우저 작업과 성격이 달라 별도 스킬로 나눈다. 회원 상태와 API 응답은 기존 E2E fixture를 재사용해야 해서 캡처는 Playwright 테스트 러너에 남긴다. |
| 영향 | 화면 표현은 머지 조건에서 빠지고 PR 전 검사로만 확인한다. 건드리지 않은 화면이 공용 코드 변경으로 바뀌는 경우를 매 PR 자동으로 잡지 못하므로, 공용 코드를 바꾼 PR은 홈, 스토리 상세, 채팅방, 제작 탭, 마이를 함께 검사한다. 비주얼 스펙만 연결된 QA 케이스는 `수동(UI 검사)`, 다른 E2E와 함께 연결된 케이스는 ◐로 바꿨다. agent-browser는 Chrome만 쓰므로 Safari 화면은 기존 Mobile Safari E2E와 실기기 검수로 확인한다. |
| 근거 | [5-1 검증 수단](5-VERIFICATION.md#5-1-검증-수단), [KNK-2131](https://kimandkang.atlassian.net/browse/KNK-2131) |
