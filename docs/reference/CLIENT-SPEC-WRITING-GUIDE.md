# 클라이언트 Spec 작성 가이드

문장과 파일명은 제품 Spec 작성 가이드를 적용한다. ([제품 Spec 작성 가이드](PRODUCT-SPEC-WRITING-GUIDE.md))

<br>

## 작성 순서

```text
배경 → 사용자 기대와 요구사항 → 화면 설계
     → 연동과 구현 설계 → 검증 → 배포
```

각 단계는 앞 문서의 계약을 구체화한다. 같은 단계에서도 앞 문서가 뒤 문서의 입력이다. 예를 들어 `LAYOUT.md`의 배치를 바꾸면서 `REQUIREMENTS.md`의 입력 제한을 완화하거나, `VERIFICATION.md`의 테스트 결과에 맞춰 `USER-STORY.md`의 사용자 기대를 바꾸지 않는다. 상위 요구를 바꿔야 한다면 별도의 요구 변경으로 그 단계부터 다시 시작하고 이후 문서에 전파한다.

| 단계 | 읽고 답할 수 있어야 하는 질문 | 포함하지 않는 것 |
|---|---|---|
| 1 배경 | 누구의 어떤 문제를 다루는가 | 화면 상세, API, 저장 방식 |
| 2 사용자 기대와 요구사항 | 무엇을 할 수 있어야 하며 성공과 실패는 무엇인가 | 컴포넌트, 쿠키, 클래스와 함수 |
| 3 화면 설계 | 어디에 무엇이 보이며 조작하면 어디로 가는가 | API 호출 순서, 캐시와 저장 알고리즘 |
| 4 연동과 구현 설계 | 앞의 화면 계약을 어떤 경계와 데이터 흐름으로 구현하는가 | 새로운 제품 정책과 수용 기준 |
| 5 검증 | 앞의 계약을 어떤 상황과 절차로 확인하는가 | 테스트를 통과시키기 위한 계약 변경 |
| 6 배포 | 검증한 구현을 어떤 설정과 호환 조건으로 적용하는가 | 상위 기능 범위와 품질 기준 변경 |

<br>

## 폴더와 적용 범위

| 위치 | 내용 |
|---|---|
| `docs/domain/<DOMAIN>/CLIENT/` | 공통 배경, 유저 스토리, 요구사항, 화면 계약과 공용 데이터 형식 |
| `CLIENT/WEB/` | 웹의 적용 범위, URL, 브라우저 동작, 저장과 구현 |
| `CLIENT/ANDROID/` | Android의 적용 범위, 화면 이동, 기기 수명, 저장과 구현 |
| `docs/experience/` | 앱 셸, 탐색, 테마, 서비스 안내와 외부 앱 진입 |
| `docs/platform/CLIENT-CONTRACT.md`, `docs/platform/WEB/`, `docs/platform/ANDROID/` | 여러 도메인의 전송, 컴포넌트, 상태 수명, 관측, 검증과 빌드 규칙 |
| `docs/operations/` | 공용 인프라, 배포와 복구 |
| `docs/reference/` | 작성 기준, 용어, 분석과 결정 원문 |

`COMMON/`은 만들지 않는다. 같은 역할의 파일을 모든 폴더에 복제하지 않고 실제 내용이 있는 파일만 둔다. 공통 유저 스토리를 플랫폼별로 다시 쓰지 않는다.

**읽는 순서**는 단계마다 공통, 해당 플랫폼 순서다. `CLIENT/REQUIREMENTS.md` → `CLIENT/WEB/REQUIREMENTS.md` → `CLIENT/INFORMATION-ARCHITECTURE.md` → `CLIENT/WEB/INFORMATION-ARCHITECTURE.md`처럼 읽는다. `experience/`에서는 그 폴더의 공통 문서와 WEB 또는 ANDROID 문서를 같은 순서로 읽는다. 공통 문서는 플랫폼 하위 문서를 근거로 요구사항을 정의하지 않는다. 플랫폼별 적용 여부와 의도된 차이는 공통 요구사항에서 먼저 구분하고, 플랫폼 문서는 그 범위 안에서 구체화한다.

외부 서버 API는 제공자의 별도 계약이다. 제공자의 읽는 순서를 클라이언트 문서에 적용하지 않는다. `CONTRACT.md`에서 합의된 서버 계약을 입력으로 연결하며, 연동 제약 때문에 사용자 요구를 임의로 바꾸지 않는다. 불일치는 Jira에 남긴다.

## 파일 역할

| 파일 | 작성 내용 |
|---|---|
| `BACKGROUND.md` | 대상 사용자, 해결할 문제, 도메인 범위와 용어 |
| `USER-STORY.md` | ID, 사용자와 상황, 원하는 행동, 이유. 성공으로 받아들일 결과를 사용자 관점으로 작성 |
| `REQUIREMENTS.md` | 유저 스토리별 기능 조건, 입력 제한, 권한, 데이터 보존, 실패와 복구 결과, 접근성 및 품질 제약. 확정하지 않은 수치는 만들지 않음 |
| `INFORMATION-ARCHITECTURE.md` | 화면 목록, 접근 조건, 진입점, 정보 우선순위. 플랫폼의 URL과 내비게이션 |
| `INTERACTION-FLOWS.md` | 사용자 조작에 따른 화면 전환, 분기, 취소와 복귀. API 실행 순서와 구분 |
| `LAYOUT.md` | 화면과 상태별 배치, 문구, 입력 표시, 접근 가능한 이름. 필요한 와이어프레임은 HTML로 작성 |
| `CONTRACT.md` | 서버 계약 연결, 화면 입력과 요청의 변환, 응답 사용처. 클라이언트 전용 형식의 타입, 생략과 null, 호환 조건 |
| `COMPONENT-ARCHITECTURE.md` | 컴포넌트와 모듈의 책임, 의존 방향, 공용 포트와 조립 경계 |
| `STATE-MANAGEMENT.md` | 상태의 기준, 저장 위치와 수명, 복원, 취소와 늦은 응답 반영 조건 |
| `EXECUTION.md` | 인증, 데이터 연동, 갱신과 정리의 실행 순서. 기술 오류별 재시도 한도와 종료 조건 |
| `VERIFICATION.md` | 앞 단계의 요구와 화면 계약을 연결한 사전조건, 절차, 기대 결과와 검증 수단. 실행 결과는 PR과 CI |
| `DEPLOYMENT.md` | 도메인별 설정, 외부 공급자 등록, 호환성과 되돌리기 조건. 공용 배포 절차는 참조 |
| `AGENTS.md` | 읽는 순서, 문서와 코드의 위치, 작성과 검증 안내 |
| `DECISIONS.md` | 날짜, 배경, 대안, 선택과 영향의 이력. 현재 계약의 대체 문서로 사용하지 않음 |

컴포넌트 이후에 사용자 흐름을 정하지 않는다. 오류의 사용자 결과는 요구사항, 오류 상태의 문구와 배치는 화면 설계, 재시도와 정리 알고리즘은 구현 설계에 둔다. 품질 목표는 요구사항에 두고 검증 단계에서는 측정과 판정 방법만 구체화한다. 현재 설계는 해당 본문에 쓰므로 별도 `DESIGN-DECISIONS` 파일을 만들지 않는다.

## 본문과 참조

- 문서마다 “무엇을 결정한다”는 소개를 반복하지 않는다. 문서 역할과 읽는 순서는 `AGENTS.md`에서 안내한다.
- 하나의 사실은 한 곳에서 설명한다. 조건과 결과는 표, 시간순 동작은 짧은 순서나 그림으로 표현한다. 표를 긴 문단으로 다시 설명하지 않는다.
- 유저 스토리는 사용자 목표별로 작성한다. 로그인 공급자나 플랫폼 구현만 다른 같은 목표는 합치고, HTTP 상태나 저장소는 넣지 않는다.
- 유저 스토리 ID는 `<DOMAIN>-US-<세 자리 일련번호>`로 작성한다. 예를 들어 `ACCOUNT-US-001`은 파일과 절 번호에 의존하지 않는다. 도메인별 `CLIENT/USER-STORY.md`에서 정의하고 WEB과 ANDROID는 같은 ID를 참조한다. 앱 전체 목표는 `docs/experience/USER-STORY.md`에서 정의한다. 공통 사용자 경험은 `CLIENT-US-<세 자리 일련번호>`를 사용한다. 기존 `CLIENT-US-001`부터 `CLIENT-US-004`까지는 유지하고 새 목표는 사용하지 않은 `CLIENT-US-005`부터 부여한다. 플랫폼 전용 목표는 사용자와 상황에 적용 범위를 명시한다.
- 발급한 ID는 문서 이동과 순서 변경 때 유지한다. 새 목표에는 사용하지 않은 다음 번호를 부여하고, 통합하거나 폐기한 ID를 재사용하지 않는다. 현재 문서에는 유효한 목표만 두며 과거 결정과 근거는 `DECISIONS.md`와 Git 이력에 보존한다.
- 요구사항과 검증은 유저 스토리 ID를 참조한다. 목표를 통합하거나 폐기하면 현재 참조를 함께 갱신하며, 확정된 과거 결정의 본문과 ID는 바꾸지 않는다.
- 명세 본문의 기준 참조는 같은 단계의 앞 문서 또는 이전 단계로 향한다. 목차와 후속 문서 탐색 링크는 `AGENTS.md`에 둔다. 과거 결정과 코드 위치도 안내 문서에서 찾도록 한다.
- 코드의 경로와 클래스 목록은 `AGENTS.md`에 둔다. 본문에는 구현을 제한하는 책임, 수명, 순서, 보안 조건만 남긴다. 호환성을 설명하는 데 필요한 식별자와 버전은 보존한다.
- 공용 UI 토큰을 도메인마다 복제하지 않는다. 도메인 특유의 배치만 `LAYOUT.md`에 쓰고 공용 디자인 원본을 연결한다.
- 실제 명세와 구현이 다르면 구현에 맞춰 명세를 고치지 않는다. 미정, 비적용, 미구현을 구분한다.

## 이관과 검증

- 관련 Spec, Design, ADR, QA를 함께 확인한다. 확정된 ADR의 ID, 당시 상태와 본문은 보존한다.
- 일부만 이관한 혼합 파일에는 남은 내용을 유지하고 새 위치를 연결한다. 모두 이관한 파일과 빈 폴더는 삭제하며 참조를 새 위치로 갱신한다. 원본과 이동 대응은 Git 이력과 이관 근거에 보존한다.
- 현재 링크와 앵커는 새 위치로 갱신하고 과거 커밋에 고정된 근거 링크는 유지한다.
- 기존 절 번호 기반 US ID는 도메인 이관 때 사용자 목표를 정리해 새 형식으로 한 번 발급한다. 이전 ID와 새 ID의 대응, 통합과 폐기 사유는 이관 PR에 기록하고 현재 Spec에는 남기지 않는다.
- 중복 QA ID는 원본과 내용을 구분해 대응을 남긴다. 통합하거나 폐기한 ID를 재사용하지 않는다.
- 유저 스토리, 요구사항, 화면과 검증의 연결을 확인한다. 뒤 문서에서만 처음 등장하는 제품 조건이 없는지 검토한다.
- 원문 계약과 예외 보존, ADR 본문, QA 케이스, 링크, 앵커, ID 중복을 확인하고 `git diff --check`를 실행한다.
- 명세의 작성, 수정과 검토를 서브에이전트에 맡기지 않는다.
