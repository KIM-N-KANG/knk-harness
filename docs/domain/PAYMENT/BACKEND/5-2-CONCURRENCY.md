# 5-2 동시성

이 문서는 PAYMENT 도메인의 동시 요청 처리 규칙을 정한다. 지갑 행 잠금과 잠금 순서, 멱등과 1회 처리, 유니크 위반, 체험 카운터의 원자성, 배치의 겹침, 수용한 경쟁 조건을 다룬다.

연산별 단계와 트랜잭션 경계는 처리 흐름에, 로트 수명과 배치 주기는 오류 처리에 있다. ([4-1-2 적립](4-1-PIPELINES.md#4-1-2-적립), [4-1-3 차감](4-1-PIPELINES.md#4-1-3-차감), [5-3-5 재시도와 시간 한도](5-3-ERROR-HANDLING.md#5-3-5-재시도와-시간-한도))

<br>

### 5-2-1 지갑 행 잠금

잔액을 바꾸는 모든 연산은 지갑 행에 비관적 쓰기 잠금을 걸어 같은 회원의 증감을 직렬화한다. 잠금 안에서 원장, 로트, 잔액 캐시를 함께 기록한다.

| 경로 | 막는 경쟁 조건 |
|---|---|
| 적립 | 같은 멱등 키의 동시 적립이 두 번 기록되는 경쟁 조건<br>동시 적립이 월 상한 경계를 넘는 경쟁 조건 |
| 차감 | 두 차감이 각자 잔액을 충분하다고 보고 합계가 잔액을 넘는 경쟁 조건<br>같은 로트를 두 차감이 소진하는 경쟁 조건 |
| 만료 정리 | 같은 로트를 두 번 만료 처리하는 경쟁 조건<br>정리는 잠금을 건 적립과 차감 안에서만 수행 |
| 대사 환불 | 두 실행이 같은 그룹의 부족분을 각각 발행하는 경쟁 조건<br>잠금 뒤 환불 수를 다시 셈 |
| 결제 환불 회수 | 회수와 차감이 같은 로트를 동시에 줄이는 경쟁 조건 |

잠금 순서는 환불 표식, 주문, 지갑, 로트 순이다. 초대 보상의 두 지갑은 계정 도메인이 내부 ID 오름차순으로 잠근다. 사용자 행을 잠그는 경로는 사용자 행을 먼저 잠근 뒤 지갑을 잠근다. 모든 경로의 순서가 같으므로 순환하는 교차 대기가 생기지 않는다.

<br>

### 5-2-2 멱등과 1회 처리

가입과 초대 보상의 키는 계정 도메인이 정한다. ([ACCOUNT 5-2-2 멱등과 1회 처리](../../ACCOUNT/BACKEND/5-2-CONCURRENCY.md#5-2-2-멱등과-1회-처리))

| 대상 | 멱등 키 | 처리 |
|---|---|---|
| 가입 보상 | 계정 도메인이 정함 | 로그인마다 요청하고 1회만 적립 |
| 출석 보상 | `attendance:{보상 신원}:{KST 날짜}` | 하루 1회 |
| 초대 보상 | 계정 도메인이 정함 | 쌍당 수혜자별 1회<br>초대자 월 상한은 키의 접두부와 접미부 패턴으로 초대자 역할 행만 집계 |
| 간편 제작 환불 | `refund:story:{차감 시도별 UUID}` | 재시도마다 새 차감이 생기므로 시도별 키로 각 차감과 짝지음 |
| 채팅 턴 환불 | `refund:charge:{소모 행 ID}`<br>체험으로 처리된 턴은 `refund:chatturn:{요청별 UUID}` | 요청 단위 중복 처리 방지와 멱등 키로 중복 환불 방지 |
| 채팅 이미지 환불 | `refund:charge:{소모 행 ID}` | 저장 트랜잭션이 롤백되면 키도 롤백돼 재시도 가능 |
| 그로블 구매 적립 | `groble:{이벤트 ID}` | 같은 통지의 재전송은 적립 없이 무시<br>주문 상태 검사로 중복 적립을 최종 방지 |
| 대사 환불 | 없음 | 잠금 안에서 현재 환불 수를 세어 부족분만 발행 |
| 소모, 만료, 회수 | 없음 | 호출자가 재시도하면 실제로 다시 차감<br>환불 키로 시도별 차감과 환불을 연결 |

멱등성은 잠금 전 확인, 잠금 뒤 재확인, 원장 유니크 제약으로 보장한다.

<br>

### 5-2-3 유니크 위반 처리

| 대상 | 처리 |
|---|---|
| 지갑 `user_id` | 동시 첫 적립의 위반은 독립 트랜잭션 안에서 처리<br>바깥 트랜잭션은 이미 있는 지갑을 잠그고 계속 실행 |
| 원장 `idempotency_key` | 잠금 뒤 재확인이 먼저 막음<br>드물게 위반이 발생하면 오류 반환. 재시도는 기존 키로 멱등하게 처리 |
| 환불 표식 `merchant_uid` | 충돌을 무시하는 삽입 뒤 잠금 조회<br>삽입과 조회 사이에 삭제됐으면 다시 삽입 |

<br>

### 5-2-4 체험 카운터의 원자성

| 상황 | 처리 |
|---|---|
| 동시 예약 | "한도 미만이면 1 증가"를 하나의 Redis 스크립트로 실행해 한도를 초과한 예약 방지 |
| 중복 복원 | 0 아래로 내려가지 않는 조건부 감소<br>호출 도메인이 요청당 한 번만 복원 |
| 동시 첫 로그인의 스냅샷 | 값이 없을 때만 쓰는 조건부 기록<br>완료 시각은 계정 도메인이 비어 있을 때만 기록 |

<br>

### 5-2-5 배치의 겹침

| 배치 | 처리 |
|---|---|
| 선차감 대사 | 고정 지연 실행이라 같은 인스턴스에서 겹치지 않음<br>다중 인스턴스의 동시 실행은 지갑 잠금 뒤 환불 수 재확인이 초과 환불을 막음<br>마지막 차감이 기준 시각보다 오래된 그룹만 대상으로 해 진행 중 요청과의 경쟁을 피함 |
| 정책 갱신 | 갱신끼리만 직렬화<br>읽기는 잠금 없이 스냅샷 참조 |

<br>

### 5-2-6 수용한 경쟁 조건

| 상황 | 수용 이유 |
|---|---|
| 같은 초대자의 보상이 진행 중일 때 탈퇴 후 재가입한 새 계정의 보상 | 집계는 보상 신원 단위지만 잠금은 지갑 단위라 월 상한을 1건 초과할 수 있음<br>보상 신원에 공통 잠금을 걸면 새 교차 대기 경로가 생김 |
| 정책값 갱신과 소모 요청이 겹침 | 요청은 시작 때 읽은 값을 끝까지 쓰므로 차감과 환불은 같음<br>요청마다 다른 값이 적용되는 것은 정상 |
| 만료 직후의 잔액 조회와 정리 | 잔액 조회는 만료 행이 아직 없어도 만료 로트를 제외하므로 정리 시점과 무관하게 같은 값 |
| 선차감 직후 프로세스 중단 | 환불 코드가 실행되지 못함<br>대사가 기준 시각 뒤에 보정 |
