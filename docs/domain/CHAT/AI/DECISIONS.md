# DECISIONS.md

채팅에 해당하는 기존 AI 서버 ADR을 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 두고 여기에는 결정 당시의 이유와 변경 이력을 남긴다. ([AI 서버 ADR](../../../reference/decisions/AI.md))

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다. 기존 D, A ID와 근거 티켓을 유지한다.
- 상태는 원본 기록 기준이다. 과거의 모델 선택, 적용 대기와 해결 여부를 현재 상태로 단정하지 않는다.
- 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.
- 간편 제작 전용 결정과 명세에 반영된 공통 구조 결정(D1~D4, D9, D10, D13)은 옮기지 않는다.

**D5. 채팅 프롬프트를 6레이어로 분리**

| 항목 | 내용 |
| --- | --- |
| 상태 | 기각 (2026-10-21 단일 채팅 프롬프트 사용 결정으로 대체) |
| 배경 | 채팅 프롬프트는 안전 규칙, 서사 진행 규칙, 세계관, 인물, 주인공과 대화 요약처럼 성격이 다른 책임을 함께 담는다. |
| 채택 | SAFETY > CORE > MEMORY > STORY > CHARACTER > USER 우선순위의 6레이어로 나누고 충돌하면 상위 레이어가 이긴다. CHARACTER를 USER보다 위에 두어 사용자 입력이 인물 설정을 덮어쓰지 못하게 한다. 동적 요약은 대화 끝 근처에 두고 정적 가드레일은 생성 직전에 다시 넣는다. |
| 대안 | 한 편의 시스템 프롬프트로 쓰는 안. 책임이 섞여 한 부분의 수정이 전체 회귀를 부르고, 대화가 길어지면 앞쪽 지시가 약해지며, 사용자 입력을 막을 우선순위 구조가 없어 채택하지 않았다. |
| 영향 | 조립 로직과 템플릿 계약이 복잡해진다. |

**D6. 선택지를 본문과 분리된 별도 API로 생성**

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 배경 | 처음에는 본문 끝에 선택지 블록을 붙이고 마커로 파싱했다. 모델 전환 후 운영에서 선택지 블록이 통째로 빠지는 턴이 반복됐고, 한 번 빠지면 다음 턴도 빠졌다(KNK-194). |
| 채택 | 마커 파싱을 폐기하고 본문은 스트리밍, 선택지는 JSON 모드 별도 호출로 분리했다(KNK-230). 이후 2026-07-20 팀 합의로 선택지를 전용 엔드포인트로 옮겼다(KNK-625). 선택지는 항상 별도 API로 만든다. |
| 대안 | 채팅 턴 API 안의 두 번째 호출로 두는 안은 선택지가 끝나야 `completed`가 나가 본문 확정이 밀렸다. 요청 플래그로 동시 생성 여부를 정하는 안은 선택지를 다시 켜는 경로에 결국 전용 API가 필요해 폐기했다. |
| 영향 | 선택지로 인한 완료 지연이 사라지고 선택지 표시 여부는 프론트가 API 호출 여부로 정한다. 백엔드가 턴마다 두 번 호출해야 한다. 프론트 전환과 남은 시간 문제는 A11에 남긴다. |

**D11. 판정은 AI, 상태는 백엔드, 수렴은 강제하지 않음**

| 항목 | 내용 |
| --- | --- |
| 상태 | 기각 (KNK-1626) |
| 배경 | 채팅이 주요 사건을 향해 전개되고 조건을 충족하면 엔딩을 생성하려면 진행 상태와 사용자 입력의 사건 관련성 판정이 필요하다. |
| 채택 | 사건 관련성, 엔딩 목적 달성과 사건 완결은 의미 판정이라 AI가 LLM으로 판정한다. 엔딩 최소 턴 수는 결정적이라 백엔드가 충족한 후보만 보낸다. 목표 사건, 진행 카운터와 도달 기록은 백엔드가 채팅 단위로 저장하고 매 턴 요청에 싣는다. 사용자가 사건을 벗어나도 본문을 사건과 엔딩으로 끌고 가지 않고 방향 제안은 선택지로만 한다. |
| 대안 | 결정적 매칭으로 판정하는 안은 의미 판정을 풀 수 없어 채택하지 않았다. |
| 영향 | 채팅 턴 요청과 응답 계약이 커지고 정성 판정의 일관성을 프롬프트와 평가로 관리해야 한다. AI 서버 구현과 백엔드 연결은 완료로 기록돼 있다(A6, KNK-413, 417, 420, 422, 465, KNK-521~523). |

**D12. 판정을 채팅 턴 API 안의 별도 LLM 호출로 실행**

| 항목 | 내용 |
| --- | --- |
| 상태 | 기각 (KNK-1626) |
| 배경 | D11로 목표 사건 선정, 사건 완결과 엔딩 도달 판정이 매 턴에 들어왔다. 판정을 턴의 어느 지점에서 수행할지가 남았다. |
| 채택 | 본문과 분리된 별도 호출로 판정한다. 6레이어에 들어가지 않는 판정 템플릿을 쓰고 본문 스트림이 끝난 뒤 실행한다. 판정 재료가 없으면 호출을 건너뛰고 실패하면 판정 메타를 `null`로 반환한다. 판정 결과는 재료가 있는 턴에 항상 필요하므로 별도 API로 나누지 않고 채팅 턴 API 안에 둔다. |
| 대안 | 본문 프롬프트에 판정 지시를 함께 넣는 안은 창작과 판정이 토큰과 주의를 다투고 판정이 깨지면 본문도 깨져 채택하지 않았다. 선택지처럼 API를 나누는 안은 백엔드 호출만 늘어 채택하지 않았다. |
| 영향 | 재료가 있는 턴은 완료 이벤트가 판정만큼 기다린다. 턴 하나의 LLM 호출은 채팅 턴 API가 본문 1회와 판정 0~1회, 선택지 API가 1~3회다. |

**KNK-748, 749, 750. 판정 대기 중 연결 유지와 시간 제한**

| 항목 | 내용 |
| --- | --- |
| 상태 | 기각 (KNK-1626) |
| 배경 | 판정을 기다리는 동안 데이터를 보내지 않아 백엔드가 연결을 끊었다. 판정은 성공했지만 사용자는 본문을 다 읽은 뒤 오류를 받았다. |
| 채택 | 판정 대기 중 10초마다 `data: {}`를 담은 `ping` 이벤트를 보낸다. 판정 전체는 60초와 남은 턴 시간 중 작은 값으로 제한하고 시간이 끝나면 SDK 재시도도 취소한다. 자체 시간 제한으로 판정을 건너뛰거나 중단하면 받은 목표와 카운터를 그대로 반환한다. |
| 대안 | 주석 전송은 백엔드가 이벤트로 읽지 않아 대기 시간을 초기화하지 못했다. 판정을 일찍 포기하면 진행 판단 결과를 잃는다. 백엔드 대기 제한을 늘리면 멈춘 호출도 오래 기다린다. 본문 직후 `completed`를 보내고 판정을 후속 이벤트로 분리하는 안은 세 서비스 계약을 함께 바꿔야 해 보류했다. 새 `judgementStatus` 필드도 동시 계약 변경이 필요해 보류했다. |
| 영향 | 백엔드 전체 상한을 넘을 위험을 줄이지만 보장하지는 않는다. 빠르게 실패하는 503과 429의 SDK 재시도 기회는 유지한다. 예산 계산 시점의 차이는 A15, 시간 초과 외 판정 실패는 A16에 남긴다. |

**KNK-1626. 사건과 엔딩 판정을 AI 서버에서 제거**

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 배경 | 2026-10-16 사용자 결정으로 결말은 AI가 본문에서 쓰도록 맡기고, 서비스는 사건 진행과 엔딩 도달을 판정하지 않기로 했다. |
| 채택 | 판정 호출, 판정 대기 `ping`과 시간 예산을 없애고 본문 직후 `completed`를 보낸다. 요청의 `target_main_event`, `occurred_main_event_names`는 받아도 쓰지 않는다. 응답에서는 `targetMainEvent`, `occurredMainEventName`, `endingName`을 뺀다. 주요 사건과 엔딩 후보는 계속 받아 본문과 선택지 프롬프트에 넣는다. |
| 대안 | 기록된 대안 없음. |
| 영향 | 백엔드는 빠진 응답 필드를 `null`로 읽는다. 그래서 목표 사건을 해제하고 사건 완결과 엔딩 도달을 기록하지 않는다. 서비스는 결말이 나왔는지 알지 못한다. 채팅 턴 API의 LLM 호출은 본문 1회다. D11, D12, KNK-748, 749, 750, KNK-549, KNK-1416, KNK-1101, 1264~1268, A10, A12, A15, A16의 판정 관련 내용을 기각한다. |

**KNK-1416. 선택지 모델을 본문 모델과 따로 선택**

| 항목 | 내용 |
| --- | --- |
