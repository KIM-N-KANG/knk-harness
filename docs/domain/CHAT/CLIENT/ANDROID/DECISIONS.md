## A-043. 채팅 공유를 앱에 적용하고 Android 공유 시트로 전달

- 결정일: 2026-09-18 · 기록 확정 상태: Accepted
- 대체 관계: 2026-08-29의 "채팅 공유 앱 비적용"(Android 계획 문서 결정, ADR 미기재)을 대체합니다. [A-026](../../../ACCOUNT/CLIENT/ANDROID/DECISIONS.md#a-026)의 공유 시트 사용을 채팅 공유로 확장합니다.
- **맥락:** 메뉴 시트 전환([A-042](../../../../adr/1-3-android-adr.md#a-042))으로 웹과 같은 자리에 공유하기를 둘 수 있게 됐습니다. 공통 계약은 발급한 링크를 클립보드에 복사하고 토스트로 알리지만, 앱에서는 링크를 손에 쥔 뒤 다시 공유 앱을 찾아야 해 초대 코드 공유보다 한 단계 깁니다.
- **결정:** 채팅 메뉴와 채팅 목록 카드 옵션 시트의 공유하기는 `POST /chats/{id}/shares`로 발급한 웹 열람 URL을 초대와 같은 Android 공유 시트(`ACTION_SEND`)로 바로 보냅니다. 클립보드 복사·성공 토스트는 두지 않고 실패 안내·진행 표시는 공통 계약을 따릅니다. 링크의 origin 은 데이터 계층 설정(`webBaseUrl`)이 완성합니다.
- **이유:** 링크를 받는 쪽은 앱이 아니라 웹이라 앱은 전달만 맡으면 되고, 시스템 공유 시트가 클립보드보다 한 번의 탭으로 목적지까지 닿습니다. 공유 SDK 를 싣지 않는 초대의 결정과 같은 이유입니다.
- **주요 영향:** 열람 화면은 여전히 웹 소유입니다. 디버그 빌드는 API 가 dev 이고 웹 origin 기본값이 운영이라 발급 링크를 운영 웹이 찾지 못하며, dev 웹은 SSO 뒤라 공개 origin 이 없어 수용합니다.
- 근거: [KNK-1320](https://kimandkang.atlassian.net/browse/KNK-1320), [Android 계획](../../../../../../manyak-android/docs/plans/chat-room.md)

## A-048. 채팅 안내 투어를 같은 컴포지션의 오버레이로 그리고 뒤로가기를 건너뛰기로 처리

- 결정일: 2026-09-26 · 기록 확정 상태: Accepted
- **맥락:** 공통 [첫 진입 안내](../2-2-REQUIREMENTS.md#2-2-6-처음-사용-안내)는 웹 구현(DOM 측정·`body` 포털)을 전제로 합니다. 앱은 컴포저 버튼의 위치를 재서 딤을 뚫어야 하고, 웹에는 없는 시스템 뒤로가기가 투어 중에 눌릴 수 있습니다.
- **결정:** 투어는 `Dialog`·`Popup` 창이 아니라 채팅방 컴포지션 맨 위의 상자로 그리고, 대상 버튼은 `onGloballyPositioned`로 루트 좌표를 올립니다. 뒤로가기는 채팅방을 떠나지 않고 건너뛰기와 같이 닫으며 `client_chat_tourSkipButton_clicked`를 그 시점의 스텝으로 보냅니다. 노출 판정·기록·분석과 지금 스텝은 `ChatRoomViewModel`이, 대상이 그려진 스텝 고르기와 배치는 화면이 맡습니다.
- **이유:** 별도 창은 좌표계가 달라 창 위치를 다시 맞춰야 하고, 같은 컴포지션이면 측정한 좌표를 그대로 씁니다. 뒤 화면 조작은 `pointerInput`, 보조기술은 `clearAndSetSemantics`로 창과 같은 모달성을 얻습니다. 투어가 뜬 채 뒤로가기로 방을 나가면 이미 열람 기록이 남아 다시 볼 수 없으므로, 앱 모달의 관례대로 투어만 닫습니다. 이탈 지점을 보는 지표라 건너뛰기로 셉니다. 스텝을 ViewModel에 두는 것은 회전 뒤 첫 스텝으로 되돌아가거나 도달 이벤트가 중복되지 않게 하려는 것입니다.
- **주요 영향:** 건너뛰기 이벤트에 버튼 클릭과 뒤로가기가 섞입니다. 프로세스가 재생성되면 투어 상태가 사라지지만 열람 기록이 이미 남아 다시 열리지 않습니다(웹 새로고침과 같음).
- 근거: [KNK-1431](https://kimandkang.atlassian.net/browse/KNK-1431), [Android 계획](../../../../../../manyak-android/docs/plans/chat-tour.md)

## A-050. 실시간 이미지 안내의 수명과 시트 위 오버레이

- 결정일: 2026-10-04, 기록 확정 상태: Accepted
- 후속 관계: [A-048](DECISIONS.md#a-048)의 첫 진입 투어 결정은 유지합니다. 설정 시트 위의 실시간 이미지 안내에만 별도 Popup을 적용합니다.
- **맥락:** 공통 계약은 기기의 두 번째 전송 완료 순간에만 실시간 이미지 안내를 판단합니다. Android 구성 변경으로 예약이 사라지거나 안내가 닫히면 다시 노출할 기회가 없습니다. 설정 시트는 ModalBottomSheet의 별도 창이라 Activity 안에 그린 투어는 시트 위를 덮지 못합니다.
- **결정:** 완료 횟수는 기존 기기 DataStore의 정수 키로 원자적으로 증가시키고 3에서 멈춥니다. 예약, 시트, 안내 표시는 ViewModel이 들고 구성 변경에서 유지합니다. 화면 이탈과 프로세스 종료에는 복원하지 않습니다. 시트가 펼쳐진 뒤 focusable Popup으로 딤과 안내를 그리며 화면 좌표로 행 위치를 맞춥니다. 시스템 뒤로가기는 안내를 먼저 닫고 시트를 남깁니다.
- **이유:** 계정에 속하지 않는 안내를 로그아웃으로 반복시키지 않으며 별도 저장소나 마이그레이션 없이 기존 기기 설정 소유권을 따릅니다. DataStore의 원자적 저장 결과가 있어야 판정하므로 저장 실패를 성공으로 취급하지 않습니다. 뒤로가기로 방이나 시트까지 닫으면 사용자가 안내받은 스위치를 찾기 위해 시트를 다시 열어야 합니다. 공통 투어 딤 그리기는 재사용하되 서로 다른 창의 좌표와 포커스 처리는 분리합니다.
- **주요 영향:** 예약 중 다음 전송이 시작되면 응답 종료 뒤 다시 기다립니다. 회전 뒤 좌표와 장식 애니메이션은 새로 구성합니다. 기기 기록은 남아 프로세스 종료 뒤 같은 안내가 되살아나지 않습니다.
- 근거: [KNK-1517](https://kimandkang.atlassian.net/browse/KNK-1517), [Android 작업 기록](../../../../../../manyak-android/docs/plans/realtime-image-nudge.md)

## A-066. 채팅 실시간 이미지 대기를 마스코트가 인물을 그리는 애니메이션으로 바꾸기

- 날짜: 2026-10-07
- 상태: 확정
- 범위: Android 채팅 실시간 이미지 턴의 4:3 장면 썸네일 자리, 마스코트 안무와 그리기의 공용 재료
- 대체 관계: A-065의 "채팅 실시간 이미지의 장면 썸네일 자리는 점 로딩을 유지합니다"를 대체합니다. 완성 중 표지에 관한 A-065의 나머지 결정은 그대로입니다.

웹([W-025](../WEB/DECISIONS.md#w-025))이 먼저 장면 썸네일 자리를 마스코트가 베레모를 쓰고 붓으로 인물 세 장을 그리는 안무로 바꿨고, Android도 사용자 요청에 따라 같은 값으로 따라갑니다. 응답을 기다리는 약 15초 동안 점 패턴은 진행 중이라는 사실만 말해, 이미지 한 장을 기다리는 자리라 점 로딩이 맞다는 A-065의 판단을 뒤집었습니다. 계약은 [공통 부분 렌더](../2-2-REQUIREMENTS.md#2-2-2-입력과-추천)를 따르고 Android 표현 차이는 없습니다.

안무의 재료(자세와 눈 모양, 낱동작, 막 이음, 붓길 해석)와 그리기 도구(베레모, 붓, 붓질, 무대 색)는 채팅과 제작 탭이 함께 쓰므로 `designsystem`의 `mascot` 패키지에 둡니다. 붓길은 웹과 같은 SVG path 문자열을 그대로 읽어 두 플랫폼이 같은 문자열을 공유하고, 색은 웹 Canvas와 같은 값이 나오도록 지각 색 공간을 거치는 Compose `lerp` 대신 sRGB 값을 그대로 섞습니다.

준비 막은 처음 한 번만 연기하므로 무한 반복 전환 대신 `withFrameMillis`로 무대가 처음 그려진 뒤 흐른 시간을 셉니다. 시간 상태는 그리기 단계에서만 읽어 프레임마다 재구성하지 않으며, 기기 애니메이션 배율이 0이면 첫 그림을 마친 장면에 멈춥니다. 사용처가 없어진 `ImageGenerationLoading`과 점 변위 토큰은 지웠습니다.

## A-068. 채팅 실시간 이미지 대기 그림을 웹 개편 값의 창가 인물화 한 장으로 따라가기

- 날짜: 2026-10-07
- 상태: 확정
- 범위: Android 채팅 실시간 이미지 턴의 4:3 장면 썸네일 안무와 그림, 마스코트 자세의 붓 회전과 누름
- 대체 관계: A-066의 "베레모를 쓰고 붓으로 인물 세 장을 그리는 안무"와 첫 그림을 마친 정지 장면을 대체합니다. 웹이 먼저 바꾼 값([W-027](../WEB/DECISIONS.md#w-027))을 그대로 따르며, 공용 재료를 `designsystem`의 `mascot` 패키지에 두고 sRGB로 색을 섞는 A-066의 나머지 결정은 그대로입니다.

웹이 사용자 요청으로 세 장을 빠르게 그리던 안무를, 아자아자 막을 빼고 4:3 가로 도화지에 창가 인물화 한 장을 11획으로 천천히 그리는 안무로 바꿨습니다. 첫 시안이 정신없다는 피드백을 받아 획 수와 붓끝 속도를 줄였고, 붓은 몸과 따로 움직여 그을 때 끌리고 밑칠에서 눌리고 획 끝에서 튕기며 색을 바꿀 때 물그릇에 헹굽니다. Android도 같은 안무 값과 붓길 문자열로 따라가 한 바퀴가 16.43초로 같아지고, 무대 시작부터 15초에 사인을 마칩니다. 계약은 [공통 부분 렌더](../3-3-LAYOUT.md#3-3-4-생성-대기와-이미지)를 따르고 Android 표현 차이는 없습니다.

붓 회전(`brush`)과 붓털 누름(`press`)은 공용 `MascotPose`의 기본값 0인 필드로 더해 완성 중 표지는 바뀌지 않습니다. 붓털 끝 계산은 그리기와 같은 순서(쥔 자리는 몸 변환, 붓털 벡터는 몸 회전과 붓 회전)로 맞춰 붓이 기울어도 선과 붓끝이 어긋나지 않게 했습니다. 공용 `easeOutBack`은 시작 전 값을 정확히 0으로 고정해, 부동소수 오차로 아직 나오지 않은 소품이 점으로 그려지지 않게 했습니다.

## A-078. 채팅 생성 이어받기를 화면 ViewModel의 재연결 루프로 두고 409를 상세로 가르기

- 결정일: 2026-10-17 · 기록 확정 상태: Accepted
- **맥락:** 서버가 연결이 끊겨도 생성을 계속하고 채팅마다 생성을 하나만 돌리게 되어(KNK-1677, KNK-1678), 공통 계약은 끊긴 생성에 다시 붙고 재진입에서 생성 중인 턴을 이어받으며 409를 `CHAT_TURN_IN_PROGRESS`와 `CHAT_TURN_STALE`로 나눠 다루게 했습니다. Android는 409를 상태 하나로만 알았고, 종단 사건 없는 끊김은 곧바로 상세를 다시 읽어 확정했습니다. 웹은 `followChatGeneration`으로 같은 재연결을 구현했습니다.
- **결정:** 재연결과 결과 판정은 `chat`의 `followGeneration`과 `ChatRoomViewModel`이 맡고 저장소는 스트림 하나씩만 엽니다. 재연결 횟수와 간격은 웹과 같은 4번, 1, 2, 4초입니다. 409는 응답 본문의 `code`를 읽지 않고 상세를 다시 읽어 `generatingTurn`이 있으면 이어받고 없으면 최신 턴을 보입니다. 열린 뒤 읽다가 끊긴 실패는 `ChatSseSource`가 `Interrupted`로 올립니다. 앱이 백그라운드로 가면(구성 변경 제외) 받던 생성의 수신을 끊고, 돌아오면 상세로 이어받거나 저장된 턴을 보입니다.
- **이유:** 결과마다 확정 목록, 전송 잠금, 입력 되돌리기, 선택지 생성이 함께 바뀌어 화면 상태를 가진 ViewModel 밖으로 빼면 같은 정본을 여러 곳이 고칩니다. 409의 두 코드는 어느 쪽이든 입력을 되돌리고 상세를 다시 읽으며, 생성 중이면 상세에 그 생성이 있으므로 코드를 읽지 않아도 같은 결과가 나옵니다. 웹도 같은 판정을 씁니다. 스트리밍 응답 본문을 읽지 않는 기존 원칙도 지킵니다. 읽던 연결의 실패를 네트워크 실패로 올리면 서버가 계속하는 생성을 실패로 안내하게 됩니다. 백그라운드에서는 기기가 프로세스를 얼리거나 연결을 끊어 재연결 시도가 헛돌고, 그 실패 안내가 돌아온 화면에 뜨며 저장된 턴은 방을 다시 열어야 보였습니다. 포그라운드 서비스로 연결을 붙잡는 것은 응답 하나에 알림을 띄워야 해 과합니다.
- **주요 영향:** 409에 새 코드가 생겨도 상세로 판단하므로 따로 다루려면 그때 본문을 읽어야 합니다. 스트림을 열기 전의 네트워크 실패도 상세에 생성 중인 턴이 있으면 이어받는데, 그 생성이 방금 보낸 요청이면 되돌린 입력이 생성 중인 입력과 함께 보입니다. 잠깐 다른 앱을 다녀와도 받던 응답을 처음부터 다시 받습니다. `ChatRoomViewModel`이 detekt `LargeClass` 기준을 넘어 억제합니다.
