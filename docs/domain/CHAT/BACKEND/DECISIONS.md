# DECISIONS.md

CHAT 도메인 백엔드의 중요한 결정을 날짜, 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 둔다. 여기에는 결정 당시의 이유와 변경 이력을 남긴다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 상태는 결정 당시 기준이다. 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.

<br>

### 2. 턴과 판정

**1. 의미 판정은 AI가, 결정적 판정과 상태 보관은 백엔드가 맡는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-04 결정, 2026-07-09 구현 |
| 상태 | 채택 |
| 배경 | AI 서버는 상태를 저장하지 않아 채팅의 진행 상태를 보관할 수 없다. 백엔드는 LLM 없이 의미 관련성을 판정할 수 없다. |
| 채택 | 주요 사건의 관련성, 완결, 진행 턴 수와 엔딩 달성 조건은 AI가 판정해 완료 이벤트로 돌려준다. 엔딩 최소 턴 수는 백엔드가 정해진 기준으로 판정해 조건을 충족한 엔딩만 후보로 보낸다. 목표 사건, 거쳐온 사건, 도달 엔딩은 채팅에 저장하고 매 턴 되돌려 보낸다. |
| 대안 | 백엔드가 문자열 매칭으로 사건을 판정하는 방식. 키워드가 본문에 그대로 나올 때만 동작해 채택하지 않았다. |
| 영향 | 채팅 행에 목표 사건, 진행 턴 수, 도달 엔딩 컬럼이 추가되고 거쳐온 사건 조인 테이블이 생겼다. |

**2. 엔딩 도달은 턴 기록과 사용자, 스토리 집계로 나눈다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-04 결정, 2026-07-09 구현 |
| 상태 | 채택. 집계 키는 5번 결정에서 이름으로 변경 |
| 배경 | 도달 이벤트는 특정 턴에서 발생한다. 스토리 상세의 "본 엔딩" 표시는 사용자와 스토리 단위다. 하나의 기록으로 두 용도를 모두 충족할 수 없다. |
| 채택 | 도달 턴의 AI 응답 메시지와 채팅 행에 도달 엔딩을 기록한다. 회원은 사용자와 스토리 단위 집계를 독립 트랜잭션에 기록하고 게스트는 집계하지 않는다. 채팅당 최초 1회만 인정하고 도달 뒤에도 이어쓰기는 허용한다. 완료 이벤트와 상세 턴 항목에 도달 엔딩 이름을 싣는다. |
| 대안 | 턴 기록만 두고 상세에서 매번 집계하는 방식. 게스트는 서버에 식별 수단이 없어 집계할 수 없고 회원도 매번 채팅 전체를 훑어야 해 채택하지 않았다. |
| 영향 | 클라이언트는 카드의 도달 엔딩을 합산해 게스트의 "본 엔딩"을 표시한다. 이관 시 게스트 채팅의 도달 기록을 반영해 집계를 보정한다. |

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-07 |
| 상태 | 채택 |

| 영향 | 재생성 횟수는 이프 선차감 대사가 완료 수를 셀 때 턴 수에 더해져 성공한 재생성이 환불되지 않게 한다. |

**4. 선택지 생성을 턴 스트림에서 분리한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-20 |
| 상태 | 채택 |
| 배경 | AI가 선택지 3개를 만들기 위해 내부 재호출을 하면 본문 완료가 선택지 생성에 걸린 시간만큼 늦어졌다. |
| 채택 | 본문 스트림의 완료 이벤트는 선택지를 비워 보낸다. 클라이언트가 턴 ID로 전용 요청을 보내면 백엔드가 같은 AI 입력 데이터에 저장된 본문을 더해 AI에 선택지 생성을 요청한다. 선택지는 무료이며 이미 있으면 다시 만들지 않는다. 클라이언트는 상세 재조회로 표시한다. |
| 대안 | 완료 이벤트에서 선택지를 기다리는 방식. 지연 시간을 줄일 수 없어 채택하지 않았다. 선택지를 후속 이벤트로 보내는 방식은 세 클라이언트의 SSE 계약이 모두 바뀌어 채택하지 않았다. |
| 영향 | 완료 이벤트의 `choices` 필드는 계약 유지를 위해 빈 배열로 남는다. AI 호출 기록이 본문과 선택지 두 행으로 나뉘고 채팅과 턴 번호로 조인한다. 본문 성공 뒤 선택지만 실패해도 환불하지 않는다. |

**5. 사건과 엔딩은 이름으로 다시 연결하고 이름 스냅샷을 보관한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-08-31, 2026-09-01 |
| 상태 | 채택 |
| 배경 | 스토리를 수정할 때 엔딩과 주요 사건 행을 삭제하고 다시 만들어 FK가 비워졌다. 공개 스토리에서 제작자가 엔딩을 손보기만 해도 모든 독자의 도달 기록이 사라졌다. AI 입력 데이터를 공개본에서 읽으면 AI가 돌려준 이름이 현재 행에 없어 매칭이 실패했다. |
| 채택 | 판정 후보는 AI에 실제로 보낸 목록에서 찾는다. 현재 행은 FK 값이 필요할 때만 이름으로 다시 찾고 없으면 이름만 기록한다. 채팅과 메시지에 도달 엔딩 이름과 거쳐온 사건 이름을 스냅샷으로 보관한다. 집계 테이블의 유니크 키도 이름이다. 프롤로그도 채팅 생성 시점 값을 보관해 시작 설정 참조가 끊기면 쓴다. |
| 대안 | 공개본의 ID를 현재 FK에 직접 저장하는 방식. 현재 행의 ID와 달라 FK 제약을 만족하지 못해 채택하지 않았다. 목표 사건의 이름도 보관하는 방식은 매 턴 AI가 다시 지목하므로 잃는 것이 한 턴의 연속성뿐이라 채택하지 않았다. |
| 영향 | 2번의 집계 키가 엔딩 ID에서 이름으로 바뀌었다. 배포 전에 이미 참조가 끊긴 과거 도달은 턴 단위 표시가 복구되지 않는다. |

### 3. 이미지

**6. 장면 이미지는 AI가 본문에 삽입한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-07 결정, 2026-07-10 계약 확정 |
| 상태 | 채택. 마커 형식과 상세 재구성은 7번이 대체 |
| 배경 | 이미지를 장면에 연결하는 판정을 누가 맡을지 정해야 했다. 장면 적합성은 본문을 생성하는 AI가 이미 아는 정보다. |
| 채택 | 백엔드가 인물 이미지 목록을 요청에 싣고 AI가 본문에 마커로 위치를 표시한다. 인물 이미지는 컴파일 1회에 확정해 DB에 고정하고 매 턴 결정적으로 치환한다. |
| 대안 | 백엔드가 트리거 문자열 매칭으로 연결하는 방식. 키워드가 본문에 그대로 나올 때만 동작하고 삽입 위치를 제어할 수 없어 채택하지 않았다. 매 턴 AI가 후보에서 인물 이미지를 고르는 방식은 턴마다 얼굴이 바뀔 수 있어 채택하지 않았다. 완료 이벤트에 오프셋과 키를 싣고 백엔드가 삽입하는 방식은 언어별 오프셋 단위가 달라 채택하지 않았다. |
| 영향 | 업로드와 프리셋 선택 API, 턴 메타의 이미지 필드가 계약에서 빠졌다. |

**7. 인물 이미지는 화자 라벨 감지와 URL 마커로 전달하고 상세에서 재구성하지 않는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-08-27 합의, 2026-09-13 클라이언트 계약 정리 |
| 상태 | 채택 |
| 배경 | AI가 명시 태그를 빠뜨려 이미지가 나오지 않았다. 본문에 이미지 이름만 저장하면 과거 턴의 이미지를 현재 인물 테이블에 의존해 복원해야 했다. |
| 채택 | AI가 줄 머리의 인물 라벨을 감지해 실시간 이벤트를 보내고 완료 본문의 대사 줄 위에 `[[URL]]` 마커를 둔다. 저장 원본은 마커를 포함한 본문이다. 상세와 공유는 본문을 그대로 돌려주고 이미지 목록을 만들지 않는다. 클라이언트로 보내는 실시간 이벤트에는 이름과 URL만 포함한다. 완료 이벤트에는 이미지 목록을 싣지 않는다. |
| 대안 | 이미지 이름을 저장하고 조회 때 URL로 바꾸는 방식. 인물이 수정되면 과거 턴이 바뀌어 채택하지 않았다. 실시간 이벤트에 이미지 이름을 함께 보내는 방식은 클라이언트가 쓰지 않는 값이라 채택하지 않았다. |
| 영향 | 6번의 태그 감지와 상세 목록 복원 부분을 대체한다. AI에서 백엔드로 오는 이미지 목록은 실시간 이미지 검증에만 쓴다. |

**8. 실시간 이미지는 백엔드가 발급한 자리에 AI가 올리고 백엔드가 검증한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-16 |
| 상태 | 채택 |
| 배경 | 턴 진행 중 장면 이미지를 새로 생성하려면 저장 위치와 비용 관리가 필요했다. 생성 이미지용 계약을 따로 두면 마커 URL을 확정하는 책임이 두 곳으로 갈라진다. |
| 채택 | 백엔드는 턴마다 presigned PUT 업로드 위치 1개를 요청에 포함한다. AI는 해당 위치에 생성한 이미지를 업로드한 뒤 기존 이벤트와 마커를 쓴다. 백엔드는 발급한 URL과 정확히 일치하고 객체가 존재하는 마커만 통과시키고 나머지 실시간 URL은 제거한다. 이미지는 턴과 별개의 체험 카운터와 비용을 쓰고 유료 항목은 한 번의 잔액 판정으로 합산 차감한다. 환불은 차감 행별로 한다. |
| 대안 | AI가 임의 위치에 업로드하고 URL을 보내는 방식. 백엔드가 소속과 비용을 검증할 수 없어 채택하지 않았다. 턴당 여러 장은 비용 때문에 채택하지 않았다. |
| 영향 | 이미지 차감은 선차감 대사 배치의 대상이 아니라 프로세스 중단 시 자동 환불되지 않을 수 있다. 빈도가 낮아 수용한다. |

### 4. 과금과 동시성

**9. 과금은 저장 확정 시점에 굳히고 환불은 백그라운드 작업이 한 번만 판정한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-08-07 |
| 상태 | 채택. 완료 콜백의 시작 전 취소는 16번이 대체 |
| 배경 | 스트림 시간 초과와 저장이 겹치면 저장된 턴이 환불되거나 실패한 턴이 과금된 채 남을 수 있었다. 첫 환불 실패에 대한 알림이 누락됐다. |
| 채택 | 턴 저장이 확정되면 과금을 확정하고 이후 전송 실패는 환불하지 않는다. 환불은 백그라운드 작업 종료 시 한 곳에서 판정한다. 스트림 완료 콜백은 시작 전 취소만 처리한다. 결과와 환불 지표를 두고 환불 지표는 기동 시 0으로 등록한다. |
| 대안 | 완료 콜백에서도 환불하는 방식. 저장과 경쟁해 이중 판정이 생겨 채택하지 않았다. |
| 영향 | 저장된 턴은 클라이언트가 완료 이벤트를 받지 못해도 과금된다. 클라이언트는 결과를 알 수 없으면 상세를 다시 조회한다. |

**10. 이어쓰기와 재생성은 채팅 행 잠금으로 직렬화한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-07 |
| 상태 | 채택. 저장 잠금은 유지하고 생성 선점과 시작 상태 재확인은 16번이 보완 |
| 배경 | 재생성이 이어쓰기로 생성됐지만 아직 커밋되지 않은 새 턴을 보지 못하고 이전 마지막 턴을 교체할 수 있었다. 동시 재생성은 중복 과금과 재생성 횟수 유실을 일으켰다. |
| 채택 | 저장 트랜잭션에서 채팅 행에 비관적 쓰기 잠금을 걸고 마지막 턴을 재확인한다. 다르면 결과를 폐기하고 환불한다. 선택지 저장과 공유 발급, 삭제도 같은 잠금을 쓴다. |
| 대안 | 메시지 순서 유니크에만 의존하는 방식. 제자리 교체는 유니크로 직렬화되지 않아 채택하지 않았다. |
| 영향 | AI 호출과 스트리밍 동안에는 잠금을 유지하지 않는다. |

**16. 연결과 무관하게 생성하고 채팅별 선점과 이벤트 보관으로 이어받는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-16 |
| 상태 | 채택 |
| 배경 | 사용자가 응답 전에 채팅 화면을 나갔다 돌아오면 완료 전 입력과 응답이 보이지 않았다. 끊긴 것으로 오인해 재전송하면 두 요청이 차례로 저장됐다. 7월 간편 제작 생성 복구(KNK-623)에서도 화면 이탈과 생성 작업의 수명을 분리했다. 채팅에도 같은 원칙을 적용한다. 큐 대기와 저장 중 마감, Redis 실패, 이벤트 보관과 수신 종료의 경계도 함께 정한다. |
| 채택 | 연결이 끊겨도 생성을 계속하고 저장 후 과금한다. 생성 마감은 요청 접수부터 큐 대기를 포함해 120초이며 연결 종료나 재연결로 초기화하지 않는다. 마감과 저장 진입은 CAS로 겨룬다. 저장 진입 전 마감 초과는 실패와 환불로 끝나며 `CANCELLED`를 마감 종료 상태로 재사용한다. 저장에 먼저 진입하면 마감이 지나도 저장을 마치고 DB의 저장 결과로 정산한다.<br>이어쓰기와 재생성은 채팅별 Redis 생성 중 키 `chat:{chatId}:generating`을 공유하고 `SET NX`로 선점하며 TTL은 150초다. Redis 오류로 키를 획득하지 못하면 과금 없이 503 `SERVICE_UNAVAILABLE`로 거절하고 결과는 `failure`로 집계한다. 상세의 생성 중 상태와 `started`에 UUID 문자열인 생성 ID를 제공한다. 선택 필드 `lastTurnId`로 낡은 이어쓰기를 거절한다. 저장 시 채팅 행 잠금 안에서 마지막 턴과 재생성 교체 상태를 포함한 시작 상태를 재확인해 다르면 폐기하고 환불한다.<br>생성 이벤트 전부를 Redis Streams에 기록하고 처음 연결과 재연결 모두 처음부터 읽는다. 첫 연결인 이어쓰기와 재생성 POST는 자기 생성의 스트림을 기다리며 404로 판정하지 않는다. 재연결 GET은 스트림이 없고 생성 중 키도 해당 생성 ID를 담고 있지 않을 때만 스트림 부재로 404를 반환한다. 키가 해당 생성 ID를 담고 있으면 큐 대기 중 이벤트가 없어도 스트림을 기다린다.<br>이벤트 기록 실패는 생성과 저장을 중단하지 않는다. 수신 연결은 `completed` 또는 `error`를 받으면 닫는다. 읽기 대기는 5초 단위로 끊어 확인하며 생성 중 키가 더 이상 해당 생성 ID를 담고 있지 않은데 종료 이벤트가 없으면 종료 이벤트 없이 연결을 닫는다. 기록 실패, 서버 강제 종료, 스트림 만료에도 같은 조건을 적용한다. 클라이언트는 종료 이벤트 없이 닫힌 연결을 상세 재조회로 처리한다.<br>스트림 생성 시 TTL 150초를 설정하고 종료 시 5분으로 다시 설정한다. TTL, 보관 기간, 읽기 대기 확인 주기 5초는 코드 상수다. 저장 진입 뒤 저장이 길어져 스트림이 먼저 만료되면 재생할 이벤트가 없는 한계를 수용한다. TTL 연장 장치는 두지 않는다. 수신 연결은 위 종료 조건으로 닫히고 상세 재조회로 복구한다. 턴과 과금은 DB의 저장 결과가 기준이므로 영향이 없다. |
| 대안 | 15번처럼 연결 종료를 취소로 처리하면 재진입 때 작업 상태를 확인하거나 결과를 이어받을 수 없다. 저장 단계의 직렬화만으로는 중복 AI 호출과 선차감을 막지 못한다. `lastTurnId` 필수화는 강제 업데이트 장치가 없는 구버전 앱을 막아 채택하지 않았다. 큐 대기를 마감에서 빼면 요청 후 전체 대기가 길어진다. 저장 진입 후 마감으로 저장을 중단하면 정산 판정이 불명확해진다. Redis 선점 오류에도 생성을 허용하면 중복 생성 방지 보장이 약해진다. 스트림 TTL 연장 대신 이벤트 유실 시 상세 재조회로 복구하는 한계를 수용한다. |
| 영향 | 15번의 연결 종료에 의한 취소 선점과 환불 판정을 대체하고 9번의 완료 콜백에 의한 시작 전 취소도 제거한다. 10번의 저장 잠금은 유지하고 생성 선점과 시작 상태 재확인을 추가한다. 채팅 충돌 코드는 생성 중, 낡은 턴, 엔딩 도달 재생성으로 나눈다. DB 스키마는 바꾸지 않는다. 연결 종료의 `cancelled` 결과는 과거 조회용으로만 유지하고 저장 진입 전 마감 초과는 `failure`로 집계한다. 생성 중 키 획득 오류도 과금은 없지만 채팅 생성 전체를 막는 장애이므로 `failure` 알림 대상이다.<br>이탈 중 실패하면 입력이 사라진 것처럼 보일 수 있으나 환불한다. KNK-1677에서 생성 상태, 동시성, 연결 독립 실행을 적용하고 KNK-1678에서 이벤트 이어받기를 적용한다. 1단계는 이탈 중 재생성의 성공과 실패를 상세만으로 구분하지 못한다. 2단계는 클라이언트가 생성 ID를 받아 보관한 경우(`started` 또는 생성 중 상세에서 수신)에만 보관된 스트림의 `completed` 또는 `error`로 재생성의 성공과 실패를 구분한다. `started` 전에 이탈하고 생성이 끝난 뒤 돌아와 생성 ID를 모르면 1단계와 같은 한계가 남는다. 스트림이 먼저 만료되면 생성 ID를 알아도 재생할 이벤트가 없어 상세 재조회로 복구한다. 롤링 배포 중 구버전이 섞인 몇 분 동안 생성 선점 보장이 일부 빠지는 일회성 한계를 수용하며 별도 배포 전환 장치는 두지 않는다. |

| 상태 | 채택. 회원 체험 턴의 청구 모델은 19번이 대체 |
| 배경 | AI 서버가 채팅 본문을 등급별 LLM으로 라우팅하게 됐다(KNK-1739). AI 턴 계약에 회원 공개 식별자 `user_id`와 모델 코드 `model_tier`가 생겼고 백엔드는 두 값을 보내지 않고 있었다. 오로라 모델의 LLM은 비용이 커 턴 가격을 모델별로 달리해야 한다. 모델 목록과 가격은 앞으로 바뀔 수 있다. |
| 채택 | 사용자는 채팅 단위로 모델을 고르고 언제든 바꾼다. 새 채팅의 기본은 오로라(`AURORA`)이고 모델 컬럼 추가 전의 채팅은 라이트(`LITE`)로 채워 진행 중 채팅의 가격이 바뀌지 않게 한다. 컬럼은 `NOT NULL DEFAULT 'LITE'`로 추가해 백필과 구버전 코드의 컬럼 생략 삽입을 함께 처리하고, 새 채팅의 기본값은 DB 기본값이 아니라 앱이 기본 모델(`is_default`)을 명시해 정한다. 모델의 코드, 표시 이름, 턴당 가격, 노출 순서, 노출 여부, 기본 여부를 `chat_models` 행으로 두고 활성 행을 누구나 조회할 수 있게 한다. 가격은 라이트 20, 오로라 50이며 재생성도 같다. 턴마다 청구 모델을 정한다. 게스트 턴과 회원의 체험 턴은 선택과 무관하게 라이트(`LITE`)이고 체험을 소진한 회원 턴은 요청 시점의 유효 모델이다. 회원 턴은 AI 요청에 공개 식별자를 항상 싣는다. 보관한 모델이 비활성이면 읽기와 턴에서 기본 모델로 대체하고 행은 고치지 않는다. 모델 변경은 생성 중 키와 채팅 행 잠금 없이 수행하고 진행 중인 턴은 시작 시점의 모델과 가격으로 끝낸다. 환불은 차감 행의 금액 그대로다. 턴 가격의 정본은 모델 표 하나이며 PAYMENT 정책 키 `chat_turn_cost`는 폐기한다. 정책값 응답의 `chatTurnCost`는 이번 릴리스에서 라이트(`LITE`) 가격으로 유지하고 다음 릴리스에서 제거한다. 오로라 모델 안의 A/B 배정은 AI 서버의 일이며 백엔드는 저장하거나 관리하지 않는다. |
| 대안 | 코드값을 AI 계약의 `BASIC`, `ADVANCED`로 두는 방식. 표시 이름과 코드가 따로 놀아 상품 이름 `LITE`, `AURORA`로 통일하고 AI 계약을 함께 바꾼다. 턴 단위 선택. 요청마다 모델을 받으면 생성 중 상태와 재생성에도 모델을 실어야 하고 클라이언트가 매 요청 가격을 계산해야 해 채택하지 않았다. 서버 enum과 설정값으로 모델을 두는 방식. 가격 조정과 노출 변경마다 배포가 필요해 채택하지 않았다. 모델 가격을 정책 오버라이드 키로 두는 방식. 모델마다 키가 늘고 이름과 순서까지 담을 수 없으며 모델 표와 이중 정본이 되어 채택하지 않았다. 체험 턴에도 선택한 모델을 쓰는 방식. 무료 턴에 오로라 모델의 LLM 비용이 들어 채택하지 않았다. 모델 변경 시 진행 중 턴을 거절하거나 새 모델로 재정산하는 방식. 차감과 환불의 금액이 어긋날 수 있어 채택하지 않았다. |
| 영향 | `story_chats`에 모델 컬럼이 생기고 채팅 생성, 상세, 모델 목록, 모델 변경 계약이 바뀐다. AI 요청에 `user_id`와 `model_tier`를 싣는다. 같은 채팅의 턴 차감액이 섞이므로 저장한 AI 응답과 버전 이력에 차감 행 ID를 연결하고 턴 차감의 참조 종류를 `CHAT_TURN`으로 바꾸며 PAYMENT 선차감 대사를 차감 행 단위로 바꾼다(PAYMENT 세트 18번 결정). 새 모델 코드는 AI 라우팅 배포가 먼저여야 한다. 웹은 모델 선택과 가격 표시를 같은 릴리스에서 반영한다. |

**19. 회원의 턴 체험은 라이트 턴에만 적용한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-23 |
| 상태 | 채택. 17번 결정의 회원 체험 턴 청구 모델을 대체 |
| 배경 | 17번 결정은 회원의 체험 턴을 고른 모델과 무관하게 라이트(`LITE`)로 생성했다. 새 채팅의 기본이 오로라(`AURORA`)라 체험이 남은 회원은 오로라를 골라도 라이트 응답을 받았다. 회원이 고른 모델로 응답하지 않는 문제가 있었다. |
| 채택 | 회원 턴의 청구 모델은 체험 잔여와 무관하게 요청 시점의 유효 모델이다. 턴 체험은 청구 모델이 라이트인 턴에만 적용한다. 라이트 턴은 체험 잔여를 먼저 쓰고 소진되면 라이트 가격을 선차감한다. 다른 모델의 턴은 체험을 예약하지 않고 그 모델의 가격을 선차감하며 잔액이 부족하면 402로 거절하고 체험 카운터를 바꾸지 않는다. 재생성도 같은 규칙이다. 게스트 턴은 17번 결정대로 라이트로 생성하고 체험 횟수를 예약한다. 이미지 체험은 바꾸지 않는다. |
| 대안 | 회원 체험 턴을 선택과 무관하게 라이트로 생성하는 방식(17번 결정). 회원이 고른 모델로 응답하지 않아 대체했다. 체험 턴에 오로라도 무료로 여는 방식. 오로라의 LLM 원가가 라이트의 20~30배라 채택하지 않았다. |
| 영향 | 체험이 남은 회원도 오로라 턴은 50 이프를 차감한다. API 필드와 응답 형태, DB 스키마, AI 계약은 바뀌지 않는다. 체험과 적용가를 고른 모델과 무관하게 표시하던 클라이언트는 라이트 턴에만 체험을 적용하도록 함께 바꾼다. |

### 7. 출력 분량

**18. 출력 분량은 채팅 단위로 보관하고 채팅 설정 변경으로 바꾼다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-23 |
| 상태 | 채택 |
| 배경 | AI 서버가 턴 요청의 `long_response`로 본문 분량을 고르게 됐다. 값은 boolean이고 `false`는 짧은 응답, `true`는 긴 응답이며 생략하면 `false`다. 채팅 화면에 기본 꺼짐인 "많은 출력" 토글을 두기로 했다. 사용자가 채팅을 나갔다 들어오거나 다른 기기에서 열어도 토글 상태가 유지돼야 한다. |
| 채택 | 출력 분량을 `story_chats.long_response`로 채팅 단위로 보관한다. 컬럼은 `NOT NULL DEFAULT false`로 추가해 기존 채팅을 짧은 응답으로 채우고 구버전 코드의 컬럼 생략 삽입을 받는다. 새 채팅은 짧은 응답으로 시작하고 생성 요청에서 값을 받지 않는다. 변경은 17번 결정의 모델 변경 요청 `PATCH /chats/{chatId}`를 부분 수정으로 넓혀 `model`과 `longResponse`를 각각 선택 필드로 받는다. 보낸 필드만 바꾸므로 `model`만 보내는 기존 클라이언트는 그대로 동작한다. 두 필드가 모두 없거나 어느 한쪽이라도 `null`이면 거절한다. 응답의 모델은 상세와 같은 유효 모델이다. 설정 변경은 보낸 필드의 컬럼만 갱신해 동시 변경이나 턴 저장과 서로의 값을 덮지 않는다. 권한, 정지 계정, 생성 중 규칙은 모델 변경과 같다. 진행 중인 턴은 시작 시점의 값으로 끝나고 바꾼 값은 다음 이어쓰기와 재생성부터 적용된다. 게스트 턴과 회원의 체험 턴도 보관한 값을 쓴다. 긴 응답과 짧은 응답의 턴 원가 차이가 작아 모델처럼 라이트(`LITE`)로 고정해 제한하지 않는다. 이어쓰기와 재생성은 턴 시작 시점의 값을 AI 요청에 항상 싣는다. AI 계약의 boolean 형태는 그대로 쓴다. |
| 대안 | 턴 요청마다 클라이언트가 값을 싣는 방식. 채팅을 나갔다 들어오면 상태가 사라지고 기기 사이에 유지되지 않아 채택하지 않았다. 모델도 채팅 단위로 보관한다(17번 결정). 출력 분량 전용 엔드포인트를 두는 방식. 모델과 같은 채팅 설정이라 PATCH 하나로 충분해 채택하지 않았다. 회원 단위 설정으로 두는 방식. 합의한 범위가 채팅 화면의 토글이라 채택하지 않았다. |
| 영향 | `story_chats`에 출력 분량 컬럼이 생기고 채팅 생성, 상세, 채팅 설정 변경 계약에 `longResponse`가 생긴다. AI 요청에 `long_response`를 싣는다. 턴 저장과 재생성 로그, 턴 결과 분석 이벤트에 `long_response`를 남겨 A/B 비교에서 짧은 응답 턴만 고를 수 있게 한다. 결과 지표 태그에는 싣지 않는다. 구버전 AI는 모르는 필드를 무시하므로 서버와 AI의 배포 순서는 무관하다. 토글이 없으면 켤 수 없으므로 웹과 앱의 토글과 같은 릴리스에서 배포한다. |

### 8. 대화 요약

**20. 대화 요약은 백엔드가 시점과 범위를 정하고 요약 끝 턴과 함께 채팅 행에 보관한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-28 |
| 상태 | 채택 |
| 배경 | 턴 요청은 매번 대화 내역 전체를 싣고 AI 서버는 입력을 줄이지 않아 턴이 쌓일수록 AI 입력이 커진다. AI 서버는 요청 사이에 상태를 저장하지 않는다. `story_chats.summary` 컬럼은 있었지만 쓰지 않았고 턴 요청의 `summary`는 항상 빈 문자열이었다. |
| 채택 | 이어쓰기 턴 저장이 커밋되고 완료 턴 수가 10의 배수가 되면 백엔드가 AI 서버의 요약 API를 비동기로 호출한다. 턴 진행은 요약을 기다리지 않는다. 요청은 기존 요약과 아직 요약하지 않은 완료 턴의 원문이고 응답은 갱신된 요약 하나다. AI 서버는 요약 생성, 재시도, LLM 전환만 맡는다. 요약 범위는 백엔드가 요청을 시작할 때 고정한다. 성공한 요약은 기존 `summary` 컬럼에 저장하고 요약 끝 턴은 새 컬럼 `summary_through_turn`에 함께 저장한다. 요약 끝 턴은 `NOT NULL DEFAULT 0`이고 0은 요약 없음이다. 요약마다 첫 턴부터 끝 턴까지를 모두 담으므로 채팅 행 잠금 안에서 끝 턴이 저장된 값보다 클 때만 저장해 늦게 끝난 이전 범위의 요약이 새 요약을 덮지 않게 한다. 이후 턴 요청은 요약과 요약 범위 뒤의 원문을 싣고 원본 메시지는 보존한다. 실패하면 기존 요약과 원문을 유지하고 다음 10턴 경계에서 다시 요청한다. 요약 입력의 이미지 마커는 AI 서버가 지우고 백엔드는 저장 원문을 그대로 보낸다. 대화 요약 설정은 기본 꺼짐이고 끄면 요약 요청과 저장된 요약의 사용을 함께 멈춘다. 재생성의 요약 무효화는 설정과 무관하게 수행한다. |
| 대안 | 명세 작성 중 검토한 대안이다. AI 서버가 요약과 범위를 보관하는 방식. AI 서버가 상태를 두지 않는 구조와 맞지 않아 채택하지 않았다. 응답에 요약 끝 위치를 돌려받는 방식. 범위는 요청을 보낸 백엔드가 이미 알고 있어 채택하지 않았다. 매 턴 요약을 기다리는 방식. AI 서버의 재시도를 포함하면 요약 한 번이 수 분까지 걸려 채택하지 않았다. 실패한 요약을 매 턴 다시 요청하는 방식. AI 장애 중 요청이 매 턴 몰려 채택하지 않았다. 요약 끝 턴의 요약 없음을 `NULL`로 두는 방식. 저장 조건의 비교마다 `NULL`을 따로 다뤄야 해 `current_turn`과 같은 0 기준을 택했다. 설정이 요약 요청만 막는 방식. 요약 품질 문제로 끌 때 저장된 요약이 계속 실려 채택하지 않았다. |
| 영향 | `story_chats`에 요약 끝 턴 컬럼이 생기고 `ai_call_logs`에 `chat_compact` 호출이 기록된다. 클라이언트 계약은 바뀌지 않는다. 요약 API의 경로와 오류 계약은 AI 세트의 5 계약이 정하고 백엔드의 실패 처리는 오류 종류와 무관하다. 서버는 설정을 끈 채 AI 서버보다 먼저 배포할 수 있다. AI 세트 A20의 이미지 마커 처리는 AI 서버가 지우는 쪽으로 정해진다. |

<br>

**21. 요약 중 재생성이 있으면 바뀐 턴의 위치와 무관하게 요약을 버린다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-29 |
| 상태 | 채택 |
| 배경 | 요약하는 사이 요약 범위의 턴이 재생성되면 그 요약은 이전 응답을 담는다. 재생성은 마지막 턴을 제자리에서 교체하고 턴 수를 바꾸지 않으며 재생성 횟수를 올린다. |
| 채택 | 요약을 시작할 때 원문과 같은 스냅샷에서 재생성 횟수를 기록한다. 저장할 때 채팅 행 잠금 안에서 비교해 다르면 결과를 버린다. 바뀐 턴이 요약 범위 밖이어도 버린다. 버린 범위는 다음 10턴 경계에서 다시 요약한다. |
| 대안 | 명세 작성 중 검토한 대안이다. 재생성된 턴 번호를 따로 기록해 요약 범위 안일 때만 버리는 방식. 범위 밖 재생성으로 버리는 경우는 요약하는 사이 범위 뒤에 새로 저장된 턴이 재생성될 때뿐이고 다음 경계에서 다시 요약해 손해가 작다. 턴별 기록을 새로 두는 비용이 더 커 채택하지 않았다. 요약에 재생성 횟수를 함께 저장하고 요약을 쓸 때마다 비교하는 방식. 이전 이미지로 되돌린 기간의 재생성으로 남은 낡은 요약을 걸러 낼 수 있지만 재생성은 범위 밖 턴에도 횟수를 올려 멀쩡한 요약까지 못 쓰게 되어 채택하지 않았다. 그 경우는 다시 배포할 때 요약을 일괄로 비우는 절차로 처리한다. |
| 영향 | 요약하는 동안 재생성이 잦은 채팅은 요약이 다음 경계로 밀릴 수 있다. 폐기는 `chat_compact_discarded` 로그의 `reason=REGENERATED`로 확인한다. |

**22. 선택지와 재생성의 대상 턴이 요약 범위에 들면 요약 없이 원문으로 보낸다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-28 |
| 상태 | 채택 |
| 배경 | 재생성과 선택지 요청은 대상 턴인 마지막 턴을 `history`에서 빼고 `user_input`과 `ai_output`으로 따로 보낸다. 요약 끝 턴이 마지막 턴과 같으면 요약이 대상 턴을 담고 있어 같은 장면이 요약과 별도 필드에 두 번 실린다. 재생성은 대상 턴의 응답을 버리고 다시 쓰는 요청이라 버릴 응답이 요약에 남는다. |
| 채택 | 대상 턴이 요약 범위에 들면 그 요청은 `summary`를 빈 문자열로 보내고 `history`에 대상 턴을 뺀 원문 전체를 싣는다. 대상 턴이 범위 밖이면 요약과 요약 범위 뒤의 원문을 싣고 대상 턴은 `history`에서 뺀다. 재생성이 성공하면 같은 트랜잭션에서 대상 턴을 담은 요약과 요약 끝 턴을 비우고 다음 10턴 경계에서 다시 요약한다. 선택지 생성은 요약을 바꾸지 않는다. |
| 대안 | 명세 작성 중 검토한 대안이다. 요약을 그대로 싣는 방식. 대상 턴이 두 번 실리고 재생성으로 버릴 응답이 요약에 남아 채택하지 않았다. 재생성 직후 바로 다시 요약하는 방식. 요약 시점이 10턴 경계 하나라는 규칙에 예외가 생기고 다음 경계까지의 원문 전송은 요약 도입 전과 같은 상태라 채택하지 않았다. |
| 영향 | 요약 끝 턴과 마지막 턴이 같은 동안의 재생성과 선택지 요청은 원문 전체를 싣는다. 무효화한 뒤 다음 경계까지의 턴 요청도 원문 전체를 싣는다. |

### 9. AI 호출과 응답 기록

**23. 실시간 이미지도 AI 호출 기록에 `chat_image` 행으로 남긴다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-24 |
| 상태 | 채택 |
| 배경 | 관리자 대시보드의 기능별 AI 성공률과 평균 호출 시간에 실시간 이미지를 넣어 달라는 요청이 있었다. 실시간 이미지는 턴 본문 호출 안에서 AI가 만들어 올리므로 서버가 따로 부르는 호출이 없고 `ai_call_logs`에 남지 않았다. `ck_ai_call_logs_feature`도 네 값만 허용했다. |
| 채택 | 업로드 위치를 발급한 턴마다 `feature=chat_image` 행을 `STARTED`로 남기고 검증 결과로 `SUCCEEDED` 또는 `FAILED`로 바꾼다. 소요 시간은 본문 호출 시작부터 발급 URL이 실린 첫 `character_image` 이벤트까지다. 이미지 생성은 토큰 수를 주지 않아 토큰 컬럼은 `null`이다. 기록 실패는 턴과 이미지 결과를 바꾸지 않는다. 이름은 이프 사유 `CHAT_IMAGE`와 같은 `chat_image`로 한다. |
| 대안 | 본문 행에 이미지 성공 여부 컬럼을 더하는 안은 기능별 집계가 `feature` 하나로 되지 않고 관리자 차트가 따로 셈해야 한다. AI 서버가 이미지 호출을 따로 보고하게 하는 안은 AI 계약이 바뀌어 동반 배포가 필요하다. 업로드 위치 발급 실패도 `FAILED`로 남기는 안은 AI가 이미지를 만들지 않은 경우까지 AI 실패로 세게 된다. |
| 영향 | `ck_ai_call_logs_feature`를 DROP 뒤 ADD로 다시 만드는 마이그레이션이 필요하다. 관리자 AI 차트의 기능이 다섯 개가 된다. 관리자 AI 비용은 토큰 기반이라 `chat_image`를 넣지 않는다(ADMIN 결정 20). |
| 보완 | 2026-10-24 ADMIN 결정 21 채택으로 관리자 AI 비용은 `chat_image`의 성공 수에 장당 원가를 곱해 넣는다. 영향의 "관리자 AI 비용은 `chat_image`를 넣지 않는다"는 이 보완으로 바뀐다. |

**24. AI 응답 행에 그 턴을 만든 청구 모델을 기록한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-24 |
| 상태 | 채택 |
| 배경 | 관리자 대시보드가 모델별 턴 수를 채팅의 `model_code`로 묶었다. 채팅 모델은 언제든 바뀌어 과거 턴까지 새 모델로 다시 분류되고, 게스트 턴은 채팅에 `AURORA`가 보관돼 있어도 실제로는 `LITE`로 생성된다(17번, 19번 결정). 채팅 모델로는 실제 사용량을 알 수 없다. |
| 채택 | `story_messages`에 NULL 허용 `model_code`를 더해 AI 응답 행에 그 활성본을 만든 턴의 청구 모델 코드를 기록한다. 재생성으로 활성본이 바뀌면 그 재생성의 청구 모델로 바꾼다. 사용자 입력 행과 컬럼 추가 전의 행은 `NULL`이고 백필하지 않는다. |
| 대안 | `ai_call_logs`의 기록으로 모델을 찾는 안은 그 표가 실제 LLM 이름을 담고 청구 등급을 담지 않으며 턴과의 연결이 저장 뒤에야 확정된다. 기존 행을 채팅 모델로 백필하는 안은 바로 그 재분류 문제를 과거 값에 남긴다. |
| 영향 | 마이그레이션 하나가 생기고 관리자 대시보드의 모델별 턴 수가 이 값을 쓴다(ADMIN 결정 23 보완). 기록 전 턴은 관리자 화면에서 "기록 전"으로 보인다. |

**25. AI의 주요 사건과 엔딩 도달 판정을 없앤다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-22(팀 재확인), 반영 2026-10-30 |
| 상태 | 채택<br>1번 결정의 "주요 사건의 관련성, 완결, 진행 턴 수와 엔딩 달성 조건은 AI가 판정해 완료 이벤트로 돌려준다"를 대체 |
| 배경 | 판정이 스토리 진행에 도움이 적고 비용만 든다는 AI 담당의 제안을 팀이 합의했다(KNK-1626, manyak-ai #177). AI v0.5.0(#183)부터 완료 이벤트의 목표 사건, 완결 사건, 도달 엔딩 판정이 항상 비어 온다. |
| 채택 | 도달 여부 판정만 뺀다. 주요 사건과 엔딩은 스토리 제작 입력과 저장 필드로 남고 본문과 선택지 생성 재료로 계속 AI에 보낸다. 서버는 판정이 비어 오면 지금 규칙대로 목표 사건을 해제하고 진행 턴 수를 0으로 저장하며 엔딩 도달을 기록하지 않는다. |
| 대안 | 판정을 유지하는 안. 진행에 주는 효과에 비해 턴마다 드는 비용이 커 채택하지 않았다. |
| 영향 | 거쳐온 사건과 엔딩 도달 기록, 사용자와 스토리 단위 엔딩 도달 집계는 v0.5.0 이전 값만 남는다. 서버의 판정 저장 경로, 요청의 `target_main_event`, `occurred_main_event_names` 필드, 엔딩 도달 화면의 정리는 티켓이 없으며 착수하면 이 세트를 먼저 고친다. |
