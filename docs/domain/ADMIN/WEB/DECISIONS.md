# DECISIONS.md

ADMIN 도메인 웹의 중요한 결정을 날짜, 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 둔다. 여기에는 결정 당시의 이유와 변경 이력을 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 상태는 결정 당시 기준이다. 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.

### 2. 화면 구성

**1. 지표 화면 네 개를 대시보드 그룹에 두고 탭으로 나눈다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-23 |
| 상태 | 채택<br>메뉴, 경로, 화면 구성은 결정 35가 대체 |
| 배경 | 서버가 캠페인 분석과 사용자, 전환, 기능과 품질 지표 엔드포인트 14개를 제공하게 됐다(BACKEND 결정 12, 13). 웹 화면 명세가 없어 구현이 멈췄고 웹 작업자가 메뉴와 탭 구성안을 냈다. 사용자가 구성안을 승인했다. |
| 채택 | 사이드바의 대시보드 구역에 캠페인, 사용자, 전환, 기능과 품질 메뉴를 더하고 경로는 `/analytics/campaigns`, `/analytics/users`, `/analytics/conversion`, `/analytics/quality`로 둔다. 화면마다 서버 엔드포인트 단위의 탭을 두고 현재 탭의 요청만 보낸다. 기존 개요와 분석 화면은 그대로 둔다. 캠페인 분석 화면 제목은 알림 구역의 푸시 캠페인과 구분되게 "캠페인 분석"으로 한다. |
| 대안 | 모든 지표를 개요나 분석 화면에 더하는 안은 화면이 길어지고 Amplitude 비용 예산을 한 번에 많이 쓴다. 메뉴를 엔드포인트마다 두는 안은 메뉴가 열네 개가 된다. 별도 "지표" 구역을 두는 안은 개요와 분석과 같은 대시보드 성격의 화면이 두 구역으로 나뉜다. |
| 영향 | 메뉴 이름 "캠페인"이 대시보드와 알림 두 구역에 있다. 탭 상태가 URL에 들어가 링크로 공유할 수 있다. 화면마다 탭 하나의 실패가 다른 탭을 가리지 않는다. |

**2. 기간은 화면 단위로 공유하고 탭 상한을 넘으면 자르지 않고 오류로 알린다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-23 |
| 상태 | 채택<br>탭 단위 상한 판정은 결정 35가 영역 단위로 대체 |
| 배경 | 서버의 기간 상한이 탭마다 다르다. 일별 지표는 366일, 캠페인 간편 제작 퍼널은 20일, 상세 진입 퍼널과 전환 퍼널은 31일, 유입 소스는 10일이고 리텐션은 끝 날짜가 어제 이하다. 사용자는 고른 기간이 조용히 바뀌지 않기를 원했다. |
| 채택 | URL에 기간이 있으면 그 화면의 모든 탭에 같은 기간을 쓰고 없으면 탭마다 서버의 기본 기간을 쓴다. 고른 기간이 현재 탭의 상한이나 끝 날짜 제한을 넘으면 기간을 바꾸지 않고 기간 오류를 보이며 요청하지 않는다. 오류 상자의 맞추기 버튼을 누를 때만 기간을 바꾼다. 서버에는 `from`과 `to`만 보낸다. 캠페인을 바꾸면 기간 쿼리를 지워 캠페인 기간을 기본으로 쓴다. |
| 대안 | 탭마다 기간을 따로 두는 안은 탭을 오갈 때 같은 기간을 다시 골라야 한다. 상한에 맞춰 기간을 자동으로 자르는 안은 관리자가 본 값의 범위를 착각하게 한다. 서버에 `days`를 보내는 안은 탭마다 허용 값이 달라 오류가 늘어난다. |
| 영향 | 캠페인 기간이 탭 상한보다 길면 퍼널과 유입 소스 탭이 기간 오류부터 보인다. |

### 3. 값 표시

**3. 서버가 준 합계와 평균을 쓰고 준비 중과 값 없음을 0과 구분한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-23 |
| 상태 | 채택 |
| 배경 | 서버는 지난 날짜의 Amplitude 값을 나눠 받아 준비 중 날짜를 응답에 알리고(BACKEND 결정 16) 고유 사용자 수, MAU, 가중 평균, 비율의 분모가 0인 경우를 `null`로 준다. 일별 고유 사용자 수는 더하면 같은 사람을 여러 번 센다. |
| 채택 | 요약 카드는 서버가 준 합계, 평균, MAU, 가중 평균만 쓰고 일별 값이나 플랫폼별 값으로 다시 계산하지 않는다. 준비 중 날짜는 0으로 채우지 않고 차트 선을 끊는다. `null`과 분모 0은 의미에 맞는 문구로 표시한다. 준비 중 날짜나 준비 중 값이 있으면 60초 간격으로 같은 요청을 다시 보낸다. 퍼널 전환율과 스트림 오류율은 100%를 넘어도 자르지 않는다. |
| 대안 | 빈 날짜를 0으로 채우는 안은 실제 0과 구분되지 않는다. 일별 DAU 합으로 기간 사용자 수를 보이는 안은 같은 사람을 여러 번 센다. 100%로 자르는 안은 근사치나 건수 비율이라는 사실을 가린다. |
| 영향 | 일부 요약 카드는 고유 사용자 수의 기간 합 대신 마지막 날 값이나 누계를 쓴다. 고정 데이터에 준비 중 응답과 `null` 응답이 필요하다. |

**8. 개요는 요약 카드 10개와 서버 DB 일별 그래프 8개만 둔다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-23 |

**26. 스토리 상세에 공개 중단 버튼을 두고 사유 분류를 고르게 하며 공개 중단 표시는 삭제 표시와 같은 배지로 보인다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-27 |
| 상태 | 채택 |
| 배경 | 서버가 회원 스토리 공개 중단 API와 스토리 응답의 공개 중단 시각과 사유 분류를 주게 됐다(BACKEND 결정 33, MODERATION 결정 9, 10, 11). 관리자는 신고된 스토리를 보고 그 자리에서 공개를 멈출 수 있어야 한다. |
| 채택 | 스토리 상세 머리에 공개 중단 버튼을 둔다. 버튼은 회원 소유이고 삭제되지 않았으며 공개 중단되지 않은 스토리에만 보인다. 확인 대화상자는 보류 해제와 같은 공용 대화상자를 쓰되 자유 입력 사유 대신 사유 분류 네 개의 단일 선택을 필수로 두고 메모 칸은 선택으로 둔다. 기타를 고르면 소유자에게 보일 사유를 받는 한 줄 칸을 필수로 보이고 다른 분류로 바꾸면 칸과 값을 버린다. 이 사유는 알림 본문의 "{사유} 사유로" 자리에 들어가므로 도움말로 짧은 명사구를 요청한다. 메모가 감사 로그에만 남는다는 안내는 메모 라벨 옆 툴팁에 둔다. 확인 문구는 이미 비공개인 스토리에도 맞게 "비공개로 둔다"로 적고 관리자가 되돌릴 수 없다는 점을 따로 적는다. 성공하면 "공개 중단 조치를 적용했습니다."를 보이고 상세와 스토리 목록 캐시를 무효화해 상세를 다시 받아 "공개 중단됨" 배지와 시각, 사유를 보인다. 기타는 사유를 "기타 (입력 사유)"로 보인다. 목록 행에도 같은 배지를 둔다. 배지는 삭제 배지와 같은 모양이다. 409는 대화상자를 연 채 오류 문구를 보이고 상세를 다시 받는다. 404는 스토리가 없으므로 상세를 다시 받지 않고 목록 캐시만 무효화해 목록에서 확인하도록 안내한다. 관리자 화면은 "공개 중단"이라는 용어를 쓰고 소유자에게 보이는 알림과 알림함은 "공개 제한"이라고 부른다. 되돌리기 버튼과 공개 중단 필터는 두지 않는다. |
| 대안 | 스토리 목록 행마다 공개 중단 버튼을 두는 안은 내용을 확인하지 않고 누를 수 있어 상세에만 둔다. 사유 분류를 드롭다운으로 두는 안은 네 개를 한눈에 비교할 수 없다. 메모 안내를 칸 아래 문장으로 늘 보이는 안은 화면에 늘 보이는 설명을 두지 않는 규칙과 어긋난다. 성공 뒤 응답 값으로 화면을 바로 고치는 안은 목록과 상세가 서로 다른 값을 보일 수 있어 다시 요청한다. |
| 영향 | 2-1-17에 동작과 표시를 정하고 검수 제출의 실패 원인 표시 이름에 `STORY_TAKEN_DOWN`을 더했다. 공용 확인 대화상자가 사유 분류 선택과 선택 메모를 받는다. BFF 경로 하나와 고정 데이터 응답이 생기고 서버 OpenAPI 스냅샷을 다시 받아야 한다. 서버가 먼저 배포돼야 한다. |

**28. 신규 가입자, 채팅 턴 도달률, 채팅 옵션 비중에 플랫폼별 값과 대상 선택을 두고 가입 경로의 그 외를 없앤다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-27 |
| 상태 | 채택 |
| 배경 | 서버가 세 DB 지표에 Amplitude 플랫폼 값(Web, Android, 불명)을 더하고 채팅 턴 도달률과 채팅 옵션 비중에 대상 쿼리 `segment`(`all`, `guest`, `member`)를 받는다(BACKEND 결정 35, 36). 신규 가입자의 `signups.other`는 재가입 예전 계정이라 없어진다. 캠페인 추이의 신규 가입자는 Web만 세고 Android 가입이 따로 온다. 사용자는 게스트와 회원으로도 나눠 보기를 원했고 화면 용어는 기존 DB 지표와 같은 "게스트", "회원"으로 정했다. 관리자 저장소에는 세그먼트 컨트롤 구성 요소가 없고 조건은 조건 줄의 선택 상자로 고른다. |
| 채택 | 서버 DB 카드와 차트는 그대로 두고 플랫폼별 값은 별도 카드, 차트, 표로 보이며 그 제목 옆에 출처 "Amplitude"를 표시한다. 플랫폼 이름은 결정 21과 같은 "웹", "앱", "플랫폼 없음"을 쓴다. 채팅 턴 도달률과 채팅 옵션 비중의 조건 줄에 "대상"(전체, 게스트, 회원, 기본 전체)을 플랫폼과 같은 선택 상자로 두고 URL `segment`와 요청 `segment`로 쓴다. 대상은 플랫폼별 값에만 적용하고 서버 DB 도달률 차트는 전체, 게스트, 회원 선을 늘 그린다. 플랫폼과 대상을 겹쳐 웹 회원, 앱 게스트 같은 조합을 하나씩 본다. 플랫폼별 도달률은 서버 DB 도달률과 분모와 날짜 기준이 달라 다른 차트에 둔다. 신규 가입자의 가입 경로는 구글과 카카오만 보이고 "그 외" 계열을 지운다. 캠페인 추이의 가입 카드와 차트는 "웹 신규 가입자"로 이름을 바꾸고 "앱 신규 가입자"를 더한다. 플랫폼 필드가 없는 응답은 그 자리를 준비 중으로 두고 재요청하지 않는다. |
| 대안 | 화면 상단에 새 세그먼트 컨트롤을 만드는 안은 없는 구성 요소를 새로 만들고 다른 조건과 자리가 갈린다. 플랫폼 이름을 "Web", "Android", "불명"으로 쓰는 안은 사용자 활동과 기능 사용 화면의 이름과 달라진다. 대상이 서버 DB 차트도 거르는 안은 세 구분을 한 차트에서 비교하던 기능이 사라지고 서버 DB의 게스트는 현재 소유자, Amplitude의 게스트는 그 턴의 로그인 상태라 같은 말의 기준이 섞인다. 플랫폼별 도달률을 서버 DB 차트에 겹치는 안은 분모가 달라 같은 축에서 비교하면 잘못 읽힌다. |

**31. 지표 화면의 플랫폼과 대상은 기간 선택기 옆 공통 선택 하나로 고르고 고른 값 하나로 그린다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-28 |
| 상태 | 채택<br>결정 28의 플랫폼별 카드, 차트, 표와 대상의 적용 범위, 결정 29의 조건 줄 플랫폼(웹, 앱, 기본 웹), 결정 30의 탭별 라벨을 대체 |

| 채택 | 지표 화면 페이지 머리의 기간 선택기 바로 왼쪽에 플랫폼(전체, 웹, 앱)과 대상(전체, 게스트, 회원)을 이 순서로 둔다. 고른 값을 탭의 모든 카드, 차트, 표에 적용하고 플랫폼이나 대상을 나란히 그리지 않는다. 전체는 서버의 합계이고 플랫폼 없음은 선택지로 두지 않는다. 고른 구분으로 나눌 수 없는 값은 전체 값을 그대로 보이고 제목 옆에 "플랫폼 전체 기준", "대상 전체 기준", "플랫폼과 대상 전체 기준"을 표시한다(사용자 결정). 그 탭에 없는 구분은 선택 상자를 숨기고 URL 값은 지우지 않는다(사용자 결정). 탭마다 지원하는 구분은 2-1-2의 표 하나에 둔다. 선택은 URL `platform`, `segment`에 두고 사이드바의 지표 화면 메뉴도 이 둘을 붙여 연다. 광고 구분은 URL `adSegment`로 옮긴다. 전환 퍼널 탭은 전체를 웹으로 요청하고 플랫폼 라벨의 "?" 툴팁으로 알린다. 채팅 턴 도달률의 게스트에서 회원으로 카드는 대상으로 나눌 수 없는 묶음이라 대상을 게스트나 회원으로 고르면 숨긴다(사용자 결정). 서버 DB 탭 안의 Amplitude 값은 플랫폼별이 아니게 되어 제목을 "가입 이벤트 기준 신규 가입자", "1턴 대비 도달률", "응답 저장 기준 모델별 턴 수"로 바꾼다. 대상 라벨은 모든 탭에서 "대상"이고 도움말에 Amplitude와 서버 DB의 게스트 기준을 함께 적는다. |
| 대안 | 탭마다 따로 두는 안은 같은 선택이 탭을 옮길 때 다르게 적용되고 라벨이 "대상"과 "플랫폼별 지표 대상"으로 갈려 사용자가 요청한 한 자리 선택이 되지 않는다. 플랫폼을 고르면 플랫폼 정보가 없는 서버 DB 값을 숨기는 안은 신규 가입자 탭과 채팅 옵션 비중 탭의 대부분이 비고 서버 DB 값을 보려면 다시 전체로 돌려야 한다. 서버 DB 값 자리에 같은 플랫폼의 Amplitude 값을 넣는 안은 팀 계정 포함 여부, 국가 조건, 날짜 기준, 분모가 달라 같은 이름의 값이 선택에 따라 다른 정의가 된다(결정 28). 전환 퍼널에서 전체를 웹과 앱 퍼널의 합으로 보이는 안은 두 플랫폼을 함께 쓴 사용자를 두 번 세고 세 퍼널을 두 번씩 요청해 기본 7일에 태스크 예산 500을 넘는다(결정 29). 전환 퍼널 탭에서만 선택지를 웹과 앱으로 두는 안은 선택 상자의 선택지가 탭마다 달라진다. 기간 선택기를 조건 줄로 내리는 안은 개요, 분석 화면과 기간 선택기 자리가 달라진다. 광고 구분과 대상이 `segment`를 계속 함께 쓰는 안은 광고 유입을 고르는 순간 고른 대상이 사라진다. |
| 영향 | 채팅 턴 도달률의 서버 DB 차트에서 전체, 게스트, 회원을 한 차트로 비교하지 않고 대상을 바꿔 하나씩 본다. 서버 DB의 게스트는 채팅의 현재 소유자이고 Amplitude의 게스트는 그 이벤트의 로그인 상태라는 차이는 대상 도움말에 둔다. 사용자당 채팅 메시지 전송 수는 서버가 전체 값을 주지 않아 플랫폼 전체에서 빈 안내를 보인다. 플랫폼 없음 값은 따로 보이지 않고 전체에만 들어가 2-3의 플랫폼 묶음에서 플랫폼 없음 계열이 빠진다. 예전 링크의 `segment=ads`, `segment=nonAds`는 광고 구분으로 읽지 않는다. 응답에서 고르는 탭은 플랫폼이나 대상을 바꿔도 다시 요청하지 않는다. 서버 계약 변경이 없어 웹만 배포한다. |

| 채택 | 대시보드 메뉴를 개요, 성장, 스토리, 채팅, 결제, 운영 여섯으로 두고 경로는 `/dashboard`, `/analytics/growth`, `/analytics/stories`, `/analytics/chats`, `/analytics/payments`, `/analytics/ops`로 한다. 분석, 유입, 사용자, 전환, 기능과 품질, 인프라 메뉴는 없앤다. 카드, 차트, 표의 내용과 계산, 문구, API 호출은 바꾸지 않고 두는 화면과 탭만 바꾼다. 탭 하나에 예전 탭 여럿이 들어가므로 탭 본문을 영역으로 나누고 영역마다 제목, 출처, 기간 상한, 요청, 상태를 따로 둔다. 기간 상한은 영역마다 판정해 넘는 영역만 기간 오류를 보이고 기간 선택기는 탭 영역 상한 가운데 가장 큰 값을 쓴다. 성장의 유입 탭(캠페인 추이, 유입 소스, 푸시 열람)과 운영의 서비스 탭(서비스와 요청, 저장소, DB 테이블)은 하위 구분으로 나눠 예전 탭의 기본 기간, 상한, 광고 캠페인 선택을 그대로 쓰고 `tab`에는 하위 구분 값을 쓴다. 스토리는 광고 캠페인 퍼널 둘을 예전 탭 그대로 두고 그 앞에 제작 탭을 둔다. 성장의 기본 탭은 첫 탭인 유입이 아니라 활동이다(사용자 결정). 영역 제목은 그 영역의 내용으로 짓는다. 기능 사용과 안정성 응답을 나눠 둔 영역은 채팅 옵션과 입력 탭에서 "입력 방식", 결제에서 "이프와 초대 신호", 운영 AI 품질 탭에서 "오류 표시"이고 분석의 사용자 구역에서 온 분포는 "채팅 소유자" 영역이다(사용자 결정). 예전 탭 이름을 영역 제목으로 쓰면 결제 화면에 "기능 사용과 안정성"이 보이는 것처럼 출처 기준 이름이 다시 드러난다. 전환 퍼널 영역이 있는 성장 가입, 스토리 제작, 채팅 참여 탭의 기본 기간은 예전 전환 퍼널과 같은 최근 7일이다. 캠페인 추이의 제작 요청 차트는 성장의 유입에 그대로 두고 스토리에 다시 두지 않는다. 그 차트는 광고 캠페인 응답의 웹 이벤트 수라 캠페인 선택과 캠페인 기간에 묶여 있고 같은 응답의 스토리라인 생성 요청, 간편 제작 요청 요약 카드와 짝을 이룬다. 예전 경로는 이동 표로 새 경로와 `tab`에 옮기고 나머지 쿼리는 그대로 둔다. 카드가 여러 탭으로 나뉜 예전 분석, 전환 퍼널, 기능 사용과 안정성은 카드가 가장 많이 옮겨 간 채팅 참여, 성장 가입, 운영 AI 품질로 연다. 성장, 스토리, 채팅, 결제 화면 제목 옆에 회원, 스토리, 채팅, 결제 목록 링크를, 그 목록 제목 옆에 지표 화면 링크를 쿼리 없이 둔다. 사이드바의 지표 메뉴는 `campaign`도 붙여 열어 성장과 스토리 사이에서 고른 광고 캠페인을 잇는다. 퍼널 카드가 있는 탭의 기본 기간 7일, 활동 탭의 대상 선택과 "대상 전체 기준" 표시, 상호 링크 문구, 스토리 제작 탭의 `tab` 값 `making`, 사이드바 이동의 `campaign` 유지, 탭마다 준비 중 알림 하나는 사용자가 초안대로 확정했다(사용자 결정). 함께 퍼널 첫 단계는 앞 단계가 없어 앞 단계 대비 전환율을 두지 않고 막대 옆에는 사용자 수만 두며 수치 표 칸은 빈칸으로 둔다. 해당 없는 값이라 "계산할 수 없음"이 아니고 검수 제출의 판정 전 시각처럼 빈칸이 맞다. 탭의 준비 중 알림은 영역마다 두지 않고 하나로 합친다. 한 줄에 혼자 남는 차트 카드와 평균 세션 길이, 세션 길이 분포는 두 열을 모두 차지한다. |
| 대안 | 대시보드와 관리를 도메인마다 한 화면으로 합치는 안은 목록의 필터, 정렬, 페이지와 지표의 기간, 플랫폼, 대상 선택이 한 화면에 섞이고 관리 화면은 이 세트 밖이라 범위가 커져 상호 링크로 잇는다. 분석 화면을 유지하는 안은 분포 차트 9개가 채팅, 스토리, AI 품질에 걸쳐 응답 단위 화면이 하나 남아 도메인 하나를 보려면 여전히 두 화면을 오간다. 성장을 유입과 사용자로 나누는 안은 메뉴가 일곱이 되고 유입에서 가입, 활동, 리텐션으로 이어지는 흐름이 두 화면으로 갈라지며 가입 탭을 어느 쪽에 둘지 다시 정해야 한다. 탭 상한을 영역 상한 가운데 가장 작은 값으로 두는 안은 가입 탭의 신규 가입자와 채팅 참여 탭의 채팅 턴 도달률을 31일까지만 보게 된다. 유입을 하위 구분 없이 한 본문에 합치는 안은 캠페인 기간이 유입 소스의 상한 10일을 넘어 처음 열자마자 유입 소스가 기간 오류를 보이고 광고 캠페인 선택이 일부 영역에만 걸린다. 가입 탭의 기본 기간을 최근 30일로 두는 안은 퍼널 카드 셋의 Amplitude 비용이 840으로 태스크 예산 500을 넘어 처음 열 때 일부 카드가 사용 불가가 된다. 제작 요청 차트를 스토리로 옮기는 안은 광고 캠페인 선택이 없는 제작 탭에 캠페인 기간 값이 섞이고 캠페인 추이의 요약 카드와 차트가 갈라진다. |
| 영향 | 서버 계약, BFF 경로, 요청 쿼리가 바뀌지 않아 웹만 배포한다. 예전 URL은 이동 표로 새 화면과 탭에 열려 북마크가 유지된다. 기능 사용과 안정성 응답과 대시보드 차트 응답을 여러 탭이 나눠 쓰고 같은 쿼리면 서버 상태 캐시를 함께 쓴다. 기본 기간에서 퍼널 다섯 개의 비용 합은 예전과 같은 350이지만 신규 가입자, 분포 카드, 간편 제작 실패율, 채팅 턴 도달률은 처음 열 때 예전 30일보다 짧은 7일을 보인다. 세션은 활동 탭에 들어가 기본 기간이 14일에서 30일이 된다. 활동 탭과 채팅 참여 탭에 대상 선택이 생겨 대상을 나누지 못하는 사용자 활동, 분포 카드, 상세 진입 채팅 카드는 대상을 고르면 "대상 전체 기준"으로 보인다. 사이드바의 대시보드와 관리 구역에 스토리, 채팅, 결제가 두 번 보인다. 결정 5의 캠페인과 달리 같은 도메인의 지표와 목록이라 메뉴 이름과 화면 제목을 그대로 두고 구역 이름과 상호 링크로 구분한다(사용자 결정). 문구는 사라진 화면 이름이나 탭 단위 판정을 가리키던 셋만 바꾼다. 유입 Amplitude 출처 안내의 "유입 분석은 팀 계정을 제외하지 않습니다."는 "팀 계정은 제외하지 않습니다.", 웹 첫 접속 정의의 "유입 분석 간편 제작 퍼널"은 "스토리 화면의 간편 제작 퍼널 탭", 기간 상한 초과 안내의 "이 탭은"은 "이 지표는"이다. 분석 화면의 범위 줄은 기간 선택기와 겹쳐 두지 않고 분포 카드와 일별 추이 영역에는 예전처럼 출처 표시를 두지 않는다. 1턴 대비 도달률, 페르소나 시작 클릭 비중, 응답 저장 기준 모델별 턴 수의 준비 중 알림은 그 차트 위가 아니라 탭의 알림 하나에 들어간다. 지표 정의 표의 화면 열을 화면과 탭으로 바꿔 성장 안의 두 신규 방문자 정의를 가른다. |

**36. 대화 요약을 AI 기능 표시에 더하고 채팅 상세에 요약 끝 턴을 보인다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-29 |
| 상태 | 채택 |
| 배경 | BACKEND 결정 45로 AI 기능 지표와 AI 비용에 `chat_compact`가 생기고 채팅 응답에 `summaryThroughTurn`이 생겼다. 요약 호출은 서버에 토큰 수가 없어 `callsWithoutTokens`가 늘 `calls`와 같다. 사용자가 10/29에 기능 표시 이름을 "대화 요약"으로 정하고 채팅 상세에는 요약 끝 턴만 보이기로 정했다(KNK-1913). |
| 채택 | `chat_compact`의 표시 이름은 "대화 요약"이고 기능 계열 순서의 맨 뒤라 색은 셋 이상 나열 규칙대로 `--muted-foreground`다. AI 비용 표의 대화 요약 행은 입력 토큰, 출력 토큰, 토큰 수가 없는 호출 수 칸을 "기록하지 않음"으로 두고 토큰 없음 안내의 호출 수에서 뺀다. 턴당 원가 정의에 대화 요약 비용을 더한다. 채팅 상세 요약의 턴 수 다음에 "요약 끝 턴"을 두고 0이면 "요약 없음"으로 보인다. 재생성으로 비워진 요약도 같은 표시다. 요약 본문은 서버가 싣지 않아 보이지 않고 대화 내용 미제공 문구를 그대로 둔다(BACKEND 결정 45). |
| 대안 | 대화 요약을 채팅 기능 묶음에 맞춰 실시간 이미지 생성 뒤에 두는 안은 스토리라인 생성과 간편 제작의 색이 바뀐다. 토큰 칸을 "해당 없음"으로 두는 안은 요약도 토큰을 쓰므로 뜻이 다르다. 토큰 없음 안내에 대화 요약을 넣는 안은 대화 요약을 켜면 안내가 늘 보여 기록 누락을 알리는 쓸모가 없어진다. 무효화를 따로 표시하는 안은 서버 값으로 구별할 수 없다. 요약 끝 턴을 채팅 목록 열로 두는 안은 승인 범위가 상세였다. |
| 영향 | 서버를 먼저 배포하고 웹 배포 전까지 `chat_compact`가 코드 이름 그대로 보인다. 대화 요약은 호출 기록에 모델이 없어 비용 표에 하루 두 행 이상으로 나뉜다. 호출 수는 모델 없는 행에 있고 금액은 Langfuse 모델 이름 행에 있어 모델 없는 행의 비용 칸은 "비용 기록 없음"일 수 있다. 관리자 BFF의 채팅 목록 쿼리 검증과 고정 데이터에 `chat_compact`를 더해야 AI 품질 막대에서 연 목록이 열린다. |

**37. Amplitude 대시보드 개편에 맞춘 지표를 성장 화면에 더하고 전체를 웹이나 앱 사용자 한 번으로 보인다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-30 |
| 상태 | 채택 |
| 배경 | BACKEND 결정 46~50으로 분석 도구 지표의 전체가 웹이나 앱 사용자를 한 번 센 값이 되고 해외 로그인 앱 회원이 빠졌으며 가입은 커스텀 이벤트로 한 번 센다. 같은 결정으로 첫 방문 활성화 퍼널, 누적 도달, 광고 소재, 앱 배너, 설치 경로, 웹 이용 후 앱 이용, 활성 사용자 플랫폼 구성, 기기 유형별 신규 방문자, 활동량, 사용자당 세션 수, 일별 세션 수, 가입 전환율, 앱 신규 활성 사용자, 신규 사용자 활성화와 로그인 화면 가입과 앱 신규 활성화 퍼널이 생겼다. 지표 화면은 결정 35대로 도메인 기준 화면과 탭으로 나뉘어 있다. |
| 채택 | 새 지표는 모두 성장 화면에 둔다. 유입 탭에 첫 방문 활성화(`activation`), 광고 소재(`creatives`), 앱 유입(`app`) 하위 구분을 더해 캠페인 추이, 첫 방문 활성화, 광고 소재, 유입 소스, 앱 유입, 푸시 열람 순서로 둔다. 첫 방문 활성화와 광고 소재는 광고 캠페인을 쓰고 첫 방문 활성화는 광고 구분도 쓴다. 광고 구분 `adSegment`는 성장과 스토리가 함께 쓴다. 캠페인 추이에 기기 유형별 웹 신규 방문자 차트를, 활동 탭에 활성 사용자 플랫폼 구성 차트와 활동량 영역과 사용자당 세션 수, 일별 세션 수 차트를, 가입 탭에 가입 전환율 차트와 앱 신규 활성 사용자 영역과 신규 사용자 활성화, 로그인 화면 가입, 앱 신규 활성화 퍼널 카드를 둔다. 퍼널 카드 순서는 웹 첫 접속, 앱 첫 접속, 신규 사용자 활성화, 로그인 화면 가입, 앱 신규 활성화, 게스트 한도 로그인이다. 웹 이용 후 앱 이용 카드는 앱 유입 하위 구분에 두고 배지 없이 단계 이름(웹 활동, 앱 활동)으로 플랫폼을 보인다. 한 플랫폼 값만 있는 영역과 카드는 고른 플랫폼과 무관하게 그 값을 보이고 제목 옆에 플랫폼 배지를 둔다. 활성 사용자 플랫폼 구성은 플랫폼 선택과 무관하게 웹, 앱, 플랫폼 없음을 누적 막대로 그리며 플랫폼 없음만 응답의 `unknown`을 쓴다. 전체 값과 출처 안내 문구에서 해외 로그인과 "두 번 셉니다"를 지우고 "웹과 앱을 함께 쓴 사람을 한 번 셉니다"로 바꾼다. 가입 정의 문구의 "두 경로로 가입하면 두 번 셈"은 "두 경로로 가입해도 한 번 셈"이다. 가입 탭의 3단계 퍼널 이름은 유입의 4단계 "첫 방문 활성화"와 가르려고 "신규 사용자 활성화"로 둔다. |
| 대안 | 앱 지표를 모은 새 화면이나 탭을 두는 안은 결정 35의 도메인 기준 배치와 달리 출처나 플랫폼 기준 화면을 다시 만든다. 광고 소재와 첫 방문 활성화를 캠페인 추이 하위 구분 안에 영역으로 더하는 안은 캠페인 추이를 열 때마다 하루 70의 조회 비용이 함께 나가 다른 카드의 준비 중이 길어진다. 앱 신규 활성 사용자를 활동 탭에 두는 안은 활동 탭의 요청이 다섯으로 늘고 가입 탭의 앱 첫 접속, 앱 신규 활성화 카드와 떨어진다. 플랫폼 고정 영역에 "플랫폼 전체 기준"을 쓰는 안은 그 값이 전체가 아니라 앱 값이라 뜻이 틀린다. 두 활성화 퍼널에 같은 이름을 쓰는 안은 단계 수가 다른 두 카드가 같은 이름으로 보인다. |

**39. 푸시 열람 하위 구분을 알림 열람으로 바꾸고 웹과 앱으로 나눈 값과 알림함 열람을 보인다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-30 |
| 상태 | 채택<br>결정 19의 "알림함에서 누른 열람은 보이지 않는다"와 웹 기준 출처 안내, 결정 35와 37의 하위 구분 이름 "푸시 열람"을 대체 |
| 배경 | BACKEND 결정 53으로 푸시 열람 응답의 `pushOpens`가 웹과 앱의 합계가 되고 웹, 앱 값과 알림함 열람이 생겼다. 앱 값은 앱 측정 시작일 전이면 `null`이고 알림함 열람에는 열람률이 없다. BACKEND 결정 55로 활동 알림이 이프 만료 예정까지 네 종류가 됐다. 하위 구분에 알림함 열람이 함께 보여 사용자가 묶음 이름을 "알림 열람"으로 정했다(10/30). |
| 채택 | 성장 유입 탭의 하위 구분 이름을 "알림 열람"으로 바꾼다. 지표 이름인 푸시 열람과 알림함 열람은 그대로 두고 URL의 `tab` 값은 `push`를 유지한다. 관리자 캠페인 표와 활동 알림 표에 알림함 열람 열을 열람률 다음에 둔다. 활동 알림 표는 이프 만료 예정을 더해 4행이다. 푸시 열람과 알림함 열람 칸은 첫 줄에 합계, 둘째 줄에 작은 회색 글자로 "웹 {값}, 앱 {값}"을 보이고 `null`인 플랫폼은 "측정 시작 전"으로 쓴다. 열람률은 합계 기준이다. 측정 상태 문구는 알림함 열람 칸에도 같게 쓴다. 출처 안내는 웹의 페이지 조회와 앱의 알림 열기를 함께 밝히고 합계의 중복과 앱 측정 시작일은 지표 정의 툴팁에 둔다. |
| 대안 | 웹, 앱, 합계를 열로 나누는 안은 관리자 캠페인 표가 열한 열이 되어 좁은 화면에서 제목이 밀린다. 합계만 보이고 플랫폼 값을 툴팁에 넣는 안은 앱 측정 전인지 앱 열람이 0인지를 표에서 구분할 수 없다. 알림함 열람률을 보이는 안은 BACKEND 결정 53 대안과 같이 분모가 맞지 않는다. 하위 구분 이름을 푸시 열람으로 두는 안은 알림함 열람이 함께 보여 이름과 내용이 맞지 않는다. `tab` 값을 `inbox`나 `notification`으로 바꾸는 안은 저장된 링크와 예전 경로 이동(`/analytics/acquisition?tab=push`)을 다시 이어야 하고 값이 화면에 보이지 않아 얻는 것이 없다. 앱 측정 시작일 안내를 표 위 문장으로 두는 안은 화면에 늘 보이는 설명 문장을 두지 않는 규칙과 맞지 않고 칸의 "측정 시작 전"과 겹친다. |
| 영향 | 두 표에 열이 하나씩 늘고 활동 알림 표가 4행이 된다. 웹은 서버 배포 뒤 배포하며 그 사이 옛 화면은 합계를 웹 기준 안내와 함께 보인다. 하위 구분 막대, 영역 제목, 출처 안내와 부분 집계 안내의 위치 이름이 알림 열람으로 바뀌고 `tab=push` 링크는 그대로 열린다. |

| 상태 | 채택<br>결정 18의 게시 확인 문구로 알림 대상을 알리는 부분과 결정 20 전부를 대체 |
| 배경 | 공지 게시가 알림을 보내지 않고 공지 알림은 관리자 캠페인이 게시된 공지를 연결해 보내게 됐다(NOTICE 결정 5, NOTIFICATION 결정 21). 캠페인 종류는 연결한 공지의 태그가 정하고 관리자가 고르지 않는다. |
| 채택 | 공지 작성과 수정에서 알림 제목과 알림 본문 칸을 지우고 상세에서도 알림 문구 항목을 지운다. 게시 확인 문구는 태그와 알림 요청 이력에 관계없이 하나로 두고 알림이 가지 않는다고 알린다. 게시된 공지 상세에 "알림 보내기" 링크를 두어 그 공지를 고른 캠페인 작성 화면을 연다. 캠페인 작성에서 광고성과 정보성 선택을 지우고 이동 대상을 없음, 스토리, 공지 중에서 고르게 한다. 공지는 게시된 공지만 검색해 고르고 고른 공지의 태그로 알림 성격을 보이며 대상 수도 그 성격으로 조회한다. 요청에는 `noticeId`만 싣고 `kind`는 싣지 않는다. |
| 대안 | 캠페인 작성에 종류 선택을 남기고 공지 태그와 다르면 막는 안은 고를 수 없는 선택지를 보여 혼란스럽다. 공지 상세에 캠페인 작성 화면을 끼워 넣는 안은 예약, 대상 수, 확인 흐름을 두 화면에 중복한다. 공지 선택에 초안까지 보여 주는 안은 서버가 거절할 항목을 고르게 한다. |
| 영향 | 2-1-14의 절 이름이 "공지의 태그와 알림 보내기"가 됐고 2-1-21이 생겼다. 서버를 먼저 배포해야 한다. 관리자 웹이 먼저면 이전 서버가 알림 문구 누락으로 공지 작성을 거절하고 `noticeId`를 무시해 공지 없는 광고 캠페인을 만든다. 서버만 배포된 동안 이전 관리자 웹의 공지 게시 확인 문구는 알림이 간다고 안내하지만 알림은 가지 않는다. |
| 보완(2026-10-30) | 예약한 공지 알림은 발송 선점 때 공지를 다시 읽어 게시 상태가 아니면 실패하고 태그가 바뀌었으면 그 태그로 알림 성격을 다시 정한다(NOTIFICATION 결정 21 보완). 캠페인 작성의 확인 대화상자에 이 재확인을 알리는 문구를 두고 캠페인 상세에 실패 사유 `failureReason` 문구와 예약 공지 알림의 "발송 때 다시 확인" 표시를 둔다(2-1-22). 예약 화면의 알림 성격과 대상 회원 수는 예약 때 기준이라 실제 발송과 다를 수 있다. |

**42. 개요를 증감이 있는 카드 6개와 그래프 하나로 줄이고 지표 화면을 유입, 사용자, 콘텐츠, 채팅, 수익으로 다시 나눈다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-02 |
| 상태 | 채택<br>결정 7의 개요 카드 10개와 그래프 8개, 결정 25의 성장, 스토리, 채팅, 결제, 운영 다섯 화면 구성을 대체 |
| 배경 | 사용자가 대시보드가 보기 어렵고 복잡하다고 했다(11/2). 성장 화면은 영역 16개에 유입, 활동, 가입, 리텐션이 한 화면에 있었고 광고 캠페인 분석은 성장과 스토리 두 화면에 나뉘어 같은 캠페인 선택을 두 화면에서 되풀이했다. 결제 화면의 일별 추이 네 그래프는 개요의 그래프 8개에 다시 들어 있었다. 개요 카드는 누적, 오늘, 기간 합계만 보여 지난 기간보다 늘었는지 알 수 없었다. |
| 채택 | 개요는 오늘 활성 사용자, 가입자, 채팅 시작, 턴, 결제 금액 (환불 포함), 앱 설치 카드 6개와 지표를 고르는 일별 추이 그래프 하나다. 서버 DB 카드는 선택 기간 합계를 큰 숫자로 두고 차트 응답의 직전 기간 합계(BACKEND 결정 56)로 증감률을 보인다. 성장 화면을 유입(광고 캠페인, 유입 소스, 앱, 알림)과 사용자(활동, 가입, 리텐션)로 나누고 스토리의 간편 제작 퍼널과 상세 진입 퍼널 탭을 유입의 광고 캠페인 탭으로 옮긴다. 스토리는 콘텐츠로, 결제는 수익으로 이름을 바꾸고 운영은 사이드바의 운영 구역으로 옮긴다. 새 경로는 `/analytics/inflow`, `/analytics/audience`, `/analytics/content`, `/analytics/revenue`이고 예전 경로 이동 표에 성장, 스토리, 결제 경로를 더한다. |
| 대안 | 성장 화면의 탭만 줄이는 안은 광고 캠페인이 두 화면에 남는다. 개요 카드 10개를 두고 증감만 더하는 안은 카드가 5열 2행이라 증감까지 넣으면 더 빽빽하다. 그래프 8개를 유지하는 안은 개요가 지표 화면의 요약이 아니라 또 하나의 지표 화면이 된다. 예전 경로 `/analytics/acquisition`, `/analytics/users`를 새 화면 경로로 되살리는 안은 저장된 링크가 결정 25 이전의 탭 구성으로 열려 이동 표가 두 의미를 가진다. 운영을 대시보드 구역에 두는 안은 운영자가 매일 보는 화면 사이에 개발자용 화면이 섞인다. |
| 영향 | 2-1의 절이 유입, 사용자, 콘텐츠, 채팅, 수익, 운영으로 바뀌고 2-1-9 이하 절 번호가 하나씩 밀린다. 서버 DB 카드의 기간 합계를 일별 값으로 더하던 계산을 응답 `totals`로 바꾼다. 분석 지표 요청의 범위가 오늘 하루에서 어제와 오늘 이틀이 된다. 사이드바 저장소의 구역 키에 운영이 늘어 펼침 상태 저장 형식이 바뀐다. 서버의 차트 응답에 `totals`와 `previous`가 있어야 증감이 보이며 없으면 큰 숫자와 증감 자리에 준비 중을 둔다. 관리자 저장소의 화면, 라우트, 고정 데이터, 테스트를 함께 고친다. |

**43. 알림 열람에 서버 DB 채팅 전환 열과 카드를 더한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-02 |
| 상태 | 채택 |
| 배경 | 앱이 알림 열기 이벤트를 보내기 전이라 열람 값이 웹뿐이고 캠페인의 성과를 볼 수 없었다. BACKEND 결정 57로 푸시 열람과 캠페인 열람 응답에 채팅 전환 회원 수, 사전 채팅 회원 수, 채팅 전환율이 생겼다. |
| 채택 | 유입 알림 탭의 관리자 캠페인 표와 활동 알림 표에 도달 회원 다음으로 채팅 전환 열과 전환율 열을 둔다. 채팅 전환 칸은 첫 줄에 전환 회원 수, 둘째 줄에 작은 회색 글자로 도달 전 24시간 채팅 회원 수를 보인다. 캠페인 상세의 열람 영역은 채팅 전환, 전환율 카드를 열람 카드 앞에 둔다. 두 값은 `openState`와 무관하게 늘 보이고 도달 회원이 없을 때만 도달 없음으로 쓴다. 영역 출처 표시는 "Amplitude와 서버 DB"다. |
| 대안 | 열람 열을 지우고 전환 열만 두는 안은 앱 열람이 측정되기 시작하면 다시 넣어야 한다. 사전 채팅 회원 수를 별도 열로 두는 안은 관리자 캠페인 표가 열 열이 되어 좁은 화면에서 제목이 밀린다(결정 39와 같은 이유). 사전 채팅 회원 수를 툴팁에만 두는 안은 전환율이 부풀려 보이는 표에서 비교값을 바로 볼 수 없다. |
| 영향 | 두 표에 열이 둘씩 늘고 캠페인 상세 열람 영역의 카드가 다섯 장이 된다. 서버를 먼저 배포하며 응답에 세 필드가 없으면 열과 카드를 두지 않는다. 고정 데이터의 열람 응답에 세 값을 더한다. |
