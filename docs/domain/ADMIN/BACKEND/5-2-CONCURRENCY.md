# 5-2 동시성

이 문서는 ADMIN 도메인의 동시 요청 처리 규칙을 정한다. 감사 기록의 트랜잭션 참여, 멱등과 1회 처리, 역할 변경과의 경쟁, 수용한 경쟁 조건을 다룬다.

흐름별 단계는 처리 흐름에 있으며 토큰 수명은 오류 처리에 있다. ([4-1-4 감사 기록](4-1-PIPELINES.md#4-1-4-감사-기록)과 [5-3-5 재시도와 시간 한도](5-3-ERROR-HANDLING.md#5-3-5-재시도와-시간-한도))

<br>

### 5-2-1 감사 기록의 트랜잭션

ADMIN은 자체 행 잠금을 두지 않는다. 변경 작업의 잠금은 그 변경을 적용하는 도메인이 건다.

| 기록 | 트랜잭션 |
|---|---|
| 변경 감사 기록 | 호출 도메인의 트랜잭션에 참여<br>트랜잭션이 없으면 거부해 변경 없는 로그나 로그 없는 변경이 생기지 않게 함 |
| 접속 기록 | 조회 뒤 독립 트랜잭션<br>조회 자체는 트랜잭션이 없음 |

<br>

### 5-2-2 멱등과 1회 처리

| 대상 | 처리 |
|---|---|
| 관리자 로그인 | 요청마다 새 토큰<br>서버 상태가 없어 반복해도 부작용 없음 |
| 변경 감사 기록 | 변경 1건에 로그 1행<br>변경의 멱등은 그 도메인이 정하고 멱등으로 건너뛴 재시도는 로그를 남기지 않음 |
| 접속 기록 | 조회마다 1행<br>같은 회원을 반복 조회하면 행이 늘어남 |
| 대시보드, 목록, 상세, DB 분석 지표 | 읽기 전용 |
| 분석 도구 지표 갱신 | 엔드포인트와 쿼리 값마다 태스크 안 갱신 표식과 쿨다운이 따로<br>값이 없거나 만료된 날짜가 있을 때 첫 요청 하나만 갱신 표식을 잡고 호출<br>그 사이 요청은 기다리지 않고 저장 값과 준비 중 날짜로 응답<br>실패 뒤 60초 쿨다운 동안은 그 키의 어떤 요청도 호출하지 않음 |
| Amplitude 조회 값 저장 | 조회 하나가 성공하면 그 조회의 날짜별 행을 한 트랜잭션으로 upsert<br>같은 키는 고유 키 충돌로 한 행만 남고 나중에 저장한 값이 덮어씀<br>`finalized_at`이 있는 행은 덮어쓰지 않아 확정 값이 바뀌지 않음<br>호출 직전에 저장 값을 다시 읽어 다른 태스크가 먼저 저장한 날짜는 조회하지 않음<br>태스크 사이에는 잠금을 두지 않음 |
| 설치 지표 캐시 | 만료 뒤 첫 요청 하나만 갱신 표식을 잡고 호출<br>그 사이 요청은 기다리지 않고 만료된 캐시 또는 사용 불가로 응답<br>실패 뒤 60초 쿨다운 |
| 분석 도구 비용 예산 | 태스크마다 계수기 하나<br>남은 예산 확인과 갱신 비용 예약을 한 번에 원자적으로 처리해 서로 다른 키의 갱신이 같은 잔여 예산을 함께 통과하지 않음<br>갱신이 끝나면 실패한 조회와 보내지 않은 조회의 예약분을 반환 |
| 분석 도구 호출 | 태스크 안에서 한 번에 하나<br>다른 갱신의 호출이 끝날 때까지 기다리며 기다린 시간도 그 갱신의 시간 한도에 포함 |

<br>

### 5-2-3 유니크 위반 처리

| 대상 | 처리 |
|---|---|
| 감사 로그 `public_id` | 서버가 생성하는 UUID라 충돌이 드러나지 않음 |
| 관리자 역할 `user_id` | 역할 관리 운영자가 직접 기록하므로 위반은 저장소가 거절 |
| Amplitude 조회 값의 키 | upsert라 위반이 드러나지 않음 |

<br>

### 5-2-4 역할 변경과의 경쟁

| 상황 | 처리 |
|---|---|
| 판정 통과 뒤 역할 회수 커밋 | 그 요청은 끝까지 처리됨<br>다음 요청부터 거절 |
| 판정 통과 뒤 계정 정지 커밋 | 같음<br>변경 도메인이 사용자 행을 잠그는 경로는 그 도메인의 재검사를 따름 |

<br>

### 5-2-5 수용한 경쟁 조건

| 상황 | 수용 이유 |
|---|---|
| 역할 회수와 진행 중 요청이 겹쳐 회수 뒤 변경이 1건 커밋됨 | 요청마다 재확인하므로 영향이 요청 처리 시간으로 제한됨<br>감사 로그에 처리자가 남아 추적 가능 |
| 대시보드 집계가 도메인별로 다른 스냅샷을 읽음 | 읽기 트랜잭션을 하나로 묶지 않음<br>운영 현황 수치라 집계 사이의 수 건 차이를 수용 |
| 목록의 전체 건수와 현재 페이지가 다른 시점을 읽음 | 두 쿼리 사이에 행이 추가되면 `totalElements`와 마지막 페이지 건수가 어긋남<br>다음 요청에서 맞음 |
| 차트 막대 값과 그 막대가 연 목록의 건수가 다름 | 두 요청 사이의 새 행과 팀 계정 제외 차이<br>목록은 전체를 보여 주는 것이 목적 |
| 두 태스크가 같은 키의 같은 날짜를 동시에 받음 | 태스크 사이 잠금이 없어 비용이 두 번 들 수 있고 한쪽 값만 남음<br>같은 날짜를 거의 같은 때 받은 값이라 차이가 작고 확정 뒤에는 다시 받지 않아 중복이 그날에 한정됨<br>분석 도구 호출 동안 DB 잠금을 잡지 않는 쪽을 택함 |
| 갱신 중인 요청이 끝나기 전의 요청이 10분 넘은 오늘 값을 받음 | 몇 초 차이이고 분석 도구 자체가 몇 분 지연되는 수치라 수용 |
| 쿨다운 60초 동안 분석 도구가 복구돼도 호출하지 않음 | 연속 실패로 한도를 소모하는 것을 막는 쪽을 택함 |
| 비용 예산 계수기가 태스크마다 따로라 배포 중 새 태스크와 옛 태스크가 겹치는 것처럼 태스크가 셋 이상이면 합이 5분 1,000을 넘을 수 있음 | 태스크당 500이라 평소 두 태스크의 합은 한도 안<br>넘으면 분석 도구가 한도 초과로 응답해 쿨다운으로 흡수됨 |
| 실패한 조회의 예약분을 반환하지만 분석 도구는 그 조회의 비용을 이미 셌을 수 있음 | 계수기가 실제 소비보다 작게 셀 수 있으나 넘친 만큼은 한도 초과 응답과 쿨다운으로 흡수됨 |
| 분석 도구 지표 엔드포인트 여럿을 같은 5분에 갱신하면 뒤의 요청이 예산 부족으로 준비 중 날짜를 남김 | 일별 지표는 받은 날짜를 저장해 다음 요청에서 이어 받고 범위 지표는 한 번의 조회가 예산 안이라 쿨다운 뒤 다시 시도함<br>긴 범위의 첫 조회가 여러 5분 동안 예산을 차지해 다른 카드가 늦게 채워질 수 있음 |
| 태스크 안 호출이 한 번에 하나라 다른 갱신의 호출을 기다리다 시간 한도를 넘을 수 있음 | 그 갱신은 시간 초과로 실패하고 쿨다운 뒤 다시 갱신됨<br>프로젝트 동시 요청 한도를 넘기지 않는 쪽을 택함 |
| 확정한 날짜를 분석 도구가 나중에 소급 보정해도 반영되지 않음 | 지난 날짜의 보정은 드묾<br>필요하면 운영 DB에서 그 행을 지워 다시 받게 함 |
| 어제 값을 자정 직후 받으면 늦게 들어온 이벤트가 빠진 채 확정될 수 있음 | 분석 도구의 수집 지연이 몇 분 수준이라 차이가 작음 |
| 접속 기록 전에 조회 응답이 만들어짐 | 기록 실패 시 응답을 실패로 바꾸므로 기록 없는 조회 응답은 나가지 않음 |
