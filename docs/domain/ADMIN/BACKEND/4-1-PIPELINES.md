# 4-1 처리 흐름

이 문서는 ADMIN 도메인의 요청 수신부터 응답까지의 처리 단계와 다른 도메인의 관리자 API가 쓰는 판정과 감사 기록의 단계를 정한다.

요청 필드, 응답 필드와 실패 응답은 계약에, 토큰 수명과 복구 규칙은 오류 처리에, 트랜잭션 규칙은 동시성에 있다. ([4-2 계약](4-2-CONTRACT.md), [5-3 오류 처리](5-3-ERROR-HANDLING.md), [5-2 동시성](5-2-CONCURRENCY.md))

<br>

### 4-1-1 공통 처리

모든 요청은 상관관계 필터에서 요청 ID를 받는다. 관리자 로그인은 토큰을 읽지 않는다. 그 밖의 관리자 경로는 관리자 판정 필터가 요청자를 정한다. 앱 경로의 토큰 검증은 관리자 표식이 있는 토큰을 거절한다.

관리자 경로는 `/api/v1/admin/` 아래 전체다. 다른 도메인의 관리자 API도 같은 접두 아래에 두어 같은 필터를 거친다. 필터를 거치지 않는 관리자 경로는 없다.

관리자 판정은 토큰의 값으로 끝내지 않는다. 요청마다 토큰 주체의 회원 행을 읽어 관리자 역할과 계정 상태를 다시 확인한다.

흐름도에서 Google과 다른 도메인을 호출하는 단계는 주황색이다.

<br>

- 검증 실패와 자격 없음은 다른 상태로 응답하되 자격 없음 안에서 회원 없음, 역할 없음, 정지, 탈퇴는 구분하지 않는다.
- 계정을 만들지 않고 가입 보상, 체험 스냅샷, 세션 생성, 로그인 분석 이벤트도 수행하지 않는다.
- 로그인 결과는 구조화 로그로 남긴다. 성공은 회원 공개 식별자를 기록하고 실패는 사유 분류만 기록한다.

- 앱 접근 토큰은 표식이 없어 첫 단계에서 거절된다. 유효한 관리자 토큰이라도 그 사이 역할이 회수되거나 계정이 정지되면 두 번째 단계에서 거절된다.
- 요청자는 회원 내부 ID로 확정해 핸들러와 감사 기록에 전달한다.

<br>

### 4-1-4 감사 기록

다른 도메인의 관리자 API가 변경을 적용한 뒤 같은 트랜잭션에서 호출한다. ADMIN의 회원 검색과 상세는 조회 뒤 접속 기록으로 호출한다.

```mermaid
%%{init: {"flowchart": {"curve": "basis", "nodeSpacing": 24, "rankSpacing": 40}}}%%
flowchart LR
    A["`**변경 적용**
호출 도메인의 트랜잭션`"] --> B["`**변경 전후 값 조립**
호출 도메인`"]
    B --> C["`**감사 로그 행 추가**
같은 트랜잭션`"]
    C --> D{"`**커밋**`"}
    D -->|성공| E["`**변경과 로그 확정**`"]
    D -->|실패| F["`**변경과 로그 모두 롤백**`"]
    classDef comp fill:#E8F2E8,stroke:#527A59,color:#182D1D
    class A,B,C,D,E,F comp
```

- 변경 전후 값은 호출 도메인이 작업별 기록 허용 목록의 필드로 조립한다. ([3-2-4 감사 로그](3-2-DB-SCHEMA.md#3-2-4-감사-로그)) 생성은 변경 전 값이 없고 삭제는 변경 후 값이 없다.
- 대상은 외부 식별자로 기록한다. 순차 PK를 넣지 않는다.
- 접속 기록은 조회 응답을 만든 뒤 독립 트랜잭션으로 기록한다. 기록에 실패하면 조회 응답도 실패로 바꾼다.

### 4-1-5 목록 공통 처리

스토리, 채팅, 회원, 결제, 이프 내역, 감사 로그 목록은 같은 순서로 처리한다.

```mermaid
%%{init: {"flowchart": {"curve": "basis", "nodeSpacing": 24, "rankSpacing": 40}}}%%
flowchart LR
    A["`**쿼리 해석**
검색어 정규화, 날짜 범위, enum, 페이지와 정렬`"] --> B["`**조건 조립**
검색어, 필터, 정렬을 AND`"]
    B --> C["`**전체 건수 조회**`"]
    C --> D["`**현재 페이지 조회**
다른 도메인 테이블`"]
    D --> E["`**표시 조립**
회원 요약, 스토리 요약`"]
    E --> F["`**응답**
페이지 구조`"]
    classDef comp fill:#E8F2E8,stroke:#527A59,color:#182D1D
    classDef task fill:#F5D9C9,stroke:#B97450,color:#452B1D
    class A,B,C,E,F comp
    class D task
```

| 항목 | 규칙 |
|---|---|
| 검색어 | 앞뒤 공백 제거, 연속 공백 하나로, 소문자화<br>부분 일치는 대상 문자열을 같은 규칙으로 정규화한 뒤 포함 여부<br>정확 일치는 정규화한 값이 같은지<br>UUID 형식이면 정확 일치 대상에만 비교 |
| 날짜 범위 | KST 달력 날짜를 UTC 구간으로 바꿔 시각 컬럼과 비교<br>`from`이 있으면 그날 자정 이상, `to`가 있으면 다음 날 자정 미만<br>한쪽만 있으면 그 경계만 적용 |
| 정렬 | 요청 열과 방향 뒤에 공개 식별자 오름차순을 항상 덧붙임<br>`null`은 마지막 |
| 페이지 | 건너뛸 행 수는 `(page - 1) × size`<br>전체 건수와 현재 페이지는 별도 쿼리 |
| 팀 계정 | 목록과 상세에는 제외 목록을 적용하지 않음 |
| 삭제 행 | 삭제된 스토리와 채팅은 목록과 상세에서 제외<br>탈퇴 회원은 `excludeDeleted`가 없으면 포함 |

### 4-1-6 대시보드 요약

```mermaid
%%{init: {"flowchart": {"curve": "basis", "nodeSpacing": 24, "rankSpacing": 40}}}%%
flowchart LR
    A["`**현재 시각과 KST 오늘 범위 고정**`"] --> B["`**도메인별 집계 조회**
ACCOUNT, STORY, CHAT, PAYMENT`"]
    B --> C["`**응답 조립**
오늘과 누적`"]
    classDef comp fill:#E8F2E8,stroke:#527A59,color:#182D1D
    classDef task fill:#F5D9C9,stroke:#B97450,color:#452B1D
    class A,C comp
    class B task
```

- 지표 정의는 제품 제약을 따른다. ([2-4 제품 제약](2-REQUIREMENTS.md#2-4-제품-제약))
- 오늘 범위는 요청 시작 때 한 번 계산해 모든 집계에 같은 값을 쓴다. 자정을 걸치는 요청에서 지표끼리 기준이 어긋나지 않게 한다.
- 집계는 읽기 전용이며 캐시하지 않는다.
- 팀 계정 제외 목록은 설정에서 읽어 모든 집계의 소유 회원 조건에 적용한다.

<br>

| 항목 | 규칙 |
|---|---|
| 날짜 범위 | `from`과 `to`가 있으면 그대로, `days`면 오늘을 포함한 최근 N일, 둘 다 없으면 최근 30일<br>`to`는 오늘 이하이고 길이는 1~366일<br>날짜 경계는 KST 자정 |
| 일별 추이 | 지표마다 날짜별로 집계한 뒤 범위의 모든 날짜를 채움<br>기준 시각 컬럼은 제품 제약의 표 |
| 분포 | 차트마다 한 번의 집계 쿼리<br>구간 차트는 값이 0인 구간도 항목으로 둠 |
| 제작 세션 차트 | 팀 계정 제외 목록에서 공식 계정을 뺀 나머지만 제외<br>오리지널 제작 세션을 포함하기 위함<br>인물 수는 스토리 목록의 주변 인물 수와 같은 판정 |
| 그 외 차트와 추이 | 요약과 같은 제외 목록 적용 |
| 목록 링크 | 막대마다 그 막대의 조건을 목록 쿼리 이름으로 바꿔 넣음<br>날짜 범위는 응답의 `from`과 `to` 그대로이며 차트가 정한 접두가 붙은 이름 |
| 캐시 | 없음<br>기간 상한 366일이 집계 범위를 제한 |

| 보류 상태 | 그 스토리를 대상으로 하는 대기 상태이면서 보류 시각이 있는 제출본이 있으면 `HELD` |

| 신규 가입자 | `users`를 `created_at`의 KST 날짜로 묶고 팀 계정 제외 목록을 뺌<br>가입 경로는 그 회원의 `social_accounts` 중 `connected_at`이 가장 이른 행의 `provider`가 `GOOGLE`, `KAKAO`, 그 외<br>게스트 이관은 `migrated_at`이 있는 회원 |

### 4-1-20 Amplitude 조회 공통

분석 지표, 캠페인 분석, 사용자와 전환과 기능 지표의 Amplitude 조회가 함께 쓰는 규칙이다. 엔드포인트별 조회 구성은 각 절에 있다.

**1. 호출과 조건**

| 항목 | 규칙 |
|---|---|
| 호출 대상 | Amplitude Dashboard REST API<br>사용자 수 `GET /api/2/users`, 이벤트 세분화 `GET /api/2/events/segmentation`, 퍼널 `GET /api/2/funnels`, 리텐션 `GET /api/2/retention`, 평균 세션 길이 `GET /api/2/sessions/average`<br>US 데이터 센터 주소<br>API 키와 시크릿 키의 기본 인증 |
| 사용자 속성 조건 | 국가, 플랫폼, 캠페인, 소스 같은 사용자 속성 조건은 세그먼트 `s`가 아니라 이벤트 필터로 넣음<br>`e`의 `filters`에 `subprop_type`이 `user`인 조건이며 퍼널은 단계마다 같은 조건을 넣음<br>`gp:` 접두 속성 이름은 그대로 씀<br>세그먼트는 기본 하나뿐이라 조건 수가 1 |
| 세그먼트 조건 | 이벤트가 없는 사용자 수 조회와 세션 조회, 이벤트 필터가 적용되지 않는 것으로 확인된 리텐션 조회, 코호트 조건에만 `s`를 씀 |
| 값이 정해진 묶음 | 플랫폼과 입력 방식처럼 값을 미리 아는 묶음은 묶음 속성을 쓰지 않음<br>값마다 이벤트 필터를 건 같은 이벤트를 따로 조회<br>세분화 요청 하나에는 `e`와 `e2`로 이벤트 둘까지 넣을 수 있음 |
| 값이 열린 묶음 | 유입 소스와 게시글처럼 값을 미리 알 수 없는 묶음만 묶음 속성을 쓰고 한 조회에 하나만 씀 |
| 날짜 | `i=1`, `start`와 `end`는 범위의 `YYYYMMDD`<br>Amplitude 프로젝트 시간대가 KST라 응답 날짜를 그대로 씀 |
| 호출 순서 | 한 태스크의 Amplitude 호출은 엔드포인트와 갱신이 달라도 한 번에 하나만 보냄<br>프로젝트 전체의 동시 요청 한도 5를 여러 태스크가 나눠 쓰기 때문 |

<br>

**2. 비용 산식**

Amplitude는 요청마다 비용을 매기고 프로젝트 전체에 5분 1,000, 1시간 108,000의 한도를 둔다.

| 항목 | 규칙 |
|---|---|
| 비용 | 일수 × 조건 수 × 유형 비용 |
| 일수 | 요청의 `start`부터 `end`까지의 날짜 수<br>`i`와 무관 |
| 조건 수 | 세그먼트 수 + 세그먼트 안 조건 수<br>`s`가 없으면 기본 세그먼트 하나라 1<br>코호트 조건은 조건으로 셈<br>이벤트 필터는 세지 않음<br>묶음 속성 하나는 세그먼트 4개로 셈 |
| 유형 비용 | 세분화는 이벤트 수, 묶음 속성이 있으면 묶음 하나와 이벤트 하나마다 4를 더함<br>퍼널은 단계 수 × 2, 묶음 속성이 있으면 같은 방식으로 더함<br>리텐션 8<br>세션 4<br>사용자 수 조회 1 |

이벤트 하나에 묶음 속성 하나를 건 세분화 조회는 조건 수 1 + 4 = 5, 유형 비용 1 + 4 = 5라 하루 25이고 묶음 속성이 둘이면 9 × 9 = 81이다.

<br>

**3. 비용 예산**

| 항목 | 규칙 |
|---|---|
| 예산 | 태스크마다 최근 5분 동안 500<br>설정값<br>운영 태스크 둘이 프로젝트 한도 1,000을 나눠 쓰는 몫 |
| 예약 | 갱신을 시작할 때 그 갱신의 조회 비용 합을 한 번에 예약<br>남은 예산 확인과 예약을 원자적으로 처리해 서로 다른 키의 갱신이 같은 잔여 예산을 함께 통과하지 않음 |
| 부족 | 예약할 수 없으면 호출하지 않고 실패와 같이 그 키에 60초 쿨다운을 시작<br>로그 사유 `budget_exceeded` |
| 반환 | 갱신이 끝나면 성공한 조회의 비용만 남김<br>실패한 조회와 보내지 않은 조회의 예약분은 되돌림 |
| 기간 상한 | 엔드포인트마다 한 번의 갱신 비용이 500 안에 들도록 정함 |

**4. 캐시와 갱신**

| 항목 | 규칙 |
|---|---|

**5. 엔드포인트별 비용**

조회마다 조건 수 × 유형 비용을 하루 비용으로 적었다. 기간 비용은 일수 × 하루 비용에 기간과 무관한 고정 비용을 더한 값이다. 이 비용은 캐시가 없거나 만료된 키를 갱신할 때만 들고 그 뒤로는 캐시(오늘 포함 범위 10분, 지난 범위 24시간)로 응답한다. 여러 엔드포인트를 같은 5분에 갱신하면 합이 500을 넘을 수 있고 예산이 부족한 엔드포인트는 만료된 캐시나 사용 불가로 응답한다. 관리자 페이지는 그 카드만 쿨다운 뒤 다시 요청한다.
