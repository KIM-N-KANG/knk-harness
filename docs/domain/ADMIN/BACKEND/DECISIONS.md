# DECISIONS.md

ADMIN 도메인 백엔드의 중요한 결정을 날짜, 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 둔다. 여기에는 결정 당시의 이유와 변경 이력을 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 상태는 결정 당시 기준이다. 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.

<br>

### 2. 도메인 배치

**1. 운영 기능은 데이터의 주인 도메인이 정하고 ADMIN은 관리자 자체의 것만 정한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 이프 정책값, 캠페인, 계정 정지, 검수 보류 해제가 "운영자가 저장소에서 직접 변경"으로 정의돼 있어 DB에 접근하는 한 사람만 처리할 수 있었다. 원장과 아웃박스 같은 불변식을 SQL이 우회할 위험도 있었다. 관리자 페이지를 만들면서 관리자 기능을 어느 세트에 둘지 정해야 했다. |
| 채택 | 바뀌는 데이터를 관리하는 도메인이 그 관리자 API를 정한다. 이프 지급과 정책값은 PAYMENT, 캠페인과 문구는 NOTIFICATION, 공지는 NOTICE, 계정 정지는 ACCOUNT, 보류 해제는 MODERATION, 오리지널 등록과 수정은 STORY가 정한다. ADMIN은 관리자 인증과 권한, 감사 로그, 대시보드, 회원 조회만 정한다. 모든 관리자 API는 `/api/v1/admin/` 아래에 두고 ADMIN의 판정 필터와 감사 기록 연산을 쓴다. |
| 대안 | 관리자 기능 전부를 ADMIN 세트 하나에 모으는 안. 원장 규칙, 캠페인 선점 규칙, 정지 집행 규칙을 두 세트가 같이 정하게 되어 같은 사실을 두 곳에서 정하게 된다. |
| 영향 | 기존 네 세트의 "운영자가 저장소에서 직접 변경" 항목이 관리자 API로 바뀌었다. 관리자 역할 부여와 회수, 전송 중 상태로 멈춘 캠페인을 실패로 바꾸는 작업만 저장소 직접 변경으로 남는다. 각 세트의 4-2에 `관리자` 인증 수준이 생겼고 그 토큰 규칙은 ADMIN 4-2가 정한다. |

<br>

### 3. 인증과 권한

**2. 관리자 토큰은 대상 클레임으로 구분하고 갱신 없이 2시간만 유효하다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 서버에 역할 개념이 없었다. 앱 접근 토큰을 그대로 관리자 API에 쓰면 앱 토큰 유출이 곧 관리자 권한 유출이 된다. 관리자 페이지는 별도 호스트의 서버 측 처리기가 호출하며 토큰을 httpOnly 쿠키에 둔다. |
| 채택 | 관리자 전용 로그인이 Google 신원 증명을 앱과 같은 검증기로 검증하고 관리자 역할이 있는 활성 회원에게만 토큰을 발급한다. 토큰은 앱과 같은 대칭키의 HS256 JWT에 대상 클레임 `manyak-admin`을 더해 구분한다. 앱 경로는 대상 클레임이 있는 토큰을 회원으로 식별하지 않아 인증 필수 경로에서는 거절하고 선택 인증 경로에서는 익명으로 처리하며, 관리자 경로는 대상 클레임이 없는 토큰을 거절한다. 수명은 2시간이고 갱신 토큰이 없다. 역할은 토큰 값을 믿지 않고 요청마다 저장소에서 다시 읽는다. |
| 대안 | 앱 접근 토큰에 역할 클레임을 넣는 안은 토큰 수명 동안 회수가 반영되지 않고 앱 토큰 유출이 관리자 권한 유출이 된다. 별도 대칭키는 주입할 시크릿이 늘어난다. 갱신 토큰을 두는 안은 앱과 같은 회전과 재사용 탐지 복잡도를 관리자에게도 들여온다. 수명은 앱 접근 토큰 30분, 동의 대기 코드 10분, 링크 코드 5분을 보고 정했다. 30분은 갱신 없이 쓰기에 짧고 8시간 이상은 쿠키 탈취 위험에 노출되는 시간이 길다. 캠페인 예약과 공지 게시처럼 여러 단계가 이어지는 운영 작업 한 묶음을 재로그인 없이 마칠 수 있도록 2시간으로 했다. |
| 영향 | 관리자가 앱을 쓰려면 앱 로그인을 따로 한다. 개별 토큰 폐기는 없고 역할 회수와 계정 정지가 즉시 차단 수단이다. 대칭키를 바꾸면 앱과 관리자 토큰이 함께 무효가 된다. 관리자 페이지는 2시간마다 다시 로그인한다. |

<br>

**3. 관리자 역할은 별도 테이블의 행으로 두고 부여와 회수는 API 없이 저장소에서만 한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 관리자 페이지의 쿠키나 계정이 탈취되면 공격자가 자기 계정에 역할을 더하거나 다른 관리자를 지울 수 있다. |
| 채택 | 역할은 `users`의 컬럼이 아니라 `admin_accounts` 행의 존재로 표현한다. 역할 행의 추가와 삭제는 마이그레이션이나 SQL로만 한다. 관리자 API에는 역할을 바꾸는 경로가 없다. 관리자 역할이 있는 회원은 계정 정지 API의 대상이 될 수 없고 정지하려면 역할을 먼저 회수한다. |
| 대안 | 관리자 사이의 등급을 두고 상위 관리자만 역할을 바꾸게 하는 안. 팀 구성원이 소수라 등급을 둘 실익이 없고 상위 계정 탈취 시 같은 문제가 남는다. `users`에 역할 컬럼을 두는 안은 조회 한 번을 줄이고 구조가 단순하지만 세 가지 이유로 기각했다. `users`와 그 수명 규칙인 탈퇴, 정지, 재가입은 ACCOUNT가 정하므로 역할 컬럼을 넣으면 두 세트가 같은 테이블을 나눠 정하게 된다. 역할이 `users`에 있으면 프로필 수정처럼 회원 행을 바꾸는 API의 바인딩 실수가 곧 권한 상승이 되는데, 별도 테이블이면 회원 API에 그 테이블을 바꾸는 경로가 없다. 부여 시각 같은 정보를 `users`의 nullable 컬럼으로 늘리지 않고 두며 회수는 행 삭제로 끝난다. |
| 영향 | 첫 관리자는 배포 뒤 운영 DB에서 직접 넣는다. 관리자끼리 정지시킬 수 없어 관리자 화면 탈취로 다른 관리자를 잠그는 공격이 막힌다. |

<br>

### 4. 감사

**4. 모든 관리자 변경은 같은 트랜잭션의 감사 로그로 남기고 회원 조회도 접속 기록으로 남긴다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 여러 사람이 운영 작업을 하면 누가 언제 왜 바꿨는지 알아야 한다. 회원 개인정보를 조회하는 관리자 화면은 개인정보 안전성 확보조치의 접속 기록 보관 대상이다. |
| 채택 | 다른 도메인의 관리자 API는 변경을 적용한 뒤 같은 트랜잭션에서 감사 기록 연산을 호출한다. 기록에 실패하면 변경도 롤백된다. 처리자, 작업 이름, 대상의 외부 식별자, 사유, 변경 전후 값, 요청 ID를 남긴다. 회원 검색과 상세는 조회 뒤 독립 트랜잭션으로 접속 기록을 남기고 기록에 실패하면 조회 응답도 실패로 바꾼다. 감사 로그는 삭제와 수정 경로가 없고 영구 보존한다. |
| 대안 | 변경 뒤 비동기로 로그를 남기는 안은 로그 없는 변경을 만든다. 애플리케이션 로그에만 남기는 안은 보존 기간과 조회 수단이 로그 스택에 묶이고 관리자 페이지에서 볼 수 없다. 보존 기간을 1년이나 2년으로 정하는 안은 삭제 배치가 필요하고 법정 최소 기간을 넘기는 영구 보존이 더 단순하다. |
| 영향 | 모든 변경 API 요청 본문에 사유가 필수다. 감사 로그가 요청 ID를 64자로 저장하므로 상관관계 필터가 헤더 값의 길이와 문자를 검사해 어긋나면 서버 생성 값으로 바꾸고 응답 헤더와 감사 로그가 같은 값을 쓴다. 거절 대신 재발급을 택한 것은 상관관계 헤더가 클라이언트 추적 편의용이라 요청 자체를 막을 이유가 없기 때문이다. 관리자 역할이 있는 회원의 탈퇴는 회원 행이 남으므로 처리자 FK가 깨지지 않는다. 사유는 자유 문장이라 개인정보가 들어갈 수 있는 한계를 수용했다. |

<br>

### 5. 대시보드

**5. 대시보드는 서버 DB에 있는 숫자만 집계하고 방문자 수와 외부 도구는 연동하지 않는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 운영 지표가 분석 도구, 오류 추적 도구, AI 관측 도구, 운영 DB에 흩어져 있다. 방문자 수의 기준은 클라이언트 기기 식별자와 분석 도구다. |
| 채택 | 회원, 채팅, 스토리, 이프, 결제, 검수 보류의 오늘과 누적 수치를 서버 DB에서 집계한다. 오늘은 KST 자정 기준이고 한 응답의 모든 지표는 같은 기준 시각으로 계산한다. 채팅 턴은 AI 응답 메시지 수로 세고 재생성 판본은 세지 않는다. 팀 계정은 설정값의 회원 내부 ID 목록으로 모든 지표에서 제외하며 기본 목록은 운영 Terraform의 Grafana 서비스 통계 대시보드가 소비 활동에서 제외하는 팀 계정과 같다. 방문자 수는 세지 않고 오류 추적 도구와 AI 관측 도구는 관리자 페이지가 링크만 둔다. |
| 대안 | 서버가 요청 로그로 방문자를 세는 안은 분석 도구의 숫자와 다른 두 번째 숫자를 만든다. 외부 도구 API를 서버가 호출하는 안은 자격 증명 주입과 장애 전파 범위를 늘린다. |
| 영향 | 지표 정의는 기존 세트의 테이블 의미를 따른다. 팀 계정 제외는 대시보드에만 적용하고 회원 조회와 감사 로그에는 적용하지 않는다. 목록을 코드에 두지 않아 팀원이 바뀌면 환경 변수만 바꾼다. 집계는 요청마다 실행하고 캐시하지 않는다. 탈퇴 수, 환불 건수, 검수 보류 수는 결정 7에서 요약에서 뺐다. |

<br>

### 6. 목록

**6. 관리자 목록은 번호 페이지와 열 정렬을 쓰고 커서를 두지 않는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 앱의 목록은 무한 스크롤이라 keyset 커서를 쓴다. 관리자 페이지는 표 머리글을 눌러 정렬하고 아래 페이지 번호로 이동하는 화면이라 전체 건수와 임의 페이지 접근이 필요하다. 처음 초안은 앱과 같은 커서 방식이었다. |
| 채택 | 모든 관리자 목록은 `page`(1부터)와 `size`(1~100, 기본 20)로 요청하고 `items`, `page`, `size`, `totalElements`, `totalPages`를 돌려준다. 정렬은 `sort`와 `order`로 받고 허용 목록 밖은 거절한다. 같은 값은 항목의 공개 식별자 오름차순으로 고정해 페이지 사이에 행이 겹치거나 빠지지 않게 한다. 다른 도메인의 관리자 목록(캠페인, 공지, 보류)도 같은 구조를 쓴다. |
| 대안 | 커서 방식은 임의 페이지와 전체 건수를 줄 수 없고 정렬 열마다 커서 형식이 달라진다. 커서를 유지하고 전체 건수만 더하는 안은 두 방식을 함께 유지하게 된다. 내부 ID로 동률을 고정하는 안은 응답에 없는 값이라 클라이언트가 순서를 재현할 수 없다. |
| 영향 | 전체 건수 조회와 페이지 조회가 각각 실행되어 큰 OFFSET과 필터 COUNT가 전체 스캔이 될 수 있다. 관리자 전용 저빈도 호출이라 수용한다. 관리자 커서 비봉인 규칙과 관련 보안 행은 없어졌다. 공지와 알림 종류별 통계처럼 앱이 쓰는 목록은 그대로 커서다. |

<br>

**7. 대시보드는 차트에서 목록, 상세로 이어지며 목록은 대화 원문 없이 다른 도메인을 읽기만 한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 운영 통계는 Grafana 서비스 통계 대시보드의 SQL 패널 23개로 보고 있었고 DB 접근 권한이 있는 한 사람만 패널 뒤의 데이터를 따라갈 수 있었다. 관리자 페이지의 첫 화면을 차트 대시보드로 정하고 차트를 누르면 조건이 걸린 목록, 목록에서 상세로 가는 구조를 정했다. 요약의 탈퇴, 환불, 검수 보류 카드는 쓰임이 없다고 판단했다. |
| 채택 | 요약에서 탈퇴 수, 환불 건수, 검수 보류 수를 뺀다. 차트 엔드포인트 하나가 요청한 날짜 범위의 일별 추이 9종과 분포 차트 8개를 돌려주고 막대마다 그 조건을 목록 쿼리 이름과 값으로 함께 준다. 분포 차트는 Grafana 패널 중 장르별 깊이, 턴 수 분포, 게스트 비율, 회원별 채팅방 수, 첫 메시지 시간, AI 지연, AI 성공률, 제작 세션 인물 수를 같은 정의로 옮긴다. 스토리, 채팅방, 회원, 결제는 번호 페이지 목록과 상세를 두고 다른 도메인의 테이블을 읽기만 한다. 채팅방 응답에는 메시지 원문을 두지 않는다. 회원 검색에 활성 소셜 연동 이메일의 정확 일치를 더하되 응답에 이메일을 넣지 않는다. 접속 기록은 검색어가 있는 회원 목록, 회원 상세, 회원 거래 내역, 회원 출석 기록에 남긴다. 회원 상세의 하위 데이터 중 이프 거래와 출석은 별도 페이지 엔드포인트로 두고 결제, 채팅방, 스토리는 각 목록의 `memberId` 필터로 본다. 팀 계정 제외는 요약과 차트에만 적용하고 제작 세션 차트는 공식 계정의 세션을 포함한다. 캐시는 두지 않고 기간 상한으로 집계 범위를 제한한다. 상한은 처음 90일이었고 결정 10에서 366일로 올렸다. |
| 대안 | 연속 턴 간격, 이용 세션, 활동일당 소모, 출석 보상 충족 비율, 출석 요약 패널은 관리자 페이지 초안이 쓰지 않아 옮기지 않았다. 막대에 관리자 페이지 경로를 그대로 담는 안은 서버가 화면 경로를 알게 되어 목록 이름과 쿼리로 바꿨다. 이메일을 마스킹해 보여 주는 안은 찾은 회원이 맞는지 확인하는 데 쓰일 수 있지만 닉네임과 식별자로 충분하고 개인정보 최소화 원칙에 어긋나 넣지 않았다. Grafana처럼 UUID 앞 8자만 보여 주는 규칙은 관리자 권한과 접속 기록이 있으므로 두지 않았다. 검색어 없는 회원 목록도 접속 기록으로 남기는 안은 특정 회원을 지목한 조회가 아니고 행이 페이지마다 늘어나 뺐다. 집계 결과를 수 분 캐시하는 안은 현재 규모에서 1년 집계가 요청당 수백 밀리초 안이라 두지 않았다. 회원 상세에 거래, 결제, 채팅방, 스토리, 출석 배열을 모두 담는 안은 응답이 커지고 페이지를 넘길 수 없어 뺐다. |
| 영향 | 제작 세션 입력 인물 수는 주변 인물 행 수가 아니라 사용자가 직접 입력한 인물 수다. 웹 제작 화면이 입력칸을 기본으로 열어 두고 빈 칸도 한 명으로 보내 AI가 채우므로 행 수를 세면 0명이 사실상 나오지 않는다(KNK-1767). 대시보드의 이프 지급과 소진 카드, 일별 추이의 지급과 소진은 회원 목록이 아니라 전체 회원의 원장 행을 최신순으로 보여 주는 이프 거래 내역으로 잇는다(KNK-1771). 운영자가 개별 거래를 보고 싶어 했고 회원 목록은 행이 아니라 회원을 세기 때문이다. 회원 목록의 `creditDirection`과 `creditDate` 필터는 남긴다. 관리자 페이지 초안의 타입과 다른 점은 막대의 `href`가 `link` 객체로 바뀐 것, 출석 분포가 일별 추이로 합쳐진 것, 회원 상세에 배열이 없는 것, 채팅방 항목에 `aiFeature`가 없는 것, 스토리 소유자가 `null`일 수 있는 것, AI 기능 이름이 저장 값 4종인 것이다. 목록은 전체 건수와 페이지 쿼리를 따로 실행해 큰 OFFSET과 필터 COUNT가 전체 스캔이 될 수 있다. 대시보드 지표의 새 열은 제품 제약의 표에 더하고 참조 컬럼 표를 함께 고친다. |

**8. 활성과 신규 사용자 수는 Amplitude 사용자 수 조회로 받아 10분 캐시하고 팀 계정은 코호트로 뺀다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택<br>결정 5의 "외부 도구는 연동하지 않는다"를 분석 지표에 한해 대체 |
| 배경 | 방문자 수의 기준은 분석 도구이고 서버 DB에는 없다. 팀원이 Amplitude를 따로 열지 않고 대시보드에서 오늘 활성 사용자와 일별 활성, 신규 사용자를 보고 싶어 했다. 운영 프로젝트는 하나이고 개발 서버도 같은 프로젝트를 읽는다. Dashboard REST API 문서를 확인한 결과 이벤트 세분화의 특수 이벤트는 `_active`와 `_all`뿐이고 `_new`는 리텐션 조회 전용이라 세분화 조회로는 신규 사용자를 받을 수 없다. |
| 채택 | 서버가 Dashboard REST API의 활성·신규 사용자 수 조회 `GET /api/2/users`를 US 주소로 호출한다. `m=active`와 `m=new`를 `i=1`로 각 1회, `start`와 `end`는 오늘을 포함한 최근 90일이다. 결과를 프로세스 안에 10분 보관하고 `days`는 캐시를 잘라 응답한다. 팀 계정은 분석 도구에 저장한 코호트를 세그먼트 정의 `s`의 `userdata_cohort` `is not` 조건으로 뺀다. 코호트 ID는 환경 변수이고 비어 있으면 제외하지 않는다. 캐시 만료 뒤 갱신은 요청 하나만 하고 나머지는 기다리지 않고 만료된 캐시나 사용 불가를 받는다. 호출이 실패하면 60초 동안 다시 부르지 않고 만료된 캐시나 사용 불가로 응답한다. 자격 증명은 기존 API 키와 새 시크릿 키를 Secrets Manager의 앱 시크릿 JSON에 두고 태스크 정의에 참조를 추가한다. |
| 대안 | 이벤트 세분화 조회는 신규 사용자 이벤트를 받지 못해 쓸 수 없고 비용 기반 한도도 더 빨리 소모한다. 세그먼트 정의는 내장 속성, 사용자 속성, 코호트만 받고 사용자 ID 값 목록은 받지 않아 서버의 팀 계정 ID 목록을 그대로 쓸 수 없다. 클라이언트가 팀 계정에 사용자 속성을 붙이는 안은 세 클라이언트 배포가 필요하고 과거 이벤트에 소급되지 않는다. 캐시를 두지 않는 안은 관리자 페이지 새로고침마다 호출이 생겨 시간당 360회 한도에 가까워진다. 10분은 분석 도구의 집계 지연과 같은 자릿수라 더 짧아도 새 값이 없다. 기간마다 따로 조회하는 안은 호출이 세 배가 된다. 동시 요청이 각각 호출하는 안은 만료 직후 관리자 수만큼 호출이 몰리고, 갱신 중 요청을 기다리게 하는 안은 5초 시간 한도만큼 화면이 멈춘다. 쿨다운이 없으면 장애 중 새로고침마다 실패 호출이 쌓여 복구 뒤에도 한도에 걸린다. 관리자 페이지가 Amplitude를 직접 호출하는 안은 시크릿 키가 Vercel에도 생기고 호출 한도를 두 곳이 나눠 쓴다. |

**9. 안드로이드 설치 수는 Play Console 일괄 보고서를 읽어 기기 설치 합으로 집계하고 1시간 캐시한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-22 |
| 상태 | 채택 |
| 배경 | 앱 설치 수는 서버 DB에도 Amplitude에도 없다. Play Console 홈의 획득 수를 팀원이 따로 열어 보고 있었다. Play Console은 통계를 Google Cloud Storage 버킷에 월별 CSV 일괄 보고서로 내보내며 읽기 전용 서비스 계정으로 받을 수 있다. 보고서는 며칠 늦게 채워지고 날짜는 Play 기준 태평양 시간이다. |
| 채택 | 서버가 서비스 계정 키로 보고서 버킷의 설치 개요 CSV를 월별로 모두 내려받아 gzip과 UTF-16LE를 풀고 합산한다. 누적 설치는 일별 기기 설치 열의 전체 합, 활성 기기는 마지막 행의 활성 기기 설치, 기준 날짜는 마지막 행의 날짜이고 KST로 바꾸지 않는다. 일별 추이는 첫 날짜부터 마지막 날짜까지 모든 날이며 행마다 설치 누계와 활성 기기를 담아 누적 추이 그래프를 그릴 수 있게 한다. 보고서에 없는 날은 차트의 빈 날 0 채움과 맞춰 설치와 삭제 0, 누계는 전날 값으로 채우고 활성 기기는 모르는 값이라 `null`로 둔다. 보고서가 2026년 9월부터라 행 수가 작아 기간 쿼리를 두지 않는다. 결과는 1시간 캐시하고 갱신, 쿨다운, 실패 응답 규칙은 분석 지표와 같다. 키는 운영 앱 시크릿 JSON에만 두고 개발 서버는 설치 지표가 사용 불가다. |
| 대안 | Play Developer Reporting API는 별도 API 활성화와 쿼리 조립이 필요하고 같은 지연을 가진다. 일괄 보고서는 Play Console이 이미 만들어 두어 저장소 읽기만 하면 된다. 총 사용자 설치 열은 현재 보고서에서 항상 0으로 채워져 쓸 수 없고, Play Console 홈의 획득 수와 같은 계열인 일별 기기 설치 합을 누적값으로 썼다. 10분 캐시는 하루 한 번 갱신되는 원천에 과하고 1시간이면 보고서 반영 시점을 한 시간 안에 따라간다. 날짜를 KST로 바꾸는 안은 Play가 집계한 하루 경계와 어긋나 Play Console 화면과 다른 값이 된다. 개발 환경에도 키를 넣는 안은 운영 설치 수를 개발 화면에 보여 줄 이유가 없어 뺐다. |
| 영향 | 서버 설정에 Play 서비스 계정 키가 생기고 운영 Terraform이 태스크 정의에 시크릿 참조를 추가해야 한다. 기준 날짜가 오늘보다 며칠 전이라 화면은 기준 날짜를 함께 보여 준다. 보고서 열 구성이 바뀌면 해석 실패로 사용 불가가 된다. Google Cloud Storage가 외부 의존 대상에 추가된다. |
