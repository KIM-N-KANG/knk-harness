# DECISIONS.md

ADMIN 도메인 백엔드의 중요한 결정을 날짜, 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 둔다. 여기에는 결정 당시의 이유와 변경 이력을 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 상태는 결정 당시 기준이다. 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.

<br>

### 2. 도메인 배치

**1. 운영 기능의 도메인별 배치**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 이프 정책값, 캠페인, 계정 정지, 검수 보류 해제가 "운영자가 저장소에서 직접 변경"으로 정의돼 있어 DB에 접근하는 한 사람만 처리할 수 있었다. 원장과 아웃박스 같은 불변식을 SQL이 우회할 위험도 있었다. 관리자 페이지를 만들면서 관리자 기능을 어느 세트에 둘지 정해야 했다. |
| 채택 | 바뀌는 데이터를 관리하는 도메인이 그 관리자 API를 정한다. 이프 지급과 정책값은 PAYMENT, 캠페인과 문구는 NOTIFICATION, 공지는 NOTICE, 계정 정지는 ACCOUNT, 보류 해제는 MODERATION, 오리지널 등록과 수정은 STORY가 정한다. ADMIN은 관리자 인증과 권한, 감사 로그, 대시보드, 회원 조회만 정한다. 모든 관리자 API는 `/api/v1/admin/` 아래에 두고 ADMIN의 판정 필터와 감사 기록 연산을 쓴다. |
| 대안 | 관리자 기능 전부를 ADMIN 세트 하나에 모으는 안. 원장 규칙, 캠페인 선점 규칙, 정지 집행 규칙을 두 세트가 같이 정하게 되어 같은 사실을 두 곳에서 정하게 된다. |
| 영향 | 기존 네 세트의 "운영자가 저장소에서 직접 변경" 항목이 관리자 API로 바뀌었다. 관리자 역할 부여와 회수, 전송 중 상태로 멈춘 캠페인을 실패로 바꾸는 작업만 저장소 직접 변경으로 남는다. 각 세트의 4-2에 `관리자` 인증 수준이 생겼고 그 토큰 규칙은 ADMIN 4-2가 정한다. |

### 3. 인증과 권한

**2. 관리자 토큰의 구분과 2시간 수명**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 서버에 역할 개념이 없었다. 앱 접근 토큰을 그대로 관리자 API에 쓰면 앱 토큰 유출이 곧 관리자 권한 유출이 된다. 관리자 페이지는 별도 호스트의 서버 측 처리기가 호출하며 토큰을 httpOnly 쿠키에 둔다. |
| 채택 | 관리자 전용 로그인이 Google 신원 증명을 앱과 같은 검증기로 검증하고 관리자 역할이 있는 활성 회원에게만 토큰을 발급한다. 토큰은 앱과 같은 대칭키의 HS256 JWT에 대상 클레임 `manyak-admin`을 더해 구분한다. 앱 경로는 대상 클레임이 있는 토큰을 회원으로 식별하지 않아 인증 필수 경로에서는 거절하고 선택 인증 경로에서는 익명으로 처리하며, 관리자 경로는 대상 클레임이 없는 토큰을 거절한다. 수명은 2시간이고 갱신 토큰이 없다. 역할은 토큰 값을 믿지 않고 요청마다 저장소에서 다시 읽는다. |
| 대안 | 앱 접근 토큰에 역할 클레임을 넣는 안은 토큰 수명 동안 회수가 반영되지 않고 앱 토큰 유출이 관리자 권한 유출이 된다. 별도 대칭키는 주입할 시크릿이 늘어난다. 갱신 토큰을 두는 안은 앱과 같은 회전과 재사용 탐지 복잡도를 관리자에게도 들여온다. 수명은 앱 접근 토큰 30분, 동의 대기 코드 10분, 링크 코드 5분을 보고 정했다. 30분은 갱신 없이 쓰기에 짧고 8시간 이상은 쿠키 탈취 위험에 노출되는 시간이 길다. 캠페인 예약과 공지 게시처럼 여러 단계가 이어지는 운영 작업 한 묶음을 재로그인 없이 마칠 수 있도록 2시간으로 했다. |
| 영향 | 관리자가 앱을 쓰려면 앱 로그인을 따로 한다. 개별 토큰 폐기는 없고 역할 회수와 계정 정지가 즉시 차단 수단이다. 대칭키를 바꾸면 앱과 관리자 토큰이 함께 무효가 된다. 관리자 페이지는 2시간마다 다시 로그인한다. |

**3. 관리자 역할의 별도 저장과 DB 관리**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 관리자 페이지의 쿠키나 계정이 탈취되면 공격자가 자기 계정에 역할을 더하거나 다른 관리자를 지울 수 있다. |
| 채택 | 역할은 `users`의 컬럼이 아니라 `admin_accounts` 행의 존재로 표현한다. 역할 행의 추가와 삭제는 마이그레이션이나 SQL로만 한다. 관리자 API에는 역할을 바꾸는 경로가 없다. 관리자 역할이 있는 회원은 계정 정지 API의 대상이 될 수 없고 정지하려면 역할을 먼저 회수한다. |
| 대안 | 관리자 사이의 등급을 두고 상위 관리자만 역할을 바꾸게 하는 안. 팀 구성원이 소수라 등급을 둘 실익이 없고 상위 계정 탈취 시 같은 문제가 남는다. `users`에 역할 컬럼을 두는 안은 조회 한 번을 줄이고 구조가 단순하지만 세 가지 이유로 기각했다. `users`와 그 수명 규칙인 탈퇴, 정지, 재가입은 ACCOUNT가 정하므로 역할 컬럼을 넣으면 두 세트가 같은 테이블을 나눠 정하게 된다. 역할이 `users`에 있으면 프로필 수정처럼 회원 행을 바꾸는 API의 바인딩 실수가 곧 권한 상승이 되는데, 별도 테이블이면 회원 API에 그 테이블을 바꾸는 경로가 없다. 부여 시각 같은 정보를 `users`의 nullable 컬럼으로 늘리지 않고 두며 회수는 행 삭제로 끝난다. |
| 영향 | 첫 관리자는 배포 뒤 운영 DB에서 직접 넣는다. 관리자끼리 정지시킬 수 없어 관리자 화면 탈취로 다른 관리자를 잠그는 공격이 막힌다. |

### 4. 감사

**4. 관리자 변경 감사와 회원 조회 접속 기록**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 여러 사람이 운영 작업을 하면 누가 언제 왜 바꿨는지 알아야 한다. 회원 개인정보를 조회하는 관리자 화면은 개인정보 안전성 확보조치의 접속 기록 보관 대상이다. |
| 채택 | 다른 도메인의 관리자 API는 변경을 적용한 뒤 같은 트랜잭션에서 감사 기록 연산을 호출한다. 기록에 실패하면 변경도 롤백된다. 처리자, 작업 이름, 대상의 외부 식별자, 사유, 변경 전후 값, 요청 ID를 남긴다. 회원 검색과 상세는 조회 뒤 독립 트랜잭션으로 접속 기록을 남기고 기록에 실패하면 조회 응답도 실패로 바꾼다. 감사 로그는 삭제와 수정 경로가 없고 영구 보존한다. |
| 대안 | 변경 뒤 비동기로 로그를 남기는 안은 로그 없는 변경을 만든다. 애플리케이션 로그에만 남기는 안은 보존 기간과 조회 수단이 로그 스택에 묶이고 관리자 페이지에서 볼 수 없다. 보존 기간을 1년이나 2년으로 정하는 안은 삭제 배치가 필요하고 법정 최소 기간을 넘기는 영구 보존이 더 단순하다. |
| 영향 | 모든 변경 API 요청 본문에 사유가 필수다. 감사 로그가 요청 ID를 64자로 저장하므로 상관관계 필터가 헤더 값의 길이와 문자를 검사해 어긋나면 서버 생성 값으로 바꾸고 응답 헤더와 감사 로그가 같은 값을 쓴다. 거절 대신 재발급을 택한 것은 상관관계 헤더가 클라이언트 추적 편의용이라 요청 자체를 막을 이유가 없기 때문이다. 관리자 역할이 있는 회원의 탈퇴는 회원 행이 남으므로 처리자 FK가 깨지지 않는다. 사유는 자유 문장이라 개인정보가 들어갈 수 있는 한계를 수용했다. |

### 5. 대시보드

**5. 서버 DB 대시보드 집계와 외부 연동 제외**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 운영 지표가 분석 도구, 오류 추적 도구, AI 관측 도구, 운영 DB에 흩어져 있다. 방문자 수의 기준은 클라이언트 기기 식별자와 분석 도구다. |
| 채택 | 회원, 채팅, 스토리, 이프, 결제, 검수 보류의 오늘과 누적 수치를 서버 DB에서 집계한다. 오늘은 KST 자정 기준이고 한 응답의 모든 지표는 같은 기준 시각으로 계산한다. 채팅 턴은 AI 응답 메시지 수로 세고 재생성 판본은 세지 않는다. 팀 계정은 설정값의 회원 내부 ID 목록으로 모든 지표에서 제외하며 기본 목록은 운영 Terraform의 Grafana 서비스 통계 대시보드가 소비 활동에서 제외하는 팀 계정과 같다. 방문자 수는 세지 않고 오류 추적 도구와 AI 관측 도구는 관리자 페이지가 링크만 둔다. |
| 대안 | 서버가 요청 로그로 방문자를 세는 안은 분석 도구의 숫자와 다른 두 번째 숫자를 만든다. 외부 도구 API를 서버가 호출하는 안은 자격 증명 주입과 장애 전파 범위를 늘린다. |
| 영향 | 지표 정의는 기존 세트의 테이블 의미를 따른다. 팀 계정 제외는 대시보드에만 적용하고 회원 조회와 감사 로그에는 적용하지 않는다. 목록을 코드에 두지 않아 팀원이 바뀌면 환경 변수만 바꾼다. 집계는 요청마다 실행하고 캐시하지 않는다. 탈퇴 수, 환불 건수, 검수 보류 수는 결정 7에서 요약에서 뺐다. |

### 6. 목록

**6. 관리자 목록의 번호 페이지와 열 정렬**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 앱의 목록은 무한 스크롤이라 keyset 커서를 쓴다. 관리자 페이지는 표 머리글을 눌러 정렬하고 아래 페이지 번호로 이동하는 화면이라 전체 건수와 임의 페이지 접근이 필요하다. 처음 초안은 앱과 같은 커서 방식이었다. |
| 채택 | 모든 관리자 목록은 `page`(1부터)와 `size`(1~100, 기본 20)로 요청하고 `items`, `page`, `size`, `totalElements`, `totalPages`를 돌려준다. 정렬은 `sort`와 `order`로 받고 허용 목록 밖은 거절한다. 같은 값은 항목의 공개 식별자 오름차순으로 고정해 페이지 사이에 행이 겹치거나 빠지지 않게 한다. 다른 도메인의 관리자 목록(캠페인, 공지, 보류)도 같은 구조를 쓴다. |
| 대안 | 커서 방식은 임의 페이지와 전체 건수를 줄 수 없고 정렬 열마다 커서 형식이 달라진다. 커서를 유지하고 전체 건수만 더하는 안은 두 방식을 함께 유지하게 된다. 내부 ID로 동률을 고정하는 안은 응답에 없는 값이라 클라이언트가 순서를 재현할 수 없다. |
| 영향 | 전체 건수 조회와 페이지 조회가 각각 실행되어 큰 OFFSET과 필터 COUNT가 전체 스캔이 될 수 있다. 관리자 전용 저빈도 호출이라 수용한다. 관리자 커서 비봉인 규칙과 관련 보안 행은 없어졌다. 공지와 알림 종류별 통계처럼 앱이 쓰는 목록은 그대로 커서다. |

**7. 대시보드에서 목록과 상세로 이어지는 읽기 조회**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 운영 통계는 Grafana 서비스 통계 대시보드의 SQL 패널 23개로 보고 있었고 DB 접근 권한이 있는 한 사람만 패널 뒤의 데이터를 따라갈 수 있었다. 관리자 페이지의 첫 화면을 차트 대시보드로 정하고 차트를 누르면 조건이 걸린 목록, 목록에서 상세로 가는 구조를 정했다. 요약의 탈퇴, 환불, 검수 보류 카드는 쓰임이 없다고 판단했다. |

| 배경 | 명세는 Amplitude 비용을 세분화 일수 × 이벤트 수, 퍼널 일수 × 단계 수 × 2로만 계산해 조건 수를 1로 잡았다. Dashboard REST API의 공식 산식은 일수 × 조건 수 × 유형 비용이고 조건 수는 세그먼트 수에 세그먼트 안 조건 수를 더하며 묶음 속성 하나를 세그먼트 4개로 센다. 이벤트 필터는 조건으로 세지 않는다. 유형 비용은 리텐션 8, 세션 4다. 국가와 플랫폼을 세그먼트에 넣은 정의로는 캠페인 추이 30일이 1,470, 간편 제작 퍼널 31일이 2,604, 리텐션과 세션 30일이 각 1,920이라 5분 한도 1,000을 넘었다. 2026-10-21과 22일 운영 키로 사용자 속성 조건을 이벤트 필터(`subprop_type` `user`)로 넣어도 세그먼트 방식과 결과가 같음을 확인했다. `_new`에 국가, 플랫폼, 캠페인 필터를 건 값은 [58, 152], `_active`에 국가와 플랫폼 필터를 건 값은 [81, 200]으로 차트와 같았다. 국가 조건을 빼면 10월 1일부터 21일까지 Web DAU 합이 1,444에서 1,736으로 늘어 국가 조건은 유지한다. 운영 태스크가 둘 이상일 수 있는데 계수기는 태스크마다 따로다. |

| 채택 | `GET /admin/stories/{storyId}/settings`를 둔다. 오리지널 상세처럼 STORY 세트 수정 폼의 현재 저장값 조립을 소유자 검사 없이 쓰고 `submission`과 인물 이미지의 `objectKey`를 빼서 응답한다. 삭제되지 않은 모든 스토리가 대상이고 없거나 삭제됐으면 스토리 상세와 같이 404다. 수정 폼 조립이 이미 검수 게이트 없이 표지와 인물 이미지 전부와 검수 상태를 실으므로 그대로 쓴다. `objectKey`는 현재 저장값 조립에서 항상 `null`이고 소유자가 수정 요청에서 새 업로드를 다시 잇는 값이라 읽기 전용 응답에 쓸모가 없다. 접속 기록은 남기지 않는다. 접속 기록은 회원 개인정보 조회에만 남기고 채팅 상세와 오리지널 상세를 포함한 콘텐츠 조회는 기록하지 않는 규칙을 따른다. 시작 설정의 추천 입력은 채팅 원문이 아니라 제작 입력이라 이 응답에 싣는다. 화풍은 스토리에 저장되지 않아(화풍 테이블은 선택 목록만) 응답에 없다. ([3-2-4 감사 로그](3-2-DB-SCHEMA.md#3-2-4-감사-로그), [5-1-4 감사와 접속 기록](5-1-SECURITY.md#5-1-4-감사와-접속-기록)) |
| 대안 | 스토리 상세 응답에 설정을 합치는 안은 목록 항목 구조를 넓힌 상세가 설정 본문만큼 커지고 요약만 보는 화면도 본문을 받는다. 오리지널 상세의 범위를 모든 스토리로 넓히는 안은 STORY 세트 경로의 의미와 404 조건을 바꾼다. 소유자 수정 폼처럼 승인 전 제출본을 반영하는 안은 아직 공개와 채팅에 쓰이지 않는 값을 현재 설정처럼 보이게 하고 제출본은 MODERATION 세트가 다룬다. 접속 기록을 남기는 안은 같은 내용을 보이는 오리지널 상세가 기록하지 않아 규칙이 갈리고 `ACCESS` 분류의 뜻(개인정보 조회)이 넓어진다. |
| 영향 | 4-2-7이 새로 생겨 채팅 목록부터 다른 도메인과의 경계까지 절 번호가 하나씩 밀렸고 관리자 웹 명세의 링크도 바뀌었다. 이전 결정 본문의 4-2-7 이후 절 번호는 당시 번호이며 결정 21의 "4-2-32 응답"은 현재 4-2-33 AI 비용이다. 관리자 경로 회귀 테스트의 수집 수가 하나 는다. 지금 저장 흐름은 표지와 인물 이미지를 `APPROVED`로만 저장해 `PENDING`과 `REJECTED`는 기존 데이터나 이후 자동 검수에서만 보인다. MODERATION 세트의 관리자 제출본 상세는 계속 설정 본문을 싣지 않는다. 관리자 웹은 스토리 상세에 스토리 설정 구역을 둔다(관리자 웹 결정 23). |
| 보완 | 2026-10-26 결정 32로 삭제된 스토리도 대상이다. 채택의 "삭제되지 않은 모든 스토리가 대상이고 없거나 삭제됐으면 스토리 상세와 같이 404"는 없는 스토리만 404로 바뀌고 응답에 `deletedAt`이 생긴다. |

**32. 관리자 스토리와 채팅 조회는 삭제된 행도 보이고 목록은 기본으로 제외한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-26 |
| 상태 | 채택<br>결정 31의 "삭제되지 않은 모든 스토리가 대상"을 대체 |
| 배경 | 스토리와 채팅 삭제는 삭제 시각만 기록하고 설정, 시작 설정, 인물, 이미지, 메시지 같은 하위 데이터를 지우지 않는다. ([STORY 4-1-8 삭제](../../STORY/BACKEND/4-1-PIPELINES.md#4-1-8-삭제), [CHAT 4-1-5 삭제](../../CHAT/BACKEND/4-1-PIPELINES.md#4-1-5-삭제)) 그런데 관리자 목록은 삭제된 행을 빼고 상세와 설정은 404라 운영자가 사용자가 삭제한 스토리와 채팅을 볼 수 없었다(KNK-1855와 KNK-1856). 회원은 반대로 탈퇴 회원을 기본 포함하고 `excludeDeleted`로 뺀다. |
| 채택 | 스토리 목록과 채팅 목록에 삭제 필터 `deleted`를 둔다. 값이 없으면 지금처럼 삭제된 행을 빼고 `include`는 함께 싣고 `only`는 삭제된 행만 싣는다. 그 밖의 값은 다른 필터 enum과 같이 400이다. `memberId`나 `storyId`로 좁힌 목록에도 같은 필터를 쓴다. 기본값을 제외로 두는 것은 차트가 여는 목록의 쿼리와 결과를 지금과 같게 두어 차트와 목록의 일치 불변식을 깨지 않기 위해서다. 차트의 목록 링크와 관리자 페이지가 일별 추이로 만드는 목록 쿼리에는 `deleted`를 넣지 않는다. 목록 항목, 스토리 상세, 채팅 상세, 스토리 설정 응답에 `deletedAt`을 더하고 상세와 설정은 삭제된 행도 공개 식별자로 찾아 응답한다. 하위 데이터가 남아 있어 삭제 전과 같은 내용을 보인다. 집계 값의 정의는 바꾸지 않는다. 스토리 목록의 채팅 수와 턴 합, 기준 턴 도달률, 최근 채팅은 삭제된 스토리에서도 그 스토리의 삭제되지 않은 채팅으로 정하고 대시보드, 차트, 회원 통계도 그대로다. 접속 기록, 감사 로그, 권한 규칙은 바꾸지 않는다. ([3-1-3 품질 속성](3-1-SOFTWARE-ARCHITECTURE.md#3-1-3-품질-속성), [4-1-5 목록 공통 처리](4-1-PIPELINES.md#4-1-5-목록-공통-처리)) |
| 대안 | 회원처럼 삭제된 행을 기본으로 싣고 제외 필터를 두는 안은 차트가 여는 목록에 삭제된 행이 섞여 지금의 막대와 목록 건수 관계가 바뀌고 차트 링크마다 제외 쿼리를 넣어야 한다. 불리언 `includeDeleted` 하나로 두는 안은 삭제된 행만 모아 볼 수 없다. 삭제된 행을 별도 엔드포인트로 두는 안은 같은 필터와 정렬을 두 번 정하게 된다. 삭제된 스토리의 채팅 수에 삭제된 채팅까지 세는 안은 같은 열의 뜻이 행마다 달라진다. |
| 영향 | 스토리 목록과 채팅 목록의 쿼리에 `deleted`가 생기고 목록 항목과 스토리 설정 응답에 `deletedAt`이 생긴다. 상세와 설정의 404 조건에서 삭제가 빠져 5-3의 대상 없음 처리도 바뀐다. 스토리를 삭제하면 그 제출본도 지워져 삭제된 스토리의 보류 상태는 항상 `APPROVED`다. 채팅의 삭제 판정은 채팅 자신의 삭제 시각이라 삭제된 스토리의 채팅은 지금처럼 기본 목록에 있다. 관리자 웹은 두 목록과 범위 목록에 삭제 필터를 두고 목록 행과 상세 머리에 삭제 표시를 둔다(관리자 웹 결정 24). 서버가 먼저 배포돼야 관리자 웹의 삭제 필터가 동작한다. |

**33. 회원 스토리 공개 중단은 MODERATION이 정하고 ADMIN은 감사 작업 이름과 스토리 응답의 공개 중단 표시만 더한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-27 |
| 상태 | 채택<br>결정 4의 "모든 변경 API 요청 본문에 사유가 필수"를 공개 중단에 한해 사유 분류 필수와 메모 선택으로 대체 |
| 배경 | 관리자가 회원 스토리를 공개 중단하게 됐다. 공개 중단을 푸는 조건이 검수 승인이라 규칙은 MODERATION 세트에 있다(MODERATION 결정 9, 10, 11). 관리자 페이지는 스토리 목록과 상세에서 공개 중단 여부를 보여야 하고 감사 로그에 사유 분류와 메모가 남아야 한다. 결정 28의 활동 알림은 알림 내역의 `ACTIVITY` 분류와 같은 세 종류로 정의돼 있었다. |

ADMIN은 감사 작업 이름 `STORY_TAKEN_DOWN`(분류 `CHANGE`, 대상 `STORY`)과 기록 허용 필드를 더한다. 변경 전 값은 `visibility`, 변경 후 값은 `visibility`, `takedownReason`, `takedownReasonDetail`, `takenDownAt`, `memo`다. 감사 로그의 `reason`은 비어 있으면 안 되므로 소유자에게 보인 사유(분류 표시 이름, `ETC`는 입력 사유)를 넣고 내부 메모는 변경 후 값에 둔다. 스토리 목록 항목과 상세에 `takenDownAt`, `takedownReason`, `takedownReasonDetail`을 더한다. 공개 중단 필터는 두지 않는다. 푸시 열람의 활동 알림은 스토리 완성, 검수 완료, 출석 리마인드 세 종류를 유지하고 공개 중단 알림은 넣지 않는다. 공개 중단 알림은 드문 운영 통지라 열람률을 재방문 지표로 볼 이유가 없다. |
| 대안 | 공개 중단 API를 ADMIN 세트에 두는 안은 결정 1과 어긋나고 해제 규칙이 있는 MODERATION과 같은 사실을 나눠 정한다. 메모를 `reason`에 넣고 없을 때만 표시 이름을 넣는 안은 같은 컬럼의 뜻이 행마다 달라 검색어로 분류를 찾을 수 없다. 활동 알림에 공개 중단을 넣는 안은 응답의 `activityTypes`가 4항목이 되어 관리자 웹과 함께 바꿔야 하고 열람 대응에 캠페인 값이 하나 는다. |
| 영향 | 스토리 목록 응답에 필드 세 개가 늘어 관리자 웹과 함께 배포한다. 감사 로그 조회의 작업 이름 필터에 `STORY_TAKEN_DOWN`이 생긴다. 1-5의 활동 알림 정의가 `ACTIVITY` 분류 전체가 아니게 되었다. |
| 보완(2026-10-30) | 결정 55로 푸시 열람의 활동 알림에 이프 만료 예정 알림을 더해 채택의 "스토리 완성, 검수 완료, 출석 리마인드 세 종류를 유지"를 네 종류로 대체한다. 공개 중단 알림을 넣지 않는 판단은 유지한다. |

**34. 회원 목록에 누적 턴 수와 기간 턴 수를 두고 누적 턴 수로 정렬한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-27 |
| 상태 | 채택<br>결정 27의 "회원 목록에는 두지 않는다"를 대체 |
| 배경 | 관리자가 회원 목록에서 채팅 수만으로는 실제 이용량을 알 수 없어 턴 수도 보고 정렬하기를 원했다. 결정 27은 목록 한 페이지마다 회원별 메시지 집계가 붙고 정렬하려면 전체 회원의 턴 수를 세야 한다는 이유로 상세에만 두었다. `story_chats`의 회원 인덱스는 삭제 제외 부분 인덱스라 삭제된 채팅까지 세는 누적 턴 수에는 쓰이지 않는다. |
| 채택 | 회원 목록 항목에 `turnCount`를 더하고 정의는 회원 상세와 같게 해 같은 회원의 목록과 상세 값이 같다. 상세는 목록 항목 구조를 그대로 쓰므로 상세의 `turnCount` 정의도 목록 항목에서 정한다. `chatFrom`이나 `chatTo`가 있으면 `periodChatCount`처럼 `periodTurnCount`를 준다. 기간은 스토리 목록과 같이 채팅 생성일로 거르고 그 채팅의 모든 턴을 센다. 나머지 정의는 `turnCount`와 같아 삭제된 채팅을 포함하고 기간을 넓히면 `turnCount`와 같아진다. 정렬 키 `turnCount`를 더하고 `chatCount`와 같이 기간과 무관한 누적 값으로 정렬한다. 정렬 열이 아닌 회원 집계는 정렬과 페이지를 적용한 뒤 현재 페이지 회원에만 계산한다. 삭제된 채팅을 포함하는 `story_chats (user_id, created_at)` 인덱스를 더해 회원별 채팅을 찾고 채팅별 AI 응답은 기존 `story_messages (chat_id, role, created_at)` 인덱스로 센다. |
| 대안 | 기간 턴 수를 `periodChatCount`와 같이 삭제되지 않은 채팅으로만 세는 안은 기간을 넓혀도 같은 행의 `turnCount`와 맞지 않는다. 기간 턴 수를 메시지 생성일로 세는 안은 기간 채팅 수와 기간 기준이 달라진다. 기간 턴 수로 정렬하는 키를 따로 두는 안은 기존 `chatCount` 정렬이 누적 값이라 정렬 의미가 둘로 갈린다. 회원별 턴 수를 따로 집계해 저장하는 안은 메시지 저장과 재생성마다 갱신 경로가 생긴다. 인덱스 없이 두는 안은 턴 수 정렬마다 걸러진 회원 수만큼 `story_chats`를 처음부터 훑는다. |
| 영향 | 회원 목록 응답에 필드 두 개와 정렬 키 하나가 늘어 관리자 웹과 함께 배포한다. `story_chats`에 인덱스 하나를 더하는 마이그레이션이 필요하다. 누적 턴 수 정렬은 요청마다 걸러진 회원의 AI 응답 메시지를 모두 세는 비용이 들며 이를 수용한다. 같은 행의 `chatCount`는 삭제되지 않은 채팅 수, `turnCount`는 삭제된 채팅을 포함한 턴 수라 두 값의 기준이 다르다. |

**35. 가입 수에서 재가입으로 연동을 넘긴 예전 계정을 빼고 가입을 Amplitude 플랫폼으로도 나눈다**

**36. 채팅 턴 도달률과 채팅 옵션 비중에 Amplitude 플랫폼 값과 게스트, 회원 구분을 더한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-27 |
| 상태 | 채택<br>결정 13 채택의 "턴 도달률은 Amplitude의 동일 채팅 고정 퍼널 대신 DB로 계산한다"는 DB 값에 그대로 두고 플랫폼 값만 Amplitude로 더함 |
| 배경 | 턴 도달률과 채팅 옵션 비중은 DB로만 계산해 Web과 Android를 나눌 수 없다. DB의 채팅과 메시지에는 플랫폼이 없다. 턴 도달률은 DB에서 현재 소유자로 게스트와 회원을 나누고 채팅 옵션 비중은 나누지 않는다. | 채택 | 턴 도달률의 플랫폼 값은 AI 응답 성공 이벤트 중 `is_regenerated`가 거짓이고 `turn_number`가 기준 턴인 이벤트의 합계(`m=totals`)다. 한 채팅의 한 턴은 성공 이벤트가 한 번이라 이벤트 수가 그 턴을 저장한 채팅 수다. 비율의 분모는 1턴 이벤트 수다. 채팅 생성 이벤트가 없어 DB처럼 0턴 채팅을 분모에 넣을 수 없다. 기준 턴은 DB와 같은 12개이고 플랫폼은 결정 35와 같이 국내 조건 안의 세 조회와 그 합이다. 채팅 옵션 비중의 플랫폼 값은 두 가지다. 채팅 시작 버튼 클릭을 `persona_type`의 `default`, `persona`로 나눈 클릭 수와 같은 성공 이벤트를 `model_code`로 나눈 턴 수다. 채팅 수, 페르소나 채팅 수, 채팅 모델별 채팅 수는 채팅 생성과 그 모델을 알리는 이벤트가 없어 나누지 않는다. 쿼리 `segment`(`all`, `guest`, `member`, 기본 `all`)로 플랫폼 값을 사용자 속성 `user_id`가 없는 이벤트(게스트)와 있는 이벤트(회원)로 거른다. 앱·해외 로그인 조회의 기존 조건 표현과 같다. 플랫폼과 `segment`를 겹쳐 Web 회원, Android 게스트 같은 조합을 한 번에 하나씩 볼 수 있다. | 보완 | 2026-10-30 결정 46으로 플랫폼 값은 웹과 앱 두 조회이고 `all`은 둘의 합이며 `unknown`은 없다. 하루 비용은 턴 도달률 24, 모델 둘일 때 채팅 옵션 8이다. |

**37. 기능 사용과 사용자 세션에도 게스트와 회원 구분 `segment`를 둔다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-27 |
| 상태 | 채택<br>결정 36의 `segment`를 기능 사용과 안정성, 사용자 세션으로 넓힘 |
| 배경 | 결정 36으로 턴 도달률과 채팅 옵션 비중에 `segment`(`all`, `guest`, `member`)가 생겼다. 사용자가 이미 플랫폼으로 나뉜 Amplitude 지표 가운데 기능 사용과 세션에도 같은 구분을 원했다. 기능 사용은 이벤트 세분화라 사용자 속성 조건을 이벤트 필터로 넣는다. 평균 세션 길이 조회는 이벤트를 받지 않아 국가와 플랫폼 조건을 세그먼트 `s`에 넣고 있다. 앱·해외 로그인 조건에는 이미 `user_id` `is not` `(none)`이 들어 있다. |
| 채택 | 두 엔드포인트에 쿼리 `segment`(기본 `all`)를 두고 응답에 적용 값을 싣는다. 기능 사용은 모든 조회에 `user_id` `is` `(none)`(게스트)이나 `is not` `(none)`(회원) 이벤트 필터를 더한다. 게스트에서는 회원만 담는 앱·해외 로그인 묶음을 조회하지 않고 0으로 둔다. 회원에서는 앱·해외 로그인 묶음을 `all`과 같은 조회로 쓴다. 세션은 `s`에 `{"prop":"user_id","op":"is","values":["(none)"]}`나 `op`가 `is not`인 같은 조건을 더한다. 새벽 배치는 `segment` `all`만 미리 받는다. |
| 대안 | 세션을 이벤트 필터로 거르는 안은 세션 조회가 이벤트를 받지 않아 쓸 수 없다. 기능 사용의 게스트에서도 앱·해외 로그인 묶음을 조회하는 안은 늘 0인 조회에 비용을 쓴다. 사용자 활동의 신규 방문자, 리텐션, 전환 퍼널에 같은 구분을 두는 안은 시작 이벤트가 로그인 전 첫 이벤트이거나 퍼널 첫 단계가 게스트 행동이라 회원으로 거르면 값이 거의 비어 이번에 넣지 않는다. |
| 영향 | 기능 사용의 비용은 이벤트 필터라 그대로이고 게스트는 앱·해외 로그인 묶음만큼 줄어든다. 세션은 조회마다 세그먼트 조건이 하나 늘어 `guest`와 `member`의 하루 비용이 32에서 44가 되고 기본 14일 첫 조회가 616이라 예산 한 번에 다 받지 못하고 준비 중 날짜가 남는다. 세션의 세그먼트는 사용자 속성으로 판정하므로 로그인 전후가 섞인 세션의 분류는 Amplitude 세그먼트 판정을 따르며 배포 뒤 같은 조건의 Amplitude 차트와 대조한다(6-7). |
| 보완 | 2026-10-30 결정 46으로 앱·해외 로그인 묶음이 없어져 게스트와 회원 모두 전체, 웹, 앱 묶음에 `user_id` 필터만 더한다. 기능 사용의 `all`은 전체 조건 묶음 하나다. |

**45. 대화 요약 호출을 AI 기능 지표와 AI 비용에 넣고 채팅 응답에는 요약 끝 턴만 더한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-29 |
| 상태 | 채택 |
| 배경 | CHAT 결정 20으로 백엔드가 10턴마다 AI 요약 API를 비동기로 호출하고 `ai_call_logs`에 `feature=chat_compact`로 남기며 성공한 요약을 `story_chats.summary`와 `summary_through_turn`에 저장한다(KNK-1898). 관리자 AI 평균 호출 시간, AI 성공률, AI 비용, 채팅 목록의 AI 호출 필터는 기능 목록을 고정해 이 호출을 빼므로 대화 요약을 켜면 호출 수와 성공률이 보이지 않고 비용은 `unmapped`로만 잡힌다. AI 요약 응답에는 `meta`가 없어 호출 기록의 `model`, `provider`, 토큰 수가 비고 AI 서버는 요약 호출을 Langfuse 추적 `대화 요약` 아래 모델 시도마다 사용량과 함께 남긴다(manyak-ai `src/api/v1/chat.py`). 사용자가 10/29에 대화 요약을 운영 지표와 턴당 원가에 넣고 관리자 채팅 상세에는 요약 끝 턴만 보이기로 정했다(KNK-1912). |
| 채택 | 기능 `chat_compact`를 `ai-latency`, `ai-success`, AI 비용의 `byFeature`, 채팅 목록 `aiFeature`에 더한다. 순서는 기존 다섯 기능 뒤 여섯째다. 팀 계정 판정은 다른 채팅 기능처럼 기록의 채팅 ID가 가리키는 채팅의 소유 회원이고 막대는 채팅 목록으로 잇는다. 성공률은 AI 요약 호출의 성공과 실패로 센다. 요약 저장, 폐기(`chat_compact_discarded`), 무효화(`chat_compact_invalidated`) 건수는 지표에 넣지 않는다. 그 값은 로그 이벤트에만 있고 DB에 없으며 요약 실패는 이 성공률로 본다. AI 비용은 추적 이름 `대화 요약`을 `chat_compact`에 대응해 다른 기능과 같은 Langfuse 경로로 계산한다. 호출 기록에 모델이 없으므로 호출 수는 모델 `null` 항목에 실리고 금액은 Langfuse 모델 이름 항목에 따로 실리는 기존 대응 규칙을 그대로 쓴다. 턴당 원가의 분자에 대화 요약 비용을 넣는다. 요약은 턴 진행에 딸린 비용이고 실시간 이미지와 달리 따로 이프를 받지 않는다. 채팅 목록 항목과 상세에는 `summaryThroughTurn`(요약 끝 턴)만 더하고 0이면 요약 없음이다. 요약 본문은 싣지 않는다. 관리자 응답에 대화 내용을 싣지 않는 원칙(4-2-1과 5-1-6)을 그대로 두며 요약은 AI가 스토리 전개와 사용자가 말한 내용을 정리한 최대 3,000자 글이라 대화 내용에 해당한다. |
| 대안 | 요약 호출을 `chat_response`에 섞는 안은 요약 실패가 턴 본문 성공에 가려진다. 저장, 폐기, 무효화 건수를 지표로 두는 안은 로그 집계를 새로 붙여야 한다. 요약의 호출 수와 금액을 한 항목으로 합치는 안은 대화 요약만 기능과 모델 대응 규칙을 바꿔야 한다. 턴당 원가에서 빼는 안은 요약을 켠 뒤 채팅 한 턴의 실제 비용보다 작게 보인다. 무효화된 요약을 따로 표시하는 안은 무효화가 `summary`를 `NULL`로 비우고 `summary_through_turn`을 0으로 되돌려 DB로 처음 상태와 구별할 수 없다. 요약 본문을 싣는 안은 대화 내용을 보이지 않는 관리자 채팅 상세("이 화면에서는 대화 내용을 제공하지 않습니다.")의 열람 범위를 넓힌다. |
| 영향 | DB 변경은 없고 기능 목록, 추적 이름 매핑, 매핑 허용값을 고친다. 서버를 먼저 배포하고 관리자 페이지 배포 전까지 `chat_compact`가 코드 이름 그대로 보인다. 대화 요약 설정을 켜기 전에는 요약 값이 모두 0이다. 대화 요약은 `callsWithoutTokens`가 `calls`와 같아 토큰 합에 들지 않는다. 요약 호출은 응답 대기가 300초까지라 평균 호출 시간이 다른 기능보다 길게 보일 수 있다. 턴당 원가는 요약을 켠 날부터 커진다. Langfuse 모델 설정에 요약 모델 단가가 없으면 `unpricedModels`에 보인다. |

| 항목 | 내용 |

MAU는 전체 조건 `_active`의 30일 `seriesCollapsed` 하나다. 세션의 전체는 세그먼트 `s`에 국가 조건과 `{"prop":"platform","op":"is","values":["Web","Android"]}`를 둔다. |

**47. 신규 가입자는 구글과 카카오 가입 이벤트를 묶은 커스텀 이벤트로 한 사람을 한 번 센다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-30 |
| 상태 | 채택<br>결정 12 채택의 "신규 가입자는 커스텀 이벤트 대신 구글과 카카오 로그인 성공 이벤트를 각각 받아 더한다", 결정 13 대안의 "구성 이벤트 두 개를 합산한다", 결정 35의 플랫폼별 가입 두 이벤트 합, 결정 39의 가입자 시작 집단 두 배열 합을 대체 |
| 배경 | 관리자는 가입을 구글 로그인 성공(`server_login_googleLogin_processed_succeeded`)과 카카오 로그인 성공(`server_login_kakaoLogin_processed_succeeded`) 가운데 `is_new_user`가 `true`인 이벤트로 따로 조회해 더했다. 그래서 같은 날 두 경로로 가입한 사람을 두 번 셌다. 대시보드는 두 이벤트를 OR로 묶은 커스텀 이벤트 `ce:신규 가입 (구글·카카오)`로 한 번 센다(통합 `js7475t8`, Web `fkf1kk5g`, Android `sxngkmwl`). | 대안 | 두 이벤트를 따로 받아 더하는 지금 방식은 사용자가 정한 한 번 세기와 다르다. 두 이벤트를 하나로 합친 서버 이벤트를 새로 보내는 안은 서버 이벤트 계약을 바꾸고 지난 날짜를 채우지 못한다(결정 39 대안). 구글과 카카오 고유 사용자 합에서 두 경로 가입자를 빼는 안은 그 교집합을 REST로 셀 수 없다. |
| 영향 | 커스텀 이벤트 정의가 Amplitude 화면에 있어 이름을 바꾸거나 지우면 조회가 실패하거나 비고, 구성을 바꾸면 확정 전 날짜의 값만 달라지고 확정한 값은 그대로다. 매개변수 해시에는 이름만 들어 구성을 바꿔도 새 키가 생기지 않는다. 커스텀 이벤트의 이름과 구성은 바꾸지 않고 바꿔야 하면 이 결정과 명세를 먼저 고친다. 6-7에서 커스텀 이벤트 조회 값을 대시보드 차트와 대조한다. 캠페인 추이의 가입 조회, 신규 가입자 플랫폼, 가입자 리텐션은 조회 정의가 바뀌어 새 키로 다시 받는다. 비용은 캠페인 가입 조회 6회에서 3회, 신규 가입자 플랫폼 6회에서 3회(결정 46의 `unknown` 제거 포함), 가입자 리텐션 하루 48에서 24로 준다. 같은 날 두 경로 가입 중복이 빠져 값이 조금 작아진다. 게스트 한도 로그인 퍼널의 로그인 성공 단계는 가입이 아니라 로그인이라 이 결정 밖이다. |

**53. 푸시 열람에 앱 알림 열기를 더하고 알림함 열람을 따로 센다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-30 |
| 상태 | 채택<br>결정 28 채택의 "알림 내역(알림함)에서 누른 열람은 범위 밖"과 열람을 웹 페이지 조회로만 센다는 정의, 영향의 Android 열람 누락을 대체 |
| 배경 | 결정 28의 열람은 웹 `[Amplitude] Page Viewed`의 푸시 UTM만 셌다. Android 앱은 푸시와 알림함에서 딥링크를 앱 화면으로 바꿔 열며 쿼리를 버려 Amplitude에 UTM이 남지 않았다. 최근 60일 `utm_source` `push` 페이지 조회는 3건, `inbox`는 21건이고 모두 웹이었다. 도달 회원에는 앱 수신 회원이 들어 열람률이 낮게 나왔다. 사용자가 알림마다 눌러서 들어왔는지 보기로 했다(10/30). 같은 날 Android 담당과 앱이 v1.7.7부터 알림 열기 이벤트 `client_notification_opened`(`screen_name` `notification`)를 보내기로 합의했다. 속성은 딥링크 쿼리의 `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`를 디코딩한 값과 서버 `type` 원문인 `notification_type`이다. 푸시는 누른 순간, 알림함은 항목을 누른 순간 보내고 로그인하지 않았거나 다른 계정의 알림이라 홈으로 가도 보낸다. 딥링크나 UTM이 없으면 보내지 않는다. Android 담당은 업데이트하지 않은 사용자가 이벤트를 보내지 않으니 앱 열람을 앱 배포일부터 세 달라고 요청했다. |
| 채택 | 열람은 웹 페이지 조회와 앱 알림 열기를 따로 조회해 웹, 앱, 합계로 준다. 조회는 두 이벤트와 `utm_source` `push`, `inbox`의 네 조합이고 모두 `utm_campaign` 묶음 하나다. 알림함 열람도 웹, 앱, 합계로 세고 열람률은 두지 않는다. 합계는 웹과 앱 값의 합이다. 측정 시작일은 웹(기존 설정값)과 앱(`MANYAK_ADMIN_PUSH_OPENS_APP_MEASURED_FROM`)으로 나눈다. 플랫폼은 대상의 시작(캠페인은 마지막 회차 선점 KST 날짜, 활동 알림은 집계 구간 첫날)부터 측정했을 때만 세고 아니면 그 플랫폼 값을 `null`로 둔다. 활동 알림의 집계 구간은 설정된 측정 시작일 가운데 가장 이른 날부터다. `openState`는 측정한 플랫폼이 하나도 없을 때 측정 시작 전이다. 응답은 `pushOpens`와 `pushOpenRate`의 뜻을 합계로 바꾸고 `webPushOpens`, `androidPushOpens`, `inboxOpens`, `webInboxOpens`, `androidInboxOpens`, `androidMeasuredFrom`을 더한다. 앱 조회에도 국가와 플랫폼 조건을 넣지 않는다. 알림 열기 이벤트는 앱만 보내기 때문이다. |
| 대안 | 합계를 한 조회의 고유 사용자로 세는 안은 웹과 앱의 이벤트가 달라 세분화 하나로 셀 수 없다(결정 29 대안). 두 이벤트를 묶은 Amplitude 커스텀 이벤트를 만드는 안은 정의가 명세 밖 Amplitude 화면에 남고(결정 47 영향) 웹과 앱 값을 보려면 조회가 더 든다. 그래서 같은 날 웹과 앱에서 모두 연 회원을 두 번 세는 합을 받아들인다. 같은 회원이 다른 날 다시 열면 두 번 세는 날짜별 합(결정 28)과 같은 성격이다. 푸시와 알림함을 `utm_source` `is` `["push","inbox"]` 한 조회에 `utm_source`와 `utm_campaign` 두 묶음으로 받는 안은 플랫폼마다 하루 81이라 두 조회의 50보다 비싸다. 알림함 열람률을 도달 회원 수로 나누는 안은 알림함에 푸시를 끄거나 토큰이 없는 회원의 알림도 기록돼 분모가 맞지 않고 알림함 수신 회원 수는 NOTIFICATION에 집계 연산이 없다. 앱 측정 시작일을 웹과 하나로 두는 안은 앱 배포 전 날짜가 앱 열람 0으로 보인다. 측정 시작 뒤 날짜만 플랫폼마다 더하는 안은 대상의 시작보다 늦게 측정을 시작한 플랫폼이 일부 날짜만 들어 합계와 열람률이 날짜마다 다른 구성의 값이 된다. `pushOpens`를 웹, 앱, 합계 객체로 바꾸는 안은 응답 형태가 바뀌어 관리자 페이지 배포 전까지 열람 칸이 깨진다. 알림함 열람을 계속 세지 않는 안은 웹에서 푸시보다 많은 알림함 진입을 볼 수 없다. |
| 영향 | 푸시 열람의 하루 비용이 25에서 100(앱 측정 시작일 전 날짜는 50)으로, 기본 7일 첫 조회가 175에서 700으로 늘어 한 5분 예산 500에 들지 않는다. 결정 54의 새벽 배치와 초기 백필이 지난 날짜를 채워 평소 화면 요청은 오늘 값만 받는다. 웹 푸시 조회는 지금 조회와 정의가 같아 저장 값을 그대로 쓰고 알림함과 앱 조회는 새 키로 받는다. 앱 측정 시작일은 v1.7.7을 Play에 배포한 날로 설정한다. 그 뒤에도 업데이트하지 않은 회원이 앱에서 연 알림은 빠진다. 앱 이벤트는 누른 순간 보내 홈으로 간 경우도 들어 페이지가 열려야 남는 웹보다 조금 넓다. 범위 첫날이 앱 측정 시작일보다 앞선 기간은 활동 알림의 앱 값이 `null`이다. 서버를 먼저 배포하면 관리자 페이지 배포 전까지 푸시 열람 칸에 합계가 웹 기준 안내와 함께 보인다. |

| 배경 | 사용자가 알림 화면의 캠페인 상세에서도 그 캠페인의 열람을 보기로 했다(10/30). 캠페인 상세는 NOTIFICATION의 `GET /admin/push/campaigns/{campaignId}`이고 캠페인 목록, 예약, 취소, 재실행과 같은 캠페인 구조를 쓴다. 열람의 Amplitude 조회, 값 저장, 비용 예산은 ADMIN에 있다. 캠페인 상세 화면에는 기간 선택이 없다. |
| 채택 | ADMIN에 `GET /admin/campaigns/push-opens/{campaignId}`를 둔다. 집계 범위는 마지막 회차 선점 KST 날짜부터 오늘까지이고 366일에서 자른다. 조회 정의는 푸시 열람과 같아 같은 키의 저장 값을 함께 쓰고 측정함이 아니면 분석 도구를 부르지 않는다. 캠페인의 선점 시각, 딥링크 포함 여부, 도달 회원 수는 NOTIFICATION의 새 연산인 캠페인 하나의 도달 요약으로 읽는다. 관리자 웹 캠페인 상세는 상세와 열람을 따로 부른다. 푸시 열람의 네 조회를 새벽 배치와 초기 백필의 기본 지표 키에 넣고 백필은 플랫폼마다 측정 시작일부터 받는다. |
| 대안 | NOTIFICATION 캠페인 상세 응답에 열람을 싣는 안은 결정 28 대안처럼 NOTIFICATION이 ADMIN 분석 저장소를 불러 ADMIN에서 NOTIFICATION으로 읽기만 하는 의존 방향이 뒤집히고 캠페인 상세가 분석 도구 장애와 최대 10초 대기에 묶인다. 캠페인 구조를 함께 쓰는 목록, 예약, 취소, 재실행 응답에도 필드가 생기거나 상세만 다른 구조가 된다. 푸시 열람 API에 `campaignId` 쿼리를 더하는 안은 한 경로가 기간 응답과 캠페인 응답 두 형태를 갖고 기간 쿼리와의 조합 규칙이 생긴다. 관리자 웹이 캠페인 상세의 선점 날짜로 기간을 정해 푸시 열람 API를 부르는 안은 서버 변경이 없지만 상세 응답을 받은 뒤에야 보낼 수 있고 응답에 그 기간의 모든 캠페인과 활동 알림이 함께 온다. 집계 범위를 선점일부터 7일로 고정하는 안은 캠페인끼리 비교하기 쉽지만 상세에서 기대하는 지금까지의 열람과 다르다. 새벽 배치에 넣지 않는 안은 지난 캠페인 상세를 처음 열 때 날짜마다 100이 들어 선점한 지 5일이 지난 캠페인부터 한 5분 예산 500에 들지 않아 준비 중으로 보인다. |
| 영향 | 관리자 경로 회귀 테스트의 수집 수가 하나 는다. 4-2의 다른 도메인과의 경계가 4-2-43으로 밀린다. NOTIFICATION 경계에 캠페인 하나의 도달 요약 연산이 는다. 새벽 배치 하루 비용은 1,112에서 1,212(앱 측정 시작일 전 1,162)가 되어 5분 300씩 다섯 번에 끝난다. 초기 백필은 웹 측정 시작일부터 확정일까지 하루 50, 앱 측정 시작일부터 하루 50을 더 받는다. 캠페인 열람은 오늘이 집계 범위 안이면 오늘 값만 10분마다 다시 받고 이 키는 관리자 웹 알림 열람 하위 구분과 함께 쓴다. 회차를 다시 실행한 캠페인은 마지막 회차의 선점 날짜부터 세어 앞 회차를 그 전 날짜에 연 열람은 빠진다. 서버를 먼저 배포하고 관리자 웹을 뒤에 배포한다. |

**55. 푸시 열람의 활동 알림에 이프 만료 예정 알림을 넣는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-30 |
| 상태 | 채택<br>결정 33 채택의 활동 알림 세 종류 유지를 대체 |
| 배경 | 이프 만료 예정 알림(`CREDIT_EXPIRY_REMINDER`, NOTIFICATION 결정 13)이 생긴 뒤 서버의 푸시 열람과 관리자 웹은 활동 알림을 네 종류로 다뤘고 명세는 세 종류였다. 이 알림은 알림 내역의 `ACTIVITY` 분류이고 딥링크가 있어 열람을 셀 수 있다. 사용자가 명세를 코드에 맞춰 네 종류로 두기로 했다(10/30). 이 알림의 알림함 사본은 푸시 데이터와 같은 딥링크(`utm_source` `push`)를 저장한다(NOTIFICATION 결정 19 보완). |
| 채택 | 활동 알림은 `STORY_COMPLETED`, `STORY_MODERATION_COMPLETED`, `ATTENDANCE_REMINDER`, `CREDIT_EXPIRY_REMINDER` 순서의 네 종류이고 종류 코드 `credit_expiry_reminder`로 대응한다. 알림함에서 누른 이 알림의 열람은 푸시 열람으로 들고 알림함 열람은 0으로 둔다. 이 한계는 제품 제약과 지표 정의에 적는다. 공개 중단 알림은 계속 넣지 않는다. |
| 대안 | 명세대로 세 종류로 줄이는 안은 이미 배포된 서버와 관리자 웹을 되돌려야 하고 회원 자산 안내 알림의 재방문을 볼 수 없다. 이 알림의 알림함 사본 딥링크를 `inbox` UTM으로 바꾸는 안은 NOTIFICATION 결정 19 보완을 뒤집는 다른 도메인 변경이라 이번 범위 밖이다. 이 알림의 알림함 열람을 따로 셀 방법이 없어 푸시 열람에서 빼는 안은 푸시로 연 열람까지 빠진다. |
| 영향 | 응답의 `activityTypes`가 4항목이 되고 관리자 웹 활동 알림 표가 4행이 된다. 조회와 비용은 같다. 묶음 값 하나를 더 대응할 뿐이다. 이 알림의 열람률은 알림함에서 연 회원도 분자에 들고 분모는 푸시 도달 회원뿐이라 다른 활동 알림보다 높게 나올 수 있다. |
