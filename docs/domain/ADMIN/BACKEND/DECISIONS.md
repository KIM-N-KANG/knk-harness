# DECISIONS.md

ADMIN 도메인 백엔드의 중요한 결정을 날짜, 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 둔다. 여기에는 결정 당시의 이유와 변경 이력을 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 상태는 결정 당시 기준이다. 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.

<br>

### 2. 도메인 배치

**1. 운영 기능은 데이터의 주인 도메인이 정하고 ADMIN은 관리자 자체의 것만 정한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 이프 정책값, 캠페인, 계정 정지, 검수 보류 해제가 "운영자가 저장소에서 직접 변경"으로 정의돼 있어 DB에 접근하는 한 사람만 처리할 수 있었다. 원장과 아웃박스 같은 불변식을 SQL이 우회할 위험도 있었다. 관리자 페이지를 만들면서 관리자 기능을 어느 세트에 둘지 정해야 했다. |
| 채택 | 바뀌는 데이터를 관리하는 도메인이 그 관리자 API를 정한다. 이프 지급과 정책값은 PAYMENT, 캠페인과 문구는 NOTIFICATION, 공지는 NOTICE, 계정 정지는 ACCOUNT, 보류 해제는 MODERATION이 정한다. ADMIN은 관리자 인증과 권한, 감사 로그, 대시보드, 회원 조회만 정한다. 모든 관리자 API는 `/api/v1/admin/` 아래에 두고 ADMIN의 판정 필터와 감사 기록 연산을 쓴다. |
| 대안 | 관리자 기능 전부를 ADMIN 세트 하나에 모으는 안. 원장 규칙, 캠페인 선점 규칙, 정지 집행 규칙을 두 세트가 같이 정하게 되어 같은 사실을 두 곳에서 정하게 된다. |
| 영향 | 기존 네 세트의 "운영자가 저장소에서 직접 변경" 항목이 관리자 API로 바뀌었다. 관리자 역할 부여와 회수만 저장소 직접 변경으로 남는다. 각 세트의 4-2에 `관리자` 인증 수준이 생겼고 그 토큰 규칙은 ADMIN 4-2가 정한다. |

<br>

### 3. 인증과 권한

**2. 관리자 토큰은 대상 클레임으로 구분하고 갱신 없이 1시간만 유효하다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 서버에 역할 개념이 없었다. 앱 접근 토큰을 그대로 관리자 API에 쓰면 앱 토큰 유출이 곧 관리자 권한 유출이 된다. 관리자 페이지는 별도 호스트의 서버 측 처리기가 호출하며 토큰을 httpOnly 쿠키에 둔다. |
| 채택 | 관리자 전용 로그인이 Google 신원 증명을 앱과 같은 검증기로 검증하고 관리자 역할이 있는 활성 회원에게만 토큰을 발급한다. 토큰은 앱과 같은 대칭키의 HS256 JWT에 대상 클레임 `manyak-admin`을 더해 구분한다. 앱 경로는 대상 클레임이 있는 토큰을 거절하고 관리자 경로는 대상 클레임이 없는 토큰을 거절한다. 수명은 1시간이고 갱신 토큰이 없다. 역할은 토큰 값을 믿지 않고 요청마다 저장소에서 다시 읽는다. |
| 대안 | 앱 접근 토큰에 역할 클레임을 넣는 안은 토큰 수명 동안 회수가 반영되지 않고 앱 토큰 유출이 관리자 권한 유출이 된다. 별도 대칭키는 주입할 시크릿이 늘어난다. 갱신 토큰을 두는 안은 앱과 같은 회전과 재사용 탐지 복잡도를 관리자에게도 들여온다. 수명은 앱 접근 토큰 30분, 동의 대기 코드 10분, 링크 코드 5분을 보고 정했다. 30분은 갱신 없이 쓰기에 짧고 8시간 이상은 쿠키 탈취 위험에 노출되는 시간이 길어 두 배인 1시간으로 했다. |
| 영향 | 관리자가 앱을 쓰려면 앱 로그인을 따로 한다. 개별 토큰 폐기는 없고 역할 회수와 계정 정지가 즉시 차단 수단이다. 대칭키를 바꾸면 앱과 관리자 토큰이 함께 무효가 된다. 관리자 페이지는 1시간마다 다시 로그인한다. |

<br>

**3. 관리자 역할 부여와 회수는 API 없이 저장소에서만 한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 관리자 페이지의 쿠키나 계정이 탈취되면 공격자가 자기 계정에 역할을 더하거나 다른 관리자를 지울 수 있다. |
| 채택 | 역할 행의 추가와 삭제는 마이그레이션이나 SQL로만 한다. 관리자 API에는 역할을 바꾸는 경로가 없다. 관리자 역할이 있는 회원은 계정 정지 API의 대상이 될 수 없고 정지하려면 역할을 먼저 회수한다. |
| 대안 | 관리자 사이의 등급을 두고 상위 관리자만 역할을 바꾸게 하는 안. 팀 구성원이 소수라 등급을 둘 실익이 없고 상위 계정 탈취 시 같은 문제가 남는다. |
| 영향 | 첫 관리자는 배포 뒤 운영 DB에서 직접 넣는다. 관리자끼리 정지시킬 수 없어 관리자 화면 탈취로 다른 관리자를 잠그는 공격이 막힌다. |

<br>

### 4. 감사

**4. 모든 관리자 변경은 같은 트랜잭션의 감사 로그로 남기고 회원 조회도 접속 기록으로 남긴다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 여러 사람이 운영 작업을 하면 누가 언제 왜 바꿨는지 알아야 한다. 회원 개인정보를 조회하는 관리자 화면은 개인정보 안전성 확보조치의 접속 기록 보관 대상이다. |
| 채택 | 다른 도메인의 관리자 API는 변경을 적용한 뒤 같은 트랜잭션에서 감사 기록 연산을 호출한다. 기록에 실패하면 변경도 롤백된다. 처리자, 작업 이름, 대상의 외부 식별자, 사유, 변경 전후 값, 요청 ID를 남긴다. 회원 검색과 상세는 조회 뒤 독립 트랜잭션으로 접속 기록을 남기고 기록에 실패하면 조회 응답도 실패로 바꾼다. 감사 로그는 삭제와 수정 경로가 없고 영구 보존한다. |
| 대안 | 변경 뒤 비동기로 로그를 남기는 안은 로그 없는 변경을 만든다. 애플리케이션 로그에만 남기는 안은 보존 기간과 조회 수단이 로그 스택에 묶이고 관리자 페이지에서 볼 수 없다. 보존 기간을 1년이나 2년으로 정하는 안은 삭제 배치가 필요하고 법정 최소 기간을 넘기는 영구 보존이 더 단순하다. |
| 영향 | 모든 변경 API 요청 본문에 사유가 필수다. 관리자 역할이 있는 회원의 탈퇴는 회원 행이 남으므로 처리자 FK가 깨지지 않는다. 사유는 자유 문장이라 개인정보가 들어갈 수 있는 한계를 수용했다. |

<br>

### 5. 대시보드

**5. 대시보드는 서버 DB에 있는 숫자만 집계하고 방문자 수와 외부 도구는 연동하지 않는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 운영 지표가 분석 도구, 오류 추적 도구, AI 관측 도구, 운영 DB에 흩어져 있다. 방문자 수의 기준은 클라이언트 기기 식별자와 분석 도구다. |
| 채택 | 회원, 채팅, 스토리, 이프, 결제, 검수 보류의 오늘과 누적 수치를 서버 DB에서 집계한다. 오늘은 KST 자정 기준이고 한 응답의 모든 지표는 같은 기준 시각으로 계산한다. 채팅 턴은 AI 응답 메시지 수로 세고 재생성 판본은 세지 않는다. 방문자 수는 세지 않고 오류 추적 도구와 AI 관측 도구는 관리자 페이지가 링크만 둔다. |
| 대안 | 서버가 요청 로그로 방문자를 세는 안은 분석 도구의 숫자와 다른 두 번째 숫자를 만든다. 외부 도구 API를 서버가 호출하는 안은 자격 증명 주입과 장애 전파 범위를 늘린다. |
| 영향 | 지표 정의는 기존 세트의 테이블 의미를 따르며 팀 계정을 제외하지 않는다. 집계는 요청마다 실행하고 캐시하지 않는다. |
