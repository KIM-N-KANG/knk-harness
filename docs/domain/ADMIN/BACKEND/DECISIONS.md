# DECISIONS.md

ADMIN 도메인 백엔드의 중요한 결정을 날짜, 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 둔다. 여기에는 결정 당시의 이유와 변경 이력을 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 상태는 결정 당시 기준이다. 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.

<br>

### 2. 도메인 배치

**1. 운영 기능의 도메인별 배치**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 이프 정책값, 캠페인, 계정 정지, 검수 보류 해제가 "운영자가 저장소에서 직접 변경"으로 정의돼 있어 DB에 접근하는 한 사람만 처리할 수 있었다. 원장과 아웃박스 같은 불변식을 SQL이 우회할 위험도 있었다. 관리자 페이지를 만들면서 관리자 기능을 어느 세트에 둘지 정해야 했다. |
| 채택 | 바뀌는 데이터를 관리하는 도메인이 그 관리자 API를 정한다. 이프 지급과 정책값은 PAYMENT, 캠페인과 문구는 NOTIFICATION, 공지는 NOTICE, 계정 정지는 ACCOUNT, 보류 해제는 MODERATION, 오리지널 등록과 수정은 STORY가 정한다. ADMIN은 관리자 인증과 권한, 감사 로그, 대시보드, 회원 조회만 정한다. 모든 관리자 API는 `/api/v1/admin/` 아래에 두고 ADMIN의 판정 필터와 감사 기록 연산을 쓴다. |
| 대안 | 관리자 기능 전부를 ADMIN 세트 하나에 모으는 안. 원장 규칙, 캠페인 선점 규칙, 정지 집행 규칙을 두 세트가 같이 정하게 되어 같은 사실을 두 곳에서 정하게 된다. |
| 영향 | 기존 네 세트의 "운영자가 저장소에서 직접 변경" 항목이 관리자 API로 바뀌었다. 관리자 역할 부여와 회수, 전송 중 상태로 멈춘 캠페인을 실패로 바꾸는 작업만 저장소 직접 변경으로 남는다. 각 세트의 4-2에 `관리자` 인증 수준이 생겼고 그 토큰 규칙은 ADMIN 4-2가 정한다. |

### 3. 인증과 권한

**2. 관리자 토큰의 구분과 2시간 수명**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 서버에 역할 개념이 없었다. 앱 접근 토큰을 그대로 관리자 API에 쓰면 앱 토큰 유출이 곧 관리자 권한 유출이 된다. 관리자 페이지는 별도 호스트의 서버 측 처리기가 호출하며 토큰을 httpOnly 쿠키에 둔다. |
| 채택 | 관리자 전용 로그인이 Google 신원 증명을 앱과 같은 검증기로 검증하고 관리자 역할이 있는 활성 회원에게만 토큰을 발급한다. 토큰은 앱과 같은 대칭키의 HS256 JWT에 대상 클레임 `manyak-admin`을 더해 구분한다. 앱 경로는 대상 클레임이 있는 토큰을 회원으로 식별하지 않아 인증 필수 경로에서는 거절하고 선택 인증 경로에서는 익명으로 처리하며, 관리자 경로는 대상 클레임이 없는 토큰을 거절한다. 수명은 2시간이고 갱신 토큰이 없다. 역할은 토큰 값을 믿지 않고 요청마다 저장소에서 다시 읽는다. |
| 대안 | 앱 접근 토큰에 역할 클레임을 넣는 안은 토큰 수명 동안 회수가 반영되지 않고 앱 토큰 유출이 관리자 권한 유출이 된다. 별도 대칭키는 주입할 시크릿이 늘어난다. 갱신 토큰을 두는 안은 앱과 같은 회전과 재사용 탐지 복잡도를 관리자에게도 들여온다. 수명은 앱 접근 토큰 30분, 동의 대기 코드 10분, 링크 코드 5분을 보고 정했다. 30분은 갱신 없이 쓰기에 짧고 8시간 이상은 쿠키 탈취 위험에 노출되는 시간이 길다. 캠페인 예약과 공지 게시처럼 여러 단계가 이어지는 운영 작업 한 묶음을 재로그인 없이 마칠 수 있도록 2시간으로 했다. |
| 영향 | 관리자가 앱을 쓰려면 앱 로그인을 따로 한다. 개별 토큰 폐기는 없고 역할 회수와 계정 정지가 즉시 차단 수단이다. 대칭키를 바꾸면 앱과 관리자 토큰이 함께 무효가 된다. 관리자 페이지는 2시간마다 다시 로그인한다. |

**3. 관리자 역할의 별도 저장과 DB 관리**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 관리자 페이지의 쿠키나 계정이 탈취되면 공격자가 자기 계정에 역할을 더하거나 다른 관리자를 지울 수 있다. |
| 채택 | 역할은 `users`의 컬럼이 아니라 `admin_accounts` 행의 존재로 표현한다. 역할 행의 추가와 삭제는 마이그레이션이나 SQL로만 한다. 관리자 API에는 역할을 바꾸는 경로가 없다. 관리자 역할이 있는 회원은 계정 정지 API의 대상이 될 수 없고 정지하려면 역할을 먼저 회수한다. |
| 대안 | 관리자 사이의 등급을 두고 상위 관리자만 역할을 바꾸게 하는 안. 팀 구성원이 소수라 등급을 둘 실익이 없고 상위 계정 탈취 시 같은 문제가 남는다. `users`에 역할 컬럼을 두는 안은 조회 한 번을 줄이고 구조가 단순하지만 세 가지 이유로 기각했다. `users`와 그 수명 규칙인 탈퇴, 정지, 재가입은 ACCOUNT가 정하므로 역할 컬럼을 넣으면 두 세트가 같은 테이블을 나눠 정하게 된다. 역할이 `users`에 있으면 프로필 수정처럼 회원 행을 바꾸는 API의 바인딩 실수가 곧 권한 상승이 되는데, 별도 테이블이면 회원 API에 그 테이블을 바꾸는 경로가 없다. 부여 시각 같은 정보를 `users`의 nullable 컬럼으로 늘리지 않고 두며 회수는 행 삭제로 끝난다. |
| 영향 | 첫 관리자는 배포 뒤 운영 DB에서 직접 넣는다. 관리자끼리 정지시킬 수 없어 관리자 화면 탈취로 다른 관리자를 잠그는 공격이 막힌다. |

### 4. 감사

**4. 관리자 변경 감사와 회원 조회 접속 기록**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 여러 사람이 운영 작업을 하면 누가 언제 왜 바꿨는지 알아야 한다. 회원 개인정보를 조회하는 관리자 화면은 개인정보 안전성 확보조치의 접속 기록 보관 대상이다. |
| 채택 | 다른 도메인의 관리자 API는 변경을 적용한 뒤 같은 트랜잭션에서 감사 기록 연산을 호출한다. 기록에 실패하면 변경도 롤백된다. 처리자, 작업 이름, 대상의 외부 식별자, 사유, 변경 전후 값, 요청 ID를 남긴다. 회원 검색과 상세는 조회 뒤 독립 트랜잭션으로 접속 기록을 남기고 기록에 실패하면 조회 응답도 실패로 바꾼다. 감사 로그는 삭제와 수정 경로가 없고 영구 보존한다. |
| 대안 | 변경 뒤 비동기로 로그를 남기는 안은 로그 없는 변경을 만든다. 애플리케이션 로그에만 남기는 안은 보존 기간과 조회 수단이 로그 스택에 묶이고 관리자 페이지에서 볼 수 없다. 보존 기간을 1년이나 2년으로 정하는 안은 삭제 배치가 필요하고 법정 최소 기간을 넘기는 영구 보존이 더 단순하다. |
| 영향 | 모든 변경 API 요청 본문에 사유가 필수다. 감사 로그가 요청 ID를 64자로 저장하므로 상관관계 필터가 헤더 값의 길이와 문자를 검사해 어긋나면 서버 생성 값으로 바꾸고 응답 헤더와 감사 로그가 같은 값을 쓴다. 거절 대신 재발급을 택한 것은 상관관계 헤더가 클라이언트 추적 편의용이라 요청 자체를 막을 이유가 없기 때문이다. 관리자 역할이 있는 회원의 탈퇴는 회원 행이 남으므로 처리자 FK가 깨지지 않는다. 사유는 자유 문장이라 개인정보가 들어갈 수 있는 한계를 수용했다. |

### 5. 대시보드

**5. 서버 DB 대시보드 집계와 외부 연동 제외**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 운영 지표가 분석 도구, 오류 추적 도구, AI 관측 도구, 운영 DB에 흩어져 있다. 방문자 수의 기준은 클라이언트 기기 식별자와 분석 도구다. |
| 채택 | 회원, 채팅, 스토리, 이프, 결제, 검수 보류의 오늘과 누적 수치를 서버 DB에서 집계한다. 오늘은 KST 자정 기준이고 한 응답의 모든 지표는 같은 기준 시각으로 계산한다. 채팅 턴은 AI 응답 메시지 수로 세고 재생성 판본은 세지 않는다. 팀 계정은 설정값의 회원 내부 ID 목록으로 모든 지표에서 제외하며 기본 목록은 운영 Terraform의 Grafana 서비스 통계 대시보드가 소비 활동에서 제외하는 팀 계정과 같다. 방문자 수는 세지 않고 오류 추적 도구와 AI 관측 도구는 관리자 페이지가 링크만 둔다. |
| 대안 | 서버가 요청 로그로 방문자를 세는 안은 분석 도구의 숫자와 다른 두 번째 숫자를 만든다. 외부 도구 API를 서버가 호출하는 안은 자격 증명 주입과 장애 전파 범위를 늘린다. |
| 영향 | 지표 정의는 기존 세트의 테이블 의미를 따른다. 팀 계정 제외는 대시보드에만 적용하고 회원 조회와 감사 로그에는 적용하지 않는다. 목록을 코드에 두지 않아 팀원이 바뀌면 환경 변수만 바꾼다. 집계는 요청마다 실행하고 캐시하지 않는다. 탈퇴 수, 환불 건수, 검수 보류 수는 결정 7에서 요약에서 뺐다. |

### 6. 목록

**6. 관리자 목록의 번호 페이지와 열 정렬**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 앱의 목록은 무한 스크롤이라 keyset 커서를 쓴다. 관리자 페이지는 표 머리글을 눌러 정렬하고 아래 페이지 번호로 이동하는 화면이라 전체 건수와 임의 페이지 접근이 필요하다. 처음 초안은 앱과 같은 커서 방식이었다. |
| 채택 | 모든 관리자 목록은 `page`(1부터)와 `size`(1~100, 기본 20)로 요청하고 `items`, `page`, `size`, `totalElements`, `totalPages`를 돌려준다. 정렬은 `sort`와 `order`로 받고 허용 목록 밖은 거절한다. 같은 값은 항목의 공개 식별자 오름차순으로 고정해 페이지 사이에 행이 겹치거나 빠지지 않게 한다. 다른 도메인의 관리자 목록(캠페인, 공지, 보류)도 같은 구조를 쓴다. |
| 대안 | 커서 방식은 임의 페이지와 전체 건수를 줄 수 없고 정렬 열마다 커서 형식이 달라진다. 커서를 유지하고 전체 건수만 더하는 안은 두 방식을 함께 유지하게 된다. 내부 ID로 동률을 고정하는 안은 응답에 없는 값이라 클라이언트가 순서를 재현할 수 없다. |
| 영향 | 전체 건수 조회와 페이지 조회가 각각 실행되어 큰 OFFSET과 필터 COUNT가 전체 스캔이 될 수 있다. 관리자 전용 저빈도 호출이라 수용한다. 관리자 커서 비봉인 규칙과 관련 보안 행은 없어졌다. 공지와 알림 종류별 통계처럼 앱이 쓰는 목록은 그대로 커서다. |

**7. 대시보드에서 목록과 상세로 이어지는 읽기 조회**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 운영 통계는 Grafana 서비스 통계 대시보드의 SQL 패널 23개로 보고 있었고 DB 접근 권한이 있는 한 사람만 패널 뒤의 데이터를 따라갈 수 있었다. 관리자 페이지의 첫 화면을 차트 대시보드로 정하고 차트를 누르면 조건이 걸린 목록, 목록에서 상세로 가는 구조를 정했다. 요약의 탈퇴, 환불, 검수 보류 카드는 쓰임이 없다고 판단했다. |

### 8. 캠페인 분석

**12. 캠페인 분석은 저장 차트 대신 명세의 정의로 Amplitude를 직접 조회하고 비용 예산으로 호출을 나눈다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-23 |
| 상태 | 채택 |
| 배경 | 광고 캠페인 성과를 Amplitude 대시보드의 차트 8개로 보고 있었다. 사용자는 차트가 지워지거나 바뀔 수 있어 저장 차트를 가져오지 않기를 원했다. 원본 차트는 광고 유입을 행동 세그먼트(기간 이후 그 캠페인 속성으로 활성 이벤트 1회 이상)로 정의하는데 REST 조회에서 같은 속성 조건으로 바꿔 2026-10-22 값을 대조하니 광고 152, 전체 162로 차트와 같았다. Dashboard REST API의 비용 한도는 5분 1,000이고 세분화 조회는 일수 × 이벤트 수, 퍼널 조회는 일수 × 단계 수 × 2다. |
| 채택 | 지표 정의를 명세에 두고 서버가 이벤트 세분화와 퍼널 조회로 계산한다. 광고 유입은 사용자 속성 `gp:initial_utm_campaign` 조건으로 대체하고 광고 외 유입은 조회하지 않고 전체에서 뺀다. 신규 가입자는 커스텀 이벤트 대신 구글과 카카오 로그인 성공 이벤트를 각각 받아 더한다. 캠페인 값, 대상 스토리는 쿼리와 설정값으로 받고 소스 목록은 고정값이다. 엔드포인트는 추이(하루 비용 14)와 퍼널(하루 비용 38)로 나눈다. 추이 상한 45일(630), 퍼널 상한 7일(266)로 두 묶음을 같은 5분에 모두 갱신해도 896으로 예산 안이다. 모든 Amplitude 호출은 5분 1,000의 예산 계수기를 공유해 예상 비용이 남은 예산을 넘으면 호출하지 않고 쿨다운처럼 처리한다. 한 갱신 안의 조회는 하나씩 순서대로 보낸다. 캐시 10분, 단일 갱신, 쿨다운 60초, 장애 격리는 분석 지표 규칙을 재사용한다. 팀 계정 코호트는 제외하지 않는다. |
| 대안 | 저장 차트 조회 API는 차트 삭제와 변경에 깨지고 정의가 명세 밖에 있게 된다. 한 엔드포인트에 8개 지표를 모두 담는 안은 30일 기준 하루 비용 52로 1,560이 되어 5분 예산을 넘는다. 퍼널을 30일까지 허용하는 안은 퍼널만 1,140이다. 광고 외 유입을 따로 조회하는 안은 비용이 늘고 속성 `is not` 조건의 null 처리 차이가 생긴다. 행동 세그먼트를 REST로 그대로 옮기는 안은 세그먼트 정의가 복잡하고 대조 결과 차이가 없었다. 예산을 계수하지 않는 안은 관리자 둘이 다른 캠페인을 같은 때 열면 한도 초과 응답이 쿨다운으로 이어져 한 명이 1분 동안 아무 값도 못 본다. |
| 영향 | 캠페인 퍼널은 7일 창으로만 본다. 추이와 퍼널의 기간 선택기가 따로다. 신규 가입자는 같은 날 두 경로로 가입한 사용자를 두 번 셀 수 있다. 원본 차트와 달리 신규 가입자의 `platform` 조건이 행동 필터가 아니라 사용자 속성이라 모바일 앱에서 가입한 사용자가 섞일 수 있어 구현 후 하루치 대조가 필요하다. 2026-10-23 운영 키로 확인한 결과 서버 가입 이벤트 대부분에 `platform` 속성이 없어(사흘치 none 13, Android 2, Web 1) 속성 조건을 걸면 가입자가 거의 빠지므로 가입자 조회에는 `platform` 조건을 두지 않고 `country`와 `gp:initial_utm_campaign`만 쓴다. 플랫폼별 가입은 Amplitude로 세지 않는다. 설정에 기본 캠페인과 기본 대상 스토리가 생긴다. |
| 보완 | 2026-10-23 사용자 지시 반영. 캠페인은 설정 파일의 캠페인 목록(1차 202607 7/21~7/31, 2차 202608 8/21~9/16, 3차 202609 9/17~10/21, 4차 202610 10/22~)으로 고르고 기간이 함께 채워진다. 환경 변수 기본 캠페인과 기본 스토리는 목록으로 대체했다. 퍼널은 간편 제작과 상세 진입을 별도 엔드포인트로 나눠 각각 31일 상한(744, 434)으로 올렸다. 유입 소스와 매체와 게시글별 방문자 표를 더했다. 광고 유입 정의는 사용자 속성 `gp:initial_utm_campaign` 하나로 통일하고 9월 대시보드가 쓴 페이지 조회 이벤트 속성 `utm_campaign`과 `utm_medium` 방식은 쓰지 않는다. 사용자 불변 속성이라 차수 간 비교가 가능하고 방문 이벤트 속성은 같은 사용자를 여러 캠페인에 넣을 수 있기 때문이다. 오늘을 포함하지 않는 범위는 값이 바뀌지 않아 캐시를 24시간으로 늘렸고 결정 10의 "과거 범위도 10분"은 이 보완이 대체한다. |
| 보완 | 2026-10-23 결정 15로 비용 산식, 예산, 기간 상한이 바뀌었다. 채택의 하루 비용 14와 38, 5분 1,000 공유 계수기, 보완의 31일 상한(744, 434)은 조건 수를 세지 않은 값이다. 현재 상한은 추이 35일, 간편 제작 퍼널 20일, 상세 진입 퍼널 31일, 유입 소스 10일이고 사용자 속성 조건은 세그먼트가 아니라 이벤트 필터로 넣는다. 유입 소스 표는 매체로, 게시글 표는 소스로 묶지 않는다. |

**28. 푸시 열람은 유입 분석의 탭으로 두고 웹 페이지 조회의 푸시 UTM으로 센다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-24 |
| 상태 | 채택 |
| 배경 | 푸시 딥링크에 팀 UTM 규격의 네 필드가 붙었다(NOTIFICATION 결정 16). 유입 분석은 첫 유입 속성 기준이라 이미 가입한 회원이 대상인 푸시는 잡히지 않았다. 사용자가 캠페인별로 발송 성공 대비 열람 수와 열람률을 보기로 했다(10/24). |
| 채택 | 서버가 `[Amplitude] Page Viewed`에 이벤트 속성 `utm_source`가 `push`인 이벤트 필터와 `utm_campaign` 이벤트 묶음을 걸어 날짜별 고유 사용자 수를 받고 캠페인 공개 식별자와 활동 알림 종류 코드로 나눈다. 분모는 NOTIFICATION 발송 결과의 도달 회원 수이고 활동 알림은 종류와 날짜마다 회원을 중복 없이 센다. 엔드포인트는 ADMIN의 `GET /admin/campaigns/push-opens`이고 관리자 웹 유입 분석의 푸시 열람 탭이 쓴다. 일별 지표로 저장해 366일까지 보고 열람 수는 날짜별 고유 사용자 수의 합이다. 국가, 플랫폼, 팀 계정 조건은 넣지 않는다. 측정 시작일(설정값) 전은 0이 아니라 측정 시작 전으로 구분하고 마지막 회차가 딥링크 없이 나간 캠페인은 측정 불가로 구분한다. 알림 내역(알림함)에서 누른 열람은 푸시를 보고 들어온 것이 아니라 범위 밖이다(사용자 결정 10/24). 전환(채팅 시작 등)도 넣지 않는다. |
| 대안 | NOTIFICATION 캠페인 상세 응답에 붙이는 안은 Amplitude 값 저장과 비용 예산이 ADMIN에 있어 NOTIFICATION이 ADMIN 분석 저장소를 불러야 하고 캠페인 상세가 분석 도구 장애에 묶인다. 알림 화면은 관리자 웹 세트 밖이라 화면 계약을 둘 곳도 없다. 유입 분석은 이미 Amplitude의 UTM 지표를 탭으로 보여 주므로 같은 기간 선택기와 출처 표시를 쓴다. 범위 고유 사용자(`seriesCollapsed`)로 같은 회원의 재열람을 한 번만 세는 안은 범위 지표가 되어 하루 비용 25에 20일 상한이 생긴다. 캠페인마다 고정 값 필터로 조회하는 안은 캠페인이 늘 때마다 조회 정의와 호출이 늘어 묶음 조회 1회보다 복잡하다. 이동 대상 스토리의 유무로 측정 불가를 정하는 안은 회차 때 스토리가 비공개여서 딥링크 없이 나간 캠페인을 열람 0으로 보이게 한다. |
| 영향 | Amplitude 조회 1회와 하루 비용 25가 늘고 기본 7일 첫 조회는 175다. NOTIFICATION 캠페인에 딥링크 포함 여부가 발송 요청과 같은 트랜잭션에서 기록되고 재실행해도 한 번 참이면 거짓으로 바뀌지 않는다. 딥링크를 넣은 요청이 하나라도 있으면 열람이 생길 수 있어 측정함으로 보고 발송 요청 기록이 없는 캠페인은 발송 기록 없음으로 둔다. Android 앱은 페이지 조회 이벤트를 보내지 않고 푸시 진입은 딥링크를 앱 화면으로 바꿔 열어 Android에서 연 알림이 열람에 빠진다. Android 수신자가 많을수록 열람률이 낮게 나온다. 같은 회원이 같은 알림을 다른 날 다시 열면 두 번 세어 열람률이 1을 넘을 수 있다. 측정 시작일은 푸시 UTM이 든 서버를 운영에 배포한 날로 설정한다. 2026-10-24 운영 데이터에서 페이지 조회의 UTM 이벤트 속성이 그 페이지 주소의 쿼리 값임을 광고 유입으로 확인했다. 지난 30일 페이지 조회는 모두 `platform` `Web`이었고 `utm_source` `push` 값은 서버 릴리스 전이라 아직 없다. 첫 릴리스 뒤 캠페인 하나로 값을 대조한다. |

**29. Android 사용자는 국가와 무관하게 세고 플랫폼을 가로지르는 값은 두 조회의 합으로 계산한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-24 |
| 상태 | 채택. 결정 8 보완과 결정 13, 25의 국가 조건을 Android에 한해 대체 |
| 배경 | Amplitude 기반 관리자 지표가 모든 조회에 사용자 속성 `country`가 `South Korea` 또는 `(none)`인 조건을 걸어 미국에서 스토리를 만든 Android 사용자가 빠졌다. 국가 조건은 해외 봇이 들어오는 Web을 막으려고 둔 것이다. 사용자가 Android는 앱 설치가 필요하므로 국가와 무관하게 세기로 했다(10/24). |
| 채택 | Web과 플랫폼 속성이 없는 사용자는 국가 조건을 유지하고 Android 조회에서는 국가 조건을 뺀다. 팀 계정 코호트 제외는 그대로다. 합계와 전체처럼 플랫폼을 가로지르는 값은 Android 외 조회(국가 조건과 `platform` `is not` `Android`)와 Android 조회의 합이다. 분석 지표의 합계 조회는 없애고 Web과 Android 값을 더한다. 리텐션 전체는 두 코호트의 `count`와 `outof`를 더한다. 평균 세션 길이 전체는 더할 수 없어 국가 조건만 건 조회를 유지한다. 전환 퍼널은 플랫폼마다 따로라 Android 퍼널에서 국가 조건만 뺀다. 캠페인 분석(Web 전용)과 푸시 열람(결정 28)은 바꾸지 않는다. 지난 저장 값은 매개변수 해시가 바뀐 조회만 새 키로 다시 받고 해시가 같은 Web 조회의 값은 그대로 쓴다. |
| 대안 | "Android 또는 (Web 그리고 국가 조건)"을 한 조회로 세는 안은 Dashboard REST가 지원하지 않는다. 공식 문서(2026-10-24 확인)는 세그먼트를 조건 객체의 배열로, 이벤트 필터를 속성 조건의 목록으로만 정의하고 연산자는 `is`, `is not`, `contains` 같은 값 비교뿐이며 조건을 OR로 묶는 연산자나 묶음이 없다. 이 조건으로 저장한 행동 코호트를 `userdata_cohort`로 거는 안은 코호트가 이벤트 시점이 아니라 계산 시점의 사용자 속성으로 정해지고 조건 수가 늘어 비용이 커지며 정의가 명세 밖 Amplitude 화면에 남는다. 전체를 플랫폼별 셋의 합으로 바꾸는 안은 로그인 회원의 서버 이벤트(플랫폼 없음)와 Web 이벤트를 두 번 세어 겹침이 크다(2026-10-17~10-24 일별 0~12명, 10-22에 전체 252명 중 12명). |
| 영향 | 두 조회 합의 중복은 같은 날 Android와 다른 플랫폼에서 함께 활동한 사용자다. 2026-09-24~10-24 실데이터에서 Web과 Android 겹침은 일별 0~3명(그날 합계의 2% 이내)이고 30일 기간 전체로는 3,225명 중 11명이다. 분석 지표의 하루 비용은 12에서 8로, 세션은 32에서 28로 줄고 MAU는 30에서 60, 기능 사용의 `all`은 12에서 24로 는다. 새벽 배치의 하루 비용은 약 848에서 약 840이다. 해시가 바뀌는 조회는 분석 지표의 Android, 사용자 활동의 전체와 Android, MAU, 리텐션의 전체와 Android, 세션의 Android, 기능 사용의 `all`과 `android`다. 초기 백필이 서비스 시작일(2026-07-01)부터 확정일까지 약 114일을 다시 받으며 하루치 약 41에 리텐션 코호트 하루 16을 더해 약 6,500이고 배치 몫 300으로 5분마다 나눠 두 시간쯤 걸린다. 그동안 긴 범위를 처음 여는 화면은 준비 중 날짜로 응답한다. 옛 국가 조건 행은 남지만 쓰지 않는다. 같은 기간 Android 활성 사용자를 국가로 묶으면 한국 102명, 미국 82명, 그 밖 4명이다. 미국 82명 중 71명은 로그인하지 않았고 앱 버전마다 4~7명씩 나타나 Play 사전 출시 보고서의 테스트 기기로 보인다. 이 기기도 Android 값에 든다. |
| 보완(2026-10-24) | 플랫폼 기준은 운영체제가 아니라 웹과 앱이다. `platform` `Android`가 앱이고 아이폰은 웹(PWA)이다. 이 결정의 "Android 사용자"는 앱 사용자를 뜻하며 Amplitude 조건 값 `Android`는 그대로 둔다. 화면 표시는 관리자 웹 결정 21을 따른다. |
