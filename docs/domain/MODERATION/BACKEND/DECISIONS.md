# DECISIONS.md

MODERATION 도메인 백엔드의 중요한 결정을 날짜, 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 둔다. 여기에는 결정 당시의 이유와 변경 이력을 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 상태는 결정 당시 기준이다. 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.

<br>

### 2. 접수와 반영

**1. 등록과 수정을 제출본으로 접수하고 승인된 것만 현재 스토리에 반영한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-26 |
| 상태 | 채택 |
| 배경 | AI 검수는 텍스트와 표지, 인물 이미지를 함께 판정하며 요청 하나가 150초까지 걸린다. 검수 중 사용자를 화면에서 그만큼 기다리게 할 수 없고 반려된 입력은 사용자가 고쳐 다시 제출할 수 있어야 한다. 미승인 데이터가 현재 스토리에 섞이면 목록, 검색, 상세, 공개 스냅샷, 진행 중 채팅의 읽기 규칙을 모두 바꿔야 한다. |
| 채택 | 공개와 비공개를 가리지 않고 일반 제작 등록과 수정을 현재 스토리와 분리된 제출본에 저장하고 접수로 응답한다. 커밋 후 비동기로 검수하고 승인 시에만 현재 스토리에 적용한다. 간편 제작 완성본은 검수하지 않고 이후 수정부터 검수한다. 기존 현재 스토리는 승인된 것으로 간주해 소급하지 않는다. 스토리당 대기 중 제출본은 한 건이며 대기 중에는 수정과 이미지 삭제를 거절하고 스토리 삭제와 제출본 취소는 허용한다. 내용 위반은 반려, 실행 실패는 실패로 나누고 입력과 사유를 보존한다. 반려와 실패는 같은 식별자로 재제출한다. |
| 대안 | 동기 검수는 최대 150초의 대기와 연결 유지를 요구한다. 현재 스토리에 저장한 뒤 공개 대기 상태를 두는 안은 모든 읽기 경로의 규칙을 바꿔야 한다. 등록의 멱등 키는 접수 응답 유실 시 사용자가 미승인 목록에서 정리할 수 있어 두지 않았다. |
| 영향 | 등록과 수정의 응답이 완성본에서 접수로 바뀌어 서버, 웹, 앱을 함께 배포했다. 푸시 토큰이 회원 전용이라 게스트는 결과를 받을 수 없으므로 등록과 수정을 인증 필수로 바꿨다. 개별 인물 이미지 연결 API는 검수 우회 경로라 폐지하고 이미지 추가는 등록과 수정 본문으로만 받는다. |

**2. 검수 직전에 만든 복사본으로 판정하고 승인 저장에도 같은 복사본을 쓴다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-26 |
| 상태 | 채택 |
| 배경 | 업로드 서명 URL은 10분 동안 유효해 승인 뒤에도 같은 객체 키에 다른 파일을 덮어쓸 수 있다. 검수한 이미지와 현재 스토리에 저장된 이미지가 달라질 수 있다. |
| 채택 | 새 표지와 인물 이미지는 AI 호출 직전에 서버 전용 경로로 복사하고 검수 입력과 승인 저장에 같은 복사본 URL을 쓴다. 복사 경로는 서명 URL 발급 대상이 아니며 클라이언트가 직접 제출할 수 없다. 매핑은 재선점 때 재사용하고 재제출 때 비운다. 매핑이 없으면 원본으로 대체하지 않는다. 현재 스토리의 기존 이미지는 복사하지 않는다. |
| 대안 | 원본을 그대로 검수하고 저장하면 승인과 다른 이미지가 게시될 수 있다. 서명 URL 수명을 줄이는 안은 업로드 실패를 늘린다. |
| 영향 | 제출본에 복사 매핑 컬럼이 생겼고 복사는 트랜잭션 밖에서 하며 매핑 기록은 짧은 트랜잭션에서 회차를 확인한다. 복사본 객체는 지우지 않는다. |

### 3. 실행

**3. 제출본은 DB 선점과 임대로 실행하고 회차 번호로 결과를 한 번만 반영한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-26 |
| 상태 | 채택 |
| 배경 | 접수 트랜잭션에서 메모리 큐에 넣으면 인스턴스가 사라질 때 작업을 잃고, 회수 재실행이 겹치면 중복 실행이 늘어난다. 같은 제출본의 재제출과 재선점에서 이전 판정이 새 입력에 적용되면 안 된다. |
| 채택 | 접수는 대기 행만 커밋한다. 폴러가 인스턴스의 빈 슬롯 수만큼 잠긴 행을 건너뛰며 선점하고 임대 시작 시각과 회차를 기록한다. 실행기는 대기 큐가 없다. 결과는 대기 상태이고 회차가 같을 때만 반영하며 재제출과 재선점은 회차를 올린다. 임대가 만료되면 같은 폴러가 새 회차로 재선점하고 별도 회수 스케줄러는 두지 않는다. 선점마다 새 요청 ID를 만들어 AI 호출과 완료 이벤트의 상관관계 시작점으로 삼는다. |
| 대안 | 접수 시 바로 실행기에 넘기는 안은 인스턴스 종료 때 작업을 잃는다. 접수 시각을 임대 시작으로 쓰고 별도 스케줄러가 회수하는 안은 선점과 회수의 경로가 둘이 된다. 접수 요청의 상관 식별자를 저장하는 안은 실행과 요청의 수명이 달라 두지 않았다. |
| 영향 | 임대를 넘긴 실행이 끝나기 전에 재선점되면 AI를 두 번 호출할 수 있으며 결과는 회차로 한 번만 반영한다. 임대가 AI 시간 제한보다 길어야 기동한다. 신규 등록의 승인은 제출본 행을 잠근 채 스토리를 만들어 중복 생성을 막는다. |

**4. 사용자가 고칠 사유가 없는 일시 실패만 두 번 재시도하고 세 번째는 보류해 운영자에게 알린다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-27 |
| 상태 | 채택. SQL 해제는 결정 7이 대체 |
| 배경 | 이미지 내려받기, 모델 호출, 통신 장애는 일시적이라 사용자가 입력을 고칠 사유가 아니다. 그때마다 실패로 확정하면 사용자가 같은 입력을 다시 제출해야 한다. 반대로 내용 위반과 깨진 이미지는 반복 호출해도 결과가 같다. |
| 채택 | 오류 코드가 이미지 다운로드 실패, 모델 호출 실패, 검수 불가이고 위반 항목과 영구 이미지 오류가 없으면 대기 상태를 유지한 채 1분, 5분 간격으로 두 번 재시도한다. 세 번째 실패는 보류하고 커밋 후 Slack으로 한 번 알린다. 알림에는 제출본 식별자, 종류, 사유 코드, 시도 횟수만 싣는다. 보류는 완료가 아니라 완료 알림을 보내지 않고 사용자에게는 대기로 보인다. 운영자가 SQL로 보류를 해제하면 새 회차로 실행한다. 형식이 잘못된 응답이라도 위반 항목이나 영구 이미지 오류가 보이면 재시도하지 않는다. |
| 대안 | 모든 실행 실패를 즉시 실패로 확정하는 안은 일시 장애를 사용자에게 돌린다. 횟수 상한 없는 재시도는 장애 중 AI 서버에 반복해서 부하를 준다. 보류 해제 API는 권한 체계를 먼저 정해야 하므로 두지 않았다. 알림을 영속 아웃박스로 보장하는 안은 보류 상태가 DB에 남아 조회할 수 있으므로 과하다. |
| 영향 | 제출본에 재시도 횟수, 다음 시도 시각, 보류 시각과 사유 컬럼이 생겼고 선점 조건에서 예약과 보류를 제외한다. 예약과 보류 상태의 늦은 결과는 무시한다. 전용 웹훅이 없으면 신고 웹훅을 쓴다. |

<br>

**5. AI 요청 용량을 접수 전에 예산으로 검사한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-27 |
| 상태 | 채택 |
| 배경 | AI 서버는 요청 본문이 48MiB를 넘으면 이미지를 깨진 것으로 보고해 사용자가 원인을 알 수 없다. 이미지는 base64로 전송되어 원본보다 커진다. |
| 채택 | 접수의 입력 검증 단계에서 이미지 전체 크기를 base64로 환산한 값과 검수 입력 JSON 크기의 합이 40MiB를 넘으면 용량 초과로 거절한다. 새 이미지는 검증 때 받은 크기를 재사용하고 유지 이미지의 크기는 저장소에서 조회하며 조회할 수 없으면 장당 5MiB로 계산한다. AI 서버의 방어 검사는 그대로 둔다. |
| 대안 | AI 서버의 방어 검사에만 맡기면 사용자가 고칠 수 있는 오류가 실행 실패로 나타난다. |
| 영향 | 접수 전에 유지 이미지마다 저장소 조회가 생긴다. 예산은 AI 상한에서 프롬프트 여유를 뺀 추정치다. |

**6. 검수 입력의 필드 이름은 폼의 camelCase를 그대로 쓴다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-19 |
| 상태 | 채택 |
| 배경 | 검수 입력은 폼의 camelCase 필드 이름을 유지하면서 기본 주인공 이름만 `protagonist_name`으로 바꿔 보냈다. AI 서버는 요청을 camelCase 이름으로 읽고 모르는 필드를 버리므로 기본 주인공 이름은 검수 대상에서 빠진 채 승인됐다. 인물 소개도 AI 서버가 받는 칸이 없어 같은 방식으로 빠졌다. 두 칸 모두 공개되는 글이어서 AI 담당이 검수 대상에 넣기로 했다. |
| 채택 | 기본 주인공 이름도 다른 필드와 같이 `protagonistName`으로 보내고 snake_case 예외를 없앤다. 위반 항목의 위치는 전송한 필드 경로 그대로 받으며 `protagonistName`과 `characters[n].description`도 문자열 위치로 허용한다. 주인공 이름 자리의 치환 토큰을 위반으로 보는지는 AI 서버가 정한다. |
| 대안 | AI 서버가 `protagonist_name`을 별칭으로 추가로 받는 안은 필드 하나만 다른 이름 규칙이 남고 위치 경로도 폼 이름으로 되돌려야 한다. |
| 영향 | 백엔드의 이름 변경과 위치 변환이 사라진다. AI 서버가 `protagonistName`을 모르는 동안에는 기본 주인공 이름이 검수 없이 승인되는 상태가 유지되므로 두 서버의 배포 순서에 제약이 없다. 저장된 위반 항목에 `protagonist_name` 위치는 없다. AI 서버가 그 이름을 받지 않아 위반 항목을 돌려준 적이 없기 때문이다. |

### 4. 운영

**7. 보류 목록 조회와 해제를 관리자 API로 한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택. 결정 4의 SQL 해제를 대체 |
| 배경 | 보류 해제는 운영 DB에서 SQL을 한 건씩 실행하는 방식이라 DB에 접근하는 한 사람만 할 수 있었고 누가 언제 풀었는지 남지 않았다. 결정 4가 미뤘던 관리자 역할 체계가 ADMIN 세트로 생겼다. |
| 채택 | 관리자 API로 보류 중 제출본 목록을 보여 주고 사유와 함께 해제한다. 해제는 SQL과 같은 범위로 보류 시각, 사유, 재시도 횟수, 다음 시도 시각, 임대를 초기화하며 대기이고 보류 중일 때만 조건부로 갱신한다. 원인 조치는 사람이 한다. 목록은 보류 알림과 같은 원칙으로 사용자 입력 원문, 검수 폼, 이미지 URL을 싣지 않고 식별자, 종류, 사유 코드, 회차, 시각만 싣는다. 해제는 관리자 도메인의 감사 로그에 남는다. |
| 대안 | 해제가 원인 조치까지 자동으로 하는 안은 AI 서버와 저장소 상태를 서버가 판단할 수 없다. 목록에 검수 폼을 실어 관리자가 내용을 보게 하는 안은 보류 알림에 원문을 넣지 않는 규칙과 어긋나고 보류 원인은 내용과 무관한 실행 실패다. 상태 전이를 바꿔 보류를 별도 상태로 두는 안은 사용자에게 대기로 보이는 계약과 선점 조건을 함께 바꿔야 한다. |
| 영향 | 제출본 테이블의 보류 필드를 저장소에서 직접 바꾸지 않는다. 관리자 대시보드가 보류 건수를 집계한다. 해제 뒤 원인이 그대로면 두 번 재시도한 뒤 다시 보류되는 동작은 그대로다. |

<br>

| 항목 | 내용 |
|---|---|

| 상태 | 채택 |
| 배경 | 반려된 새 스토리 제출은 `stories`에 행이 없고 `story_submissions`에만 남아 관리자 화면 어디서도 보이지 않았다. 관리자 API는 보류 목록과 해제만 있었다. |
| 채택 | 관리자 제출본 목록 `GET /admin/moderation/submissions`과 상세 `GET /admin/moderation/submissions/{submissionId}`를 둔다. 목록은 상태(대기, 보류, 승인, 반려, 실패), 접수일, 소유자, 스토리, 검색어로 거르고 접수 시각, 판정 시각, 보류 시각으로 정렬한다. 위반 요약, 보류 원인, 실행 실패 코드, 회차를 보인다. 보류 원인은 회원 응답에는 없고 관리자에게만 보인다. 상세는 소유자 상세와 같은 복원을 거쳐 제목과 소개 같은 검수 대상 필드 일부, 위반 항목 전체, 이미지 결과를 보이고 설정 본문과 이미지 URL은 싣지 않는다. 관리자가 승인하거나 반려를 뒤집는 경로는 두지 않는다. 반려는 모아서 보기만 하고 사용자가 고쳐 재제출한다. 기존 보류 목록과 해제 계약은 그대로 둔다. |
| 대안 | 관리자 수동 승인을 두는 안은 검수 기준을 사람이 우회하는 경로가 생기고 승인 적용 단계의 검증을 따로 거쳐야 한다. 상세에 설정 본문과 이미지를 그대로 싣는 안은 관리자 스토리 조회가 설정 본문을 싣지 않는 범위와 어긋난다. 보류 목록을 넓혀 쓰는 안은 기존 해제 화면의 계약을 바꾼다. |
| 영향 | 관리자 웹에 검수 제출 화면이 생긴다. 반려 이유가 설정 본문에 있으면 관리자는 위치와 이유로만 판단한다. |
