# 4-1 처리 흐름

이 문서는 NOTIFICATION 도메인의 요청 수신부터 응답까지의 처리 단계, 발송 요청이 생겨서 기기에 도착하기까지의 단계를 정한다.

요청 필드, 응답 필드, 푸시 데이터는 계약에, 재시도와 시간 한도, 복구 규칙은 오류 처리에, 잠금과 선점, 멱등은 동시성에 있다. ([4-2 계약](4-2-CONTRACT.md), [5-3 오류 처리](5-3-ERROR-HANDLING.md), [5-2 동시성](5-2-CONCURRENCY.md))

<br>

### 4-1-1 공통 처리

모든 요청은 상관관계 필터에서 요청 ID를 받는다. 이어서 보안 필터가 경로의 인증 수준에 따라 요청자를 정한다. 내부 API는 토큰을 읽지 않고 공유 시크릿 헤더로 인증한다. 시크릿이 설정되지 않은 환경에서는 내부 API 경로가 없는 것처럼 응답한다. 그 외 경로는 토큰이 없거나 무효이면 거절한다.

토큰 등록과 삭제, 동의 조회와 변경은 사용자 행에 비관적 잠금을 건 뒤 상태를 다시 검사한다. 정지 계정은 거절하고 탈퇴 계정은 인증 실패로 응답한다.

발송 모드는 설정으로 하나만 활성화한다. 원격 모드에서는 모든 시나리오의 발송 요청이 아웃박스와 메시지 큐를 거쳐 알림 서비스로 간다. 로컬 모드에서는 서버 안 발송기가 아웃박스 기록 없이 직접 보내므로 기록 기반 중복 방지와 재발행 보장이 없다. 발송 직전에 원격 모드에서는 소비자가, 로컬 모드에서는 서버 안 발송기가 자격을 다시 확인한다.

광고 알림의 발송 데이터를 조립할 때 서버가 제목 앞에 광고 표기를, 본문 끝에 줄바꿈과 수신거부 안내를 붙인다. 제목이 이미 광고 표기로 시작하면 표기를, 끝 공백을 뺀 본문이 이미 수신거부 안내로 끝나면 안내를 다시 붙이지 않고 본문을 그대로 둔다. 서비스 알림의 제목과 본문은 그대로 쓴다. 광고 표기와 수신거부 안내는 발송 데이터에만 붙이고 회원이 앱 안에서 다시 보는 알림 내역에는 저장된 원문 제목과 본문을 쓴다.

흐름도에서 FCM, 메시지 큐, Redis, 서버 내부 API, 다른 도메인을 호출하는 단계는 주황색이다.


- 토큰 행도 잠그고 읽는다. 커밋 전 삭제 중인 행을 읽으면 갱신이 0건이 되어 요청이 실패한다.
- 삽입이나 소유권 이전으로 기기가 하나 늘어나기 전에 기존 기기 수가 상한보다 하나 적어지도록 토큰을 삭제한다. 같은 소유자의 재등록은 개수가 그대로라 삭제하지 않는다.
- 갱신 시각은 값이 그대로여도 재등록마다 갱신한다. 상한 초과 삭제와 발송 대상 선택의 근거다.

- 삭제 조건을 삭제문 안에 둔다. 조회 뒤 ID로 지우면 그 사이 소유자가 바뀐 행까지 지운다.
- 탈퇴 시 계정 도메인이 회원의 토큰을 전부 삭제하는 연산을 호출한다.
- 로그아웃 처리는 토큰을 직접 지우지 않는다. 기기가 여러 대일 수 있어 클라이언트가 그 기기의 토큰으로 삭제를 호출한다.

- 모든 푸시 데이터에는 수신자 식별자를 덧붙인다.

- 게스트 제작은 발행하지 않는다. 같은 요청 ID의 재처리는 완료 표시에 이르지 않아 다시 발행하지 않는다.
- 원격 모드의 아웃박스 기록 실패는 완료 표시도 되돌린다. 로컬 모드의 발송 실패와 실행기 포화는 로그만 남기고 제작 응답을 바꾸지 않는다.
- 메시지 식별자는 `story-completed:{완성 요청 ID}`다.

### 4-1-8 출석 리마인드

```mermaid
%%{init: {"flowchart": {"curve": "basis", "nodeSpacing": 24, "rankSpacing": 40}}}%%
flowchart LR
    A["`**오늘 회차 선점**

    B -->|아니오| X["`**건너뜀**`"]
    B -->|예| C["`**대상 조회**

    C --> D["`**문구 해석**
회차에 1회, 광고 표기와 수신거부 안내`"]
    D --> E{"`**발송 모드**`"}
    E -->|원격| F["`**회원마다 발송 요청 기록**
당일 유효 기한, 식별자 충돌은 무시`"]
    E -->|로컬| H["`**회원마다 자격 재확인과 발송**
FCM, 보통 우선순위`"]
    F --> G["`**회차 결과 로그**`"]
    H --> G
    classDef comp fill:#E8F2E8,stroke:#527A59,color:#182D1D
    classDef task fill:#F5D9C9,stroke:#B97450,color:#452B1D
    class B,D,E,F,G,X comp
    class A,C,H task
```

- 매일 정해진 시각에 실행한다. 선점 키는 날짜별이며 Redis 장애로 선점 여부를 알 수 없으면 그날은 건너뛴다. 광고성이라 중복보다 누락이 낫다.
- 문구는 회차 시작에 한 번 해석하고 광고 표기와 수신거부 안내를 붙인다.
- 출석 미수령은 이프 원장에 `attendance:{보상 신원}:{KST 날짜}` 키가 없는 것으로 판정한다. 출석 보상이 쓰는 키와 같다.
- 대상은 회원 ID만 조회한다. 활성 상태, 광고 동의, 야간 동의는 발송 직전에 소비자가 자격 조회로 다시 확인한다.
- 메시지 식별자는 회원과 날짜로 구성되므로 같은 회원의 요청은 하루에 두 번 기록되지 않는다. 발송 요청의 유효 기한은 당일 KST 자정이다.
- 회차의 발송 요청은 한 트랜잭션으로 기록하고 커밋한다. 기록에 실패하거나 커밋 전에 인스턴스가 종료되면 그날 요청은 남지 않으며 회차를 실패로 기록하고 다음 날 회차로 넘어간다.
- 로컬 모드는 회원마다 자격을 다시 확인한 뒤 기기마다 발송 직전에 유효 기한을 검사하고 남은 TTL을 다시 계산한다. 자정이 지나면 남은 회원과 기기에 보내지 않는다.

### 4-1-9 프로모션

```mermaid
%%{init: {"flowchart": {"curve": "basis", "nodeSpacing": 24, "rankSpacing": 40}}}%%

    D --> E{"`**발송 모드**`"}
    E -->|원격| F["`**회원마다 발송 요청 기록**
식별자 충돌은 무시`"]
    E -->|로컬| H["`**회원마다 자격 재확인과 발송**

    F --> G["`**캠페인에 결과 기록**

    H --> G
    classDef comp fill:#E8F2E8,stroke:#527A59,color:#182D1D
    classDef task fill:#F5D9C9,stroke:#B97450,color:#452B1D
    class A,B,C,E,F,G,X comp
    class D,H task
```

- 운영자가 예약 행을 추가하면 발송이 예약되고 선점 전에 취소 상태로 바꾸면 취소된다.
- 문구는 회차 시작에 캠페인 행에서 한 번 읽는다. 종류가 `MARKETING`인 캠페인만 광고 표기와 수신거부 안내를 붙이고 종류가 `SERVICE`인 공지 캠페인은 제목과 본문을 그대로 쓴다.
- 야간에 도래한 캠페인은 연기하지 않고 야간 동의자에게만 보낸다. 야간 여부는 회차 시작 시각이 아니라 소비자가 보내기 직전의 시각으로 판정한다.
- 회차의 발송 요청은 한 트랜잭션으로 기록하고 커밋한다. 기록에 실패하면 캠페인을 실패로 기록하고 요청은 남지 않는다.
- 캠페인에는 마지막 회차의 대상 수와 기록한 요청 수를 남긴다. 캠페인별 거절과 발송 결과는 남기지 않으며 확인 경로는 [5-4-4 오류 확인](5-4-OBSERVABILITY.md#5-4-4-오류-확인)에 있다.
- 회차가 예외로 끝나면 실패 상태로 기록하고 자동으로 재실행하지 않는다. 운영자가 원인을 확인한 뒤 같은 행을 예약 상태로 되돌리면 다시 실행한다. 메시지 식별자는 캠페인과 회원으로 구성되므로 이미 기록한 요청은 중복 기록되지 않는다.

### 4-1-15 이프 만료 예정 알림


- 매일 정해진 시각에 실행한다. 선점 키는 날짜별이며 Redis 장애로 선점 여부를 알 수 없으면 그날은 건너뛴다.
- 대상은 활성 회원 가운데 실행 시각 기준 `now < expires_at <= now + 24시간`이고 `remaining > 0`인 로트를 가진 회원이다. 만료 시각이 없는 승계 로트, 잔여 0 로트, 이미 만료된 로트는 판정에 들지 않는다. 서비스 알림 설정과 토큰 보유는 대상 조건이 아니다. 푸시를 꺼 둔 회원도 알림 내역은 받는다. 회원마다 창 안 로트 중 가장 늦은 만료 시각을 함께 조회해 발송 요청의 유효 기한으로 쓴다.
- 쿨다운 키가 있는 회원은 대상에서 뺀다. 쿨다운 조회에 실패하면 아무것도 기록하지 않고 회차를 실패로 기록한다.
- 대상 회원마다 알림 내역을 활동 분류로 기록한다. 제목과 본문은 해석한 문구, 딥링크는 푸시 데이터와 같다. 메시지 키는 메시지 식별자와 같아 같은 날 재실행해도 회원당 한 행이다.
- 원격 모드는 같은 트랜잭션에서 회원마다 발송 요청을 기록한다. 발송 요청은 서비스 알림 종류이며 소비자가 발송 직전에 서비스 알림 설정과 토큰을 확인한다. 알림 내역과 발송 요청은 한 트랜잭션으로 커밋한다. 어느 한 회원의 기록에 실패하거나 커밋 전에 인스턴스가 종료되면 그날 내역과 요청은 남지 않으며 회차를 실패로 기록하고 다음 날 회차로 넘어간다.
- 쿨다운은 커밋 뒤 알림 내역을 기록한 대상 회원 전원에게 7일 수명으로 건다. 모드와 푸시 수신 여부에 관계없다. 발송 직전 자격 거절로 푸시를 받지 못한 회원도 알림 내역은 받았으므로 7일 동안 대상이 아니다. 쿨다운 기록에 실패하면 회차를 실패로 기록하되 커밋한 내역과 요청은 유지한다. 원격 모드에서는 유지된 요청이 발행되므로 알림이 나간다.
- 로컬 모드는 쿨다운 기록 뒤 트랜잭션 밖에서 회원마다 활성 상태, 서비스 알림 설정, 토큰을 다시 확인하고 기기마다 발송 직전에 그 회원의 유효 기한을 검사해 남은 TTL을 다시 계산한다. 자격 거절, 발송기 예외, FCM 자격 증명 미설정은 모두 발송 결과로만 남고 쿨다운에 영향이 없다.
- 서비스 알림이라 광고 표기와 수신거부 안내를 붙이지 않고 광고 동의를 보지 않는다. 금액, 수량, 만료 시각은 제목, 본문, 데이터, 알림 내역 어디에도 싣지 않는다.
- 메시지 식별자는 `credit-expiry:{회원 공개 식별자}:{KST 날짜}`다.
