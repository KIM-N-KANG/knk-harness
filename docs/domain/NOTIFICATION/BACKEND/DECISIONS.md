### 1. 기록 규칙

### 2. 토큰과 동의

**1. 토큰은 전역 유일이며 같은 기기에서 계정이 바뀌면 소유자를 옮긴다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-03 |
| 상태 | 채택 |
| 배경 | 푸시 토큰은 기기의 앱 설치본 주소라 회원이 아니라 기기에 묶인다. 한 기기에서 로그아웃하고 다른 계정으로 로그인하면 이전 회원의 알림이 그 기기로 가면 안 된다. |
| 채택 | 토큰에 유니크 제약을 두고 같은 토큰을 다른 회원이 등록하면 소유자를 옮긴다. 같은 토큰을 재등록하면 갱신한다. 회원당 기기 상한은 10개이고 넘으면 가장 오래 갱신되지 않은 토큰을 지운다. 삭제는 요청자 소유 조건을 삭제문 안에 둔 조건부 삭제다. |
| 대안 | 회원과 토큰의 다대다를 허용하면 이전 회원의 알림이 공유 기기로 계속 간다. 설치본 식별자를 함께 받아 좀비 행을 정리하는 방식은 앱 계약을 바꿔야 해 채택하지 않았다. |
| 영향 | 등록은 사용자 행과 토큰 행을 잠근다. 상한에 찬 두 회원이 같은 순간 서로의 토큰을 교차 등록하면 한쪽이 교차 대기로 실패하는 것을 수용했다. 로그아웃은 토큰을 지우지 않고 클라이언트가 그 기기의 토큰을 삭제한다. 좀비 행이 실제로 관측되면 설치본 식별자 방식을 다시 검토한다. |

|---|---|

| 상태 | 채택 |

| 배경 | 커밋 후 외부 발송에 실패하면 재개할 근거가 없었다. 발송은 시나리오 데이터와 회원 자격 조회를 경계로 분리할 수 있어 다른 기능과의 결합도가 가장 낮은 후보였다. 분리 범위를 알림으로 제한하고 운영 브로커는 SQS, 로컬은 Kafka로 두며 메시지 큐 전환 전에 동기 경로를 먼저 검증하기로 했다. |

| 대안 | 검색 색인까지 분리하는 안은 범위가 넓다. 알림 서비스가 회원 데이터를 복제하는 안은 동의 철회가 늦게 반영된다. 커밋 후 메시지 큐에 직접 발행하는 안은 발행 실패를 보존하지 못한다. |

**9. 소비자는 Redis 멱등 기록으로 2분 선점하고 완료를 7일 보존한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-26 |
| 상태 | 채택 |
| 배경 | 알림 서비스에 PostgreSQL을 두지 않기로 했다. 메시지 큐는 최소 한 번 전달하므로 소비자가 중복을 걸러야 한다. 처리 중 소비자가 종료되면 재전달 가능 시간 안에 다른 소비자가 이어받아야 한다. |
| 채택 | 메시지 식별자 키를 소유자 값과 2분 수명으로 선점하고 완료 표시를 7일 보존한다. 성공한 토큰 해시를 집합으로 남겨 재전달 때 제외한다. 선점은 연장하지 않고 소유자 값이 같을 때만 완료와 해제를 반영한다. 처리 예산 10초가 지나면 새 기기 발송을 시작하지 않는다. |
| 대안 | 처리 중 선점을 연장하면 종료된 소비자의 메시지를 재전달 가능 시간 안에 다시 선점할 수 없다. 영구 저장소에 멱등 테이블을 두려면 서비스에 DB를 도입해야 한다. |
| 영향 | 운영 Redis가 수명 있는 키를 먼저 제거하므로 드물게 중복이 가능하다. 정확히 한 번 도달은 보장하지 않으며 유실보다 중복을 택했다. 소비자 재전달 값은 메시지 큐 설정과 같아야 하고 선점 수명은 재전달 가능 시간보다 짧아야 한다. |

| 채택 | 라이브러리 재시도를 0회로 두고 일시 오류와 429는 즉시 재전달로 돌린다. 연결과 쓰기는 1초, 읽기는 5초다. 잘못된 인자와 인증, 권한, 없음, 발신자 불일치는 영구 오류로 폐기한다. 무효 토큰만 삭제한다. |
| 대안 | 라이브러리 기본 재시도를 두면 재시도가 중첩되어 선점 수명 안에 끝나지 않는다. |
| 영향 | 서버 안 발송기는 라이브러리 재시도를 유지한다. 두 발송기의 시간 설정이 다르다. |

**11. 운영 알림 서비스는 별도 ECS 서비스이고 사설 DNS로 서버를 호출한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-30 결정, 2026-10-06 운영 원격 모드 전환 |
| 상태 | 채택 |
| 배경 | 개발은 서버 태스크 안의 컨테이너로 충분했지만 운영은 배포와 권한을 분리해야 했다. 공유 시크릿만으로 보호하면 공개 경로에서 내부 API에 접근할 수 있었다. |
| 채택 | 운영 알림은 별도 ECS 서비스로 두고 서버를 사설 DNS에 등록해 호출한다. 공개 ALB는 내부 경로에 없음으로 응답한다. 메시지 큐 권한은 서버가 발행, 알림이 수신과 삭제로 나눈다. 멱등 기록은 서버와 같은 Redis를 접두어로 구분해 쓴다. 로그는 서버와 같은 경로로 보내고 CloudWatch 안전망을 유지한다. 실패 메시지 큐 경보를 개발과 운영에 둔다. |
| 대안 | 공개 ALB와 NAT 출발지 IP 규칙은 Cloudflare 프록시를 켜면 동작하지 않아도 문제가 드러나지 않는다. 내부 ALB는 서비스 하나의 내부 호출에 고정비가 과하다. |
| 영향 | 전환은 인프라 준비, 운영 CD, 시크릿 주입, 소비 확인, 서버 원격 모드 전환 순서로 했다. 서버의 FCM 자격 증명은 롤백 가능 기간과 출석, 프로모션 발송을 위해 유지한다. 유지 이유는 결정 12로 바뀌었다. 본 큐 적체 경보는 임계값 근거가 없어 두지 않았다. |

**12. 출석 리마인드와 프로모션도 아웃박스와 메시지 큐로 보낸다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-17 |
| 상태 | 채택. 결정 4, 5, 7, 11의 회차 발송 방식을 대체. 발송 결과를 기록하지 않는 부분은 결정 15가 대체 |
| 배경 | 큐 전환 뒤에도 출석과 프로모션은 서버 안 발송기가 직접 보냈다. 발송 경로가 둘이라 메시지 구성이 어긋났고, 회차 도중 인스턴스가 종료되면 출석은 남은 회원이 누락되고 프로모션은 재예약으로 중복이 났다. 큐 메시지 계약은 처음부터 두 시나리오의 식별자 규칙을 갖고 있었다. |
| 채택 | 원격 모드에서는 스케줄러가 대상을 조회해 회원마다 아웃박스에 발송 요청을 기록하고 릴레이와 소비자가 나머지를 맡는다. 발송 직전 자격 재확인과 야간 판정은 소비자가 한다. 출석 요청은 당일 KST 자정을 유효 기한으로 싣는다. 메시지 식별자가 회원과 날짜, 캠페인과 회원으로 구성되어 재실행해도 회원당 한 건만 기록된다. 캠페인에는 대상 수와 기록한 요청 수만 남기고 거절과 발송 결과는 지표로 확인한다. 회차의 요청은 한 트랜잭션으로 기록해 부분 기록을 남기지 않는다. 실패한 캠페인은 운영자가 같은 행을 예약 상태로 되돌려 재실행한다. 서버 안 발송기는 로컬 모드 롤백용으로만 남긴다. |
| 대안 | 서버 안 발송기를 유지하는 안은 발송 경로가 둘이라 구성 불일치와 회차 중단 손실이 남는다. 캠페인 행에 소비 결과를 되돌려 기록하는 안은 알림 서비스가 서버 DB에 쓰거나 별도 API가 필요해 경계를 넘는다. |
| 영향 | 회차마다 대상 수만큼 아웃박스 행과 큐 메시지, 소비자의 자격 조회, 멱등 키가 생긴다. 릴레이 배치와 소비 동시성은 대상 수가 늘면 다시 본다. 서버 아웃박스 메시지에 유효 기한 필드가 필요하다. 회차 로그의 `sent`는 기록한 요청 수를 의미하고 `skipped`는 없어진다. 캠페인의 `skipped_count`는 쓰지 않는다. |

### 5. 관리자 API와 공지 알림

**13. 캠페인과 문구는 관리자 API로 바꾸고 캠페인에 종류를 두어 정보성 공지를 보낸다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택. 결정 5의 운영자 저장소 직접 변경을 대체 |
| 배경 | 캠페인 예약과 취소 및 문구 변경이 저장소 직접 변경이라 DB에 접근하는 한 사람만 할 수 있었고 전체 발송 전에 규모를 확인할 장치가 없었다. 결정 5가 미뤘던 관리자 역할 체계가 ADMIN 세트로 생겼다. 공지 도메인이 생기면서 광고가 아닌 소식을 서비스 알림 설정을 켠 회원에게 보낼 경로가 필요했다. |
| 채택 | 캠페인 예약, 선점 전 취소, 실패 재실행, 문구 오버라이드 추가와 기본 문구 복귀를 관리자 API로 한다. 즉시 발송은 예약 시각을 현재로 둔 캠페인이다. 확정 전에 종류별 대상 수를 미리보기로 제공한다. 캠페인에 종류 컬럼과 공지 참조를 두어 광고 종류는 기존 프로모션 규칙으로, 서비스 종류는 서비스 알림 설정을 조건으로 보낸다. 서비스 종류의 시나리오는 `NOTICE`이고 광고성 공지는 `PROMOTION`에 공지 식별자와 딥링크를 더한다. 모든 변경은 관리자 도메인의 감사 로그에 남는다. 실패 메시지 큐의 확인과 되돌리기는 관리자 API에 넣지 않는다. |
| 대안 | 정보성 공지에 새 알림 종류와 새 수신 설정을 두는 안은 동의 변경 계약의 세 필드를 바꿔 클라이언트 동반 배포가 필요하고 법적으로 요구되지도 않는다. 공지 도메인이 직접 아웃박스에 기록하는 안은 캠페인 선점과 대상 판정을 중복 구현한다. 실패 메시지 큐 조회 API는 서버가 메시지 큐를 읽는 권한과 알림 서비스와의 경계 변경이 필요하며 경보와 콘솔로 충분하다. 문구 오버라이드를 갱신하거나 삭제하는 안은 이전 문구의 이력을 잃는다. |
| 영향 | 캠페인 테이블에 종류와 공지 참조 컬럼이 생겼다. 알림 서비스의 큐 메시지 검증에 `NOTICE` 시나리오를 추가해야 하며 서버보다 먼저 배포한다. 캠페인과 문구는 저장소에서 직접 고치지 않는다. 즉시 발송한 캠페인도 선점 전에는 취소되지만 다음 폴링에서 바로 선점되므로 취소 기회가 짧다. 전송 중으로 멈춘 캠페인의 처리는 결정 14가 정한다. |

**14. 전송 중으로 멈춘 캠페인은 시간 한도 뒤 스케줄러가 실패로 전환하고 관리자 재실행으로 잇는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 회차 도중 인스턴스가 종료되면 캠페인이 전송 중 상태로 남는다. 관리자 재실행은 실패 상태만 받으므로 저장소에서 상태를 고쳐야 했고 결정 13이 그 한계를 남겼다. |
| 채택 | 캠페인 폴링마다 선점 시각부터 시간 한도가 지난 전송 중 캠페인을 조건부 갱신으로 실패로 바꾸고 경고 로그를 남긴다. 시간 한도는 설정값이며 기본 30분이다. 실패는 자동으로 재실행하지 않는다는 규칙은 그대로 두고 관리자 재실행 API로 잇는다. 원격 모드에서는 회차의 요청이 한 트랜잭션으로 기록되고 메시지 식별자가 캠페인과 회원으로 구성되므로 재실행해도 이미 기록된 회원에게는 다시 가지 않는다. 로컬 모드는 회원별 기록이 없어 중복 발송을 수용하며 롤백 경로라 별도 기록을 두지 않는다. 선점 시각 컬럼이 이미 있어 스키마 변경은 없다. |
| 대안 | 전송 중 캠페인을 바로 실패로 두는 전용 관리자 API는 정상 진행 중인 회차를 사람이 끊을 수 있다. 시간 한도 뒤 자동 재실행은 같은 실패를 반복하지 않는다는 결정 5의 규칙과 어긋난다. 시간 한도 없이 두면 저장소 직접 수정이 그대로 남는다. |
| 영향 | 30분은 회차가 대상을 조회해 아웃박스에 회원당 한 행을 한 트랜잭션으로 기록하는 데 수천 명 기준 수 초가 걸리고 폴링 간격이 60초인 점에 비해 충분히 길다. 롤링 교체와 DB 지연을 더해도 수 분 안에 끝나므로 정상 회차가 실패로 전환될 가능성은 없다. 멈춘 캠페인은 최대 30분과 폴링 1회 뒤 실패로 보이고 관리자가 재실행한다. 전환과 늦게 끝난 회차의 결과 기록은 조건부 갱신으로 한쪽만 반영된다. 결과 기록의 조건에 상태뿐 아니라 선점 시각을 넣어, 전환 뒤 재실행된 새 회차의 전송 중 상태를 옛 회차의 늦은 결과가 덮어쓰지 못하게 한다. 선점 시각이 회차의 실행 식별자 역할을 하므로 별도 컬럼은 두지 않는다. |

**15. 알림 서비스가 메시지마다 발송 결과를 서버에 보고하고 서버가 영구 보존해 캠페인별, 종류별 날짜별 도달 통계를 낸다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택. 결정 12의 "거절과 발송 결과는 지표로 확인"을 대체 |
| 배경 | 캠페인에는 대상 수와 기록한 요청 수만 남아 실제로 몇 명에게 갔는지 알 수 없었다. 성공 기기 기록은 알림 서비스 Redis의 멱등 기록이라 7일 뒤 사라지고 출석 리마인드, 완성, 검수 알림은 회차 로그와 지표뿐이었다. 관리자 페이지가 알림마다 도달 수를 보여 줘야 했고 알림 서비스는 서버 DB에 직접 접근하지 않는다는 경계가 있다. |
| 채택 | 알림 서비스가 메시지 하나의 처리를 끝낼 때 결과를 서버 내부 API로 보고한다. 보고에는 메시지 식별자, 시나리오, 종류, 수신자, 캠페인, 결과, 도달 기기 수, 실패 기기 수, 완료 시각이 담긴다. 결과는 도달, 미도달, 폐기의 세 가지다. 도달은 FCM이 받아들인 기기가 하나 이상인 경우이고 미도달은 발송했으나 도달 기기 수가 0인 경우이며 폐기는 만료나 자격 거절로 발송 없이 끝난 경우다. 서버는 메시지 식별자 유니크로 한 행씩 저장하고 재보고는 처음 행을 유지한다. 로컬 모드는 서버 안 발송기가 같은 행을 기록한다. 보고는 완료 기록 뒤 동기 호출 1회이며 연결 1초, 읽기 2초 안에 끝나지 않거나 오류 응답이면 경고만 남기고 재시도하지 않는다. 캠페인 구조에 도달 회원 수, 도달 기기 수, 실패 기기 수를 더하고 캠페인 상세와 시나리오별 KST 날짜별 통계 API를 둔다. 통계 기간은 최대 366일이고 기본은 오늘까지 7일이다. 집계 단위는 하루이고 주 단위나 월 단위 합계는 관리자 페이지가 날짜 행을 더해 만든다. 결과 행은 영구 보존하고 팀 계정을 제외하지 않는다. 서버의 보고 API를 먼저 배포하고 알림 서비스가 보고를 시작한다. |
| 대안 | 알림 서비스가 서버 DB에 직접 쓰는 안은 결정 12가 둔 경계를 깨고 알림 서비스에 DB 자격 증명을 주입해야 한다. 소비 결과를 큐로 되돌려 서버가 소비하는 안은 큐와 소비자가 하나 더 생겨 보고를 위한 HTTP 호출 한 번보다 복잡하다. 캠페인 행에 도달 수를 누적하는 안은 재전달과 재보고의 중복 가산을 막을 수 없어 메시지마다 행을 두고 집계한다. 보고를 재시도하는 안은 소비자의 처리 예산 안에서 발송과 경쟁하고 서버 장애 때는 자격 조회도 실패해 처리 자체가 재전달되므로 실익이 작다. 결과 행에 보존 기간을 두는 안은 캠페인의 도달 수가 시점에 따라 줄어들고 정리 작업이 필요하며 행 수가 발송 요청과 같아 아웃박스를 영구 보존하는 규칙과 다를 이유가 없다. 팀 계정을 제외하는 안은 발송 결과가 운영 사실이고 대시보드처럼 사용자 규모를 보는 지표가 아니라 채택하지 않았다. 주 단위나 월 단위 집계 API를 따로 두는 안은 관리자 페이지가 날짜 행을 더해 집계할 수 있어 채택하지 않았다. 366일 상한은 기간을 바꿔 가며 1년치까지 한 번에 볼 수 있고 날짜와 시나리오 조합도 최대 1,830행으로 한 응답에 담을 수 있는 크기다. |
| 영향 | 발송 결과 테이블, 결과 보고 내부 API, 캠페인 상세와 알림 통계 관리자 API가 생겼다. 큐 소비 흐름에 보고 단계가 들어가고 알림 서비스에 결과 보고 클라이언트가 생긴다. 보고가 실패한 메시지는 통계에서 빠지며 누락 규모는 발송 지표와 비교해 확인한다. 도달은 FCM 수락 기준이라 기기 표시 수와 다를 수 있다. 서버 안 발송기가 메시지 식별자를 알아야 로컬 모드 기록이 가능하다. |

**16. 푸시 딥링크에 팀 UTM 규격의 네 필드를 붙인다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-24 |
| 상태 | 채택 |
| 배경 | 푸시 알림을 눌러 들어온 방문이 분석 도구에서 다른 유입과 구분되지 않았다. 팀은 광고와 게시글 링크에 `utm_source`, `utm_medium`, `utm_campaign`, `utm_content` 네 필드를 쓴다. |
| 채택 | 모든 딥링크에 `utm_source=push`, `utm_medium=push`를 붙인다. `utm_campaign`은 관리자 캠페인 발송(공지와 프로모션)이면 캠페인 공개 식별자, 그 밖의 서비스 알림과 출석 리마인드는 `type`을 소문자로 바꾼 종류 코드다. `utm_content`는 `promotion`, `notice`, 또는 그 종류 코드다. 기존 경로에 쿼리만 붙이고 이미 쿼리가 있으면 `&`로 잇고 값은 URL 인코딩한다. |
| 대안 | 캠페인 값으로 공지 제목을 쓰는 안은 값이 길고 바뀔 수 있다. `utm_medium`을 `notification`으로 두는 안은 팀 규격의 값과 맞추려고 `push`로 통일했다. |
| 영향 | 클라이언트가 딥링크 쿼리를 지우지 않고 열어야 분석 도구가 UTM을 받는다. 관리자 웹 유입 분석에서 푸시 캠페인을 보는 방법은 정하지 않았다. 유입 분석은 첫 유입 속성(`gp:initial_utm_*`)과 설정 파일의 광고 캠페인 목록으로 계산하는데 푸시는 이미 가입한 회원이 대상이라 첫 유입으로 잡히지 않는다. 보려면 페이지 조회 이벤트의 `utm_campaign` 기준 지표와 캠페인 목록 항목이 필요하다(결정 필요). |

**17. 회원별 알림 내역을 서버가 한 목록으로 누적 보관하고 소식과 활동으로 나눈다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-24 |
| 상태 | 채택 |
| 배경 | 푸시는 기기에 한 번 표시되고 사라져 회원이 지난 알림을 다시 볼 곳이 없었다. 서비스 알림을 끄거나 토큰이 없는 회원은 완성과 검수 결과를 앱 안에서 알 방법도 없었다. 웹은 다른 서비스의 알림 센터처럼 탭으로 나눈 알림함을 만들기로 했다. |
| 채택 | 알림 내역 테이블에 회원이 받은 알림을 한 행씩 기록하고 공지를 포함해 서버가 한 목록으로 준다. 기록은 시나리오별 기존 트랜잭션에서 한다. 완성과 검수는 도메인 트랜잭션, 출석과 캠페인은 회차 트랜잭션이며 원격 모드의 발송 요청 기록과 같은 위치다. 대상은 예약 발송 조건에서 토큰 보유와 야간 조건을 뺀 회원이고 서비스 알림 설정은 보지 않는다. 광고 알림은 광고 동의자에게만 남긴다. 회원과 메시지 식별자 유니크로 재처리와 재실행의 중복을 막는다. 공지는 게시가 만든 공지 알림 캠페인의 회차에서 기록하고 기능 배포 이전의 공지와 알림은 소급하지 않는다. 각 행에 분류(`NEWS` 소식, `ACTIVITY` 활동)와 종류(`type`)를 함께 싣는다. 공지와 프로모션은 소식이고 완성, 검수, 출석 리마인드는 활동이다. 새 종류는 분류를 함께 정한다. 회원 API는 분류 필터가 있는 커서 목록, 분류별 안 읽은 수, 한 건 읽음, 분류별 모두 읽음이다. 내역은 회원마다 누적하고 보관 기간과 정리 작업을 두지 않으며 탈퇴할 때만 그 회원의 행을 모두 지운다. |
| 대안 | 목록을 조회할 때 공지 테이블을 합치는 안은 공지별 읽음 상태를 따로 저장해야 하고 커서가 두 원본에 걸친다. 발송 결과 행으로 내역을 만드는 안은 푸시를 보내지 않은 회원의 내역이 없고 알림 서비스의 보고가 실패하면 빠진다. 커밋 뒤 별도 트랜잭션에서 기록하는 안은 실패 시 내역만 빠지는 불일치가 생기고 아웃박스와 같은 위치에 두는 편이 단순하다. 90일 보관과 정리 배치는 오래된 알림까지 내려 볼 수 있게 하라는 결정(10/24)에 따라 두지 않았다. 분류를 응답 시 종류에서 계산하는 안은 분류별 인덱스를 쓸 수 없다. 경로를 `/me/notifications`로 두는 안은 모든 회원 API가 쓰는 `/users/me/...` 관례와 달라 채택하지 않았다. |
| 영향 | 알림 내역 테이블과 회원 API 4개가 생기고 탈퇴 처리에 내역 삭제가 들어간다. 행 수는 회원당 하루 1~2건(출석 리마인드 1건과 가끔의 공지, 프로모션, 완성) 수준이라 활성 회원 1,000명이면 한 해 수십만 행이고 조회는 회원별 인덱스 범위라 당분간 문제없다. 테이블이 수천만 행에 이르거나 저장 비용이 눈에 띄면 보관 정책을 다시 검토한다. 내역의 딥링크는 `utm_source=inbox`, `utm_medium=inbox`로 푸시 유입과 구분한다. 행은 기록 시점의 사본이라 게시 해제한 공지나 삭제된 스토리의 내역도 남는다. 탈퇴와 같은 순간에 진행된 회차는 탈퇴 회원의 내역을 남길 수 있다. 웹과 Android는 서버 배포 뒤 알림함을 붙인다. |
| 보완(2026-10-24) | 공지는 게시하면 항상 알림을 보낸다(NOTICE 결정 2). 알림 없이 게시하는 선택지가 없어져 게시된 공지마다 공지 알림 캠페인과 내역이 생긴다. 공지당 캠페인 한 건과 메시지 식별자 유니크로 수정과 재게시에 내역이 늘지 않는다. 관리자가 선점 전에 공지 알림 캠페인을 취소하는 경로는 남기며 취소하면 그 공지는 푸시와 내역 모두 없다. 게시 직후 바로 선점되는 즉시 발송이라 취소 기회가 짧고 잘못 게시한 공지를 알리기 직전에 멈출 유일한 수단이라 막지 않았다. |
| 보완(2026-10-24) | 공지 태그가 알림 유형을 정한다(NOTICE 결정 3). 공지 발송 요청이 태그를 함께 넘기고 캠페인에 `notice_tag`로 남긴다. 회차는 그 값을 푸시 데이터와 알림 내역의 `noticeTag`로 싣는다. 응답 필드 이름은 같은 항목의 `noticeId`와 맞춰 `noticeTag`로 했다. 분류는 태그와 무관하게 공지 알림 전부 `NEWS`다. |
| 보완(2026-10-24) | 알림 내역은 회원 전용이다(사용자와 강동우 합의). 게스트는 알림 내역 API를 쓰지 않고 게스트의 간편 제작 완료도 활동 내역을 남기지 않는다. 앱 사용자는 모두 회원이다. 게스트에게 소식을 보여 주는 일은 클라이언트가 공개 공지 목록 API로 한다. |

**18. 관리자의 스토리 공개 중단을 서비스 알림 `STORY_TAKEN_DOWN`으로 알리고 내역은 항상 남긴다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-27 |
| 상태 | 채택 |
| 배경 | 관리자가 회원 스토리를 공개 중단하게 됐다(MODERATION 결정 9). 소유자는 스토리가 왜 비공개가 됐는지, 어떻게 다시 공개하는지 알아야 한다. 공개 중단은 회원이 유발한 작업의 결과가 아니라 운영 조치지만 회원 콘텐츠에 대한 통지라 광고가 아니다. |
| 채택 | 알림 종류 `STORY_TAKEN_DOWN`을 둔다. 종류는 서비스 알림, 분류는 `ACTIVITY`다. 알림 내역은 검수 완료처럼 공개 중단 트랜잭션에서 동기로 기록하고 푸시는 서비스 알림 설정을 따른다. 원격 모드는 같은 트랜잭션의 아웃박스를, 로컬 모드는 커밋 후 서버 안 발송기를 쓴다. 메시지 식별자는 `story-taken-down:{스토리 공개 식별자}:{공개 중단 시각의 epoch 밀리초}`라 공개 중단 한 번에 한 번이고 재검수로 해제된 뒤 다시 공개 중단되면 새로 보낸다. 딥링크는 소유자가 스토리를 고치고 재검수를 받는 내 제작 목록 `/studio`다. 제목은 고정 문구 `스토리 공개가 중단됐어요`이고 본문에 스토리 제목, 사유 분류 표시 이름, 재검수 안내를 싣는다. 스토리 제목과 사유를 제목에 넣지 않은 이유는 Android 잠금 화면이 서비스 알림의 제목 줄만 보이기 때문이고 검수 완료 알림과 같은 구성이다. 메모와 처리 관리자는 싣지 않는다. 소유 회원이 탈퇴했으면 내역과 발송 요청을 만들지 않는다. |
| 대안 | 검수 완료 알림에 상태 값을 더해 보내는 안은 제출본이 없는 조치를 제출본 식별자와 회차 규칙에 끼워 넣어야 한다. 알림 없이 공개 중단하는 안은 소유자가 비공개 전환의 이유를 모르고 다시 공개를 시도하다 검수로 넘어가는 이유도 알 수 없다. 메시지 식별자에 감사 로그 공개 식별자를 쓰는 안은 알림 경로가 ADMIN의 반환 값에 묶인다. 사유 분류를 푸시 데이터 필드로 따로 싣는 안은 클라이언트가 쓸 곳이 없어 문구에만 넣었다. |
| 영향 | 알림 내역 `type`의 체크 제약에 값이 하나 늘어 마이그레이션이 필요하다. 알림 서비스의 큐 메시지 검증에 새 시나리오를 서버보다 먼저 배포한다. 웹과 앱의 알림함에 "공개 중단" 라벨을 더하며 구버전은 라벨 없이 제목, 본문, 딥링크 이동으로 보인다. 관리자 푸시 열람의 활동 알림에는 넣지 않는다(ADMIN 결정 33). |
