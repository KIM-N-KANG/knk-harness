# DECISIONS.md

ACCOUNT 도메인 백엔드의 중요한 결정을 날짜, 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 둔다. 여기에는 결정 당시의 이유와 변경 이력을 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 상태는 결정 당시 기준이다. 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.

<br>

### 2. 인증과 세션

**1. Kakao 로그인은 OIDC ID 토큰 방식으로 한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-31 |
| 상태 | 채택 |
| 배경 | Google 로그인은 ID 토큰 검증 한 가지 방식이었다. Kakao를 추가하면서 같은 구조로 둘지 Kakao의 사용자 조회 API를 쓸지 정해야 했다. |
| 채택 | Kakao도 OIDC ID 토큰을 검증한다. 공개 키 주소, 발급자, 허용 대상만 제공자별로 다르다. 검증기와 흐름은 같다. 동의항목은 요청하지 않아 제공자 쪽 식별자만 받는다. |
| 대안 | access 토큰으로 Kakao 사용자 조회 API를 호출하는 방식. 로그인마다 외부 호출이 추가돼 장애와 시간 초과를 처리할 범위가 늘어난다. HTTP 클라이언트와 실패 경로도 새로 생겨 채택하지 않았다. 이메일과 닉네임은 쓰지 않는 데이터다. 수집하면 심사 부담과 가입 이탈만 늘어나므로 채택하지 않았다. |
| 영향 | Kakao의 제공자 쪽 식별자는 앱마다 달라 허용 대상 목록에 단일 앱의 키만 넣어야 한다. 스키마 변경은 없다. |

**2. 계정 통합은 도입하지 않는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-31 |
| 상태 | 채택 |
| 배경 | 같은 사람이 Google과 Kakao로 각각 로그인하면 별개 계정이 된다. 이프와 스토리가 갈라진다. |
| 채택 | 갈라진 계정을 합치는 기능을 두지 않는다. 대신 로그인한 계정에 다른 제공자를 추가하는 계정 연동으로 계정이 갈라지는 일을 막는다. |
| 대안 | Kakao 이메일에는 검증 여부가 없고 동의항목도 요청하지 않으므로 이메일은 병합 키가 될 수 없다. 이메일 일치 시 자동 병합은 계정 탈취 경로가 된다. 같은 이메일 안내는 가입 여부를 드러내는 열거 오라클이 된다. 병합 API는 이프 로트 이관, 초대 그래프의 자기참조, 도달 집계 유니크 충돌, 이관 잠금과 정지 상태의 선택까지 새 정책이 필요하다. 본인확인 기반 통합은 실명과 전화번호 수집이 전제라 최소 수집 원칙과 충돌한다. |
| 영향 | 연동 해제도 두지 않는다. 해제 뒤 로그인이 새 계정을 만들어 다시 갈라지고 되돌릴 병합이 없기 때문이다. 수요가 확인되면 문의 기반 수동 처리를 우선한다. |

**3. 계정 연동은 재인증과 링크 코드의 2단계로 한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-31 |
| 상태 | 채택 |
| 배경 | 연동은 계정에 로그인 수단을 영구히 추가한다. 공용 기기에 남은 세션을 다음 사용자가 쓰면 일시적인 접근 권한이 영구적인 접근 권한으로 바뀐다. 소셜 신원 증명은 OAuth 콜백 시점에만 있어 한 요청에 두 제공자의 증명을 함께 받을 수 없다. |
| 채택 | 이미 연동된 제공자의 신선한 신원 증명으로 본인을 재확인하고 짧은 수명의 링크 코드를 발급한다. 연동 요청은 그 코드와 추가할 제공자의 증명을 함께 받는다. 코드는 헤더로만 전달하고 성공했을 때만 소비한다. 실패에는 세션 오류 코드를 쓰지 않는다. |
| 대안 | 세션만으로 연동을 허용하면 공용 기기 사용자를 보호할 수 없다. 한 요청에 두 증명을 받는 방식은 첫 증명을 두 번째 리다이렉트 너머까지 보관해야 한다. |
| 영향 | 끊긴 연동에 해당하는 소셜 계정은 연동하지 않고 거절한다. 끊긴 연동을 활성 연동으로 되돌려 연결하면 재가입 경로의 승계와 정지 판정을 건너뛰는 세탁 경로가 된다. 검증기에 인가 대상 검사를 더해 다른 앱이 우리 client ID를 대상으로 받은 증명을 막는다. |

**4. 동의 대기 코드로 가입 완료를 분리한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-05 |
| 상태 | 채택 |
| 배경 | 필수 동의 전에는 계정 행 자체를 만들지 않아야 했다. 신원 검증은 동의보다 먼저 끝나고 신원 증명은 저장할 수 없다. |
| 채택 | 소셜 인증은 신원 검증 뒤 필수 동의가 없으면 Redis 대기 코드를 발급한다. 동의 완료는 코드와 제출 버전을 받아 계정, 연동, 동의를 하나의 생성 트랜잭션으로 저장한 뒤 로그인 후속 처리를 실행한다. 기존 회원의 재동의는 같은 계정에 기록한다. 코드는 해시를 키로 쓴다. 헤더로만 받으며 성공 시에만 소비한다. |
| 대안 | 계정 상태에 미동의 값을 추가하는 방식. 미동의 계정을 먼저 만들어야 한다. 모든 회원 조회 경로에서 새 상태도 처리해야 하므로 채택하지 않았다. 생성 트랜잭션 밖에서 동의를 기록하는 방식은 계정만 남는 경우를 만든다. |
| 영향 | 미동의 회원의 일반 API 접근을 서버 게이트로 제한한다. 허용 목록과 기본 꺼짐 스위치로 기존 세션의 재동의와 단계적 전환을 지원한다. 호환 로그인은 웹과 Android 전환 동안 유지한다. 로그인 뒤에만 동의를 받던 계약을 대체한다. |

**5. 갱신 토큰 동시 회전에 재사용 유예를 둔다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-15 |
| 상태 | 채택 |
| 배경 | 접근 토큰이 만료된 직후 웹 BFF가 같은 갱신 토큰으로 회전 요청을 동시에 여러 건 보냈다. 첫 요청 이후의 나머지 요청을 재사용으로 판정해 세션을 폐기했다. 사용자는 로그아웃됐다. 요청 간격은 수 밀리초에서 1초였다. |
| 채택 | 회전 시 제시 토큰 해시에 대응하는 새 갱신 토큰 원문을 짧은 유예 동안 보관한다. 유예 안의 재사용에는 같은 원문과 새 접근 토큰을 돌려주고 세션은 바꾸지 않는다. 유예 밖과 후속 회전 뒤의 재사용은 종전대로 세션을 폐기한다. 하나의 Redis 스크립트에서 판정한다. |
| 대안 | 클라이언트 안에서 진행 중인 갱신 요청 하나를 공유하게 해도 BFF 밖 클라이언트와 여러 탭의 동시 요청까지 막지는 못한다. 유예 응답에 다른 새 토큰을 발급하면 쿠키 덮어쓰기 순서에 따라 과거 토큰이 남아 재사용 탐지가 재발한다. 접근 토큰 수명 연장은 빈도만 줄인다. 재사용 탐지를 제거하면 탈취에 대응할 수 없다. |
| 영향 | 평소 해시만 저장하던 Redis에 새 원문이 유예 동안 남는다. 유예 안의 과거 토큰 보유자는 현재 토큰을 받을 수 있지만 그 토큰은 직전까지 유효했으므로 유예 없이도 회전할 수 있었다. 유예 적용은 구조화 로그로 기록한다. 요청과 응답 형식이 같아 클라이언트를 함께 배포할 필요가 없다. |

### 3. 세션 조회와 프로필

**6. 세션 조회 응답에 잔액과 당일 출석 여부를 싣는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-08 |
| 상태 | 채택 |
| 배경 | 앱 진입 시 세션 복원과 함께 이프 잔액과 출석 상태를 그려야 했다. 당일 출석 여부는 조회 수단이 없었고 출석 요청은 조회가 아니라 적립이다. |
| 채택 | 세션 조회 응답에 잔액과 당일 출석 여부를 포함한다. 출석 여부는 출석 보상과 같은 멱등 키를 가진 원장 행이 있는지로 판정한다. 부수효과는 없다. |
| 대안 | 출석 여부 전용 조회는 초기 데이터 조회의 왕복 횟수가 3회로 늘어난다. 진입 시 출석 요청을 자동 호출해 결과로 판별하는 방식은 사용자가 누르기 전에 보상이 지급된다. |
| 영향 | 세션 조회가 지갑과 원장을 함께 읽는다. 이후 연동 제공자 목록과 인라인 썸네일도 같은 응답에 더해 연동 상태 전용 조회를 두지 않았다. |

<br>

**7. 프로필 이미지는 닉네임 명사에 1:1로 대응하는 프리셋으로 배정한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-08 |
| 상태 | 채택 |
| 배경 | 실명과 외부 사진 노출을 피하려고 소셜 프로필 대신 랜덤 닉네임을 발급한다. 닉네임은 형용사 40개와 명사 40개의 조합이다. 이미지도 함께 발급해야 했다. |
| 채택 | 명사마다 팀이 만든 이미지 1개를 대응시켜 가입 시 배정한다. 원본은 서버 정적 자산으로 제공하고 48×48 썸네일을 기동 시 만들어 회원 행에 저장한다. |
| 대안 | 풀에서 무작위로 배정하면 닉네임과 무관한 이미지가 붙어 정체성이 없다. 제작량도 줄지 않는다. 사용자 업로드는 검수와 저장소 부담이 생긴다. |
| 영향 | 명사를 추가하면 이미지도 추가해야 한다. 대응이 없으면 기본 아바타다. 저장된 URL이 전체 값이라 CDN 전환은 기본 URL 변경만으로 된다. |

<br>

**8. 닉네임은 정규화 기준으로 유일하며 회원이 직접 바꾼다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-05 결정, 2026-09-12 접미와 공백 규칙 갱신 |
| 상태 | 채택 |
| 배경 | 공개 스토리의 작성자 표시가 닉네임뿐이라 같은 이름이면 사칭을 구분할 수 없었다. 가입 시 받은 랜덤 닉네임을 바꿀 수단도 필요했다. |
| 채택 | 소문자로 바꾸고 공백을 지운 정규화 키에 부분 유니크 인덱스를 둔다. 입력은 2~20자의 완성형 한글, 영문, 숫자만 받고 공백은 거절한다. 프로필 수정 API로 닉네임과 프리셋 이미지를 바꾼다. 가입 발급도 충돌 시 다시 뽑고 그래도 충돌하면 구분자 없는 숫자 4자리를 붙인다. 기존 중복 닉네임은 같은 규칙의 접미사를 붙여 정리했다. |
| 대안 | 순차 PK 접미는 내부 ID를 노출하고 허용 문자 밖의 구분자를 쓴다. 변경 주기 제한과 금칙어 필터는 두지 않고 유사 문자 사칭은 신고로 대응한다. |
| 영향 | 닉네임을 바꾸면 소유 스토리 전체의 재색인을 요청한다. 공개 전환과의 경쟁에 대응하도록 비공개와 초안도 포함한다. 닉네임을 바꿔도 이미지는 다시 매핑하지 않는다. |

### 4. 게스트 데이터와 핸드오프

**9. 게스트와 회원의 교차 접근을 차단한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-07 |
| 상태 | 채택 |
| 배경 | 이관 1회 제한만으로는 회원이 게스트 콘텐츠의 식별자로 소유자 없는 채팅과 스토리를 직접 쓰는 우회가 남았다. 소유자 없는 콘텐츠에 회원 이프가 소모되는 비정상 상태였다. |
| 채택 | 소유자 없는 콘텐츠는 익명 요청만, 회원 소유 콘텐츠는 소유자만 허용한다. 회원은 이관으로 소유권을 얻은 뒤 접근한다. 게스트끼리의 접근은 서버가 게스트를 식별할 수 없어 막지 않는다. |
| 대안 | 익명과 회원 모두 허용하는 방식은 이관 제한을 무력화한다. 콘텐츠에 기기 식별자를 저장해 게스트끼리도 막는 방식은 개인정보를 저장하지 않는 경계를 깬다. |
| 영향 | 로그인 상태에서 게스트 시절 주소로 들어가면 거절되므로 클라이언트 안내가 필요하다. |

**10. 이관은 계정당 성공 1회와 시도 5회로 제한한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-07-07 결정, 2026-07-08 시도 상한 추가 |
| 상태 | 채택 |
| 배경 | 횟수 제한 없는 이관은 기기를 갈아타며 게스트 체험으로 만든 콘텐츠를 반복해 옮기는 파밍 경로였다. 항목별 결과 응답은 소유 상태를 알려주는 열거 오라클이 될 수 있었다. |
| 채택 | 한 건이라도 이관되면 그 계정의 추가 이관을 차단한다. 이관된 항목이 없으면 시도 상한 전까지 다시 요청할 수 있다. 호출 자체는 계정당 5회까지만 평가하고 초과하면 닫힌 응답을 반환한다. 닫힌 계정의 재호출은 오류가 아니라 빈 결과다. |

**19. 게스트 서버 이벤트의 `device_id`는 기기 식별자 원본으로 보낸다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-22 |
| 상태 | 채택 |
| 배경 | 서버 이벤트는 게스트를 pepper 해시로 Amplitude `device_id`에 보냈다. 웹과 Android는 같은 기기 식별자의 원본을 `X-Manyak-Device-Id` 헤더와 Amplitude SDK `device_id`에 쓴다. 서버 이벤트만 다른 값이라 클라이언트 프로필과 병합되지 않았고, 서버 이벤트만 가진 사용자가 최근 30일 신규의 약 21%였다. |
| 채택 | 서버 분석 이벤트의 Amplitude `device_id`는 게스트와 회원 모두 요청 헤더 `X-Manyak-Device-Id` 원본으로 통일한다. 헤더가 없으면 게스트는 `unknown`, 회원은 생략한다. 로그 MDC, Sentry, `ai_call_logs`, 체험 한도 키, 게스트 동의, AI 서버 전달, 이벤트 프로퍼티 `device_id_hash`는 해시를 유지한다. 분석 이벤트 경로에서는 원본을 저장하지 않고 요청 처리 중 Amplitude 발송까지만 전달한다. 동의 대기의 원문 보관은 기존 보존 규칙 그대로다. 같은 원본을 클라이언트가 이미 같은 Amplitude 프로젝트에 직접 보내므로 새 수신자와 항목이 생기지 않는다. 회원 이벤트까지 넓힌 이유는 회원 이벤트만 해시를 쓰면 Amplitude에 그 회원의 기기가 원본과 해시 두 개로 잡혀 플랫폼과 국가가 빈 기기가 생기기 때문이다. 원본을 Amplitude에 보내기로 정한 이상 회원으로 넓혀도 새 노출이 없다. |
| 대안 | 클라이언트가 서버와 같은 해시를 보내는 방식은 pepper가 서버 비밀이라 불가능하고, pepper 없는 해시는 원본과 같은 보호 수준이라 효과가 없다. 서버 해시를 유지하면 병합이 불가능하다. 게스트 이벤트만 원본으로 바꾸는 방식은 회원의 기기 프로필이 둘로 갈라진다. 서버 해시의 목적은 서버 내부 기록에 원본을 남기지 않는 것이고 이번 변경으로 깨지지 않는다. |
| 영향 | 변경 이후의 서버 이벤트부터 클라이언트 프로필과 병합된다. 과거 이벤트는 재병합하지 않는다. 알림 서비스가 호출하는 내부 API는 원본 헤더가 없어 헤더 없음 규칙을 따른다. AI 서버 전달, DB 저장, 클라이언트는 바꾸지 않는다. 처리방침 문구 정정은 웹 담당이다. |

**20. 앱 요청의 서버 분석 이벤트에 `platform`과 `app_version`을 싣는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-28 |
| 상태 | 채택 |
| 배경 | 서버 분석 이벤트는 `platform`을 보내지 않는다. Amplitude는 플랫폼이 없는 이벤트에 그때까지 그 사용자에게 아는 플랫폼을 붙인다. 앱 SDK는 이벤트를 모아 늦게 올려서 그 전에 도착한 서버 가입 이벤트가 플랫폼 없음으로 잡혔다. 10/21~27 플랫폼 없음 가입 26명 가운데 17명은 실제로 앱 사용자와 병합된 계정이었다. 관리자 신규 가입자의 플랫폼 값에서 플랫폼 없음이 부풀고 앱이 작게 나온다. Android 앱은 모든 요청에 `X-Manyak-App-Version`을 싣고 웹은 싣지 않는다. |
| 채택 | 요청에 `X-Manyak-App-Version` 헤더가 있으면 서버 분석 이벤트의 Amplitude 기기 필드 `platform`에 `Android`, `app_version`에 헤더 값(1~50자일 때만)을 싣는다. 헤더가 없으면 둘 다 생략하고 웹은 지금처럼 클라이언트 이벤트와의 병합을 따른다. 발행기 하나에서 처리해 ACCOUNT, CHAT, STORY, PAYMENT의 서버 이벤트에 같이 적용한다. |
| 대안 | 서버가 `User-Agent`로 플랫폼을 추정하는 안은 웹뷰와 브라우저의 값이 섞여 판정 규칙이 새로 필요하다. 웹 요청에도 `Web`을 싣는 안은 웹 요청을 가릴 헤더가 없어 헤더 없는 앱 내부 호출과 알림 서비스 호출까지 `Web`으로 잡힌다. 관리자 지표에서 플랫폼 없음을 Android로 넘겨 세는 안은 웹 사용자의 같은 지연과 구분되지 않는다. |
| 영향 | 배포 뒤 앱 요청의 서버 이벤트부터 Android로 잡히고 지난 이벤트는 바뀌지 않는다. ADMIN의 신규 가입자, 채팅 턴 도달률, 채팅 옵션 비중, 리텐션 가입자와 채팅 시작자의 Android 값이 늘고 플랫폼 없음이 준다. 앱 버전 헤더 값은 이벤트에만 싣고 저장하지 않는다. 클라이언트는 바꾸지 않는다. |

### 9. 계정 상태

**18. 계정 정지와 해제는 관리자 API로 하고 관리자 역할 보유자는 정지하지 않는다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택 |
| 배경 | 계정 정지는 운영자가 저장소에서 상태 컬럼을 직접 바꾸는 방식이라 DB에 접근하는 한 사람만 할 수 있었고 누가 왜 정지했는지 남지 않았다. 해제도 같은 방식이었다. 관리자 역할 체계가 ADMIN 세트로 생겼다. |
| 채택 | 활성 계정의 정지와 정지 계정의 해제를 관리자 API로 한다. 사유가 필수이고 전후 상태와 함께 관리자 도메인의 감사 로그에 남는다. 사용자 행을 잠근 뒤 상태를 다시 확인해 같은 상태로의 재요청과 탈퇴 계정을 거절한다. 관리자 역할이 있는 회원은 자기 자신을 포함해 정지할 수 없고 운영자가 역할을 회수한 뒤에만 정지한다. 정지는 세션을 폐기하지 않으며 쓰기 거절과 회전 시 세션 폐기는 기존 집행 규칙이 맡는다. |
| 대안 | 정지 시 세션을 즉시 폐기하는 안은 정지 계정도 로그인과 조회는 할 수 있다는 기존 규칙과 어긋나고 토큰 회전이 어차피 세션을 폐기한다. 관리자끼리 정지를 허용하는 안은 관리자 화면 하나가 탈취되면 나머지 관리자를 전부 잠글 수 있다. 정지 사유를 회원 행에 두는 안은 사유 변경 이력이 남지 않아 감사 로그에만 둔다. |
| 영향 | 계정 상태를 저장소에서 직접 바꾸지 않는다. 재가입 시 정지 승계 규칙은 그대로다. 관리자 계정을 정지하려면 역할 회수가 먼저라 두 단계가 된다. |
