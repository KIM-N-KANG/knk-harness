# 5-2 동시성

이 문서는 ACCOUNT 도메인의 동시 요청 처리 규칙을 정한다. 사용자 행 잠금, 멱등과 1회 처리, 유니크 위반, 토큰 회전의 원자성, 핸드오프 상태 전이, 수용한 경쟁 조건을 다룬다.

흐름별 단계와 트랜잭션 경계는 처리 흐름에, 코드와 토큰의 수명은 오류 처리에 있다. ([4-1-5 로그인 후속 처리](4-1-PIPELINES.md#4-1-5-로그인-후속-처리), [4-1-6 계정 생성과 재가입](4-1-PIPELINES.md#4-1-6-계정-생성과-재가입), [5-3-5 재시도와 시간 한도](5-3-ERROR-HANDLING.md#5-3-5-재시도와-시간-한도))

<br>

### 5-2-1 사용자 행 잠금

회원 행에는 버전 컬럼이 없다. 갱신 시 모든 컬럼을 읽은 스냅샷으로 덮어쓴다. 표식을 바꾸는 경로는 모두 사용자 행에 비관적 쓰기 잠금을 걸어 같은 계정의 동시 갱신을 직렬화한다. 잠금 뒤 상태를 다시 검사한다.

| 경로 | 막는 경쟁 조건 |
|---|---|
| 탈퇴 | 초대 코드 제출과 겹치면 방금 기록한 초대자가 비워져 재가입 계정이 초대 자격을 되찾는 경쟁 조건<br>재가입 시각, 보상 신원, 체험 스냅샷 시각, 이관 횟수, 초대 코드도 같은 위험 |
| 이관 | 두 요청이 모두 잠기지 않은 계정으로 판정해 1회 제한을 넘는 경쟁 조건 |
| 초대 코드 발급 | 동시 조회가 각자 다른 코드를 만들어 먼저 공유한 코드가 어떤 회원과도 맞지 않게 되는 경쟁 조건 |
| 초대 코드 제출 | 같은 계정의 동시 제출이 자격 판정, 관계 저장, 적립을 두 번 하는 경쟁 조건 |
| 프로필 수정 | 같은 계정의 동시 변경 |
| 페르소나 생성 | 동시 생성이 상한을 넘는 경쟁 조건<br>잠금 순서는 사용자 행 다음 페르소나 행 |
| 회원 동의 조회와 기록 | 탈퇴 커밋 뒤에 동의 행이 들어가는 경쟁 조건 |
| 동의 완료의 기존 회원 | 동의 삽입과 로그인 시각 갱신이 탈퇴와 겹치는 경쟁 조건 |
| 재가입 | 이전 소유자의 사용자 행을 잠가 묘비 묶음 이동을 직렬화<br>소셜 행을 각각 잠그면 제공자별 획득 순서가 달라 교차 대기 |

잠금 순서는 사용자 행이 먼저이고 지갑, 소셜 연동, 페르소나, 푸시 토큰이 그 뒤다. 모든 경로의 잠금 순서가 같으므로 교차 대기 고리가 생기지 않는다. 초대 제출의 두 지갑 잠금은 내부 ID 오름차순으로 잡는다.

### 5-2-2 멱등과 1회 처리

| 대상 | 처리 |
|---|---|
| 가입 보상 | 멱등 키 `signup:{보상 신원}`<br>로그인마다 요청하고 원장이 1회만 적립 |
| 초대 보상 | 멱등 키 `invite:{초대자 신원}:{제출자 신원}:{수혜자 신원}`<br>쌍당 수혜자별 1회 |
| 회원 체험 스냅샷 | 회원 카운터가 설정되지 않았을 때만 값을 쓰고 완료 시각은 비어 있을 때만 기록<br>동시 첫 로그인에도 안전 |
| 핸드오프 소비 | 소비권을 한 번만 선점<br>같은 코드를 실은 동시 로그인 중 하나만 이관하고 나머지는 기록하지 않음<br>종료 상태의 코드는 재이관하지 않음 |
| 동의 대기 코드 | 성공 시에만 삭제<br>소비 전에 코드를 읽은 동시 완료의 토큰 중복 발급은 허용 |
| 링크 코드 | 성공 시에만 삭제 |
| 동의 기록 | PK 충돌을 무시하는 조건부 삽입으로 최초 시각 유지 |
| 이관 항목 | 소유자가 비어 있을 때만 바꾸는 조건부 갱신<br>갱신 0행이면 실제 소유자를 다시 읽어 결과를 정함 |
| 로그인 시각 갱신 | 묘비가 아닐 때만 바꾸는 조건부 단일 컬럼 갱신<br>엔티티 갱신으로 쓰면 그 사이 커밋된 탈퇴의 묘비와 이메일 삭제가 되돌아감 |
| 로그아웃 | 없는 토큰도 같은 응답 |

### 5-2-3 유니크 위반 처리

| 대상 | 처리 |
|---|---|
| 소셜 연동 `(provider, provider_user_id)` | 동시 첫 로그인의 위반은 계정 생성의 독립 트랜잭션 안에서 처리하고 새 시각으로 재조회해 상대가 만든 계정 재사용<br>동의 완료는 두 번 더 재시도 |
| 묘비 재사용 | 갱신이라 유니크가 막지 못함<br>이전 소유자 행 잠금 뒤 요청한 연동이 이미 살아 있으면 실패시켜 고아 계정을 남기지 않음 |
| 닉네임 정규화 키 | 가입 발급은 재조회 뒤 한 번 더 생성<br>프로필 수정은 트랜잭션 밖에서 잡아 중복 거절로 변환 |
| 계정 연동 `(user_id, provider)`와 `(provider, provider_user_id)` | 사전 판정 뒤 삽입이 실패하면 충돌 판정을 다시 해 사유 확정<br>트랜잭션을 열지 않아 롤백 전용 상태로 바뀌지 않음 |
| 초대 코드 | 사전 존재 확인 10회와 유니크 제약 |
| 동의 PK | 충돌 무시 삽입 |

### 5-2-4 토큰 회전의 원자성

회전, 유예 판정, 재사용 탐지, 계열 폐기는 하나의 Redis 스크립트로 실행한다.

| 상황 | 처리 |
|---|---|
| 같은 갱신 토큰의 동시 회전 | 첫 요청이 회전하고 유예 키에 새 원문을 보관<br>유예 안의 나머지 요청은 보관된 같은 원문과 새 접근 토큰을 받음<br>계열과 수명은 바꾸지 않음 |
| 유예 뒤 재사용 | 계열 전체 폐기 |
| 회전과 로그아웃의 경쟁 | 로그아웃이 계열을 지우므로 회전으로 발급된 새 토큰도 함께 무효 |
| 과거 토큰 매핑의 수명 | 유예보다 짧게 남으면 유예 길이까지 늘려 유예 판정이 매핑 소멸로 실패하지 않게 함 |
| 탈퇴와 정지 | 회전 뒤 계정을 읽어 거부하면 새 토큰이 속한 계열을 폐기 |

<br>

### 5-2-5 핸드오프 상태 전이

| 상황 | 처리 |
|---|---|
| 확인과 소비의 경쟁 | 확인은 소비권이 없을 때만 남은 수명을 유지한 채 착지 상태를 기록<br>소비권 확인, 수명 조회, 쓰기를 하나의 스크립트로 묶음 |
| 이관 실패 | 소비권 삭제로 재시도 허용 |
| 결과 저장 실패 | 소비권은 유지하고 저장만 3회 재시도<br>그래도 실패하면 소유권은 옮겨졌으나 상태는 대기로 남음 |

<br>

### 5-2-6 수용한 경쟁 조건

| 상황 | 수용 이유 |
|---|---|
| 계정을 읽은 뒤 토큰 발급 전에 탈퇴가 커밋됨 | 결과는 거부되는 토큰<br>로그인 경로에 상시 잠금을 두는 비용이 더 큼 |
| 초대 제출과 초대자 탈퇴나 정지가 겹침 | 초대자 행을 잠그지 않아 1건이 통과할 수 있음<br>잠그면 교차 대기 경로 |
| 같은 초대자의 보상이 진행 중일 때 탈퇴 후 재가입한 새 계정의 보상 | 월 상한을 1건 초과할 수 있음<br>보상 신원 공통 잠금은 새 교차 대기 경로 |
| 동의 완료의 동시 요청 | 코드 소비 전에 둘 다 코드를 읽으면 토큰이 두 번 발급됨<br>보상, 스냅샷, 동의는 멱등이므로 데이터는 1회만 기록 |
