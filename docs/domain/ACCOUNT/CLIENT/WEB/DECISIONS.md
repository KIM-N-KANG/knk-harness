## W-002. 게스트 서재 초기 상태를 세 가지로 구분

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문 W:102](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L102-L120)
- **맥락:** SSR 시점에는 localStorage를 읽을 수 없습니다.
- **결정:** `null`은 미확정, 빈 배열은 빈 서재, 값이 있는 배열은 조회 대상으로 구분합니다.
- **이유:** 빈 배열 하나로 초기화하면 데이터가 있는 사용자에게도 빈 서재가 먼저 깜빡입니다.
- **주요 영향:** 목록과 온보딩은 저장소 확인 뒤에 판정합니다.

- **주요 영향:** BFF가 스트리밍 전달·선제 재발급을 소유하고 회원 판정은 별도 응답에 의존합니다.

<a id="w-011"></a>

## W-011. 동의 전 로그인은 탭 표시로 판정해 fail-closed 로그아웃

- 결정일: 2026-09-19 · 기록 확정 상태: Accepted
- 근거: [웹 사용자 모델](2-2-REQUIREMENTS.md#2-2-1-게스트와-회원) · [동의 게이트](4-3-STATE-MANAGEMENT.md#4-3-3-회원-동의-상태)
- **맥락:** 게스트 제작·채팅 체험을 신규 경로에서 없애고 로그인 직후 명시 동의를 받게 되면서, 동의를 마치지 않은 로그인이 탭을 닫아도 쿠키로 남는 문제가 생겼습니다. 서버는 미동의 회원의 다른 API를 막지 않고, 브라우저 쿠키는 탭 단위로 격리할 수 없습니다.
- **결정:** 동의 상태는 루트의 동의 게이트 한 곳에서 `GET /users/me/consents`로 판정하고, 회원 기능·로그인 직후 부수 효과·회원 전용 자동 조회는 모두 `isMember`(인증 + 동의 완료)로만 엽니다. OAuth 시작 직전에 `sessionStorage`에 탭 로그인 표시를 남기고, 인증 상태인데 필수 동의가 남았으며 표시가 없는 일반 진입은 이전 탭의 미완 로그인으로 보고 로그아웃합니다. 공개 법적 문서 경로는 이 판정에서 제외합니다. 게스트 보호 기능 진입은 요청·이동 전에 `requireLogin`으로 한 번 확인합니다.
- **이유:** 서버가 막지 않는 상태에서 화면별로 세션·동의를 따로 판정하면 누락된 진입점이 남습니다. `localStorage`나 쿠키 플래그는 탭을 닫아도 남아 "탭 종료 시 로그인 미유지"를 만들 수 없고, `sessionStorage`는 OAuth 복귀·같은 탭 새로고침을 이어 주면서 다른 탭·새 브라우저 실행에는 남지 않는 가장 작은 장치입니다. 문서 탭이 원래 탭의 쿠키를 지우는 사고를 막으려면 법적 문서 경로만 예외로 두는 편이 단순합니다.
- **주요 영향:** 동의 완료 여부의 정본은 서버 조회이며 탭 표시는 판정 보조라 탭 복원·복제·`noopener` 없는 새 창에서 복사될 수 있음을 문서에 남깁니다. 게스트 체험 한도 선차단·한도 시트·`client_guestLimitDialog_*` 이벤트는 신규 경로에서 사라지고, 회원 402는 이프 부족 토스트만 남습니다. 예전 게스트 로컬 데이터·핸드오프 이관은 복구용으로 유지합니다. W-009의 인앱 게스트 체험 허용은 열람만 허용하는 것으로 좁아집니다.

<a id="w-012"></a>

## W-012. 게스트 체험은 별도 동의 후 허용

- 결정일: 2026-09-20, 기록 확정 상태: Accepted
- 근거: [게스트 이용 동의](3-2-INTERACTION-FLOWS.md#3-2-1-게스트-이용-동의), [게스트 동의 시트](4-4-EXECUTION.md#4-4-3-동의-게이트와-이관)
- **대체 범위:** W-011 중 게스트의 제작과 채팅 진입에 로그인을 강제하고 체험을 열람으로 제한한 부분만 대체합니다. 회원의 서버 동의 판정과 동의 전 세션 정책은 유지합니다.
- **맥락:** 로그인 전에도 제작과 채팅을 체험하게 하되 게스트에게 적용되는 이용 조건과 개인정보 수집 및 이용, 만 14세 이상 확인을 먼저 고지해야 합니다. 게스트 동의 API는 아직 없습니다.
- **결정:** 제작 진입 및 채팅 전송 앞에서 공용 바텀 시트를 열고 상세 보기와 단일 동의 버튼을 제공합니다. 동의 버전과 시각은 브라우저에 저장하며 동의하면 대기 중인 동작 하나만 이어갑니다. 체험 한도는 서버 정책을 따르고 소진 시 로그인을 안내합니다.
- **이유:** 회원 동의 API를 게스트에게 재사용하거나 가상 API를 만드는 대신 현재 가능한 로컬 흐름만 구현합니다. 시크릿 모드를 탐지하지 않고 브라우저 저장소 격리로 새 시크릿 세션에서 다시 동의받습니다.
- **주요 영향:** 로컬 기록은 서버 증빙이나 보안 경계가 아닙니다. 저장소를 사용할 수 없으면 현재 페이지에서만 동의를 유지합니다. API 제공 시 서버 기록 성공 기준으로 교체하고, 문서 개정 공개 시 회원 요구 버전과 배포 일정을 조율합니다.

## W-013. 게스트 제작 동의는 스토리라인 생성 직전에 확인

- 결정일: 2026-09-20, 기록 확정 상태: Accepted
- 근거: [게스트 이용 동의](3-2-INTERACTION-FLOWS.md#3-2-1-게스트-이용-동의)
- **대체 범위:** W-012의 제작 화면 진입 전 동의만 대체하며 채팅, 회원 동의와 저장 방식은 유지합니다.
- **결정과 이유:** 먼저 키워드를 입력할 수 있도록 제작 진입과 초안 재개는 허용하고, 입력 검증을 통과한 스토리라인 생성 버튼에서 서버 요청 직전에 동의를 받습니다. 이미 있는 생성 요청 가드를 재사용합니다.
- **주요 영향:** 취소 시 입력과 단계를 유지하며 동의 후 대기 요청 하나만 실행합니다. 동의 시트가 열린 동안 제작 화면의 뒤로가기 가드는 처리하지 않아 종료 확인창이 겹치지 않게 합니다.

- **맥락:** 기존 외부 전환 직행은 로그인 화면을 건너뛰며 원래 인앱의 회원 세션을 만들지 않습니다.
- **결정:** KakaoTalk, Instagram, Threads는 OS에 관계없이 일반 로그인 화면을 유지합니다. Google은 기존 Auth.js 팝업, Kakao는 같은 탭의 redirect로 시작하며 신규 핸드오프를 만들지 않습니다. PKCE, state, nonce 및 기존 callback과 백엔드 세션 발급을 재사용합니다.
- **이유:** 별도 SDK나 코드 교환기를 추가하지 않고 기존 인증 보안 경계에서 인앱 로그인을 시도할 수 있습니다.
- **주요 영향:** W-009의 신규 로그인 외부 전환을 대체하고 W-010의 기존 핸드오프 복구는 유지합니다. 완료 메시지는 origin, source와 시도 ID를 검증한 후 원래 창의 Auth.js 세션 및 인증 API로 재확인합니다. 창 연결과 쿠키 저장소 공유 및 실제 앱의 인증 허용은 별도 실기기 검증 대상입니다.

## W-022. 동의 전에는 세션을 만들지 않고 Credentials로 가입을 완료

- 결정일: 2026-10-05, 기록 확정 상태: Accepted
- 근거: [공통 동의 모델](../3-2-INTERACTION-FLOWS.md#3-2-1-로그인과-필수-동의), [웹 로그인과 회원 이관](3-2-INTERACTION-FLOWS.md#3-2-2-로그인과-회원-이관), [토큰 세션](4-4-EXECUTION.md#4-4-2-토큰-재발급과-종료), [백엔드 동의 후 가입 완료 흐름](../../BACKEND/4-1-PIPELINES.md#4-1-3-동의-완료)
- **대체 범위:** W-011 중 OAuth 복귀 직후 세션을 만들고 그 세션에서 동의를 받는 부분만 대체합니다. 로그인한 세션에 동의가 남은 경우의 탭 표시 판정과 fail-closed 로그아웃은 유지합니다.
- **맥락:** 서버가 소셜 인증과 가입 완료를 나눠 필수 동의 전에는 계정과 토큰을 만들지 않게 됐습니다. 웹은 OAuth 콜백의 `jwt` 콜백에서 백엔드 로그인과 Auth.js 세션을 함께 만들고 있어, 동의 대기 응답을 받으면 세션 없이 콜백을 끝내고 동의 후에 세션을 만들 경로가 필요했습니다.
- **결정:** 소셜 인증은 Auth.js `signIn` 콜백에서 호출합니다. 동의가 남으면 대기 코드를 HttpOnly 쿠키에 담고 원래 `callbackUrl`을 반환해 세션 없이 돌려보냅니다. 동의 제출은 Credentials 프로바이더 `signup-consent`의 `authorize`가 완료 API를 호출하고 성공했을 때만 세션을 만듭니다. 대기 만료와 약관 개정은 시트를 닫고 다시 로그인하게 합니다.
- **이유:** `signIn` 콜백의 문자열 반환과 Credentials 프로바이더는 Auth.js가 지원하는 경로라 세션 JWT를 직접 인코딩하지 않아도 됩니다. `jwt` 콜백에서 예외로 돌려보내면 정상 흐름마다 Auth.js 오류 로그가 남고, 빈 세션을 먼저 만들면 동의 전 세션이 생겨 서버 계약과 어긋납니다. 웹은 ID 토큰을 보관하지 않으므로 서버 계약의 재인증을 OAuth 재시작으로 대신합니다.
- **주요 영향:** 동의 전에는 세션이 없어 탭 표시가 복사돼도 회원 기능이 열리지 않습니다. 가입 대기 확인용 BFF 라우트와 팝업 완료의 `consentRequired` 신호가 생깁니다. 소셜 인증 실패의 `/login?error=` 값이 `Configuration`에서 `AccessDenied`로 바뀝니다. `signIn`과 `jwt` 콜백이 같은 `account` 객체를 받는 @auth/core 동작에 기대므로 Auth.js를 올릴 때 확인합니다.

## W-028. 히스토리 이동으로 돌아온 문서와 OAuth 오류 화면에서 끝내지 않은 로그인을 정리

- 결정일: 2026-10-07, 기록 확정 상태: Accepted
- 근거: [웹 로그인과 회원 이관](3-2-INTERACTION-FLOWS.md#3-2-2-로그인과-회원-이관), [동의 게이트](4-3-STATE-MANAGEMENT.md#4-3-3-회원-동의-상태), [C-010](../DECISIONS.md#c-010)
- **맥락:** 동의 시트는 `useCloseOnBack`으로 히스토리 항목을 하나 쌓고 그 `popstate`를 거절로 처리합니다. OAuth 복귀 화면은 사용자 조작 없이 시트를 열기 때문에 Chrome이 그 화면을 뒤로가기 버튼에서 건너뛰어, 거절 처리 없이 Google 화면으로 떠났습니다. 탭 로그인 표시와 가입 대기 쿠키가 남아 앱 화면으로 돌아오면 시트가 다시 떴고, 다시 뜬 시트도 같은 이유로 건너뛰어졌습니다. Google 화면에서 계정을 다시 고르면 Auth.js의 PKCE·state 쿠키가 이미 소비되어 `/login?error`로 돌아오고, 남은 대기로 실패 토스트와 가입 시트가 함께 떴습니다.
- **결정:** 동의 게이트가 마운트될 때 navigation type이 `back_forward`이거나 `pageshow`가 `persisted`(bfcache 복원)이면, 남은 탭 표시를 끝내지 않은 로그인으로 보고 표시를 지우고 가입 대기를 취소합니다. bfcache 복원은 이전 판정을 들고 있으므로 정리 뒤 다시 불러옵니다. 로그인 화면이 `?error`로 열려도 같은 정리를 합니다. 정리 뒤 판정은 기존 경로를 따라 세션이 없으면 게스트, 동의가 남은 세션이면 fail-closed 로그아웃입니다.
- **이유:** 히스토리 건너뛰기는 남용을 막는 브라우저 정책이라 `pushState`로 우회할 수 없습니다. 시트 화면을 뒤로가기로 떠났다가 돌아온 것은 동의를 이어 가지 않겠다는 신호로 볼 수 있습니다. 새로고침은 navigation type이 `reload`라 기존 계약대로 시트를 이어 가고, 인앱 팝업 로그인의 원래 탭 이동도 히스토리 이동이 아니라 영향이 없습니다. `pagehide`에서 취소하면 새로고침과 구분할 수 없어 택하지 않았습니다.
- **주요 영향:** 첫 뒤로가기가 Google 화면으로 가는 동작은 그대로이며, 거기서 돌아오면 게스트 화면입니다. 시트를 연 채 다른 화면으로 갔다가 뒤로가기로 돌아와도 시트가 다시 뜨지 않으므로 다시 로그인해야 합니다. E2E의 `page.goBack()`은 CDP로 항목을 직접 지정해 Chrome의 건너뛰기를 재현하지 못하므로 그 부분은 실기기로 확인합니다.

## W-032. 소셜 로그인은 팝업을 기본으로 하고 복귀는 로그인 화면 칸을 교체

- 결정일: 2026-10-09, 기록 확정 상태: Accepted
- 근거: [웹 인앱 로그인 계약](3-2-INTERACTION-FLOWS.md#3-2-3-팝업과-계정-연동), [소셜 로그인 인증 팝업](4-4-EXECUTION.md#4-4-5-인증-팝업), [W-031](../../../APP/CLIENT/WEB/DECISIONS.md#w-031)
- **맥락:** 일반 브라우저의 소셜 로그인은 같은 탭에서 OAuth 화면으로 떠나 복귀해, 히스토리가 `[이전 화면, 로그인, 인증 화면, 복귀 화면]`이 됐습니다. 로그인 직후 뒤로가기는 인증 화면으로 돌아갔다가 다시 리다이렉트되는 함정이었고, 인앱 Google용 팝업 로그인은 이미 실기기에서 검증돼 있었습니다.
- **결정:** 인앱의 Kakao를 제외한 모든 소셜 로그인은 팝업을 먼저 시도하고, 일반 브라우저에서 팝업이 차단되면 같은 탭으로 폴백합니다. 팝업 성공 복귀는 `location.assign` 대신 `location.replace`로 로그인 화면 칸을 복귀 화면으로 바꿉니다.
- **이유:** 같은 탭 OAuth가 남긴 인증 화면 항목은 페이지 쪽에서 지울 수 없습니다. 팝업은 원래 탭의 히스토리를 건드리지 않고, 기존 검증 로직(세션 재조회, 회원 ID 일치, COOP 대비)을 그대로 씁니다.
- **주요 영향:** 데스크톱 브라우저에서 팝업 창이 뜹니다. 카카오톡 인앱의 Kakao는 그대로이며 Kakao 팝업은 실기기 확인이 필요합니다. 로그인 화면에서 시작한 로그인은 복귀 뒤 뒤로가기가 로그인 화면 이전 화면으로 갑니다.

## W-034. refresh 재발급은 브라우저에서 한 번으로 묶는다

- 결정일: 2026-10-15, 기록 확정 상태: Accepted
- 근거: [토큰 세션 (BFF)](4-4-EXECUTION.md#4-4-2-토큰-재발급과-종료), [W-003](#w-003), [KNK-1655](https://kimandkang.atlassian.net/browse/KNK-1655), [KNK-1645](https://kimandkang.atlassian.net/browse/KNK-1645)
- **맥락:** access(30분)가 만료된 뒤 화면이 열리면 몰린 요청이 같은 refresh 토큰으로 1초 안에 재발급을 최대 6건 보냈습니다. 첫 회전 뒤의 요청은 재사용으로 판정돼 refresh family가 폐기되고 사용자가 로그아웃됐습니다. BFF의 재발급 중복 방지는 메모리 캐시라 같은 함수 인스턴스 안에서만 동작하고, 버스트가 여러 인스턴스로 흩어지면 묶이지 않았습니다. 백엔드는 직전 refresh를 10초 동안 같은 결과로 받아 주는 유예를 넣었지만, 그보다 늦은 요청과 재사용 탐지 로그의 잡음은 남습니다.
- **결정:** 버스트를 만드는 브라우저에서 재발급을 묶습니다. 만료 시각 쿠키를 JS에 열고, 공용 요청 계층이 요청 직전 만료 2분 전 이내면 전용 BFF 라우트로 재발급을 한 번 보내 나머지 요청이 그 결과를 기다리게 합니다. 서버는 같은 2분 창으로 다시 판정하고, 프록시의 선제 재발급(1분 전)은 게이트를 거치지 않은 요청의 안전망으로 남깁니다.
- **이유:** 인스턴스를 넘는 잠금은 공유 저장소(KV·Redis)와 잠금 만료 처리를 새로 들여야 합니다. 한 화면의 요청은 한 브라우저에서 나오므로 브라우저의 in-flight Promise 하나로 충분합니다. 만료 시각은 자격증명이 아니고 바꿔도 자기 세션의 재발급 시점만 달라집니다. 게이트 창을 프록시보다 넓게 잡아야 프록시가 먼저 재발급하는 경합이 없습니다.
- **주요 영향:** 만료가 임박한 첫 요청은 재발급 왕복만큼 늦게 나갑니다. 기기 시계가 1분 넘게 늦거나, 앞서서 서버가 이르다고 판정하면 게이트가 비켜서고 예전처럼 프록시가 재발급합니다. 탭 사이 동시 재발급과 refresh만 남은 복구 상태는 묶지 않고 백엔드 유예에 맡깁니다. 새 브라우저 요청 경로는 `waitForFreshSession`을 거쳐야 합니다.

- 결정일: 2026-10-19, 기록 확정 상태: Accepted
- 근거: [웹 인앱 로그인 계약](3-2-INTERACTION-FLOWS.md#3-2-3-팝업과-계정-연동), [인앱 게스트 허용과 로그인](4-4-EXECUTION.md#4-4-5-인증-팝업), [KNK-1711](https://kimandkang.atlassian.net/browse/KNK-1711)
- **대체 범위:** [W-005](#w-005)와 [W-010](#w-010) 전체, [W-011](#w-011)의 "핸드오프 이관은 복구용으로 유지", [W-014](#w-014)의 "W-010의 기존 핸드오프 복구는 유지"를 대체합니다. 인앱 게스트 허용과 인앱 로그인 방식은 유지합니다.
- **맥락:** [W-014](#w-014) 뒤로 웹은 핸드오프를 새로 만들지 않았고, 이미 발급된 코드를 위한 외부 랜딩(`/login/continue`), 쿠키 이전 BFF, 인앱 복귀 정리와 로그인 요청의 `handoffCode`만 남아 있었습니다. 서버의 코드 수명은 30분이라 마지막 발급 뒤로 유효한 코드가 남을 수 없고, 서버도 핸드오프 기능을 제거하면서 로그인 요청의 `handoffCode`는 받아도 무시하기로 했습니다.
- **결정:** 웹의 핸드오프 수신과 복구 코드를 모두 제거합니다. 외부 랜딩과 그 화면의 외부 전환 안내, 쿠키 이전 BFF, 인앱 복귀 정리, 기기 안 진행 중 핸드오프 기록, 분석 마스킹의 핸드오프 코드 처리, 로그인 BFF의 `handoffCode` 전달을 지웁니다. 공유 식별자 마스킹은 유지합니다.
- **이유:** 유효한 코드가 없어 복구 경로가 동작할 수 없고, 남겨 두면 서버가 엔드포인트를 지운 뒤 상태 조회가 실패를 반복하거나 생성 API 클라이언트를 다시 만들 때 타입이 깨집니다.
- **주요 영향:** 예전에 발급된 `/login/continue` 링크는 열리지 않습니다. 기기에 남은 진행 중 핸드오프 기록은 읽지 않고 그대로 남습니다. 서버가 `handoffCode`를 무시하므로 웹과 서버의 배포 순서 제약이 없습니다. `client_inappBrowser_escapeAttempted`, `client_inappBrowser_bannerShown`, `client_loginContinue_*` 이벤트는 더 이상 발화하지 않습니다.

## W-042. 로그인한 세션의 재동의는 로그아웃 없이 시트로 받는다

- 결정일: 2026-10-21, 기록 확정 상태: Accepted
- 근거: [공통 재동의](../3-2-INTERACTION-FLOWS.md#3-2-1-로그인과-필수-동의), [웹 로그인과 회원 이관](3-2-INTERACTION-FLOWS.md#3-2-2-로그인과-회원-이관), [동의 게이트](4-3-STATE-MANAGEMENT.md#4-3-3-회원-동의-상태), [KNK-1726](https://kimandkang.atlassian.net/browse/KNK-1726)
- **대체 범위:** [W-011](#w-011)의 "인증 상태인데 필수 동의가 남았으며 표시가 없는 일반 진입은 이전 탭의 미완 로그인으로 보고 로그아웃"과 [W-022](#w-022)의 "로그인한 세션에 동의가 남은 경우의 탭 표시 판정과 fail-closed 로그아웃은 유지"를 대체합니다. 가입 대기의 탭 표시 판정, 공개 법적 문서 경로 예외, `isMember` 단일 판정은 유지합니다.
- **맥락:** 개인정보 처리방침 v1.8로 서버의 요구 버전이 오르자, 며칠 전에 로그인한 회원은 탭 표시가 없어 접속하자마자 로그아웃됐습니다. 다시 로그인하면 동의 대기로 넘어가는데, 로그아웃 뒤에도 남은 이전 세션 쿠키로 미리 보낸 동의 조회가 401을 받아 세션 만료 로그아웃이 두 번 더 일어났습니다. 기존 회원 전원이 로그인을 세 번 해야 했습니다.
- **결정:** 로그인한 세션에 필수 동의가 남으면 탭 표시와 무관하게 회원 동의 시트를 띄우고 회원 동의 API로 기록합니다. 소셜 인증이 동의 대기를 응답하면 남은 이전 세션 쿠키를 지우고, 세션이 게스트로 확정되면 미리 보낸 동의 조회 응답을 버립니다.
- **이유:** [W-022](#w-022) 뒤로는 동의 전에 세션이 생기지 않아, 동의가 남은 세션은 이전 탭의 미완 로그인이 아니라 문서 개정의 대상입니다. 공통 계약도 로그인한 세션의 재동의를 회원 동의 API로 받는다고 정합니다. 시트가 열린 동안 회원 기능은 계속 잠겨 있어 로그아웃하지 않아도 동의 없이 기능이 열리지 않습니다.
- **주요 영향:** 탭 표시는 세션 없는 가입 대기를 조회할지 정하는 데만 씁니다. 동의를 마치지 않고 탭을 닫은 기존 세션은 다음 접속에서 시트가 다시 뜹니다. 시트의 로그아웃과 뒤로가기는 그대로 로그아웃합니다.

## W-043. 재동의가 필요 없는 문서 개정은 서버 요구 버전을 올리지 않는다

- 결정일: 2026-10-22, 기록 확정 상태: Accepted
- 근거: [법적 콘텐츠 소스](4-1-CONTRACT.md#4-1-2-법적-콘텐츠), [공통 재동의](../3-2-INTERACTION-FLOWS.md#3-2-1-로그인과-필수-동의), [KNK-1766](https://kimandkang.atlassian.net/browse/KNK-1766)
- **대체 범위:** [웹 설계](4-1-CONTRACT.md#4-1-2-법적-콘텐츠)의 "문서 버전을 개정할 때는 백엔드 요구 버전을 공개 본문에 맞춘다"를 대체합니다. 재동의가 필요한 개정에서 요구 버전을 올리는 것과 [W-042](#w-042)의 재동의 시트 동작은 유지합니다.
- **맥락:** v1.8까지는 문서를 개정할 때마다 서버 요구 버전을 함께 올려 기존 회원 전원에게 재동의 시트를 띄웠습니다. 처리방침 19항은 공지 후 시행을 약속하는데, 실제로는 공지 없이 재동의로 대신해 왔고 v1.8에서는 이 시트에서 로그인 버그도 생겼습니다. 처리방침은 공개하는 문서이고 서비스 제공에 필요한 처리는 계약 이행을 근거로 합니다.
- **결정:** 공개 본문의 버전과 서버의 동의 요구 버전을 분리합니다. 재동의가 필요하지 않은 개정은 공지 후 시행일부터 적용하고 서버 요구 버전을 올리지 않습니다. 새 선택 동의 항목처럼 법적으로 동의가 필요한 개정만 요구 버전을 올립니다. 첫 적용은 처리방침 v1.9(Amplitude 전송 식별자와 해시 처리 범위 정정)이며, 서버 요구 버전은 v1.8로 둡니다.
- **이유:** 사실과 다른 문구를 바로잡는 개정마다 기존 회원 전원을 재동의 시트로 막는 것은 이용자 부담에 비해 얻는 것이 없습니다. 공지 후 시행은 문서에 이미 적힌 방식입니다.
- **주요 영향:** 동의 시트는 서버가 준 요구 버전을 그대로 기록하므로, 공개 본문이 v1.9여도 새 가입자의 동의 기록은 v1.8로 남습니다. 운영 배포는 관리자 공지 기능으로 개정 공지를 올린 뒤에 합니다. 약관의 간주 동의 조항 도입은 별도 결정입니다.
