# 6-3 AI 얼라인먼트

이 문서는 어떤 결과를 개선 대상으로 삼고, 어떤 변경을 허용하며, 변경을 어떻게 비교해 채택하는지 정한다.

지표의 목표값은 2-2 운영 요구사항에, 채점 방법은 6-4 평가 방법에 있다. ([2-2-2 핵심 지표 요약](2-2-OPERATION-REQUIREMENTS.md#2-2-2-핵심-지표-요약), [6-4-4 채점](6-4-AI-EVALUATION-METHOD.md#6-4-4-채점))

<br>

### 6-3-1 개선 대상

| 대상 | 확인할 문제 | 1차 원인 후보 |
|---|---|---|
| 정답 장애 탐지 | 정답 구간에 이상 후보가 안 열림 | 탐지 기준값이 높거나 확정 조건(5분 중 3분)이 길다 |
| 정답 장애 탐지 | 이상 후보는 열렸는데 `not_incident`나 `undetermined` | 지연 기준이 설명서에 없거나 조회가 비어 있다 |
| 의심 구성 요소 1순위 | 증상이 있는 서비스를 지목하고 원인 구성 요소를 놓침 | 설명서의 description이 부족하거나 분해 단계를 건너뛴다 |
| 첫 이상 시각 | 신호 첫 시각을 그대로 씀 | 증상 단계에서 분 단위 조회를 안 한다 |
| 원인 가설 | 증상을 원인으로 씀 | 프롬프트의 메커니즘 예시가 약하다 |
| 근거 검증 | 조회 결과에 없는 값을 씀 | 결과가 잘려 모델이 어림잡는다 |
| 근거 검증 | 코드 근거의 줄 범위나 인용 문장이 사본과 다름 | 모델이 줄 번호를 어림잡거나 인용을 줄여 쓴다 |
| 오탐 | 부하만 높은 구간을 장애로 판정 | 자원 포화 신호만으로 후보가 열리고 지연 기준 대조를 안 한다 |
| 비용 | 조회가 20회를 넘거나 결과가 큼 | 결과 상위 30개가 너무 크거나 분해 단계가 넓다 |

<br>

### 6-3-2 허용하는 변경

| 수단 | 허용 | 조건 |
|---|---|---|
| 시스템 프롬프트 수정 | 허용 | 변경 전후를 6-4 벤치마크로 비교함 |
| 시스템 설명서 description 보강 | 허용 | 설계 사실만 적고 정답의 원인 문장을 옮겨 적지 않음 |
| 탐지 기준값, 확정 조건, 닫기 조건 변경 | 허용 | 오탐과 탐지 지연을 함께 봄 |
| 도구 결과 형식 변경 | 허용 | 상위 개수, 백분위, 표본 수 |
| 추론 강도 변경 | 허용 | 비용 한도 안에서 |
| 모델 교체 | 허용 | 같은 프롬프트로 6-4를 돌려 품질, 시간, 비용을 함께 비교함 |
| 정답 수정 | 정답 자체가 틀렸을 때만 | 결정 기록에 남김. 점수를 올리려고 정답을 바꾸지 않음 |
| 파인튜닝 | 안 함 | 정답 4건으로 학습 데이터를 만들 수 없음 |
| 정답 구간의 수치를 프롬프트에 넣기 | 안 함 | 벤치마크가 평가 기능을 잃음 |

<br>

### 6-3-3 원인 구분

실패 사례를 볼 때 아래 순서로 원인을 가른다. 앞 원인이 확인되면 뒤를 보지 않는다.

| 순서 | 원인 | 확인 방법 |
|---|---|---|
| 1 | 자료 누락 | `queries/`의 결과가 비어 있거나 재적재 건수가 모자람 |
| 2 | 탐지 규칙 | 이상 후보가 안 열렸거나 늦게 열림 |
| 3 | 설명서 부족 | 모델이 설명서에 없는 설계값을 물었거나 틀린 상한을 가정함 |
| 4 | 조회 선택 | 분해나 확장 단계를 건너뛰고 제출함 |
| 5 | 모델 판단 | 자료를 봤는데 틀린 메커니즘을 씀 |
| 6 | 구현 결함 | 조회 결과가 원천과 다름 |

<br>

### 6-3-4 비교와 채택

| 단계 | 내용 |
|---|---|
| 기준 | 현재 채택된 모델, 프롬프트, 설명서, 기준값 조합의 6-4 결과 |
| 후보 | 변경 하나만 적용한 조합. 변경 둘을 섞어 비교하지 않음 |
| 비교 | 6-4-5대로 3회 실행. 품질 지표 전부가 기준 이상이고 비용이 한도 안이면 채택 |
| 기록 | 채택과 보류를 6-6 성능 리포트에 남김 |
