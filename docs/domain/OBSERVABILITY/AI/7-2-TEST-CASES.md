# 7-2 테스트 케이스

이 문서는 코드의 동작을 확인하기 위한 테스트 범위, 구성 요소별 케이스, 통합 테스트를 정한다.

신호 규칙은 4-1 인지 구조에, 설정 항목과 보고 필드는 5 계약에, 오류 처리는 7-1 오류 처리에 있다. ([4-1-2 이상 후보 추림](4-1-DESIGN-COGNITIVE-ARCHITECTURE.md#4-1-2-이상-후보-추림), [5-2 설정 파일](5-CONTRACT.md#5-2-설정-파일), [5-7 진단 보고](5-CONTRACT.md#5-7-진단-보고), [5-9 슬랙 메시지](5-CONTRACT.md#5-9-슬랙-메시지), [7-1-2 오류별 처리](7-1-ERROR-HANDLING.md#7-1-2-오류별-처리))

<br>

### 7-2-1 테스트 범위

| 종류 | 확인 범위 | 외부 의존성 | 실행 |
|---|---|---|---|
| 단위 | 설정 읽기, 탐지기, 후보 관리자, 자료 접근기의 변환, 보고 검사기, 보고 기록기, 세션 관리자, 슬랙 연결기, 도구 호출 전후 훅, 하위 프로세스 환경 | 조회, 모델 세션, 슬랙 호출을 테스트 대역으로 대체 | 개발자 PC와 CI |
| 조회 통합 | 탐지기의 OpenSearch 집계 질의와 결과 변환 | 테스트용 OpenSearch에 작은 표본 적재 | 개발자 PC |
| 세션 통합 | 진단 요청 하나의 진단부터 대화 턴까지 | 실제 모델 호출, 실제 MCP 서버, 테스트용 OpenSearch, 슬랙 테스트 채널 | 수동. 비용 발생 |
| 운영 연결 | 실행 단계별 운영 자료 조회와 슬랙 연결 | 운영 OpenSearch, CloudWatch, 슬랙 채널 | 수동. 각 단계 시작 뒤 |

실행 명령과 테스트 파일 위치는 저장소 안내 문서에 둔다.

<br>

### 7-2-2 설정

| 확인 항목 | 입력과 상황 | 기대 결과 |
|---|---|---|
| 우선순위 환경 변수 | 설정 파일 `limits.queries` 30과 `DIAG_LIMITS_QUERIES` 40 | 40 적용. `run.json`에 40과 덮어쓴 환경 변수 이름 |
| 우선순위 설정 파일 | 설정 파일만 `limits.queries` 30 | 30 적용 |
| 우선순위 기본값 | 설정 파일에 `limits.queries`가 없고 `DIAG_LIMITS_QUERIES`도 없음 | 25 적용 |
| 덮어쓰기 이름 변환 | `DIAG_DETECTION_MIN_SAMPLES` 15 | `detection.min_samples` 15 |
| 중첩 키 덮어쓰기 | `DIAG_FIELDS_SPAN_DURATION` `duration_us` | `fields.span.duration` `duration_us` |
| 배열 덮어쓰기 | `DIAG_REDACT_FIELDS` | 알 수 없는 환경 변수로 시작 검사 실패 |
| 이름이 틀린 환경 변수 | `DIAG_LIMIT_QUERIES` | 시작 검사 실패. 표준 오류에 `DIAG_LIMIT_QUERIES` |
| 타입 변환 실패 | `DIAG_LIMITS_QUERIES` `many` | 시작 검사 실패. 표준 오류에 이름만 있고 값은 없음 |
| 시간대 이름 | `DIAG_SLACK_TIMEZONE` `Asia/Seol` | 시작 검사 실패 |
| 알 수 없는 키 | 설정 파일에 `detecton.min_samples` | 시작 검사 실패 |
| 필수 항목 누락 | 설정 파일에 `opensearch.log_index` 없음 | 시작 검사 실패. 실행 폴더 없음. 표준 오류에 키 이름 |
| 문제 여럿 | 필수 항목 두 개가 누락됨 | 시작 검사 실패. 표준 오류에 두 키가 한 줄씩 |
| 서비스 지도 저장소 이름 | `paths[]`에 `code_repositories`에 없는 `manyak-web/` 경로 | 시작 검사 실패 |
| 상대 경로 | 설정 파일이 `examples/`에 있고 `session_dir`이 `runs/sessions` | `examples/runs/sessions`에 세션 파일을 씀 |
| Parameter Store 위치 | `DIAG_CONFIG`가 `ssm:`으로 시작함 | 테스트 대역 Parameter Store의 파라미터 값을 설정 파일로 읽음 |
| 비밀값 출처 둘 | `DIAG_SECRET_ID`와 `DIAG_SECRETS_FILE`이 모두 있음 | 시작 검사 실패 |
| 비밀값 출처 없음 | 둘 다 없음 | 시작 검사 실패 |
| 출처와 단계 무관 | 1단계 실행에 `DIAG_SECRET_ID`만 있음 | 테스트 대역 Secrets Manager에서 비밀값을 읽음 |
| 식별자 차단 확인 | 테스트 대역 OpenSearch의 검색 결과에 `message` 필드가 있음 | 시작 검사 실패. 표준 오류에 필드 이름만 있음 |
| 서비스 이름 | `service_name` `예시몰` | 시스템 프롬프트 첫 문장이 `너는 예시몰 서비스의 장애 진단 담당자다.` |
| 시간대 안내 | `slack.timezone` `Asia/Seoul` | 시스템 프롬프트 보고 규칙의 시각 줄에 `Asia/Seoul(UTC+09:00)` |
| 앱 지표 꺼짐 | `prometheus.workspace_url`이 빈 값 | 세션의 `mcp_servers`에 `prometheus`가 없음. 시스템 프롬프트 자료 위치에 앱 지표 줄이 없음 |
| 앱 지표 켜짐 | `prometheus.workspace_url`이 있음 | `prometheus` 서버가 `--url`에 그 값을 받아 등록됨 |
| MCP 실행 파일 없음 | 인터프리터와 같은 bin 폴더에 `awslabs.cloudwatch-mcp-server`가 없음 | 시작 검사 실패. 실행 폴더 없음. 표준 오류에 `awslabs.cloudwatch-mcp-server` |

### 7-2-3 탐지기와 후보 관리자

| 확인 항목 | 입력과 상황 | 기대 결과 |
|---|---|---|
| 신호 확정 | 진입 지연이 5분 중 3분 기준 초과 | 신호 확정. 첫 시각은 처음 넘은 분 |
| 신호 미확정 | 5분 중 2분만 초과 | 확정 안 됨 |
| 표본 부족 | p95는 기준 초과인데 그 분의 스팬이 19건 | 그 분은 조건 미충족 |
| 지연 기준 없음 | 서비스 지도에 없는 진입 스팬 이름 | 진입 지연 신호를 판정하지 않음 |
| 대기 스팬 이름 | `detection.queue_spans`가 `chat.turn.queue` 하나이고 다른 이름의 스팬 p95가 1초 이상 | 그 스팬으로는 대기 지연 신호를 판정하지 않음 |
| 대기 스팬 없음 | `detection.queue_spans`가 빈 배열 | 대기 지연 신호를 판정하지 않음 |
| 기준값 변경 | `detection.confirm_minutes` 2이며 5분 중 2분 초과 | 신호 확정 |
| 후보 열기 | 확정 신호가 있고 열린 후보 없음 | 후보 열림. `candidates.jsonl`에 한 줄 |
| 신호 붙이기 | 열린 후보가 있는데 다른 종류 신호 확정 | 같은 후보의 신호 목록에 추가. 진단 요청 없음 |
| 후보 닫기 | 모든 신호가 10분 동안 조건 미충족 | `closed_at` 채운 줄 추가 |
| 닫은 뒤 재발 | 닫은 다음 분에 다시 확정 | 새 ID로 새 후보 |
| 하루 상한 초과 | 그날 누적 $5.01일 때 새 후보가 열림 | 후보 줄에 `skip_reason` `daily_budget_exceeded`. 진단 호출 0회. 채널 안내 1회 |
| 하루 상한 안내 1회 | 같은 날 두 번째 후보도 생략됨 | 채널 안내 없음 |
| 하루 경계 | UTC 0시가 지난 뒤 새 후보 | 진단을 부름 |
| 탐지 조회 실패 | 첫 호출 연결 오류 후 두 번째 호출 성공 | 그 분의 판정을 함. 표준 출력에 끊김 줄과 재시도 줄 없음 |
| 탐지 조회 재시도 소진 | 14:01 분의 두 번 모두 실패 | 그 분의 판정을 건너뛰고 다음 분에 계속함. 14:01 분을 다시 조회하지 않음 |
| 연속 실패 로그 | 14:00 분을 판정한 뒤 14:01~14:03 분이 모두 재시도까지 실패하고 14:04 분은 성공 | 표준 출력의 감시 조회 줄은 `감시 조회 끊김 14:01`과 `감시 조회 복구 14:04, 건너뛴 분 3개` 두 줄뿐. 분별 실패와 재시도 줄 없음 |
| 밀린 분 건너뜀 | 14:00 분을 판정한 뒤 잠자기로 루프가 멈췄다가 14:31:05에 깨어남 | 14:30 분만 조회해 판정함. 14:01~14:29 분은 조회하지 않음. 표준 출력에 `감시 지연 복구 14:30, 건너뛴 분 29개` |
| 같은 분 한 번 | 14:21 분을 판정한 뒤 14:23 경계 전에 대기가 끝나 판정할 분이 다시 14:21 분이 됨 | 조회와 판정을 하지 않음. 14:21 분의 감시 줄이 한 번만 남음 |
| 건너뛴 분과 닫기 | 열린 후보의 모든 신호가 6분 조용한 뒤 2분을 판정하지 못하고 그 뒤 조용한 분이 이어짐 | 건너뛴 뒤 조용한 9분째까지 열려 있고 10분째에 닫힘 |

### 7-2-4 자료 접근기

| 확인 항목 | 입력과 상황 | 기대 결과 |
|---|---|---|
| 나노초 변환 | `durationInNanos` 48,600,000,000 | p95 48.6초 |

### 7-2-5 진단 실행기와 보고 검사기

| 확인 항목 | 입력과 상황 | 기대 결과 |
|---|---|---|
| 조회 규칙 | 진단 턴에 조립한 시스템 프롬프트 | 보고 규칙 앞에 `## 조회 규칙` 절이 6-1-4 원문 그대로 있음. 집계 질의 우선, `size` 인자 0, 문서 5건 이하와 `_source` 지정, 같은 조회 금지 문장이 들어 있음 |
| 조회 번호 | MCP 조회 2회와 `scaling_history` 1회 | 결과에 `[query 1]`~`[query 3]`이 붙음. `queries/`에 3줄 |
| 저장소 읽기는 조회 아님 | 조회 사이에 `Read` 2회 | 번호가 이어지고 `usage.queries`가 늘지 않음 |
| 근거 검증 통과 | `query_ref` 2이며 `value`가 그 결과에 있음 | `verified` 참 |
| 근거 검증 실패 | `value`가 결과에 없음 | `verified` 거짓. 보고는 기록됨 |
| 없는 조회 번호 | `query_ref` 9이며 조회는 3회 | `verified` 거짓 |
| 출력 간 조건 위반 | `incident`인데 `actions`가 `null` | 위반 회신 1회 |
| 요약 칸 누락 | `incident`인데 `headline.cause`가 `null` | 위반 회신 1회 |
| 글자 상한 초과 | `headline.impact`가 80자인 `incident` 보고 | 위반 회신 없이 보고 기록. 보고 파일의 값은 80자 그대로 |
| 두 번째 위반 | 회신 뒤에도 같은 위반 | 실행 실패 `report` |
| 미제출 | 글만 두 번 | 실행 실패 `budget` |
| 조회 소진 | 25회 뒤 제출 | 보고 기록. `usage.queries` 25 |
| 시간 소진 | 테스트 대역 모델이 6분 걸림 | 실행 실패 `budget` |
| 거절 | 테스트 대역 모델이 `refusal` | 실행 실패 `model` |
| 중복 보고 | 같은 ID의 보고 파일이 이미 있음 | 실행 실패. 기존 파일 유지 |
| 진단 턴 비용 한도 | 테스트 대역 SDK가 비용 한도 도달로 끝남 | 실행 실패 `budget` |
| 사용량 집계 | 결과 메시지의 사용량 | 합계와 비용이 단가표대로. SDK의 비용 추정값은 쓰지 않음 |
| 코드 근거 통과 | `code_ref`의 경로가 코드 사본에 있고 `quote`가 줄 범위 안에 있음 | `verified` 참 |
| 설정 파일 근거 | `code_ref`가 manyak-terraform의 `autoscaling.tf`이고 `quote`가 그 줄에 있음 | `verified` 참 |
| 코드 근거 범위 밖 인용 | `quote`가 파일에는 있지만 줄 범위 밖에 있음 | `verified` 거짓. 보고는 기록됨 |
| 코드 근거 없는 경로 | 코드 사본에 없는 `path` | `verified` 거짓 |
| 코드 근거 줄 수 초과 | `end_line`이 파일 줄 수보다 큼 | `verified` 거짓 |
| 근거 형식 위반 | 근거 하나에 `query_ref`와 `code_ref`가 둘 다 있음 | 실행 실패 `report` |
| MCP 서버 연결 실패 | init 메시지에서 `opensearch` 서버가 `failed` | 모델 호출 없이 실행 실패 `query`. 사유에 `opensearch` |
| 도구 오류 | `SearchIndexTool`이 오류를 돌려줌 | 오류가 도구 결과로 모델에 전달됨. 턴 계속 |

### 7-2-6 도구 범위와 자격

| 확인 항목 | 입력과 상황 | 기대 결과 |
|---|---|---|
| 노출 도구 | 세션 init 메시지의 도구 목록 | `Read`, `Grep`, `Glob`, 6-1-5의 활성화한 도구, `diagnosis` 서버의 두 도구만 있음. `Edit`, `Write`, `Bash`, `Agent`, 웹 도구, `GenericOpenSearchApiTool`, `ListIndexTool`, `MsearchTool`, `get_metric_metadata`, CloudWatch Logs 도구가 없음 |
| 끈 도구 호출 | 테스트 대역 모델이 `mcp__opensearch__ListIndexTool`, `mcp__opensearch__MsearchTool`, `mcp__cloudwatch__get_metric_metadata`를 부름 | 세 호출 모두 실행되지 않고 거부나 오류가 도구 결과로 돌아감. 턴은 계속됨. 조회 번호가 붙지 않고 `queries/`에 줄이 늘지 않음 |
| 사본 안 읽기 | 코드 사본 안 파일을 `Read` | 실행됨 |
| 사본 밖 읽기 | `Read`로 `~/.aws/credentials`와 비밀 파일 경로 | 거부 결과가 돌아가고 턴은 계속됨 |
| 심볼릭 링크 우회 | 코드 사본 안에 사본 밖을 가리키는 링크를 두고 그 링크를 `Read` | 실제 경로가 사본 밖이라 거부 |
| `Grep`과 `Glob` 범위 | `path`를 `/`로 준 `Grep`과 `Glob` | 거부 |
| OpenSearch 연결 인자 | `SearchIndexTool` 입력에 `opensearch_url`을 넣은 호출 | 거부. 다른 주소로 질의하지 않음 |
| 대화 턴의 제출 | 대화 턴에서 `submit_report` 호출 | 거부 |
| MCP 서버 자격 비노출 | OpenSearch 비밀번호와 AWS 자격을 MCP 서버 환경에만 넘긴 세션에서 모델이 `Read`, `Grep`, `Glob`으로 프로세스 환경 파일(`/proc/self/environ`, MCP 서버 프로세스의 `/proc/<pid>/environ`)을 읽고 코드 사본 폴더를 비밀번호 문자열로 검색함 | 환경 파일 읽기는 거부됨. 사본 검색 결과에 비밀번호가 없음. 세션의 어느 도구 결과에도 비밀번호와 AWS 자격 값이 없음 |
| 하위 프로세스 환경 | SDK가 띄운 프로세스의 환경 | 모델 API 키와 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`이 있음. OpenSearch 비밀번호, 슬랙 토큰, 저장소 토큰이 없음 |
| 설정 격리 | 코드 사본의 manyak-server 저장소에 CLAUDE.md가 있음 | 세션 맥락에 그 내용이 들어가지 않음 |

### 7-2-7 세션 관리자와 슬랙 연결기

| 확인 항목 | 입력과 상황 | 기대 결과 |
|---|---|---|
| 이상 후보 보고 게시 | 이상 후보의 보고 | 채널에 새 메시지. `sessions.jsonl`에 그 메시지의 타임스탬프와 세션 ID |
| 운영자 요청 | 채널 최상위 메시지에서 봇을 멘션 | `mentions.jsonl`에 한 줄. 진단 후 그 메시지의 스레드에 보고가 답글로 올라감 |
| 스레드 안 멘션 | 세션이 없는 스레드의 답글에서 봇을 멘션 | 운영자 요청. 보고는 그 스레드의 첫 메시지 기준 스레드에 올라감 |
| 세션 스레드의 멘션 | 열린 세션의 스레드에서 봇을 멘션 | 새 진단 없이 대화 턴 |
| 멘션 없는 메시지 | 세션 스레드 밖에서 멘션 없이 쓴 메시지 | 무시 |
| 진단 중 멘션 | 이상 후보 진단 중에 운영자 요청이 옴 | 앞 진단이 끝난 뒤 운영자 요청 진단을 실행함. 두 진단 턴은 동시에 실행하지 않음 |
| 운영자 요청과 하루 상한 | 그날 누적이 상한 이상일 때 멘션 | 진단 호출 0회. 그 스레드에 생략 안내. `mentions.jsonl`에 `skip_reason` |
| 요청 받음 반응 | 채널 최상위 메시지에서 봇을 멘션 | `mentions.jsonl`에 한 줄 쓴 뒤 그 멘션 메시지에 `eyes` |
| 보고 뒤 반응 | 운영자 요청의 보고를 스레드에 올림 | 멘션 메시지의 `eyes`가 지워지고 `white_check_mark`가 달림 |
| 실패 뒤 반응 | 운영자 요청의 진단이 실행 실패로 끝남 | 스레드에 실패 안내. 멘션 메시지의 `eyes`가 지워지고 `x`가 달림 |
| 실패 안내 형식 | 진단이 실행 실패 `budget`으로 끝남 | `❌ 실행 실패 · budget · <reason>` 한 줄. `<reason>`은 `failures.jsonl`의 그 줄 `reason` |
| 생략 뒤 반응 | 그날 누적이 상한 이상일 때 멘션 | 스레드에 생략 안내. 멘션 메시지의 `eyes`가 지워지고 `x`가 달림 |
| 반응 실패 | 운영자 요청 진단 중 반응 API가 매번 오류를 돌려줌 | 진단이 끝나고 보고가 스레드에 올라감. 표준 출력에 사유. `failures.jsonl`에 줄 없음 |
| 반응 없는 메시지 | 이상 후보의 보고 게시와 열린 세션 스레드의 대화 턴 | 반응 API 호출 0회 |
| 세션 찾기 | 같은 `thread_ts`의 사람 메시지 | 그 세션 ID로 대화 턴 시작 |
| 봇 메시지 무시 | 봇 사용자 ID의 스레드 메시지 | 대화 턴 없음 |
| 이상 후보 세션 수명 | 후보를 닫은 지 24시간 1분 | `closed_at` 기록. 이후 메시지에 종료 안내 1회 |
| 운영자 요청 세션 수명 | 보고를 올린 지 24시간 1분 | `closed_at` 기록. 이후 메시지에 종료 안내 1회 |
| 보고 요약 | 근거 7개 중 하나가 검증 실패이고 조치 5개인 보고의 대화 턴 시작 | 사용자 메시지 앞 요약에 의심 구성 요소, 배제한 원인, 근거 7줄, 조치 5줄이 있음. 검증 실패 근거는 `- ⚠ 검증 실패`로 시작함 |
| 조치 지시 | 대화 턴에서 "동시 실행 수를 8로 올려 줘" | 답변이 스레드에 올라감. 코드 사본에 변경 없음. 쓰기 도구 호출 없음 |
| 비용 초과 | 누적 $1.95에서 $0.10이 드는 턴 | 턴 뒤 종료 안내. `closed_at`과 누적 비용 기록 |
| 다시 시작 | 열린 세션이 있던 프로세스를 다시 띄운 뒤 그 스레드에 메시지 | 대화 턴 없음. 멘션이 있으면 새 운영자 요청 |
| 게시 실패 | 슬랙 전송이 두 번 실패 | 실행 실패 `notify`. 보고 파일은 있음 |
| 보고 메시지 형식 | 5-7 예시 보고와 `slack.timezone` `Asia/Seoul` | 5-9 장애 예시와 같은 `text`와 블록. 블록은 `header`, 칸, 원인 가설, 주요 근거, 할 일, `context` 순서. 칸은 영향, 원인, 첫 이상, 배제한 원인 순서. 주요 근거는 보고의 앞 근거 3개. 할 일 줄은 두 조치 목록의 첫 항목만. `impact.summary`, 넷째부터의 근거, `diagnosis_id`가 없음 |
| 첫 원인 가설만 | 의심 구성 요소가 둘인 `incident` 보고 | 원인 가설 블록에 첫 의심 구성 요소의 가설만 있음 |
| 장애 아님 형식 | 근거 5개가 모두 검증되고 `ruled_out`이 빈 배열이며 `actions`가 `null`인 `not_incident` 보고 | `header`가 `🟢 이상 없음`. 칸은 확인한 범위와 주요 수치 둘. 원인 가설 블록과 조치 블록이 없음. 주요 근거 블록에 앞 근거 3개만 보고 순서대로 있고 넷째와 다섯째 관찰이 없음. `context`가 `근거 5개 중 5개 검증`으로 시작함 |
| 장애 아님 배제한 원인 | `ruled_out`이 `["큐 대기", "CPU"]`인 `not_incident` 보고 | 셋째 칸이 `*배제한 원인:* 큐 대기, CPU` |
| 판단 불가 형식 | 의심 구성 요소, 근거, 배제한 원인이 없는 `undetermined` 보고 | `header`가 `🟡 판단 불가`. 칸은 확인한 범위와 주요 수치 둘. 원인 가설, 주요 근거, 조치 블록이 없음. `context`가 `조회`로 시작함 |
| 판단 불가 원인 칸 | 의심 구성 요소가 있는 `undetermined` 보고 | `header` 끝에 그 구성 요소가 붙고 셋째 칸이 원인. 원인 가설 블록이 그 구성 요소의 가설 |
| 배제한 원인 없음 | `ruled_out`이 빈 배열인 `incident` 보고 | 칸은 영향, 원인, 첫 이상 셋 |
| 검증 실패 표시 | 근거 셋 가운데 둘째의 `verified`가 거짓 | `context`가 `⚠ 근거 3개 중 1개 검증 실패`로 시작함. 주요 근거 블록의 둘째 줄만 `• ⚠ `로 시작함 |
| 코드 근거 위치 | 첫 근거의 `code_ref`가 `path` `src/main/resources/application.yml`, `start_line` 111, `end_line` 112 | 주요 근거 첫 줄이 `` • <observation> (`application.yml:111`) ``. 저장소 이름, 경로 앞부분, `end_line`이 없음 |
| 칸 말줄임 | `headline.impact`가 45자 | 영향 칸 값이 앞 39자 뒤에 `…`. 보고 파일의 값은 그대로 |
| 원인 가설 말줄임 | `suspects[0].hypothesis`가 130자 | 원인 가설 값이 앞 119자 뒤에 `…`. 보고 파일의 값은 그대로 |
| 근거 말줄임 | 관찰이 90자이고 `verified`가 거짓이며 `code_ref`가 있는 근거 | 그 줄이 `• ⚠ `와 관찰 앞 79자, `…`, 파일 위치 순서. `⚠ `와 파일 위치는 줄지 않음. 보고 파일의 값은 그대로 |
| 비용 줄 | 근거 5개가 모두 검증되고 `usage.queries` 7, `usage.elapsed_seconds` 94.6, `usage.cost_usd` 0.104 | `context`가 `근거 5개 중 5개 검증 · 조회 7회 · 95초 · $0.10` |
| 대화 답변 비용 줄 | 세션 누적 $0.18에서 $0.01이 드는 대화 턴 | 답변 끝 줄이 `이번 답변 $0.01 · 세션 누적 $0.19`. `sessions.jsonl`의 `cost_usd`가 0.19 |
| 시간대 변환 | `slack.timezone`이 `Asia/Seoul`이고 `first_anomaly_at`이 `2026-10-26T09:16:00Z` | 첫 이상 칸 값이 `18:16`. 보고 파일의 `first_anomaly_at`은 그대로 |
| 생략 안내 시각 | `slack.timezone` `Asia/Seoul`에서 하루 상한 때문에 진단을 생략함 | 안내 줄 끝이 `09:00에 다시 시작` |

### 7-2-8 통합 테스트

| 확인 항목 | 입력과 상황 | 기대 결과 |
|---|---|---|
| 조회 통합 | 표본 스팬 200건 적재 후 진입 스팬 이름별 집계 | 건수와 p95가 표본에서 직접 계산한 값과 같음 |
| 필드 대응표 적용 | 같은 표본 스팬과 로그를 필드 이름만 바꿔 다른 인덱스에 적재하고 `fields.span`, `fields.log`, 인덱스 패턴을 그 이름으로 둠 | 진입 스팬 이름별 건수, p95, 서비스별 로그 건수가 기본 이름 인덱스의 결과와 같음 |
| FLS 적용 | 테스트용 OpenSearch에 `redact_fields`를 FLS로 뺀 역할과 사용자를 만들고 그 사용자로 `SearchIndexTool`을 부름 | 결과 문서에 `message`, `device_id_hash`, `session_id`, `request_id`, `span.attributes.http@url`이 없음 |
| 세션 통합 | 슬랙 테스트 채널에서 봇을 멘션해 표본 구간의 채팅 턴 지연을 물은 뒤 스레드에 질문 1건 | 그 스레드에 보고가 올라감. 멘션 메시지의 반응이 `eyes`에서 `white_check_mark`로 바뀜. 질문에 답변 게시. 보고의 조회 근거가 모두 `verified` 참 |
| 1단계 운영 연결 | 운영자 PC에서 상주 실행을 시작한 직후 | 시작 검사 통과. 표준 출력에 감시가 1분마다 남음. 직전 1시간 진입 스팬 건수가 운영 OpenSearch에서 직접 센 값과 같음 |
| 2단계 운영 연결 | 운영 태스크 배포 직후 | 1단계 운영 연결과 같음. 표준 출력이 CloudWatch Logs에 남음 |

통합 테스트의 표본은 부하 테스트 보관 자료에서 가져오고 가져온 구간을 기록한다.
