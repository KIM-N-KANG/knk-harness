# DECISIONS.md

NOTICE 도메인 백엔드의 중요한 결정을 날짜, 상태, 배경, 채택, 대안과 영향으로 정리한다. 현재 적용 기준은 각 명세에 둔다. 여기에는 결정 당시의 이유와 변경 이력을 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다.
- 상태는 결정 당시 기준이다. 결정이 바뀌면 이전 기록을 지우지 않고 후속 결정에 대체 범위와 근거를 적는다.

<br>

### 2. 공지와 알림

**1. 공지는 초안과 게시의 두 상태만 두고 게시 시 알림을 공지당 한 번 요청한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-21 |
| 상태 | 채택. 게시와 같은 트랜잭션의 알림 요청과 공지당 한 번은 결정 5가 대체 |
| 배경 | 점검과 정책 변경 같은 소식을 사용자에게 전할 수단이 서비스 안에 없었다. 프로모션 푸시는 있었지만 알림을 놓친 사용자가 다시 읽을 곳이 없었고 광고성이 아닌 소식도 광고 동의자에게만 갈 수 있었다. |
| 채택 | 공지를 초안과 게시의 두 상태로 두고 공개 조회는 게시만 읽는다. 게시할 때 관리자가 정보성 또는 광고성 알림을 고르면 게시와 같은 트랜잭션에서 알림 도메인에 캠페인 1건을 요청한다. 알림 요청은 공지당 한 번이며 게시 해제 뒤 재게시해도 다시 보내지 않는다. 알림을 요청한 공지는 삭제할 수 없다. 알림 본문은 공지 본문의 앞 300자다. |
| 대안 | 예약 게시와 보관 상태를 더하는 안은 상태 전이와 화면이 늘어나며 당장 필요하지 않다. 알림을 게시와 별도 API로 보내는 안은 게시 없는 알림이 생길 수 있다. 공지 자체가 발송 회차를 돌리는 안은 알림 도메인의 캠페인 선점과 대상 판정을 중복 구현하게 된다. |
| 영향 | 알림 도메인에 캠페인 종류와 공지 참조가 생겼고 정보성 공지 시나리오가 추가됐다. 클라이언트에 공지 목록과 상세 화면이 필요하며 그 세트는 별도 작업이다. 공지 알림 딥링크의 화면이 없으면 알림 없이 게시만 한다. |

<br>

**2. 공지를 게시하면 항상 알림을 보낸다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-24 |
| 상태 | 채택. 결정 1의 "알림을 고르면 요청"과 "화면이 없으면 알림 없이 게시"를 대체. 결정 5가 전부 대체 |
| 배경 | 회원 알림함이 공지를 소식으로 보여 주게 됐다(NOTIFICATION 결정 19). 알림 없이 게시한 공지는 알림함에 없어 회원이 놓치고 관리자는 게시마다 알림 여부를 따로 골라야 했다. |
| 채택 | 게시하면 게시와 같은 트랜잭션에서 공지 알림을 항상 요청한다. 게시 요청의 `notify`는 받지 않고 보내도 무시한다. 알림 요청은 지금처럼 공지당 한 번이고 알림 요청 시각으로 판정한다. 수정과 재게시는 알림을 다시 보내지 않는다. 알림 유형은 결정 3의 태그가 정한다. |
| 대안 | `notify`가 `false`인 요청을 400으로 거절하는 안은 관리자 웹을 먼저 배포해야 하고 순서가 바뀌면 게시가 막힌다. 처음 게시일 때만 알림을 보내도록 게시 시각으로 판정하는 안은 알림 요청 시각 판정을 바꿔야 해 서버 변경이 커진다. |
| 영향 | 알림 없이 게시하던 때의 공지는 알림 요청 시각이 비어 있어 게시 해제 뒤 다시 게시하면 그때 처음 알림이 간다. 한 번 게시한 공지는 알림을 요청했으므로 삭제할 수 없다. 관리자가 선점 전에 공지 알림 캠페인을 취소하면 그 공지의 푸시와 알림 내역은 없고 다시 게시해도 새로 만들지 않는다. 관리자 웹은 공지 상세의 알림 체크박스를 지운다. |

<br>

**3. 공지마다 태그를 필수로 두고 태그가 정보성과 광고성을 정한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-24 |
| 상태 | 채택. 결정 1의 "게시할 때 관리자가 정보성 또는 광고성 알림을 고른다"를 대체. 태그로 정한 종류의 알림을 게시가 요청하는 부분은 결정 5가 캠페인 연결로 대체 |
| 배경 | 공지 목록에서 점검 안내와 이벤트가 구분되지 않았다. 다른 서비스처럼 공지에 태그를 달아 보여 주기로 했다(사용자와 강동우 합의). 게시마다 고르던 알림 유형은 태그와 겹친다. |
| 채택 | 공지마다 `SERVICE`(공지사항), `UPDATE`(업데이트), `MAINTENANCE`(점검), `EVENT`(이벤트), `PROMOTION`(홍보) 중 하나의 태그를 필수로 둔다. 작성에서 필수이고 수정에서는 생략하면 유지한다. 공개 목록과 상세, 관리자 공지 구조에 태그를 싣고 공개 목록은 태그로 거를 수 있다. `SERVICE`, `UPDATE`, `MAINTENANCE`는 정보성이라 서비스 종류로, `EVENT`와 `PROMOTION`은 영리 목적의 광고성 정보라 광고 종류로 알림을 요청한다. 광고 종류는 정보통신망법 제50조에 따라 광고 동의자에게만 가고 야간에는 야간 동의자에게만 가며 푸시와 알림 내역 제목 앞에 서버가 `(광고)`를 붙인다. 이미 붙어 있으면 다시 붙이지 않고 공지 원문 제목에는 붙이지 않는다. 게시 요청의 `notificationKind`는 받지 않는다. 기존 공지는 마이그레이션에서 `SERVICE`로 채운다. |
| 대안 | 태그와 알림 유형을 따로 고르는 안은 이벤트 공지를 정보성으로 보내는 실수를 막지 못한다. 수정에서도 태그를 필수로 받는 안은 부분 수정 관례와 어긋난다. 태그 인덱스는 공지 수가 적어 두지 않았다. |
| 영향 | 공지 테이블에 태그 컬럼이 생기고 공지 발송 요청에 태그가 더해진다. 알림 도메인은 캠페인에 태그를 남겨 푸시 데이터와 알림 내역에 싣는다. 게시 뒤 태그를 바꿔도 이미 요청한 알림의 유형은 그대로다. 태그 `SERVICE`와 알림 유형 `SERVICE`, 태그 `PROMOTION`과 알림 시나리오 `PROMOTION`은 이름이 같지만 다른 값이다. 관리자 웹 공지 화면에 태그 선택과 표시가 필요하다. |
| 보완(2026-10-29) | 광고 표기는 푸시 제목 앞에만 붙고 알림 내역에는 원문 제목을 저장한다. 채택의 "푸시와 알림 내역 제목 앞에 서버가 `(광고)`"는 푸시 제목에만 해당한다. 서버도 알림 내역에 원문을 저장한다(`push/inbox/ScheduledNotificationWriter.kt`). ([NOTIFICATION 4-1-1 공통 처리](../../NOTIFICATION/BACKEND/4-1-PIPELINES.md#4-1-1-공통-처리)) |

<br>

**4. 공지 알림의 제목과 본문은 관리자가 공지와 따로 입력한다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-24 |
| 상태 | 채택. 결정 1의 "알림 본문은 공지 본문의 앞 300자"를 대체. 공지의 알림 문구는 결정 5가 캠페인의 제목과 본문으로 대체 |
| 배경 | 공지를 게시하면 공지 제목과 본문 앞 300자가 그대로 푸시와 알림 내역의 문구로 나갔다. "~~ 안내" 같은 공지 제목은 알림 문구로 어색하다는 판단에 사용자와 강동우가 알림 문구를 따로 쓰기로 했다(10/24). |
| 채택 | 공지에 알림 제목(1~100자)과 알림 본문(1~300자)을 두고 작성에서 필수로 받는다. 수정에서는 선택이며 알림을 요청하기 전에만 바꿀 수 있다. 공지 알림의 캠페인 제목과 본문은 알림 문구를 그대로 쓰고 공지 원문은 쓰지 않는다. 자동 생성은 하지 않는다. 게시 시 항상 알림, 태그별 대상, 광고 표기 자동 접두는 그대로다. 기존 공지의 알림 문구는 NULL로 두고 알림을 요청하지 않은 공지를 게시하려면 먼저 입력해야 한다. |
| 대안 | 알림 요청 뒤에도 알림 문구 수정을 허용하는 안은 공지에 남은 알림 문구와 실제로 나간 캠페인 문구가 달라져 관리자 상세가 사실과 어긋난다. 기존 공지를 공지 제목과 본문 앞 300자로 채우는 안은 이미 알림을 요청한 공지에는 쓰이지 않고 남은 초안에는 피하려던 문구를 그대로 넣는다. 게시 요청 본문에서 알림 문구를 받는 안은 작성 화면에서 미리 쓰고 고치는 흐름과 맞지 않는다. |
| 영향 | 공지 테이블에 열 두 개가 생기고 관리자 공지 구조, 작성, 수정, 게시 계약이 바뀐다. 길이 상한은 관리자 캠페인 예약과 같아 광고 표기를 붙인 제목도 알림 내역 제목 열(120자) 안에 든다. 서버를 먼저 배포하는 동안 이전 관리자 웹의 작성은 400이다. |

<br>

**5. 게시는 공지만 공개하고 공지 알림은 관리자 캠페인이 게시된 공지를 연결해 보낸다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-30 |
| 상태 | 채택. 결정 1의 게시와 같은 트랜잭션의 알림 요청과 공지당 한 번, 결정 2 전부, 결정 3의 게시가 알림을 요청하는 부분, 결정 4의 공지 알림 문구를 대체 |
| 배경 | 게시하면 알림이 바로 한 번 나가서 알림 시각을 고를 수 없었고 같은 공지를 다시 알릴 수도 없었다. 알림 문구를 공지 화면에서 쓰고 프로모션 문구는 캠페인 화면에서 써서 알림을 만드는 곳이 둘이었다. 관리자 캠페인은 종류가 광고로 고정되어 정보성 알림은 공지 게시로만 보낼 수 있었다. 사용자가 10/30에 게시와 알림을 나누기로 정했다. |
| 채택 | 공지는 게시만 하고 게시는 캠페인을 만들지 않는다. 공지의 알림 제목과 본문 입력을 없앤다. 작성과 수정 요청의 `notificationTitle`, `notificationBody`는 보내도 무시하고 게시 응답의 `notified`를 없앤다. 관리자 캠페인 예약의 이동 대상에 게시된 공지를 더하고 예약 발송은 캠페인 기능을 그대로 쓴다. 캠페인 종류는 관리자가 고르지 않고 연결한 공지의 태그로 정한다. 공지사항, 업데이트, 점검 공지는 서비스 종류이고 이벤트, 홍보 공지와 연결 대상이 없거나 스토리인 캠페인은 광고 종류다. 공지 하나에 캠페인을 여러 개 연결할 수 있게 캠페인의 공지 참조 유니크를 지운다. 연결은 NOTICE의 알림 연결 연산이 캠페인 생성 트랜잭션에서 공지 행을 잠그고 게시 상태를 확인한다. 처음 연결할 때 공지의 알림 요청 시각을 기록한다. 이미 알림이 나간 공지의 캠페인 연결과 알림 요청 시각은 그대로 둔다. 알림 문구 열은 읽기와 쓰기를 멈춘 서버가 운영에 나간 다음 릴리스에서 지운다. |
| 대안 | 게시 화면에서 알림 여부와 예약 시각을 고르는 안은 예약, 취소, 재실행을 공지 도메인이 다시 만들어야 한다. 캠페인에서 관리자가 종류를 고르고 공지를 연결하는 안은 이벤트 공지를 서비스 알림으로 보내 광고 수신에 동의하지 않은 회원에게 광고가 가는 실수(정보통신망법 제50조)를 막지 못한다. 공지당 캠페인 한 건을 유지하는 안은 같은 공지를 다시 알릴 수 없다. 공지 삭제 때 연결된 캠페인이 있는지 조회하는 안은 NOTICE가 캠페인 테이블을 읽어야 하고 관리자 화면의 알림 요청 표시도 따로 계산해야 한다. 첫 연결에 알림 요청 시각을 기록하면 삭제 판정과 관리자 목록의 알림 요청 여부가 그대로 맞는다. 알림 문구 필드를 400으로 거절하는 안은 결정 2의 `notify`와 같은 이유로 채택하지 않았다. 관리자 웹을 먼저 배포해야 하고 순서가 바뀌면 공지 작성이 막힌다. 알림 문구 열을 이번 릴리스에서 바로 지우는 안은 롤링 교체 중 이전 태스크가 열을 읽고 써서 실패한다. |
| 영향 | 공지 알림의 알림 내역 유형, 푸시 데이터, 딥링크, UTM은 게시가 만들던 캠페인과 같은 규칙이라 웹과 앱 변경이 없다. 정보성은 `NOTICE`, 광고성은 `PROMOTION`에 `noticeId`, `noticeTag`, `/notices/{noticeId}` 딥링크가 실리고 `utm_campaign`은 캠페인 공개 식별자다. 같은 공지를 연결한 캠페인마다 회원의 알림 내역이 한 행씩 생긴다. 결정 3의 태그별 알림 성격과 2026-10-29 보완의 광고 표기 규칙은 캠페인 연결에 그대로 적용된다. 광고 표기는 푸시 제목 앞에만 붙고 알림 내역에는 원문 제목이 남는다. 결정 4의 알림 제목과 본문 자리는 캠페인의 제목과 본문이 맡고 길이 상한(100자, 300자)도 같다. 알림 요청 시각의 의미는 공지를 연결한 첫 캠페인을 만든 시각이 되고 게시가 알림을 요청하던 공지는 그 게시 시각이 남는다. 공지를 고쳐도 이미 만든 캠페인의 종류와 태그는 바뀌지 않는다. 서버를 먼저 배포한다. 관리자 웹이 먼저면 이전 서버가 알림 문구 누락으로 공지 작성을 거절하고 캠페인의 `noticeId`를 무시해 공지 없는 광고 캠페인을 만든다. 서버만 배포된 동안 이전 관리자 웹의 게시 확인 문구는 알림이 간다고 안내하지만 알림은 가지 않는다. NOTIFICATION 결정 21과 ADMIN 웹 결정 37이 같은 변경의 알림과 관리자 화면 쪽이다. |
