# 6. 배포

이 문서는 NOTICE 도메인이 포함된 서버의 배포 단위와 의존 대상, 배포 경로, 이 도메인이 읽는 환경 변수, 배포 조건, 설정 변경, 적용과 복구 절차를 정한다.

서버 전체 배포 절차 중 NOTICE 도메인과 관련된 항목만 다룬다.

알림 발송의 시간 한도와 딥링크 설정은 알림 도메인에 있으며 관측 스택과 조회 도구는 관측에 있다. ([NOTIFICATION 5-3-5 재시도와 시간 한도](../../NOTIFICATION/BACKEND/5-3-ERROR-HANDLING.md#5-3-5-재시도와-시간-한도), [NOTIFICATION 6-3 환경 변수와 시크릿](../../NOTIFICATION/BACKEND/6-DEPLOYMENT.md#6-3-환경-변수와-시크릿), [5-4-1 관측 스택](5-4-OBSERVABILITY.md#5-4-1-관측-스택))

<br>

### 6-1 배포 단위와 의존성

배포 단위는 서버 컨테이너 하나다. NOTICE만 따로 배포하지 않는다. 이 도메인이 기동과 요청 처리에 쓰는 의존 대상은 다음과 같다.

| 의존 대상 | 내용 | NOTICE 도메인이 쓰는 것 |
|---|---|---|
| PostgreSQL | 기동 시 마이그레이션 적용 | 공지 테이블 |
| Data Prepper | 트레이스를 받아 OpenSearch에 적재 | 트레이스 전송 |

<br>

| 의존 대상 | 연결과 설정 실패 시 동작 |
|---|---|
| PostgreSQL | 연결할 수 없으면 기동 실패 |
| Data Prepper | 추적을 켜고 주소가 비면 기동 실패<br>추적이 꺼지면 스팬을 만들되 전송하지 않음 |

<br>

### 6-2 배포 경로

테스트와 빌드를 마친 뒤 이미지를 게시하고 배포한다. `main` push는 같은 소스 트리의 `dev` 성공 실행이 있으면 테스트를 다시 실행하지 않는다. `dev`로 PR을 올리면 테스트와 빌드만 한다.

| 단계 | 개발 | 운영 |
|---|---|---|
| 자동 시작 | `dev` push | `main` push |
| 머지 규칙 | 기능 브랜치에서 `dev`로 squash | `release/vX.Y.Z`에서 `main`으로 merge commit |
| 이미지 태그 | 커밋 SHA 앞 7자리<br>환경 태그 `dev` | 커밋 SHA 앞 7자리<br>배포 시 `latest` 태그 지정<br>실패하면 이전 digest로 복원 |
| 상태 검사 | 배포 완료, 서버 컨테이너 정상, health `UP` | 동일 |

<br>

### 6-3 환경 변수와 시크릿

NOTICE 전용 환경 변수는 없다. 공지 알림 딥링크의 앞부분은 알림 도메인의 설정이다. 관측 관련 환경 변수는 서버 공통이며 다른 세트의 표와 같다.

<br>

### 6-4 배포 조건

| 확인 항목 | 기준 | 자동 여부와 한계 |
|---|---|---|
| 알림 시나리오 | 공지 시나리오를 알림 서비스가 먼저 받도록 알림 서비스 배포가 선행 | 수동 검토 |
| 공지 화면 | 딥링크 경로의 웹 화면이 있어야 알림을 눌렀을 때 공지가 열림 | 수동 검토<br>화면이 없으면 캠페인에 공지를 연결하지 않음 |
| 태그 응답 | 공개 목록과 상세의 `tag`는 추가 필드라 클라이언트를 함께 배포하지 않아도 됨 | 수동 검토 |
| 게시와 알림 분리 | 유니크 제거 마이그레이션과 서버를 먼저 배포한 뒤 관리자 웹이 공지의 알림 문구 칸을 지우고 캠페인 작성에 공지 연결을 더함<br>서버만 배포된 동안 이전 관리자 웹이 보내는 알림 문구는 무시되고 게시해도 알림이 가지 않음<br>관리자 웹이 먼저면 이전 서버가 알림 문구 누락으로 공지 작성을 거절하고 캠페인의 `noticeId`를 무시해 공지 없는 광고 캠페인을 만듦<br>웹과 앱은 푸시 데이터와 알림 내역이 같아 함께 배포하지 않음 | 수동 검토 |
| 알림 문구 열 제거 | 알림 문구 열을 읽고 쓰지 않는 서버가 운영에 나간 다음 릴리스에서 제거 | 수동 검토 |
| 와이어 계약 변경 | 공개 조회 응답이 바뀌면 클라이언트와 함께 배포 | 수동 검토 |
| 마이그레이션 | 기동 시 실행하므로 새 마이그레이션은 해당 코드보다 먼저 적용<br>재실행해도 같은 결과 | 기동 시 자동 적용<br>마이그레이션 경로 변경 PR은 `tbls lint`와 `dbdoc/` 비교를 CI에서 자동 실행 |
| 코드 테스트 | 전체 테스트 통과 | CI 자동 |
| 컨테이너 기동 | 컨테이너 헬스체크와 `/actuator/health` `UP` | CI 자동 |

<br>

### 6-6 적용과 복구

**1. 적용 순서**

| 순서 | 작업 | 확인 항목 |
|---|---|---|
| 1 | 설정 확인 | 마이그레이션 순서 |
| 2 | 동반 배포 확인 | 알림 서비스 먼저<br>관리자 웹은 서버 다음<br>클라이언트 공지 화면 |
| 3 | 배포 실행 | |
| 4 | 적용 결과 확인 | 배포 후 확인 항목 |

<br>

**2. 진행 중인 요청**

| 상황 | 처리와 한계 |
|---|---|
| 롤링 교체 중 게시 | 이전 태스크가 받은 게시는 이전 동작대로 알림 캠페인을 만들고 알림 요청 시각을 기록함<br>새 태스크가 받은 게시는 캠페인을 만들지 않음 |
| 개발 stop-then-start | 교체 중 모든 요청 실패<br>데이터 컨테이너 재시작 |

<br>

**3. 복구**

자동 복구가 실행돼도 서비스가 정상으로 돌아오지 않았을 수 있으므로 실제 서버 상태를 확인한다.

| 상황 | 복구 방식 | 한계와 확인 사항 |
|---|---|---|
| 새 태스크 헬스체크 실패 | 직전 배포로 자동 복귀 | 환경 태그가 실패한 이미지를 가리킬 수 있으므로 다음 재배포 전에 태그 확인 |
| 배포는 정상이나 동작 오류 | revert 커밋 릴리스 또는 이전 이미지를 환경 태그로 다시 태깅한 뒤 새 배포 | health 기반 자동 복구는 공지 오류를 탐지하지 않음 |
| 잘못 게시한 공지 | 관리자 API로 수정 또는 게시 해제 | 이미 발송된 알림은 회수 불가<br>선점 전 캠페인은 알림 도메인의 취소 |
| 마이그레이션 적용 후 되돌리기 | 적용된 마이그레이션은 되돌리지 않음 | 새 테이블은 구버전 코드와 호환<br>유니크를 지운 뒤에도 구버전의 게시는 공지 행의 알림 요청 시각으로 공지당 한 번만 캠페인을 만듦 |

<br>

### 6-7 배포 후 확인

| 확인 항목 | 자료 | 기준 |
|---|---|---|
| 기동 | 해당 배포 ID의 태스크 상태, 헬스체크 `/actuator/health`, 스모크 테스트 | 의도한 이미지로 기동<br>`UP` |
| 공개 조회 | 공개 목록 응답 | 게시된 공지만 보임 |
| 게시 | 로그 `notice_published`<br>알림 도메인의 캠페인 행 | 새 태스크의 게시는 캠페인을 만들지 않음 |
| 공지 알림 | 공지를 연결한 캠페인 예약 응답과 캠페인 행 | 캠페인의 `noticeId`와 태그가 정한 `kind` |

<br>

### 6-8 배포 실패 진단

| 실패 상황 | 확인할 자료와 위치 | 원인별 조치 |
|---|---|---|
| 게시가 전부 서버 오류 | Sentry<br>공지 테이블 존재 여부 | 마이그레이션 적용 확인 |
| 알림이 가지 않음 | 캠페인 행의 상태<br>알림 도메인의 회차 로그 | 알림 도메인의 배포 실패 진단 |
| 알림을 눌렀는데 공지가 열리지 않음 | 푸시 데이터의 `deepLink`<br>클라이언트 공지 화면 | 딥링크 앞부분과 클라이언트 경로 확인 |
