# 4-1 처리 흐름

이 문서는 NOTICE 도메인의 요청 수신부터 응답까지의 처리 단계를 정한다.

요청 필드, 응답 필드와 실패 응답은 계약에, 복구 규칙은 오류 처리에, 잠금과 알림 연결의 1회 기록은 동시성에 있다. ([4-2 계약](4-2-CONTRACT.md), [5-3 오류 처리](5-3-ERROR-HANDLING.md), [5-2 동시성](5-2-CONCURRENCY.md))

<br>

### 4-1-1 공통 처리

모든 요청은 상관관계 필터에서 요청 ID를 받는다. 공개 조회는 토큰을 읽지 않는다. 관리자 경로는 관리자 판정 필터가 요청자를 정하고 통과하지 못하면 거절한다.

상태를 바꾸는 관리자 작업은 공지 행에 비관적 잠금을 건 뒤 상태를 다시 확인한다. 변경을 적용한 뒤 같은 트랜잭션에서 감사 기록을 호출한다.

흐름도에서 다른 도메인을 호출하는 단계는 주황색이다.

<br>

```mermaid
    E --> F{"`**게시 상태인가**`"}
    F -->|아니오| X["`**없는 것으로 응답**`"]

```

- 목록은 본문을 싣지 않는다. 태그를 지정하면 그 태그의 공지만 준다. 정렬은 게시 시각 내림차순이며 같으면 내부 ID 내림차순이다. 커서는 마지막 항목의 게시 시각과 내부 ID를 담은 불투명 문자열이다.
- 상세는 없는 공지와 초안을 같은 결과로 응답한다.

### 4-1-3 작성과 수정

```mermaid
%%{init: {"flowchart": {"curve": "basis", "nodeSpacing": 24, "rankSpacing": 40}}}%%
flowchart LR
    A{"`**요청**`"} -->|작성| B["`**초안 행 생성**
작성 관리자 기록`"]
    A -->|수정| C["`**공지 행 잠금**`"]
    C --> D["`**제목, 본문, 태그 덮어쓰기**
보낸 필드만`"]
    B --> E["`**감사 기록**
ADMIN, 같은 트랜잭션`"]
    D --> E
    E --> F["`**응답**
관리자 공지 구조`"]
    classDef comp fill:#E8F2E8,stroke:#527A59,color:#182D1D
    classDef task fill:#F5D9C9,stroke:#B97450,color:#452B1D
    class A,B,C,D,F comp
    class E task
```

- 수정은 상태와 무관하게 허용한다. 게시된 공지의 수정은 공개 조회에 바로 반영되고 알림을 보내지 않는다.
- 이미 만든 캠페인과 알림 내역은 캠페인을 만든 시점의 사본이다. 공지 제목, 본문, 태그를 바꿔도 그 캠페인의 종류, 문구, 알림 내역은 바뀌지 않는다.
- 감사 기록의 변경 전후 값은 제목, 태그, 상태다. 본문은 변경 전후 값의 길이 상한을 넘을 수 있어 넣지 않는다.

### 4-1-8 알림 연결

알림 도메인이 관리자의 캠페인 예약을 처리할 때 캠페인 생성 트랜잭션 안에서 호출한다. 관리자 API 경로가 아니며 감사 기록은 알림 도메인의 캠페인 예약 기록에 포함된다. ([NOTIFICATION 4-1-16 캠페인 관리](../../NOTIFICATION/BACKEND/4-1-PIPELINES.md#4-1-16-캠페인-관리))

```mermaid
%%{init: {"flowchart": {"curve": "basis", "nodeSpacing": 24, "rankSpacing": 40}}}%%
flowchart LR
    A["`**공지 공개 식별자로
공지 행 잠금**`"] --> B{"`**게시 상태인가**`"}
    B -->|아니오, 없음| X["`**연결 불가**`"]
    B -->|예| C{"`**알림 요청 시각이
비어 있는가**`"}
    C -->|예| D["`**알림 요청 시각 기록**`"]
    C -->|아니오| E["`**공지 참조와 태그 반환**`"]
    D --> E
    classDef comp fill:#E8F2E8,stroke:#527A59,color:#182D1D
    class A,B,C,D,E,X comp
```

| 항목 | 규칙 |
|---|---|
| 연결 대상 | 게시 상태인 공지만<br>초안, 게시 해제된 공지, 없는 공지는 연결 불가 |
| 잠금 | 게시 해제, 삭제와 같은 공지 행 쓰기 잠금<br>캠페인 생성 트랜잭션이 끝날 때까지 유지 |
| 알림 요청 시각 | 처음 연결할 때만 기록하고 이후 연결은 바꾸지 않음<br>캠페인 생성이 실패하면 함께 롤백<br>공지의 수정 시각은 바꾸지 않음 |
| 횟수 | 같은 공지를 여러 캠페인에 연결할 수 있음 |
| 돌려주는 값 | 공지 내부 참조와 지금의 태그<br>알림 도메인이 캠페인에 공지 참조와 태그를 저장하고 태그로 종류를 정함 |

| 태그 | 표시 이름 | 알림 성격 | 알림 유형 |
|---|---|---|---|
| `SERVICE` | 공지사항 | 정보성 | `SERVICE` |
| `UPDATE` | 업데이트 | 정보성 | `SERVICE` |
| `MAINTENANCE` | 점검 | 정보성 | `SERVICE` |
| `EVENT` | 이벤트 | 광고성 | `MARKETING` |
| `PROMOTION` | 홍보 | 광고성 | `MARKETING` |

- 광고성 태그는 영리 목적의 광고성 정보라 정보통신망법 제50조에 따라 사전 동의자에게만 보내고 야간에는 별도 동의자에게만 보내며 푸시 제목 앞에 `(광고)`를 붙인다. 이 판정과 표기는 알림 도메인이 하며 관리자가 캠페인 제목에 `(광고)`를 직접 쓰지 않아도 된다. 공지 원문 제목은 공개 목록과 상세에 표기 없이 그대로 보인다.
- 캠페인의 종류는 관리자가 고르지 않고 이 표의 알림 유형으로 정한다. 광고성 공지를 정보성 알림으로 보내는 실수를 막기 위해서다.
- 점검은 서버 점검 예고, 장애, 오류, 복구 안내를 모두 포함한다.
- 표의 순서가 선택과 필터의 표시 순서다. 태그를 새로 더할 때는 이 표에 알림 성격을 함께 정한다.
