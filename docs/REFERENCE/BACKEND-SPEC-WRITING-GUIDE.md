# 백엔드 Spec 작성 가이드

하나의 도메인에 필요한 백엔드 명세의 파일 구성과 각 파일이 정하는 것을 적는다. 문장, 파일명과 제목 번호는 [제품 Spec 작성 가이드](PRODUCT-SPEC-WRITING-GUIDE.md)를 따른다. 아래 항목은 해당 도메인의 실제 결정으로 채우며 해당 없는 파일은 만들지 않는다.

<br>

## 1. 개요

백엔드는 클라이언트가 필요한 것을 받쳐 주고 AI 서버에 입력을 만들어 주는 양쪽 계약의 가운데에 있다. 그래서 상위 설계와 계약을 정하는 1~4단계까지는 클라이언트와 AI 담당자와 합의한 뒤 5~6단계의 품질과 릴리스로 넘어간다. 앞 단계의 결정이 뒤 단계의 기준이며, 구현에 맞추려고 앞 단계를 임의로 바꾸지 않는다.

문서는 처음부터 완벽하게 쓰지 않는다. 정해진 것이 적으면 짧게 쓰고, 구현해 보고 버리면서 빠진 결정을 채운다. 다른 팀원이나 사내 에이전트가 "이 도메인의 엔드포인트가 어디냐, 실패하면 어떻게 되냐"를 이 문서만 보고 답할 수 있으면 충분하다.

<br>

## 2. 파일 구조

```text
1-BACKGROUND.md
2-REQUIREMENTS.md
3-1-DESIGN-SOFTWARE-ARCHITECTURE.md
3-2-DESIGN-DB-SCHEMA.md
3-3-DESIGN-CONVENTIONS.md
3-4-DESIGN-DECISIONS.md
4-1-INTERACTION-PIPELINES.md
4-2-INTERACTION-CONTRACT.md
5-1-QUALITY-SECURITY.md
5-2-QUALITY-CONCURRENCY.md
5-3-QUALITY-ERROR-HANDLING.md
5-4-QUALITY-OBSERVABILITY.md
5-5-QUALITY-EVENT-TRACKING.md
6-1-RELEASE-TEST-CASES.md
6-2-RELEASE-DEPLOYMENT.md
CLAUDE.md
DECISIONS.md
```

`1~2`는 배경과 요구사항, `3~4`는 상위 설계와 계약, `5`는 품질, `6`은 릴리스다. `1`과 `5`는 반드시 둔다.

| 파일 | 정하는 것 |
|---|---|
| `1-BACKGROUND.md` | 이 도메인에 어떤 백엔드가 왜 필요한지. 도메인 배경, 관련 정책과 기존 시스템의 위치, 이 세트에서 쓰는 용어 |
| `2-REQUIREMENTS.md` | 유저 스토리가 아니라 백엔드의 기술 요구사항. 클라이언트와 AI 서버가 백엔드에 기대하는 것, 응답 시간과 처리량, 보존 기간 같은 제약을 측정 가능한 값으로 |
| `3-1-DESIGN-SOFTWARE-ARCHITECTURE.md` | 개요, 배경과 목표, 품질 속성, 배포 단위, 모듈 구조, 의존 방향, 도메인 모델, 용어. 도메인 모델은 이 도메인의 개념으로 쓴다 |
| `3-2-DESIGN-DB-SCHEMA.md` | 이 도메인이 정하는 테이블, 컬럼, 인덱스, 제약과 데이터 수명. 다른 도메인 테이블은 참조만 한다 |
| `3-3-DESIGN-CONVENTIONS.md` | 이름, 패키지, 예외, 트랜잭션, 로그 규칙 같은 코딩 컨벤션. 반드시 지킬 것과 구현자가 선택할 수 있는 것을 구분한다 |
| `3-4-DESIGN-DECISIONS.md` | 현재 적용 중인 설계 결정과 근거. 날짜와 대안이 붙은 이력은 `DECISIONS.md`에 둔다 |
| `4-1-INTERACTION-PIPELINES.md` | 요청 수신부터 응답까지 처리 흐름. 단계 경계에서 오가는 데이터 모델의 필드와 타입, AI 서버 호출, 큐와 이벤트 흐름 |
| `4-2-INTERACTION-CONTRACT.md` | 클라이언트와 AI 서버 양쪽의 계약. 엔드포인트, 요청과 성공 응답의 실제 예시, 헤더와 메타 필드, 필수와 선택. 실패 형식은 `5-3`에서 정하고 여기서는 참조한다 |
| `5-1-QUALITY-SECURITY.md` | 인증과 권한, 입력 검증, 비밀값 취급, 개인정보 |
| `5-2-QUALITY-CONCURRENCY.md` | 동시 요청, 멱등성, 잠금, 경합과 순서 보장 |
| `5-3-QUALITY-ERROR-HANDLING.md` | 오류 분류와 코드, 복구와 재시도 한도, 최종 실패의 처리와 사용자 노출. 오류 처리를 여기 한곳에 모은다 |
| `5-4-QUALITY-OBSERVABILITY.md` | 로그, 메트릭, 트레이스에 남길 필드와 알림 기준 |
| `5-5-QUALITY-EVENT-TRACKING.md` | 이 도메인의 분석 이벤트와 프로퍼티. 이벤트 이름 규칙은 용어집을 따른다 |
| `6-1-RELEASE-TEST-CASES.md` | 단위와 통합 테스트 케이스, 실행 명령과 통과 증거, 린트. 케이스가 있는 것과 실행해 통과한 것을 구분한다 |
| `6-2-RELEASE-DEPLOYMENT.md` | 배포 단위와 의존성, 배포 경로, 환경 변수와 시크릿, 배포 조건, 되돌리기 |
| `CLAUDE.md` | 문서의 역할, 읽는 순서, 작업별 참조, 명세와 코드의 대응. 명세 본문을 복사하지 않는다 |
| `DECISIONS.md` | 결정의 날짜, 배경, 채택한 선택, 대안, 영향과 재검토 조건 |

<br>

## 3. 작성 기준

- 같은 사실은 한 곳에서 정한다. 계약은 `4-2`가 기준이고 클라이언트와 AI 세트는 이 문서를 참조한다.
- 오류 처리는 `5-3`에 모은다. 파이프라인이나 계약 문서에 오류 처리를 흩어 적으면 같은 오류를 두 번 처리하거나 책임이 섞인다.
- 검증은 `6-1`에 둔다. 테스트 통과와 린트 같은 검증 항목을 릴리스 절에 모아 리뷰 자동화에 연결한다.
- 숫자와 필드명은 코드와 설정에서 확인한 값만 적는다. 미정, 비적용, 미구현을 구분한다.
- 명세의 작성, 수정과 검토를 서브에이전트에 맡기지 않는다.
