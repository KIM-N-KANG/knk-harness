# AI Spec 작성 가이드

하나의 AI 태스크에 필요한 명세의 파일 구성과 작성 내용을 정의한다. 태스크는 주어진 입력으로 특정 판단이나 생성 결과를 만드는 작업이다. 모델 호출뿐 아니라 전처리, 후처리, 평가와 운영까지 다룬다. 다른 시스템은 입력과 결과를 주고받는 계약과 책임 범위에서 다룬다.

문장, 파일명과 제목 번호는 [제품 Spec 작성 가이드](PRODUCT-SPEC-WRITING-GUIDE.md)를 따른다. 아래 항목은 해당 태스크의 실제 결정으로 작성한다. 모델, 정책, 수치나 경로를 임의로 채우지 않고 미정, 비적용, 미구현을 구분한다.

<br>

## 개요

정의한 문제를 해결하는 결과를 빠르고 반복 가능하게 출시하는 것을 목표로 한다. AI가 개발 작업을 수행해도 문제 정의, 설계 판단, 검토와 운영에 대한 책임은 담당자에게 있다.

- **명세로 구현을 통제한다.** 해결할 문제와 기대 결과를 정하고 구현자가 지켜야 할 동작, 책임과 품질 기준을 전달한다. 상위 설계만으로 정해지지 않는 실행 순서, 컴포넌트 경계, 구현 컨벤션과 금지 패턴까지 구체화한다.
- **AI의 역할을 구분한다.** 개발 AI는 명세 작성과 구현을 수행하고 제품 AI는 사용자의 태스크를 수행한다. LLM-as-a-judge를 사용하면 결과를 채점하는 역할도 구분한다. 각 역할의 입력, 권한과 성공 기준을 섞지 않는다.
- **검증과 운영을 연결한다.** 코드 생성 후 테스트와 AI 품질 평가로 요구사항 충족 여부를 확인한다. 평가한 코드, 프롬프트와 설정을 배포 버전과 연결하고 운영에서 발견한 문제를 개선 자료로 남긴다. 규칙에는 실제 검사와 확인 기록을 연결한다.
- **앞 단계의 결정을 기준으로 작성한다.** 변경은 해당 단계와 영향을 받는 이후 단계에 반영한다. 계약을 정한 5단계가 바뀌면 1~4단계의 결정은 유지하고 계약과 이후 구현, 평가 문서를 수정한다. 하위 구현에 맞추려고 상위 요구사항을 임의로 바꾸지 않는다.

<br>

## 파일 구조와 관리

아래는 하나의 AI 태스크에 대한 명세 파일이다. 같은 폴더에 나란히 둔다.

```text
1-BACKGROUND.md
2-1-USER-STORY.md
2-2-OPERATION-REQUIREMENTS.md
3-TASK-DEFINITION.md
4-1-DESIGN-COGNITIVE-ARCHITECTURE.md
4-2-DESIGN-SOFTWARE-ARCHITECTURE.md
5-CONTRACT.md
6-1-AI-EXECUTION.md
6-2-SOFTWARE-IMPLEMENTATION.md
6-3-AI-ALIGNMENT.md
6-4-AI-EVALUATION-METHOD.md
6-5-AI-EVALUATION-IMPLEMENTATION.md
6-6-AI-PERFORMANCE-REPORT.md
7-1-ERROR-HANDLING.md
7-2-TEST-CASES.md
7-3-OBSERVABILITY.md
7-4-DEPLOYMENT.md
```

`1~5`에서 목적, 요구사항, 태스크, 상위 설계와 외부 계약을 정한다. `6`에서는 상세 구현, 품질 개선과 평가를, `7`에서는 오류 처리, 테스트, 관측과 배포를 정한다. `1~5`를 작성해 구현을 시작할 수 있어도 평가와 운영 준비까지 완료된 것은 아니다. 평가 기준은 요구사항을 정할 때 함께 정하고 이후 문서에서 실행 방법을 구체화한다.

각 문서에는 적용 태스크, 상태, 담당자, 기준 자료와 버전을 표시한다. 실제 구현과 검증 기록이 있으면 해당 위치를 연결한다. 중요한 미정 사항에는 결정할 담당자와 영향을 받는 작업을 적는다.

<br>

### 기준 문서와 참조

같은 사실은 한 곳에서 정하고 다른 문서는 해당 파일과 항목 번호를 참조한다. 정책, 프롬프트, 스키마와 데이터셋에 원본이 있으면 위치와 버전을 연결한다.

| 내용 | 기준 문서 |
|---|---|
| 사용자 기대 | `2-1-USER-STORY.md` |
| 개발자 기대, 품질 목표, 비용과 시간 제한 | `2-2-OPERATION-REQUIREMENTS.md` |
| 입력과 출력의 의미 | `3-TASK-DEFINITION.md` |
| AI의 판단과 생성 구조 | `4-1-DESIGN-COGNITIVE-ARCHITECTURE.md` |
| 컴포넌트 책임과 데이터 처리 흐름 | `4-2-DESIGN-SOFTWARE-ARCHITECTURE.md` |
| 외부 전송 형식과 실패 계약 | `5-CONTRACT.md` |
| 실행과 프롬프트 조립 규칙 | `6-1-AI-EXECUTION.md` |
| 코드 구조와 구현 규칙 | `6-2-SOFTWARE-IMPLEMENTATION.md` |
| 평가 방법과 합격 판정 방법 | `6-4-AI-EVALUATION-METHOD.md` |
| 현재 성능과 실험 결과 | `6-6-AI-PERFORMANCE-REPORT.md` |
| 오류별 복구와 최종 처리 | `7-1-ERROR-HANDLING.md` |

번호 문서 외의 안내와 기록은 다음 역할로 관리한다.

- **`CLAUDE.md`:** 문서의 역할, 읽는 순서, 작업별 참조, 명세와 코드의 대응 관계, 작성 규칙과 검증 명령의 위치를 안내한다. 명세 본문을 복사하지 않는다.
- **`DECISIONS.md`:** 중요한 결정의 날짜, 상태, 배경, 채택한 선택, 대안, 영향과 재검토 조건을 기록한다. 현재 적용할 기준은 해당 명세에 반영하고 과거 결정은 이력으로 남긴다.

<br>

### 그림 작성 규칙

| 항목 | 규칙 |
|---|---|
| 배치 | 소제목 아래에 표를 먼저 두고 설명과 그림을 이어 배치한다. 입력은 왼쪽, AI 작업은 가운데, 출력은 오른쪽에 둔다 |
| 입력과 출력 | 항목마다 박스를 나누고 위아래로 가지런히 쌓는다. 박스 안에는 짧은 항목 이름을 쓴다 |
| 박스 글자 | 박스를 대표하는 이름은 굵게 쓰고 세부 설명은 줄을 바꿔 일반 글자로 쓴다. Mermaid에서는 `<b>이름</b><br/>설명` 형식을 사용한다 |
| 연결 | 항목마다 연결선을 그린다. AI 작업으로 모이는 입력선에는 화살촉을 붙이지 않는다. 출력선과 단계 간 전달에는 화살표를 쓴다 |
| 화살표 모양 | 곧게 연결할 수 있으면 직선으로 그린다. 다른 박스를 피해야 할 때만 곡선을 쓴다. 직각으로 꺾는 선은 쓰지 않는다 |
| 간격 | 선이 연결 대상 외의 박스나 글자를 침범하지 않도록 간격을 확보한다. 연결선 끝의 위치는 Mermaid 자동 배치를 따른다 |
| 선택 항목 | 항목 이름에 선택 여부를 표시하고 연결선은 점선으로 그린다. 색만으로 의미를 구분하지 않는다 |
| 색상 | 입력과 출력은 연한 초록색, AI 작업은 연한 주황색으로 구분한다. 문서 안에서 같은 역할에는 같은 색을 쓴다 |
| 파일 형식 | Markdown 안의 Mermaid 코드로 관리한다. 배치를 맞추려고 별도 SVG 파일로 바꾸지 않는다 |

도식 구성은 [Anthropic의 Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)를 참고한다. 태스크 정의에서는 입력과 출력을, AI 설계에서는 생성과 검증 단계를, 소프트웨어 설계에서는 시스템 간 호출 관계를 보여준다. 한 그림에 서로 다른 설명 수준을 섞지 않는다.

그림을 수정한 뒤에는 실제 표시 결과에서 항목 정렬, 연결 대상, 선과 박스의 간격, 글자 잘림을 확인한다.

<br>

## 파일별 작성 기준

각 절은 해당 파일의 목적과 필요한 결정을 설명한다. 실제 소제목은 작성할 내용의 큰 주제에 맞춰 정한다. 아래의 개별 작성 항목을 모두 소제목으로 만들지는 않는다.

<br>

### 1-BACKGROUND.md

왜 이 태스크가 필요하며 어떤 업무를 바꾸려는지 설명한다.

- **현재 업무와 문제:** 누가 어떤 절차로 일하며 어떤 부담, 오류나 지연이 발생하는지 작성한다. 확인된 현상과 아직 확인하지 않은 규모를 구분한다.
- **목적과 영향:** 문제를 해결하면 누가 어떤 결과를 얻는지 적는다. AI 도입 자체를 목적으로 쓰지 않는다.
- **범위:** AI가 보조하거나 자동 처리할 일, 사람이 계속 결정할 일, 이번에 다루지 않을 대상을 구분한다.
- **용어와 근거:** 공통 용어를 정의하고 관련 정책, 기획, 기존 시스템과 데이터의 위치, 관리 담당과 버전을 연결한다.

모델 설정이나 구현 방법은 뒤의 설계 문서에서 정한다. 이 문서를 읽으면 해결할 문제, 대상 사용자와 책임 범위를 설명할 수 있어야 한다.

<br>

### 2-1-USER-STORY.md

AI가 만드는 결과를 누가 사용하며 어떤 성질을 기대하는지 작성한다.

- **사용자와 상황:** 최종 사용자, 내부 검수자 등 결과를 사용하는 사람과 필요한 상황을 구분한다. 호출 시스템이 결과를 어떻게 전달하거나 사용하는지도 확인한다.
- **기대 결과와 이유:** 필요한 산출물과 그 결과로 할 행동을 적는다. 판정, 근거, 요약과 안내처럼 쓰임이 다르면 구분한다.
- **수용 조건:** 기대를 만족하는 결과와 위반하는 결과를 구별할 기준을 작성한다. 의미가 모호하면 예시를 덧붙인다.
- **판단과 후속 책임:** 결과를 바로 적용하는지, 사람이 확인하는지, 잘못된 결과에 어떻게 의견을 전달하는지 정한다.
- **연결:** 각 스토리를 `3-TASK-DEFINITION.md`의 출력과 `6-4-AI-EVALUATION-METHOD.md`의 평가 항목에 연결한다. 정량 목표는 `2-2-OPERATION-REQUIREMENTS.md`에서 정한다.

<br>

### 2-2-OPERATION-REQUIREMENTS.md

실제 운영에서 개발자가 만족하기 위한 품질, 비용, 시간과 제약을 정한다.

- **오류의 우선순위:** 잘못된 결과와 실행 실패가 사용자와 업무에 미치는 영향을 구분한다. 줄여야 할 오류, 자동 처리 범위와 사람 확인 조건을 정한다.
- **품질 지표:** 태스크에 맞는 지표를 선택한다. 분류에는 accuracy, precision, recall 등을 사용할 수 있으며 생성 결과에는 별도의 채점 기준이 필요하다. 지표마다 계산식, 집계 대상, 분모와 제외 조건을 명시한다.
- **지표의 의미:** precision과 recall은 양성으로 정한 대상을 명시한다. 승인 정밀도는 AI가 승인한 것 중 정답도 승인인 비율이고 자동 승인율은 전체 처리 대상 중 자동 승인한 비율이다. 두 지표를 같은 것으로 쓰지 않는다. 실행 실패, 보류, 중복과 분모가 0인 경우의 집계도 정한다.
- **수용 기준:** 목표값, 하한 또는 상한, 적용 조건, 미달 시 처리와 승인 담당을 적는다. 아직 합의하지 않은 값은 미정으로 남긴다.
- **비용:** 한 건의 단위, 통화와 산정 기준, 평균 비용과 필요한 상한을 정한다. 최초 호출, 복구, 폴백, 검색과 실패 비용 중 무엇을 포함하는지 명시한다. 제품 실행 비용과 채점용 AI 비용은 구분한다.
- **시간과 처리량:** 측정 시작과 종료, 큐 대기 포함 여부, 평균 처리 시간, 필요한 상위 지연 지표와 전체 처리 시간 상한을 정한다. 동시 처리, 최대 요청량, 외부 호출 제한과 입력 크기 조건도 작성한다.
- **운영 제약:** 허용 환경, 모델 제공 경로, 데이터의 저장과 외부 전달, 비밀 정보 취급 조건을 정한다.

현재 측정값은 `6-6-AI-PERFORMANCE-REPORT.md`에 기록한다. 목표와 실제 성능을 같은 값처럼 쓰지 않는다.

<br>

### 3-TASK-DEFINITION.md

요구사항을 AI가 수행할 구체적인 작업으로 바꾸고 입력과 출력의 의미를 정한다.

- **처리 단위:** 한 번의 요청이 해결하는 작업을 정의한다. 사진 한 장, 후기 한 건, 대화의 다음 한 턴처럼 입력과 평가의 단위를 명확히 한다.
- **입력:** 필요한 원본과 맥락, 출처, 필수 여부, 허용 범위와 누락 시 의미를 정한다.
- **출력:** 각 항목의 의미, 결과를 사용하는 대상과 후속 행동을 적는다. 출력별로 무엇을 맞는 결과로 보는지 정한다.
- **출력 간 조건:** 여러 항목이 함께 만족해야 하는 조건을 정한다. 여러 근거의 표현, 중복 처리, 값 없음과 빈 목록의 차이, 결과를 합치는 책임을 포함한다.
- **결과와 실패:** 업무상 판정과 유효한 결과를 만들지 못한 실행 실패를 구분한다. 검수에서 반려를 판단한 것과 판정에 실패한 것은 다른 결과다.
- **사례:** 정상 입력, 정보 부족, 범위 밖 입력과 실패에서 반환할 결과를 설명한다. 분석용 태그와 핵심 판정처럼 역할이 다른 출력은 평가 기준도 구분한다.

외부 필드명과 전송 형식은 `5-CONTRACT.md`에서 정한다. 이 단계에서 입력, 출력과 정답의 의미가 정해져야 평가 데이터의 형식을 정의할 수 있다.

<br>

### 4-1-DESIGN-COGNITIVE-ARCHITECTURE.md

입력에서 무엇을 인식하고 판단하며 어떤 과정을 거쳐 결과를 생성할지 정한다.

- **접근과 근거:** 규칙 기반 처리, 단일 모델 호출, 다단계 호출, RAG, 에이전트 루프 중 사용할 방식을 선택하고 요구사항과 연결해 이유를 적는다. 사용하지 않는 방식과 이유도 명시한다.
- **판단 단계:** 단계마다 필요한 정보와 중간 결과, 최종 결과로 이어지는 순서를 설명한다.
- **모델과 코드의 책임:** 모델에 맡길 의미 판단과 코드가 처리할 검증이나 변환을 구분한다. 코드가 모델의 실패를 임의의 정상 판정으로 바꾸지 않도록 한다.
- **상태와 지식:** 요청 간 상태, 대화 이력, 정책과 검색 정보의 필요 여부와 관리 담당을 정한다. 무상태를 선택하면 AI 모듈이 보관하지 않는 정보와 외부에서 관리할 상태를 구분한다.
- **경계와 종료:** 애매한 판단, 부족한 맥락, 부적격 입력을 어느 단계에서 처리하는지 정한다. 반복과 복구가 있으면 허용 조건, 종료 기준과 예산을 정한다.
- **조건부 기능:** RAG를 사용하면 검색 실패, 근거 부족, 문서 접근 권한과 정보 갱신을 다룬다. 도구나 에이전트를 사용하면 허용 작업, 권한, 반복 제한과 중지 조건을 다룬다.

클래스 구조와 실제 호출 옵션은 이 문서에서 확정하지 않고 소프트웨어 설계와 상세 실행에서 구체화한다.

<br>

### 4-2-DESIGN-SOFTWARE-ARCHITECTURE.md

AI의 판단 구조를 컴포넌트와 데이터의 처리 흐름으로 표현한다.

- **시스템 경계:** AI 모듈 내부와 호출 시스템, 저장소, 큐, 모델 게이트웨이 등 외부 시스템을 구분한다. 사용하는 시스템만 포함한다.
- **요청 처리 흐름:** 요청 수신, 내부 입력 변환, 데이터 취득, AI 실행, 결과 변환과 전달 순서를 정한다. 동기 또는 비동기 방식을 명시한다.
- **컴포넌트:** 각 구성 요소의 입력, 출력, 책임과 하지 않는 일을 적는다. 모델 호출, 전처리, 프롬프트 조립과 결과 전달의 관계를 설명한다.
- **내부 데이터 모델:** 외부 계약과 내부 입력, 출력의 대응 관계와 변환 책임을 정한다.
- **상태와 자원:** 작업 상태, 중복 처리, 결과 저장과 동시 실행을 누가 관리하는지 정한다. 외부 클라이언트와 연결 자원의 생성, 재사용과 종료 책임도 적는다.
- **공통 실행 경로:** 운영 요청과 평가 CLI가 같은 실행 코드를 호출하도록 경계를 정한다. 오류와 취소가 어디로 전달되는지도 연결한다.

실제 파일 배치와 함수 인터페이스는 `6-2-SOFTWARE-IMPLEMENTATION.md`에서 구체화한다.

<br>

### 5-CONTRACT.md

다른 시스템이 AI 내부 코드를 보지 않고도 요청, 결과와 실패를 처리할 수 있도록 약속을 정한다.

- **연동 대상과 방식:** 제공자, 소비자, 담당자와 전달 방향을 적는다. API라면 메서드, 경로와 상태 코드를, 이벤트라면 채널, 생산자, 소비자와 버전을 정의한다.
- **요청과 결과:** 필드명, 타입, 필수 여부, 허용값, 단위, 크기 제한, 기본값, 누락과 `null`의 의미를 정한다. `3-TASK-DEFINITION.md`의 의미와 일치시킨다.
- **실패 계약:** 정상 결과와 실행 실패의 구조, 오류 코드, 재시도 가능 여부, 최종 실패 통지와 후속 책임을 정한다.
- **식별과 전달:** 요청, 이벤트와 추적 ID의 관계, 중복 수신, 순서, 결과 전송 실패와 재처리 책임을 정한다.
- **시간과 복구:** 호출자, AI 실행기와 외부 호출 계층의 시간 제한과 재시도 책임을 합의한다. 여러 계층의 재시도가 전체 예산을 넘지 않도록 한다.
- **권한과 호환성:** 인증, 접근 권한, 외부 전달 금지 정보, 스키마 변경과 소비자 전환 조건을 정한다.
- **계약 예시:** 정상 요청, 정상 결과와 실패 결과를 스키마에 맞춰 작성한다. 실제 값이나 비밀 정보를 예시에 넣지 않는다.

모델 게이트웨이와 데이터 전달 시스템은 각각 계약을 정한다. 존재하지 않는 API를 추가하지 않으며 내부 구현 전체를 외부 계약으로 고정하지 않는다.

<br>

### 6-1-AI-EXECUTION.md

태스크 입력이 최종 결과로 바뀌는 실행 순서와 분기를 상세하게 정한다.

- **진입과 종료:** 입력 모델, 반환 모델, 실행 중 변경할 수 있는 대상과 취소 전달 방식을 정한다.
- **입력 검증과 취득:** 필수값, 데이터 형식과 크기, 외부 URL 허용 조건, 다운로드와 파싱 제한, 취득 실패 처리를 정한다.
- **전처리:** 해당 입력에 필요한 변환, 정규화, 길이 제한, 인코딩과 출력 형식을 명시한다. 이미지를 다룬다면 지원 형식, 크기와 리사이징 조건을 정한다.
- **프롬프트 조립:** 시스템 지시, 정책, 사용자 입력, 맥락과 출력 형식을 어떤 순서로 구성하는지 적는다. 정책 원본과 프롬프트를 구분하고 버전, 누락과 길이 초과 처리를 명시한다. 외부 데이터의 문장을 시스템 지시로 취급하지 않는다.
- **모델 호출:** 기본 모델, 허용 폴백, 지원 파라미터, 출력 제한, 응답 형식, 시간 제한과 설정의 출처를 정한다. 지원하지 않는 옵션을 전송하지 않는다.
- **검증과 복구:** 응답 파싱, 타입, 필수값과 출력 간 조건을 확인하는 순서를 정한다. 재시도, 출력 복구와 폴백의 전환 조건은 `7-1-ERROR-HANDLING.md`의 기준을 따른다.
- **후처리와 기록:** 필요한 결과 변환, 중복 제거, 최종 모델 조립을 정한다. 실제 적용한 정책, 프롬프트, 모델과 설정, 시도별 결과를 기록하도록 연결한다.

응답의 형식이 맞는 것과 내용이 맞는 것은 구분한다. 누락된 판정을 후처리에서 임의로 만들어 채우지 않는다.

<br>

### 6-2-SOFTWARE-IMPLEMENTATION.md

상세 실행을 어떤 코드 구조와 규칙으로 구현할지 정한다.

- **파일 배치:** 패키지, 모듈과 파일의 역할을 적고 신규, 수정과 재사용 대상을 구분한다.
- **인터페이스와 모델:** 주요 클래스나 함수의 이름, 입력과 출력 타입, 비동기 여부, 오류와 상태 변경을 정의한다. 외부 계약, 내부 태스크와 모델 응답 사이의 변환 책임을 적는다.
- **의존성:** 외부 클라이언트, 설정과 기록 도구를 어디서 만들고 전달하는지 정한다. 테스트에서 외부 의존성을 대체할 경계도 명시한다.
- **외부 라이브러리:** 사용 범위, 버전 관리, 공통 모듈의 재사용과 변경 절차를 적는다.
- **구현 규칙:** 이름, 타입, 예외, 비동기 취소, 자원 해제, 설정 접근과 로그 규칙을 정한다. 규칙에 맞는 범위에서 구현자가 선택할 수 있는 부분을 구분한다.
- **금지 패턴과 검증:** 운영과 평가 코드의 복제, 비밀값 하드코딩, 무제한 재시도, 예외를 숨기는 처리와 임의 기본 판정 등을 제한하고 확인할 테스트나 검사에 연결한다.

프롬프트 조립과 모델 설정의 기준은 `6-1-AI-EXECUTION.md`를 참조한다. 이 문서에서는 해당 자산을 코드에 전달하고 사용하는 구조를 정한다.

<br>

### 6-3-AI-ALIGNMENT.md

기대 결과와 실제 결과의 차이를 어떤 자료와 수단으로 줄일지 정한다.

- **개선 대상:** 유저 스토리와 운영 요구사항 중 어떤 결과나 지표를 개선하는지 명시한다.
- **피드백과 검수:** 라벨 검토, 사용자나 검수자의 피드백, 운영 기록과 실패 사례의 수집 위치, 담당과 사용 범위를 정한다. 피드백을 검토 없이 정답으로 확정하지 않는다.
- **원인 구분:** 정책의 모호함, 라벨 오류, 맥락 부족, 모델 판단과 구현 결함을 구분한다.
- **개선 과정:** 사례 검토, 원인 가설, 변경, 비교 평가, 기존 기능의 품질 확인, 채택과 운영 확인을 연결한다.
- **허용 수단:** 정책 갱신, 프롬프트 수정, 모델 교체와 파이프라인 변경 중 허용 범위를 정한다. 파인튜닝, DPO, GRPO나 내부 모델 서빙을 제외한다면 이유와 재검토 조건을 기록한다. 특정 태스크의 제외 결정을 공통 금지로 적용하지 않는다.
- **평가 데이터와 채택:** 튜닝에 사용하는 데이터와 별도 검증 데이터를 구분한다. 정책 변경에 따른 정답 갱신과 점수를 높이기 위한 기준 변경을 혼동하지 않는다. 채택한 실험은 성능 기록과 배포 버전에 연결한다.

채점 기준과 계산 방법은 `6-4-AI-EVALUATION-METHOD.md`에서 정한다.

<br>

### 6-4-AI-EVALUATION-METHOD.md

무엇을 어떤 데이터로 실행하고 어떤 기준으로 채점할지 정한다.

- **평가 범위:** 태스크의 처리 단위와 평가의 시작, 종료 지점을 정한다. 모델만 평가하는지 실제 실행 파이프라인을 평가하는지 구분한다.
- **벤치마크:** 데이터 위치, 접근 권한, 버전, 사례 ID, 입력과 정답 형식, 적용 정책을 기록한다. 실제 분포, 중요 사례, 제외 조건과 표본 규모의 근거를 적는다.
- **정답과 데이터 분리:** 출력별 정답과 수용 기준, 라벨 검토 담당, 이견 처리와 정책 변경 시 갱신 방법을 정한다. 개발, 튜닝과 최종 검증 데이터의 구분과 중복을 확인한다.
- **코드 기반 평가:** 스키마, 필수값과 출력 간 조건을 검사한다. 분류 지표는 운영 요구사항에서 정한 대상과 계산 조건을 따른다.
- **정성 평가:** 근거, 요약과 안내처럼 의미를 평가할 항목을 구분한다. LLM-as-a-judge를 사용하면 채점 모델, 프롬프트, 점수별 기준과 사람 평가를 비교하는 방법을 정한다.
- **변동과 실패:** 반복 실행과 집계 방법, 결과의 변동을 기록할 범위를 정한다. 제품 실행 실패, 채점 실패와 평가 누락을 구분하고 실패한 사례를 제거해 점수를 높이지 않는다.
- **합격 판정:** `2-2-OPERATION-REQUIREMENTS.md`의 목표를 참조해 통과, 미달과 판정 불가 조건을 정한다. 비용과 시간도 같은 측정 범위를 사용한다. 통합 테스트로 가져갈 사례의 선정 기준을 연결한다.

평가 코드 작성 전에 입력 한 건의 형식, 출력별 채점과 전체 평가의 판정 방법을 설명할 수 있어야 한다.

<br>

### 6-5-AI-EVALUATION-IMPLEMENTATION.md

평가 방법을 CLI에서 실행하고 결과를 남기는 프로그램의 구현을 정한다.

- **CLI 진입점:** 명령과 인자, 데이터셋과 설정 선택, 실행 환경, 권한, 예산과 결과 저장 위치를 정한다. 실제 명령과 구현 예정 인터페이스를 구분한다.
- **공통 실행 코드:** 운영과 같은 전처리, 프롬프트, 모델 호출과 후처리 구현을 호출한다. 평가용으로 제품 실행 로직을 복사하거나 다시 만들지 않는다.
- **데이터 처리:** 벤치마크 형식과 자산을 확인하고 입력을 공통 실행 코드에 전달한다. 정답은 채점 단계에서 사용하며 제품 AI의 입력에 넣지 않는다.
- **실행 관리:** 동시 처리, 속도, 시간과 비용 제한, 취소, 중단 후 재개와 사례별 상태를 정한다. 설정이 다른 결과를 같은 조건의 평가로 섞지 않는다.
- **채점과 기록:** 제품 실행과 채점을 분리하고 각각의 실패, 모델과 비용을 기록한다. 실행 ID, 사례 ID, 코드, 정책, 프롬프트, 모델, 설정, 데이터셋과 채점 기준의 버전을 결과와 함께 남긴다.
- **결과 재사용:** 새로 생성한 결과, 기존 결과를 다시 채점한 경우와 중단 후 재사용한 결과를 구분한다.
- **격리와 완료:** 평가 결과를 실제 사용자나 운영 데이터에 반영하지 않도록 한다. 사례별 결과, 집계, 합격 여부와 누락을 저장하고 통과, 기준 미달과 실행 오류를 구분해 종료한다.

평가 경로는 다음과 같이 구성한다.

```text
운영: 서비스 요청 → 공통 AI 실행 코드 → 서비스에 결과 전달
평가: CLI → 벤치마크 입력 → 같은 AI 실행 코드 → 채점 → 집계와 기록
```

CLI는 평가 프로그램의 시작점이다. 검수 AI라면 CLI가 평가용 입력을 기존 검수 함수에 넣고 반환된 결과를 정답과 비교한다. 공통 코드 사용이 큐와 결과 발행을 포함한 전체 운영 경로의 검증을 뜻하지는 않으며 해당 범위는 `7-2-TEST-CASES.md`에 정한다.

<br>

### 6-6-AI-PERFORMANCE-REPORT.md

현재 운영 버전의 성능과 과거 실험을 구분해 기록한다.

- **현재 상태:** 배포된 코드, 정책, 프롬프트, 모델과 설정 조합, 적용 시점과 근거 평가 실행을 앞에 표시한다. 최신 실험 후보를 현재 운영 버전으로 표시하지 않는다.
- **평가 조건:** 데이터셋, 채점 기준, 환경과 측정 시점을 적는다. 평가 결과와 운영 관측 결과를 구분한다.
- **품질:** 전체와 중요한 사례 집단의 지표, 표본 수, 분자와 분모, 실패, 제외와 판정 불가 수를 기록한다. 목표와 측정값을 비교한다.
- **시간과 비용:** 단위, 포함한 실행 범위, 평균과 필요한 상위 지연, 실패 처리 시간, 제품 호출과 평가 비용을 구분한다.
- **비교와 이력:** 변경 가설, 기준 버전과 후보 결과, 기존 품질 저하 여부, 채택이나 보류 이유, 담당과 원본 결과 위치를 남긴다. 평가 조건이 다르면 직접 비교 가능한지 명시한다.
- **한계:** 미평가 대상, 부족한 데이터, 알려진 오류와 후속 확인 사항을 적는다. 측정하지 않은 값을 0으로 쓰지 않는다.

<br>

### 7-1-ERROR-HANDLING.md

실행 단계별 오류를 누가 처리하며 어떤 결과로 종료할지 정한다.

- **오류 분류:** 입력, 데이터 취득, 전처리, 모델 호출, 응답 검증, 결과 전송과 관측에서 발생하는 오류를 구분한다.
- **처리 기준:** 발생 단계, 탐지 조건, 내부 오류와 외부 코드, 복구 가능 여부, 제한, 최종 결과와 담당을 작성한다.
- **복구 구분:** 같은 요청의 재시도, 잘못된 출력의 복구, 다른 모델로의 폴백과 메시지 재처리를 구분한다. 각 처리의 담당 계층을 정한다.
- **전체 한도:** 총 호출 수, 시간과 비용 예산, 재시도 간 대기와 취소 조건을 정한다. 여러 계층의 복구가 한도를 넘지 않도록 종료 조건을 둔다.
- **최종 실패:** 허용된 대체 모델, 수동 검토, 보류나 사용자 재시도 경로를 정한다. 실행 실패를 정상 승인이나 반려로 바꾸지 않는다.
- **전달과 노출:** 계산 실패와 결과 전송 실패를 구분한다. 중복 전달, 수신 확인과 재처리 책임을 정하고 사용자 안내와 내부 진단 정보를 분리한다.
- **연결:** 오류별 관측과 테스트를 연결한다. 외부 실패 형식은 `5-CONTRACT.md`와 일치시킨다.

<br>

### 7-2-TEST-CASES.md

코드와 외부 연동이 명세의 정상 동작과 오류 처리 규칙을 따르는지 검증한다. AI 결과의 품질 평가는 `6-4-AI-EVALUATION-METHOD.md`와 구분한다.

- **범위:** 단위와 통합 테스트가 확인할 경계를 정한다. 계약 검사와 실제 외부 연동을 포함하면 해당 범위도 명시한다.
- **케이스:** 식별자, 연결 요구사항, 사전 조건, 입력, 실행 단계, 기대 결과와 상태 변화, 테스트 데이터, 코드 위치와 실행 환경을 적는다.
- **단위 검증:** 전처리, 프롬프트 조립, 설정, 응답 검증과 결과 조립을 확인한다. 외부 의존성을 대체한 범위를 표시한다.
- **통합 검증:** 요청 수신부터 결과 전달까지 확인할 단계와 실제 호출할 외부 시스템을 정한다. 벤치마크에서 사례를 가져오면 버전과 선정 기준을 기록한다.
- **실패와 반복:** 시간 초과, 호출 제한, 잘못된 출력, 취소, 복구 한도 소진, 중복과 결과 전송 실패를 확인한다. 모델 출력의 문장 일치와 의미나 형식 검사를 구분한다.
- **실행 증거:** 실행 명령, 대상 버전, 결과와 로그를 남긴다. 실패, 생략과 미실행을 구분하고 반복 실행이나 기준 완화로 통과를 만들지 않는다.

일부 통합 사례의 통과를 전체 AI 품질의 합격으로 쓰지 않는다. 테스트 코드가 있는 것과 실제 실행해서 통과한 것도 구분한다.

<br>

### 7-3-OBSERVABILITY.md

운영 요청의 실행을 추적하고 품질, 시간과 비용의 변화를 확인할 기준을 정한다.

- **추적 단위:** 요청, 실행 시도와 모델 호출을 연결할 ID를 정한다. 필요한 경우 대화의 세션과 턴, 요청과 결과 이벤트도 연결한다.
- **단계별 기록:** 데이터 취득, 전처리, 프롬프트 조립, 모델 호출, 복구, 검증과 결과 전송의 상태와 시간을 구분한다. 관측 도구의 이름만 적고 끝내지 않는다.
- **실행 정보:** 환경, 코드, 정책, 프롬프트, 모델, 설정과 스키마 버전, 오류 코드, 실제 폴백과 복구 횟수를 남긴다.
- **지표:** 처리량, 실행 실패, 스키마 오류, 복구와 폴백, 시간, 비용, 큐 대기와 사람 검토 전환 중 필요한 지표를 정한다. 사용량과 비용의 산정 범위, 누락 여부도 기록한다.
- **품질 피드백:** 검수 결과나 사용자 피드백을 해당 실행과 연결한다. 정답 확인 없이 측정한 승인 비율을 승인 정밀도로 표시하지 않는다.
- **알림과 대응:** 기준값, 측정 기간, 필요한 최소 건수, 알림 대상, 담당과 대응 절차를 연결한다.
- **데이터와 수집 실패:** 기록할 입력과 출력, 마스킹, 접근 권한, 보존과 삭제, 환경 분리를 정한다. 기록 전송 실패, 재전송과 일부 요청만 수집하는 경우의 처리도 정한다.

<br>

### 7-4-DEPLOYMENT.md

검증한 실행 조합을 배포하고 문제 발생 시 되돌리는 방법을 정한다.

- **단위와 의존성:** 서비스, 워커나 라이브러리 중 배포 형태와 함께 있어야 하는 외부 시스템을 명시한다. 포함할 코드, 정책, 프롬프트와 설정을 정한다.
- **배포 경로:** 빌드 대상, 결과물, 저장소, 배포 흐름, 인프라 설정 위치와 담당을 기록한다.
- **평가 도구 분리:** 운영에 필요한 공통 코드와 평가 CLI, 데이터셋, 개발 의존성을 구분하고 배포 포함 여부를 정한다.
- **배포 조건:** 문서와 계약 검토, 코드 검사, 테스트와 AI 평가의 통과 기준, 버전 일치와 승인 담당을 연결한다.
- **환경 변수와 비밀 정보:** 이름, 의미, 타입, 필수 여부, 기본값, 환경별 출처, 주입 담당과 변경 적용 방식을 적는다. 실제 비밀값은 문서나 코드에 넣지 않는다.
- **운영 설정:** 모델, 폴백, 시간 제한, 예산과 라우팅 중 코드 변경 없이 조정할 항목, 허용 범위와 설정 우선순위를 정한다. 설정 변경도 검증과 배포 절차에 포함한다.
- **적용과 복구:** 배포 순서, 구버전과의 호환, 진행 중 작업의 처리, 되돌릴 코드와 설정 조합, 대체 경로와 담당을 정한다.
- **배포 후 확인:** 오류, 시간, 비용과 품질을 확인할 기간과 기준을 정한다. 실제 배포한 조합에 맞춰 `6-6-AI-PERFORMANCE-REPORT.md`의 현재 상태를 갱신한다.

## 4 검토와 변경

- **결정의 연결:** 사용자 기대가 출력에 반영되고 목표값, 평가 방법과 배포 조건이 같은 기준을 따르는지 확인한다.
- **책임과 구현:** 컴포넌트의 책임, 외부 계약과 오류 처리가 일치하는지 확인한다. 반드시 지킬 구현 규칙과 선택 가능한 범위를 구분한다.
- **원본과 참조:** 같은 정책, 프롬프트와 스키마를 참조하는지 확인한다. 파일명이나 소제목 번호가 바뀌면 링크와 안내도 갱신한다.
- **실행 증거:** 운영과 평가가 같은 실행 코드를 사용했는지, 실제 테스트와 평가를 실행했는지, 기록한 버전이 배포 대상과 같은지 확인한다.
- **미정과 완료:** 미정 사항의 담당과 영향을 기록한다. 문서 작성, 구현, 검증 통과와 배포 완료를 서로 다른 상태로 남긴다.
- **변경 범위:** 기존 태스크의 수정은 관련 명세에 반영한다. 바뀐 결정과 영향을 받는 이후 문서, 다시 확인할 테스트와 평가를 기록한다. 중요한 선택의 이유와 대안은 `DECISIONS.md`에 남긴다.
