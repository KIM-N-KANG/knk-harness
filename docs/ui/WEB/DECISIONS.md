# DECISIONS.md

현재 적용 기준은 각 명세에 두고 결정 당시의 이유와 대체 관계는 이 문서에 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다. 기존 ID, 날짜, 당시 상태와 근거를 유지한다.
- 상태와 구현 설명은 원본의 기록 시점을 기준으로 해석한다. 현재 적용 여부나 배포 완료를 과거 기록만으로 단정하지 않는다.
- 결정이 바뀌면 새 ID로 기록하고 대체하는 결정과 적용 범위를 명시한다.
- 원문에 구분되지 않은 배경, 대안과 영향은 추측해서 보충하지 않는다.

<a id="w-030-탭으로-나가는-이동은-navigation-api로-아래-탭-기록까지-되돌아감"></a>

**W-030. 탭으로 나가는 이동은 Navigation API로 아래 탭 기록까지 되돌아감**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-09 |
| 상태 | Accepted (원문 기록 기준) |
| 배경 | 제작 화면 나가기와 스토리, 채팅 삭제는 지금 화면을 탭으로 교체해, 그 탭에서 들어온 경우 같은 탭이 기록에 두 번 남아 뒤로가기 한 번이 아무 변화를 만들지 않았다. Android는 쌓인 화면을 걷어내고 하단 탭을 연다. 웹은 지나온 기록을 지울 수 없고, 앱 안 이동 추적은 진입 이후 이동이 있었는지만 알아 아래 기록이 어느 화면인지 모른다. |
| 채택 | Navigation API `entries()`에서 가장 가까운 아래 탭 기록을 찾아 `history.go`로 되돌아간다. 갈 탭과 다르면 되돌아간 뒤 갈 탭을 `push`해 걷어낸 화면을 앞으로 가기에서도 없앤다. API가 없거나 아래 탭 기록이 없으면, 또는 그 기록이 이전 문서에 있으면 지금처럼 교체한다. 이전 문서로 돌아가면 문서를 다시 열어 떠나며 띄운 토스트가 사라지고 이어서 이동할 수도 없다. 이 결정은 KNK-1566의 일반 제작 승인 뒤 채팅방 아래 화면(채팅 목록)도 Android처럼 새 스토리 상세로 대체한다. |
| 대안 | 원문에 별도 항목으로 구분하지 않음 |
| 이유 | 진입점마다 출발 화면을 표시해 넘기면 공유 링크, 온보딩, 카드처럼 진입 경로가 늘 때마다 표시를 빠뜨릴 수 있고, 새로고침으로 표시가 사라진다. 브라우저가 가진 실제 기록을 읽으면 진입 경로와 관계없이 같은 판정을 한다. 결제 복귀(W-023)에서 `entries()`를 쓰지 않은 이유는 다른 출처를 지나면 그 이전 항목이 보이지 않기 때문이며, 여기서는 아래 탭 기록이 같은 출처라 해당하지 않는다. |
| 영향 | Navigation API가 없는 브라우저는 같은 탭이 두 번 쌓이는 기존 동작을 유지한다. 탭 기록이 이전 문서에 있는 경우(새로고침, 로그인 복귀 뒤)도 같은 탭이 두 번 쌓일 수 있다. 하단 탭끼리의 이동은 계속 교체라 탭 화면의 뒤로가기는 Android와 달리 홈으로 가지 않는다. |
| 근거 | [웹 화면 전환 규칙](3-2-INTERACTION-FLOWS.md#3-2-1-기록과-뒤로가기), [Android 내비게이션과 화면 계약](../ANDROID/3-1-INFORMATION-ARCHITECTURE.md#3-1-1-셸과-진입) |

**W-031. 오버레이 뒤로가기 닫기를 히스토리 레이어 매니저로 통합**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-09 |
| 상태 | Accepted (원문 기록 기준) |
| 배경 | 뒤로가기 가로채기가 `useCloseOnBack`, `usePreventPageLeave`, 게스트 동의 프로바이더에 흩어져 각자 더미 히스토리 항목을 쌓았고, 시트 27종 중 4종만 뒤로가기로 닫혔다. Android는 시스템 뒤로가기로 모든 시트를 닫는다. 같은 클릭에서 드로어 닫기와 다이얼로그 열기가 겹치면 각자의 `history.back()`과 `pushState`가 어긋났고, 제작 퍼널 위에 시트가 열리면 시트의 뒤로가기가 퍼널 가드에도 닿았다. |
| 채택 | 더미 히스토리 항목 방식을 유지하되 전역 레이어 스택 하나가 더미 쌓기와 되감기를 큐로 직렬화하고 캡처 단계 `popstate` 리스너로 맨 위 레이어에만 전달한다. `Drawer`, `Dialog`, `AlertDialog` 래퍼가 기본으로 레이어를 열어 새 시트도 코드 없이 뒤로가기로 닫히고, 뒤로가기에 다른 의미를 주는 시트만 `closeOnBack`을 끈다. 사용자 조작 없이 열린 오버레이는 더미를 쌓지 않는다. 시트 안에서 떠나는 이동은 `leaveLayers`로 더미를 먼저 소비한다. |
| 대안 | 원문에 별도 항목으로 구분하지 않음 |
| 이유 | Navigation API의 traverse 취소는 Chromium 계열에만 있어 Safari, Firefox용 더미 폴백을 함께 가져가야 하므로 보류했다. 시트마다 훅을 붙이는 방식은 누락이 반복됐고 더미 순서를 조율하는 곳이 없었다. Chrome은 조작 없이 쌓인 항목을 뒤로가기에서 건너뛰므로(W-028) 자동으로 열린 오버레이는 더미를 쌓아도 보장되지 않고 앞으로가기에 빈 칸만 남긴다. |
| 영향 | 시트 안에서 `router.push`, `replace`, 전체 이동을 부르는 새 코드는 `leaveLayers`를 거쳐야 돌아올 때 빈 칸이 남지 않는다. 자동으로 열린 시트는 지금처럼 뒤로가기가 화면을 떠난다. 주소로 바로 연 제작 화면은 첫 입력 전까지 이탈 확인이 없다. 되감기 대기 중 사용자가 뒤로가기를 한 번 더 누르면 그 입력은 되감기 결과로 흡수된다. |
| 근거 | [공통 오버레이와 뒤로가기](../2-2-REQUIREMENTS.md#2-2-1-적용-범위), [웹 화면 전환 규칙](3-2-INTERACTION-FLOWS.md#3-2-1-기록과-뒤로가기), [W-028](../../domain/ACCOUNT/CLIENT/WEB/DECISIONS.md#w-028), [W-030](#w-030) |

<a id="w-033-앱-안내-배너는-클라이언트에서-판정하고-패키지를-명시한-intent로-앱을-연다"></a>

**W-033. 앱 안내 배너는 클라이언트에서 판정하고 패키지를 명시한 intent로 앱을 연다**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-12 |
| 상태 | Accepted (원문 기록 기준) |
| 배경 | 모바일 웹 방문자를 Android 앱과 iOS 홈 화면 설치본으로 안내하는 배너가 필요했다. 노출은 브라우저 종류, 홈 화면 설치본 여부, 접속 회차에 따라 달라지고, Android 앱에는 외부 링크를 받는 intent-filter와 App Links가 없었다. |
| 채택 | 노출은 클라이언트에서 UA와 브라우저 저장소로 판정한다. Android 앱 열기는 App Links 대신 `package=app.manyak`를 명시한 `intent://` 링크로 하고, 앱은 전용 스킴 `manyak://manyak.app` intent-filter로 받는다. 어트리뷰션 SDK의 스마트 배너는 쓰지 않는다. |
| 대안 | 원문에 별도 항목으로 구분하지 않음 |
| 이유 | 서버 판정은 홈을 매 요청 동적 렌더로 바꾸면서도 접속 회차와 설치본 여부를 알 수 없어 결국 클라이언트 판정이 섞인다. 패키지를 명시한 intent는 도메인 검증 없이 설치 여부에 따라 앱 또는 플레이스토어로 간다. 받는 쪽을 검증되지 않은 https 필터로 두면 Android 11 이하(minSdk 24)에서 다른 앱의 manyak.app 링크마다 앱 선택창이 떠서, https 링크와 겹치지 않는 전용 스킴을 쓴다. SDK는 비용, 웹과 앱 양쪽 도입, 처리방침 개정이 필요하다. |
| 영향 | 배너는 하이드레이션 뒤 나타난다. 앱이 열렸는지 플레이스토어로 갔는지 웹에서 구분할 수 없어 설치는 Play Console과 referrer로 본다. App Links와 설치 뒤 목적지 복원은 후속(KNK-927, 디퍼드 딥링크)이다. |
| 근거 | [앱 안내 배너](3-3-LAYOUT.md#3-3-1-셸과-공용-요소), [앱 안내 배너 구조](4-4-EXECUTION.md#4-4-1-이동과-레이어-정리), [KNK-1630](https://kimandkang.atlassian.net/browse/KNK-1630) |

<a id="w-041-android-앱-열기가-일어나지-않으면-플레이스토어-주소로-직접-이동"></a>

**W-041. Android 앱 열기가 일어나지 않으면 플레이스토어 주소로 직접 이동**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-20 |
| 상태 | Accepted (원문 기록 기준) |
| 배경 | Android 인스타그램 인앱 브라우저는 앱이 없으면 intent 링크를 받고 아무것도 열지 않는다. 실기기(Galaxy S25, Android 17) logcat에서 액티비티 시작 기록이 없었고, `S.browser_fallback_url`을 넣어도 같았다. 같은 화면에서 `market://`과 `https://play.google.com` 주소는 플레이스토어를 열었다. |
| 채택 | Android 앱 열기를 누른 뒤 0.7초 안에 문서가 한 번도 숨겨지지 않으면 `https://play.google.com/store/apps/details?id=app.manyak`(배너 referrer 포함)로 이동한다. intent 링크에는 `browser_fallback_url`을 넣지 않는다. |
| 대안 | 원문에 별도 항목으로 구분하지 않음 |
| 이유 | 인앱 브라우저가 intent를 버리는지 웹에서 미리 알 수 없어, iOS 인앱 외부 전환 실패 판정과 같은 문서 숨김 감지로 실패를 판단한다. 대기 1.5초는 실패한 사용자가 체감할 만큼 길었고, 카카오톡에서 앱 실행 시도부터 플레이스토어가 뜨기까지 수십 ms였으므로 0.7초로 줄였다. `market://` 대신 https 주소를 쓰는 이유는 플레이스토어가 없는 기기에서도 웹 페이지로 열리기 때문이다. |
| 영향 | 인스타그램에서 앱이 없으면 0.7초 뒤 플레이스토어가 열린다. 앱이 설치된 느린 기기에서 0.7초 안에 앱이 뜨지 않으면 플레이스토어가 함께 열릴 수 있다. Chrome과 카카오톡은 기존처럼 플레이스토어를 바로 열고 두 번 열지 않는다. |
| 근거 | [앱 안내 배너](3-3-LAYOUT.md#3-3-1-셸과-공용-요소), [앱 안내 배너 구조](4-4-EXECUTION.md#4-4-1-이동과-레이어-정리), [KNK-1716](https://kimandkang.atlassian.net/browse/KNK-1716) |
| 보완 범위 | [W-033](#w-033)의 "패키지를 명시한 intent는 설치 여부에 따라 앱 또는 플레이스토어로 간다"를 보완한다. intent 링크로 앱을 여는 방식은 유지한다. |
