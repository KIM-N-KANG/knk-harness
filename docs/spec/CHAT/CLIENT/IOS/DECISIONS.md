# DECISIONS.md

현재 적용 기준은 각 명세에 두고 결정 당시의 이유와 대체 관계는 이 문서에 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다. 기존 ID, 날짜, 당시 상태와 근거를 유지한다.
- 상태와 구현 설명은 원본의 기록 시점을 기준으로 해석한다. 현재 적용 여부나 배포 완료를 과거 기록만으로 단정하지 않는다.
- 결정이 바뀌면 새 ID로 기록하고 대체하는 결정과 적용 범위를 명시한다.
- 원문에 구분되지 않은 배경, 대안과 영향은 추측해서 보충하지 않는다.
- 이 세트의 ID는 I-090부터 I-109까지 쓴다. 사용자가 확인하기 전의 작성 중 결정은 상태를 Proposed로 둔다.

**I-090. SSE는 URLSession.bytes로 직접 해석**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | 시간 제한과 재연결 차례는 [I-092](#i-092), 응답 판정은 [I-100](#i-100) |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | Android는 OkHttp의 SSE 모듈로 채팅 응답을 받는다. Apple은 SSE 전용 API를 제공하지 않는다. 서드파티 mattt/EventSource는 Swift 6 이상을 요구하고 마지막으로 확인한 릴리스는 1.1.1이며 2026년 릴리스 여부는 확인하지 못했다(2026-11-26 웹 확인). |
| 채택 | SSE는 `URLSession.bytes`로 받아 앱이 줄과 이벤트를 직접 해석한다. 서드파티 SSE 라이브러리를 쓰지 않는다. |
| 대안 | mattt/EventSource(서드파티) |
| 이유 | 대화에서 별도 이유를 남기지 않았다. |
| 영향 | 줄 나누기, 필드와 이벤트 경계, 시간 제한과 실패 변환을 앱이 구현하고 단위 테스트로 확인한다([4-4-1](4-4-EXECUTION.md#4-4-1-요청과-sse-해석), [4-4-2](4-4-EXECUTION.md#4-4-2-sse-실패-변환)). 전송 계층이 첫 조각을 붙잡아 두지 않는지는 실기기로 확인한다. |
| 근거 | [KNK-2154](https://kimandkang.atlassian.net/browse/KNK-2154), Android 현황과 iOS 대응 정리(2026-11-26, 저장소 미포함) 2절, 7절 22번 |

<a id="i-091-백그라운드에서-스트림을-끊고-복귀-때-서버-상태로-복구"></a>

**I-091. 백그라운드에서 스트림을 끊고 복귀 때 서버 상태로 복구**

|---|---|

| 상태 | Accepted |
| 관계 | 복귀 절차는 [I-093](#i-093). 제작 완성 요청의 재전송은 STORY의 iOS 결정 기록 |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | Android는 백그라운드 실행 유지 없이 앱이 백그라운드로 가면 받던 생성의 수신을 끊고 돌아오면 상세로 이어받는다([A-078](../ANDROID/DECISIONS.md#a-078)). iOS는 앱이 백그라운드로 가면 곧 실행이 멈춘다. 실행 유지 수단으로 BackgroundTasks 프레임워크가 후보였다. 서버는 연결이 끊겨도 생성과 저장을 계속하고 재연결은 생성과 과금을 다시 시작하지 않는다. |

| 대안 | BackgroundTasks 프레임워크로 백그라운드 실행 유지 |
| 이유 | 대화에서 별도 이유를 남기지 않았다. |
| 영향 | 잠깐 다른 앱을 다녀와도 받던 응답을 처음부터 다시 받는다. 백그라운드에서 끝난 생성은 돌아온 뒤에 확정 턴으로 보인다. 공통 [2-2-3](../2-2-REQUIREMENTS.md#2-2-3-생성-실패와-복구)에 iOS 적용 범위를 더했다. |
| 근거 | [KNK-2154](https://kimandkang.atlassian.net/browse/KNK-2154), Android 현황과 iOS 대응 정리 1-7절, 7절 22번 |

<a id="i-092"></a>
<a id="i-092-sse-시간-제한과-재연결-차례"></a>

**I-092. SSE 시간 제한과 재연결 차례**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | [I-090](#i-090)의 구현 조건 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | 공통 실행은 연결 횟수와 대기 간격을 플랫폼 문서에 맡긴다. 웹과 Android 문서는 첫 재연결 포함 4회와 1초, 2초, 4초 간격을 쓴다. Android 코드의 SSE 연결은 읽기 간격 60초이고 전체 호출 제한이 없다. 서버는 heartbeat를 보내지 않고 AI 이벤트 간격 60초를 넘기면 `AI_STREAM_FAILED`로 끝내며 생성 마감은 접수부터 120초다. 확정용 상세 조회가 실패했을 때의 처리는 공통 문서가 이어받지 못한 결과에만 정한다. |
| 채택 | 새 바이트 간격 60초를 넘으면 읽기 시간 초과, 연결 전체 시간 상한 없음. 재연결은 첫 재연결 포함 최대 4회로 첫 재연결은 즉시, 이후 1초, 2초, 4초를 기다린다. 확정용 상세 조회 실패도 같은 간격으로 다시 조회하고, 소진하면 결과 불명은 실패 안내, 완료와 명시적 실패는 방 오류 상태와 다시 시도로 바꾼다. |
| 대안 | 읽기 간격 상한 없음: heartbeat가 없어 멈춘 연결을 알아차리지 못한다<br>확정용 상세 실패를 실패 안내로 처리: 서버가 저장한 완료 턴을 실패로 안내한다 |
| 이유 | 세 플랫폼이 같은 재연결 한도를 써야 서버 수신 부하와 실패 지표를 같은 기준으로 본다. 방 오류 상태의 다시 시도는 재진입과 같은 상세 조회라 저장 결과를 잘못 확정하지 않는다. |
| 영향 | 재연결 간격은 주입한 시계로 테스트한다. 서버 상한이나 heartbeat가 바뀌면 이 값을 다시 정한다. |
| 근거 | [공통 4-4-2](../4-4-EXECUTION.md#4-4-2-이어받기와-종료), [BACKEND 5-3-5](../../BACKEND/5-3-ERROR-HANDLING.md#5-3-5-재시도와-시간-한도), Android 현황과 iOS 대응 정리 2절 |

<a id="i-093"></a>
<a id="i-093-복귀는-보관한-생성-단계에서-새-차례-예산으로-다시-시작"></a>

**I-093. 복귀는 보관한 생성 단계에서 새 차례 예산으로 다시 시작**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | [I-091](#i-091)의 절차 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | Android는 수신 중 여부와 중단 여부를 따로 들고 복귀 때 상세를 먼저 읽어 진행 중이면 어떤 생성이든 이어받는다. 서버 계약은 `started.generationId`를 받은 클라이언트가 같은 화면에서 바로 재연결하도록 정하고, 이탈 중 끝난 재생성의 성공과 실패는 생성 ID로 보관 스트림을 다시 받아야 구분된다. iOS는 앱 전환마다 스트림이 끊긴다. |
| 채택 | 채팅방 Store는 생성 단계 하나(없음, 시작, 수신, 이어받기, 확인, 중단)를 가진다. 백그라운드에서 판정용 상세 조회를 포함한 생성 작업 전체를 끊고 생성 종류, 요청 스냅샷, 대신하는 턴, 전송 시점 턴 수, 생성 ID와 확인 중이던 결과를 보관한다. 복귀 때 확인 중이던 결과가 있으면 같은 결과로 다시 확인하고, 없으면 새 차례 예산으로 이어받기를 시작하며 아는 생성 ID로 먼저 재연결한다. |
| 대안 | 복귀 때 상세부터 읽기: 이탈 중 끝난 재생성의 성공과 실패를 구분하지 못한다<br>판정용 상세 조회는 끊지 않음: 실행이 멈춘 사이 실패한 조회가 실패 안내나 거절 판정을 바꾼다 |
| 이유 | 같은 보관 값에서 다시 시작하므로 복귀가 여러 번 반복돼도 같은 결과로 끝나고, 거절 판정의 409 무음 처리가 결과 불명의 실패 안내로 바뀌지 않는다. |
| 영향 | 복귀마다 보관 스트림을 처음부터 다시 받아 진행 조각이 다시 그려진다. 서버 수신 연결 상한을 넘으면 503으로 다음 차례가 된다. 생성 ID를 받기 전에 끊긴 요청이 서버에 늦게 도착해 저장되면 복귀 판정 뒤의 상세 조회에서 나타난다. |
| 근거 | [BACKEND 4-2-6](../../BACKEND/4-2-CONTRACT.md#4-2-6-이어쓰기), [BACKEND 4-2-13](../../BACKEND/4-2-CONTRACT.md#4-2-13-생성-스트림-재연결), [4-4-4](4-4-EXECUTION.md#4-4-4-백그라운드와-복귀) |

<a id="i-094-채팅방-헤더는-화면이-그리는-겹침-헤더"></a>

**I-094. 채팅방 헤더는 화면이 그리는 겹침 헤더**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | 공통 UI IOS의 하위 화면 헤더 규칙에서 채팅방 헤더를 화면에 맡긴 부분. 투어 중 가장자리 밀기 차단은 공통 UI IOS [I-052](../../../../ui/IOS/DECISIONS.md#i-052) 이탈 확인 규칙의 대상 |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | 공통 화면 계약은 헤더를 본문 빈 곳 탭으로만 숨기고, 본문 높이를 접지 않으며 숨긴 헤더를 초점에서 뺀다. 시스템 내비게이션 바의 표시를 바꾸면 안전 영역이 바뀌어 대화 위치가 움직인다. 공통 투어는 뒤로가기를 방 이탈 없이 건너뛰기로 정하지만 iOS에는 시스템 뒤로가기가 없고 가장자리 밀기는 화면 스택을 바로 줄인다. |
| 채택 | 채팅방은 시스템 내비게이션 바를 숨기고 뒤로, 제목, 모델과 더보기를 담은 겹침 헤더를 그린다. 뒤로 아이콘은 Asset Catalog의 원본 SVG를 쓴다. 가장자리 밀기 뒤로가기는 유지하되 투어가 열린 동안에는 막는다. |
| 대안 | 시스템 내비게이션 바의 표시 전환 |
| 이유 | 헤더 전환에 대화 높이와 읽던 위치가 흔들리지 않는다. 투어 중 방을 떠나면 열람 기록만 남아 투어를 다시 볼 수 없다. |
| 영향 | 채팅방 뒤로 버튼의 모양은 다른 하위 화면의 시스템 뒤로 버튼과 다르다. 내비게이션 바를 숨긴 화면에서 가장자리 밀기가 동작하는지 구현에서 확인한다. 공통 [2-2-6](../2-2-REQUIREMENTS.md#2-2-6-처음-사용-안내)에 iOS 적용 범위를 더했다. |
| 근거 | [공통 3-3-1](../3-3-LAYOUT.md#3-3-1-목록과-채팅방), [공통 UI IOS 3-3-1](../../../../ui/IOS/3-3-LAYOUT.md#3-3-1-셸-헤더와-실행-화면) |

<a id="i-095-삭제-진행-표시는-알림창-밖에-둠"></a>

**I-095. 삭제 진행 표시는 알림창 밖에 둠**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | 공통 UI IOS [I-047](../../../../ui/IOS/DECISIONS.md#i-047)의 시스템 알림창 사용 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | 공통 배치는 삭제 중 확인 창 안에 문구 공간을 유지한 스피너를 두고 두 버튼과 배경 닫기를 잠근다. 공통 UI IOS는 확인 다이얼로그를 시스템 알림창으로 바꾸고, 시스템 알림창은 버튼을 누르면 닫힌다. |
| 채택 | 삭제 확정과 함께 알림창을 닫는다. 채팅방은 화면 가운데 시스템 진행 표시(접근성 이름 "삭제 중")와 방 전체 조작 잠금, 목록은 해당 카드의 진행 표시와 카드 조작 잠금을 둔다. 실패하면 잠금을 풀고 토스트를 띄운다. |
| 대안 | 자체 확인 덮개로 공통 배치를 그대로 따름: 다른 확인 창과 모양과 역할 처리가 달라진다 |
| 이유 | 확인 창 모양을 앱 안에서 하나로 두면서 공통 계약의 요청 중 잠금과 중복 요청 금지를 지킨다. |
| 영향 | 삭제 실패 뒤 다시 지우려면 메뉴나 옵션부터 다시 연다. 300ms 안에 끝나면 진행 표시가 보이지 않는다. |
| 근거 | [공통 3-3-3](../3-3-LAYOUT.md#3-3-3-설정과-메뉴), [공통 UI IOS 3-3-3](../../../../ui/IOS/3-3-LAYOUT.md#3-3-3-시트-알림창과-덮개) |

<a id="i-096-공유-링크를-ios-시스템-공유-시트로-전달"></a>

**I-096. 공유 링크를 iOS 시스템 공유 시트로 전달**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | Android [A-043](../ANDROID/DECISIONS.md#a-043)과 같은 전달 방식 |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | 공통 요구는 플랫폼별 공유 수단을 적용 범위로 나눈다. 웹은 링크 복사와 성공 안내, Android는 시스템 공유 시트다. 공유본 열람은 웹 화면이다. |
| 채택 | 발급한 웹 링크를 메뉴가 닫힌 뒤 iOS 시스템 공유 시트로 전달한다. 복사 성공 토스트는 두지 않고 실패 안내와 진행 표시는 공통 계약을 따른다. 링크 앞에는 Android와 같은 안내 문장을 둔다. 턴이 없는 방은 이야기 소개 문장, 턴이 있는 방은 턴 수를 담은 문장이며 문구는 [3-3-2 시트, 알림창과 뷰어](3-3-LAYOUT.md#3-3-2-시트-알림창과-뷰어)에 둔다. |
| 대안 | 웹처럼 클립보드 복사와 성공 토스트 |
| 이유 | 앱은 받는 쪽이 웹인 링크를 전달만 하면 되고, 공유 시트가 목적지 앱까지 한 번에 닿는다. 공유 시트에도 복사 동작이 있다. |
| 영향 | 공통 [2-2-1](../2-2-REQUIREMENTS.md#2-2-1-적용-범위와-목록)에 iOS 적용 범위를 더했다. 안내 문장은 Android 코드(조사 커밋 `37ae68bc`)의 문자열을 그대로 옮겼다. 하네스의 공통과 Android 문서에는 이 문장이 없다. 별도 티켓으로 기준 문서 정리 |
| 근거 | [A-043](../ANDROID/DECISIONS.md#a-043), [공통 2-2-7](../2-2-REQUIREMENTS.md#2-2-7-공유와-피드백) |

<a id="i-097-이미지-안내는-설정-시트-내용-위-덮개"></a>

**I-097. 이미지 안내는 설정 시트 내용 위 덮개**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | Android [A-050](../ANDROID/DECISIONS.md#a-050)의 시트 위 별도 창과 다른 배치 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | 공통 안내는 설정 시트가 자리 잡은 뒤 화면 전체를 딤으로 덮고 켜기, 확인, 딤 또는 뒤로가기로 안내만 닫으며 시트를 닫으면 안내도 끝낸다. 시스템 시트의 내용은 시트 밖에 그릴 수 없다. |
| 채택 | 시트가 다 올라온 뒤 시트 내용 위에 딤과 카드를 그리고 실시간 이미지 행만 뚫는다. 안내가 열린 동안 시트의 끌어내리기와 바깥 탭 닫기를 막고 안내가 끝나면 푼다. |
| 대안 | 앱 창 위 별도 덮개 층으로 화면 전체를 덮음: 시스템 시트와 좌표, 초점과 VoiceOver 모달 처리를 따로 맞춰야 한다 |
| 이유 | 같은 화면 계층에서 행 좌표를 그대로 쓰고, 안내를 닫으려던 탭이 시트까지 닫지 않는다. |
| 영향 | 시트 밖 영역은 시스템 시트의 배경 처리라 딤 색이 시트 안과 다를 수 있다. 안내 중 바깥 탭은 아무 일도 하지 않는다. |
| 근거 | [공통 2-2-6](../2-2-REQUIREMENTS.md#2-2-6-처음-사용-안내), [공통 3-3-5](../3-3-LAYOUT.md#3-3-5-안내와-공유본) |

|---|---|

| 상태 | Proposed |
| 관계 | IOS 기반 [I-008](../../../../platform/CLIENT/IOS/DECISIONS.md#i-008)의 기기 귀속 suite |

<a id="i-100"></a>
<a id="i-100-시작-거절은-상태와-상세로-판정"></a>

**I-100. 시작 거절은 상태와 상세로 판정**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | Android [A-078](../ANDROID/DECISIONS.md#a-078)의 409 판정과 같은 기준 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | 공통 연동은 409의 `CHAT_TURN_IN_PROGRESS`, `CHAT_TURN_STALE`, `CHAT_ENDED` 결과를 따로 적지만 세 결과 모두 입력을 되돌리고 상세를 다시 읽어 진행 중 생성이나 최신 턴을 보인다. 스트림 시작 후 `error`는 코드와 관계없이 상세 확인 뒤 기본 실패 안내다. IOS 기반의 기본 변환은 오류 본문의 `code`를 `Server`에 싣는다. |
| 채택 | 채팅방은 시작 거절을 상태로만 나눈다. 402는 이프 부족 시트, 409는 상세 판정과 무음, 그 밖은 상세 판정과 실패 안내다. `error` 이벤트의 `code`와 `message`는 분기와 문구에 쓰지 않는다. 2xx인데 `text/event-stream`이 아닌 응답은 `Serialization`으로 시작 거절이다. |
| 대안 | 409를 `code`별로 분기: 세 코드의 사용자 결과가 같아 분기만 늘어난다 |
| 이유 | 진행 중 생성의 유무는 상세가 기준이라 `code`를 읽지 않아도 같은 결과가 나오고, 409에 새 코드가 생겨도 상세로 판단한다. |
| 영향 | 409에 다른 사용자 결과가 필요해지면 그때 `code` 분기를 더한다. 공통 연동의 `Accept: text/event-stream`을 그대로 보내며 Android 코드는 `application/json`도 함께 보낸다. 별도 티켓으로 기준 문서 정리 |
| 근거 | [공통 4-1-3](../4-1-CONTRACT.md#4-1-3-상세와-오류의-해석), [A-078](../ANDROID/DECISIONS.md#a-078) |

**I-101. 결과 불명으로 실패한 이어쓰기의 입력을 입력칸에 복구**
