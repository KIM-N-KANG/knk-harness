# OBSERVABILITY AI

운영 관측 자료를 감시해 장애를 찾고 원인과 제안 조치를 슬랙으로 보고하는 진단 에이전트의 AI 세트다. 1 배경부터 5 계약까지만 둔다.

<br>

### 1. 문서의 역할

| 문서 | 내용 |
|---|---|
| [1 배경](1-BACKGROUND.md) | 관측 도메인, 현재 문제, 목적과 범위, 주체, 용어 |
| [2-1 유저 스토리](2-1-USER-STORY.md) | 운영자가 보고와 슬랙 대화에 기대하는 품질 |
| [2-2 운영 요구사항](2-2-OPERATION-REQUIREMENTS.md) | 품질, 시간, 비용 목표와 운영 제약 |
| [3 태스크 정의](3-TASK-DEFINITION.md) | 에이전트가 풀 문제, 진단과 대화의 입력과 출력 |
| [4-1 인지 구조](4-1-DESIGN-COGNITIVE-ARCHITECTURE.md) | 에이전트 루프, 진단 전략, 조회 도구, 모델과 코드의 책임, 종료 조건 |
| [4-2 소프트웨어 설계](4-2-DESIGN-SOFTWARE-ARCHITECTURE.md) | 시스템 경계, 실행 환경, 요청 처리 흐름, 감시 규칙, 상태, 평가 방식 |
| [5 계약](5-CONTRACT.md) | 설정과 비밀값, 자료 원천, 서비스 지도, 진단 요청과 진단 보고 필드, 실행 폴더, 슬랙 메시지, 평가 사례 |
| [DECISIONS](DECISIONS.md) | 결정의 배경, 채택, 대안, 영향 |

<br>

### 2. 작업별 참조

| 하려는 일 | 먼저 볼 곳 | 함께 볼 곳 |
|---|---|---|
| 에이전트가 무엇을 하는지 알기 | 1 배경 | 3 태스크 정의, 4-1 인지 구조 |
| 감시 규칙 변경 | 4-2 소프트웨어 설계 | 2-2 운영 요구사항 |
| 진단 전략 변경 | 4-1 인지 구조 | 2-2 운영 요구사항 |
| 조회 도구나 도구 권한 변경 | 4-1 인지 구조 | 2-2 운영 요구사항, 5 계약 |
| 보고 필드나 슬랙 메시지 변경 | 5 계약 | 3 태스크 정의 |
| 설정 변경이나 다른 서비스 연결 | 5 계약 | 구현 저장소의 예시 설정 |
| 구현과 운영 배포 | 4-2 소프트웨어 설계 | 5 계약 |
| 이미 내린 결정인지 확인 | DECISIONS | 해당 결정에서 말한 절 |

### 4. 명세와 코드의 대응

코드 경로는 구현 저장소의 `src/manyak_diagnosis/` 기준이다.

| 범위 | 코드 위치 | 관련 명세 |
|---|---|---|
| 설정과 비밀값 읽기 | `config.py`, `app.py` | 5-2 |
| 감시 조회, 신호 판정, 이상 후보, 하루 비용 | `access.py`, `detection.py` | 4-2-4, 5-3, 5-5 |
| 진단 턴과 대화 턴, 자체 도구 | `runner.py` | 4-1-2, 4-1-4 |
| 공식 MCP 등록과 도구 범위 제한 | `tools.py` | 4-1-2, 4-1-3, 5-1 |
| 보고 검사, 실행 실패, 비용 계산 | `reports.py` | 4-1-3, 5-7, 5-8 |
| 프롬프트 원문과 조립 | `system.txt`, `candidate.txt`, `mention.txt`, `conversation.txt`, `violation.txt`, `prompts.py` | 3-2, 3-3, 4-1-2 |
| 원인 영역별 절차 | `plugin/skills/` 아래 절차마다 `SKILL.md` | 4-1-2 |
| 코드 사본 | `repositories.py` | 3-2 |
| 슬랙 연결, 진단 대기열, 세션 | `slack.py` | 4-2-3, 5-9 |
| 실행 폴더 기록 | `storage.py` | 5-8 |
| 재현 평가와 재생 모드 | `evaluate.py`, `replay.py` | 4-2-6, 5-10 |
