# DECISIONS.md

현재 적용 기준은 각 명세에 두고 결정 당시의 이유와 대체 관계는 이 문서에 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다. 기존 ID, 날짜, 당시 상태와 근거를 유지한다.
- 상태와 구현 설명은 원본의 기록 시점을 기준으로 해석한다. 현재 적용 여부나 배포 완료를 과거 기록만으로 단정하지 않는다.
- 결정이 바뀌면 새 ID로 기록하고 대체하는 결정과 적용 범위를 명시한다.
- 원문에 구분되지 않은 배경, 대안과 영향은 추측해서 보충하지 않는다.
- 이 세트의 iOS 결정 ID는 I-140부터 I-159까지 쓴다. 사용자가 확인하기 전의 작성 중 결정은 상태를 Proposed로 둔다.

**I-140. iOS 푸시 계약은 서버 선행 변경으로 둠**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | [I-141](#i-141), [I-142](#i-142) |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | dev OpenAPI(2026-11-26 조회)의 푸시 토큰 등록 `platform`은 `ANDROID`, `WEB`만 받는다. 서버는 Android에 데이터만 있는 메시지를 보내고 앱이 알림을 만든다. iOS는 앱이 꺼져 있을 때 데이터만 있는 메시지로 앱 코드를 확실히 실행할 수 없어 서버가 표시할 내용을 실어 보내야 한다. |
| 채택 | 토큰 등록 `platform`에 iOS를 추가하는 것과 iOS용 표시형 알림(notification 페이로드) 전송은 NOTIFICATION BACKEND의 선행 변경이다. 클라이언트 문서는 값 이름, 필드와 페이로드 형식을 만들지 않고 미정(서버 선행 변경 필요)으로 표시하며 앱이 요구하는 정보만 정리한다. |
| 대안 | 원문에 별도 항목으로 구분하지 않음 |
| 이유 | 대화에서 별도 이유를 남기지 않았다. |
| 영향 | 서버 변경이 배포되기 전 iOS 빌드는 토큰을 등록하지 않아 푸시를 받지 않는다. iOS 첫 출시는 이 서버 변경을 선행 조건으로 둔다([I-149](#i-149)). 앱의 요구는 [4-1-1 서버 선행 변경](4-1-CONTRACT.md#4-1-1-서버-선행-변경)에 둔다. |
| 근거 | [KNK-2154](https://kimandkang.atlassian.net/browse/KNK-2154), Android 현황과 iOS 대응 정리(2026-11-26, 저장소 미포함) 2절 푸시 항목과 7절 3번, [토큰 등록 계약](../../BACKEND/4-2-CONTRACT.md#4-2-2-토큰-등록) |

**I-142. 표시 전 수신자 확인을 보장하지 않음**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | 구현 세부는 [I-144](#i-144), [I-145](#i-145) |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | Android는 표시 전에 `recipientId`가 현재 회원과 같은지 최대 5초 확인하고 확인하지 못하면 버린다. iOS는 앱이 백그라운드이거나 종료된 동안 시스템이 앱 코드 없이 알림을 표시하며 표시 전 확인은 Notification Service Extension(알림 표시 직전에 내용을 고치는 확장)으로만 일부 대응된다. |
| 채택 | 표시 전 차단을 보장하지 않으며 Notification Service Extension을 두지 않는다. 로그아웃 시 푸시 토큰 삭제와, 알림을 눌렀을 때 수신자 ID가 현재 회원과 다르면 홈으로 보내는 규칙으로 대응한다. 앱이 포그라운드일 때는 앱이 표시 여부를 판단하므로 수신자 불일치 알림을 표시하지 않는다. |
| 대안 | Notification Service Extension으로 표시 직전 수신자 확인 |
| 이유 | 대화에서 별도 이유를 남기지 않았다. |
| 영향 | 토큰 삭제가 실패하거나 늦으면 이전 회원의 알림이 백그라운드와 종료 상태에서 표시될 수 있다. 이 한계를 수신자 검증 완료로 표시하지 않는다. 앱 확장 타깃이 없다. |
| 근거 | [KNK-2154](https://kimandkang.atlassian.net/browse/KNK-2154), Android 현황과 iOS 대응 정리 2절 푸시 항목과 7절 5번 |

<a id="i-143-알림-권한은-미결정일-때만-회원-화면-첫-표시에-요청"></a>

**I-143. 알림 권한은 미결정일 때만 회원 화면 첫 표시에 요청**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | 없음 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | Android는 필수 동의를 마친 회원 화면에서 설치당 한 번 권한을 요청하고 질문 여부를 기기 저장소에 기록하며, 초대 안내와 광고 재질문은 권한 응답 뒤에 연다. 알림 설정의 알림 켜기는 시스템이 더 묻지 않으면 앱 알림 설정을 연다. iOS 시스템 요청 창은 권한이 미결정일 때만 뜨고 한 번 답하면 앱이 다시 띄울 수 없다. |
| 채택 | 실행마다 필수 동의를 마친 회원 화면이 처음 나타날 때 권한이 미결정이면 알림 표시와 소리를 함께 요청한다. 질문 여부는 시스템 권한 상태로 판정하고 앱이 따로 저장하지 않는다. 알림 켜기는 미결정이면 요청 창을, 거부면 시스템 설정의 이 앱 알림 화면을 연다. 임시 허용(묻지 않고 알림 센터에만 조용히 전달하는 방식)은 쓰지 않는다. |
| 대안 | 첫 알림이 필요한 화면에서 요청<br>임시 허용으로 시작 |
| 이유 | 요청 시점과 안내 순서를 Android 앱과 같게 두어 초대 안내와 광고 재질문 규칙을 그대로 쓴다. 시스템이 질문 여부를 기억하므로 앱 기록과 어긋나지 않는다. 임시 허용은 광고 재질문의 기기 알림 허용 판정과 꺼짐 안내를 다시 정해야 한다. |
| 영향 | 배지 권한은 요청하지 않는다. ([I-148](#i-148)) |

<a id="i-144-앱이-앞에-있을-때는-확인된-현재-회원의-알림만-표시"></a>

**I-144. 앱이 앞에 있을 때는 확인된 현재 회원의 알림만 표시**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | [I-142](#i-142)의 구현 조건 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | iOS는 앱이 앞에 있을 때 받은 알림의 표시 여부를 앱이 정한다. Android는 앞과 뒤 모두 시스템 알림을 표시하고 회원 확인 전 수신은 최대 5초 기다리며, 웹은 앞에 있을 때 토스트로 보인다. 검수 결과 중복 억제와 안 읽은 수 갱신도 앱이 앞에 있을 때만 앱 코드가 개입할 수 있다. |
| 채택 | 앱이 앞에 있으면 현재 회원 공개 식별자가 확인되고 `recipientId`가 같을 때만 시스템 배너와 알림 목록으로 표시한다. 회원 확인 전, 다른 회원과 수신자 없음은 기다리지 않고 표시하지 않는다. 일치하면 안 읽은 수를 다시 읽는다. 검수 결과 중복 억제는 앱이 앞에 있을 때만 적용한다. |
| 대안 | 앞에서는 토스트로 표시<br>회원 확인을 기다린 뒤 표시 |
| 이유 | 백그라운드 알림과 같은 모양이라 누른 뒤의 흐름이 하나다. 앞에서 표시하지 않은 알림도 알림함에 남아 기다릴 이유가 작다. |
| 영향 | 백그라운드와 종료 상태에서는 검수 결과를 기다리던 화면을 본 직후에도 같은 결과 알림이 보일 수 있다. Android의 채널별 중요도 차이(서비스 높음, 광고 보통)는 iOS에 없다. |

<a id="i-145-세션-종료에서-기기-토큰과-알림-센터를-정리"></a>

**I-145. 세션 종료에서 기기 토큰과 알림 센터를 정리**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | [I-142](#i-142)의 구현 조건 |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | I-142는 백그라운드 알림의 계정 격리를 토큰 삭제에 맡긴다. Android 코드(조사 커밋 `ccc93f77`)는 사용자 로그아웃과 탈퇴에서만 3초 안에 서버 토큰 삭제를 시도하고 Firebase SDK의 토큰 삭제는 부르지 않으며, 모든 종료의 정리에서 표시 중 알림을 지운다. 재발급 실패나 정지로 끝나는 세션은 서버 인증을 쓸 수 없어 서버 삭제가 불가능하다. |
| 채택 | 사용자 로그아웃은 쓰기 차단 전에 3초 안에서 서버 삭제를 시도한다. 탈퇴는 서버가 탈퇴 처리에서 회원의 토큰을 모두 지우므로 서버 삭제를 시도하지 않는다. 모든 종료의 회원 저장소 정리에서 Firebase Messaging의 기기 토큰을 3초 안에서 삭제하고 알림 센터의 이 앱 알림을 모두 지운다. 기기 토큰 삭제가 실패하면 기기 귀속 표시를 남겨 다음 실행이나 포그라운드 복귀에서 비로그인이면 다시 삭제한다. 실행과 포그라운드 복귀 때 알림 센터에 남은 알림 중 수신자가 현재 회원이 아닌 알림을 지운다. 어느 실패도 로그아웃을 막지 않는다. |
| 대안 | 서버 삭제만 시도<br>Android 코드처럼 탈퇴에서도 서버 삭제를 시도: 하네스 [ACCOUNT iOS 중앙 로그아웃](../../../ACCOUNT/CLIENT/IOS/4-4-EXECUTION.md#4-4-3-중앙-로그아웃과-복구)과 Android 문서는 사용자 로그아웃에서만 시도하고 탈퇴한 회원의 토큰은 서버가 지운다 |
| 이유 | 기기 토큰을 지우면 서버 삭제가 실패하거나 시도할 수 없어도 이전 토큰으로 보낸 알림이 기기에 도착하지 않는다. 남은 알림 정리는 표시 전 확인이 없는 대신 이전 회원의 알림이 알림 센터에 오래 남지 않게 한다. |
| 영향 | 다음 로그인은 새 FCM 토큰을 받아 등록한다. 공통 요구는 로그아웃, 탈퇴와 세션 종료에서 토큰 삭제 시도를 정하며 iOS는 기기 토큰 삭제로 모든 종료를 맡는다. Android 코드는 사용자 로그아웃과 탈퇴에서 서버 삭제를 시도하고 하네스 Android 문서는 사용자 로그아웃에서만 시도한다. 별도 티켓으로 기준 문서 정리 |
| 근거 | [푸시와 계정 격리](../2-2-REQUIREMENTS.md#2-2-4-푸시와-계정-격리), [Android 코드 기준](https://github.com/KIM-N-KANG/manyak-android/tree/ccc93f77289fd960def116184c2c86c552e4124e/feature/notification/src/main/java/app/manyak/notification) |

<a id="i-146-apns-기기-토큰은-앱-타깃이-직접-넘김"></a>

**I-146. APNs 기기 토큰은 앱 타깃이 직접 넘김**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | [I-141](#i-141) |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | Firebase Messaging iOS SDK는 기본 설정에서 앱 위임 메서드를 가로채(method swizzling) APNs 기기 토큰을 스스로 받는다. 서드파티 SDK 타입은 소유 타깃 밖으로 공개하지 않는다([IOS 기반 모듈과 허용 의존](../../../../platform/CLIENT/IOS/1-COMPONENT-ARCHITECTURE.md#1-2-모듈과-허용-의존)). |
| 채택 | 가로채기를 끄고 앱 타깃이 APNs 등록 결과로 받은 기기 토큰을 `ManyakNotification`의 함수로 넘긴다. Firebase Messaging은 `ManyakNotification`만 호출한다. 알림 센터 위임 객체도 `ManyakNotification`이 구현하고 앱 타깃이 실행 완료 전에 지정한다. |
| 대안 | SDK 기본 가로채기 사용 |
| 이유 | 토큰 전달 경로가 코드에 드러나 등록 실패를 추적할 수 있고 Firebase가 앱 타깃의 위임 메서드를 바꾸지 않는다. |
| 영향 | 가로채기 끔 설정을 앱 `Info.plist`에 둔다. |

**I-147. 푸시 탭 목적지는 deepLink만 해석**

| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | Android [A-045](../ANDROID/DECISIONS.md#a-045)의 `type` 매핑 대체를 iOS에 두지 않음 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | Android는 업데이트 전에 만든 알림과 deepLink 없는 프로모션을 위해 `type`과 식별자 매핑을 남긴다. 현재 서버 계약은 이동 대상이 없는 프로모션을 빼면 모든 시나리오에 deepLink를 싣는다. iOS는 새 앱이라 이전 알림이 없다. |
| 채택 | 푸시 탭은 deepLink만 해석한다. 없거나 허용 URL로 해석되지 않으면 홈이며 `type` 매핑으로 대신 정하지 않는다. |
| 대안 | Android와 같은 `type` 매핑 대체 |
| 이유 | 대체 매핑을 쓸 알림이 iOS에는 없다. 해석 실패를 `type`으로 되돌리면 서버가 목적지를 바꾼 뒤 이전 매핑으로 가게 된다. |
| 영향 | 서버가 deepLink 없는 새 시나리오를 추가하면 iOS는 홈으로 연다. 알림함 카드의 공지 ID와 스토리 ID 대체는 그대로 둔다. |
| 근거 | [푸시 데이터](../../BACKEND/4-2-CONTRACT.md#4-2-10-푸시-데이터) |

**I-148. 앱 아이콘 배지 숫자를 첫 출시에서 표시하지 않음**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | [I-143](#i-143)의 권한 요청 범위 |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | 읽지 않은 수를 정확히 보이려면 서버가 푸시 페이로드에 배지 값을 실어야 하는데 그 계약이 없다. |
| 채택 | 첫 출시에서 앱 아이콘 배지 숫자를 표시하지 않는다. 알림 권한 요청에서 배지를 빼고 앱이 배지 값을 쓰지 않는다. |
| 대안 | 읽지 않은 알림 수를 표시: NOTIFICATION BACKEND가 페이로드에 배지 값을 더해야 한다 |
| 이유 | 서버 계약 없이 앱이 세는 숫자는 다른 기기와 웹의 읽음과 어긋난다. |
| 영향 | 세션 종료의 알림 정리는 배지를 다루지 않는다. 배지를 넣으려면 서버 계약과 함께 새 결정으로 다룬다. |

**I-149. iOS 푸시의 서버 변경을 첫 출시의 선행 조건으로 둠**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | [I-140](#i-140)의 출시 조건 |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | I-140은 토큰 등록 `platform`의 iOS 값과 표시형 알림을 서버 선행 변경으로 두었다. 서버 변경이 첫 출시까지 준비되지 않을 때 푸시 없이 출시할지는 정하지 않았다. |
| 채택 | iOS 첫 출시는 이 서버 변경의 운영 배포 뒤에 한다. 푸시 권한 요청과 토큰 등록을 뺀 출시 분기를 명세에 두지 않는다. |

| 이유 | STORY 완성 중 카드의 "스토리가 완성되면 알림으로 알려드려요" 같은 문구를 그대로 쓸 수 있고 푸시 없는 분기를 따로 만들지 않는다. |
| 영향 | iOS 출시 일정이 NOTIFICATION BACKEND의 변경 일정에 묶인다. |
| 근거 | [6-2 호환과 출시 조건](6-DEPLOYMENT.md#6-2-호환과-출시-조건) |
