# DECISIONS.md

현재 적용 기준은 각 명세에 두고 결정 당시의 이유와 대체 관계는 이 문서에 기록한다.

<br>

### 1. 기록 규칙

- 결정 하나를 표 하나로 기록한다. 기존 ID, 날짜, 당시 상태와 근거를 유지한다.
- 상태와 구현 설명은 원본의 기록 시점을 기준으로 해석한다. 현재 적용 여부나 배포 완료를 과거 기록만으로 단정하지 않는다.
- 결정이 바뀌면 새 ID로 기록하고 대체하는 결정과 적용 범위를 명시한다.
- 원문에 구분되지 않은 배경, 대안과 영향은 추측해서 보충하지 않는다.
- 이 세트의 iOS 결정 ID는 I-060부터 I-079까지 쓴다. 사용자가 확인하기 전의 작성 중 결정은 상태를 Proposed로 둔다.

**I-060. 로그인 제공자는 Google과 Kakao만 두고 Sign in with Apple을 넣지 않음**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | Android [A-002](../ANDROID/DECISIONS.md#a-002)의 로그인 필수 모델을 iOS에도 적용 |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | 서버 소셜 인증의 제공자는 `google`, `kakao`뿐이다(dev OpenAPI 2026-11-26 조회, 재인증 요청 스키마에만 `APPLE`, `NAVER` 값이 보임). App Store 심사 지침 4.8은 서드파티 소셜 로그인으로 주 계정을 만드는 앱에 동등한 로그인 서비스를 요구하고 Sign in with Apple이 이를 충족한다는 자료가 있다(2026-11-26 웹 확인). 지침 원문과 예외 조항은 확인하지 않았다. |
| 채택 | iOS 로그인 제공자는 Google과 Kakao만 둔다. Sign in with Apple은 넣지 않고 심사 지침 4.8 반려 위험을 감수한다. 반려되면 그때 추가하며 서버 `/auth/social/{provider}`에 `apple`을 추가하는 것이 선행 조건이다. |
| 대안 | 첫 출시에 Sign in with Apple 포함(서버 로그인 제공자 계약과 계정 연동 계약을 먼저 넓혀야 함) |
| 이유 | 원문에 별도 항목으로 구분하지 않음 |
| 영향 | 반려되면 서버 계약 변경, iOS 제공자 추가와 재심사가 출시 일정에 더해진다. `DomainError`의 제공자 관련 오류와 연동 칩의 대상은 Google과 Kakao다. 지침 원문은 제출 전에 다시 확인해야 위험의 크기를 판단할 수 있다. |
| 근거 | [KNK-2154](https://kimandkang.atlassian.net/browse/KNK-2154), Android 현황과 iOS 대응 정리(2026-11-26, 저장소 미포함) 1-5절, 2절, 7절 1번 |

**I-061. Keychain은 기기 전용으로 두고 재설치 첫 실행에서 토큰을 지움**

| 상태 | Accepted |
| 관계 | Android [A-007](../ANDROID/DECISIONS.md#a-007)의 iOS 대응. 저장소 구분은 [IOS 기반 I-008](../../../../platform/CLIENT/IOS/DECISIONS.md#i-008), 판정 세부는 [I-064](#i-064) |

| 이유 | 원문에 별도 항목으로 구분하지 않음 |
| 영향 | 기기 백업을 다른 기기로 옮기면 토큰이 따라가지 않아 다시 로그인해야 한다. 재설치한 회원도 다시 로그인한다. |

<a id="i-064-재설치-판정과-keychain-읽기-결과-처리"></a>

**I-064. 재설치 판정과 Keychain 읽기 결과 처리**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | [I-061](#i-061)의 구현 조건 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | I-061은 UserDefaults 표시로 첫 실행을 판정한다. 기기의 첫 잠금 해제 전에는 UserDefaults가 비어 보이고 첫 잠금 해제 후 접근으로 둔 Keychain 항목도 읽을 수 없어 그때 판정하면 기존 설치를 재설치로 오인한다. Android는 손상이면 바로 정리하고 일시 읽기 실패는 3회 읽은 뒤 정리한다. |
| 채택 | 보호 데이터에 접근할 수 없으면 시작 판정을 보류한다. 설치 표시가 없을 때 토큰 항목이 있거나 확인에 실패하면 종료 안내 없는 중앙 종료로 정리하고 저널 기록이 끝난 뒤 설치 표시를 남긴다. 항목이 없으면 설치 표시를 남기고 `Guest`로 간다. 설치 표시가 있으면 손상은 바로 중앙 종료, 읽기 실패는 100ms와 200ms 간격으로 3회 읽은 뒤 중앙 종료한다. |
| 대안 | 첫 실행에서 Keychain 항목만 바로 삭제: 삭제 실패와 중단 뒤 처리를 따로 만들어야 하고 제공자 SDK가 기기에 남긴 로그인 상태와 서버 세션이 그대로 남는다 |
| 이유 | 기존 종료 절차의 저널, 재시도와 실패 상태를 그대로 쓰고 이전 세션의 서버 로그아웃도 시도한다. 설치 표시를 저널 뒤에 남기므로 중간에 끝난 실행은 다음 실행에서 저널로 이어진다. |
| 영향 | 재설치 첫 실행은 시작 화면에서 정리를 거친 뒤 로그인 화면을 보인다. 설치 표시 키를 바꾸면 모든 기존 설치가 첫 실행으로 판정된다. |
| 근거 | [4-4-4 시작과 재설치 판정](4-4-EXECUTION.md#4-4-4-시작과-재설치-판정) |

<a id="i-065-토큰-만료-판정과-재발급-일시-실패의-세션-유지"></a>

**I-065. 토큰 만료 판정과 재발급 일시 실패의 세션 유지**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | Android [A-008](../ANDROID/DECISIONS.md#a-008)의 iOS 대응 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | Android는 부팅 횟수, 단조 시계와 벽시계 앵커를 함께 저장해 만료를 판정한다. 조사 문서는 iOS에서 같은 수준의 시계 조작 방어를 할지 정하도록 남겼다. 만료 토큰을 보내도 401 뒤 재발급 한 번과 재전송 한 번으로 복구된다. 하네스는 재발급의 네트워크 실패만 세션 유지로 적고 5xx는 적지 않는다. |
| 채택 | 받은 시각의 벽시계와 `expiresIn`으로 60초 여유를 두고 판정한다. 같은 프로세스 안에서는 `ContinuousClock` 경과와 비교해 큰 값을 쓰고 벽시계 경과가 음수이면 만료로 본다. 부팅 식별 값은 저장하지 않는다. 재발급의 401과 403이 아닌 실패(네트워크, 5xx 등)는 세션을 유지한다. |
| 대안 | Android와 같은 부팅 식별과 단조 앵커 저장<br>재발급 5xx도 세션 종료 |
| 이유 | 판정이 틀려도 결과는 401 한 번과 재발급이라 부팅 식별 수단에 의존하지 않는다. 서버 일시 오류로 유효한 세션을 끝내지 않는다. |
| 영향 | 벽시계를 뒤로 돌린 기기는 재실행 뒤 첫 요청이 401을 받고 재발급한다. 재발급 5xx가 이어지면 요청만 실패하고 세션은 남는다. |
| 근거 | [4-3-1 세션과 토큰](4-3-STATE-MANAGEMENT.md#4-3-1-세션과-토큰), [4-4-2 재발급](4-4-EXECUTION.md#4-4-2-재발급), Android 현황과 iOS 대응 정리 1-5절 |

<a id="i-066"></a>
<a id="i-066-종료-저널을-원자적-파일-쓰기로-기록하고-정리-재시도를-3회로-둠"></a>

**I-066. 종료 저널을 원자적 파일 쓰기로 기록하고 정리 재시도를 3회로 둠**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | [I-063](#i-063)의 저널 기록 실패 처리 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | 하네스는 저널을 원자 기록하고 기록 실패면 파괴적 정리를 시작하지 않으며 정리 실패는 유한 재시도 뒤 `CleanupFailed`로 둔다. UserDefaults는 쓰기 결과를 돌려주지 않아 파괴적 단계 전에 기록 성공을 확인할 수 없다. Android 코드는 DataStore에 기록하고 필수 단계를 3회, 200ms부터 두 배 간격으로 시도한다. |
| 채택 | 저널은 Application Support의 파일 하나에 원자적 쓰기로 기록하고 쓰기 결과를 확인한 뒤 다음 단계로 간다. 저널 기록을 포함한 필수 단계는 3회(200ms, 400ms 간격) 시도한 뒤 `CleanupFailed`로 둔다. 저널 기록 실패는 파괴적 정리 없이 `CleanupFailed`로 두고 재시도는 저널 기록부터 다시 한다. |
| 대안 | UserDefaults 기기 suite에 저장: 기록 성공을 확인할 수 없다<br>Keychain에 저장: 앱 삭제 뒤에도 남아 재설치 판정과 섞인다 |
| 이유 | 파괴적 단계 전에 재개 지점이 기기에 남았는지 확인할 수 있고 앱 삭제와 함께 지워진다. |
| 영향 | 저널 기록 실패 뒤 프로세스가 끝나면 저널이 없으므로 다음 실행은 저장된 토큰으로 다시 판정한다. |
| 근거 | [Android 4-3-4](../ANDROID/4-3-STATE-MANAGEMENT.md#4-3-4-초대와-종료-상태), [4-4-3 중앙 로그아웃과 복구](4-4-EXECUTION.md#4-4-3-중앙-로그아웃과-복구) |

**I-067. 초대 안내 닫기 기록의 실패 상태를 두지 않음**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | 공통 [2-2-4 연동과 초대](../2-2-REQUIREMENTS.md#2-2-4-연동과-초대)의 지급 후 닫기 실패 요구를 iOS 저장 방식에 적용 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | 공통 요구는 보상 지급과 닫기 기록을 구분하고 닫기 기록만 재시도하게 한다. Android는 DataStore 쓰기 실패를 거짓으로 돌려 현재 실행의 재표시를 막는다. iOS의 회원 suite(UserDefaults)는 쓰기 결과를 돌려주지 않는다. |
| 채택 | 닫기는 회원 suite의 표시를 지우고 현재 실행의 닫힘을 메모리에 둔다. 기록 실패 상태와 지급 후 닫기 실패 표시를 두지 않으며 보상을 다시 요청하지 않는다. |
| 대안 | 닫기 기록을 쓰기 결과를 확인할 수 있는 파일에 둠: 표시 하나에 저장소를 하나 더 둔다 |
| 이유 | 보상 재요청 없음과 현재 실행의 재표시 차단은 그대로 지켜진다. |
| 영향 | 디스크 반영이 실패하면 다음 실행에서 안내가 다시 보이고 등록 자격은 유지된다. 공통 3-3-5의 지급 후 닫기 실패 문구는 iOS에서 쓰지 않는다. |
| 근거 | [4-3-4 초대와 종료 상태](4-3-STATE-MANAGEMENT.md#4-3-4-초대와-종료-상태) |

<a id="i-068-프로필-수정의-이탈-확인을-위해-시스템-뒤로-동작을-막음"></a>

**I-068. 프로필 수정의 이탈 확인을 위해 시스템 뒤로 동작을 막음**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Accepted |
| 관계 | 공통 UI iOS [I-052](../../../../ui/IOS/DECISIONS.md#i-052) 이탈 확인 규칙의 대상 화면 |
| 승인 근거 | KNK-2154 작업 대화에서 사용자가 확정했다 |
| 배경 | 공통 요구는 미저장 프로필의 이탈 확인을 요구하고 Android는 헤더와 기기 뒤로가기에 같은 확인을 띄운다. iOS의 가장자리 밀기와 시스템 뒤로 버튼은 확인 없이 화면을 닫는다. |
| 채택 | 프로필 수정에 미저장 변경이 있거나 저장 중인 동안 가장자리 밀기를 끄고 시스템 뒤로 버튼 대신 내비게이션 바의 같은 자리에 같은 모양의 뒤로 버튼을 둔다. 미저장 변경이면 이탈 확인을 띄우고 저장 중이면 동작하지 않는다. 변경이 없으면 시스템 뒤로 동작을 그대로 쓴다. |
| 대안 | 가장자리 밀기를 허용하고 닫힌 뒤 변경을 버림: 공통 이탈 확인 요구를 지키지 못한다 |
| 이유 | 공통 요구를 지키면서 변경이 없는 화면은 시스템 동작과 같게 둔다. |
| 영향 | 변경이 있는 동안 가장자리 밀기가 동작하지 않는다. 대체 버튼은 시스템 내비게이션 바 안에 있으므로 시스템 뒤로 버튼과 같은 SF Symbols 아이콘을 쓴다. |
| 근거 | [공통 2-2-3 프로필과 페르소나](../2-2-REQUIREMENTS.md#2-2-3-프로필과-페르소나), [공통 UI 셸과 헤더](../../../../ui/IOS/3-3-LAYOUT.md#3-3-1-셸-헤더와-실행-화면) |

<a id="i-069-저장-세션-시작-화면의-동의-조회-실패는-재시도만-제공"></a>

**I-069. 저장 세션 시작 화면의 동의 조회 실패는 재시도만 제공**

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-28 |
| 상태 | Proposed |
| 관계 | Android [A-069](../ANDROID/DECISIONS.md#a-069)의 시작 화면 조회 실패 처리를 iOS에 적용 |
| 승인 근거 | 작성 중 결정. 사용자 확인 전 |
| 배경 | Android는 저장 세션의 시작 화면 조회 실패에 재시도만 두고 뒤로가기로 세션을 유지한 채 앱을 떠나게 한다. iOS에는 앱을 끝내는 뒤로가기가 없다. |
| 채택 | iOS 시작 화면의 일시 실패도 재시도만 제공하고 로그아웃 버튼을 두지 않는다. 사용자가 앱을 떠나도 세션은 유지된다. 공통 2-2-1의 iOS 적용 범위에 같은 내용을 적는다. |
| 대안 | 시작 화면 실패에 로그아웃 버튼을 둠: 일시 네트워크 오류에서 유효한 세션을 버리는 출구가 생긴다 |
| 이유 | 저장 세션의 순간 오류를 세션 종료로 잇지 않는다. |
| 영향 | 실패가 계속되면 앱 안에서는 재시도만 할 수 있다. 403과 401은 각각 이용 제한과 만료 흐름으로 간다. |
| 근거 | [2-2-1 진입과 동의](2-2-REQUIREMENTS.md#2-2-1-진입과-동의) |
