웹과 Android가 만족해야 하는 현재 제품 계약입니다. 기술 구조는 플랫폼 설계, 결정 이유는 [공통 ADR](../adr/1-1-client-adr.md), 승인·적용·작업 추적은 [클라이언트 추적](../planning/client-tracking.md)이 소유합니다.

## 3-1-1. 문서 목적·범위와 관련 문서

- 사용자에게 보이는 동작·입력·상태·오류·데이터 보존·수용 기준을 정의합니다. US·FE-SCREEN·FLOW 식별자는 유지합니다.
- [웹 스펙](3-2-web-spec.md)과 [Android 스펙](3-3-android-spec.md)은 플랫폼 고유 계약과 명시적인 적용 차이만 소유합니다. 공통 본문을 복사하지 않습니다.
- 계약과 코드의 차이는 추적 문서에 기록합니다. 코드가 다르다는 이유만으로 승인된 계약을 바꾸지 않습니다.
- API의 요청·응답 형식과 서버 정책은 [백엔드](4-backend-server-spec.md), 이벤트·식별자의 의미는 [분석](6-analytics.md), 용어는 [용어집](0-glossary.md)이 정본입니다. 이 문서의 API 경로는 `/api/v1`을 생략합니다.
- 기능 계약은 승인과 적용 범위가 확정될 때 갱신합니다. 적용을 유예한 목표와 미확정 사항은 추적 문서가 연결하는 기능 계획에서 구분합니다.

## 3-1-2. 공통 계약과 플랫폼 경계

회원의 스토리·채팅 목록은 서버가 소유합니다. 생성·삭제 후 화면은 서버 결과와 일치해야 합니다. 익명 체험·브라우저 저장·회원 이관은 웹 전용이며 [웹 사용자 모델](3-2-web-spec.md#웹-사용자-모델)이 소유합니다. Android는 로그인 후 서비스에 진입합니다.

스토리 생성 요청의 복구 식별자, 채팅의 턴·스트림 의미, 서버 정책 수치의 표시, 신고·계정·법적 문서 계약은 공통입니다. URL, 브라우저 이력, SDK, 저장 기술, 모듈·스코프는 이 문서에서 정하지 않습니다.

### FE-SCREEN-001. 홈 — 오리지널 스토리 목록

| 항목     | 값                                             |
| -------- | ---------------------------------------------- |
| 관련 API | `GET /stories/originals`                       |
| 관련 US  | US-2-2, US-2-7·2-8             |

**목적** — 마냑 공식 계정의 오리지널 스토리를 탐색하고 상세로 진입합니다. 내가 만든 스토리 관리와 제작 진입은 FE-SCREEN-013 제작 탭이 담당합니다.

**진입 조건** — 인증·온보딩 정책을 충족하면 홈을 기본 화면으로 엽니다. 진입 정책은 각 플랫폼 스펙이 소유합니다.

**화면 구성** — 별도 상단 패딩 없이 시작하는 굵은 "오리지널 스토리" 제목과 2열 카드 그리드로 구성합니다. 카드는 3:4 썸네일(없으면 placeholder), 좌상단 ORIGINAL 태그, 우하단 누적 턴 수 배지(좋아요 수 배지는 현재는 표시하지 않음 — [스토리 좋아요](#fe-screen-003-스토리-상세) 절 참조), 제목 1줄, 제작자 닉네임(응답 `author.nickname` 앞에 `@`를 붙여 "@마냑") 1줄을 표시합니다. `@`는 핸들임을 드러내는 표기이므로 카드에만 붙이고, 상세의 제작자 값에는 붙이지 않습니다. 카드의 모든 텍스트가 1줄 고정이라 제목 길이와 무관하게 카드 높이가 같고, 같은 행의 제작자 줄이 같은 높이에 놓입니다. 내 스토리 목록·이어 만들기 배너·생성 버튼은 홈에 표시하지 않습니다.

**ORIGINAL 태그** — 오리지널 카드에만 표시합니다. 표지가 비치는 반투명·블러 질감을 사용하며 내 스토리 카드에는 표시하지 않습니다.

**데이터 소스** — 인증 없이 `GET /stories/originals`를 조회하며 게스트·회원 모두 서버 등록순을 그대로 유지합니다. 공식 계정이 설정되지 않은 환경은 빈 목록입니다.

| ---------- | ---------------------- | -------------------------------------------------------------------------------------- |
| 로딩       | 오리지널 목록 조회 중  | 지연 후 제목 1개 + 오리지널 카드 6개 형태(썸네일·제목·제작자)의 스켈레톤. 지연 전에는 비움 |
| 빈 상태    | 응답이 빈 배열         | 오리지널 섹션을 표시하지 않음                                                        |
| 에러       | 조회 실패              | 제목 유지 + "스토리를 불러오지 못했어요" + 다시 시도                                |

**검수 기준**

- 홈에는 오리지널 스토리만 표시하고 내가 만든 스토리·제작 CTA·이어 만들기 배너는 표시하지 않아야 합니다.
- 게스트 상태에서도 회원과 같은 오리지널 목록을 표시해야 합니다.
- 오리지널 카드를 누르면 상세로 이동해야 합니다. (US-2-2)
- 조회가 지연되면 제목과 오리지널 카드 메타 구조에 맞는 스켈레톤을 표시해야 합니다.
- 조회 실패 시 제목과 인라인 오류를 표시하고 다시 시도로 복구할 수 있어야 합니다.
- `thumbnailUrlSm`이 있는 카드는 썸네일 이미지를, 없는 카드는 placeholder를 표시해야 합니다. (US-2-7)

### FE-SCREEN-013. 제작 — 내 스토리 목록

| 항목     | 값                                                                         |
| -------- | -------------------------------------------------------------------------- |
| 관련 API | `POST /stories/batch`(게스트), `GET /users/me/stories`(회원)                |
| 관련 US  | US-2-1·2-3·2-4·2-6·2-8                                     |

**목적** — 내가 만든 스토리를 확인·관리하고 새 제작 또는 진행 중 제작을 이어갑니다.

**진입 조건** — 하단 제작 탭에서 진입합니다. 제작·편집 화면의 진입 경로는 각 플랫폼 스펙이 소유합니다.

**화면 구성** — 제작 헤더 아래에 별도 섹션 제목 없이 내 스토리 가로 카드 목록과 제작 진행 상태를 표시합니다. 초안·완성 요청의 계약은 §3-1-4가 소유합니다. 완성 스토리가 있으면 새 제작 FAB를, 빈 상태에서는 제작 CTA를 표시합니다. 플랫폼별 진행 카드·배너의 적용 범위는 플랫폼 스펙을 따릅니다.

내 스토리 목록은 콘텐츠 폭을 모두 사용하고, 각 카드 행이 가로 16px·세로 8px 내부 패딩과 16px 열 간격을 소유합니다. 카드 전체 링크는 행의 패딩 영역까지 덮습니다. 카드의 왼쪽에는 폭 128px 고정 3:4 썸네일(없으면 placeholder)을 두고, 오른쪽 정보 영역은 썸네일 높이를 최소 높이로 사용합니다. 정보 영역 위쪽에는 제목 최대 2줄과 첫 줄 오른쪽의 옵션 버튼, 한 줄 소개 최대 2줄, 한 줄 장르 배지(초과 시 `+N`)를 순서대로 표시합니다. 아래쪽에는 누적 턴 수·제작일(`createdAt`의 KST 기준 `YYYY-MM-DD` — [§3-1-7 날짜 표시 기준](#날짜-표시-기준))을 오른쪽 정렬합니다. 좋아요 수(`likeCount`)는 현재는 표시하지 않음 — [스토리 좋아요](#fe-screen-003-스토리-상세) 절 참조. 옵션 다이얼로그의 카드 축소판에도 같은 순서를 적용합니다. 좁은 화면이나 큰 숫자는 지표 단위로 줄바꿈해 날짜와 숫자가 잘리지 않게 합니다. 옵션 버튼의 크기·아이콘 자산은 플랫폼 디자인 토큰을 따릅니다. 오리지널 카드는 기존 2열 카드와 ORIGINAL 태그를 유지합니다. 각 플랫폼의 아이콘 자산과 시맨틱 글자색을 사용합니다. 로딩 스켈레톤도 같은 전체 폭 행, 가로 16px·세로 8px 패딩, 128px 표지, 제목·소개·장르·하단 메타 순서를 사용해 실제 목록으로 바뀔 때 위치가 튀지 않게 합니다.

**데이터 소스** — 회원은 `GET /users/me/stories`의 서버 목록을 사용합니다. 익명 체험 목록은 [웹 스펙](3-2-web-spec.md#웹-사용자-모델)이 소유합니다.

**카드 옵션 다이얼로그**  — 카드의 옵션 버튼은 드롭다운이 아니라 화면 가운데 다이얼로그를 엽니다. 다이얼로그 상단 회색 상자에 그 카드의 축소판(표지·제목·소개·메타를 한 단계씩 작게)을 두어 여러 장 중 무엇을 골랐는지 확인하게 합니다. 항목은 "신고하기"(회원만) → 파괴적 표기의 "삭제하기" 순서이고, 삭제하기를 고르면 **같은 다이얼로그가 확인 화면으로 바뀝니다**.

**스토리 삭제** — 자신의 스토리에서만 삭제를 제공합니다. 오리지널 카드에는 옵션 버튼을 표시하지 않습니다. 서버 실패 시 항목과 사용자 접근 경로가 유실되지 않아야 합니다. 웹 게스트의 로컬 ID 정리는 웹 스펙이 소유합니다.

| 빈 상태 | 저장된 스토리 없음                    | FAB 숨김 + "아직 만든 스토리가 없어요" + "스토리 만들기" CTA |
| 에러    | 목록 조회 실패                        | FAB 숨김 + "스토리를 불러오지 못했어요" + 다시 시도          |
| 기본    | 스토리 존재                           | 오른쪽 아래 primary FAB + 1열 가로 카드 목록                 |

**검수 기준**

- 제작 탭에는 별도 섹션 제목을 표시하지 않고, 제작 헤더 바로 아래에 내가 만든 스토리만 표시해야 합니다. 카드 행과 카드 전체 링크는 목록의 전체 폭을 사용해야 합니다.
- 빈 상태·에러·로딩·회원/게스트 목록과 상세 이동이 기존 목록 계약대로 동작해야 합니다. (US-2-1·2-2·2-6)
- 목록이 있으면 오른쪽 아래 FAB를 표시하고, 빈 상태에서는 이를 숨긴 채 기존 빈 상태 CTA만 표시해야 합니다. 두 CTA는 간편 제작으로 이동하고, 이어 만들기 배너는 이 화면에서만 표시되어야 합니다.
- FAB는 마우스 호버 중에도 primary 배경 불투명도를 유지하면서 3% 확대하고, 모션 감소 환경에서는 확대하지 않아야 합니다.
- 스토리 삭제 성공 후 현재 제작 목록에서 삭제된 카드가 사라져야 합니다.
- 카드 옵션 버튼은 상단에 그 카드의 축소판을 담은 다이얼로그를 열고, 삭제하기는 같은 다이얼로그 안에서 확인으로 바뀌어야 합니다. 신고하기는 회원에게만 보여야 합니다.

**썸네일 이미지 뷰어** — 썸네일을 누르면 전체 화면으로 엽니다. 닫기 제어·화면 탭·뒤로가기로 닫으며, 뒤로가기는 상세 화면을 떠나지 않고 뷰어만 닫아야 합니다. 이미지가 없으면 뷰어를 열지 않습니다.

**스토리 좋아요**  — **현재는 좋아요 버튼과 좋아요 수 배지를 어느 화면에도 표시하지 않습니다.** 2026-09-11 사용자 결정으로 스토리 게시·공유 기능이 나올 때까지 UI만 숨기며, 등록·취소 API와 아래 계약은 그대로 유지해 노출을 되살릴 때 다시 적용합니다. 이하는 노출 시 계약입니다. 상세 하단에서 좋아요를 등록·취소하고, 목록·상세 썸네일에서 반응 수를 확인합니다. **내가 만든 스토리에는 좋아요 버튼을 표시하지 않습니다.** 회원은 상세의 `isOwner`, 게스트는 기기에 저장된 제작 스토리 ID로 판별합니다. 소유 여부를 확인하는 동안에도 버튼을 숨겨 오노출을 막습니다. 좋아요 수 배지는 소유 여부·로그인 여부·썸네일 이미지 유무와 무관하게 표시합니다.

- 하단 채팅 시작 CTA 왼쪽에 고스트 라지 아이콘 버튼을 두고, 두 버튼 사이는 16px로 띄웁니다. 기본은 검정 계열 전경색의 아웃라인 하트이고, `isLiked`가 참이면 빨간 filled 하트입니다. 다크 모드는 전경색 토큰을 따라 대비를 유지합니다. 배지 하트는 흰색 아웃라인으로 턴 수 배지와 같은 질감을 사용합니다.
- 회원은 `POST /stories/{storyId}/like`로 등록하고 `DELETE /stories/{storyId}/like`로 취소합니다. 204 성공 뒤 버튼 상태와 상세 수를 반영하고 상세·목록 집계를 다시 조회합니다. 요청 중에는 좋아요 버튼을 비활성화해 중복 전송을 막습니다. 실패하면 기존 상태·수를 유지하고 실패 토스트를 표시합니다.
- 게스트는 버튼을 누르면 좋아요 API를 호출하지 않고 현재 상세 위에 로그인 바텀 시트를 엽니다. 제목은 "로그인이 필요한 기능이에요", 설명은 "로그인을 하면 모든 기능을 이용할 수 있어요"입니다(현재 값·정본: `manyak-web/src/features/auth/_shared/constants/login-required.ts`). 카카오·Google 로그인 버튼과 약관 고지는 기존 로그인 유도 시트를 재사용합니다. 로그인 후 해당 상세로 돌아갈 경로를 보존하며, 바깥 탭·ESC로 닫으면 상세에 그대로 머뭅니다. 로그인 진행 중에는 두 버튼과 시트 해제를 잠그고, 로그인 시작 실패 시 실패 토스트와 함께 다시 시도할 수 있게 합니다. 기존 게스트 체험 한도 시트의 문구와 동작은 유지합니다. 2026-09-06 사용자 요청으로 페이지 이동을 시트 노출로 바꿔 좋아요를 누른 화면의 맥락을 유지합니다.
- 목록 썸네일과 상세 히어로의 좋아요 수는 턴 수 배지 왼쪽에 나란히 표시합니다. 0 또는 필드 누락도 0으로 표시하고 천 단위 콤마를 사용합니다. 별도 메타 줄 없이 기존 썸네일 지표와 함께 보이게 하려는 결정입니다.
- 문구 현재 값·정본: 버튼 이름은 "좋아요"·"좋아요 취소", 배지 접근성 이름은 "좋아요 수"(`manyak-web/src/features/stories/_shared/constants/story-like.ts`), 실패 토스트는 "좋아요 변경에 실패했어요"(`src/constants/toast-message.ts`).

**스토리 신고**  — AI가 만든 내용이 부적절할 때 그 자리에서 접수하는 경로입니다. 스토리 상세와 채팅 화면([FE-SCREEN-005](#fe-screen-005-채팅-화면))이 **헤더 오른쪽 더보기 메뉴의 "신고하기"** 로 같은 시트를 열고, 제작 목록([FE-SCREEN-013](#fe-screen-013-제작--내-스토리-목록))·채팅 목록([FE-SCREEN-004](#fe-screen-004-채팅-목록)) 카드의 옵션 다이얼로그도 같은 시트를 엽니다. **채팅에서 열어도 신고 대상은 그 채팅이 참조하는 스토리입니다**(서버 계약이 스토리 단위 — [`4-backend-server-spec.md §4-3-1`](4-backend-server-spec.md)). 신고는 인증이 필요하므로(미인증 401) **게스트에게는 신고하기 항목을 표시하지 않습니다** — 로그인 유도 시트로 보내지 않는 이유는, 신고는 게스트 체험 한도처럼 사용자의 목적 달성을 막는 지점이 아니라 발견되지 않아도 되는 부가 경로이기 때문입니다. 참조 스토리가 삭제된 채팅(제목이 빈 값)에서도 신고 항목을 두지 않습니다(서버가 404로 거절).

시트는 바텀 시트이며 제목·설명, 사유 라디오 3개(도배·홍보 / 부적절한 내용 / 기타 — 줄 전체가 선택 대상), "자세한 내용 (선택)" 500자 자유 서술과 글자 수 카운터, 파괴적 표기의 "신고하기" 전송 버튼, 초대 온보딩 시트와 같은 보조색 텍스트형 "닫기" 순서로 구성합니다.  사유를 고르기 전에는 전송 버튼이 비활성이고, 전송 중에는 버튼이 문구 공간을 유지한 스피너로 잠기며 시트를 닫을 수 없습니다. 전송은 `POST /stories/{storyId}/reports {reason, detail}`(빈 서술은 `null`)이고, 성공(201)하면 시트를 닫고 접수 안내 토스트를 띄웁니다. 실패하면 **시트와 입력을 그대로 두고** 실패 토스트만 띄웁니다 — 쓰던 사유·상세를 다시 입력하게 하지 않습니다. 같은 회원이 같은 스토리를 다시 신고해도 서버가 멱등으로 흡수하므로 클라이언트는 중복을 따로 막지 않습니다. 문구의 웹 코드 정본은 `manyak-web/src/features/stories/_shared/constants/story-report.ts`(토스트는 `src/constants/toast-message.ts`)이며 앱 `strings.xml`과 같은 값을 씁니다.

신고 진입점의 구체 배치는 플랫폼 스펙이 소유합니다. 사유·입력·접수 결과는 공통 계약을 사용합니다.

**상태** — 300ms 지연 뒤 히어로·제목·소개·태그·주요 내용의 실제 구조에 맞춘 전용 스켈레톤 / 로드 실패 시 인라인 에러 + "다시 시도" / 404 시 "스토리를 찾을 수 없어요"만 표시 / 기본(본문 + CTA). 헤더는 모든 상태에서 유지됩니다. 스켈레톤은 1.4초 주기의 전용 펄스 애니메이션을 사용합니다.

본문 제목이 56px 헤더 아래로 사라지면 헤더에 같은 제목이 페이드 인해야 합니다. 이 전환은 상세 응답 속도와 전용 스켈레톤 표시 여부에 영향을 받지 않아야 합니다.

**검수 기준**

- 제목·소개·설명·시작 설정과 턴 수·생성일을 표시해야 합니다. (US-4-1)
- 본문 제목이 헤더 아래로 사라지면 응답 속도와 무관하게 헤더 제목을 표시해야 합니다.
- `thumbnailUrl`이 있으면 썸네일 이미지가, 없으면 placeholder가 표시돼야 합니다. 썸네일을 누르면 이미지 뷰어가 열리고 X·뒤로가기로 페이지 이동 없이 닫혀야 합니다. (US-4-1)
- 시작 설정이 여러 개면 Select로 상황을 바꿀 수 있고, 선택한 상황 설명이 표시돼야 합니다. (US-4-1)
- "새 채팅 시작하기"를 누르면 선택한 시작 설정(`startSettingId`)으로 채팅 화면에 이동해야 합니다. (US-4-2)
- 상세 헤더에는 뒤로가기와 더보기 메뉴만 제공하고, 메뉴에는 회원에게 신고하기를, 내가 만든 스토리에는 삭제하기를 표시해야 합니다. 둘 다 해당하지 않으면(게스트가 만들지 않은 스토리) 메뉴 버튼 자체를 두지 않습니다. 상세에서 삭제하면 제작 목록으로 돌아가야 합니다.
- 신고 시트에서 사유를 고르기 전에는 전송할 수 없고, 접수에 성공하면 시트가 닫히고 실패하면 입력이 남아 있어야 합니다.
- 404가 아닌 로드 실패는 다시 시도로 복구할 수 있어야 하며, 404에는 재시도 버튼을 표시하지 않아야 합니다. (US-4-4)
-  회원 스토리에서 엔딩에 도달하면 상세 응답의 본 엔딩 배지가 표시돼야 합니다. 익명 체험의 집계 범위는 웹 스펙을 따릅니다. (US-4-6)

**데이터 소스** — 회원은 `GET /users/me/chats`를 사용하고 서버의 최근 활동순을 유지합니다. 익명 체험 목록의 배치 조회는 웹 스펙이 소유합니다.

### FE-SCREEN-008. 로그인·마이 페이지

| 항목    | 값                                                                                                                            |
| ------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 관련 US | US-9-1 ~ 9-11, US-10-1 ~ 10-6                                                                                                 |

**목적** — 소셜 계정으로 로그인하고 프로필·연동 계정·이프·친구 초대·로그아웃·탈퇴를 관리합니다. 익명 체험 데이터의 계정 이관은 웹 전용입니다.

**진입점** — 마이 탭에서 회원 정보와 계정 관리 기능을 엽니다. 로그인 전 진입과 인증 후 목적지는 플랫폼 스펙이 소유합니다.

**마이 페이지 회원 상태 구성** — 게스트는 로그인 버튼을 표시합니다. 회원은 닉네임·프로필 이미지·연동된 계정(아래 계정 연동 문단)·이프 잔액·친구 초대·로그아웃·회원 탈퇴를 표시합니다. 이프 카드에는 잔액 오른쪽에 이프 충전(`/my/credits`)으로 가는 강조색 버튼 "충전" 하나만 둡니다 — 이프를 얻는 수단은 모두 이프 충전 화면이 소유하므로 마이에는 그 화면으로 가는 입구만 남깁니다. 출석 체크 버튼도 이때 이프 충전으로 옮겼습니다. 친구 초대 메뉴는 라벨 아래에 작은 강조색 보조 문구 "하고 N 이프 받기"를 붙여 보상을 라벨과 이어 읽게 합니다(N은 서버 정책의 초대 보상 — [§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시)). 계정 섹션은 기본 전경색의 로그아웃 아래에 위험색 회원 탈퇴를 둬 비가역 동작만 강조합니다. 화면 섹션의 테마 변경과 기타 섹션의 피드백·서비스 안내(FE-SCREEN-011)는 게스트와 회원 모두 사용할 수 있습니다.

**이프 충전**  — 마이 이프 카드의 "충전" 버튼으로 `/my/credits`에 진입합니다. 게스트 진입은 친구 초대와 같이 `/login`으로 보냅니다. 화면 성격이 내역 열람에서 충전으로 넓어졌지만 **경로는 그대로 둡니다** — 같은 자리의 같은 관심사이고, 이미 배포된 링크를 깨지 않기 위해서입니다.

- **화면 골격** · 뒤로가기 헤더("이프 충전") 아래에 잔액 상자와 탭 줄을 **셸에 고정**하고 탭 패널만 스크롤합니다. 잔액은 어느 탭에서 무엇을 하든 계속 보여야 하는 값이라 스크롤을 따라 사라지지 않습니다.  탭은 무료 충전 · 내역 두 개이고 기본값은 무료 충전이며, 스토리 생성 퍼널(FE-SCREEN-002)과 같은 밑줄 탭 모양을 씁니다. 선택한 탭은 URL에 남기지 않습니다 · 진입 경로가 마이의 "충전" 하나뿐이라 탭 자체를 공유·북마크할 일이 없습니다.
- **잔액 박스** · 화면 최상단에 중립 배경·카드 모서리·안쪽 여백 16px 상자를 두고, "내 이프" 라벨을 위에, 잔액을 그 아래 오른쪽에 한 단계 큰 글자와 천 단위 콤마로 표시합니다. 값의 정본은 마이와 같은 `GET /auth/me`의 `creditBalance`이며 진입할 때 다시 읽습니다. **내역 항목의 금액을 합산해 잔액을 만들지 않습니다** · 만료 회수가 실제 만료보다 늦게 기록되고 내역이 페이지로 나뉘어 합계가 잔액과 어긋납니다([`4-backend-server-spec.md §4-3-7`](4-backend-server-spec.md) 이용내역 조회).
- **유료 충전** — 상품 목록의 기본·보너스·총량과 플랫폼 가격을 표시하고 구매 이프가 적립 후 5년간 유효함을 안내합니다. 플랫폼 결제 진입·검증 수단은 각 플랫폼 스펙이 소유합니다. 서버 상품·주문 API는 [백엔드](4-backend-server-spec.md)가 정본입니다.

| `reason` | 라벨 |
| --- | --- |
| `SIGNUP_REWARD` | 가입 보상 |
| `ATTENDANCE_REWARD` | 출석 체크 보상 |
| `INVITE_REWARD` | 친구 초대 보상 |
| `REFUND` | 사용 취소 |
| `STORY_CREATION` | 스토리 완성 |
| `CHAT_TURN` | 채팅 전송 |
| `EXPIRE` | 기간 만료 |
| `PURCHASE` | 이프 충전 |
| `PURCHASE_REVERSAL` | 결제 환불 회수 |

- **금액 표기** — 부호는 `type`이 정합니다. `EARN`은 `+`, `SPEND`·`EXPIRE`는 `-`를 붙이고 값은 절대값에 천 단위 콤마를 씁니다. 응답의 `amount`는 원장 부호가 실린 값(소모·소멸은 음수)이지만 그 부호를 그대로 옮기지 않고 절대값을 취합니다 — 표시 규칙을 분류 하나로 모읍니다.
- **제목·날짜** · `title`이 있으면 라벨 아래 한 줄로 표시하고, 소모·사용 취소인데 `title`이 없으면(삭제된 스토리) "삭제된 스토리"로 대체합니다. 보상·소멸 항목은 제목 줄을 그리지 않습니다.  구매·결제 환불 회수도 `title=null`이므로 제목 줄을 그리지 않습니다. 날짜는 `createdAt`(KST 기준 YYYY-MM-DD · [§3-1-7 날짜 표시 기준](#날짜-표시-기준))이며, `expiresAt`이 있으면 "YYYY-MM-DD 만료"를 함께 표시합니다 · 획득은 만료 예정일, 소멸은 회수된 로트의 실제 만료일입니다. **소멸 항목의 `createdAt`을 만료일로 읽지 않습니다**(지연 정리라 실제 만료보다 늦습니다).
- **페이징** — 목록 끝에 닿으면 응답의 `nextCursor`를 그대로 실어 다음 페이지를 이어 붙입니다. 커서는 불투명 문자열이라 파싱하거나 조립하지 않고 받은 값을 되돌려 줍니다. `nextCursor`가 없으면 마지막 페이지입니다.
- **화면 상태** — 첫 조회 중에는 잔액 상자와 내역 목록 자리에 각각 골격을 표시합니다. 항목이 하나도 없으면 "아직 이프 내역이 없어요"를 표시하고, 첫 조회 실패는 "이프 내역을 불러오지 못했어요"와 다시 시도하기를 목록 자리에 둡니다(친구 초대 코드 카드와 같은 처리). 다음 페이지 조회 실패는 **이미 그린 목록을 지우지 않고** 재시도만 제공합니다.

**테마 변경** — 화면 섹션의 테마 변경 메뉴는 탭할 때마다 시스템 설정 → 라이트 모드 → 다크 모드 순으로 순환합니다. 왼쪽 아이콘(모니터·해·달)과 오른쪽 현재 값 문구가 함께 바뀌고 테마는 즉시 적용됩니다. 선택값은 기기 단위로 저장됩니다.

**친구 초대**  — 마이의 친구 초대 메뉴는 `/my/invite`로 이동하며, 게스트 진입 시 `/login`으로 보냅니다.

- **보상 안내** — 화면 상단에는 "친구가 내 초대 코드를 등록하면 모두 N 이프를 받아요"를 표시합니다(N은 서버 정책의 `inviteReward` — [§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시)).
- **초대 코드 카드** — `GET /users/me/invite`로 내 코드와 월 보상 횟수를 조회합니다. 별도 카드에 코드 복사와 공유 버튼을 표시합니다. 공유 수단과 사용 가능 판정은 각 플랫폼 스펙·설계가 소유합니다.

**이프 부족 처리** — 서버의 402를 최종 판정으로 사용합니다. 무료인 채팅방 생성에는 잔액 부족 차단을 적용하지 않습니다. 완성·채팅·재생성의 안내 위치는 각 흐름의 계약을 따릅니다. 게스트 사용량 선차단과 로그인 유도는 웹 스펙을 따릅니다.

회원의 채팅 턴 이프 부족 안내와 제작 제출 실패 안내는 각 플랫폼의 해당 흐름을 따릅니다. 서버가 실패를 반환한 요청을 성공으로 표시하거나 잔액을 임의 차감하지 않습니다.

**소셜 로그인** — Google과 Kakao를 제공합니다. 로그인 화면에서는 카카오 버튼을 Google 위에 배치합니다. 한 플랫폼 안에서는 공급자와 무관하게 같은 로그인 완료 흐름을 사용합니다.

- **계정 연동 정적 안내** — Google과 Kakao는 처음 로그인할 때 별개 계정이 될 수 있으므로([`4-backend-server-spec.md §4-5`](4-backend-server-spec.md) API 계약), 버튼 아래에 먼저 하나의 소셜 계정으로 로그인한 뒤 다른 계정을 연동하도록 안내합니다. 문구는 모든 플랫폼이 동일하게 쓰며 **이 문서가 정본을 소유합니다** — "소셜 계정 하나로 먼저 로그인한 뒤 다른 계정을 연동하면, / 어느 계정으로 로그인해도 똑같이 이용할 수 있어요".  이미 별도 회원으로 만들어진 두 계정은 연동이 409로 막히고 통합도 제공하지 않으므로, 안내는 계정이 갈라지기 전의 예방 흐름만 설명합니다. **가입 여부를 조회해 안내를 분기하지 않습니다** — 특정 계정의 가입 여부를 알려주는 열거 오라클이 되기 때문입니다.

**로그인 진행 상태** — 탭한 버튼은 문구 공간을 유지한 중앙 스피너로 바뀌고 두 공급자 버튼이 모두 잠깁니다. 로그인 실패·취소로 화면에 남으면 스피너와 잠금을 해제합니다.

**신규 가입 온보딩(초대 코드 입력)**  — 신규 가입의 첫 로그인 완료 직후 화면 아래에서 올라오는 모달 바텀 시트를 표시합니다. 제목은 "초대 코드를 등록하면 / N 이프를 받을 수 있어요" 두 줄(N은 서버 정책의 `inviteReward`), 설명은 "지금은 건너뛰고 나중에 등록해도 돼요"이며, 초대 코드 입력란 아래에 "등록하기" 주 버튼과 "닫기" 고스트 버튼을 세로로 둡니다.  적립 후 세션 저장 실패 상태의 닫기 재시도 버튼도 같은 크기·너비·정렬을 사용합니다. 제목·설명 사이는 8px, 설명과 폼 사이는 32px입니다. 제출·피드백 규칙은 `/my/invite` 입력란과 동일합니다. 열릴 때 초점은 입력란이 아니라 시트 자체에 두어 모바일 키보드가 자동으로 올라오지 않게 합니다. "닫기"는 배경 탭·ESC와 같은 처리(세션 플래그 소비 후 닫기)이며, 건너뛰어도 자격(계정당 평생 1회)은 유지되어 이후 `/my/invite`에서 입력할 수 있습니다. 입력 성공 후 세션 플래그 저장이 끝날 때까지 등록 스피너와 입력 잠금을 유지하며, 저장 실패 시 보상은 다시 요청하지 않고 "N 이프는 정상 지급되었지만, 창을 닫는 데 실패했어요"를 표시한 뒤 플래그 저장만 재시도합니다.

**계정 연동**  — 로그인된 계정에 다른 provider를 추가해 어느 쪽으로 로그인해도 같은 계정으로 들어오게 합니다. 백엔드 계약과 2단계 프로토콜(재인증 → 연동)의 정본은 [`4-backend-server-spec.md §4-5`](4-backend-server-spec.md) 계정 연동 절입니다. **연동 해제는 제공하지 않으며**, 이미 갈라진 계정은 연동할 수 없습니다(예방책).

- **연동된 계정 표시** — 마이 페이지 닉네임 아래에 Chip 행을 둡니다. 연동된 provider는 로고 + 이름("Google" · "카카오") Chip으로, 미연동 provider는 같은 모양의 점선 테두리 버튼("카카오 연동하기" · "Google 연동하기")으로 표시합니다. 둘 다 연동되면 버튼은 사라지고 Chip 2개만 남습니다. 상태 정본은 `GET /auth/me`의 `linkedProviders`(소문자, `google` → `kakao` 정렬)이며, 전용 조회 API는 두지 않습니다. `GET /auth/me` 응답 전(로딩 중)에는 칩 크기의 스켈레톤 2개로 자리를 잡아 레이아웃 시프트를 막고, 응답이 왔는데 `linkedProviders`가 비어 있으면(미제공) 섹션 자체를 렌더하지 않습니다 — 실데이터 전에 칩·버튼을 그리지 않으므로 연동 버튼 2개가 잠깐 보이는 오해도 막힙니다.
- **연동 시작 확인 다이얼로그** — 연동 버튼을 누르면 곧바로 OAuth로 보내지 않고 확인 다이얼로그를 먼저 띄웁니다. 재인증이 선행되므로 **대상 provider가 아니라 현재 로그인한 provider의 인증 창이 먼저** 뜨는데, 예고가 없으면 사용자가 흐름을 오해합니다. 또 연동은 해제할 수 없어 비가역 확인이 필요합니다. 다이얼로그는 혜택(어느 쪽으로 로그인해도 같은 마냑 계정)·재인증 순서 예고(현재 provider를 다시 인증한 뒤 대상 provider를 연동)·해제 불가 고지를 각각 한 줄로 나눠 담고, "나중에 하기"/"연동하기" 2버튼을 둡니다. 명시적 이탈 버튼이 있으므로 닫기(X) 버튼은 두지 않습니다.
- **플로우** — 확인 → 현재 provider 재인증 → `POST /auth/links/reauth`로 링크 코드 발급(클라이언트 코드에 노출되지 않게 보관) → 대상 provider 인증 → `POST /auth/links/{provider}`(`X-Manyak-Link-Code` 헤더) → 성공 시 `GET /auth/me` 재조회로 Chip 갱신 + 성공 토스트. 연동 인증이 로그인 경로(백엔드 로그인 호출·세션 교체)를 타지 않아야 하고, 단계 판정은 클라이언트 상태가 아니라 콜백 provider의 `linkedProviders` 포함 여부로 서버가 하므로 중단된 이전 시도의 잔여 상태에도 자기 교정됩니다. 재인증 요구 자체(2단계 프로토콜)는 백엔드 계약이므로 유지합니다. 웹 구현 상세(NextAuth 연동 전용 프로바이더 변형, 중계 화면, `login_hint`)는 [`1-1-web-design.md §1-1-3` 소셜 로그인·계정 연동 웹 구현](../design/1-1-web-design.md#소셜-로그인계정-연동-웹-구현)이 소유합니다.
- **에러 처리** — 409 두 종류는 안내를 구분합니다([`4-backend-server-spec.md §4-5`](4-backend-server-spec.md) API 계약 참조). `PROVIDER_ALREADY_LINKED`(이미 내 계정에 연동)는 "이미 연동된 계정이에요" 토스트 + 상태 재조회, `SOCIAL_ACCOUNT_LINKED_TO_OTHER_USER`(다른 마냑 계정에 연동 = 갈라진 계정)는 **다이얼로그**로 상황과 대처(로그아웃 후 해당 계정으로 로그인)를 안내합니다 — 사라지는 토스트로는 "그럼 어떻게 하나"에 답할 수 없기 때문입니다. 이 다이얼로그에 "기존 계정으로 로그인하기" 버튼은 두지 않습니다(현재 세션 로그아웃이라는 큰 부수효과를 한 번의 탭에 묶지 않음). 403(`REAUTH_FAILED`·`SOCIAL_TOKEN_INVALID`)은 실패 토스트만 띄우고, 링크 코드가 소비되지 않아 만료 전 재시도가 가능합니다. **연동 경로의 403·409를 세션 만료로 처리하지 않습니다**(로그아웃·토큰 재발급을 트리거하지 않음).
- **인앱 브라우저 차단 (웹 전용)** — 연동은 재인증·연동 두 단계 모두 OAuth라 Google 인증이 반드시 끼는데 인앱 WebView는 Google이 막습니다. 인앱에서 연동 버튼을 누르면 플로우를 시작하지 않고 "계정 연동은 외부 브라우저에서만 할 수 있어요" 토스트로 안내합니다(로그인의 핸드오프 경로는 재사용하지 않습니다 — 연동은 기존 세션 유지가 전제). 앱에는 인앱 브라우저 개념이 없어 이 항목이 적용되지 않습니다.

**회원 모드 데이터 소스** — 스토리·채팅은 `GET /users/me/stories`·`GET /users/me/chats`가 정본입니다. 생성·삭제 후 서버 결과를 반영하고, 같은 계정으로 다시 로그인해도 서버 서재를 유지합니다.

**로그아웃** — 서버 로그아웃과 플랫폼의 세션 종료 절차를 수행합니다. 이전 계정의 토큰·프로필·진행 결과가 다음 계정에 노출되거나 늦은 응답으로 되살아나지 않아야 합니다. 보존할 제작 데이터는 소유 계정에 격리하고, 플랫폼별 정리 범위는 해당 스펙·설계가 소유합니다.

**회원 탈퇴**  — 회원은 마이 페이지 계정 섹션의 "회원 탈퇴"에서 `/my/account-deletion`으로 이동합니다. 게스트가 경로에 직접 진입하면 `/login`으로 보냅니다. 화면은 뒤로가기 헤더("회원 탈퇴")와 확인 목록, 하단 위험색 CTA로 구성합니다.

- **사전 확인** — 제목은 "탈퇴하기 전에 / 아래 내용을 모두 확인해주세요", 설명은 "모든 항목을 확인해야 탈퇴할 수 있어요"입니다. 사용자는 잔여 이프 소멸, 기존 서재 복구·이전 불가, 공개 콘텐츠 잔존 가능성, 같은 소셜 계정으로 재로그인해도 기존 계정이 복구되지 않음을 각각 체크해야 합니다. 현재 카피의 코드 정본은 `manyak-web/src/features/my/account-deletion/constants.ts`입니다.
- **CTA 상태** — 네 항목을 모두 체크하기 전에는 "회원 탈퇴하기"를 비활성화합니다. 요청 중에는 "회원 탈퇴 중" 스피너를 표시하고 버튼을 잠가 중복 요청을 막습니다.
- **성공** — `DELETE /users/me`가 `204`를 반환하면 계정은 탈퇴 상태가 되고 소셜 연결·프로필이 제거되며 닉네임이 익명화됩니다. 잔여 이프와 비공개 서재는 복구하거나 새 계정으로 옮길 수 없습니다. 공개 스토리는 익명화된 작성자로 남고 공유 채팅은 기존 링크로 계속 열람할 수 있습니다. 클라이언트는 사용자 쿼리 캐시·분석 사용자 식별자를 정리하고 제작 데이터는 플랫폼의 계정 격리·정리 범위를 따르며 플랫폼 세션을 종료하고 해당 플랫폼의 비로그인 화면으로 이동합니다.
- **실패** — 5xx·네트워크 오류면 "회원 탈퇴에 실패했어요" 토스트를 표시하고 체크 상태와 현재 화면을 유지해 재시도를 허용합니다. 401로 세션 만료가 확정되면 플랫폼의 전역 세션 만료 흐름을 따릅니다. 탈퇴 성공 뒤 세션 종료 과정에서 이미 무효화된 refresh 토큰의 백엔드 로그아웃이 실패해도 플랫폼 로컬 세션 정리는 계속합니다.

**검수 기준**

- 게스트가 스토리 2개를 만들고 로그인하면 회원 서재에 같은 2개가 보여야 합니다. (US-9-3)
- 같은 계정으로 다른 기기·클라이언트에서 로그인하면 같은 서재가 보여야 합니다. (US-9-4)
- 로그아웃 후 재로그인해도 서재가 유지돼야 합니다. (US-9-5)
- 마이그레이션 API 실패가 로그인 완료를 막지 않아야 합니다.
- 손상된 로컬 ID가 있어도 유효 ID는 이관되고, 손상 ID로 인한 매 진입 반복 실패가 없어야 합니다.
- 회원 상태에서 만든 스토리·채팅은 로컬 목록이 아니라 서버 목록에 나타나야 합니다.
- 회원 서재 조회가 401이면 재발급 후 성공하거나, 재발급 실패 시 재로그인을 안내해야 합니다.
- 회원의 마이 페이지에 현재 연동된 provider가 Chip으로, 미연동 provider가 연동 버튼으로 보여야 합니다. 둘 다 연동한 계정에는 연동 버튼이 없어야 합니다.
- 연동 버튼을 누르면 확인 다이얼로그가 먼저 뜨고, 재인증이 현재 provider로 진행된다는 것과 해제할 수 없다는 것을 알려야 합니다.
- 다른 마냑 계정에 이미 연결된 소셜 계정을 연동하면 토스트가 아니라 다이얼로그로 상황과 대처를 안내해야 합니다.
- 연동에 실패해도 로그인 세션이 풀리지 않아야 합니다.
- 회원 탈퇴 확인 네 항목을 모두 체크하기 전에는 CTA가 비활성화되고, 모두 체크하면 활성화돼야 합니다. (US-9-11)
- 회원 탈퇴 성공 뒤 계정 캐시와 세션이 남지 않고 `/my`의 게스트 상태로 복귀해야 합니다. 실패하면 확인 화면과 체크 상태를 유지해 재시도할 수 있어야 합니다. (US-9-11)
- 잔액 부족 회원의 소모 요청은 이프 부족 토스트를, 한도 소진 게스트는 로그인 바텀 시트를 봐야 합니다. 스토리 제작 입력은 유지하고 실패한 채팅의 낙관적 버블은 제거해야 합니다. (US-10-4, US-10-5)
- 이프 충전의 무료 충전 탭에서 출석체크를 같은 날 두 번 누르면 두 번째는 적립 없이 비활성 상태가 보여야 합니다. (US-10-2)
- 이프 충전에서 탭 패널을 끝까지 스크롤해도 잔액 상자와 탭 줄이 화면에 남아야 합니다.
- `/login`에 이관 1회 안내와 약관·개인정보 처리방침 동의 고지가 표시되고, 밑줄 링크가 각각 `/terms`·`/privacy`(FE-SCREEN-010)를 새 브라우저 탭에서 열어야 합니다.
- 마이 페이지 헤더와 하단 네비게이션은 `마이`라는 접근 가능한 이름을 사용해야 합니다.
- 초대 코드 등록 중에는 버튼 문구 대신 중앙 스피너가 표시되고 입력이 잠겨야 합니다. 신규 가입 온보딩에서는 등록·"닫기" 버튼이 함께 잠겨야 합니다.

### FE-SCREEN-009. 일반 제작·스토리 수정

| 항목    | 값                                                          |
| ------- | ----------------------------------------------------------- |
| 관련 US | US-3-15, US-3-16, US-4-5                                    |

**목적** — 제작 폼에 스토리 구성 항목을 직접 입력해 등록하고(일반 제작), 같은 폼으로 기존 스토리를 수정합니다.

**폼 구성** — 섹션 아코디언 구조. 필수: 기본 정보(제목·한 줄 소개·장르), 스토리 설정(세계관·등장인물·주인공·규칙 — 섹션별 텍스트 입력을 통글 마크다운으로 조립해 전송), 시작 설정(이름·프롤로그·시작 상황), 추천 입력 3개. 선택: 주요 사건(최대 10 — 이름·설명·키 문장), 엔딩(시작 설정당 최대 10 — 각 이름·조건(`minTurns`+달성 조건)·에필로그). 주요 사건·엔딩은 저장 후 채팅 런타임(목표 진행·엔딩 판정·선택지 구성)에 반영됩니다([`4-backend-server-spec.md §4-3-10`](4-backend-server-spec.md)) — 런타임 동작 자체는 채팅 화면([§3-1-5](#3-1-5-채팅-플레이와-sse-스트리밍))의 검수 대상입니다.

- **이미지 입력은 없습니다**(B10 — [`4-backend-server-spec.md §4-3-9`](4-backend-server-spec.md)). 스토리 이미지는 전부 팀이 사전 제작해 서버가 자동 연결하며, 사용자가 업로드하거나 선택하는 폼 섹션·업로드 API를 두지 않습니다.
- (B14) — 시작 설정은 여러 개(`startSettings[]`, 1개 이상) 등록할 수 있고, 엔딩은 시작 설정별로 입력합니다([`4-backend-server-spec.md §4-3-8`](4-backend-server-spec.md)).

**동작** — 등록: `POST /stories/general` → 성공 시 스토리 상세로 이동("스토리가 등록됐어요" 토스트). 수정: 진입 시 `GET /stories/{storyId}/edit`로 편집 가능 필드 전체를 조회해 폼을 채우고, 변경 필드만 `PATCH /stories/{storyId}`로 전송 → 성공 시 상세로 복귀. 검증 실패(400)는 `details`의 필드별 사유를 해당 섹션에 인라인 표시합니다.

**검수 기준**

- 일반 제작으로 등록한 스토리가 기본 메타·스토리 설정·시작 설정 기준으로 상세·채팅 시작에서 간편 제작 산출물과 동일하게 동작해야 합니다. (US-3-15)
- 제작 화면에서 간편 제작은 `/studio/story/simple`, 일반 제작은 `/studio/story/general`로 진입할 수 있어야 합니다. (US-3-16)
- 수정 전용 조회가 폼 필드를 채울 수 있어야 하고, 수정 후 스토리 상세와 같은 스토리 설정을 참조하는 진행 중 채팅의 다음 턴에 새 설정이 반영돼야 합니다. (US-4-5)
- 폼 작성 중 이탈 후 복귀하면 작성 내용이 복원돼야 합니다.
- 타인 소유 스토리와 로컬 서재에 없는 게스트 스토리에는 수정 진입점이 보이지 않아야 합니다.

### FE-SCREEN-010. 서비스 이용약관·개인정보 처리방침

| 항목    | 값                                                                                              |
| ------- | ----------------------------------------------------------------------------------------------- |
| 관련 US | US-9(로그인·회원 전환)                                                                          |

**목적** — 서비스 이용약관과 개인정보 처리방침 전문을 열람합니다. 서비스 이용 대상은 만 14세 이상이며 두 문서에 같은 제한을 고지합니다.

**콘텐츠 동일성 계약** — 모든 플랫폼에서 같은 시행일·버전·본문을 표시합니다. 로그인 전에도 열람할 수 있으며, 로그인 화면과 서비스 안내에 진입점을 둡니다. 콘텐츠 정본·공급 방식은 [웹 설계](../design/1-1-web-design.md#법적-콘텐츠-소스-웹)가 소유합니다.

**동의 모델** — 로그인 버튼 클릭을 이용약관·개인정보 처리방침 동의로 간주한다는 고지를 표시합니다. 별도 동의 체크박스는 두지 않습니다. 개정 시 재동의 절차는 이 계약에서 정하지 않습니다. 광고성 정보 수신 동의(정보통신망법 제50조)는 이 간주 동의에 포함되지 않으며, 처리방침의 광고성 정보 수신 동의(선택) 절을 고지 정본으로 두고 Android 앱이 [알림 계약](3-3-android-spec.md#3-3-5-알림)에 따라 별도 시트로 받습니다. 웹은 푸시를 보내지 않아 동의를 받지 않습니다.

**검수 기준**

### FE-SCREEN-011. 서비스 안내

**목적** — AI 콘텐츠 특성·문의·정책 정보를 안내하고 약관·개인정보 처리방침의 상시 열람 경로를 제공합니다. 마이의 기타 섹션에서 피드백 위에 서비스 안내를 둡니다.

**검수 기준**

## 3-1-4. 스토리 생성 퍼널

### 단계 구성

단계는 **키워드 선택 → 스토리라인 선택 → 추가 정보**입니다. 세 단계의 진행 표시기를 동일 너비로 표시합니다. 완료는 편집 단계가 아니며 제출 이후의 상태입니다. 제출 이후 이동은 플랫폼별 적용 계약을 따릅니다.

| #   | 단계            | 목적                                            | 진행(다음) 조건                          |
| --- | --------------- | ----------------------------------------------- | ---------------------------------------- |
| 1   | 키워드 선택     | 장르·주인공·주변 인물 키워드 수집               | 장르 1개 이상 **그리고** 주인공 1개 이상 |
| 2   | 스토리라인 선택 | AI 생성 스토리라인 3개 중 택1(선택·재생성·평가) | 활성 스토리라인 선택 완료                |
| 3   | 추가 정보       | 추천 태그·자유 텍스트로 디테일 보강             | 생성 ID와 선택 스토리라인 ID 존재        |

### 키워드 선택 규칙

| 카테고리       | 탭 라벨        | 필수   | 상한                        | 직접 추가 |
| -------------- | -------------- | ------ | --------------------------- | --------- |
| 장르           | 장르           | 예     | 키워드 3개                  | 가능      |
| 주인공 특징    | 주인공 (나)    | 예     | 인물 1명, 특징 3개          | 가능      |
| 주변 인물 특징 | 주변 인물      | 아니오 | 인물 5명, 인물마다 특징 3개 | 가능      |

- 카테고리 탭은 화면 가로폭을 3등분하는 라인 탭입니다. 탭 행 컨테이너의 위·아래에 별도 내부 여백을 두지 않고, 선택 탭의 검은 선은 미선택 탭의 회색 기준선과 같은 높이에서 기준선을 덮습니다. 탭 아래 별도 설명 문구는 두지 않습니다.
- 각 카테고리 콘텐츠에는 칩 목록 위에 섹션 라벨을 둡니다(장르 탭 "장르 (최대 3개)", 인물 탭 "특징 (최대 3개)"). 장르·주인공 콘텐츠는 탭 기준선 아래 16px에서 시작하고, 탭 패널 하단은 32px를 확보합니다.  필수 카테고리(장르·주인공)의 라벨에는 `*`를 붙입니다.
- 태그 목록은 API로 조회하며, 로딩 시 스켈레톤 칩을 표시합니다.
- 상한에 도달하면 미선택 칩과 "키워드 추가" 트리거를 비활성화합니다(제공 태그·직접 추가 합산). 주변 인물이 5명이면 "인물 추가"도 비활성화합니다.
- 필수 카테고리의 "다음" 버튼은 선택 전에도 활성화합니다. 선택 없이 누르면 이동하지 않고 버튼 위 푸터에 "키워드를 하나 이상 선택해주세요"를 표시합니다. 오류가 생길 때만 푸터가 메시지 높이만큼 늘어나며, 해당 카테고리에서 키워드를 선택하면 오류를 제거합니다.
- 커스텀 키워드는 "키워드 추가" 다이얼로그로 입력합니다. "추가하기" 버튼은 빈 입력에서도 활성화하고, 빈 값으로 누르면 입력창 아래에 "키워드를 입력해주세요"를 표시합니다. 유효한 값을 입력하거나 다이얼로그를 닫으면 오류를 제거합니다. 클라이언트 최대 15자(서버 스키마 30자), IME 조합 중 Enter는 제출하지 않습니다. 세 카테고리 모두 직접 추가할 수 있으며, 요청에서 장르는 `customGenreTags`, 인물은 각 인물의 `customTags`로 나갑니다([`4-backend-server-spec.md §4-3-2`](4-backend-server-spec.md)).
- 카테고리 탭은 앞선 필수 카테고리가 완료되어야 잠금 해제됩니다.

#### 인물 단위 입력

주인공과 주변 인물을 특징 태그 묶음이 아니라 인물 단위로 입력받습니다. 두 탭은 같은 폼을 씁니다.

- **폼 구성** — 세로로 `기본 정보`(이름 인풋 + 성별 셀렉트를 3:2 비율로 배치) → `특징`(제공 태그 칩 + "키워드 추가") 순입니다. 기본 정보 아래에 "비워두면 랜덤으로 설정해요"를 두어 선택 항목임을 알립니다. 특징 라벨의 `*`는 주인공 탭에만 붙고, 특징이 선택 항목인 주변 인물은 칩 아래에 "선택하지 않으면 랜덤으로 설정해요"를 둡니다.
- **이름** — 직접 입력이며 클라이언트·서버 모두 30자 상한입니다. 인풋 오른쪽에 입력 글자 수를 표시합니다.
- **성별** — 셀렉트이고 기본값은 "랜덤 성별"입니다. 랜덤은 고르지 않은 상태와 같아 요청에 `null`로 나가고 AI가 정합니다.
- **주변 인물 목록** — 퍼널 진입 시 빈 인물 1명이 놓여 있고, 각 인물은 전체 폭의 중립색 헤더와 좌우 16px 여백의 폼으로 구성합니다. 헤더에는 14px의 입력 이름(비어 있으면 "주변 인물 N"), 현재 순번을 나타내는 12px `N/5` 필, 14px의 텍스트형 "삭제"를 표시합니다. 순번 필은 헤더보다 한 단계 진한 중립색 배경으로 구분합니다. 카드 테두리는 두지 않습니다. 삭제로 0명까지 줄일 수 있고, 목록 아래 가운데의 "인물 추가"로 5명까지 늘립니다. 추가 직후 새 이름 인풋이 화면 중앙에 오도록 부드럽게 스크롤하되 자동으로 초점을 옮기지 않아 모바일 키보드는 열지 않습니다. 항목을 채우지 않은 폼도 인원으로 집계됩니다(빈 폼 3개 = 주변 인물 3명).
- **이름 중복 금지** — 한 스토리 안에서 주인공과 주변 인물의 이름은 겹칠 수 없습니다. AI가 이름 글자로 인물의 등장 여부를 확인하기 때문입니다. 판정 키는 서버와 같습니다 — NFC 정규화 → 공백 제거 → 소문자([`4-backend-server-spec.md §4-3-2`](4-backend-server-spec.md)). 먼저 쓴 이름을 남기고 뒤에 겹친 인물의 이름 인풋에 "이미 사용한 이름이에요"를 즉시 표시하고, 그 상태에서 "스토리라인 만들기"를 누르면 요청을 보내지 않고 푸터에 "인물 이름이 겹치지 않게 해주세요"를 표시합니다. 비워 둔 이름은 AI가 각각 지어 주므로 판정 대상이 아닙니다. 서버도 400으로 막습니다([`4-backend-server-spec.md §4-3-2`](4-backend-server-spec.md)).

### 스토리라인 생성·평가

- **선택 UI** — 생성된 3개 결과는 키워드 단계와 같은 전체 폭 3등분 라인 탭("첫 번째"·"두 번째"·"세 번째")으로 전환합니다. 탭 컨테이너에는 위·아래 내부 여백을 두지 않고 선택선은 회색 기준선과 같은 높이에서 덮습니다. 본문은 탭 기준선 아래 16px에서 시작하고 패널 하단은 32px를 확보합니다. 스토리라인 본문과 추가 정보 단계의 선택 스토리라인 요약은 16px MaruBuri, 자간 -2%, 행간 175%(28px)를 함께 사용합니다. 하단 푸터에는 위·좌·우 여백 없이 앱 프레임 전체 폭을 채우는 높이 40px의 각진 중립색 "선택한 키워드 보기" 버튼을 두고, "다시 만들기"·"선택하기" 행과는 8px 간격으로 구분합니다. 라벨은 보조 전경색으로 표시합니다. 누르면 기존 선택 키워드 드로어를 열며 장르·주인공·주변 인물 등 키워드 그룹 사이는 24px로 구분합니다.
- **생성** — `POST /stories/simple/storylines {genreTagIds, customGenreTags, protagonist, supportingCharacters}`. 인물 객체는 `{name, gender, featureTagIds, customTags}`이고 비워 둔 이름·성별은 `null`로 보냅니다. 클릭 직후 "스토리라인 만들기" 버튼을 비활성화하고 문구 공간을 유지한 중앙 스피너를 표시하며, 동시에 스토리라인 선택 단계로 전환해 로딩 화면을 렌더합니다. 응답은 스토리라인 3개와 생성 ID(`simpleCreationId`)를 포함합니다. 로딩 중에는 타자기형 문구와 15·30초 시점 힌트를 표시합니다.  — 회원은 무료이고, 게스트의 체험 한도·카운터는 웹 스펙을 따릅니다.
- **재생성** — "다시 만들기"는 저장된 생성 요청을 재호출합니다. 생성 요청 이벤트는 최초 1회만 발화합니다.  익명 체험의 선차단은 웹 스펙을 따릅니다.
- **평가** — 스토리라인별 좋아요·별로예요를 토글합니다. 300ms 디바운스 후 설정(`PUT`)·해제(`DELETE`)로 동기화합니다. 동일 평가를 다시 누르면 해제되고, 실패 시 상태를 되돌리고 실패 토스트를 표시합니다. **평가는 보조 신호이며 완성 페이로드에 포함되지 않고 진행을 막지 않습니다.**

### 추가 정보 진입·스토리라인 재선택

- 추가 정보 단계의 선택 스토리라인은 첫 렌더부터 한 줄로 접고 **더보기/접기 토글을 항상 렌더링**합니다. 내용 길이를 측정한 뒤 토글을 제거하지 않아 짧은 스토리라인에서도 첫 렌더 레이아웃이 움직이지 않아야 합니다.
- 추천 추가 정보 목록과 자유 입력 영역 사이는 32px로 구분하고 자유 입력 패널 하단도 32px를 확보합니다. 자유 입력 영역의 제목 행은 기본 전경색의 `추가 정보 (최대 10개)`로 표시하고, `입력`이라는 중복 설명은 붙이지 않습니다. "정보 추가" 직후 새 입력 행이 화면 중앙에 오도록 부드럽게 스크롤하되 자동으로 초점을 옮기지 않아 모바일 키보드는 열지 않습니다. 키보드 Tab 이동 순서는 웹 스펙을 따릅니다.
- 추가 정보 단계 하단 푸터에는 CTA 행 바로 위에 앱 프레임 전체 폭을 채우는 높이 40px의 각진 중립색 비용 행을 둡니다. 왼쪽에는 보조 전경색으로 `스토리 완성 비용`, 오른쪽에는 기본 전경색의 굵은 `N 이프`를 표시하고 CTA 행과는 8px 간격으로 구분합니다. N은 서버 정책의 `storyCreationCost`이며([§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시)), 문구는 이 절이 소유합니다.
- 추가 정보나 추천을 아직 고르지 않은 상태에서 "다시 선택하기"를 누르면 경고 없이 스토리라인 선택 단계로 돌아갑니다. 공백만 있는 자유 입력과 처음부터 놓인 빈 입력 행은 작성한 정보로 보지 않습니다.
- 공백이 아닌 자유 입력 또는 선택한 추천이 하나라도 있으면 `스토리라인을 바꿀까요? / 입력한 추가 정보는 모두 사라져요` 경고를 표시합니다. `닫기`는 단계·스토리라인·입력·추천을 모두 유지합니다. 파괴적 스타일의 `다시 선택하기`를 확정하면 선택 스토리라인, 자유 입력 전부, 추천 선택 전부를 초기화하고 스토리라인 선택 단계로 돌아갑니다.

### 완성 제출과 복구

- 키워드·추가 정보의 검증을 통과한 요청만 전송합니다. 같은 요청의 재시도에는 같은 `requestId`와 명령을 사용합니다.
- 생성·완성 요청은 전송 전에 복구 가능한 형태로 저장합니다. 저장 실패를 제출 성공으로 표시하지 않습니다.
- 서버 결과를 받지 못한 경우 확정 실패와 구분하고, 복구 조회로 결과를 확인합니다. 백그라운드에서 화면용 폴링을 계속하지 않습니다.
- 사용자 편집·요청 전환·서버 결과 반영은 오래된 저장이 새 요청을 덮지 않도록 처리합니다. 저장 구조와 직렬화 수단은 플랫폼 설계가 소유합니다.
- 로그아웃·계정 변경 후 이전 계정의 제작 내용을 다른 계정에 표시하거나 이전 작업 결과를 새 세션에 반영하지 않습니다.

### 제작 카드와 다중 완성 진행

이 절은 초안과 완성 요청을 분리하는 계약입니다. Android의 적용 동작은 [Android 제작 계약](3-3-android-spec.md#제작과-데이터-보존), 웹 단일 슬롯 흐름의 적용 범위는 [웹 제작 계약](3-2-web-spec.md#웹-제작-흐름)이 소유합니다.

- 편집 중 초안 한 개와 여러 완성 요청을 독립적으로 표시합니다. 새 제작·초안 삭제는 완성 요청을 지우지 않습니다.
- 제출 요청을 영속화한 뒤에는 완성 응답을 기다리지 않고 제작 탭으로 돌아옵니다. 자동으로 채팅방을 만들거나 채팅 화면에 진입하지 않습니다.
- 저장 실패 시 전송하지 않고 입력을 유지한 채 오류를 안내합니다. 제출 연타로 같은 요청이 중복 생성되지 않습니다.
- 완성 중 요청과 완성 스토리를 구분합니다. 서버 스토리와 같은 `storyId`의 로컬 완료 항목을 이중 표시하지 않습니다.
- 완료된 스토리는 상세 화면을 거쳐 사용자가 채팅을 시작합니다. 실패 카드의 재시도·삭제·편집 복귀 정책은 [확인 항목](../planning/client-tracking.md#계약-확인-항목)에서 관리하며 이 절에서 확정하지 않습니다.

### 검수 기준

- 저장 실패에는 요청을 보내지 않고 입력을 유지합니다.
- 같은 요청의 재전송은 중복 스토리를 만들지 않으며, 불명확한 응답은 복구 조회 결과와 일치시킵니다.
- 초안 삭제·새 제작은 다른 완성 요청에 영향을 주지 않습니다.
- 플랫폼의 제출 후 목적지·이탈·저장 계약을 충족하고, 계정 변경 뒤 다른 회원의 데이터가 노출되지 않습니다.

## 3-1-5. 채팅 플레이와 SSE 스트리밍

FE-SCREEN-005의 상세입니다. 실시간 AI 출력이 이 앱에서 가장 복잡한 경로이므로 스트리밍 계약과 렌더 규칙을 명확히 정의합니다.

### 턴 모델

- 채팅은 스토리 상세 또는 퍼널 완료에서 `POST /chats {storyId, startSettingId}`로 생성됩니다(`startSettingId`는 상세에서 선택한 시작 설정, 생략 시 첫 번째). 채팅 목록에서는 생성하지 않습니다.
- **턴** = 사용자 입력 + AI 출력 + 다음 선택지입니다. 사용자 입력과 AI 출력은 응답이 완료될 때 한 턴으로 저장됩니다.
- 채팅 화면은 `GET /chats/{id}`로 스토리 제목·프롤로그·턴 목록·추천 입력을 조회합니다.
- 렌더 순서: 프롤로그 버블 → 각 턴(사용자 버블 → AI 버블) → 진행 중 스트리밍 블록.
- 선택지는 **마지막 턴에만** 표시합니다. 턴이 0개면 시작 화면의 추천 입력을 선택지로 표시합니다.

### SSE 스트리밍 계약

채팅 턴은 사용자 입력을 본문에 실은 `POST` 요청의 응답을 SSE로 받습니다([백엔드 계약](4-backend-server-spec.md)). 수신·파싱 수단은 각 플랫폼 설계가 소유합니다.

- **요청** — `POST /chats/{id}/turns/stream`, 헤더 `Accept: text/event-stream` + `X-Manyak-*` 식별자, 본문 `{userInput}`(서버 검증 상한 3000자, 프론트는 별도 차단 없음).
- **이벤트 계약** (원천: [`4-backend-server-spec.md §4-3-3`](4-backend-server-spec.md))

| 이벤트          | 데이터 필드          | 프론트 처리                                                                                                                                   |
| --------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `started`       | —                    | 수신만(무동작)                                                                                                                                |
| `token`         | `text`               | 현재 위치의 텍스트 조각에 누적해 부분 렌더                                                                                                    |
| `character_image` | `name`, `imageUrl` | . 이벤트를 받은 즉시 현재 스트리밍 위치에 인물 이미지 조각을 추가. 같은 이벤트가 다시 오면 이미지도 다시 추가      |
| `completed`     | `chatId`, `turnId`, `aiOutput`, `choices`, `reachedEnding` | 상세 refetch로 확정 턴을 받은 뒤 진행 중 조각 목록과 한 번에 교체. 클라이언트는 `completed`의 별도 이미지 목록에 의존하지 않음 |
| `error`         | `message`            | 실패 토스트                                                                                                                                   |

- `token`은 `data: {"text":"..."}`(JSON) 또는 원문 텍스트를 모두 허용합니다.
- **스트리밍 순서의 정본은 이벤트 도착 순서입니다** 진행 중 AI 출력은 하나의 문자열이 아니라 순서가 있는 `text | character_image` 조각 목록으로 관리합니다. `token`은 마지막 조각이 텍스트면 그 조각에 이어 붙이고, `character_image`는 현재 위치에 새 이미지 조각을 추가하며, 그다음 `token`은 이미지 뒤의 새 텍스트 조각으로 시작합니다. AI 서버는 이미지가 있는 인물의 `이름:` 토큰보다 `character_image`를 먼저 보내므로, 클라이언트는 이미지 → 인물명 → 대사 순서를 그대로 표시합니다. 이름 기준 정렬·중복 제거·`completed`까지 표시 지연은 금지합니다.
- **인물 이미지가 먼저 나온 뒤 턴이 실패한 경우** 이미지도 텍스트 토큰과 같은 미확정 스트리밍 결과입니다. `error` 이벤트가 오면 낙관적 사용자 버블과 진행 중 텍스트·이미지 조각을 함께 제거합니다. `completed`·`error` 없는 EOF는 서버 저장 여부를 알 수 없으므로 기존 EOF 규칙대로 상세를 refetch하고, 저장된 턴이 있으면 확정 `aiOutput`의 `[[URL]]` 마커로 복원하며 없으면 진행 중 조각을 제거합니다. 실패한 턴의 이미지만 화면에 남겨 확정 이력처럼 보이게 하지 않습니다.
- `completed` 수신 시 진행 중 조각을 즉시 지우지 않습니다. 상세 재조회가 성공한 프레임에 서버 확정 턴의 조각 목록으로 한 번에 교체해, 본문·이미지가 사라졌다 다시 나타나거나 URL 마커가 한 프레임 노출되지 않게 합니다. 완료 후 채팅 목록을 무효화해 미리보기·시각을 갱신합니다.
- 클라이언트와 백엔드 사이의 전달 계층은 SSE 청크를 버퍼링하지 않아야 합니다(웹: BFF 프록시 스트리밍 통과 — [`1-1-web-design.md §1-1-3`](../design/1-1-web-design.md#1-1-3-bff-프록시토큰-세션)).
- **타임아웃** — 백엔드 쪽 상한은 두 층이고 종료 모양이 다릅니다(값·근거의 정본은 [`4-backend-server-spec.md §4-3-3`](4-backend-server-spec.md)): 클라이언트향 SSE **전체 상한**을 넘기면 `error` 이벤트 **없이** 스트림이 닫히고(클라이언트는 EOF로 관측 — 위 예외 처리), 백엔드→AI의 **이벤트 간 idle** 상한을 넘기면 `AI_STREAM_FAILED` `error` 이벤트가 옵니다. 클라이언트의 연결·읽기 제한은 플랫폼 설계가 소유하고, 웹의 추가 시간 상한 검토는 [추적 G5](../planning/client-tracking.md#기존-간극의-처리)에 연결합니다.

### 입력창과 선택지

- **입력 모드** — 일반 텍스트 모드와 블럭 모드(상황·대사)를 제공합니다. 두 모드는 같은 전송·추천 입력 규칙을 사용합니다. 블럭의 X(입력 삭제) 버튼은 탭 순서에서 제외해 키보드 포커스가 블럭 인풋 사이를 바로 오가게 합니다(터치·클릭으로는 계속 삭제 가능).
- **입력이 있을 때** — 전송 버튼에 위쪽 화살표 아이콘을 표시합니다. 공백 제거 후 1자 이상이고 스트리밍 중이 아닐 때 `Enter`(Shift 없이, IME 조합 아님)·폼 제출·버튼으로 전송합니다. 일반 모드 텍스트에어리어는 최대 `20dvh`까지 자동 확장합니다.
- **입력이 없을 때** — 현재 추천 입력이 1개 이상이면 전송 버튼을 filled 재생 아이콘으로 표시하고 활성화합니다. 누르면 현재 추천 입력 중 하나를 무작위로 골라 즉시 전송합니다. 추천 입력도 없으면 같은 아이콘을 유지한 채 버튼을 비활성화합니다.
- **채팅 턴 이프 비용** — 회원에게는 전송 버튼 바로 왼쪽 8px 위치에 `N 이프`(서버 정책의 `chatTurnCost` — [§3-1-7 이프 정책 수치 표시](#이프-정책-수치-표시))를 12px 보조 전경색으로 표시합니다. 블럭·일반 입력 모드와 위쪽 화살표·랜덤 전송·응답 대기 스피너 상태에서 같은 위치를 유지합니다. 게스트는 이프가 아니라 체험 턴 수를 사용하므로 이 문구를 표시하지 않습니다.
- **응답 대기 스피너** — 스트리밍 중에는 전송 버튼의 아이콘(화살표·재생 공통)을 스피너로 바꿔 응답을 받는 중임을 알립니다(스크린 리더 라벨 "응답을 받는 중"). 두 입력 모드와 응답 재생성에 동일하게 적용하며, 완료·실패로 스트리밍이 끝나면 원래 아이콘으로 돌아옵니다. 버튼은 스피너 표시 중에도 전송 잠금 규칙대로 비활성 상태입니다.
- **추천 입력 소스** — 턴이 0개면 상세 응답의 `suggestedInputs`, 턴이 있으면 마지막 턴의 `choices`를 사용합니다.
- **선택지** — 각 선택지에 "채우기"(입력창에 채워 편집)와 "전송"(바로 제출) 버튼을 둡니다. 추천 입력 목록은 컨테이너 위에서 12px 띄우고 항목끼리는 8px 간격을 둡니다. 본문은 14px MaruBuri, 자간 -2%, 행간 175%(24.5px)를 사용합니다. 바로 전송 시 상황(`*...*`)과 대사를 빈 줄로 구분해 정규화한 뒤 전송합니다(블럭 입력 전송과 동일한 포맷). **등장은 항목이 차례로 흐르는 모션입니다** — 각 항목이 8px 아래에서 300ms(ease-out) 동안 올라오며 나타나고 항목마다 80ms씩 늦게 출발하며, 1회성 인라인 힌트도 첫 항목으로 셉니다. 로딩 스켈레톤과 생성 실패 안내도 같은 모션을 씁니다(실패 안내는 한 덩이로). 같은 묶음은 한 번만 흐릅니다 — 목록이 길어 추천이 화면 밖으로 나갔다 돌아와도 다시 흐르지 않고, 스켈레톤 → 추천처럼 내용이 바뀐 때만 다시 흐릅니다.
- **블럭 순번과 개수 상한** — 블럭 모드의 각 입력 라벨에 종류별 순번을 붙입니다("상황 1", "대사 1"). 순번 자리는 두 자리 폭으로 미리 잡아 한 자리에서 두 자리로 넘어가도 입력 글자의 시작 위치가 밀리지 않습니다. 같은 종류가 여럿일 때 방금 늘어난 칸이 어느 것인지 라벨만 보고 알 수 있게 하는 표시이며, 순번은 화면 표시 전용이라 전송 본문에는 싣지 않습니다. 블럭은 상황·대사를 합쳐 **최대 50개**이고, 상한에 닿으면 두 추가 버튼을 비활성화합니다. 모드 전환·추천 채우기로 파싱된 블럭은 상한을 넘을 수 있습니다 — 문장을 잘라 버리지 않기 위해 파싱 결과는 그대로 두고 추가 버튼만 잠급니다. 칸을 더하면 아래에서 자라 오르고 지우면 같은 변을 붙잡은 채 접히며, **목록이 높이 상한에 걸려 스크롤 중이면 더한 칸이 보이도록 끝까지 따라 내려갑니다** — 접힌 자리에 생기면 추가가 일어났는지 보이지 않습니다. 모드 전환·추천 채우기·전송 뒤 초기화처럼 목록 전체가 갈리는 경로는 칸별 모션 없이 한 번에 교체합니다.
- **강조 삽입** — "상황 추가" 버튼이 선택 영역을 `*...*`로 감쌉니다.
- **전송 잠금** — 스트리밍 중에는 컴포저·입력창·버튼이 모두 비활성화됩니다(전송 버튼은 비활성 상태로 스피너를 표시).
- **추천 입력 토글** — 선택지(추천 입력) 생성을 응답 스트림에서 분리합니다([`4-backend-server-spec.md §4-3-3`](4-backend-server-spec.md)). 인풋 애드온 줄(입력 모드 메뉴 왼쪽)에 추천 입력 on/off 드롭다운 메뉴(AI 말풍선 아이콘 트리거)를 둡니다 — 켬/끔 라디오 항목(라벨+설명)에서 선택하고, on이면 트리거 아이콘을 primary 색으로 표시합니다. 토글 on이면 `completed` 수신·상세 refetch(본문 확정) 후 선택지 생성 API(`POST /chats/{id}/turns/{turnId}/choices`)를 호출합니다(본문 확정과 선택지 도착 사이의 지연은 허용). 응답 200은 저장 완료 신호이며 렌더 소스가 아닙니다 — 상세를 한 번 더 재조회해 마지막 턴 `turns[].choices`로 표시합니다(`completed`의 `choices`는 렌더 소스로 쓰지 않음). 토글 off면 호출하지 않으며, 표시 중이던 마지막 턴 선택지도 숨깁니다(빈 입력의 무작위 추천 전송 대상에서도 제외 — 서버 데이터는 유지되므로 다시 켜면 재호출 없이 재표시). off 상태로 턴이 끝난 뒤 토글을 켜면 같은 API로 마지막 턴의 선택지만 생성합니다. flag 없이 "API를 부르는가"로 on/off를 처리합니다. 토글 기본값은 on이고 변경값은 로컬 저장소에 기기 단위로 기억합니다(저장 수단·키는 플랫폼 소유 — 플랫폼 설계 참조). 선택지 생성은 무료이며 마지막 턴만·턴당 1회 멱등 계약입니다([`4-backend-server-spec.md §4-3-3`](4-backend-server-spec.md)). 선택지 로딩은 선택지 자리의 스켈레톤 칩 3개로 표시하고, 도착하면 교체합니다. 실패하면 선택지 자리에 에러 문구와 재시도 버튼을 표시하고, 재시도는 같은 API를 다시 호출합니다(선택지가 없어도 직접 입력으로 채팅은 계속 진행 가능).

### 첫 진입 안내

처음 채팅을 시작한 사용자에게 입력 영역 사용법을 안내합니다. 안내 대상은 진입 경로와 무관하게 생애 첫 채팅방 진입 사용자 전원이며, 온보딩 경유 여부는 따지지 않습니다.

- **노출 조건** — 기기에 열람 기록이 없고, 턴 0개(프롤로그와 첫 추천만 있는 상태)이며 스트리밍 중이 아닐 때 짧은 지연 뒤 1회 자동 노출합니다. 노출 시점에 열람 기록을 남깁니다. 조건을 만족하지 않는 방(이미 대화가 진행된 방)에서는 노출하지 않고 기록도 남기지 않습니다. 기기 단위 1회이며 **재열람 진입점은 두지 않습니다**. 로컬 저장소 접근이 막힌 환경에서는 기록이 남지 않아 진입마다 다시 노출될 수 있으며, 이는 허용합니다.
- **형태** — body로 포털되는 오버레이(딤 + 대상 컷아웃 하이라이트 + 말풍선 카드)입니다. 앱 프레임 내부가 아니라 다이얼로그와 같은 층에 그리므로 앱 프레임 안의 `fixed` 사용 제약([3-2-web-spec.md §3-2-4](3-2-web-spec.md#3-2-4-라우팅레이아웃공통-셸))에 걸리지 않습니다. 투어 중 뒤 화면 상호작용은 오버레이가 막고, "다음"으로 진행하며 언제든 "건너뛰기"로 닫을 수 있습니다.
- **카드 배치** — 카드는 뷰포트가 아니라 앱 프레임(`max-w-md`) 안에 둡니다. 기본은 하이라이트 중앙 정렬이고, 대상이 좌우 끝이라 중앙에 둘 수 없으면 그쪽 하이라이트 변에 카드 변을 맞춥니다(프레임 여백에만 맞추면 카드가 하이라이트보다 안쪽으로 들어가 어긋나 보이기 때문). 세로는 하이라이트 기준 남은 공간을 `max-height`로 걸어 문구가 길어져도 화면을 벗어나지 않습니다.
- **스텝(3개)** — ① 상황·대사 추가 버튼 ② 추천 입력 토글 + 입력 모드 메뉴 ③ 전송(랜덤) 버튼. 첫 스텝은 입력 모드에 따라 갈립니다 — 블럭 모드는 두 추가 버튼을 함께 잡아 "입력창이 하나 늘어난다"로, 일반 모드는 대사 추가 버튼이 없으므로 상황 추가 버튼만 잡고 강조 마커(`*...*`) 삽입 동작으로 안내합니다. 화면에 대상이 없는 스텝은 건너뛰고, 모든 스텝의 대상이 없으면 투어를 열지 않습니다.
- **추천 입력은 투어 대상이 아닙니다** — 추천 입력은 메시지 스크롤 영역 안에 있어 프롤로그가 길면 화면 밖으로 밀려나고, 그때 설명만 뜨고 대상이 보이지 않는 문제가 있었습니다. 대신 첫 추천 목록 바로 위에 **1회성 인라인 힌트**를 콘텐츠로 함께 렌더합니다(두 줄: "AI가 추천하는 입력이에요" / "탭하면 바로 전송되고, 연필 버튼으로 고쳐서 보낼 수 있어요"). 추천과 같이 스크롤되므로 위치가 어긋나지 않습니다. 노출 기록은 투어와 별도 플래그(웹 키: `manyak:chat-choices-hint-seen`)로 관리하며, 턴 0개 화면에서 노출된 순간 기록합니다(같은 방에 머무는 동안은 유지, 재진입부터 미노출).
- **계측** — 투어는 노출·스텝 도달·완주·건너뛰기 4종을 수집합니다([`6-analytics.md §6-4-2-6`](6-analytics.md)). 인라인 힌트는 별도 이벤트를 두지 않습니다.

### 렌더와 스크롤

- **부분 렌더** — `token`이 누적되는 동안 AI 버블에 실시간 텍스트를 표시하고, `character_image`가 오면 같은 버블의 해당 위치에 이미지를 즉시 표시합니다. 첫 표시 가능 이벤트(`token` 또는 `character_image`) 전에는 "작성 중" shimmer 로딩(스크린 리더 라벨 "답변을 작성하고 있어요")을 표시하고, 이미지가 먼저 오면 첫 토큰을 기다리지 않고 로딩을 이미지로 교체합니다.
- **본문 타이포그래피·패딩** — 프롤로그·사용자 입력·AI 출력은 16px MaruBuri, 자간 -2%, 행간 175%(28px)를 사용합니다. MaruBuri 자간과 행간은 웹 공통 스타일 한 곳에서 관리해 스트리밍 로딩·스토리 제작 본문·추천 입력에도 같은 비율을 적용합니다. 사용자·AI 메시지 영역은 위·아래 20px, 좌우 16px을 확보합니다.
- **강조 마크업** — `**볼드**`는 굵게, `*...*`는 서술·독백 강조로 렌더합니다.
- **진입 스크롤 위치** — 턴이 있는 방은 마지막 메시지 위치에서, 턴이 0개인 방은 프롤로그가 보이도록 상단에서 시작합니다.
- **새 턴 앵커** — 전송하면 새 턴(사용자 버블 + 스트리밍 블록)을 뷰포트 상단에 이전 메시지와의 여백 없이 밀착해 앵커하고, 텍스트·이미지 조각이 추가돼도 화면이 끌려 내려가지 않습니다. 스트리밍 중 사용자가 옮긴 스크롤 위치는 완료(상세 refetch) 후에도 유지됩니다.
- **하단 이동 버튼** — 스크롤이 하단에 있지 않으면 "맨 아래로 이동" 버튼을 표시합니다. 스트리밍 중에도 동일하게 동작합니다.
- **헤더 show/hide** — 상단 근처·위로 스크롤 시 표시, 아래로 스크롤 시 숨깁니다. 스크롤된 위치로 진입하면(마지막 메시지 앵커) 등장 없이 처음부터 숨긴 채 시작합니다. 숨긴 헤더는 보조기술·포커스 대상에서도 제외합니다(웹: `aria-hidden`·`inert`). 헤더 back은 채팅 목록으로 이동합니다.

### 입력 설정 메뉴와 삭제

입력 모드·추천 입력 설정은 입력 툴바의 드롭다운 메뉴에 두고, 채팅 삭제는 헤더 우측 옵션 메뉴(⋮)에 둡니다. 헤더 우측은 공유 버튼 + 옵션 메뉴 두 개이며, 공유 발급은 위 [채팅 공유하기](#채팅-공유하기)가 정의합니다.

- **입력 설정** — 입력 툴바(추가 버튼들 오른쪽)에 추천 입력 on/off 메뉴와 입력 모드 메뉴를 나란히 둡니다. 둘 다 라디오 항목(라벨 + 설명)으로 고르는 드롭다운이며, 상세 계약은 위 [입력창과 선택지](#입력창과-선택지)의 "추천 입력 토글"을 따릅니다.
- **옵션 메뉴** — 헤더 우측 ⋮ 버튼이 드롭다운을 열고, 항목은 "신고하기"(회원만,  — [FE-SCREEN-005](#fe-screen-005-채팅-화면)) → destructive "삭제하기" 순서입니다. 게스트에게는 삭제하기 하나만 보입니다.
- **삭제 흐름** — "삭제하기" → 확인 다이얼로그("채팅을 삭제할까요?") 표시 → 확정 시 낙관적 삭제([웹 사용자 모델](3-2-web-spec.md#웹-사용자-모델)과 동일 규칙: 204 완료 토스트, 404 무음 성공) 후 채팅 목록으로 이동합니다. 확정 버튼은 요청 중 문구 공간을 유지한 중앙 스피너("삭제 중")로 잠깁니다.
- 채팅 목록(FE-SCREEN-004)의 카드 옵션 다이얼로그도 같은 삭제 절차를 쓰되, 목록에서는 이동 없이 그 카드만 제거합니다.

### 응답 재생성과 채팅 이미지

응답 재생성은 , 배경 이미지는 , 인물 이미지는 입니다.

**재생성 버튼** — 마지막 턴의 AI 버블 하단에 "다시 생성" 버튼을 둡니다(US-6-10). 마지막 턴에만 표시하고, 스트리밍 중에는 전송 잠금과 같은 조건으로 비활성화합니다. 버튼 터치 영역 아래 20px과 추천 입력 목록 위 12px을 합쳐 첫 추천 입력까지 32px을 확보합니다. 엔딩 도달 턴(`reachedEnding` 존재)에는 버튼을 표시하지 않습니다 — 서버도 동기 409로 거부합니다([`4-backend-server-spec.md §4-3-9`](4-backend-server-spec.md)).

**재생성 흐름** — 클릭 → `POST /chats/{id}/turns/regenerate/stream {turnId}`(SSE 이벤트 계약은 턴 진행과 동일) → 기존 마지막 AI 버블·선택지를 스트리밍 블록으로 대체 → `completed` 수신 시 상세 refetch로 서버 확정본을 표시합니다. 사용자 입력 버블은 그대로 유지합니다. 서버는 이전 출력을 버전 이력으로 보존하지만([`4-backend-server-spec.md §4-8`](4-backend-server-spec.md) B11) 상세 조회·SSE에는 활성본만 실리므로, 프론트엔드 화면 계약은 변하지 않습니다.

**재생성 실패 처리** — 실패 종류에 따라 다르게 처리합니다.

- **`error` 이벤트 수신** — 서버가 교체하지 않았음이 보장되므로([`4-backend-server-spec.md §4-3-9`](4-backend-server-spec.md)) 기존 본문·선택지를 복원하고 실패 토스트를 표시합니다.
- **네트워크 실패·EOF(`completed`·`error` 없이 종료)** — 서버 교체 성공 후 전달만 끊겼을 수 있어 결과 불명입니다. 기존 본문을 임의로 복원하지 않고 상세 refetch로 서버 확정 상태를 표시합니다(교체됐으면 새 본문, 아니면 기존 본문).
- **402** — 턴 진행과 동일하게 이프 부족(회원)·로그인(게스트) 다이얼로그를 띄우고 기존 본문을 유지합니다.
- **409**(이미 새 턴이 추가된 낡은 화면) — 상세 refetch로 최신 상태를 반영합니다.

**배경 이미지 렌더** — 배경 이미지는 별도 턴 필드가 아니라 **`aiOutput` 본문 안의 이미지 마커**로 옵니다(US-6-11). 어떤 장면에 어떤 이미지를 삽입할지는 AI가 응답 생성 중 결정하고 서버가 마커를 검증하며([`4-backend-server-spec.md §4-3-9`](4-backend-server-spec.md) B10 — 이미지는 전부 팀 제작 자산), 클라이언트는 본문 렌더 시 마커 위치에 이미지를 표시하기만 합니다.

- **마커 포맷은 확정됐습니다** — 본문 인라인 `[[image:<imageKey>]]` 1종이고, 서버가 검증한 목록이 `completed`·상세 응답의 `images[]`(`{imageKey, type, url}`)로 동봉됩니다(정본: [`4-backend-server-spec.md §4-3-9`](4-backend-server-spec.md)). 남은 선행 조건은 AI 서버 계약 정렬이며 [`4-backend-server-spec.md §4-8`](4-backend-server-spec.md) B10이 추적합니다.
- **무효 마커는 마커 텍스트째 숨깁니다** — `images[]`에 없는 키의 마커는 이미지를 띄우지 않는 데 그치지 않고 `[[image:…]]` 문자열 자체를 출력하지 않습니다. 사용자에게 마커 원문이 보이는 것은 어떤 경우에도 계약 위반입니다.
- 이미지 로드 실패 시 이미지 영역을 제거하고 본문만 표시합니다.

**인물 이미지 렌더** 위 배경 마커와 별개로, 인물 이미지는 스트리밍 중에는 `character_image` 이벤트로, 저장 뒤에는 `aiOutput` 본문 안의 저장 마커로 전달합니다(정본: [`4-backend-server-spec.md §4-3-9`](4-backend-server-spec.md) · [`5-ai-server-spec.md §5-3-4`](5-ai-server-spec.md)). 클라이언트 렌더 규칙은 다음과 같습니다.

- **적용 경로** — 새 턴 이어쓰기, 마지막 응답 재생성, 채팅 상세와 공유 열람은 같은 조각 렌더 규칙을 사용합니다. 재생성 중에는 기존 AI 본문·이미지를 진행 중 조각 목록으로 대체하고, 완료 시 새 저장 마커 결과로 교체합니다. 명시적 `error`면 기존 확정 본문·이미지를 함께 복원합니다. 공유 열람도 저장 마커를 숨기는 데 그치지 않고 원본 채팅과 같은 위치의 이미지를 표시합니다.
- **진행 중 렌더** — `character_image`를 받는 즉시 AI 메시지의 현재 위치에 이미지 블록을 추가합니다. 이미지 이벤트 뒤에 해당 인물의 `이름:`과 대사가 `token`으로 이어지므로, 아직 오지 않은 글자를 기다리거나 완료 본문에서 위치를 다시 추측하지 않습니다. 같은 인물이 같은 턴에서 다시 말하면 새 이벤트마다 같은 이미지를 다시 표시합니다. 다만 웹 허용 목록(운영 `cdn.manyak.app`·개발 `dev-cdn.manyak.app`의 HTTPS `/characters/generated/**` 또는 `/characters/originals/**`) 밖의 URL은 이미지 조각에 추가하지 않습니다. 사용자 생성 스토리는 `generated`, 오리지널 스토리는 `originals` 경로를 사용합니다.
- **저장 마커 `[[URL]]`** — `completed` 뒤 상세 refetch, 재진입, 공유 열람에서 받는 턴의 `aiOutput`에서 이미지가 표시된 대사(`인물명:` 줄) 바로 앞에 독립된 한 줄로 오고, 마커와 대사 사이에는 빈 줄 하나가 있습니다. 웹은 마커가 독립된 한 줄 전체이고, 뒤에 빈 줄 하나를 사이에 둔 다음 줄이 비어 있지 않은 `인물명:` 라벨로 시작하며, URL이 위 생성·오리지널 인물 이미지 허용 목록에 속할 때만 `text | character_image` 조각으로 바꿉니다. 이미지 대체 텍스트에 쓸 이름은 뒤 대사 라벨에서 가져옵니다. 세 조건 중 하나라도 어긋난 마커 모양 문자열은 제거하거나 이미지로 요청하지 않고 일반 본문으로 유지합니다. 유효한 마커의 글자와 URL 원문은 출력하지 않으며 그 위치에 이미지를 표시합니다. 위치는 마커가 알려 주므로 별도 이미지 목록에 의존하지 않습니다. 같은 인물이 여러 번 말하면 마커 횟수만큼 표시합니다. 웹 PR이 머지되기 전에 AI 계약이 이 형식으로 전환됐으므로 이전 `[[인물이름:URL]]` 형식은 지원하지 않습니다.
- **스트리밍→확정 교체** — 진행 중 `character_image`와 확정 저장 마커는 같은 위치·순서·횟수를 표현합니다. 상세 refetch가 끝날 때 전체 조각 목록을 원자적으로 교체하며, 이벤트 이미지와 저장 마커 이미지를 동시에 렌더해 중복시키지 않습니다.
- **레이아웃·접근성** — 이미지는 AI 메시지 본문 안의 독립된 가로 4:3 블록으로 렌더합니다(현행 생성 자산 `1024×768`, 정본: AI 서버 `IMAGE_SIZE`). **이미지는 AI 메시지 양쪽에서 16px씩 띄우고, 20px 곡률과 전체 1px 시맨틱 보더를 적용합니다.** 앞 텍스트 조각과 이미지 사이는 40px, 이미지와 뒤 텍스트 조각 사이는 20px을 띄웁니다. 이미지가 메시지의 첫 조각이면 별도 상단 여백을 추가하지 않습니다. 텍스트 조각과 엔딩 배지도 기존 좌우 16px 패딩을 유지해 이미지·본문의 좌우 기준선을 맞춥니다. 이벤트 수신 즉시 여백 안쪽의 가로 4:3 영역을 예약해 로드 완료로 본문이 크게 밀리지 않게 하고, 별도 등장 지연이나 완료 대기 애니메이션을 두지 않습니다. 원본 전체가 보이도록 비율을 유지하며 자르지 않습니다. 대체 텍스트는 `"{name} 인물 이미지"`로 제공합니다. 인물 이름 캡션은 바로 뒤의 대사 라벨과 중복되므로 추가하지 않습니다.
- **로드 실패** — 깨진 이미지 아이콘·대체 텍스트·URL 원문을 남기지 않고 해당 이미지 블록만 제거합니다. 앞뒤 텍스트와 이후 스트리밍은 계속 표시합니다.

### 엔딩 도달 표시

엔딩 도달 여부는 서버가 판정하고([`4-backend-server-spec.md §4-3-10`](4-backend-server-spec.md) ), 클라이언트는 값 유무로만 렌더합니다 — 채팅 이미지와 같은 원칙입니다.

- **도달 턴 배지** 완료 후 상세 refetch의 턴 항목에 `reachedEnding`이 있으면 해당 AI 응답의 가장 위 왼쪽에 `엔딩 · {엔딩 이름}` 배지를 표시합니다(US-6-13). 스토리 제작의 "임시 저장됨" 배지와 같은 primary 10% 배경·primary 전경색·보조 배지 크기를 사용하고, 긴 이름은 버블 폭 안에서 줄바꿈합니다. 스트리밍 중 임시 응답에는 표시하지 않고 서버가 확정한 턴에만 표시합니다.
- **도달 후 계속 진행** 엔딩 도달이 입력을 잠그지 않습니다. 입력창·선택지는 일반 턴과 동일하게 동작하고(잠금 조건은 스트리밍 여부뿐 — [입력창과 선택지](#입력창과-선택지)의 전송 잠금), 이후 턴은 배지 없는 일반 턴으로 이어집니다(US-6-14). 서버도 도달 후 턴 진행을 계속 허용합니다. **재생성 버튼만 예외로 도달 턴에서 숨깁니다**(위 재생성 절 — 서버가 409로 거부).
- 익명 체험의 본 엔딩 집계는 [웹 스펙](3-2-web-spec.md#웹-사용자-모델)이 소유합니다.

### 채팅 공유하기

공유 시점까지의 채팅을 읽기 전용 링크로 다른 사람에게 보여주는 기능입니다(US-6-17·6-18). 서버 계약은 [`4-backend-server-spec.md §4-3-11`](4-backend-server-spec.md)이 정의합니다.

**발급** — 헤더 우측 옵션 메뉴(⋮) 왼쪽에 share 아이콘 버튼(접근 이름 "채팅 공유하기 버튼")을 둡니다. 클릭하면 바로 발급하지 않고 확인 다이얼로그를 먼저 엽니다 — 링크를 받은 사람은 누구나 대화를 볼 수 있으므로, 공개 범위를 알린 뒤 사용자가 확정하게 합니다.

- **다이얼로그 구성** — 제목 "이 채팅을 공유할까요?", 설명 "이 링크가 있으면 누구든지 내가 지금까지 이어온 채팅을 볼 수 있어요", 하단 버튼 두 개(왼쪽 "나중에 하기" 보조 스타일 · 오른쪽 "링크 복사하기" 주 스타일, 같은 폭). 타이틀은 의도(공유)를 묻고 확정 버튼은 실제 동작(링크 복사)을 예고합니다 — 버튼까지 "공유"라 하면 공유 시트 등 다른 결과를 기대하게 되기 때문입니다. 닫기(X) 버튼은 없고 "나중에 하기"·배경 탭·ESC로 발급 없이 닫습니다.
- **확정** — "링크 복사하기"를 누르면 `POST /chats/{id}/shares`로 공유를 발급하고, 응답의 공유 식별자로 `{서비스 origin}/share/{shareId}` URL을 만들어 클립보드에 복사한 뒤 "채팅 공개 링크가 복사되었어요" 토스트를 표시하고 다이얼로그를 닫습니다 — 문구는 모든 플랫폼 공통이며 이 문서가 정본입니다.
- **실패** — "공유 링크 생성에 실패했어요" 토스트를 표시하고 다이얼로그를 유지해 재시도할 수 있게 합니다.
- **진행 중** — 확정 버튼은 문구 공간을 유지한 중앙 스피너("복사 중")로 전환되고, 두 버튼과 배경 탭·ESC 닫기가 모두 잠깁니다.
- 턴이 0개인 채팅에서도 발급을 막지 않습니다(프롤로그만 보이는 공유).

**열람 화면(FE-SCREEN-012)** — `GET /shares/{id}` 응답을 채팅 화면과 같은 렌더 규칙으로 표시하되, 상호작용 요소를 모두 제거합니다.

- **유지** — 프롤로그 버블 → 각 턴(사용자 버블 → AI 버블) 렌더 순서, 강조 마크업(`**볼드**`·`*...*`), 엔딩 배지(`reachedEnding`), 하단 이동 버튼, 헤더 show/hide. 배경 이미지 마커 렌더도 채팅 화면과 동일합니다. 유효한 인물 이미지 저장 마커도 채팅 화면과 같은 위치의 이미지로 표시하고, 마커 글자와 URL은 숨깁니다.
- **제거** — 입력창(컴포저), 선택지·추천 입력, 재생성 버튼, 옵션 메뉴, 온보딩, 스트리밍 관련 UI 전부. 열람은 완결된 스냅샷이므로 SSE·refetch가 없습니다.
- **헤더** — 뒤로가기 대신 서비스 로고(홈 링크)와 스토리 제목을 표시합니다. 열람자는 앱 내 이력 없이 외부에서 진입하기 때문입니다. 인앱 브라우저 탈출 안내([3-2-web-spec.md §3-2-5](3-2-web-spec.md#3-2-5-반응형접근성브라우저-지원))도 같은 로고 홈 링크 헤더를 씁니다.
- **안내 문구** — 대화 위에 "친구가 공유한 채팅을 보고 있어요"를 표시합니다. 외부 링크로 바로 진입한 사람은 자기가 무엇을 보고 있는지 알 단서가 없으므로, 읽기 전용 스냅샷이라는 맥락을 첫 화면에서 알려 줍니다.
- **하단 CTA** — "나만의 스토리 만들고 채팅하기" 버튼을 항상 고정해 스토리 생성 퍼널(`/studio/story/simple`)로 **직결**합니다. 제작 탭을 거치지 않는 이유는 공유 열람이 이미 서비스를 보여준 상태라 한 단계 더 두면 이탈만 늘기 때문입니다. 같은 이유로 클릭 시 온보딩을 본 것으로 기록해, 만들기 후 메인 탭에 돌아왔을 때 온보딩 게이트([3-2-web-spec.md §3-2-4](3-2-web-spec.md#3-2-4-라우팅레이아웃공통-셸))를 다시 마주치지 않게 합니다.
- **진입 스크롤** — 처음부터 읽는 것이 목적이므로 항상 프롤로그가 보이는 상단에서 시작합니다.
- **진입 애니메이션** — 로딩 스피너가 열람 화면으로 교체될 때 헤더·대화·CTA를 포함한 화면 전체를 채팅 화면과 같은 150ms로 페이드인합니다. 메시지를 순차 등장시키는 연출은 두지 않습니다.
- **로드 실패** — 404(삭제된 채팅·잘못된 링크)를 포함한 로드 실패 시 "공유된 채팅을 찾을 수 없어요" 안내와 홈(`/`) 이동 링크를 표시합니다.

**링크 미리보기** — 서버가 공유본을 읽어 제목에 스토리 제목, 설명에 프롤로그 발췌, 이미지에 스토리 썸네일을 담은 오픈그래프 메타데이터를 만듭니다. 공유 열람 응답에는 썸네일이 없어 스토리 상세(`GET /stories/{storyId}`, 공개 식별자 접근)를 한 번 더 조회하며, 썸네일이 없거나 조회에 실패하면 루트의 브랜드 오픈그래프 이미지가 쓰입니다. 공유본 조회에 실패하면 제목·설명 없이 색인 차단만 담은 기본값을 돌려주고 페이지는 그대로 띄웁니다 — 미리보기가 비는 것이 페이지가 뜨지 않는 것보다 낫기 때문입니다. 이때 탭 제목은 기본 문서 제목으로 남으므로, 화면이 클라이언트에서 공유본을 받은 뒤 `제목 - 마냑`으로 덮어써 채팅방과 형식을 맞춥니다([3-2-web-spec.md §3-2-4](3-2-web-spec.md#3-2-4-라우팅레이아웃공통-셸) 문서 제목).

공유 URL의 플랫폼 공통 계약은 세 가지입니다: ① 로그인·게스트 구분 없이 누구나 열람할 수 있고, ② 열람은 열람자의 로컬 서재([웹 사용자 모델](3-2-web-spec.md#웹-사용자-모델))에 아무것도 저장하지 않으며, ③ 분석 이벤트·Sentry에 공유 식별자를 싣지 않습니다([`6-analytics.md §6-4-2-14`](6-analytics.md)). 검색 색인 정책(유효 공유본 색인 허용, 조회 불가 URL의 `noindex, nofollow`)은 웹 소유입니다([3-2-web-spec.md §3-2-4](3-2-web-spec.md#3-2-4-라우팅레이아웃공통-셸) 색인 범위).

### 검수 기준

- 프롤로그와 추천 입력을 표시해야 합니다. (US-6-1)
- 메시지를 전송하면 응답이 스트리밍되어 누적되어야 합니다. (US-6-2·6-3)
- 전송한 턴은 뷰포트 상단에 앵커되어 토큰 누적이 화면을 끌어내리지 않아야 하고, 스트리밍 중 옮긴 스크롤 위치가 완료 후에도 유지돼야 합니다.
- 헤더 옵션 메뉴에서 채팅을 삭제하면 완료 안내 후 채팅 목록으로 돌아가야 합니다. (US-5-3)
- 추천 입력의 수정 버튼은 입력창을 채우고, 본문 탭은 바로 전송해야 합니다. (US-6-4)
- 스트리밍이 실패하면 오류 안내가 떠야 합니다. (US-6-8)
- 응답을 받는 동안 전송 버튼에 스피너가 표시되고, 완료되면 원래 아이콘으로 돌아와야 합니다.
- 투어 미열람 + 턴 0개 채팅에 진입하면 안내 투어가 1회 자동 노출되고, 완주·건너뛰기 후 재진입 시 다시 뜨지 않아야 합니다. 일반 입력 모드에서는 첫 스텝이 상황 추가 버튼만 안내해야 합니다.
- 안내 카드는 앱 프레임 좌우 여백과 화면 위아래를 벗어나지 않아야 합니다.
- 첫 추천 입력 위에 인라인 힌트가 1회 표시되고, 재진입 시에는 보이지 않아야 합니다.
- 로컬 게스트 채팅 카운터가 5회에 도달하면 스트림 요청을 보내지 않아야 합니다. 서버 402를 받으면 실패한 낙관적 버블을 제거하고 사유에 맞는 다이얼로그를 표시해야 합니다. (US-10-4·5)
-  다시 생성 시 마지막 AI 응답이 새 본문으로 교체되고 사용자 입력 버블은 유지돼야 합니다. `error` 이벤트 시 기존 본문이 복원되고, `completed`·`error` 없는 종료 시에는 refetch 결과(서버 확정 상태)가 표시돼야 합니다. (US-6-10)
-  `aiOutput` 본문에 이미지 마커가 포함된 턴은 마커 위치에 이미지가 표시돼야 하고, 마커가 없는 턴에는 이미지가 없어야 합니다. (US-6-11)
-  인물 이미지: 스트리밍 중 허용된 `character_image` 이벤트가 도착하면 `completed` 전에 그 위치에 이미지가 즉시 표시돼야 하고, 뒤따르는 인물명·대사는 이미지 다음에 토큰 단위로 계속 나타나야 합니다. 같은 인물의 이벤트가 다시 오면 다시 표시돼야 합니다. 완료·상세·공유 화면에서는 유효한 `[[URL]]` 마커 글자와 URL이 보이지 않고 같은 위치·순서·횟수의 이미지가 표시돼야 하며, 스트리밍→확정 교체 중 이미지가 사라지거나 중복되지 않아야 합니다. 허용 CDN·독립 줄·빈 줄 하나·뒤따르는 인물명 대사 라벨을 충족하지 않는 값은 이미지로 요청하지 않고 본문으로 유지해야 합니다. `error` 또는 저장되지 않은 EOF 뒤에는 미확정 텍스트·이미지를 함께 제거합니다.
- 엔딩에 도달한 뒤에도 입력·선택지가 정상 동작해 다음 턴을 이어갈 수 있어야 합니다. 단 엔딩 도달 턴에는 재생성 버튼이 표시되지 않아야 합니다. (US-6-14)
-  `reachedEnding`이 있는 확정 턴에는 AI 응답 최상단 왼쪽에 `엔딩 · {이름}` 배지가 표시돼야 합니다.
-  선택지에 주요 사건 방향 제안이 포함돼야 합니다 — 구성 자체는 AI 계약이 담보하므로([`5-ai-server-spec.md §5-3-5`](5-ai-server-spec.md)) 프론트엔드는 3개 렌더만 검수합니다. (US-6-12)
- 헤더 공유 버튼으로 공유 URL이 클립보드에 복사돼야 합니다. 헤더 우측에 홈 버튼은 없어야 합니다.
- 공유 열람 화면은 발급 시점까지의 턴만 표시하고, 입력창·선택지·재생성 등 상호작용 요소가 없어야 합니다. 로그인하지 않은 사용자도 열람할 수 있어야 합니다. (US-6-18)
- 공유 열람의 하단 CTA는 스토리 생성 퍼널로 바로 이동하고, 이후 홈 진입에서 온보딩이 다시 뜨지 않아야 합니다.

## 3-1-7. API 연동·에러 처리 계약

API 상세 명세는 [백엔드](4-backend-server-spec.md)가 소유합니다. 여기서는 호출 시점과 응답별 사용자 처리를 정합니다. 인증 정보 전달과 호출 창구는 [웹 설계](../design/1-1-web-design.md#1-1-3-bff-프록시토큰-세션)·[Android 설계](../design/1-2-android-design.md#1-2-5-인증과-세션)가 소유합니다.

### 요청 헤더

논리 `device_id`·`session_id`의 의미는 [분석](6-analytics.md#6-2-식별자-정책)이 정본입니다. 플랫폼은 같은 의미의 값을 API 헤더와 분석 SDK에 사용합니다. 초기화·필수 헤더·누락 처리의 플랫폼별 보장은 해당 설계에서 정합니다.

| 헤더                  | 값                     |
| --------------------- | ---------------------- |
| `X-Manyak-Device-Id`  | 논리 `device_id`       |
| `X-Manyak-Session-Id` | 논리 `session_id`      |

두 헤더가 없어도 일반 요청은 거부되지 않습니다(백엔드가 `unknown`으로 채움). 단 **`X-Manyak-Device-Id`가 정책상 필수인 경로**가 있습니다 — 게스트 체험 한도 대상 요청(누락 시 400 — [`4-backend-server-spec.md §4-3-7`](4-backend-server-spec.md)), 로그인 핸드오프 생성(`POST /auth/handoffs`), 핸드오프 없는 첫 로그인의 회원 체험 시드([`4-backend-server-spec.md §4-3-5`](4-backend-server-spec.md)). `X-Manyak-Session-Id`는 모든 경로에서 best-effort입니다.

**백엔드가 처리하는 상관관계** — `X-Manyak-Request-Id`가 없으면 백엔드가 생성해 응답 헤더로 echo합니다(백엔드는 수신 헤더가 있으면 그 값을 우선하지만, 클라이언트 앱은 이 헤더를 만들지 않습니다 — [`4-backend-server-spec.md §4-3` 요청·응답 헤더](4-backend-server-spec.md)). 퍼널의 생성 요청 **본문**에 싣는 `requestId`([§3-1-4](#3-1-4-스토리-생성-퍼널) 백그라운드 생성 복귀)는 멱등·복구용 별개 값이며 이 헤더와 무관합니다. device/session 헤더가 없어도 요청을 막지 않고 `unknown`으로 채운 뒤 경고 로그만 남깁니다.

**프론트가 채팅·스토리라인 요청에 추가로 싣는 값** 백엔드가 AI 호출을 Langfuse 트레이스로 연결하는 데 쓰는 값으로, 값 자체는 백엔드가 헤더로 변환해 forward합니다([`4-backend-server-spec.md §4-7`](4-backend-server-spec.md)).

- 채팅 턴 요청(`POST /chats/{chatId}/turns/stream`)에 `userSource`(선택, `"choice" | "edited_choice" | "typed"`)를 추가합니다 — 추천 선택지를 그대로 보낸 경우 `choice`, 고쳐서 보낸 경우 `edited_choice`, 직접 입력한 경우 `typed`입니다. 문자열만으로는 서버가 구분할 수 없어 프론트가 명시해야 하며, 허용값 밖의 값은 400입니다([`4-backend-server-spec.md §4-3`](4-backend-server-spec.md)).
- 같은 채팅 턴 요청에 `sourceTurnId`(직전 턴의 `turnId` = 채팅 상세 `turns[].id`)와 `choiceOrder`(선택지 순번)를 함께 실으면 백엔드가 어느 선택지를 골랐는지, 원문 그대로 보냈는지를 DB에 기록합니다( [`4-backend-server-spec.md §4-3-3`](4-backend-server-spec.md)). `choiceOrder`는 `turns[].choices` 배열의 **인덱스 + 1**입니다 — 0부터 보내면 400이 아니라 조용히 기록만 누락됩니다. 두 값 모두 선택 필드라 보내지 않아도 요청은 정상 처리되고, 값이 낡았거나(그새 턴이 진행됨) 범위 밖이어도 400·409가 아니라 기록만 생략되므로 프론트는 방어 없이 값을 그대로 보내면 됩니다. 시작 추천 입력과 직접 입력에는 원본 턴 선택지가 없으므로 두 값을 보내지 않습니다.
- 스토리라인 생성 재요청이 재생성(다시 만들기)일 때 **바로 직전** 시도의 `trace_creation_id`(AI 트레이스 연결 ID — 요청 필드 이름은 `parentCreationId`, 값은 스토리라인 요청 UUID)를 함께 보내면 백엔드가 검증 후 `X-Manyak-Parent-Creation-Id`로 AI에 forward합니다. 보내지 않으면 헤더가 생략되고 서버는 신규 진행으로 취급합니다 — 스토리라인 재생성은 전용 API가 없어 서버가 원본과의 연결을 스스로 알 수 없기 때문입니다. 백엔드가 검증에 실패해도(부모 미존재·소유 불연속 등) 400이 아니라 헤더만 조용히 생략되므로, 프론트엔드는 실패를 방어할 필요 없이 값을 그대로 보내기만 하면 됩니다([`4-backend-server-spec.md §4-7`](4-backend-server-spec.md)). 요청 필드명은 `parentCreationId`(UUID, nullable)이며, 제품 분석 이벤트의 `analytics_creation_id`(`simpleCreationId`)와는 **다른 값**입니다([`6-analytics.md §6-2`](6-analytics.md)).

**입력 출처 판정** — 아래 규칙을 따릅니다. 플랫폼별 판정 함수와 QA 연결은 각 설계·QA가 소유합니다.

- 선택지 본문 탭과 무작위 추천 전송(Play 버튼)은 대조 없이 `choice`입니다. 두 경로 모두 전송 전에 사용자가 문장에 손댈 기회가 없습니다.
- "채우기"로 입력창에 넣고 보내는 경로는 전송 시점의 텍스트를 채운 원문과 대조해 가릅니다 — 같으면 `choice`, 다르면 `edited_choice`입니다. 앞뒤 공백 차이는 같은 것으로 보고, **블럭 모드에서 채우면 블럭으로 파싱했다가 다시 직렬화되어 문자열이 달라지므로 그 왕복 결과도 "그대로"로 인정합니다** — 사용자가 손대지 않았는데 `edited_choice`가 되면 선호 신호가 오염됩니다.
- 채운 뒤 내용을 전부 지우고 새로 써도 `edited_choice`입니다. 추천을 본 뒤의 입력이라 순수 `typed`와 구분하는 편이 선호 분석에 유용하고, "고쳐 쓴 것"의 극단으로 두는 편이 규칙이 단순합니다. 이는 의 현행 구현 기준이며,  전환 뒤에는 아래 Langfuse 선호 행동 전달 계약대로 입력을 완전히 비운 시점에 선택지 연결을 지우고 이후 새 입력을 `typed`로 보냅니다.
- 채우기를 쓴 적이 없으면 `typed`입니다. 기억해 둔 원문은 전송에 성공하면 비워, 다음 턴 입력이 앞 턴에서 채운 선택지와 대조되지 않게 합니다.
- 스토리라인은 **최초 생성에도 `parentCreationId`를 `null`로 명시해** 보냅니다. 재생성이 직전 요청 본문을 그대로 재사용하는 구조라, 값을 비워두면 직전 요청의 `parentCreationId`가 딸려와 체인이 부모가 아닌 조부모를 가리킵니다.

### 이프 정책 수치 표시

이프 적립·소모 수치는 서버 정책이 정본입니다. 클라이언트는 고정 수치를 대체값으로 두지 않습니다.

- **출처는 `GET /credits/policies` 하나입니다.** 인증이 필요 없어 게스트 화면에서도 같은 값을 씁니다. 응답은 평평한 6개 필드입니다 — `signupReward` · `inviteReward` · `inviteMonthlyCap` · `attendanceReward` · `storyCreationCost` · `chatTurnCost`. `inviteMonthlyCap`만 이프가 아니라 **초대자 몫의 월 적립 횟수**입니다.
- **수치를 쓰는 자리** — 추가 정보 단계의 스토리 완성 비용(`storyCreationCost`), 회원 채팅 입력창의 턴 비용(`chatTurnCost`), 이프 충전 무료 충전 탭의 출석 제목(`attendanceReward`), 친구 초대 메뉴 보조 문구·초대 화면·초대 온보딩·등록 성공 토스트·카카오 공유 제목(`inviteReward`).
- **문구는 수치를 받아 만듭니다.** 문구 정본은 여전히 클라이언트 상수이되 값을 인자로 받는 빌더 형태이며, 리터럴로 굳은 문자열을 두지 않습니다.
- **응답 전·실패 시에는 자리표시 숫자를 쉬머와 함께 그립니다.** 클라이언트에 대체 수치를 두지 않습니다 — 화면이 들고 있는 값은 서버가 정책을 바꾸는 순간 거짓이 되기 때문입니다. 대신 자릿수만 채운 자리표시 숫자에 쉬머를 얹어 아직 확정되지 않은 값임을 드러내고, 응답이 오면 그 자리에 수치가 들어갑니다. 한 줄짜리 라벨을 비워 두거나 스켈레톤으로 바꾸지 않아 문구의 줄바꿈이 흔들리지 않습니다(웹 구현은 [`1-1-web-design.md`](../design/1-1-web-design.md) §3-2-2 이프 정책 수치 패칭).
- **토스트·공유 제목처럼 그 순간 문자열이 필요한 자리는 예외입니다.** 쉬머를 얹을 대상이 없으므로 사건이 일어난 시점의 값을 한 번만 읽습니다. 화면을 띄운 뒤 동작하는 흐름이라 그때는 수치가 이미 도착해 있습니다.
- **서비스 안내(FE-SCREEN-011)는 수치를 고지하지 않습니다.** 수치를 모아 보여주는 자리를 두면 각 사용 지점과 이중으로 관리해야 해서 절 자체를 없앴습니다.
- **출시 이벤트처럼 값을 올리는 운영은 서버 정책만 바꿉니다.** 화면에 상시값·이벤트값을 나눠 적지 않습니다 — 서버 필드가 하나뿐이고, 이벤트 종료 시 문구를 되돌리는 작업이 남지 않습니다.

### 날짜 표시 기준

. 서버의 시각 필드(`createdAt` · `expiresAt` · `updatedAt`)는 **ISO 8601 UTC 문자열**입니다([`4-backend-server-spec.md §4-3` 공통 규칙](4-backend-server-spec.md#4-3-api-계약)). 화면에 `YYYY-MM-DD`를 그릴 때는 **KST(`Asia/Seoul`)로 옮긴 뒤** 자릅니다.

- **문자열 앞 10자를 그대로 자르지 않습니다.** UTC 문자열을 자르면 KST 자정~오전 9시(UTC 15:00~24:00)에 벌어진 일이 하루 전으로 표시됩니다. 예: KST 09-02 00:10에 받은 출석 보상이 `2026-09-01`로 보이고, 만료일도 같이 하루 밀립니다.
- **기기 시간대가 아니라 KST로 고정합니다.** 서비스의 하루 경계가 KST로 못박혀 있어서입니다 — 출석 보상 멱등 키가 KST 날짜이고 초대 월 상한도 KST 월 귀속입니다([`4-backend-server-spec.md §4-3-7`](4-backend-server-spec.md#4-3-api-계약)). 기기 시간대를 따르면 해외 접속자에게 "출석은 됐는데 날짜가 다른" 화면이 나옵니다. 서버 렌더 결과가 기기와 갈리지 않는 부수 효과도 있습니다.
- **적용 자리** — 이프 내역의 발생일·만료일(FE-SCREEN-008), 스토리 상세의 생성일(FE-SCREEN-003), 내 스토리 카드의 제작일(FE-SCREEN-013).
- **상대 시간 표기(채팅 목록의 "n시간 전"·"오늘"·"어제")는 이 규칙 밖입니다.** 경과 시간은 시간대와 무관하고, 날짜 경계 판정은 사용자의 체감 시각(기기 시간대)을 따르는 편이 자연스럽습니다.

### 응답·에러 처리 정책

- 읽기 응답은 HTTP 상태로 분기합니다. 정상 상태(200)가 아니면 목록은 빈 배열로, 상세는 에러 상태로 처리합니다.
- 백엔드 에러는 `ApiErrorResponse {timestamp, status, code, message, path, details[]}` 형태이며 `details`는 `{field, message}[]`입니다.
- 읽기 요청은 자동 재시도·화면 복귀 자동 재조회 없이 오류를 예외가 아닌 상태로 반환해, 화면이 인라인으로 처리합니다. 웹 TanStack Query 기본 옵션 값의 정본은 [`1-1-web-design.md §1-1-1` 데이터 패칭 기본 옵션](../design/1-1-web-design.md#데이터-패칭-기본-옵션-웹)입니다.
- 서버 원본 메시지·스택은 사용자에게 그대로 노출하지 않습니다. 회원의 인증 실패는 플랫폼의 재발급·세션 종료 절차를 거치며 화면마다 별도 세션 판정을 만들지 않습니다.

### 화면 상태 처리 (로딩·빈·에러)

화면별 상태는 각 화면 스펙([§3-1-3](#3-1-3-화면별-스펙))에 정의하며, 공통 규칙은 다음과 같습니다.

| 상황                 | 처리                                                                                |
| -------------------- | ----------------------------------------------------------------------------------- |
| 목록·상세 최초 로딩  | 지연 로딩(빠른 응답 시 스켈레톤 깜빡임 방지). 지연 전에는 아무것도 표시하지 않음    |
| 버튼 클릭 후 요청 중 | 버튼 비활성화 + 기존 문구 공간을 유지한 중앙 스피너. 버튼의 접근 가능한 이름은 유지 |
| 목록 조회 실패       | 재시도 가능한 에러 안내                                                             |

## 3-1-8. 입력·폼 검증 규칙

피드백·키워드·추가 정보·채팅과 일반 제작·수정의 입력 계약입니다. 소셜 로그인 버튼 자체는 입력 폼 검증 대상이 아닙니다.

### 일반 제작·수정 폼

서버 계약([`4-backend-server-spec.md §4-3-8`](4-backend-server-spec.md))과 동일한 규칙을 클라이언트에서 선검증합니다: 제목 ≤ 100자, 한 줄 소개 ≤ 255자, 시작 설정 이름 ≤ 100자, 장르 1~8개(각 30자 이내), 스토리 설정 4필드·시작 설정 3필드·추천 입력 3개 필수. 주요 사건 ≤ 10개(각 이름·키 문장 필수), 엔딩은 시작 설정당 ≤ 10개(각 이름 필수). 이미지 입력은 없습니다(FE-SCREEN-009, B10). 필수 미충족 섹션은 아코디언 헤더에 상태 배지로 표시하고 등록 버튼을 비활성화합니다.

### 피드백 폼

| 필드  | 타입     | 필수   | 제약                                       | 비고                                                                                                                       |
| ----- | -------- | ------ | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| body  | textarea | 예     | 최대 500자(초과 입력 차단), 글자 수 카운터 | 서버 상한은 2,000자 — 의도된 여유이며 표시 상한은 프론트엔드가 유동 조정([클라이언트 추적](../planning/client-tracking.md#기존-간극의-처리) G6) |
| email | email    | 아니오 | 최대 320자                                 | 미입력 시 `null` 전송                                                                                                      |

- 제출 버튼은 `body`가 비어 있어도 활성화합니다. 빈 값으로 제출하면 버튼 위에 "피드백 내용을 입력해주세요"를 표시하고 요청하지 않습니다. 유효한 본문을 입력하면 오류를 제거합니다. 이메일은 필수가 아닙니다.
- `platform`은 UI에서 수집하지 않고 자기 플랫폼 값(웹 `WEB`, 안드로이드 `ANDROID`)으로 고정 전송합니다.
- 제출 중에는 입력·버튼을 비활성화하고 버튼 중앙에 `피드백 전송 중` 스피너를 표시합니다.

### 키워드·커스텀 키워드 (퍼널)

- 상한: 장르 키워드 3, 인물별 특징 3, 주변 인물 5명. 상한 도달 시 미선택 칩·추가 트리거 비활성화.
- 커스텀 키워드: 클라이언트 최대 15자(서버 스키마 30자). 빈 값에서도 추가 버튼은 활성화하고, 제출 시 입력창 아래에 오류를 표시합니다. IME 조합 중 Enter는 제출하지 않습니다. 세 카테고리 모두 사용할 수 있습니다.
- 인물 이름: 클라이언트·서버 모두 30자. 주인공과 주변 인물 사이에 겹치는 이름이 있으면 해당 인풋에 오류를 표시하고 생성 요청을 막습니다. 웹은 저장 인물 이미지 마커 충돌을 막기 위해 `]`가 포함된 이름도 인풋·푸터 오류로 막습니다([§3-1-4](#3-1-4-스토리-생성-퍼널) 인물 단위 입력).
- 생성 가능 조건: 장르 1개 이상 그리고 주인공 특징 1개 이상, 겹치는 인물 이름 없음, 웹에서는 `]`가 포함된 인물 이름 없음([§3-1-4](#3-1-4-스토리-생성-퍼널)). 미충족 상태에서 다음 또는 생성 버튼을 누르면 푸터 오류를 표시합니다.
-  — 세계관 탭 개편이 구현되면 장르·배경은 각 1~2개·각 최소 1개 필수가 되고, 생성 가능 조건에 배경 1개 이상이 더해집니다([§3-1-4](#3-1-4-스토리-생성-퍼널) 세계관 탭 개편).

### 추가 정보 (퍼널)

- 추천 추가 정보 토글 + 자유 텍스트 행(추천 추가 정보 최대 3개, 자유 텍스트 UI 최대 10개, 각 100자). 공백 제거 후 비어 있지 않은 값만 전송합니다.
- 전송 페이로드 `additionalInfos`(추천 추가 정보 + 자유 텍스트)의 서버 검증 상한은 총 13개입니다.

### 채팅 입력

- 서버 검증 상한 3000자. 프론트는 `maxLength`·길이 검사가 없어 초과 입력을 차단하지 않습니다.
- 입력이 있으면 위쪽 화살표 아이콘으로 전송하고, 입력이 없고 추천 입력이 있으면 filled 재생 아이콘으로 무작위 추천 입력을 즉시 전송합니다. 입력과 추천이 모두 없거나 스트리밍 중이면 버튼을 비활성화합니다.
- `Enter`(Shift 없이, IME 조합 아님) 또는 폼 제출로 전송합니다. "상황 추가"로 선택 영역을 `*...*` 강조로 감쌉니다.

### 검증 표시 원칙

- 필드 단위 오류는 해당 필드 근처에, 폼·요청 단위 오류는 토스트로 표시합니다.
- 오류는 해당 필드와 프로그램적으로 연결해 보조기술에 노출합니다. 구현 수단은 플랫폼 소유입니다(웹: `aria-invalid`·`role=alert` — [3-2-web-spec.md §3-2-5](3-2-web-spec.md#3-2-5-반응형접근성브라우저-지원) / 앱: 접근성 시맨틱 — [`1-2-android-design.md §1-2-7`](../design/1-2-android-design.md)).
- 비밀번호·토큰 등 민감 입력은 없으며, 자유 입력 원문은 로그·이벤트에 수집하지 않습니다([`6-analytics.md §6-7`](6-analytics.md)).
