- **처음 보는 사람** — 기록 규칙을 읽고, 목차에서 관련 주제의 기록으로 이동합니다. 문서 작성일·수정일은 개별 결정일과 구분합니다.

- **리뷰·변경 작성자** — 관련 결정과 후속 대체 관계를 함께 확인합니다. 확정된 본문은 보존하고 새 기록에 대체하는 ID·범위를 남깁니다.

## W-001. SSE를 fetch와 ReadableStream으로 수신

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문 W:87](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L87-L99)
- **맥락:** 채팅 턴은 사용자 입력을 POST 본문에 실어 보내고 SSE로 응답받습니다.
- **결정:** `fetch`와 `ReadableStream`으로 수신합니다.
- **이유:** 표준 EventSource는 GET만 지원해 해당 POST 본문 계약을 충족하지 못합니다.
- **주요 영향:** 이벤트 파싱·EOF 처리를 직접 소유하고 일반 요청 타임아웃과 스트림 수명을 구분합니다.

## W-017. 편집 초안을 같은 키의 목록으로 확장

- 결정일: 2026-09-22, 기록 확정 상태: Accepted
- 근거: [제작 카드와 다중 완성 진행](../spec/3-1-client-spec.md#제작-카드와-다중-완성-진행), [웹 제작 흐름](../spec/3-2-web-spec.md#3-2-3-웹-제작-흐름), [게스트 저장소 키](../design/1-1-web-design.md#게스트-저장소-키-웹)
- **맥락:** 완성 요청은 목록이지만 편집 초안은 슬롯 한 건이라 초안이 있으면 새 제작 전에 이어서/새로 만들기를 골라야 했고 새로 만들면 기존 초안이 사라졌습니다.
- **결정:** `manyak:pending-creation-request` 값을 레코드 배열로 바꾸고 구 단일 객체는 1건 목록으로 읽습니다. 안정적인 초안 ID를 새로 두지 않고 기존 `requestId`를 목록 키로 유지하며, 퍼널 한 세션이 자기 레코드 한 건만 소유하는 규칙을 퍼널 훅 한 곳(`persistOwnRecord`)에 둡니다.
- **이유:** 단계 전환은 이미 옛 레코드를 지우고 새 레코드를 넣는 방식이라 목록화만으로 같은 결과가 나며, 서버 복구 조회 키가 `requestId`라 별도 매핑이 필요 없습니다. 같은 키를 쓰면 배포 시점에 남은 사용자 초안을 파서 호환 한 줄로 보존합니다.
- **주요 영향:** 이어서/새로 만들기 다이얼로그와 `client_storyCreate_resumeDialog_*` 이벤트를 제거합니다. 퍼널 직접 진입·FAB은 항상 새 세션이고 재개는 진행 카드에서만 합니다. 완성 실패 강등은 다른 초안이 있어도 항상 초안으로 되돌립니다. Android는 KNK-1395로 같은 계약을 따릅니다.

## W-018. 웹 푸시는 Firebase 토큰 SDK와 제작 직후 프롬프트로 도입

- 결정일: 2026-09-22, 기록 확정 상태: Accepted
- 근거: [웹 PWA 푸시](../spec/3-2-web-spec.md#pwa-푸시), [디바이스 푸시 토큰·발송 모듈](../spec/4-backend-server-spec.md#4-3-api-계약), [BE-039](2-backend-server-adr.md#be-039), [Android 알림 계약](../spec/3-3-android-spec.md#3-3-5-알림)
- **맥락:** 서버는 `platform=WEB` 토큰 등록과 webpush notification 발송을 이미 지원했지만 웹에는 매니페스트·서비스 워커·토큰 등록이 없었습니다. Next.js PWA 가이드는 순수 Web Push(`PushSubscription`+VAPID 서버 액션)를 쓰는데 서버는 FCM 토큰으로 발송합니다.
- **결정:** Firebase JS SDK의 `getToken`/`deleteToken`으로 FCM 등록 토큰을 받아 기존 토큰 API에 등록하고, 서비스 워커는 compat SDK 초기화만 두어 표시·클릭을 브라우저와 SDK에 맡깁니다. 오프라인 캐싱·next-pwa·Serwist·커스텀 push 핸들러는 두지 않습니다. 알림 권한은 Android처럼 회원 화면이 처음 열릴 때 기기당 한 번 자동으로 묻되, 신규 회원은 필수 동의 시트의 제출 클릭(사용자 제스처) 직전에 묻습니다. 광고 동의는 필수 동의 시트의 "[선택]" 항목으로 먼저 받고 첫 거절 뒤 세 번째 재진입(페이지 로드)에서 재질문 시트로 한 번 더 묻습니다. 설정은 마이 > 알림 설정에서 서비스·광고·야간을 전체 교체 PUT으로 저장하고 광고·야간 변경마다 처리 결과 다이얼로그를 표시합니다.
- **이유:** 토큰 기반이 서버·Android와 같은 계약이라 서버 변경 없이 동작합니다. SDK 12가 권고하는 FID 기반 `register`는 서버 발송 대상과 토큰 테이블 계약을 함께 바꿔야 하므로 미룹니다. Android와 같은 시점·문구로 맞춰 두 플랫폼의 동의 규칙을 하나로 유지합니다. 브라우저는 제스처 없는 권한 요청을 무시할 수 있어(Safari) 동의 시트의 제출 클릭과 알림 설정의 버튼을 제스처 경로로 둡니다. 정보통신망법 제50조의 사전 동의·야간 별도 동의·처리 결과 통지는 Android와 같은 문구·규칙을 씁니다.
- **주요 영향:** Firebase 웹 앱 설정 5개가 Vercel·`.env.local`에 필요하며 비면 전체가 꺼집니다. E2E는 VAPID 키를 비워 푸시를 끄므로 권한 요청·토큰 등록·재질문 시트는 실기기 수동 검증입니다. 백그라운드 알림은 `recipientId`를 대조할 수 없어 로그아웃 토큰 삭제가 방어선입니다. 개인정보 처리방침의 푸시·광고 동의 고지가 Android 앱 기준이라 웹 푸시 포함 개정(서버 요구 버전 상향과 같은 릴리스)이 선행돼야 합니다.

## W-019. 제작 로컬 저장을 Dexie 트랜잭션으로 전환

- 결정일: 2026-09-26, 기록 확정 상태: Accepted
- 근거: [웹 제작 계약](../spec/3-2-web-spec.md#3-2-3-웹-제작-흐름), [제작 저장 구조](../design/1-1-web-design.md#게스트-저장소-키-웹)
- **대체 범위:** W-017의 localStorage 배열 저장과 별도 쓰기 방식만 대체합니다. requestId, 다중 초안, 새 제작 및 카드 재개 계약은 유지합니다.
- **맥락:** 한 항목을 바꾸어도 전체 JSON 배열을 동기식으로 다시 썼으며 초안 교체, 완성 제출, 실패 복원 중 일부 쓰기만 성공할 수 있었습니다.
- **결정:** Dexie와 IndexedDB로 제작 두 테이블을 저장하고 상태 검사 및 전환을 트랜잭션으로 처리합니다. useLiveQuery로 구독하며, 초기 조회와 명시적 이탈 및 제출은 비동기 저장 완료를 기다립니다. 제출 전 저장 실패는 공통 계약에 맞춰 입력을 보존하고 요청을 막습니다.
- **이관:** 검증된 legacy 입력은 최초 시각과 순서를 보존하고, DB 커밋 후에만 원문을 정리합니다. 완료 표시는 같은 원본의 재삽입을 방지합니다. 이중 쓰기와 자동 localStorage 폴백은 두지 않습니다.
- **세션 경계:** 본문을 저장하지 않는 동기식 세대값으로 로그아웃 직후 지연 작업을 무효화합니다. DB 삭제 실패 시 다음 접근에서 정리를 먼저 수행합니다.
- **한계:** 종료 순간의 비동기 저장, 서버 백업, 기기 간 동기화를 보장하지 않습니다. 배포 전에 열린 구버전 탭의 localStorage 쓰기는 자동 병합하지 않습니다. 배포 시 구버전 탭 정리 및 데이터 롤백 정책을 확인해야 합니다.

## W-020. 간편 제작 편집 저장을 버튼·단계 이동·화면 숨김으로 제한

- 결정일: 2026-10-01, 기록 확정 상태: Accepted
- 근거: [웹 제작 흐름](../spec/3-2-web-spec.md#3-2-3-웹-제작-흐름), [Android 제작과 데이터 보존](../spec/3-3-android-spec.md#3-3-3-제작과-데이터-보존), [A-020](1-3-android-adr.md#a-020)
- **대체 범위:** W-019 중 명시적 이탈이 편집 저장 완료를 기다리는 부분만 대체합니다. 저장소, 트랜잭션, 생성·완성 요청의 사전 저장은 유지합니다.
- **맥락:** 웹 간편 제작은 마지막 변경 300ms 뒤 자동 저장하고 헤더에 저장 상태 배지를 보였습니다. Android 간편 제작(A-020)과 웹 일반 제작은 이미 "임시 저장" 버튼 방식이라 같은 앱 안에서 저장 방식이 달랐습니다.
- **결정:** 편집은 메모리에 두고 일반 제작과 같은 "임시 저장" 버튼, 단계 이동, 화면 숨김 때만 저장합니다. 버튼·이탈 다이얼로그·새로고침 확인창은 일반 제작 코드를 함께 씁니다. 스토리라인 생성 요청과 결과는 지금처럼 바로 저장합니다.
- **이유:** 사용자가 저장 시점을 알 수 있고, 입력 삭제 같은 편집이 말없이 확정되지 않습니다. 단계 이동 저장은 일반 제작의 탭 이동 저장과 맞춥니다. 생성 결과는 비용이 드는 서버 결과이고 복구 조회에 필요해 버튼을 기다리지 않습니다.
- **주요 영향:** 300ms 디바운스 저장과 저장 상태 배지를 제거합니다. Android와 달리 단계 이동 때도 저장합니다. 잃을 것이 없으면(입력도 저장본도 없음) 간편·일반 제작 모두 확인 다이얼로그 없이 나가고, 저장하지 않은 입력이 있으면 키워드 단계에서도 새로고침 확인창을 띄웁니다. `client_storyCreate_draftSaved`는 세 저장 계기의 쓰기 성공에서만 발생합니다.

## W-021. 일반 제작 이미지는 브라우저에서 잘라 JPEG로 올림

- 결정일: 2026-10-01, 기록 확정 상태: Accepted
- 근거: [웹 제작 흐름](../spec/3-2-web-spec.md#3-2-3-웹-제작-흐름), [일반 제작 구조](../design/1-1-web-design.md#라우트-등록과-호환)
- **맥락:** 일반 제작의 커버(3:4)와 주변 인물(4:3) 이미지는 원본 그대로 올라가, 비율이 다르면 목록·상세에서는 가운데가 임의로 잘리고 채팅의 인물 이미지에는 여백이 생겼습니다.
- **결정:** 파일을 고르면 하단 시트에서 칸 비율 프레임에 맞춰 이동·확대로 영역을 고르고, 브라우저 canvas로 잘라 긴 변 최대 1440px의 JPEG(품질 0.9)로 기존 presign 업로드에 올립니다. 크롭 UI는 `react-easy-crop`을 씁니다. 원본의 형식·5MB 선검사는 유지합니다.
- **이유:** 서버·presign 계약을 바꾸지 않고 비율을 보장합니다. `react-easy-crop`은 고정 프레임과 드래그·핀치·휠 확대, 경계 제한을 기본 제공하고 작습니다(gzip 약 7KB). Safari는 canvas에서 WebP를 만들지 못해 PNG로 바뀌므로 모든 기기에서 같은 결과가 나오는 JPEG를 택했습니다. PNG는 1440px에서도 5MB에 가까워질 수 있지만, JPEG는 최악(무작위 노이즈)에도 약 1.8MB라 5MB 제한에 여유가 있습니다.
- **주요 영향:** 업로드 Content-Type은 항상 `image/jpeg`이고 투명 배경은 흰색이 됩니다. 이미 올린 이미지를 다시 자르는 편집은 두지 않으며 다시 고르면 됩니다. 5MB가 넘는 원본은 지금처럼 고르기 전에 막습니다.

## W-024. 완성 중 표지를 Android와 같은 로고 마스코트 애니메이션으로 바꿈

- 결정일: 2026-10-06, 기록 확정 상태: Accepted
- 근거: [웹 제작 탭 진행 카드](../spec/3-2-web-spec.md), [Android A-065](1-3-android-adr.md)
- **맥락:** Android가 완성 중 카드 표지를 점 로딩에서 로고 마스코트 애니메이션으로 바꾸면서(A-065) 두 플랫폼의 표지가 갈렸습니다. 사용자는 완성을 기다리는 동안 같은 카드를 보므로 표현을 맞춥니다.
- **결정:** 웹도 같은 안무를 씁니다. 안무는 시간에서 자세를 계산하는 순수 함수라 Android의 값을 그대로 TypeScript로 옮기고, 그리기는 Canvas 2D로 같은 소품과 붓질을 그립니다. 마우스·트랙패드 환경에서는 기존 점 무리처럼 포인터에 반응하도록 마스코트 눈이 포인터를 바라보고, 동작 줄이기에서는 한 장면으로 정지합니다. A-065의 "Android 표현 차이"는 이 결정으로 플랫폼 공통 표현이 됩니다.
- **이유:** SVG와 motion 컴포넌트로 막마다 요소를 따로 움직이면 소품 수만큼 레이어와 타이밍이 늘고 Android와 값이 갈라집니다. 순수 함수 하나를 두 플랫폼이 같은 값으로 따르면 한쪽을 고칠 때 다른 쪽에 같은 수정을 옮기기 쉽고, 순간이동 없음·표지 안 유지 같은 같은 테스트로 검증할 수 있습니다.
- **주요 영향:** 완성 중 표지는 `ImageGeneration`을 쓰지 않습니다. 채팅 장면 썸네일 자리는 점 로딩을 유지합니다. 테마 토큰이 oklch라 캔버스에서 색을 섞으려고 한 점 캔버스로 sRGB 값을 읽으며, 테마가 바뀌면 다시 읽습니다. 안무를 바꿀 때는 Android `StoryCompletingChoreography`와 함께 고칩니다.

## W-025. 채팅 실시간 이미지 대기를 마스코트가 인물을 그리는 애니메이션으로 바꿈

- 결정일: 2026-10-06, 기록 확정 상태: Accepted
- 근거: [부분 렌더](../spec/3-1-client-spec.md#렌더와-스크롤), [채팅 스트림 로딩](../design/1-1-web-design.md), [W-024](#w-024)
- 대체 관계: W-024의 "채팅 장면 썸네일 자리는 점 로딩을 유지합니다"를 부분 대체합니다. 완성 중 표지에 관한 W-024의 나머지 결정은 그대로입니다.
- **맥락:** 실시간 이미지를 켠 턴은 응답까지 약 15초가 걸리는데, 그동안 썸네일 자리의 점 로딩은 무엇을 만드는지 보여 주지 않았습니다. 사용자 요청에 따라 인물 이미지를 그리는 중이라는 것이 전해지도록 완성 중 표지와 같은 마스코트 표현으로 바꿉니다.
- **결정:** 썸네일 자리에 완성 중 표지와 같은 방식(시간 → 자세 순수 함수 안무, Canvas 2D)으로 새 안무를 그립니다. 마스코트는 처음 한 번 화가 베레모를 쓰고 붓을 집어 든 뒤, 힘을 모으고 그 붓의 털 끝으로 크로키, 수채, 검은 종이 별자리처럼 분위기가 다른 인물 세 장을 그리며 사이사이 안도와 딴짓을 연기합니다. 준비를 포함해 약 15초 안에 세 장을 마치고, 응답이 더 늦으면 준비 없이 힘을 모으는 막부터 반복합니다. 인물은 사람 아이콘처럼 보이지 않게 옆선·머리카락·표정으로 그립니다. 낱동작·막 실행기·마스코트 그리기·캔버스 프레임 루프는 완성 중 표지와 함께 쓰는 공용 모듈로 옮깁니다. Android는 같은 안무 값으로 뒤따릅니다.
- **이유:** 완성 중 표지에서 쓴 순수 함수 안무는 순간이동 없음·무대 안 유지 같은 같은 테스트로 검증되고 Android로 값을 옮기기 쉽습니다. 채팅이 스튜디오 내부를 직접 가져오지 않도록 공용 부분을 도메인 밖으로 옮겼습니다. 그림의 붓길을 SVG path 문자열로 적으면 그려지는 선과 붓끝이 같은 길을 따르고, 인물 모양을 고칠 때 좌표만 바꾸면 됩니다. 완성 중 표지처럼 발을 붓 끝으로 쓰면 몸이 그림을 가려, 붓을 몸 옆에 들려 붓털 끝을 붓길에 붙잡고 몸 자리를 거꾸로 구합니다.
- **주요 영향:** 채팅 로딩은 `ImageGeneration`을 쓰지 않습니다. 완성 중 표지의 컴포넌트가 공용 `MascotStage`로 바뀌지만 값과 화면은 같습니다. 웹이 먼저 바뀌어 Android가 같은 안무로 따라오기 전까지 두 플랫폼의 대기 표현이 다릅니다. 같은 요청으로 두 무대의 바탕 점을 더 옅게(불투명도 0.45 → 0.25) 바꿔, Android가 따라오기 전까지 완성 중 표지의 바탕 점 진하기도 다릅니다. 안무를 바꿀 때는 Android 구현과 함께 고칩니다.

## W-026. 완성 중 표지 안무를 웹이 먼저 개편하고 Android가 같은 값으로 따라옴

- 결정일: 2026-10-06, 기록 확정 상태: Accepted
- 근거: [웹 제작 흐름](../spec/3-2-web-spec.md), [W-024](#w-024), [W-025](#w-025)
- 대체 관계: W-024의 "Android의 값을 그대로 TypeScript로 옮긴다"를 이 안무 개편에 한해 부분 대체합니다. 두 플랫폼이 같은 안무 값을 쓴다는 결정은 그대로입니다.
- **맥락:** 완성 중 표지의 그림 막이 능선과 해를 그려 흔한 이미지 아이콘처럼 보였고, 표정이 동그란 눈 하나뿐이었습니다. 사용자 요청에 따라 채팅 실시간 이미지 로딩(W-025)처럼 붓으로 인물을 그리고, 타자 전 에너지 드링크 막과 다양한 표정을 더합니다.
- **결정:** 웹 안무를 먼저 바꾸고 Android가 같은 값으로 이식합니다. 키워드·스토리라인·타자·뛰어다니기 막은 유지하고 표정과 소품을 더하며, 타자 앞에 에너지 드링크 막을 넣고, 그림 막은 베레모와 붓을 챙겨 세로 캔버스에 주인공 인물화를 그린 뒤 소품을 던지는 세리머니로 바꿉니다. 새 눈 모양, 베레모·붓, 붓길 해석·붓질은 채팅 로딩과 공용 모듈로 함께 씁니다.
- **이유:** 채팅 로딩에서 검증한 붓끝 고정 그리기와 SVG path 붓길을 그대로 쓰면 인물화를 좌표만으로 그릴 수 있고 두 무대의 표현이 맞춰집니다. 웹 캔버스에서 프레임을 빠르게 확인하며 다듬은 값을 Android가 옮기는 편이 두 플랫폼을 동시에 고치는 것보다 빠릅니다.
- **주요 영향:** 한 바퀴가 약 32초에서 37.71초로 늘어납니다. Android가 따라오기 전까지 두 플랫폼의 완성 중 표지 안무가 다릅니다. 완성 중 표지 비주얼 기준 이미지를 다시 만들어야 합니다.

## W-027. 채팅 실시간 이미지 대기 그림을 창가 인물화 한 장으로 바꾸고 붓을 몸과 따로 움직임

- 결정일: 2026-10-07, 기록 확정 상태: Accepted
- 근거: [부분 렌더](../spec/3-1-client-spec.md#렌더와-스크롤), [채팅 스트림 로딩](../design/1-1-web-design.md), [W-025](#w-025), [W-026](#w-026)
- 대체 관계: W-025의 "힘을 모으고", "크로키, 수채, 검은 종이 별자리처럼 분위기가 다른 인물 세 장을 그리며", "약 15초 안에 세 장을 마치고", "준비 없이 힘을 모으는 막부터 반복"을 대체합니다. 순수 함수 안무, 공용 모듈, 붓털 끝 고정 그리기, Android가 같은 값으로 따라온다는 W-025의 나머지 결정은 그대로입니다.
- **맥락:** 세 장을 15초 안에 그리느라 획이 빠르고 그림마다 짧게 끝나, 한 장의 그림이 완성되어 가는 느낌이 약했습니다. 붓은 몸에 고정되어 몸 전체만 움직였습니다. 사용자 요청에 따라 4:3 가로 종이에 인물과 배경이 있는 그림 한 장을 15초 동안 천천히 끝까지 그리고, 쉬는 동작은 유지하며, 붓도 함께 움직이게 합니다. 첫 시안은 획이 20번 남짓이라 움직임이 빨라 정신없다는 피드백을 받아, 힘을 모으는 막을 빼고 그림을 단순하게 줄였습니다.
- **결정:** 밤 창가에서 달을 보는 인물 한 장을 밑그림, 밑칠, 인물, 마무리 순서로 층을 쌓아 그리고, 사이에 휴와 딴짓을 둡니다. 그림은 창틀, 초승달과 밤 창, 옆모습, 달빛, 볼터치, 사인의 11획으로 줄이고 모든 획을 초당 격자 160칸보다 느리게 긋습니다. 준비 막 뒤에는 힘을 모으지 않고 바로 밑그림을 시작합니다. 무대 시작부터 15초에 사인을 마치고, 응답이 더 늦으면 완성 그림을 감상한 뒤 종이를 넘겨 밑그림부터 같은 그림을 다시 그립니다. 빨랫줄과 세 그림은 뺍니다. 공용 자세에 몸 기준 붓 회전과 붓털 누름을 더해 그을 때 끌림, 밑칠의 누름, 획 끝 튕김, 물그릇 헹굼, 쉬는 막의 붓 연기를 표현하고, 붓 회전까지 넣어 붓털 끝을 붓길에 붙잡습니다.
- **이유:** 층을 쌓는 순서는 응답이 어느 순간에 와도 그 순간의 종이가 그리는 중인 그림으로 읽히고, 한 장에 쓰는 시간이 늘어 획이 천천히 이어집니다. 능선과 해는 흔한 이미지 아이콘처럼 보였고(W-026 맥락), 동그란 머리와 대칭 어깨는 사람 아이콘처럼 보여, 창과 달을 배경으로 두고 인물은 비대칭 옆선으로 잡았습니다. 달을 종이 색으로 남기는 수채 표현은 회색 위주 색 규칙 안에서도 그림을 밝게 합니다. 붓 회전과 누름을 기본 0인 자세 값으로 두면 완성 중 표지는 바뀌지 않고, 그리기와 같은 순서로 붓털 끝을 계산하면 붓이 기울어도 선과 붓끝이 어긋나지 않습니다.
- **주요 영향:** 한 바퀴가 15.25초에서 16.43초로 늘어납니다. 동작 줄이기 정지 장면이 첫 그림을 마친 장면에서 완성 그림을 올려다보는 장면으로 바뀝니다. 웹이 먼저 바뀌어 Android가 같은 안무로 따라오기 전까지 두 플랫폼의 대기 표현이 다릅니다.

## W-029. 공개 오리지널 상세만 서버 렌더링하고 개인화는 다시 조회

- 결정일: 2026-10-08, 기록 확정 상태: Accepted
- 근거: [웹 검색 노출](../spec/3-2-web-spec.md#문서-열람과-검색-노출), [백엔드 읽기 가시성](../spec/4-backend-server-spec.md#4-3-api-계약)
- **맥락:** 오리지널 상세의 메타데이터는 서버에서 생성했지만 본문은 브라우저 조회 뒤에만 나타났습니다. 상세 응답에는 엔딩 달성 조건과 개인화 값도 있어 전체 응답을 초기 데이터로 전달할 수 없습니다.
- **결정:** 공개 오리지널 목록과 현재 공개 상세를 모두 확인하고 기존 화면에 필요한 공개 필드만 전달합니다. 메타데이터와 본문은 한 요청 안에서 조회를 공유합니다. 공개 초기값은 Query 캐시에 넣지 않고 인증된 클라이언트 조회를 계속합니다.
- **이유:** 숨김 본문이나 별도 검색 화면을 만들지 않고 첫 HTML을 제공하면서, 익명 초기값이 회원의 좋아요와 소유자 권한으로 사용되는 것을 막습니다. 익명 상세 404는 비공개도 뜻하므로 서버에서 미존재로 확정하면 소유자의 열람까지 차단합니다.
- **주요 영향:** 서버 상세 조회 실패는 색인을 허용하지 않고 기존 클라이언트 오류와 복구 흐름으로 넘깁니다. 미존재 URL의 HTTP 상태를 정밀하게 구분하려면 비공개를 안전하게 구별할 수 있는 백엔드 계약이 필요합니다. 채팅 시작은 인증된 상세 조회 완료까지 잠깐 비활성화됩니다.

## W-030. 탭으로 나가는 이동은 Navigation API로 아래 탭 기록까지 되돌아감

- 결정일: 2026-10-09, 기록 확정 상태: Accepted
- 근거: [웹 화면 전환 규칙](../spec/3-2-web-spec.md#화면-전환-규칙), [Android 내비게이션과 화면 계약](../spec/3-3-android-spec.md#3-3-3-내비게이션화면-계약)
- **맥락:** 제작 화면 나가기와 스토리, 채팅 삭제는 지금 화면을 탭으로 교체해, 그 탭에서 들어온 경우 같은 탭이 기록에 두 번 남아 뒤로가기 한 번이 아무 변화를 만들지 않았습니다. Android는 쌓인 화면을 걷어내고 하단 탭을 엽니다. 웹은 지나온 기록을 지울 수 없고, 앱 안 이동 추적은 진입 이후 이동이 있었는지만 알아 아래 기록이 어느 화면인지 모릅니다.
- **결정:** Navigation API `entries()`에서 가장 가까운 아래 탭 기록을 찾아 `history.go`로 되돌아갑니다. 갈 탭과 다르면 되돌아간 뒤 갈 탭을 `push`해 걷어낸 화면을 앞으로 가기에서도 없앱니다. API가 없거나 아래 탭 기록이 없으면, 또는 그 기록이 이전 문서에 있으면 지금처럼 교체합니다. 이전 문서로 돌아가면 문서를 다시 열어 떠나며 띄운 토스트가 사라지고 이어서 이동할 수도 없습니다. 이 결정은 KNK-1566의 일반 제작 승인 뒤 채팅방 아래 화면(채팅 목록)도 Android처럼 새 스토리 상세로 대체합니다.
- **이유:** 진입점마다 출발 화면을 표시해 넘기면 공유 링크, 온보딩, 카드처럼 진입 경로가 늘 때마다 표시를 빠뜨릴 수 있고, 새로고침으로 표시가 사라집니다. 브라우저가 가진 실제 기록을 읽으면 진입 경로와 관계없이 같은 판정을 합니다. 결제 복귀(W-023)에서 `entries()`를 쓰지 않은 이유는 다른 출처를 지나면 그 이전 항목이 보이지 않기 때문이며, 여기서는 아래 탭 기록이 같은 출처라 해당하지 않습니다.
- **주요 영향:** Navigation API가 없는 브라우저는 같은 탭이 두 번 쌓이는 기존 동작을 유지합니다. 탭 기록이 이전 문서에 있는 경우(새로고침, 로그인 복귀 뒤)도 같은 탭이 두 번 쌓일 수 있습니다. 하단 탭끼리의 이동은 계속 교체라 탭 화면의 뒤로가기는 Android와 달리 홈으로 가지 않습니다.

## W-031. 오버레이 뒤로가기 닫기를 히스토리 레이어 매니저로 통합

- 결정일: 2026-10-09, 기록 확정 상태: Accepted
- 근거: [공통 오버레이와 뒤로가기](../spec/3-1-client-spec.md#3-1-2-공통-계약과-플랫폼-경계), [웹 화면 전환 규칙](../spec/3-2-web-spec.md#화면-전환-규칙), [W-028](../domain/ACCOUNT/CLIENT/WEB/DECISIONS.md#w-028), [W-030](#w-030)
- **맥락:** 뒤로가기 가로채기가 `useCloseOnBack`, `usePreventPageLeave`, 게스트 동의 프로바이더에 흩어져 각자 더미 히스토리 항목을 쌓았고, 시트 27종 중 4종만 뒤로가기로 닫혔습니다. Android는 시스템 뒤로가기로 모든 시트를 닫습니다. 같은 클릭에서 드로어 닫기와 다이얼로그 열기가 겹치면 각자의 `history.back()`과 `pushState`가 어긋났고, 제작 퍼널 위에 시트가 열리면 시트의 뒤로가기가 퍼널 가드에도 닿았습니다.
- **결정:** 더미 히스토리 항목 방식을 유지하되 전역 레이어 스택 하나가 더미 쌓기와 되감기를 큐로 직렬화하고 캡처 단계 `popstate` 리스너로 맨 위 레이어에만 전달합니다. `Drawer`·`Dialog`·`AlertDialog` 래퍼가 기본으로 레이어를 열어 새 시트도 코드 없이 뒤로가기로 닫히고, 뒤로가기에 다른 의미를 주는 시트만 `closeOnBack`을 끕니다. 사용자 조작 없이 열린 오버레이는 더미를 쌓지 않습니다. 시트 안에서 떠나는 이동은 `leaveLayers`로 더미를 먼저 소비합니다.
- **이유:** Navigation API의 traverse 취소는 Chromium 계열에만 있어 Safari·Firefox용 더미 폴백을 함께 가져가야 하므로 보류했습니다. 시트마다 훅을 붙이는 방식은 누락이 반복됐고 더미 순서를 조율하는 곳이 없었습니다. Chrome은 조작 없이 쌓인 항목을 뒤로가기에서 건너뛰므로(W-028) 자동으로 열린 오버레이는 더미를 쌓아도 보장되지 않고 앞으로가기에 빈 칸만 남깁니다.
- **주요 영향:** 시트 안에서 `router.push`·`replace`·전체 이동을 부르는 새 코드는 `leaveLayers`를 거쳐야 돌아올 때 빈 칸이 남지 않습니다. 자동으로 열린 시트는 지금처럼 뒤로가기가 화면을 떠납니다. 주소로 바로 연 제작 화면은 첫 입력 전까지 이탈 확인이 없습니다. 되감기 대기 중 사용자가 뒤로가기를 한 번 더 누르면 그 입력은 되감기 결과로 흡수됩니다.

## W-033. 앱 안내 배너는 클라이언트에서 판정하고 패키지를 명시한 intent로 앱을 연다

- 결정일: 2026-10-12, 기록 확정 상태: Accepted
- 근거: [앱 안내 배너](../spec/3-2-web-spec.md#앱-안내-배너), [앱 안내 배너 구조](../design/1-1-web-design.md#앱-안내-배너-웹), [KNK-1630](https://kimandkang.atlassian.net/browse/KNK-1630)
- **맥락:** 모바일 웹 방문자를 Android 앱과 iOS 홈 화면 설치본으로 안내하는 배너가 필요했습니다. 노출은 브라우저 종류, 홈 화면 설치본 여부, 접속 회차에 따라 달라지고, Android 앱에는 외부 링크를 받는 intent-filter와 App Links가 없었습니다.
- **결정:** 노출은 클라이언트에서 UA와 브라우저 저장소로 판정합니다. Android 앱 열기는 App Links 대신 `package=app.manyak`를 명시한 `intent://` 링크로 하고, 앱은 전용 스킴 `manyak://manyak.app` intent-filter로 받습니다. 어트리뷰션 SDK의 스마트 배너는 쓰지 않습니다.
- **이유:** 서버 판정은 홈을 매 요청 동적 렌더로 바꾸면서도 접속 회차와 설치본 여부를 알 수 없어 결국 클라이언트 판정이 섞입니다. 패키지를 명시한 intent는 도메인 검증 없이 설치 여부에 따라 앱 또는 플레이스토어로 갑니다. 받는 쪽을 검증되지 않은 https 필터로 두면 Android 11 이하(minSdk 24)에서 다른 앱의 manyak.app 링크마다 앱 선택창이 떠서, https 링크와 겹치지 않는 전용 스킴을 씁니다. SDK는 비용, 웹과 앱 양쪽 도입, 처리방침 개정이 필요합니다.
- **주요 영향:** 배너는 하이드레이션 뒤 나타납니다. 앱이 열렸는지 플레이스토어로 갔는지 웹에서 구분할 수 없어 설치는 Play Console과 referrer로 봅니다. App Links와 설치 뒤 목적지 복원은 후속(KNK-927, 디퍼드 딥링크)입니다.

## W-035. 겹치는 operationId는 메서드와 경로로 생성 이름을 고정

- 결정일: 2026-10-15, 기록 확정 상태: Accepted
- 근거: [요청 흐름](../design/1-1-web-design.md#요청-흐름), [KNK-1655](https://kimandkang.atlassian.net/browse/KNK-1655)
- **맥락:** 백엔드(Springdoc)는 Java 메서드 이름으로 operationId를 만들고, 이름이 겹치면 스캔 순서대로 `get`, `get_1`, `get_2`처럼 순번을 붙입니다. Orval은 이 값으로 훅 이름(`useGet1`)을 만듭니다. 임시 저장 API(`story-draft-controller`)가 추가되자 순번이 하나씩 밀려 `useList1` 같은 import가 깨졌고, `useGet3`은 이름이 남은 채 화풍 목록 대신 장르 목록을 가리켰습니다.
- **결정:** Orval 입력 변환기(`input.override.transformer`)로 스펙을 생성 전에 고칩니다. 순번 접미사(`_숫자`)를 뗀 기본 이름이 둘 이상인 operationId는 모두 HTTP 메서드와 경로 이름으로 바꾸고(`GET /api/v1/stories/submissions/{id}` → `getStoriesSubmissionsById`), 겹치지 않는 이름은 그대로 둡니다. API와 Zod 생성에 같은 변환기를 씁니다.
- **이유:** 메서드와 경로는 API 계약 자체라 백엔드 메서드가 늘거나 스캔 순서가 바뀌어도 변하지 않습니다. 같은 이름이 다른 API를 가리키는 일은 없어집니다. 모든 이름을 경로로 바꾸면 이미 쓰는 고유 이름(`getStoryDetail` 등)까지 바뀌어, 겹치는 이름만 바꿉니다. 근본 해결은 백엔드가 `@Operation(operationId = ...)`로 고유 이름을 다는 것이지만 백엔드 코드라 웹에서 정하지 않습니다.
- **주요 영향:** 지금 고유한 이름도 나중에 백엔드에 같은 이름의 메서드가 생기면 경로 이름으로 바뀌어 import가 깨집니다. 다만 다른 API를 가리키지 않고 typecheck에서 드러납니다. 경로가 바뀌면 이름도 바뀝니다. 생성 훅 이름은 길어집니다.

## W-036. 회원 일반 제작 임시 저장본은 서버에만 둔다

- 결정일: 2026-10-16, 기록 확정 상태: Accepted
- 근거: [FE-SCREEN-009 임시 저장](../spec/3-1-client-spec.md#fe-screen-009-일반-제작스토리-수정), [스토리 제작 임시 저장](../spec/4-backend-server-spec.md#story-drafts), [KNK-1667](https://kimandkang.atlassian.net/browse/KNK-1667)
- **맥락:** 일반 제작 임시 저장본이 브라우저 IndexedDB에만 있어 다른 기기나 브라우저에서 이어서 만들 수 없고 로그아웃하면 사라졌습니다. 서버 임시 저장 API(KNK-1641)가 멱등 PUT과 버전 충돌(409)을 제공합니다.
- **결정:** 일반 제작은 회원 전용이므로 임시 저장본을 서버 초안에만 둡니다. 기기 안 캐시나 동기화 상태는 두지 않습니다. 초안 ID는 화면마다 고정한 기존 `requestId`를 그대로 씁니다. 화면 숨김 저장은 `keepalive` PUT으로 보내고 실패를 알리지 않습니다. 서버 연동 전 기기에 남은 일반 제작 저장본은 제작 탭 진입 때 같은 ID로 옮깁니다. 간편 제작과 게스트의 IndexedDB 초안, 그리고 [W-017](#w-017)의 목록 구조는 바꾸지 않습니다.
- **이유:** 서버의 같은 내용 재전송 허용과 버전 판정만으로 재시도와 여러 기기 저장을 다룰 수 있어, 기기 안 사본과 서버 사이의 동기화 상태를 따로 관리할 이유가 없습니다. 일반 제작은 처음부터 한 화면이 한 ID를 쓰므로 단계마다 ID가 바뀌는 간편 제작과 달리 ID 구조를 바꾸지 않아도 됩니다.
- **주요 영향:** 오프라인에서는 임시 저장할 수 없고 기존 저장 실패 안내를 띄웁니다. 새로고침 경고는 그대로 두어 화면 숨김 저장이 끝나지 못한 변경을 지킵니다. 옮긴 레거시 초안의 처음 저장 시각은 옮긴 시각으로 바뀝니다.

<a id="w-037"></a>

## W-037. 회원 간편 제작 초안은 세션 고정 ID로 서버에 두고 진행 기록은 기기 안에 남긴다

- 결정일: 2026-10-16, 기록 확정 상태: Accepted
- 근거: [간편 제작 임시 저장](../spec/3-1-client-spec.md#임시-저장), [스토리 제작 임시 저장](../spec/4-backend-server-spec.md#story-drafts), [KNK-1667](https://kimandkang.atlassian.net/browse/KNK-1667)
- **맥락:** [W-036](#w-036)은 일반 제작만 서버로 옮기고 간편 제작은 그대로 두었습니다. 간편 제작은 키워드 초안, 생성 중, 스토리라인 초안, 완성 중이 단계마다 다른 `requestId` 기록으로 바뀌는 구조([W-017](#w-017))라 서버 초안 하나에 그대로 대응하지 않습니다. 서버는 게스트 때 만든 생성 요청을 회원 초안에 연결하지 않고, 초안은 간편 제작과 일반 제작을 합쳐 회원당 5개까지입니다.
- **결정:** 퍼널을 열 때 세션의 저장 위치를 정합니다. 회원이 새로 시작했거나 서버 초안으로 연 세션은 세션마다 고정한 draftId로 키워드 초안과 스토리라인 초안을 서버에 덮어쓰며, 이 세션에서는 [W-017](#w-017)의 "안정적인 초안 ID를 두지 않는다"를 대체합니다. 생성 중, 생성 결과, 완성 중, 완성 실패 기록은 지금처럼 기기 안에 두고 서버 초안 ID와 기준 버전을 붙입니다. 생성 결과는 받자마자 올리지 않고 다음 사용자 저장 때 올립니다. 게스트 세션과 서버 연동 전이나 게스트 때 만든 기기 안 초안은 옮기지 않고 기기 안에 계속 저장합니다.
- **이유:** 진행 기록은 서버 생성 요청 복구 조회와 원 POST 보류 판정에 묶여 있어 기기 안에 두는 편이 기존 복구 흐름을 그대로 씁니다. 생성 결과를 받자마자 올리거나 기존 초안을 한꺼번에 옮기면 보기만 하고 떠난 제작이 5개 상한을 채워 일반 제작 저장까지 막습니다. 게스트 때 만든 스토리라인 초안은 서버가 연결을 거절하므로 기기 안 저장을 유지해야 이어서 만들 수 있습니다.
- **주요 영향:** 생성 결과는 다음 저장 전까지 그 기기에만 있어 다른 기기는 이전 서버 초안을 봅니다. 같은 제작의 서버 카드는 기기 안 진행 기록이 있고 그 기록 뒤로 서버 초안이 다시 저장되지 않은 동안 숨기고, 그 기기 안 카드를 지우면 숨긴 서버 초안도 지웁니다. 기록 뒤에 다른 기기가 저장한 서버 초안은 따로 보이고 남깁니다. 완성 요청 때 서버가 지운 초안을 실패 뒤 다시 저장하면 처음 저장 시각이 바뀝니다. 기존 기기 안 간편 제작 초안은 다른 기기에서 이어서 만들 수 없습니다. 저장 훅과 충돌 다이얼로그는 두 제작 방식이 함께 쓰도록 `stories/_shared`로 옮깁니다.

## W-038. 회원은 만들고 있는 스토리 카드가 5장이면 새 제작을 막는다

- 결정일: 2026-10-17, 기록 확정 상태: Accepted
- 근거: [제작 카드와 다중 완성 진행](../spec/3-1-client-spec.md#제작-카드와-다중-완성-진행), [스토리 제작 임시 저장](../spec/4-backend-server-spec.md#story-drafts), [KNK-1667](https://kimandkang.atlassian.net/browse/KNK-1667)
- **맥락:** [W-037](#w-037)은 생성 결과를 받자마자 서버에 올리지 않고 기기 안 카드로 둡니다. 서버 초안이 5개로 가득 찬 회원도 새 간편 제작을 시작해 스토리라인까지 받을 수 있었고, 그 결과는 서버에 올라갈 자리가 없어 그 기기에만 남았습니다. 제작 탭 카드는 5장을 넘었고, 결과를 받은 직후의 "임시 저장"은 기기 안 기록을 저장본으로 보고 "임시 저장했어요"를 띄워 다른 기기에서 보이지 않는 저장을 저장된 것처럼 알렸습니다.
- **결정:** 회원은 제작 탭에 보이는 만들고 있는 스토리 카드(서버 초안과 이 기기의 진행 기록을 같은 제작 한 장으로 센 병합 결과)가 5장 이상이면 새 제작을 시작하지 않고 토스트로 알립니다. 제작 FAB 클릭과 두 제작 화면의 새 세션 판정에서 막아 온보딩, 공유 열람 CTA, 직접 주소 진입까지 덮습니다. 이어서 만들기와 목록을 읽지 못한 경우는 막지 않습니다. 게스트는 적용하지 않습니다.
- **이유:** 서버 초안 수만 세면 서버에 없는 생성 결과 카드가 계속 늘어 문제가 남습니다. 보이는 카드 수로 세면 서버 초안 하나는 카드 많아야 한 장이라, 상한 아래에서 시작한 제작은 첫 저장에 서버 자리가 있고 카드 수도 사용자가 보는 상한과 맞습니다. 생성 결과를 받자마자 올리는 방법은 보기만 하고 떠난 제작이 자리를 차지하고, 가득 차면 결국 기기 안에만 남아 이 결정을 대신하지 못합니다. 페르소나 10개 상한과 같이 이동하지 않고 토스트로 알립니다.
- **주요 영향:** 이미 5장 이상인 회원은 4장 이하가 될 때까지 새로 만들 수 없습니다. 완성 실패로 초안이 되돌아오거나 두 기기에서 동시에 시작하면 6장이 될 수 있고, 이때 서버 저장은 기존 상한 토스트로 막힙니다. 간편 제작 주소로 바로 들어와 막힌 경우에도 퍼널이 먼저 열려 `client_storyCreate_viewed`는 발생합니다(일반 제작은 폼을 열지 않아 조회 이벤트가 없습니다).

## W-039. 간편 제작은 단계를 옮겨도 저장하지 않는다

- 결정일: 2026-10-17, 기록 확정 상태: Accepted
- 근거: [웹 제작 흐름](../spec/3-2-web-spec.md#3-2-3-웹-제작-흐름), [Android 제작과 데이터 보존](../spec/3-3-android-spec.md#3-3-3-제작과-데이터-보존), [KNK-1667](https://kimandkang.atlassian.net/browse/KNK-1667)
- **대체 범위:** [W-020](#w-020)의 저장 계기 중 단계 이동만 대체합니다. "임시 저장" 버튼과 화면 숨김 저장, 생성 요청과 결과의 즉시 저장은 유지합니다.
- **맥락:** 간편 제작 초안이 서버 초안이 되면서([W-037](#w-037)) 단계 이동 저장은 스토리라인을 고르거나 다시 고를 때마다 알림 없이 서버 PUT을 보냈습니다. Android는 처음부터 버튼과 백그라운드 전환에서만 저장해, 같은 초안을 두 플랫폼이 다른 시점에 저장했습니다.
- **결정:** 웹 간편 제작도 "임시 저장" 버튼과 화면 숨김에서만 저장합니다. 스토리라인을 골라 추가 정보로 가거나 "다시 선택하기"로 돌아와도 저장하지 않습니다.
- **이유:** 사용자가 누른 저장과 앱을 떠날 때의 저장만 남겨 저장 시점이 분명하고, 두 플랫폼의 저장 계기가 같아집니다. 단계 이동은 입력을 확정하는 동작이 아니라 알림 없는 서버 저장이 필요하지 않습니다.
- **주요 영향:** 스토리라인을 고르고 저장하지 않은 채 닫으면 고른 단계는 남지 않고 확인 다이얼로그가 저장하지 않은 내용을 알립니다. `client_storyCreate_draftSaved`는 버튼과 화면 숨김 저장의 쓰기 성공에서만 발생합니다. 일반 제작의 탭 이동 저장은 이 기록의 범위가 아닙니다.

## W-041. Android 앱 열기가 일어나지 않으면 플레이스토어 주소로 직접 이동

- 근거: [앱 안내 배너](../spec/3-2-web-spec.md#앱-안내-배너), [앱 안내 배너 구조](../design/1-1-web-design.md#앱-안내-배너-웹), [KNK-1716](https://kimandkang.atlassian.net/browse/KNK-1716)
- **보완 범위:** [W-033](#w-033)의 "패키지를 명시한 intent는 설치 여부에 따라 앱 또는 플레이스토어로 간다"를 보완합니다. intent 링크로 앱을 여는 방식은 유지합니다.
- **맥락:** Android 인스타그램 인앱 브라우저는 앱이 없으면 intent 링크를 받고 아무것도 열지 않습니다. 실기기(Galaxy S25, Android 17) logcat에서 액티비티 시작 기록이 없었고, `S.browser_fallback_url`을 넣어도 같았습니다. 같은 화면에서 `market://`과 `https://play.google.com` 주소는 플레이스토어를 열었습니다.
- **결정:** Android 앱 열기를 누른 뒤 0.7초 안에 문서가 한 번도 숨겨지지 않으면 `https://play.google.com/store/apps/details?id=app.manyak`(배너 referrer 포함)로 이동합니다. intent 링크에는 `browser_fallback_url`을 넣지 않습니다.
- **이유:** 인앱 브라우저가 intent를 버리는지 웹에서 미리 알 수 없어, iOS 인앱 외부 전환 실패 판정과 같은 문서 숨김 감지로 실패를 판단합니다. 대기 1.5초는 실패한 사용자가 체감할 만큼 길었고, 카카오톡에서 앱 실행 시도부터 플레이스토어가 뜨기까지 수십 ms였으므로 0.7초로 줄였습니다. `market://` 대신 https 주소를 쓰는 이유는 플레이스토어가 없는 기기에서도 웹 페이지로 열리기 때문입니다.
- **주요 영향:** 인스타그램에서 앱이 없으면 0.7초 뒤 플레이스토어가 열립니다. 앱이 설치된 느린 기기에서 0.7초 안에 앱이 뜨지 않으면 플레이스토어가 함께 열릴 수 있습니다. Chrome과 카카오톡은 기존처럼 플레이스토어를 바로 열고 두 번 열지 않습니다.
