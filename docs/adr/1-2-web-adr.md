- **처음 보는 사람** — 기록 규칙을 읽고, 목차에서 관련 주제의 기록으로 이동합니다. 문서 작성일·수정일은 개별 결정일과 구분합니다.
- **구현자** — [현재 스펙](../spec/3-2-web-spec.md)과 해당 설계를 먼저 확인하고, 선택 이유가 필요한 지점의 ADR을 읽습니다. 과거 기록을 현재 동작의 기준으로 사용하지 않습니다.
- **리뷰·변경 작성자** — 관련 결정과 후속 대체 관계를 함께 확인합니다. 확정된 본문은 보존하고 새 기록에 대체하는 ID·범위를 남깁니다.

## W-001. SSE를 fetch와 ReadableStream으로 수신

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문 W:87](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L87-L99)
- **맥락:** 채팅 턴은 사용자 입력을 POST 본문에 실어 보내고 SSE로 응답받습니다.
- **결정:** `fetch`와 `ReadableStream`으로 수신합니다.
- **이유:** 표준 EventSource는 GET만 지원해 해당 POST 본문 계약을 충족하지 못합니다.
- **주요 영향:** 이벤트 파싱·EOF 처리를 직접 소유하고 일반 요청 타임아웃과 스트림 수명을 구분합니다.

<a id="w-002"></a>

## W-002. 게스트 서재 초기 상태를 세 가지로 구분

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문 W:102](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L102-L120)
- **맥락:** SSR 시점에는 localStorage를 읽을 수 없습니다.
- **결정:** `null`은 미확정, 빈 배열은 빈 서재, 값이 있는 배열은 조회 대상으로 구분합니다.
- **이유:** 빈 배열 하나로 초기화하면 데이터가 있는 사용자에게도 빈 서재가 먼저 깜빡입니다.
- **주요 영향:** 목록과 온보딩은 저장소 확인 뒤에 판정합니다.

## W-003. BFF를 백엔드 호출과 토큰 보관의 단일 창구로 사용

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문 W:370](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L370-L407)
- **맥락:** 브라우저 직접 호출과 토큰 저장 위치를 선택해야 했습니다.
- **결정:** 동일 출처 BFF를 사용하고 access·refresh는 httpOnly 쿠키로 보관합니다.
- **이유:** 백엔드 주소와 인증 토큰을 브라우저 JavaScript에 노출하지 않기 위해서입니다.
- **주요 영향:** BFF가 스트리밍 전달·선제 재발급을 소유하고 회원 판정은 별도 응답에 의존합니다.

<a id="w-004"></a>

## W-004. 이관 제출 뒤 게스트 ID를 일괄 정리

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문 C:582](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-1-client.md#L582-L590)
- **맥락:** 회원 이관의 일부 항목이 실패할 때 로컬 ID를 남길지 선택해야 했습니다.
- **결정:** 이관 결과와 무관하게 게스트 배열을 정리하고 성공한 수만 안내합니다.
- **이유:** 회원 서재의 정본은 서버이며 실패 ID를 남기면 로그아웃 뒤 게스트 데이터와 혼합될 수 있습니다.
- **주요 영향:** 실패 항목을 자동 재시도 목록으로 남기지 않습니다.

<a id="w-005"></a>

## W-005. 로그인 핸드오프 데이터를 ID 스냅숏으로 식별

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문 W:524](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L524-L542)
- **맥락:** 인앱 브라우저에서 만든 데이터를 외부 브라우저 로그인으로 전달해야 했습니다.
- **결정:** 핸드오프 발급 시 ID 스냅숏을 사용하고 복귀 정리는 서버 상태 조회 결과로 판정합니다.
- **이유:** 기존 이관·원자 클레임을 재사용하고 브라우저 간 로컬 상태 추측을 피하기 위해서입니다.
- **주요 영향:** 핸드오프 뒤 새로 만든 콘텐츠는 보존하며, 상태 조회가 이관·만료·종결 계측의 기준이 됩니다.

## W-006. 공유 진입을 헤더 버튼으로 표시

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문 C:1021](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-1-client.md#L1021-L1027)
- **맥락:** 공유 진입이 옵션 메뉴에 있으면 발견하기 어려웠습니다.
- **결정:** 헤더의 홈 버튼 자리에 공유 아이콘을 둡니다.
- **이유:** 공유가 화면 안에서 직접 발견되도록 하기 위해서입니다.
- **주요 영향:** 아이콘의 접근성 이름을 제공하고 발급 전 확인을 유지합니다. 이 기록의 당시 메뉴 구성은 후속 신고 기능의 현재 구성을 덮어쓰지 않습니다.

## W-007. 계정 연동에 별도 NextAuth 공급자 사용

- 결정일: 2026-08-01 · 기록 확정 상태: Accepted
- 근거: [이관 원문 W:418](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L418-L427)
- **맥락:** 계정 연동은 현재 회원 세션을 유지한 채 신선한 ID 토큰을 받아야 합니다.
- **결정:** 연동 전용 공급자 변형과 콜백을 사용합니다.
- **이유:** 일반 로그인 흐름을 재사용하면 백엔드 로그인이 호출되어 현재 세션을 교체합니다.
- **주요 영향:** 연동 콜백·자격증명·SDK 세션 처리를 로그인과 구분하고 추가 콜백 URL을 운영 설정에 등록합니다.

## W-008. 제작 재개 의도를 URL 대신 세션스토리지에 기록

- 결정일: 2026-08-27 · 기록 확정 상태: Accepted
- 근거: [이관 원문 C:835](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-1-client.md#L835-L836), [이관 원문 W:139](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L139-L142)
- **맥락:** 재개 쿼리 파라미터가 라우터 캐시 재진입 시 마운트보다 늦게 반영될 수 있었습니다.
- **결정:** 이동 전에 재개 의도를 세션스토리지에 동기 기록합니다.
- **이유:** 컴포넌트 마운트와 히스토리 URL 반영의 순서에 의존하지 않기 위해서입니다.
- **주요 영향:** 재개와 새로 만들기의 의도를 라우팅 전에 확정합니다.

## W-009. 인앱 진입 차단을 로그인 시점 핸드오프로 대체

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L466-L505)
- **맥락:** 인앱과 외부 브라우저의 저장소가 격리됩니다.
- **결정:** 인앱에서 게스트 체험을 허용하고 외부 전환이 필요한 로그인만 핸드오프합니다.
- **이유:** 광고 유입 사용자가 체험 전에 외부 브라우저 요구를 만나 이탈한다는 가설에 따른 결정입니다.
- **주요 영향:** 진입 전면 차단·자동 탈출을 대체합니다. 체험 이중 사용 수용 여부와 제3자 인앱 로그인 지원은 별도 확인 사항으로 남습니다.

## W-010. 인앱 복귀 정리는 핸드오프 상태 조회로 판정

- 결정일: 원문 미기재 · 기록 확정 상태: Accepted
- 근거: [이관 원문](https://github.com/KIM-N-KANG/knk-harness/blob/2d77abce078b75e168d8f924e3759e3bb624515a/docs/product-specs/3-2-web-app.md#L522-L542)
- **맥락:** 인앱과 외부 브라우저의 저장소가 격리됩니다.
- **결정:** 상태 API 한 번으로 이관 성공 ID만 정리합니다.
- **이유:** 리소스별 403은 요청 수가 늘고 이관·타인 클레임·삭제를 구분하지 못합니다.
- **주요 영향:** 생성 이후 새 게스트 콘텐츠와 이관 실패 ID를 보존합니다. W-005의 ID 스냅숏 선택과 연결됩니다.

- **맥락:** 게스트 제작·채팅 체험을 신규 경로에서 없애고 로그인 직후 명시 동의를 받게 되면서, 동의를 마치지 않은 로그인이 탭을 닫아도 쿠키로 남는 문제가 생겼습니다. 서버는 미동의 회원의 다른 API를 막지 않고, 브라우저 쿠키는 탭 단위로 격리할 수 없습니다.
- **결정:** 동의 상태는 루트의 동의 게이트 한 곳에서 `GET /users/me/consents`로 판정하고, 회원 기능·로그인 직후 부수 효과·회원 전용 자동 조회는 모두 `isMember`(인증 + 동의 완료)로만 엽니다. OAuth 시작 직전에 `sessionStorage`에 탭 로그인 표시를 남기고, 인증 상태인데 필수 동의가 남았으며 표시가 없는 일반 진입은 이전 탭의 미완 로그인으로 보고 로그아웃합니다. 공개 법적 문서 경로는 이 판정에서 제외합니다. 게스트 보호 기능 진입은 요청·이동 전에 `requireLogin`으로 한 번 확인합니다.
- **이유:** 서버가 막지 않는 상태에서 화면별로 세션·동의를 따로 판정하면 누락된 진입점이 남습니다. `localStorage`나 쿠키 플래그는 탭을 닫아도 남아 "탭 종료 시 로그인 미유지"를 만들 수 없고, `sessionStorage`는 OAuth 복귀·같은 탭 새로고침을 이어 주면서 다른 탭·새 브라우저 실행에는 남지 않는 가장 작은 장치입니다. 문서 탭이 원래 탭의 쿠키를 지우는 사고를 막으려면 법적 문서 경로만 예외로 두는 편이 단순합니다.
- **주요 영향:** 동의 완료 여부의 정본은 서버 조회이며 탭 표시는 판정 보조라 탭 복원·복제·`noopener` 없는 새 창에서 복사될 수 있음을 문서에 남깁니다. 게스트 체험 한도 선차단·한도 시트·`client_guestLimitDialog_*` 이벤트는 신규 경로에서 사라지고, 회원 402는 이프 부족 토스트만 남습니다. 예전 게스트 로컬 데이터·핸드오프 이관은 복구용으로 유지합니다. W-009의 인앱 게스트 체험 허용은 열람만 허용하는 것으로 좁아집니다.

## W-012. 게스트 체험은 별도 동의 후 허용

- 결정일: 2026-09-20, 기록 확정 상태: Accepted
- 근거: [게스트 이용 동의](../spec/3-2-web-spec.md#게스트-이용-동의), [게스트 동의 시트](../design/1-1-web-design.md#게스트-동의-시트-웹)
- **대체 범위:** W-011 중 게스트의 제작과 채팅 진입에 로그인을 강제하고 체험을 열람으로 제한한 부분만 대체합니다. 회원의 서버 동의 판정과 동의 전 세션 정책은 유지합니다.
- **맥락:** 로그인 전에도 제작과 채팅을 체험하게 하되 게스트에게 적용되는 이용 조건과 개인정보 수집 및 이용, 만 14세 이상 확인을 먼저 고지해야 합니다. 게스트 동의 API는 아직 없습니다.
- **결정:** 제작 진입 및 채팅 전송 앞에서 공용 바텀 시트를 열고 상세 보기와 단일 동의 버튼을 제공합니다. 동의 버전과 시각은 브라우저에 저장하며 동의하면 대기 중인 동작 하나만 이어갑니다. 체험 한도는 서버 정책을 따르고 소진 시 로그인을 안내합니다.
- **이유:** 회원 동의 API를 게스트에게 재사용하거나 가상 API를 만드는 대신 현재 가능한 로컬 흐름만 구현합니다. 시크릿 모드를 탐지하지 않고 브라우저 저장소 격리로 새 시크릿 세션에서 다시 동의받습니다.
- **주요 영향:** 로컬 기록은 서버 증빙이나 보안 경계가 아닙니다. 저장소를 사용할 수 없으면 현재 페이지에서만 동의를 유지합니다. API 제공 시 서버 기록 성공 기준으로 교체하고, 문서 개정 공개 시 회원 요구 버전과 배포 일정을 조율합니다.

## W-013. 게스트 제작 동의는 스토리라인 생성 직전에 확인

- 결정일: 2026-09-20, 기록 확정 상태: Accepted
- 근거: [게스트 이용 동의](../spec/3-2-web-spec.md#게스트-이용-동의)
- **대체 범위:** W-012의 제작 화면 진입 전 동의만 대체하며 채팅, 회원 동의와 저장 방식은 유지합니다.
- **결정과 이유:** 먼저 키워드를 입력할 수 있도록 제작 진입과 초안 재개는 허용하고, 입력 검증을 통과한 스토리라인 생성 버튼에서 서버 요청 직전에 동의를 받습니다. 이미 있는 생성 요청 가드를 재사용합니다.
- **주요 영향:** 취소 시 입력과 단계를 유지하며 동의 후 대기 요청 하나만 실행합니다. 동의 시트가 열린 동안 제작 화면의 뒤로가기 가드는 처리하지 않아 종료 확인창이 겹치지 않게 합니다.

## W-014. 인앱 로그인을 Auth.js 팝업으로 시작하고 로그인 화면 유지

- 결정일: 2026-09-19, 기록 확정 상태: Accepted
- 근거: [웹 로그인 계약](../spec/3-2-web-spec.md#인앱-브라우저와-로그인-핸드오프), [구현 구조](../design/1-1-web-design.md#인앱-브라우저의-google-인증-팝업)
- **맥락:** 기존 외부 전환 직행은 로그인 화면을 건너뛰며 원래 인앱의 회원 세션을 만들지 않습니다.
- **결정:** KakaoTalk, Instagram, Threads는 OS에 관계없이 일반 로그인 화면을 유지합니다. Google은 기존 Auth.js 팝업, Kakao는 같은 탭의 redirect로 시작하며 신규 핸드오프를 만들지 않습니다. PKCE, state, nonce 및 기존 callback과 백엔드 세션 발급을 재사용합니다.
- **이유:** 별도 SDK나 코드 교환기를 추가하지 않고 기존 인증 보안 경계에서 인앱 로그인을 시도할 수 있습니다.
- **주요 영향:** W-009의 신규 로그인 외부 전환을 대체하고 W-010의 기존 핸드오프 복구는 유지합니다. 완료 메시지는 origin, source와 시도 ID를 검증한 후 원래 창의 Auth.js 세션 및 인증 API로 재확인합니다. 창 연결과 쿠키 저장소 공유 및 실제 앱의 인증 허용은 별도 실기기 검증 대상입니다.

## W-015. 팝업 참조 단절과 인증 취소를 구분

- 결정일: 2026-09-20, 기록 확정 상태: Accepted
- 근거: [웹 로그인 계약](../spec/3-2-web-spec.md#인앱-브라우저와-로그인-핸드오프), [팝업 구조](../design/1-1-web-design.md#인앱-브라우저의-google-인증-팝업), [Window.open 반환값](https://developer.mozilla.org/en-US/docs/Web/API/Window/open#return_value)
- **맥락:** COOP로 창 연결만 끊겨도 closed가 true가 됩니다. 대기 만료 시 인증창을 닫으면 2단계 인증이나 복구 입력을 중단시킵니다.
- **결정:** W-014의 팝업 시작과 세션 확인을 유지하며, 창 참조 단절만으로 취소하지 않습니다. 5분 만료는 원래 문서의 대기만 끝냅니다. 재시도 시 제어 가능한 이전 창을 정리하고 시작 요청은 직렬화합니다.
- **이유:** 브라우저 참조 상태나 클라이언트 타이머는 서버 인증 취소의 증거가 아닙니다.
- **주요 영향:** 직접 닫은 창도 명시적 실패를 확인하지 못하면 만료까지 기다릴 수 있습니다. 원래 창의 두 세션 검증과 완료 메시지 검증은 유지하며, 늦은 조회 결과로 이동하지 않습니다. 계정 연동의 Google에도 동일한 PKCE, state, nonce 검증을 적용합니다.

## W-016. 게스트 동의의 정본을 서버 기록으로 전환

- 결정일: 2026-09-20, 기록 확정 상태: Accepted
- 근거: [게스트 이용 동의](../spec/3-2-web-spec.md#게스트-이용-동의), [게스트 동의 시트](../design/1-1-web-design.md#게스트-동의-시트-웹)
- **대체 범위:** W-012의 브라우저 동의 기록과 메모리 폴백만 대체합니다. W-013의 동의 시점과 기존 안내 UI, 회원 동의 계약은 유지합니다.
- **결정과 이유:** 게스트 동의 GET/POST API가 제공되어 기존 생성 훅과 공통 기기 식별자 헤더로 연동합니다. 매 동작 직전 서버 상태를 확인하고 명시적으로 수락한 버전의 저장 성공 뒤 한 동작만 재개합니다. 조회 및 저장 실패와 응답 누락은 차단하고 버전 충돌은 최신 상태 확인 후 다시 명시 동의받습니다. 로컬 기록을 자동으로 서버 동의로 이전하지 않습니다.
- **주요 영향:** 기기 식별자가 바뀐 새로운 시크릿 세션은 재동의 대상입니다. 게스트 API는 `guestPrivacy`만 기록하며 회원 동의로 이관하지 않습니다. 기존 서버 API 자체의 미동의 차단이나 production 식별자 생성 방식을 이 작업에서 새로 만들지 않습니다.

## W-017. 편집 초안을 같은 키의 목록으로 확장

- 결정일: 2026-09-22, 기록 확정 상태: Accepted
- 근거: [제작 카드와 다중 완성 진행](../spec/3-1-client-spec.md#제작-카드와-다중-완성-진행), [웹 제작 흐름](../spec/3-2-web-spec.md#3-2-3-웹-제작-흐름), [게스트 저장소 키](../design/1-1-web-design.md#게스트-저장소-키-웹)
- **맥락:** 완성 요청은 목록이지만 편집 초안은 슬롯 한 건이라 초안이 있으면 새 제작 전에 이어서/새로 만들기를 골라야 했고 새로 만들면 기존 초안이 사라졌습니다.
- **결정:** `manyak:pending-creation-request` 값을 레코드 배열로 바꾸고 구 단일 객체는 1건 목록으로 읽습니다. 안정적인 초안 ID를 새로 두지 않고 기존 `requestId`를 목록 키로 유지하며, 퍼널 한 세션이 자기 레코드 한 건만 소유하는 규칙을 퍼널 훅 한 곳(`persistOwnRecord`)에 둡니다.
- **이유:** 단계 전환은 이미 옛 레코드를 지우고 새 레코드를 넣는 방식이라 목록화만으로 같은 결과가 나며, 서버 복구 조회 키가 `requestId`라 별도 매핑이 필요 없습니다. 같은 키를 쓰면 배포 시점에 남은 사용자 초안을 파서 호환 한 줄로 보존합니다.
- **주요 영향:** 이어서/새로 만들기 다이얼로그와 `client_storyCreate_resumeDialog_*` 이벤트를 제거합니다. 퍼널 직접 진입·FAB은 항상 새 세션이고 재개는 진행 카드에서만 합니다. 완성 실패 강등은 다른 초안이 있어도 항상 초안으로 되돌립니다. Android는 KNK-1395로 같은 계약을 따릅니다.

## W-018. 웹 푸시는 Firebase 토큰 SDK와 제작 직후 프롬프트로 도입

- 결정일: 2026-09-22, 기록 확정 상태: Accepted
- 근거: [웹 PWA 푸시](../spec/3-2-web-spec.md#pwa-푸시), [디바이스 푸시 토큰·발송 모듈](../spec/4-backend-server-spec.md#4-3-api-계약), [BE-039](2-backend-server-adr.md#be-039), [Android 알림 계약](../spec/3-3-android-spec.md#3-3-5-알림)
- **맥락:** 서버는 `platform=WEB` 토큰 등록과 webpush notification 발송을 이미 지원했지만 웹에는 매니페스트·서비스 워커·토큰 등록이 없었습니다. Next.js PWA 가이드는 순수 Web Push(`PushSubscription`+VAPID 서버 액션)를 쓰는데 서버는 FCM 토큰으로 발송합니다.
- **결정:** Firebase JS SDK의 `getToken`/`deleteToken`으로 FCM 등록 토큰을 받아 기존 토큰 API에 등록하고, 서비스 워커는 compat SDK 초기화만 두어 표시·클릭을 브라우저와 SDK에 맡깁니다. 오프라인 캐싱·next-pwa·Serwist·커스텀 push 핸들러는 두지 않습니다. 알림 권한은 Android처럼 회원 화면이 처음 열릴 때 기기당 한 번 자동으로 묻되, 신규 회원은 필수 동의 시트의 제출 클릭(사용자 제스처) 직전에 묻습니다. 광고 동의는 필수 동의 시트의 "[선택]" 항목으로 먼저 받고 첫 거절 뒤 세 번째 재진입(페이지 로드)에서 재질문 시트로 한 번 더 묻습니다. 설정은 마이 > 알림 설정에서 서비스·광고·야간을 전체 교체 PUT으로 저장하고 광고·야간 변경마다 처리 결과 다이얼로그를 표시합니다.
- **이유:** 토큰 기반이 서버·Android와 같은 계약이라 서버 변경 없이 동작합니다. SDK 12가 권고하는 FID 기반 `register`는 서버 발송 대상과 토큰 테이블 계약을 함께 바꿔야 하므로 미룹니다. Android와 같은 시점·문구로 맞춰 두 플랫폼의 동의 규칙을 하나로 유지합니다. 브라우저는 제스처 없는 권한 요청을 무시할 수 있어(Safari) 동의 시트의 제출 클릭과 알림 설정의 버튼을 제스처 경로로 둡니다. 정보통신망법 제50조의 사전 동의·야간 별도 동의·처리 결과 통지는 Android와 같은 문구·규칙을 씁니다.
- **주요 영향:** Firebase 웹 앱 설정 5개가 Vercel·`.env.local`에 필요하며 비면 전체가 꺼집니다. E2E는 VAPID 키를 비워 푸시를 끄므로 권한 요청·토큰 등록·재질문 시트는 실기기 수동 검증입니다. 백그라운드 알림은 `recipientId`를 대조할 수 없어 로그아웃 토큰 삭제가 방어선입니다. 개인정보 처리방침의 푸시·광고 동의 고지가 Android 앱 기준이라 웹 푸시 포함 개정(서버 요구 버전 상향과 같은 릴리스)이 선행돼야 합니다.

## W-019. 제작 로컬 저장을 Dexie 트랜잭션으로 전환

- 결정일: 2026-09-26, 기록 확정 상태: Accepted
- 근거: [웹 제작 계약](../spec/3-2-web-spec.md#3-2-3-웹-제작-흐름), [제작 저장 구조](../design/1-1-web-design.md#게스트-저장소-키-웹)
- **대체 범위:** W-017의 localStorage 배열 저장과 별도 쓰기 방식만 대체합니다. requestId, 다중 초안, 새 제작 및 카드 재개 계약은 유지합니다.
- **맥락:** 한 항목을 바꾸어도 전체 JSON 배열을 동기식으로 다시 썼으며 초안 교체, 완성 제출, 실패 복원 중 일부 쓰기만 성공할 수 있었습니다.
- **결정:** Dexie와 IndexedDB로 제작 두 테이블을 저장하고 상태 검사 및 전환을 트랜잭션으로 처리합니다. useLiveQuery로 구독하며, 초기 조회와 명시적 이탈 및 제출은 비동기 저장 완료를 기다립니다. 제출 전 저장 실패는 공통 계약에 맞춰 입력을 보존하고 요청을 막습니다.
- **이관:** 검증된 legacy 입력은 최초 시각과 순서를 보존하고, DB 커밋 후에만 원문을 정리합니다. 완료 표시는 같은 원본의 재삽입을 방지합니다. 이중 쓰기와 자동 localStorage 폴백은 두지 않습니다.
- **세션 경계:** 본문을 저장하지 않는 동기식 세대값으로 로그아웃 직후 지연 작업을 무효화합니다. DB 삭제 실패 시 다음 접근에서 정리를 먼저 수행합니다.
- **한계:** 종료 순간의 비동기 저장, 서버 백업, 기기 간 동기화를 보장하지 않습니다. 배포 전에 열린 구버전 탭의 localStorage 쓰기는 자동 병합하지 않습니다. 배포 시 구버전 탭 정리 및 데이터 롤백 정책을 확인해야 합니다.

## W-020. 간편 제작 편집 저장을 버튼·단계 이동·화면 숨김으로 제한

- 결정일: 2026-10-01, 기록 확정 상태: Accepted
- 근거: [웹 제작 흐름](../spec/3-2-web-spec.md#3-2-3-웹-제작-흐름), [Android 제작과 데이터 보존](../spec/3-3-android-spec.md#3-3-3-제작과-데이터-보존), [A-020](1-3-android-adr.md#a-020)
- **대체 범위:** W-019 중 명시적 이탈이 편집 저장 완료를 기다리는 부분만 대체합니다. 저장소, 트랜잭션, 생성·완성 요청의 사전 저장은 유지합니다.
- **맥락:** 웹 간편 제작은 마지막 변경 300ms 뒤 자동 저장하고 헤더에 저장 상태 배지를 보였습니다. Android 간편 제작(A-020)과 웹 일반 제작은 이미 "임시 저장" 버튼 방식이라 같은 앱 안에서 저장 방식이 달랐습니다.
- **결정:** 편집은 메모리에 두고 일반 제작과 같은 "임시 저장" 버튼, 단계 이동, 화면 숨김 때만 저장합니다. 버튼·이탈 다이얼로그·새로고침 확인창은 일반 제작 코드를 함께 씁니다. 스토리라인 생성 요청과 결과는 지금처럼 바로 저장합니다.
- **이유:** 사용자가 저장 시점을 알 수 있고, 입력 삭제 같은 편집이 말없이 확정되지 않습니다. 단계 이동 저장은 일반 제작의 탭 이동 저장과 맞춥니다. 생성 결과는 비용이 드는 서버 결과이고 복구 조회에 필요해 버튼을 기다리지 않습니다.
- **주요 영향:** 300ms 디바운스 저장과 저장 상태 배지를 제거합니다. Android와 달리 단계 이동 때도 저장합니다. 잃을 것이 없으면(입력도 저장본도 없음) 간편·일반 제작 모두 확인 다이얼로그 없이 나가고, 저장하지 않은 입력이 있으면 키워드 단계에서도 새로고침 확인창을 띄웁니다. `client_storyCreate_draftSaved`는 세 저장 계기의 쓰기 성공에서만 발생합니다.

## W-021. 일반 제작 이미지는 브라우저에서 잘라 JPEG로 올림

- 결정일: 2026-10-01, 기록 확정 상태: Accepted
- 근거: [웹 제작 흐름](../spec/3-2-web-spec.md#3-2-3-웹-제작-흐름), [일반 제작 구조](../design/1-1-web-design.md#라우트-등록과-호환)
- **맥락:** 일반 제작의 커버(3:4)와 주변 인물(4:3) 이미지는 원본 그대로 올라가, 비율이 다르면 목록·상세에서는 가운데가 임의로 잘리고 채팅의 인물 이미지에는 여백이 생겼습니다.
- **결정:** 파일을 고르면 하단 시트에서 칸 비율 프레임에 맞춰 이동·확대로 영역을 고르고, 브라우저 canvas로 잘라 긴 변 최대 1440px의 JPEG(품질 0.9)로 기존 presign 업로드에 올립니다. 크롭 UI는 `react-easy-crop`을 씁니다. 원본의 형식·5MB 선검사는 유지합니다.
- **이유:** 서버·presign 계약을 바꾸지 않고 비율을 보장합니다. `react-easy-crop`은 고정 프레임과 드래그·핀치·휠 확대, 경계 제한을 기본 제공하고 작습니다(gzip 약 7KB). Safari는 canvas에서 WebP를 만들지 못해 PNG로 바뀌므로 모든 기기에서 같은 결과가 나오는 JPEG를 택했습니다. PNG는 1440px에서도 5MB에 가까워질 수 있지만, JPEG는 최악(무작위 노이즈)에도 약 1.8MB라 5MB 제한에 여유가 있습니다.
- **주요 영향:** 업로드 Content-Type은 항상 `image/jpeg`이고 투명 배경은 흰색이 됩니다. 이미 올린 이미지를 다시 자르는 편집은 두지 않으며 다시 고르면 됩니다. 5MB가 넘는 원본은 지금처럼 고르기 전에 막습니다.

## W-022. 동의 전에는 세션을 만들지 않고 Credentials로 가입을 완료

- 결정일: 2026-10-05, 기록 확정 상태: Accepted
- 근거: [공통 동의 모델](../spec/3-1-client-spec.md#fe-screen-010-서비스-이용약관개인정보-처리방침), [웹 로그인과 회원 이관](../spec/3-2-web-spec.md#로그인과-회원-이관), [토큰 세션](../design/1-1-web-design.md#토큰-세션-bff), [백엔드 동의 후 가입 완료 흐름](../spec/4-backend-server-spec.md#동의-후-가입-완료-흐름)
- **대체 범위:** W-011 중 OAuth 복귀 직후 세션을 만들고 그 세션에서 동의를 받는 부분만 대체합니다. 로그인한 세션에 동의가 남은 경우의 탭 표시 판정과 fail-closed 로그아웃은 유지합니다.
- **맥락:** 서버가 소셜 인증과 가입 완료를 나눠 필수 동의 전에는 계정과 토큰을 만들지 않게 됐습니다. 웹은 OAuth 콜백의 `jwt` 콜백에서 백엔드 로그인과 Auth.js 세션을 함께 만들고 있어, 동의 대기 응답을 받으면 세션 없이 콜백을 끝내고 동의 후에 세션을 만들 경로가 필요했습니다.
- **결정:** 소셜 인증은 Auth.js `signIn` 콜백에서 호출합니다. 동의가 남으면 대기 코드를 HttpOnly 쿠키에 담고 원래 `callbackUrl`을 반환해 세션 없이 돌려보냅니다. 동의 제출은 Credentials 프로바이더 `signup-consent`의 `authorize`가 완료 API를 호출하고 성공했을 때만 세션을 만듭니다. 대기 만료와 약관 개정은 시트를 닫고 다시 로그인하게 합니다.
- **이유:** `signIn` 콜백의 문자열 반환과 Credentials 프로바이더는 Auth.js가 지원하는 경로라 세션 JWT를 직접 인코딩하지 않아도 됩니다. `jwt` 콜백에서 예외로 돌려보내면 정상 흐름마다 Auth.js 오류 로그가 남고, 빈 세션을 먼저 만들면 동의 전 세션이 생겨 서버 계약과 어긋납니다. 웹은 ID 토큰을 보관하지 않으므로 서버 계약의 재인증을 OAuth 재시작으로 대신합니다.
- **주요 영향:** 동의 전에는 세션이 없어 탭 표시가 복사돼도 회원 기능이 열리지 않습니다. 가입 대기 확인용 BFF 라우트와 팝업 완료의 `consentRequired` 신호가 생깁니다. 소셜 인증 실패의 `/login?error=` 값이 `Configuration`에서 `AccessDenied`로 바뀝니다. `signIn`과 `jwt` 콜백이 같은 `account` 객체를 받는 @auth/core 동작에 기대므로 Auth.js를 올릴 때 확인합니다.

## W-023. 결제 복귀 화면은 결제 전 충전 화면까지 히스토리를 되감음

- 결정일: 2026-10-05, 기록 확정 상태: Accepted
- 근거: [웹 유료 충전](../spec/3-2-web-spec.md#유료-충전), [결제 전 히스토리 길이](../design/1-1-web-design.md#게스트-저장소-키-웹)
- **맥락:** 그로블 결제창 이동과 그로블의 복귀 이동이 모두 히스토리 항목을 쌓아, 결제 후 충전 화면에서 뒤로가기를 누르면 그로블 결제 완료 화면이 다시 열렸습니다. 웹은 지나온 항목을 지울 수 없고 그로블의 이동 방식도 바꿀 수 없습니다.
- **결정:** 결제창으로 나가기 직전 같은 주소를 한 칸 쌓아 앞으로 항목을 자르고 그 길이를 탭 단위 sessionStorage에 남긴 뒤, 그 칸을 결제창으로 바꿉니다. 그로블의 이동·진입 페이지인 `/my/credits/return`은 길이 차이로 거리를 구해 `history.go`로 결제 전 충전 화면까지 되감습니다. 기록이 없거나 길이가 상한(50)에 닿으면 되감지 않고 `/my/credits`로 바꿔 끼웁니다. 복귀 화면은 앱 셸 없는 정적 문서로 응답합니다.
- **이유:** 새 창(팝업) 결제는 원래 탭 히스토리를 깨끗하게 두지만, 모바일과 인앱 브라우저에서 카드사·간편결제 앱을 다녀온 뒤 팝업으로 돌아오지 못할 위험이 있어 택하지 않았습니다. Navigation API의 `entries()`는 다른 출처를 지나면 그 이전 항목을 보여 주지 않아 결제 전 항목을 찾을 수 없습니다. 앞으로 항목을 자르지 않으면 결제창에서 뒤로 돌아왔다 다시 결제한 경우 길이 차이가 실제 거리보다 작아집니다. 복귀 화면에 앱 셸을 띄우면 WebKit이 되감기 시작과 함께 진행 중인 요청을 끊고, 그 실패로 열린 동의 시트가 히스토리 칸을 쌓아 되감기를 깨뜨렸습니다.
- **주요 영향:** 그로블 상품 설정의 이동 페이지와 진입 페이지를 `/my/credits/return`으로 등록해야 합니다. 되감기 직전 복귀 화면이 잠깐 빈 화면으로 보입니다. 결제창에서 뒤로 돌아오면 결제 전 충전 화면이 bfcache 대신 새로 로드될 수 있습니다. 다른 탭에서 결제를 마치거나 히스토리가 상한에 닿은 경우에는 뒤로가기가 결제창으로 갈 수 있습니다.

## W-024. 완성 중 표지를 Android와 같은 로고 마스코트 애니메이션으로 바꿈

- 결정일: 2026-10-06, 기록 확정 상태: Accepted
- 근거: [웹 제작 탭 진행 카드](../spec/3-2-web-spec.md), [Android A-065](1-3-android-adr.md)
- **맥락:** Android가 완성 중 카드 표지를 점 로딩에서 로고 마스코트 애니메이션으로 바꾸면서(A-065) 두 플랫폼의 표지가 갈렸습니다. 사용자는 완성을 기다리는 동안 같은 카드를 보므로 표현을 맞춥니다.
- **결정:** 웹도 같은 안무를 씁니다. 안무는 시간에서 자세를 계산하는 순수 함수라 Android의 값을 그대로 TypeScript로 옮기고, 그리기는 Canvas 2D로 같은 소품과 붓질을 그립니다. 마우스·트랙패드 환경에서는 기존 점 무리처럼 포인터에 반응하도록 마스코트 눈이 포인터를 바라보고, 동작 줄이기에서는 한 장면으로 정지합니다. A-065의 "Android 표현 차이"는 이 결정으로 플랫폼 공통 표현이 됩니다.
- **이유:** SVG와 motion 컴포넌트로 막마다 요소를 따로 움직이면 소품 수만큼 레이어와 타이밍이 늘고 Android와 값이 갈라집니다. 순수 함수 하나를 두 플랫폼이 같은 값으로 따르면 한쪽을 고칠 때 다른 쪽에 같은 수정을 옮기기 쉽고, 순간이동 없음·표지 안 유지 같은 같은 테스트로 검증할 수 있습니다.
- **주요 영향:** 완성 중 표지는 `ImageGeneration`을 쓰지 않습니다. 채팅 장면 썸네일 자리는 점 로딩을 유지합니다. 테마 토큰이 oklch라 캔버스에서 색을 섞으려고 한 점 캔버스로 sRGB 값을 읽으며, 테마가 바뀌면 다시 읽습니다. 안무를 바꿀 때는 Android `StoryCompletingChoreography`와 함께 고칩니다.

## W-025. 채팅 실시간 이미지 대기를 마스코트가 인물을 그리는 애니메이션으로 바꿈

- 결정일: 2026-10-06, 기록 확정 상태: Accepted
- 근거: [부분 렌더](../spec/3-1-client-spec.md#렌더와-스크롤), [채팅 스트림 로딩](../design/1-1-web-design.md), [W-024](#w-024)
- 대체 관계: W-024의 "채팅 장면 썸네일 자리는 점 로딩을 유지합니다"를 부분 대체합니다. 완성 중 표지에 관한 W-024의 나머지 결정은 그대로입니다.
- **맥락:** 실시간 이미지를 켠 턴은 응답까지 약 15초가 걸리는데, 그동안 썸네일 자리의 점 로딩은 무엇을 만드는지 보여 주지 않았습니다. 사용자 요청에 따라 인물 이미지를 그리는 중이라는 것이 전해지도록 완성 중 표지와 같은 마스코트 표현으로 바꿉니다.
- **결정:** 썸네일 자리에 완성 중 표지와 같은 방식(시간 → 자세 순수 함수 안무, Canvas 2D)으로 새 안무를 그립니다. 마스코트는 처음 한 번 화가 베레모를 쓰고 붓을 집어 든 뒤, 힘을 모으고 그 붓의 털 끝으로 크로키, 수채, 검은 종이 별자리처럼 분위기가 다른 인물 세 장을 그리며 사이사이 안도와 딴짓을 연기합니다. 준비를 포함해 약 15초 안에 세 장을 마치고, 응답이 더 늦으면 준비 없이 힘을 모으는 막부터 반복합니다. 인물은 사람 아이콘처럼 보이지 않게 옆선·머리카락·표정으로 그립니다. 낱동작·막 실행기·마스코트 그리기·캔버스 프레임 루프는 완성 중 표지와 함께 쓰는 공용 모듈로 옮깁니다. Android는 같은 안무 값으로 뒤따릅니다.
- **이유:** 완성 중 표지에서 쓴 순수 함수 안무는 순간이동 없음·무대 안 유지 같은 같은 테스트로 검증되고 Android로 값을 옮기기 쉽습니다. 채팅이 스튜디오 내부를 직접 가져오지 않도록 공용 부분을 도메인 밖으로 옮겼습니다. 그림의 붓길을 SVG path 문자열로 적으면 그려지는 선과 붓끝이 같은 길을 따르고, 인물 모양을 고칠 때 좌표만 바꾸면 됩니다. 완성 중 표지처럼 발을 붓 끝으로 쓰면 몸이 그림을 가려, 붓을 몸 옆에 들려 붓털 끝을 붓길에 붙잡고 몸 자리를 거꾸로 구합니다.
- **주요 영향:** 채팅 로딩은 `ImageGeneration`을 쓰지 않습니다. 완성 중 표지의 컴포넌트가 공용 `MascotStage`로 바뀌지만 값과 화면은 같습니다. 웹이 먼저 바뀌어 Android가 같은 안무로 따라오기 전까지 두 플랫폼의 대기 표현이 다릅니다. 같은 요청으로 두 무대의 바탕 점을 더 옅게(불투명도 0.45 → 0.25) 바꿔, Android가 따라오기 전까지 완성 중 표지의 바탕 점 진하기도 다릅니다. 안무를 바꿀 때는 Android 구현과 함께 고칩니다.
