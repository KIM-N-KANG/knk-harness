## 읽는 순서

- **처음 보는 사람** — 기록 규칙을 읽고, 목차에서 관련 주제의 기록으로 이동합니다. 문서 작성일·수정일은 개별 결정일과 구분합니다.
- **구현자** — [현재 스펙](../spec/3-3-android-spec.md)과 해당 설계를 먼저 확인하고, 선택 이유가 필요한 지점의 ADR을 읽습니다. 과거 기록을 현재 동작의 기준으로 사용하지 않습니다.
- **리뷰·변경 작성자** — 관련 결정과 후속 대체 관계를 함께 확인합니다. 확정된 본문은 보존하고 새 기록에 대체하는 ID·범위를 남깁니다.

- **이유:** 토큰 삭제 여부만으로 계정 격리를 증명할 수 없기 때문입니다.
- **주요 영향:** recipientId 없는 메시지는 버리고 표시·탭 양쪽에서 검증합니다.

## A-040. 광고 알림 동의는 첫 진입 시트로 묻고 즉시 통지

- 결정일: 2026-09-11 · 상태: Accepted
- 대체 관계: 첫 질문 자리와 "물었음" 단일 플래그는 [A-044](#a-044)가 대체합니다. 즉시 통지·야간 분리·고지 정본 결정은 유지합니다.
- **맥락:** 서버와 설정 화면은 광고·야간 동의를 옵트인으로 저장하지만 먼저 묻는 흐름과 처리 결과 통지가 없었습니다. 정보통신망법 제50조는 앱 푸시 광고에 사전 동의, 야간 별도 동의, 14일 이내 처리 결과 통지, 2년 주기 재확인을 요구하며 OS 알림 권한 허용은 동의로 인정되지 않습니다. 로그인 버튼을 약관 동의로 간주하는 현재 모델에 광고 동의를 끼우면 무효입니다.
- **선택:** 회원 그래프 첫 진입에서 권한 응답과 초대 코드 안내가 끝난 뒤 바텀 시트로 한 번 묻습니다. "물었음"은 사용자 귀속 DataStore에 두고 로그아웃에 정리하며, 서버가 이미 동의 상태이거나 기기 알림이 꺼져 있으면 묻지 않습니다. 동의·철회를 처리한 즉시 전송자·일시·처리 내용을 다이얼로그로 통지하고 일시는 의사 표시 시점의 기기 시각을 씁니다. 고지 정본은 개인정보 처리방침의 광고성 정보 수신 동의 절이며 시트에는 고지를 싣지 않고 설정 화면의 광고 행이 문서를 엽니다.
- **이유:** 시트는 알림의 가치를 이해한 뒤 묻는 자리이고, 즉시 통지는 별도 발송 경로 없이 14일 기한을 충족합니다. 서버에 "물었음"을 두지 않은 것은 API 계약을 늘리지 않기 위해서이며, 대신 재로그인 시 거절자에게 한 번 더 묻는 한계를 받아들였습니다.
- **주요 영향:** 2년 재확인 발송과 광고 페이로드의 전송자 연락처·수신 거부 문구는 서버 과제로 남습니다. 반복 노출이 문제되면 서버 필드로 올리는 후속 결정으로 대체할 수 있으며 이 기록은 보존합니다.
- 근거: [KNK-1254](https://kimandkang.atlassian.net/browse/KNK-1254), [Android 계획](../../../manyak-android/docs/plans/marketing-consent.md)

## A-042. 카드 옵션·상세 옵션·채팅 메뉴를 바텀 시트로 통일

- 결정일: 2026-09-18 · 기록 확정 상태: Accepted
- 대체 관계: [A-029](#a-029)의 다이얼로그 표현과 카드 축소판을 대체합니다. 더보기·길게 누르기 진입과 삭제 확인 절차는 유지합니다. [A-030](#a-030)의 삭제 항목 조건은 유지합니다.
- **맥락:** 웹(KNK-1306)이 카드 옵션 다이얼로그·상세 드롭다운·채팅방 헤더 옵션을 바텀 시트로 통일했고, 채팅방 메뉴에 내 이프 카드와 새 채팅 시작하기가 더해져 앵커 드롭다운으로는 항목이 넘칩니다. 앱은 카드가 가운데 다이얼로그, 상세·채팅방이 앵커 드롭다운으로 표현이 셋이었습니다.
- **결정:** 세 자리 모두 `ManyakBottomSheet` 기반 옵션 시트 하나로 그립니다. 머리글에 카드 종류와 제목을 두어 축소판 미리보기 없이 대상을 확인하고, 항목 버튼은 48dp·아이콘 20dp·간격 12dp·파괴적 변형·진행 중 스피너의 공용 규격입니다. 신고·삭제 확인·충전 이동은 시트를 먼저 닫습니다. 채팅방의 새 채팅 시작하기는 시작 설정 없이 만들고 현재 방을 새 방으로 교체합니다. 시트 열림은 구성 변경에서 유지합니다.
- **이유:** 표현을 하나로 두어 같은 항목이 자리마다 다르게 읽히지 않고, 시트는 항목이 늘어도 폭·위치 제약이 없습니다. 축소판은 머리글 두 줄로 대체되어 카드마다 미리보기 변형을 유지할 비용이 사라집니다. 교체 이동은 삭제와 같은 이유로 지운 것과 다름없는 이전 방으로 되돌아가지 않게 합니다.
- **주요 영향:** `ManyakOptionsDialog`·`ManyakOptionsMenu`·카드 축소판·`thumbnail-small` 토큰을 제거합니다. 채팅방 ViewModel이 프로필 저장소를 읽어 메뉴의 잔액을 갱신합니다. 공유하기 항목은 [A-043](#a-043)이 정합니다.

## A-043. 채팅 공유를 앱에 적용하고 Android 공유 시트로 전달

- 결정일: 2026-09-18 · 기록 확정 상태: Accepted
- 대체 관계: 2026-08-29의 "채팅 공유 앱 비적용"(Android 계획 문서 결정, ADR 미기재)을 대체합니다. [A-026](#a-026)의 공유 시트 사용을 채팅 공유로 확장합니다.
- **맥락:** 메뉴 시트 전환([A-042](#a-042))으로 웹과 같은 자리에 공유하기를 둘 수 있게 됐습니다. 공통 계약은 발급한 링크를 클립보드에 복사하고 토스트로 알리지만, 앱에서는 링크를 손에 쥔 뒤 다시 공유 앱을 찾아야 해 초대 코드 공유보다 한 단계 깁니다.
- **결정:** 채팅 메뉴와 채팅 목록 카드 옵션 시트의 공유하기는 `POST /chats/{id}/shares`로 발급한 웹 열람 URL을 초대와 같은 Android 공유 시트(`ACTION_SEND`)로 바로 보냅니다. 클립보드 복사·성공 토스트는 두지 않고 실패 안내·진행 표시는 공통 계약을 따릅니다. 링크의 origin 은 데이터 계층 설정(`webBaseUrl`)이 완성합니다.
- **이유:** 링크를 받는 쪽은 앱이 아니라 웹이라 앱은 전달만 맡으면 되고, 시스템 공유 시트가 클립보드보다 한 번의 탭으로 목적지까지 닿습니다. 공유 SDK 를 싣지 않는 초대의 결정과 같은 이유입니다.
- **주요 영향:** 열람 화면은 여전히 웹 소유입니다. 디버그 빌드는 API 가 dev 이고 웹 origin 기본값이 운영이라 발급 링크를 운영 웹이 찾지 못하며, dev 웹은 SSO 뒤라 공개 origin 이 없어 수용합니다.

## A-044. 약관 동의 시트를 legal이 소유하고 광고 동의는 선택 항목과 재진입 재질문으로 받음

- 대체 관계: [A-040](#a-040)의 첫 질문 자리(별도 시트)와 "물었음" 단일 플래그를 대체합니다. 통지·야간·고지 정본 결정은 유지합니다. 공통 [동의 모델](../spec/3-1-client-spec.md#fe-screen-010-서비스-이용약관개인정보-처리방침)의 "Android는 별도 시트" 문구를 같은 날 정정했습니다.
- **맥락:** 서버가 동의 기록 API를 갖추고(KNK-1334) 웹이 로그인 직후 명시 동의 시트로 옮겼습니다(KNK-1342). 앱은 로그인 버튼 간주 동의였고, 광고 알림 동의는 별도 시트를 한 번만 띄우도록 설계됐지만 사용자에게는 진입마다 다시 묻는 것으로 보였습니다 — 거절 기록이 로그아웃에 지워지고 ViewModel의 준비 플래그가 액티비티 수명이라 재로그인 판정도 어긋났습니다.
- **결정:** 약관·처리방침·만 14세 동의 시트는 `legal/consent`가 소유하고 루트가 회원 그래프 위에 얹습니다. 끌어내리기·스크림은 막고 뒤로가기만 로그아웃이며, 전문은 백스택이 아니라 시트 위 전체 화면 창으로 엽니다. 알림 권한은 시트보다 먼저 묻되 별개의 동의라 권한 결과와 무관하게, 광고 알림 동의는 같은 시트의 가장 아래 선택 항목으로 먼저 받고, 답은 루트가 알림 기능의 ViewModel에 넘겨 저장·통지합니다. 거절 뒤에는 세 번째 재진입에 별도 시트로 한 번 더 묻고 두 번째 거절이나 허용 뒤에는 묻지 않습니다. 두 ViewModel 모두 세션 상태를 보고 회원이 될 때마다 다시 판정합니다.
- **이유:** 필수 동의와 같은 자리에서 한 번에 받으면 첫 진입의 시트가 한 장 줄고, 선택 항목이 필수 완료 조건에 섞이지 않습니다. 기능 모듈끼리 직접 의존하지 않는 규칙을 지키려 저장은 알림 기능에 남기고 루트가 답만 전달합니다. 재진입 단위 재질문은 서버 필드 없이 반복 노출을 끊습니다. 전문을 창으로 여는 것은 모달 시트가 백스택의 문서를 덮기 때문입니다.
- **주요 영향:** 기존 회원도 다음 진입에 한 번 시트를 봅니다. 재로그인은 여전히 거절 기록을 지우므로 같은 기기의 재로그인 회원은 다시 첫 질문을 받습니다(선택 항목). 로그인 화면의 간주 동의 문구는 문서 링크만 남깁니다. `ManyakCheckbox`를 designsystem으로 올리고 `ManyakBottomSheet`에 뒤로가기 잠금을 추가했으며, 법적 문서 화면에 제목·뒤로가기 앱바를 넣어 백스택 진입과 창 진입의 표현을 통일했습니다.
- 근거: [KNK-1347](https://kimandkang.atlassian.net/browse/KNK-1347), [Android 계획](../../../manyak-android/docs/plans/legal-consent.md)

## A-045. 알림 진입 목적지는 서버 deepLink를 정본으로 해석

- 결정일: 2026-09-20 · 기록 확정 상태: Accepted
- 대체 관계: [A-034](#a-034)의 수신자 재검증은 유지하고, 그 뒤의 목적지 결정만 `type` 매핑에서 URL 해석으로 바꿉니다. `type` 매핑은 `deepLink`가 없는 payload의 하위 호환으로 남습니다.
- **맥락:** 서버가 스토리 완성·출석 리마인드 payload에 `deepLink`를 싣기 시작했습니다(KNK-1335, v0.5.1). 앱은 `type`·식별자로 목적지를 정하고 있어 두 알림 모두 이미 올바른 화면에 도착하지만, 서버가 목적지를 바꾸거나 새 알림을 추가할 때마다 앱 매핑을 갱신해야 했습니다. 서버 스펙은 "앱이 호스트·경로 허용 목록으로 검증한 뒤 이동, 허용하지 않으면 홈"을 앱 계약으로 두었습니다.
- **결정:** `deepLink`가 있으면 `:navigation`의 `DeepLink`가 `https` + `manyak.app`·`www.manyak.app`의 `/stories/{id}`·`/my/credits`만 내부 라우트로 바꾸고 그 외는 홈입니다. 해석에 실패해도 `type` 매핑으로 되돌아가지 않습니다. `deepLink`가 없을 때만 기존 `type` 매핑을 씁니다. `PushEntry`는 `deepLink` 문자열을 extra 하나로 더 싣고 기존 extra는 유지합니다. 이프 충전의 `tab` 쿼리는 읽지 않습니다.
- **이유:** URL을 정본으로 두면 서버가 목적지를 옮겨도 허용 목록 안에서는 앱 업데이트 없이 따라갑니다. 실패 시 `type`으로 되돌리면 서버가 목적지를 바꾼 뒤에도 구 매핑으로 가 서버 의도와 어긋나므로 홈으로 떨어뜨립니다. `type` 매핑을 남기는 것은 업데이트 전에 만든 PendingIntent와 `deepLink`가 없는 프로모션 때문입니다. 파서를 `java.net.URI`로 두는 것은 `android.net.Uri`가 JVM 유닛 테스트에서 빈 스텁이라서이고, 같은 파서를 뒤의 공유 URL App Links(KNK-927·928)가 재사용합니다. 탭 파라미터는 무료 탭이 기본이라 두 번째 사용처가 생기기 전에는 라우트에 싣지 않습니다.
- **주요 영향:** 사용자에게 보이는 동작은 바뀌지 않습니다. App Links(HTTPS intent-filter·`assetlinks.json`)는 이 결정에 포함하지 않습니다. 웹 이프 충전 화면은 `?tab=` 쿼리를 아직 읽지 않습니다(웹 몫).
- 근거: [KNK-1348](https://kimandkang.atlassian.net/browse/KNK-1348), [Android 계획](../../../manyak-android/docs/plans/push-deeplink.md)

## A-046. 편집 초안을 퍼널 세션 ID 키의 여러 행으로 확장

- 결정일: 2026-09-23 · 기록 확정 상태: Accepted
- 대체 관계: [C-004](1-1-client-adr.md#c-004)의 "편집 초안 한 개"와 [A-035](#a-035)의 "편집 슬롯은 기기당 한 행"을 대체합니다. 계정별 보존은 유지합니다.
- **맥락:** 공통 계약이 여러 편집 초안으로 바뀌었습니다(KNK-1394). Android 편집 슬롯은 Room 한 행이라 새 제작 전에 폐기 확인을 거쳐야 했고, 새로 만들면 기존 초안이 사라졌습니다.
- **결정:** `pending_story_creation`의 기본 키를 퍼널 세션마다 새로 만드는 `draftId`(UUID)로 바꾸고 `createdAt`을 더합니다(DB v4). 퍼널 라우트가 `draftId`를 싣고 단계 ViewModel이 퍼널 스토어에 맡깁니다. 웹처럼 `requestId`를 목록 키로 쓰지 않습니다.
- **이유:** 키워드 초안에는 `requestId`가 없고 재생성마다 `requestId`가 바뀌어, 라우트에 실은 키가 프로세스 재시작 뒤 이미 지운 행을 가리킬 수 있습니다. 세션 ID를 키로 두면 단계 전환이 같은 행을 덮어 웹의 소유 레코드 이관이 필요 없고, 완성 제출도 그 ID로 정확히 한 초안만 내립니다.
- **주요 영향:** v3→v4 마이그레이션이 편집 테이블을 다시 만들어 남은 초안을 `legacy-0`으로 옮기고 날짜 없이 맨 뒤에 둡니다. 새로 만들기 확인 다이얼로그와 `client_storyCreate_resumeDialog_*` 이벤트를 제거합니다. 퍼널 라우트에 필드가 늘어 이전 형식으로 저장된 백스택은 해석하지 못하는데, 앱 업데이트는 액티비티를 새로 시작하므로 영향이 없다고 판단했습니다.

## A-048. 채팅 안내 투어를 같은 컴포지션의 오버레이로 그리고 뒤로가기를 건너뛰기로 처리

- **맥락:** 공통 [첫 진입 안내](../spec/3-1-client-spec.md#첫-진입-안내)는 웹 구현(DOM 측정·`body` 포털)을 전제로 합니다. 앱은 컴포저 버튼의 위치를 재서 딤을 뚫어야 하고, 웹에는 없는 시스템 뒤로가기가 투어 중에 눌릴 수 있습니다.

## A-049. 상세 삭제는 제작 탭으로 복귀하고 좋아요 성공은 홈 카드에 전달

- 결정일: 2026-10-03, 기록 확정 상태: Accepted
- 후속 관계: [A-030](#a-030)의 소유자 상세 삭제에 성공 후 제작 탭 복귀를 명시합니다. 일반 뒤로가기와 채팅 복귀는 유지합니다.

- **결정:** 삭제 성공은 app이 메인 셸까지 돌아가 제작 탭을 선택합니다. 좋아요는 상세에서 낙관적으로 변경하고 실패하면 정확한 이전 값으로 복원합니다. 성공한 수만 common의 좁은 전달 계약을 통해 home 저장소로 보냅니다. 홈 ViewModel은 자신의 수명 동안 변경을 수집하며 해당 카드만 갱신합니다.
- **이유:** 기능 모듈끼리 참조하지 않고 기존 앱 조립 및 공유 계약의 소유권을 유지합니다. 목록 전체를 새로 읽으면 스크롤과 정렬 위치가 바뀌므로 카드 수만 갱신합니다. 변경 스트림은 replay나 영속 저장을 하지 않아 다음 세션에 이전 값을 전달하지 않습니다. 진행 중 조회와 겹치는 변경만 응답에 합치고 이후 조회는 서버 값을 사용합니다.
- **주요 영향:** 상세 조회가 좋아요 요청 중 낙관적 값이나 복원 값을 덮지 않도록 진행 중 조회를 취소하고 요청 중 화면 복귀 조회를 생략합니다. 헤더와 기본 심벌은 공통 계약을 그대로 적용하며 별도 그라데이션 예외를 두지 않습니다.
- 근거: [KNK-1516](https://kimandkang.atlassian.net/browse/KNK-1516), [Android 작업 기록](../../../manyak-android/docs/plans/story-detail-alignment.md)

검색과 칩은 장르 ID별 같은 선택 상태를 토글합니다. 대표 장르는 항상 카탈로그의 대표 순서를 유지합니다. 대표 목록 밖의 장르만 처음 선택할 때 마지막에 추가하고, 선택 해제와 재선택에도 최초 추가 순서를 유지합니다. 최대 선택 개수에 도달해도 기존 선택의 해제는 허용합니다.

추가 ID 목록은 유효한 비대표 장르로 정규화합니다. 이전 초안에 대표 장르가 추가 ID로 저장되어 있어도 선택 상태는 보존하고 원래 대표 위치로 복원합니다. 이 규칙으로 같은 장르가 선택 경로에 따라 다른 위치나 동작을 갖지 않게 합니다.

이미지의 objectKey와 앱 전용 파일 참조를 폼과 함께 보관합니다. Photo Picker의 임시 접근 권한이나 cache 경로만으로 저장본을 복원하지 않습니다. 파일 이름은 고유하게 만들어 저장하지 않은 이미지 교체가 이전 저장본의 파일을 덮어쓰지 않게 합니다.

## A-064. 동의 전 가입 대기를 세션 없이 auth 메모리에 두기

- 날짜: 2026-10-05
- 상태: 확정
- 범위: Android 소셜 로그인의 필수 동의 대기, 가입 완료, 가입 취소와 재로그인 안내
- 대체 관계: A-052의 "인증된 회원도 서버 필수 동의 확인 전에는 로그인 화면에 남기고 뒤로가기는 기존 로그아웃으로 연결" 중 새 소셜 로그인 부분을 대체합니다. 새 로그인은 동의 전에 세션이 없고 시트의 뒤로가기는 가입 취소입니다. A-044의 "뒤로가기만 로그아웃"은 저장 세션과 가입 완료 뒤 회원 동의 조회에만 남습니다. 서버 계정 생성 지연은 A-052가 남긴 별도 서버 계약 변경으로 해결됐습니다.

서버가 `POST /auth/social/{provider}`에서 필수 동의가 남으면 계정과 토큰 대신 대기 코드를 주고, `POST /auth/social/complete`가 성공해야 계정과 토큰을 만듭니다. Android는 대기 코드를 `auth`의 세션 저장소 필드에만 두고, 시트가 그릴 필요 항목과 요구 버전만 `PendingSignup`으로 공개합니다. 대기 코드는 남의 가입을 완료할 수 있는 단일 사용 코드라 디스크, 로그, Crashlytics, 분석, 엔티티에 싣지 않습니다. 프로세스가 재시작되면 대기가 사라지고 로그인부터 다시 시작합니다. 서버 만료가 10분이라 복원 이득보다 저장 위험이 큽니다.

시트 UI와 동의 판정은 기존 `legal/consent`를 그대로 씁니다. 동의 ViewModel이 세션 상태와 대기를 함께 보고 가입 모드와 회원 모드를 고르며, 루트는 로그인 화면 위에 같은 시트를 얹습니다. 동의 항목 타입(`ConsentItem`, `RequiredConsent`)은 `auth`와 `legal`이 함께 쓰므로 `common` 엔티티로 옮겼습니다.

가입 완료 성공은 기존 로그인과 같은 인증 작업 안에서 토큰 저장과 회원 공개를 마친 뒤 대기를 비웁니다. 회원이 된 뒤에는 기존처럼 `GET /users/me/consents`로 한 번 더 확인합니다. 요청이 하나 늘지만 정지 회원은 가입 완료까지 성공하므로 이 확인이 있어야 이용 제한 상태로 갑니다.

401 `CONSENT_TOKEN_INVALID`와 400 `CONSENT_VERSION_MISMATCH`·`CONSENT_REQUIRED_MISSING`은 웹(W-022)과 같이 시트를 닫고 로그인 화면에 재로그인 안내를 남깁니다. ID 토큰을 다시 받아 소셜 인증을 자동으로 재호출하는 방법은 제공자 창이 다시 뜰 수 있고 버전만 바꿔 제출하는 것과 구분하기 어려워 택하지 않았습니다. 안내는 화면 수명 효과가 아니라 기존 `SessionEndNotice`로 남겨 시트가 사라진 뒤에도 로그인 화면이 표시합니다.

검증 근거는 [동의 후 가입 완료 계획](../../../manyak-android/docs/plans/consent-before-signup.md)을 참조합니다.

## A-065. 완성 중 표지를 로고 마스코트 애니메이션으로 바꾸기

- 날짜: 2026-10-06
- 상태: 확정
- 범위: Android 제작 탭의 완성 중 카드 표지
- 대체 관계: 완성 중 표지에 한해 웹과 같은 이미지 생성 점 로딩을 쓰던 표현을 대체합니다. 채팅 실시간 이미지의 장면 썸네일 자리는 점 로딩을 유지합니다.

스토리 완성은 1분 넘게 걸리고 사용자는 그동안 제작 탭에서 카드를 지켜봅니다. 점 로딩은 "이미지를 만드는 중"만 말해 완성 과정이 드러나지 않았습니다. 시작 화면에서 쓰기 시작한 로고 마스코트를 같은 빈 표지 바탕과 옅은 점 위에 올려, 사용자가 방금 거친 제작 과정(키워드 고르기, 스토리라인 고르기)과 서버가 이어서 하는 일(원고 쓰기, 그림 그리기)을 차례로 연기하고 완성을 기뻐하는 막으로 끝냅니다. 바쁜 막이 쉼 없이 이어지면 정신없어 보여, 막 사이마다 가만히 두리번거리거나 천천히 통통 걷는 쉼을 둡니다. 한 바퀴는 약 32초입니다.

그림 막은 산과 해 모양을 선으로 따라 그리면 이미지 아이콘처럼 읽혀, 굵기가 변하는 붓질과 수채 번짐으로 그립니다.

이 표현은 사용자 요청에 따른 Android 표현 차이입니다. 카드의 상태 전환, 시머 제목, 안내 문구, 폴링 계약은 웹과 같습니다. 채팅 장면 썸네일은 이미지 한 장을 기다리는 자리라 점 로딩의 뜻이 맞아 바꾸지 않습니다.

안무는 시간에서 자세를 계산하는 순수 함수로 두고, 모든 막이 바닥 가운데에서 시작해 같은 자리로 돌아오게 했습니다. 막 순서를 바꾸거나 막을 빼도 이음매에서 순간이동하지 않으며, 1ms 간격 연속성 테스트가 이를 지킵니다. 마스코트 그리기는 시작 화면과 함께 쓰게 되어 `designsystem`으로 올렸습니다.

## A-069. 필수 동의 시트에 로그아웃 버튼을 두고 시작 화면 조회 실패에는 두지 않기

- 대체 관계: [A-044](#a-044)의 "뒤로가기만 로그아웃"을 [C-010](1-1-client-adr.md#c-010)에 맞춰 대체합니다. 끌어내리기·스크림으로 닫지 않는 규칙과 뒤로가기의 `Abandon`은 그대로입니다.

## A-070. 페르소나를 마이가 소유하고 상세에는 좁은 공용 계약으로 열기

- 날짜: 2026-10-09
- 상태: 확정
- 범위: Android 페르소나 저장소, 스토리 상세의 페르소나 선택과 미리 선택, 마이의 관리, 생성, 수정 화면

페르소나는 마이에서 관리하는 회원 귀속 값이고 스토리 상세는 고르기만 합니다. 화면 기능끼리 직접 의존하지 않는 규칙에 따라 새 모듈을 만들지 않고 `my/persona`가 entity, domain, data, presentation을 소유하며, 상세에는 `common`의 `PersonaAccess`(목록 관찰, 다시 읽기, 미리 선택 관찰과 지우기)만 엽니다. `ChatStarter`, `TrialsRepository`와 같은 공용 계약 모양이라 모듈과 계층 검사를 바꾸지 않습니다. 생성 화면은 상세와 관리 목록 두 곳에서 들어오므로 마이가 소유하고 `app`이 두 진입을 연결합니다.

목록은 디스크에 두지 않고 Singleton 저장소의 메모리 StateFlow에 둡니다. 상세와 관리 목록이 들어올 때마다 다시 읽고, 회원 귀속 값이라 `UserScopedStore`로 로그아웃 정리에 참여합니다. 생성, 수정, 삭제가 성공하면 응답으로 목록을 먼저 고친 뒤 다시 읽어, 다시 읽기가 실패해도 상세가 새 페르소나를 고를 수 있게 했습니다.

웹은 상세가 떠나기 전에 출발 스토리를 메모리에 남기지만, Android는 라우트에 복원 가능한 식별자만 싣는 규칙에 따라 `PersonaCreateRoute(originStoryId)`로 출발 스토리를 넘깁니다. 생성 성공 시 저장소가 `CreatedPersona(storyId, personaId)`를 메모리에 남기고, 상세는 자기 스토리의 값일 때만 미리 선택합니다. 앱을 새로 띄우면 남지 않는다는 공통 계약을 지키려고 이 값은 저장하지 않습니다. 상세 ViewModel은 백스택에 남아 채팅방에서 돌아와도 살아 있으므로, 채팅을 시작할 때 미리 선택을 지우면서 고른 주인공을 직접 고른 값으로 옮겨 돌아온 상세의 선택이 바뀌지 않게 했습니다.

## A-071. 웹의 앱 열기 링크를 https 대신 전용 스킴으로 받기

- 날짜: 2026-10-13
- 상태: 확정
- 범위: `MainActivity` intent-filter, `PushEntry`의 앱 열기 진입, 웹 앱 안내 배너의 intent 링크

웹 앱 안내 배너([웹 W-033](1-2-web-adr.md#w-033))는 패키지를 명시한 `intent://` 링크로 앱을 엽니다. 받는 쪽을 autoVerify 없는 `https://manyak.app` 필터로 두면 Android 12 이상에서는 다른 앱의 일반 링크가 그대로 브라우저로 가지만, minSdk 24인 이 앱은 Android 11 이하에서 다른 앱(메일, 메신저 등)의 manyak.app 링크마다 앱 선택창을 띄웁니다. 그래서 https 링크와 겹치지 않는 전용 스킴 `manyak://manyak.app`만 받고, 웹은 `scheme=manyak`으로 엽니다. 앱이 없을 때 브라우저가 플레이스토어를 여는 동작은 같습니다.

진입은 새 타입을 만들지 않고 기존 `PushEntry`에 `TYPE_APP_LINK`를 더해 보류, 로그인 뒤 소비, 프로세스 복원 경로를 그대로 씁니다. 특정 회원에게 보낸 링크가 아니라 수신자 비교를 건너뛰고, 경로는 https로 옮겨 푸시와 같은 `DeepLink` 해석을 씁니다. https App Links(autoVerify, `assetlinks.json`)는 KNK-927에서 따로 다룹니다.

## A-072. 간편 제작 화풍을 기존 초안 JSON에 더하고 스토리라인을 다시 만들어도 남기기

- 날짜: 2026-10-14
- 상태: 확정
- 범위: 간편 제작 추가 정보 단계의 화풍 선택, 편집 초안과 완성 요청의 저장 페이로드, 완성 requestId 재사용

고른 화풍은 편집 초안의 진행 JSON(`progress`)과 완성 명령 JSON(`completionCommand`)에 선택 필드 `artStyle`로 더합니다. 두 값은 이미 행마다 JSON 문자열 컬럼이고 디코더가 모르는 키와 빠진 키를 받아들이므로, 컬럼을 늘리지 않고 Room 버전도 올리지 않습니다. 화풍 선택 이전에 저장한 초안은 화풍을 고르지 않은 상태로 열리고, 이전에 저장한 완성 요청은 `artStyle` 없이 재전송되어 서버가 그때와 같은 ANIME로 만듭니다. Android에는 완성 실패를 초안으로 되돌리는 흐름이 없어, 실패 카드의 재시도는 저장한 명령의 화풍을 그대로 보냅니다.

공통 계약은 스토리라인을 다시 골라도 화풍을 유지하라고 합니다. Android는 스토리라인 재생성 결과가 도착하면 이전 스토리라인에 딸린 편집(선택 순번, 자유 입력, 추천 선택)을 비우는데, 화풍은 스토리라인과 무관한 선택이라 이때도 남깁니다. 웹도 화풍을 퍼널 상태로 들고 있어 재생성에 지워지지 않습니다.

완성 requestId 재사용 조건에 화풍을 더해 화풍만 바꾼 재시도도 새 requestId로 보냅니다. 화풍 목록은 추가 정보 화면에 들어올 때마다 받고 퍼널 수명에 캐시하지 않습니다. 구성 변경에는 ViewModel이 목록을 들고 있어 다시 받지 않습니다.

- 범위: `designsystem`의 `StoryCover`, 목록 카드와 상세 히어로의 `StoryThumbnail` 배지, ORIGINAL 태그, 화풍 이름 뱃지, 스토리 상세 인물 카드의 이전·다음 버튼
- 대체 관계: 코드 주석으로만 남아 있던 "앱은 흐림 없이 70% 반투명만 쓴다"는 선택을 대체합니다.

웹은 표지 위 작은 뱃지에 `bg-black/20`과 `backdrop-blur-md`를 겁니다. 앱은 흐림을 걸 수단이 API 31 이상의 `RenderEffect`뿐이고 스크롤 그리드의 비용이 걱정되어 #111414 70% 반투명으로 대신해 왔는데, 사용자 요청으로 웹과 최대한 같은 결을 내기로 했습니다.

새 라이브러리 없이 Compose `GraphicsLayer`로 구현합니다. `StoryCover`가 표지 그림을 레이어에 기록해 그리면서 같은 기록을 흐림 효과가 걸린 두 번째 레이어에 담고, 겹침 요소는 `coverBackdrop`으로 그 흐린 레이어에서 자기 자리를 모양대로 잘라 깐 뒤 검정 20%를 덮습니다. 흐림은 표지마다 한 번만 계산되어 뱃지 수와 무관하고, 뱃지 가장자리도 바깥 그림을 섞어 흐려집니다. CSS의 blur 값은 가우스 표준편차이고 Android의 흐림 반경은 `0.57735 × 반경 + 0.5px`로 표준편차가 되므로, 거꾸로 계산해 표준편차 12dp를 맞춥니다. ORIGINAL 태그는 도안에서 반투명 바탕을 빼고 같은 방식으로 흐림과 #111414 20% 바탕을 깝니다.

API 31 미만은 흐림을 그릴 수 없어 기존 #111414 70%를 그대로 깝니다. 흐림 없이 20%만 깔면 밝은 표지에서 흰 글자가 읽히지 않기 때문입니다. 웹 상세 히어로 배지(`md`)는 흐림 없는 `bg-black/70`이지만, 사용자 요청으로 앱은 상세 히어로도 목록 카드와 같은 흐린 바탕으로 맞춰 이 자리만 웹과 다릅니다. 같은 뱃지의 턴 수 아이콘도 웹과 같은 Hugeicons BubbleChat으로 바꿨습니다.

Pixel 10 API 37 에뮬레이터에서 화풍 그리드 11칸을 같은 방식으로 스크롤해 비교했을 때, 흐림을 끈 빌드와 켠 빌드 모두 세 번씩 끊긴 프레임 4.3%, 99번째 백분위 19~20ms로 차이가 없었습니다. 실기기, 특히 저사양 기기의 측정은 하지 않았습니다.

## A-074. 일반 제작 임시 저장본을 서버 초안으로 옮기고 Room에는 이관 전 초안과 접수 연결만 남기기

- 날짜: 2026-10-16
- 상태: 확정
- 범위: Android 회원 일반 제작의 임시 저장, 이어서 만들기, 제작 탭 초안 카드, 등록과 재제출의 `draftId`
- 대체 관계: [A-061](#a-061-일반-제작의-별도-초안-테이블과-제출-접수-경계)에서 `general_story_draft`를 일반 제작 입력의 저장 정본으로 쓰던 범위를 대체합니다. 같은 기록의 접수 연결 행, 늦은 저장 거절, 신규 POST를 자동 재전송하지 않는 결정은 유지합니다.

일반 제작 임시 저장본이 기기 Room에만 있어 다른 기기나 웹에서 이어서 만들 수 없었습니다. 서버 초안 API(KNK-1641)가 멱등 PUT과 버전 충돌을 제공하고 웹이 [W-036](1-2-web-adr.md#w-036)으로 먼저 서버 초안으로 옮겨, Android도 회원 일반 제작 입력을 서버 초안에만 둡니다. 기기 안 사본이나 동기화 상태는 두지 않습니다. 서버의 같은 내용 재전송 허용과 버전 판정만으로 재시도와 여러 기기 저장을 다룰 수 있어, 사본과 서버 사이의 동기화 상태를 따로 관리할 이유가 없습니다.

서버는 payload를 해석하지 않으므로 Room 폼 JSON을 그대로 보내지 않고 웹 스냅숏과 같은 v1 형식으로 바꿔 보냅니다. Android 폼은 장르를 이름으로만 들고 있어 모두 직접 이름 항목으로 씁니다. 저장마다 장르 카탈로그를 받아 제공 장르 id로 바꾸는 대안은 요청이 늘고 같은 입력의 payload가 카탈로그 응답에 따라 달라져 서버의 같은 내용 판정을 흐리므로 택하지 않았습니다. 웹은 이름으로 제공 장르를 다시 찾으므로 서로 연 초안의 장르가 유지됩니다.

`general_story_draft` 스키마는 바꾸지 않습니다. 서버 연동 전에 저장한 초안은 제작 탭 진입 때 같은 ID로 옮기고 성공이거나 이미 있는 것만 기기에서 지우며, 상한에 걸린 것은 남겨 카드와 이어서 만들기로 보이게 합니다. 접수 연결 행은 서버가 접수와 함께 초안을 지운 뒤에도 복원된 라우트를 제출본으로 잇고 늦은 저장이 같은 ID의 초안을 되살리지 못하게 막으므로 그대로 씁니다.

새로 시작한 화면은 라우트에 `resume`이 없어 상세 404를 안내 없이 빈 폼으로 엽니다. 프로세스 복원을 위해 새 화면도 상세를 조회하므로, 오프라인에서는 일반 제작 화면이 불러오기 실패와 재시도로 열립니다. 임시 저장도 오프라인에서는 실패합니다. 옮긴 초안의 처음 저장 시각은 옮긴 시각으로 바뀝니다.

검증 근거는 [KNK-1668 구현 계획](../../../manyak-android/docs/plans/knk-1668-general-draft-server.md)을 참조합니다.

## A-075. 간편 제작 초안을 세션 ID로 서버에 두고 진행 기록에 서버 초안 버전 열을 더하기

- 결정일: 2026-10-17 · 기록 확정 상태: Accepted
- 대체 관계: [A-046](#a-046)에서 Room 행을 간편 제작 편집 초안의 저장 정본으로 쓰던 범위 중, 회원 서버 세션의 키워드 초안과 스토리라인 초안 저장을 대체합니다. 퍼널 세션 ID를 행 키로 쓰는 구조, 생성 중과 생성 결과 행, 완성 요청 분리는 유지합니다.
- **맥락:** 공통 계약이 회원 간편 제작 초안을 서버 초안에 두도록 바뀌었고 웹이 [W-037](1-2-web-adr.md#w-037)으로 먼저 옮겼습니다(KNK-1667). 서버 초안 ID는 퍼널 세션마다 고정한 UUID여야 하는데, Android는 [A-046](#a-046)으로 이미 퍼널 세션마다 `draftId`를 만들어 라우트에 싣고 있습니다. 생성 중과 생성 결과 행은 서버 생성 요청 복구 조회에 묶여 기기 안에 남아야 하고, 그 행이 가리키는 서버 초안과 그때의 버전을 알아야 제작 탭이 같은 제작을 한 장으로 보입니다.
- **결정:** 세션의 `draftId`를 그대로 서버 초안 ID로 씁니다. 진입 판정에서 세션의 저장 위치를 한 번 정합니다. 기기 안 행이 있으면 그 행이 정본이고(서버 초안을 가리키면 서버 세션), 없으면 서버 상세를 읽고 서버 세션이 됩니다. 서버 연동 전에 남은 간편 제작 행은 기기 안 세션으로 열고 서버로 옮기지 않습니다. `pending_story_creation`과 `story_completion_request`에 nullable `serverDraftVersion` 열을 더하고(DB v6), 연결이 있지만 아직 서버에 저장한 적 없는 행은 0을 씁니다. 생성 결과는 다음 사용자 저장 때 서버로 옮기고 행을 지웁니다. 완성 요청에는 세션 ID를 항상 `draftId`로 싣습니다.
- **이유:** 세션 ID가 이미 계약이 요구하는 고정 ID라, 웹처럼 단계마다 바뀌는 소유 기록을 서버 초안에 다시 잇는 장치가 필요 없습니다. 연결 정보를 기존 JSON 열(생성 명령이나 진행)에 끼우면 마이그레이션은 없지만 명령과 진행의 의미가 섞여, 보존 마이그레이션 한 단계로 열을 더하는 쪽을 택했습니다. 0은 웹의 숨김 비교 `version <= (draftVersion ?? 0)`과 같은 결과를 열 하나로 냅니다. 기존 행을 옮기지 않는 이유는 [W-037](1-2-web-adr.md#w-037)과 같아, 한꺼번에 옮기면 회원당 5개 상한이 차고 서버 연동 전 생성 요청을 서버 초안에 연결할 근거가 없습니다. 일반 제작은 [A-074](#a-074-일반-제작-임시-저장본을-서버-초안으로-옮기고-room에는-이관-전-초안과-접수-연결만-남기기)로 옮기지만 간편 제작은 진행 기록이 기기 안 복구에 묶여 같은 이관이 맞지 않습니다.
- **주요 영향:** 새 간편 제작도 진입 때 서버 상세를 한 번 조회하므로 오프라인에서는 키워드 단계가 불러오기 실패와 다시 시도로 열립니다. 판정 대기는 채팅방 진입과 같은 늦게 뜨는 스피너로 보입니다. 기존 기기 안 간편 제작 초안은 다른 기기에서 이어서 만들 수 없습니다. 서버 스토리라인 초안 카드는 목록에 단계가 없어 스토리라인 라우트로 열고 복원 뒤 추가 정보 라우트를 쌓습니다. 기기 안 기록이 서버 초안 ID를 행 키로 쓰므로, 기록 뒤에 다른 곳에서 저장해 따로 보이는 서버 카드를 열면 이 기기의 기록을 새 ID의 기기 안 초안으로 떼어 낸 뒤 엽니다. 웹은 기록을 생성 요청 ID로 따로 두어 두 갈래가 서버 초안 연결을 유지하지만, Android의 떼어 낸 갈래는 기기 안에만 저장됩니다. 완성 실패로 되돌아온 초안은 [A-077](#a-077-완성-실패를-추가-정보-단계-초안으로-되돌리고-실패-카드를-없애기)을 따릅니다.
- 근거: [간편 제작 임시 저장](../spec/3-1-client-spec.md#임시-저장), [스토리 제작 임시 저장](../spec/4-backend-server-spec.md#story-drafts), [KNK-1668](https://kimandkang.atlassian.net/browse/KNK-1668), [KNK-1668 간편 제작 계획](../../../manyak-android/docs/plans/knk-1668-simple-draft-server.md)

## A-076. 새 제작 상한을 FAB에서 보이는 초안 카드로 판정하고 제작 탭 첫 조회를 한 스켈레톤으로 덮기

- 결정일: 2026-10-17 · 기록 확정 상태: Accepted
- **맥락:** 공통 계약은 회원의 만들고 있는 스토리 카드가 5장 이상이면 새 제작을 막습니다([W-038](1-2-web-adr.md#w-038)). Android의 새 제작 진입은 제작 탭 FAB에서 여는 제작 방식 선택 하나이고 딥링크나 다른 화면의 제작 진입이 없습니다. 제작 탭은 기기 안 카드를 바로 그리고 서버 초안과 검수 제출본이 늦게 끼어들어, [A-074](#a-074-일반-제작-임시-저장본을-서버-초안으로-옮기고-room에는-이관-전-초안과-접수-연결만-남기기)에서 맨 위를 보던 경우만 맨 위에 두도록 보정했습니다. 웹은 첫 조회를 한 스켈레톤으로 덮도록 바꿨습니다.
- **결정:** FAB 클릭에서 제작 탭의 병합한 초안 카드(서버 초안과 기기 안 초안을 같은 제작 한 장으로 센 결과, 일반 제작 포함)가 5장 이상이면 제작 방식 선택을 열지 않고 토스트를 띄웁니다. 완성 실패로 되돌아온 초안은 세고, 완성 중 카드와 검수 제출본은 세지 않습니다. 퍼널의 진입 판정에서는 따로 막지 않습니다. 제작 탭의 첫 조회는 내 스토리, 서버 초안 목록, 검수 제출본이 모두 응답할 때까지(실패 포함) 초안과 제출본, 내 스토리를 한 스켈레톤으로 덮고 완성 요청 카드만 위에 둡니다.
- **이유:** 서버 초안 하나는 카드 많아야 한 장이라 보이는 초안 카드가 5장 미만이면 새 제작의 첫 저장에 서버 자리가 있습니다. 진입 경로가 FAB 하나라 FAB에서 이미 그린 목록으로 판정하면 퍼널 진입에 목록 조회를 더하지 않아도 됩니다. 스켈레톤은 카드가 따로 끼어들어 목록이 밀리는 것을 막고 웹과 같은 첫 화면을 보입니다.
- **주요 영향:** 새 제작 진입 경로가 늘면 그 경로에도 같은 판정을 더해야 합니다. 서버 목록을 받기 전이나 받지 못했을 때는 기기 안 카드와 마지막으로 받은 서버 목록만 셉니다. 첫 조회 동안에는 기기 안 초안 카드도 스켈레톤 뒤에 있다가 함께 보이며, 첫 조회 뒤로는 서버 목록 조회가 실패해도 기기 안 카드를 유지합니다.
- 근거: [제작 카드와 다중 완성 진행](../spec/3-1-client-spec.md#제작-카드와-다중-완성-진행), [KNK-1668](https://kimandkang.atlassian.net/browse/KNK-1668), [KNK-1668 간편 제작 계획](../../../manyak-android/docs/plans/knk-1668-simple-draft-server.md)

## A-077. 완성 실패를 추가 정보 단계 초안으로 되돌리고 실패 카드를 없애기

- 결정일: 2026-10-17 · 기록 확정 상태: Accepted
- **맥락:** Android는 확정된 완성 실패를 제작 탭의 실패 카드로 남기고 "다시 시도하기"로 같은 요청을 다시 보내거나 삭제하게 했으며, 실패 카드의 제품 정책은 미확정으로 두었습니다. 웹은 실패한 완성 기록을 추가 정보 단계 초안으로 되돌리고 토스트로 알리며, 공통 계약도 완성 실패로 되돌아온 초안을 기기 안 진행 기록과 새 제작 상한의 카드로 셉니다. 사용자가 웹과 같은 동작으로 맞추기로 했습니다.
- **결정:** 서버가 확정적으로 실패를 알리면(완성 POST의 상태 코드 오류 뒤 복구 조회의 FAILED나 404, 새로고침 조회의 FAILED) 요청 행을 지우고 제출한 입력 그대로 그 초안의 추가 정보 단계 편집 초안으로 되돌린 뒤 제작 탭이 "스토리를 완성하지 못했어요"를 띄웁니다. 실패 카드와 같은 요청 재전송은 없앱니다. 이전 버전이 실패로 남긴 행도 새로고침에서 되돌립니다.
- **이유:** 실패한 입력을 이어서 만들기로 고쳐 다시 완성할 수 있고, 제출한 명령을 초안에 남겨 같은 입력이면 같은 requestId를 써 중복 생성과 중복 과금이 없습니다. 되돌린 초안은 서버 초안 연결과 처음 저장 시각을 지켜 카드 순서가 바뀌지 않고, 공통 계약의 상한 계산과도 맞습니다. 요청 삭제와 초안 쓰기를 한 트랜잭션으로 묶어 입력을 잃거나 카드가 겹치지 않게 합니다.
- **주요 영향:** 실패 사유(이프 부족 등)를 따로 안내하지 않고 한 문구로 알립니다. 복구 조회는 사유를 돌려주지 않아 웹의 사유별 안내와 다릅니다. 실패가 제작 탭을 보지 않는 동안 정해지면 토스트 없이 초안 카드만 보입니다. 서버가 완성 요청을 기록하며 지운 초안은 되돌린 초안을 다시 저장할 때 같은 ID로 새로 만들어져 처음 저장 시각이 저장한 시각으로 바뀝니다.

## A-078. 채팅 생성 이어받기를 화면 ViewModel의 재연결 루프로 두고 409를 상세로 가르기

- 결정일: 2026-10-17 · 기록 확정 상태: Accepted
- **맥락:** 서버가 연결이 끊겨도 생성을 계속하고 채팅마다 생성을 하나만 돌리게 되어(KNK-1677, KNK-1678), 공통 계약은 끊긴 생성에 다시 붙고 재진입에서 생성 중인 턴을 이어받으며 409를 `CHAT_TURN_IN_PROGRESS`와 `CHAT_TURN_STALE`로 나눠 다루게 했습니다. Android는 409를 상태 하나로만 알았고, 종단 사건 없는 끊김은 곧바로 상세를 다시 읽어 확정했습니다. 웹은 `followChatGeneration`으로 같은 재연결을 구현했습니다.
- **결정:** 재연결과 결과 판정은 `chat`의 `followGeneration`과 `ChatRoomViewModel`이 맡고 저장소는 스트림 하나씩만 엽니다. 재연결 횟수와 간격은 웹과 같은 4번, 1, 2, 4초입니다. 409는 응답 본문의 `code`를 읽지 않고 상세를 다시 읽어 `generatingTurn`이 있으면 이어받고 없으면 최신 턴을 보입니다. 열린 뒤 읽다가 끊긴 실패는 `ChatSseSource`가 `Interrupted`로 올립니다. 앱이 백그라운드로 가면(구성 변경 제외) 받던 생성의 수신을 끊고, 돌아오면 상세로 이어받거나 저장된 턴을 보입니다.
- **이유:** 결과마다 확정 목록, 전송 잠금, 입력 되돌리기, 선택지 생성이 함께 바뀌어 화면 상태를 가진 ViewModel 밖으로 빼면 같은 정본을 여러 곳이 고칩니다. 409의 두 코드는 어느 쪽이든 입력을 되돌리고 상세를 다시 읽으며, 생성 중이면 상세에 그 생성이 있으므로 코드를 읽지 않아도 같은 결과가 나옵니다. 웹도 같은 판정을 씁니다. 스트리밍 응답 본문을 읽지 않는 기존 원칙도 지킵니다. 읽던 연결의 실패를 네트워크 실패로 올리면 서버가 계속하는 생성을 실패로 안내하게 됩니다. 백그라운드에서는 기기가 프로세스를 얼리거나 연결을 끊어 재연결 시도가 헛돌고, 그 실패 안내가 돌아온 화면에 뜨며 저장된 턴은 방을 다시 열어야 보였습니다. 포그라운드 서비스로 연결을 붙잡는 것은 응답 하나에 알림을 띄워야 해 과합니다.
- **주요 영향:** 409에 새 코드가 생겨도 상세로 판단하므로 따로 다루려면 그때 본문을 읽어야 합니다. 스트림을 열기 전의 네트워크 실패도 상세에 생성 중인 턴이 있으면 이어받는데, 그 생성이 방금 보낸 요청이면 되돌린 입력이 생성 중인 입력과 함께 보입니다. 잠깐 다른 앱을 다녀와도 받던 응답을 처음부터 다시 받습니다. `ChatRoomViewModel`이 detekt `LargeClass` 기준을 넘어 억제합니다.
- 근거: [생성 이어받기](../spec/3-1-client-spec.md#생성-이어받기), [채팅 재연결 계약](../domain/CHAT/BACKEND/4-2-CONTRACT.md#4-2-13-생성-스트림-재연결), [KNK-1692](https://kimandkang.atlassian.net/browse/KNK-1692), [KNK-1692 계획](../../../manyak-android/docs/plans/knk-1692-resume-chat-generation.md)

## A-080. 이프 충전 링크의 tab 쿼리로 처음 열 탭을 정하기

- 결정일: 2026-10-25 · 기록 확정 상태: Accepted
- 대체 관계: [A-045](#a-045-알림-진입-목적지는-서버-deeplink를-정본으로-해석)의 "이프 충전의 `tab` 쿼리는 읽지 않습니다"와 "탭 파라미터는 두 번째 사용처가 생기기 전에는 라우트에 싣지 않습니다"를 대체합니다. `deepLink` 정본 해석, 허용 호스트와 경로, 해석 실패 시 홈, `type` 하위 호환 매핑은 유지합니다.
- **맥락:** 서버가 이프 만료 예정 알림 `CREDIT_EXPIRY_REMINDER`를 추가하고(KNK-1835), 클라이언트가 반영되면 그 `deepLink`를 이프 내역으로 가는 `/my/credits?tab=history`로 바꿉니다. 출석 리마인드는 이미 `/my/credits?tab=free`입니다. 탭 값은 웹과 `purchase`, `free`, `history`로 맞췄고 웹도 같은 쿼리를 읽습니다(KNK-1842). A-045 당시에는 사용처가 무료 탭 하나라 기본 선택만으로 도착했지만, 내역 탭이 두 번째 사용처가 됐습니다.
- **결정:** `DeepLink`는 `/my/credits`의 쿼리에서 `tab`만 골라 값이 정확히 `history`이면 `MyCreditChargeRoute(openHistory = true)`로 엽니다. 웹 전용 `purchase`, 모르는 값, 대소문자가 다른 값, 쿼리 없음은 무료 충전 탭입니다. UTM 같은 다른 쿼리는 무시합니다. `CreditChargeScreen`은 이 값을 선택 탭의 `rememberSaveable` 초기값으로만 쓰고, 탭 전환을 라우트나 URL에 다시 쓰지 않습니다.
- **이유:** Android 이프 충전의 탭은 무료 충전과 내역 둘이라 Boolean 하나로 충분하고, 라우트가 `my`의 탭 열거형을 참조하지 않아 기능 모듈 직접 참조 금지 규칙을 지킵니다. 탭은 여전히 목적지가 아니라 화면 상태라 처음 탭만 라우트로 받고 이후 선택은 구성 변경에서만 유지합니다. 모르는 값을 무료 탭으로 여는 것은 웹 전용 구매 탭 링크나 나중에 생길 값이 오류 없이 기본 화면에 도착하게 하기 위해서입니다.
- **주요 영향:** `MyCreditChargeRoute`가 `data object`에서 기본값 있는 `data class`로 바뀌어 앱 안의 진입은 `MyCreditChargeRoute()`로 무료 충전 탭을 엽니다. Android에 구매 탭이 생기면 Boolean을 탭 값으로 바꿔야 합니다. `deepLink`가 없는 출석 리마인드의 `type` 매핑은 무료 충전 탭 그대로입니다. 웹 앱 열기 링크([A-071](#a-071-웹의-앱-열기-링크를-https-대신-전용-스킴으로-받기))는 경로만 https로 옮기고 쿼리를 버리므로 그 경로로는 항상 무료 충전 탭이 열립니다.

## A-081. 이프 부족 시트의 출석 계약과 절차를 common에 두고 간편 제작은 저장한 뒤 퍼널을 걷어내기

- 결정일: 2026-10-25 · 기록 확정 상태: Accepted
- **맥락:** 회원 이프 부족 안내를 토스트에서 바텀 시트로 바꾸면서(KNK-1841) 시트에서 화면 이동 없이 출석하게 됐습니다. 출석 요청은 `my`의 `CreditRepository`에만 있었고, 시트를 여는 채팅방(`chat`)과 간편 제작 추가 정보 단계(`create`)는 `my`를 참조할 수 없습니다. 간편 제작은 완성 요청과 함께 제작 탭으로 떠나므로 퍼널 안에서 알리려면 완성 전 잔액 선검사가 필요하고, 충전으로 떠날 때 입력을 지킬 방법도 정해야 했습니다. 웹은 초안을 저장한 뒤 퍼널 칸을 이프 충전으로 바꾸고, 돌아와 퍼널을 다시 여는 동작은 히스토리 복귀가 복잡해 두지 않았습니다(KNK-1844).
- **결정:** 출석 요청을 `common`의 `AttendanceClaimer` 계약으로 올리고 `my`의 `CreditRepository`가 이를 상속해 같은 구현을 바인딩합니다. `AttendanceResult`도 `common`으로 옮깁니다. 시트 열기(프로필 재조회), 출석, 충전 중 잠금, 닫기의 절차는 `common`의 `CreditShortageController`가 맡고, 상태는 `StoryReportController`처럼 각 ViewModel 상태에 올립니다. 분석 이벤트는 유료 동작을 아는 ViewModel이 보냅니다. 시트 UI와 문구는 `designsystem`이 갖습니다. 간편 제작의 충전은 버튼 임시 저장과 같은 경로로 저장을 기다려 성공했을 때만 퍼널 이탈을 처리하고, `app`이 퍼널을 걷어낸 뒤 제작 탭 위에 이프 충전을 쌓습니다.
- **이유:** 화면 기능끼리 직접 참조하지 않는 규칙을 지키면서 출석 구현을 한 곳에 둡니다. 절차를 두 ViewModel에 되풀이하면 겹친 요청 거르기와 닫기 잠금이 갈라질 수 있고, 별도 Gradle 모듈은 클래스 하나에 과합니다. `common`은 `analytics`에 의존하지 않아 분석은 ViewModel에 남깁니다. 저장 경로를 버튼 저장과 같게 두면 서버 초안과 기기 안 초안, 충돌과 실패 안내를 새로 만들지 않습니다. 퍼널을 백스택에 남기면 돌아와 같은 퍼널을 다시 여는 동작이 생기는데, 웹과 같이 이어서 만들기는 제작 탭 카드로만 합니다.
- **주요 영향:** 이프 충전 화면의 출석과 시트의 출석이 같은 구현을 씁니다. 출석 결과 문구는 `my`와 `designsystem`에 같은 값으로 두 벌 있습니다. 간편 제작에서 충전으로 떠나면 퍼널의 편집 상태는 사라지고 저장한 초안만 남습니다. 제작 탭으로 떠난 뒤 확정된 완성 실패는 [A-077](#a-077-완성-실패를-추가-정보-단계-초안으로-되돌리고-실패-카드를-없애기)대로 한 문구로 알립니다.
- 근거: [공통 이프 부족 처리](../spec/3-1-client-spec.md#fe-screen-008-로그인마이-페이지), [KNK-1845](https://kimandkang.atlassian.net/browse/KNK-1845), [KNK-1844](https://kimandkang.atlassian.net/browse/KNK-1844), [KNK-1845 계획](../../../manyak-android/docs/plans/knk-1845-credit-shortage-sheet.md)

## A-082. 입력 수위 거절을 키워드 단계로 돌려보내고 완성 거절은 원 응답으로 알리기

- 결정일: 2026-10-27 · 기록 확정 상태: Accepted
- **맥락:** 서버가 AI의 입력 수위 거절을 다른 AI 실패(502)와 나눠 422 `CONTENT_REJECTED`로 응답하고 이프와 게스트 횟수를 돌려주게 됐습니다(KNK-1865). 같은 입력은 다시 거절되는데 Android는 이를 일반 실패와 "다시 만들기"(같은 요청 ID 재시도)로 처리해 같은 입력을 되풀이하게 했습니다. 사용자는 재시도 대신 입력 단계로 돌려보내 고치게 하기로 했습니다(KNK-1868). 웹은 첫 생성 동안 키워드 단계에 머물지만 Android는 생성 요청과 함께 스토리라인 단계로 넘어가 키워드 화면이 사라지고, 스토리 완성은 제출과 함께 제작 탭으로 떠납니다. 완성의 복구 조회는 실패 사유를 돌려주지 않습니다.
- **결정:** 스토리라인 생성이 거절되면 첫 생성, 다시 만들기, 복구 실패 뒤 재요청을 가리지 않고 같은 초안의 키워드 라우트로 바꿔 거절된 요청의 키워드를 채우고 안내합니다. 스토어는 거절 상태와 거절된 요청을 메모리에만 두고 키워드 화면이 한 번 꺼내 가며, 돌아온 키워드는 저장하지 않은 편집으로 셉니다. 다시 만들기의 거절은 직전 결과를 다른 실패처럼 기기 안 기록에 되돌린 뒤 메모리만 비웁니다. 완성 POST의 원 응답이 거절이면 복구 조회 없이 추가 정보 단계 초안으로 되돌리고 `CompletionFailure.CONTENT_REJECTED`로 알려 제작 탭이 거절 문구를 띄웁니다.
- **이유:** 키워드 화면이 생성을 기다리게 바꾸면 스토리라인 단계가 그리는 로딩과 복구 흐름을 다시 짜야 해, 이미 있는 "이어 갈 스토리라인이 없으면 키워드 라우트로 바꾸기" 경로를 씁니다. 요청 명령에 키워드가 모두 있어 프로세스 복원 경로와 같은 재료로 채울 수 있습니다. 거절된 키워드를 자동 저장하면 사용자가 누르지 않은 서버 저장이 생기고, 직전 스토리라인을 지우면 다시 얻기 비싼 결과를 잃습니다. 422는 서버가 요청을 실패로 기록하고 환불까지 마친 확정 응답이라 조회를 거칠 이유가 없고, 조회를 거치면 사유를 잃습니다.
- **주요 영향:** 스토리라인 단계 뒤에는 키워드 단계로 돌아가지 않는다는 규칙에 거절만 예외가 생깁니다. 고르지 않은 직접 입력 태그는 요청에 없어 돌아오지 않습니다. 거절된 키워드는 프로세스 종료에서 복원하지 않습니다. 다시 만들기가 거절된 초안은 키워드 단계에서 저장하지 않고 떠나면 직전 스토리라인 카드로 남고, 키워드를 저장하면 그 키워드 초안이 됩니다. 응답을 받지 못해 복구 조회로 확정한 완성 실패는 [A-077](#a-077-완성-실패를-추가-정보-단계-초안으로-되돌리고-실패-카드를-없애기)대로 한 문구입니다. `CreationProgressAccess.completionFailures`가 사유를 싣도록 바뀌었습니다.
- 근거: [Android 간편 제작 흐름과 보존](../spec/3-3-android-spec.md#간편-제작-흐름과-보존), [스토리 생성 퍼널](../spec/3-1-client-spec.md#3-1-4-스토리-생성-퍼널), [KNK-1870](https://kimandkang.atlassian.net/browse/KNK-1870), [KNK-1870 계획](../../../manyak-android/docs/plans/knk-1870-content-rejection.md)

## A-083. 신규 가입 온보딩을 메인 백스택의 루트로 두고 완료를 기기 안 회원 귀속 표시로 판정하기

- 결정일: 2026-10-28 · 기록 확정 상태: Accepted
- **맥락:** 로그인하면 바로 홈 탭이 열려, 처음 가입한 사용자가 무엇을 해야 하는지 모른 채 목록을 마주했습니다. 신규 가입 회원에게 오리지널 스토리를 넘겨 보며 바로 채팅을 시작하는 화면을 먼저 보이고, 채팅을 시작하거나 간편 제작으로 가기 전에는 이 단계를 건너뛸 수 없게 하기로 했습니다(KNK-1892). 가입 여부는 토큰 발급 응답의 `isNewUser`에만 있고 그 순간 인증 백스택이 사라지며, 신규 가입 초대 코드 안내가 이미 이 신호를 `SignupOnboardingWriter`로 기록해 회원 화면에서 소비하고 있었습니다. 서버에는 온보딩 완료 기록이 없습니다.
- **결정:** `SignupOnboardingWriter`를 Hilt `@IntoSet` 묶음으로 바꿔 `auth`가 등록된 기록기를 모두 부릅니다. `home`의 `StoryOnboardingStore`가 자기 DataStore 파일(`story-onboarding`)에 표시 하나를 두고 `UserScopedStore`로 로그아웃 정리에 참여합니다. `app`은 이 표시로 메인 백스택의 루트를 `StoryOnboardingRoute` 또는 `MainTabsRoute`로 고르고, 표시를 읽기 전에는 메인 그래프를 열지 않습니다. 채팅 생성 성공(캐러셀이나 온보딩 위에서 연 상세)과 간편 제작 진입에서 루트 키만 `MainTabsRoute`로 바꿔 끼우고, `RootViewModel`이 완료 이벤트를 보내며 표시를 지웁니다. 같은 실행의 완료는 메모리에도 둡니다.
- **이유:** 온보딩을 셸 위에 쌓으면 시스템 뒤로가기와 예측형 뒤로가기가 홈을 드러내 우회가 됩니다. 루트에 두면 뒤로가기는 앱을 떠나고 다시 열면 같은 화면이며, 뒤로가기를 가로채는 별도 처리가 필요 없습니다. 루트 키만 바꾸면 상세에서 시작한 채팅의 "상세로, 그다음 탭으로" 규칙이 그대로 이어집니다. 완료를 서버에 두면 새 API 계약이 필요하고, 기기 안 표시는 앱을 지우거나 다른 기기에서 로그인했을 때 온보딩을 건너뛰는 정도의 손실만 있습니다. 기록기를 묶음으로 바꾸면 `auth`가 가입 뒤 안내의 종류를 알 필요가 없습니다. 메모리 완료 표시는 저장 실패 뒤 화면 재생성이 채팅방에 있던 사용자를 온보딩으로 되돌리지 않게 합니다.
- **주요 영향:** 신규 가입 회원의 첫 회원 화면은 홈이 아니라 온보딩이고, 알림 권한과 초대 코드 안내, 알림이나 웹 링크로 연 화면은 온보딩 위에 뜹니다. 완료 저장이 실패하면 다음 실행에서 온보딩이 다시 열립니다. 다른 기기나 재설치 뒤의 로그인은 `isNewUser`가 거짓이라 온보딩이 열리지 않습니다. 오리지널은 첫 페이지(20편)만 읽습니다.
- 근거: [Android 신규 가입 온보딩](../spec/3-3-android-spec.md#신규-가입-온보딩), [Android 내비게이션과 화면](../design/1-2-android-design.md#1-2-4-내비게이션과-화면), [분석 Spec](../spec/6-analytics.md#6-4-2-20-신규-가입-온보딩--phase-3--구현knk-1892), [KNK-1892](https://kimandkang.atlassian.net/browse/KNK-1892), [KNK-1892 계획](../../../manyak-android/docs/plans/knk-1892-signup-story-onboarding.md)

## A-084. 로그인 화면의 가입 보상을 버튼을 가리키지 않는 흐린 유리 배지로 알리기

- 결정일: 2026-10-28 · 기록 확정 상태: Accepted
- **맥락:** 로그인 화면 버튼 위의 계정 연동 안내는 처음 온 사람에게 가입할 이유를 주지 못했습니다. 가입 보상(`signupReward`)을 버튼 근처에서 알리기로 했습니다.
- **결정:** 두 소셜 로그인 버튼 위에 표지 지표 배지와 같은 흐린 유리 바탕(`coverBackdrop`)의 배지를 두고 "지금 가입하고 N 이프 받기"를 표시합니다. N에는 `signupReward`를 그대로 쓰고, 다른 이프 수치와 같이 N 바로 앞에 이프 마크를 붙여 수치만 브랜드 색으로 강조합니다. 배지는 천천히 떠올랐다 내려앉습니다. 흐림 원천은 덮개 아래의 배경 그림입니다. 계정 연동 안내는 Android 로그인 화면에서 뺍니다.
- **이유:** 행동형 문구가 버튼을 누를 이유를 바로 말합니다. 서버 수치를 이프 그대로 보여 원화 환산에 필요한 충전 단가와 묶이지 않고, 가입 뒤 잔액에서 같은 마크와 수치를 다시 봅니다. 카카오 버튼을 가리키는 말풍선은 카카오로 가입해야만 받는 혜택처럼 읽혀 쓰지 않습니다. 흰 바탕은 어두운 화면에서 지나치게 튀어, 배경 그림을 흐리게 비추는 유리 바탕으로 화면과 어울리게 합니다. 몸통과 꼬리를 따로 그리면 움직일 때 이음새가 비쳐 한 도형으로 그립니다.
- **주요 영향:** 처음 온 사람은 이프의 가치를 문구만으로는 알 수 없습니다. 로그인 전에는 계정 연동 순서를 안내하지 않습니다. 탈퇴 뒤 재가입처럼 보상 신원이 이미 보상을 받은 사람에게도 같은 문구가 보입니다. 어두운 배경 그림 위에서는 배지 바탕이 배경과 거의 같아 글자만 떠 보이고, API 31 미만은 흐림 대신 진한 바탕입니다.

## A-085. 홈 카드에서 좋아요 수를 빼고 상세의 좋아요 성공을 홈으로 전달하지 않기

- 결정일: 2026-10-28 · 기록 확정 상태: Accepted
- 대체 관계: [A-049](#a-049)의 좋아요 성공 홈 카드 전달만 부분 대체
- **맥락:** 홈 카드에서 좋아요 수 배지를 숨기기로 했습니다. 상세에서 성공한 좋아요 수를 홈 카드에 반영하던 전달 계약과 조회 중 합산은 화면에 드러나지 않는 값만 맞추게 됐습니다.

## A-086. 신규 가입 초대 코드 안내를 가입한 다음 실행의 홈 탭에서 띄우기

- 결정일: 2026-10-29 · 기록 확정 상태: Accepted
- 대체 관계: [A-083](#a-083)의 "초대 코드 안내가 온보딩 위에 뜬다"만 부분 대체
- **맥락:** 가입한 실행에서는 알림 권한, 스토리 온보딩, 첫 채팅이 이어지는데 초대 코드 시트가 온보딩 위에 겹쳐 첫 행동을 가렸습니다. 시트를 가입한 다음 접속의 홈 탭에서 띄우기로 했습니다(KNK-1899). 가입 신호(`isNewUser`)는 가입 순간에만 있고, 안내 표시는 이미 디스크에 남아 등록하거나 닫을 때까지 유지됩니다.
- **결정:** 디스크 표시는 그대로 두고 `InviteOnboardingStore`가 가입을 기록한 실행을 프로세스 메모리에 둬, 그 실행의 `pending`을 거짓으로 냅니다. 앱을 다시 실행하면 메모리가 비어 표시가 그대로 보입니다. 루트는 메인 그래프가 알리는 홈 탭 표시 여부(셸이 메인 백스택 맨 위이고 홈 탭을 고름)가 참일 때만 시트를 그립니다. 광고 재질문은 지금처럼 `pending`이 끝난 뒤에 묻습니다.
- **이유:** "다음 접속"을 프로세스 수명으로 읽으면 새 저장 키나 시각 비교 없이 기존 표시 하나로 끝납니다. 홈 탭을 기다리면 채팅방, 제작 퍼널, 알림으로 연 화면 위에 시트가 겹치지 않습니다.
- **주요 영향:** 가입한 뒤 프로세스가 살아 있는 동안은 백그라운드에서 돌아와도 시트가 뜨지 않고, 시스템이 프로세스를 정리했으면 다음 열기에 뜹니다. 가입한 실행의 광고 재질문 판정은 초대 시트를 기다리지 않습니다. 웹은 첫 로그인 직후에 띄우는 그대로입니다.
- 근거: [Android 신규 가입 온보딩](../spec/3-3-android-spec.md#신규-가입-온보딩)

## A-087. 간편 제작 공개 범위를 기본 공개로 기존 초안 JSON에 더하고 기본값은 비워 두기

- 결정일: 2026-10-29 · 기록 확정 상태: Accepted
- **맥락:** 간편 제작 완성 요청은 서버 기본값인 비공개로만 만들어졌습니다. 추가 정보 단계의 이미지 스타일 아래에 일반 제작과 같은 공개 스위치를 두고, 일반 제작과 달리 켜진 채(공개) 시작하기로 했습니다(KNK-1899). 서버 `POST /stories/simple`은 이미 `visibility`(생략하면 `PRIVATE`)를 받습니다. 편집 초안과 완성 요청은 행마다 JSON 문자열 컬럼이고, 서버 초안 페이로드는 웹과 같은 형식(`schemaVersion` 1)입니다.
- **결정:** 공개 범위를 `CreationProgress`(기본 `PUBLIC`)와 `StoryCompletionCommand`(기본 `PRIVATE`)에 `common`의 `StoryVisibility`로 더합니다. 기기 안 JSON(`progress`, `completionCommand`)에는 각자의 기본값과 다를 때만 `visibility`를 써 이 기능 전과 같은 JSON을 남깁니다. 서버 초안 페이로드에는 진행의 `visibility`를 늘 싣고, 없거나 모르는 값은 진행이면 공개, 완성 요청이면 비공개로 읽습니다. 완성 요청에는 늘 싣고, requestId 재사용 조건에 공개 범위를 더합니다. 화풍처럼 스토리라인 재생성과 다시 선택하기에 남깁니다.
- **이유:** Room 버전과 서버 초안 스키마 버전을 올리지 않고 선택 필드 하나로 끝납니다. 진행에 값이 없으면 스위치를 처음 보는 것이므로 기본값으로 열고, 완성 명령에 값이 없으면 공개 범위 없이 나가 서버가 비공개로 만든 요청이므로 그대로 비공개로 다시 보냅니다. 웹 파서는 모르는 키를 무시해 Android가 쓴 초안을 그대로 엽니다. 공개 범위가 다르면 서버가 다른 스토리를 만들어야 하므로 이전 requestId로 저장된 결과를 돌려받으면 안 됩니다.
- **주요 영향:** 웹에서 저장한 초안과 이 기능 전에 저장한 초안은 Android에서 스위치가 켜진 채 열리므로, 그대로 완성하면 웹이나 이전 버전과 달리 공개 스토리가 됩니다. 웹이 같은 초안을 다시 저장하면 `visibility`가 빠져 다음에는 다시 켜진 채 열립니다.
