# 커밋 생성

## 목적

로컬 변경사항을 먼저 이해한 뒤 팀 Git 컨벤션에 맞는 커밋 하나를 만듭니다. 핵심은 빠르게 커밋하는 것이 아니라, 관련 없는 변경사항을 섞지 않고 Jira 이슈와 연결되는 메시지를 작성하는 것입니다.

## 팀 규칙

커밋 메시지 형식:

```text
[KNK-{Jira이슈번호}] {태그}: {커밋 제목}

- {커밋 내용}
- {커밋 내용}
```

- 제목과 본문은 한국어로 작성합니다.
- 제목과 본문 사이에는 한 줄을 띄웁니다.
- 본문끼리는 띄어쓰지 않습니다.
- 제목만으로 충분하면 본문은 생략합니다.
- 태그는 `Init`, `Feat`, `Fix`, `Docs`, `Design`, `CICD`, `Refactor`, `Chore` 중 하나를 사용합니다.

## 판단 기준

- 현재 브랜치가 `{tag}/KNK-{번호}-{제목}`이면 그 Jira 키를 우선 사용합니다.
- 브랜치에서 Jira 키를 찾을 수 없고 사용자가 제공하지 않았다면 커밋하지 말고 Jira 키를 요청합니다.
- 브랜치 태그가 없으면 변경 내용에서 추론하되, 확신이 낮으면 사용자에게 확인합니다.
- 제목은 "무엇을 했다"가 바로 보이게 짧게 씁니다.
- 제목 끝에 마침표를 붙이지 않습니다.
- 파일명 나열보다 사용자 또는 시스템 관점의 변경 의도를 우선합니다.
- 본문은 제목만으로 부족할 때만 1~3개 bullet로 씁니다.

| 브랜치 태그 | 커밋 태그 | 기준 |
|---|---|---|
| `feat` | `Feat` | 새로운 기능 추가 |
| `fix` | `Fix` | 버그 수정 |
| `docs` | `Docs` | 문서 수정 |
| `design` | `Design` | UI, 스타일, 디자인 수정 |
| `cicd` | `CICD` | 배포, CI/CD 설정 수정 |
| `refactor` | `Refactor` | 기능 변화 없는 코드 구조 개선 |
| `chore` | `Chore` | 설정, 의존성, 기타 유지보수 |

## 작업 흐름

1. 현재 위치가 Git 레포지토리인지 확인합니다.
   - `git rev-parse --show-toplevel`
   - `git status --short --branch`
2. 변경사항을 커밋 전에 반드시 검토합니다.
   - `git diff --stat`
   - `git diff --name-status`
   - `git diff --staged --stat`
   - `git diff --staged --name-status`
   - 새 파일은 파일 목록과 내용을 직접 확인합니다. 바이너리 파일은 종류와 경로만 확인합니다.
3. Jira 키와 태그를 결정합니다.
   - 현재 브랜치가 `{tag}/KNK-{번호}-{제목}`이면 그 Jira 키를 우선 사용합니다.
   - 태그는 변경사항에 맞는 적절한 태그를 사용합니다.
   - 브랜치에서 Jira 키를 찾을 수 없고 사용자가 제공하지 않았다면 커밋하지 말고 Jira 키를 요청합니다.
   - 브랜치 태그가 없으면 변경 내용에서 추론하되, 확신이 낮으면 사용자에게 확인합니다.
4. 변경사항이 하나의 논리적 작업인지 판단합니다.
   - 관련 없는 파일이 섞여 있으면 한 커밋에 묶지 말고 사용자에게 분리 여부를 확인합니다.
   - 사용자가 만들지 않은 기존 변경사항으로 보이는 파일은 임의로 수정, 되돌리기, 삭제하지 않습니다.
5. 필요한 경우 검증을 실행합니다.
   - 코드 변경이면 프로젝트에서 분명한 테스트, 타입체크, 린트 명령을 우선 실행합니다.
   - 명령이 없거나 시간이 큰 작업이면 실행하지 않은 이유를 최종 보고에 남깁니다.
6. 검토한 파일만 stage합니다.
   - `git add .`를 먼저 실행하지 않습니다.
   - `git add -- path/to/file ...`처럼 커밋 대상 파일을 명시합니다.
7. 팀 규칙에 맞는 커밋 메시지로 커밋합니다.
   - `git commit -m "[KNK-123] Feat: 로그인 화면 구현"`
   - 본문이 필요하면 메시지 파일을 만들어 `git commit --file <message-file>`로 커밋합니다.
   - 메시지 파일은 제목 다음에 빈 줄을 한 줄만 넣고, 본문 bullet 사이에는 빈 줄을 넣지 않습니다.
   - 여러 `-m` 옵션에 bullet을 하나씩 넣지 않습니다. Git은 각 `-m` 값을 별도 문단으로 처리해 bullet 사이에 빈 줄을 추가합니다.
8. 커밋 결과와 남은 변경사항을 확인합니다.
   - `git log -1 --oneline`
   - `git status --short`

## 명령 사용법

좋은 예:

```text
[KNK-141] Feat: 커밋 생성 스킬 추가

- 변경사항 검토 후 커밋하는 공용 스킬 작성
- README 스킬 목록 갱신
```

본문이 있는 커밋은 위 예시처럼 하나의 메시지 파일에 작성한 뒤 커밋합니다.

```bash
git commit --file /tmp/commit-message.txt
```

## 금지 사항

- 변경사항을 읽기 전에 `git add .` 또는 `git commit -am`을 실행하지 않습니다.
- 본문 bullet을 각각 별도 `-m` 옵션으로 전달하지 않습니다.
- `git reset`, `git checkout --`, `git clean`, `git stash`, `rm`으로 사용자 변경사항을 정리하지 않습니다.
- Jira 키가 불명확한 상태로 임의의 `KNK-*`를 만들지 않습니다.
- 관련 없는 변경사항을 "어차피 커밋 요청이니까"라는 이유로 한 커밋에 묶지 않습니다.
- 테스트 실패, 린트 실패, 남은 unstaged 변경사항을 숨기지 않습니다.

## 완료 보고

- 커밋 해시와 커밋 메시지를 보고합니다.
- 커밋에 포함한 파일을 요약합니다.
- 실행한 검증 명령과 결과를 알립니다.
- 검증을 실행하지 못했다면 이유를 짧게 알립니다.
- stage하지 않고 남긴 변경사항이 있으면 반드시 언급합니다.
