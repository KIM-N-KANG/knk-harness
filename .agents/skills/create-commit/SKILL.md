# 커밋 생성

## 메시지 규칙

```text
[KNK-{Jira이슈번호}] {태그}: {커밋 제목}

- 필요한 경우 변경 내용
- 추가 설명
```

- Jira 키는 사용자 명시 → 현재 작업에 대해 대화에서 확정된 키 → 현재 브랜치 순서로 찾습니다. 사용자가 명시적으로 키를 교체했다면 새 키를 따릅니다. 키가 없거나 충돌이 해소되지 않았거나 작업과 무관한 키로 확인되면 필요한 키만 질문합니다. 임의의 키를 만들지 않습니다.
- 제목과 본문은 한국어로 작성합니다. 제목은 변경 목적과 결과를 짧게 쓰고 마침표를 붙이지 않습니다.
- 제목만으로 충분하면 본문은 생략합니다. 본문이 필요하면 제목 뒤에 빈 줄 하나를 두고 1~3개 bullet로 씁니다. bullet 사이에는 빈 줄을 넣지 않습니다.
- 태그는 사용자가 지정한 값을 우선하고, 그 외에는 **이번 변경 내용**에 따라 아래에서 선택합니다. 브랜치 태그는 참고이며, 태그 선택만을 이유로 확인을 요청하지 않습니다.

| 변경 내용 | 태그 |
| --- | --- |
| 저장소 초기 설정 | `Init` |
| 새 기능 | `Feat` |
| 버그 수정 | `Fix` |
| 문서 수정 | `Docs` |
| UI·스타일·디자인 | `Design` |
| 배포·CI/CD | `CICD` |
| 동작을 유지하는 구조 개선 | `Refactor` |
| 설정·의존성·유지보수 | `Chore` |

## 작업 흐름

1. 대상 저장소와 현재 브랜치를 `git rev-parse --show-toplevel`, `git status --short --branch`로 확인합니다.
2. **변경 내용 자체**를 읽습니다. `git diff`와 `git diff --cached`로 unstaged·staged 내용을 모두 검토합니다. 목록·통계는 탐색 보조로만 쓰며 새 파일은 직접 읽습니다. 바이너리는 경로·종류와 작업 관련성을 확인합니다.
3. Jira 키와 커밋 범위를 결정합니다. 관련 없는 unstaged 파일은 그대로 두고 대상이 명확한 변경만 진행합니다. 같은 파일에 변경이 섞였거나 포함 범위가 불분명한 경우에만 질문합니다.
4. **기존 staged 변경도 커밋에 포함된다는 점을 확인합니다.** 요청 범위 밖의 staged 변경이 있으면 그대로 커밋하지 않으며, 임의로 unstage하거나 기존 index 구성을 바꾸지 않습니다. 분리 방법에 대한 승인이 이미 있으면 따르고, 없으면 해당 부분만 질문합니다.
5. 프로젝트의 필수 검증을 따릅니다. 동일한 변경에 대해 이미 통과한 검증은 재사용하고, 이후 변경이 있다면 필요한 검사를 다시 실행합니다. 문서만 변경했다면 프로젝트 지침에 따라 내용·경로·링크를 검증합니다. 오래 걸린다는 이유로 필수 검사를 생략하지 않습니다.
   - 필수 검증이 실패하거나 실행 불가이면 원인과 영향 범위를 확인합니다. 요청 범위의 수정 가능한 문제는 해결하고 재검증합니다.
   - 해결되지 않은 필수 검증이 있으면 커밋을 보류하고 결과를 보고합니다. 프로젝트 정책상 허용되는 예외를 사용자가 이미 승인했다면 그 범위에서 진행하고 예외를 기록합니다. 훅을 임의로 우회하지 않습니다.
6. 검토한 대상만 `git add -- <대상 파일...>`로 stage합니다. `git add .`나 `git commit -am`으로 범위를 넓히지 않습니다. `git diff --cached`와 `git diff --cached --check`로 **staged 전체**를 다시 확인합니다. staged diff가 없으면 새 커밋을 만들지 않습니다.
7. 메시지를 작성하고 커밋합니다. 본문은 임시 메시지 파일에 실제 줄바꿈으로 기록해 `git commit --file <메시지 파일>`로 전달합니다. bullet마다 `-m`을 사용하지 않습니다. 제목만 있으면 `git commit -m`을 사용할 수 있습니다.
8. `git show --stat --oneline HEAD`와 `git show --format= HEAD`로 실제 포함 내용과 커밋 훅의 수정 결과를 확인합니다. `git status --short`로 남은 staged·unstaged·미추적 변경을 확인합니다. 요청 없이 amend하거나 push하지 않습니다.

기존 변경사항을 정리하기 위해 reset·checkout 복원·clean·stash·삭제 명령을 임의로 실행하지 않습니다. 이미 승인된 커밋 범위나 작업은 같은 이유로 다시 확인하지 않습니다.

## 완료 보고

커밋 해시·메시지, 포함한 변경, 검증 결과와 예외, 남은 staged·unstaged·미추적 변경을 간결하게 보고합니다. 미완료 검사나 남은 변경사항을 숨기지 않습니다.
