# 슬랙 에러 제보·기능 요청 전송

## 목적

지금 대화에서 다룬 에러, 운영 분석 결과, 기능 아이디어를 팀 템플릿에 맞는 슬랙 메시지로 정리해 #김앤강 채널에 보냅니다. 핵심은 빠르게 보내는 것이 아니라, 받는 사람(사람과 AI 에이전트 모두)이 메시지만 보고 맥락을 조회해 바로 작업을 시작할 수 있는 메시지를 만드는 것입니다.

## 전송 대상

- 채널: #김앤강 (channel_id: `C0BM5UW3PCL`)
- 사용자가 다른 채널이나 DM을 명시하면 그쪽을 우선합니다. 채널을 찾을 수 없으면 임의로 다른 채널에 보내지 말고 사용자에게 확인합니다.

## 템플릿

메시지 형식은 `docs/templates/slack-report.md`를 따릅니다. 작성 전에 반드시 이 문서를 읽습니다. 요지는 다음과 같습니다.

- 에러 제보는 🐛 템플릿, 기능 요청은 ✨ 템플릿을 사용합니다.
- 첫 줄은 `[영역]` 접두어 + 한 줄 요약: `[web]`(manyak-web), `[server]`(manyak-server), `[ai]`(manyak-ai), `[infra]`.
- `*요청*` 줄에 `조사`, `수정`, `문서 반영`, `결정`, `공유만` 중 하나를 적습니다. 받는 쪽이 무엇을 해야 하는지 알려주는 줄이라 비워두지 않습니다.
- 앵커(Sentry 링크, 세션 리플레이, chat_id, Jira 키, 파일:라인)는 접근 가능한 MCP로 조회해서 채우고, 조회 수단이 없을 때만 `미확인`으로 남깁니다.
- 확인하지 못한 값은 지어내지 않고 `추정:` 접두어로 구분합니다. URL은 조회 결과에서 복사한 것만 사용합니다.
- 본문은 짧게, 로그·스택트레이스·상세 분석은 스레드 댓글로 보냅니다.
- 시각에는 타임존(KST/UTC)을 명시하고, 사용자 원문·secret은 넣지 않습니다.

## 작업 흐름

1. `docs/templates/slack-report.md`를 읽습니다.
2. 대화 맥락에서 제보 유형(에러/기능)과 내용을 파악합니다. 무엇을 보낼지 불명확하면 사용자에게 확인합니다.
   - 요청 유형(`조사`/`수정`/`문서 반영`/`결정`/`공유만`)을 함께 정합니다. 대화만으로 판단이 서지 않으면 임의로 `수정`을 넣지 말고 사용자에게 확인합니다.
3. 앵커를 채웁니다.
   - 대화에서 이미 확보한 링크·ID를 우선 사용합니다.
   - 비어 있는 앵커는 사용 가능한 MCP(Sentry, Amplitude, Jira)로 조회합니다. 조회에 실패하면 `미확인`으로 표기합니다.
4. 템플릿에 맞춰 본문과 스레드용 상세 내용을 나눠 작성합니다.
5. 전송 전에 템플릿의 "전송 전 체크리스트"를 확인하고, **작성한 메시지 전문을 사용자에게 보여 준 뒤 확인을 받습니다.** 슬랙 전송은 되돌릴 수 없으므로 확인 없이 보내지 않습니다.
6. 확인받은 본문을 `slack_send_message`로 채널에 보냅니다.
7. 스레드용 상세 내용이 있으면 본문 전송 결과의 `ts`를 `thread_ts`로 사용해 스레드에 이어 보냅니다.
8. 전송된 메시지 링크를 사용자에게 보고합니다.

## 슬랙 서식 주의

- 슬랙은 GitHub Markdown이 아닙니다. 굵게는 `*텍스트*`, 인라인 코드는 백틱, 목록은 `•` 또는 `-`를 사용합니다.
- 링크는 `<URL|표시 텍스트>` 형식을 사용합니다.
- 제목 수준(`#`)은 동작하지 않으므로 굵은 줄로 대신합니다.

## 금지 사항

- 사용자 확인 없이 메시지를 전송하지 않습니다.
- 확인받은 내용과 다른 내용을 보내지 않습니다. 확인 후 내용을 고쳤다면 다시 확인받습니다.
- 앵커 URL을 패턴 조합으로 만들어 넣지 않습니다.
- 사용자 입력 원문, 채팅 원문, secret 값을 메시지에 넣지 않습니다.
- 조회하지 못한 원인·위치를 사실처럼 단정하지 않습니다.
- 사용자가 조사나 공유만 원한 상황에서 요청 유형을 `수정`으로 올려 보내지 않습니다.

## 완료 보고

- 전송한 채널과 메시지 링크를 보고합니다.
- 스레드에 보낸 상세 내용이 있으면 함께 알립니다.
- `미확인`으로 남긴 앵커가 있으면 어떤 항목인지 언급합니다.
