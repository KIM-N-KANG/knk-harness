# 기술 문서 작성

## 핵심 규칙

멋져 보이기 위해서가 아니라, 전달하기 위해 쓰세요. 모든 문서는 대상 독자, 독자가 수행할 작업, 정확한 정보 전달에 맞게 최적화합니다. 일관된 용어와 객관적 근거를 사용해 명확하고 짧고 직접적인 한국어 문장을 선호합니다.

자세한 출처 노트가 필요하면, 예시, 전체 체크리스트 또는 더 깊은 한국어 표현 규칙이 필요한 작업에서 `references/technical-writing-notes.md`를 읽으세요.

## 작업 흐름

1. 초안을 작성하기 전에 문서를 계획합니다. 독자, 독자의 숙련도, 문서 목적, 독자에게 기대하는 행동, 필요한 사전 지식, 어조, 정확한 주제, 문서 유형을 파악합니다.
2. 독자의 작업 흐름을 중심으로 문서를 구성합니다. 핵심 내용을 먼저 배치한 뒤 중요한 사실, 예시, 정의를 배치합니다. 각 섹션의 요지를 드러내는 제목을 사용합니다.
3. 먼저 완성도를 목표로 초안을 작성합니다. 문법이나 문체를 다듬기 전에 독자에게 필요한 정보를 포함합니다.
4. 명확성, 간결성, 일관성을 기준으로 다시 씁니다. 한 문장에 하나의 주제만 담고, 긴 문장을 줄이며, 군더더기를 제거하고, 주어와 서술어를 맞추며, 같은 개념에는 같은 용어를 사용합니다.
5. 객관적으로 검토합니다. 제목, 목차, 누락된 정보, 불필요한 정보, 중복 내용, 근거, 출처, 용어, 문단 구성, 시각 자료, 표, 문법을 확인합니다.

## 독자와 깊이

- 비개발자를 대상으로 할 때는 개념, 기본 맥락, 필수 용어를 쉬운 말로 설명합니다. 독자의 관점에서 다시 읽습니다.
- 개발자를 대상으로 할 때는 일반적인 용어를 과도하게 설명하지 않습니다. 설명은 간결하고 작업 중심으로 유지합니다.
- 혼합 독자를 대상으로 할 때는 각 독자가 제목과 섹션에서 필요한 상세 수준을 선택할 수 있도록 문서를 구성합니다.
- 어조를 일관되게 유지합니다. 폭넓은 독자를 대상으로 할 때는 친근한 어조를 사용하고, 전문적인 작업 지침에는 필요에 따라 공식적인 명령형 어조를 사용합니다.

## 초안 작성 지침

- 결론이나 핵심 지침으로 시작합니다. 핵심 내용을 끝에 숨기지 않습니다.
- 제목은 명사 더미가 아니라 요약문처럼 씁니다. 독자는 제목만 보고도 해당 섹션의 목적을 이해할 수 있어야 합니다.
- 한 문장에는 하나의 생각만 담습니다. 주어, 서술어, 조건, 결과를 추적하기 어려워지면 문장을 나눕니다.
- 주장은 객관적 근거로 뒷받침합니다. 인상이나 추측보다 검증된 사실, 숫자, 예시, 테스트 결과 또는 인용을 선호합니다.
- 대상 독자가 모를 수 있는 용어와 약어는 처음 사용할 때 정의합니다.
- 제품명, 회사명, 숫자, 단위, 날짜, 금액을 정확하게 사용합니다. 민감한 값은 두 번 이상 확인합니다.
- 수동태가 필요한 경우가 아니라면 능동태를 선호합니다. 행위자를 명확히 합니다.

## 환경과 버전 맥락

동작이 도구, 프레임워크, 라이브러리, 런타임 또는 운영체제에 따라 달라질 때는 독자가 같은 결과를 재현할 수 있도록 문서 상단 근처에 검증된 환경을 명시합니다.

- 관련 운영체제, 런타임, 프레임워크, 라이브러리, 패키지 매니저, 데이터베이스, 브라우저, CLI 또는 SDK 버전을 포함합니다.
- 명령어나 API에 영향을 주는 Next.js, React, Tailwind CSS, Node.js, Python, Java, Spring, Gradle, Docker, Kubernetes, 클라우드 SDK와 같은 메이저 버전에 민감한 도구를 언급합니다.
- 검증된 사실과 가정을 구분합니다. 환경을 알 수 없다면 질문하거나, 예시가 실제로 버전에 독립적일 때만 버전 비의존 예시라고 표시합니다.
- 명령어, 설정, 코드 샘플을 명시한 환경에 맞게 업데이트합니다.

## 코드와 Markdown 형식

- 본문에서 파일명, 경로, 변수, 클래스, 함수, 명령어, 패키지명, UI 레이블, 리터럴 값을 언급할 때는 인라인 코드로 감쌉니다.
- 여러 줄의 코드, 명령어, 설정, 로그, 구조화된 예시는 fenced code block을 사용합니다.
- 가능하면 코드 fence에 `tsx`, `ts`, `js`, `bash`, `json`, `yaml`, `python`, `sql`, `text` 같은 언어 식별자를 추가합니다.
- 독자가 스니펫을 복사하거나 이해하는 데 도움이 될 때 짧은 코드 관련 맥락을 주석에 넣습니다. 개념 설명, 경고, 트레이드오프는 주변 본문에 둡니다.
- 실행 가능한 예시는 쉽게 복사할 수 있게 유지합니다. 장식용 주석, 숨겨진 전제 조건, 설명되지 않은 플레이스홀더를 피합니다.
- 예상 출력, 오류 출력, 입력 명령어를 함께 보여 주면 혼동될 수 있을 때는 서로 다른 fenced code block으로 분리합니다.

## 한국어 스타일 규칙

한국어 기술 문장을 다듬을 때 다음 재작성을 적극적으로 적용합니다.

- `이`, `그`, `이를 통해` 같은 모호한 대명사를 실제 명사로 바꿉니다.
- 추측하거나 완곡한 어미를 `~합니다`, `~입니다` 또는 작업에 적합한 명령형처럼 직접적인 어미로 바꿉니다.
- 의미를 더하지 않는 군더더기 명사와 가벼운 동사를 제거합니다: `진행`, `처리`, `필요`, `발생`, `제공해 주다`, `구현해 주다`.
- 번역투를 자연스러운 한국어로 바꿉니다. 흔한 대상에는 `~에 대해`, `~에 의해`, `~을 통해`, `가능하다/불가능하다`, `~을 가지고 있다`, `~의 경우`가 있습니다.
- `통해`를 정확한 동사나 조사로 바꿉니다: `클릭해`, `사용해`, `로`, `에서`, `때문에` 또는 문맥에 맞는 다른 표현.
- 같은 명사를 반복하고 문장을 길게 만드는 `무엇은 ~ 무엇이다` 구조를 피합니다.
- 불필요한 조사를 줄입니다. 특히 반복되는 `을/를`과 겹친 `의`를 줄입니다.
- 공식 문서에서는 속어, 내부 축약어 또는 비표준 약어를 사용하지 않습니다.

## 시각 자료

시각 자료는 독자가 글만 읽는 것보다 더 빠르게 이해하는 데 도움이 될 때만 사용합니다. 모든 시각 자료는 보여 주기 전에 소개합니다.

- 순서가 없는 병렬 항목에는 글머리 기호 목록을 사용합니다. 목록 항목의 문법을 일관되게 유지합니다.
- 순서가 있는 절차나 번호가 붙은 설명에는 번호 목록을 사용합니다.
- UI 안내에는 스크린샷을 사용하되, 필요한 스크린샷만 포함하고, 관련 영역으로 잘라내며, 캡처 환경과 크기를 일관되게 유지하고, 캡처 전에 예시 입력값을 채우며, 스크린샷 위에 설명 문구를 직접 추가하지 않습니다.
- 비교, 옵션, 속성, API 필드에는 표를 사용합니다. 개념 설명이나 단계별 튜토리얼을 표에 억지로 넣지 않습니다.
- 추세에는 선 차트를 사용하고, 수량 비교에는 막대 차트를 사용하며, 원형 차트는 항목 수가 적은 단순한 비율에만 사용합니다.
- 문서에 그림이나 표가 많거나 탐색에 도움이 될 때만 캡션을 추가합니다.

## 검토 체크리스트

문서나 비평을 전달하기 전에 다음을 확인합니다.

- 제목과 제목들이 실제 내용과 일치합니다.
- 목차 또는 섹션 순서가 독자가 정보를 찾는 데 도움이 됩니다.
- 용어, 약어, 작업 이름, UI 레이블이 일관됩니다.
- 필요한 전제 조건, 정의, 경고, 단계, 예시, 예상 결과가 있습니다.
- 명령어, API 또는 동작이 환경에 따라 달라질 때 환경과 버전 가정을 명시합니다.
- 인라인 코드와 fenced code block의 형식이 일관되고, 유용한 경우 언어 식별자가 포함되어 있습니다.
- 근거 없는 주장, 추측, 모호한 표현, 중복 내용, 불필요한 배경 설명을 제거합니다.
- 문장이 짧고, 가능한 경우 능동태이며, 주어와 서술어가 맞습니다.
- 출처, 숫자, 단위, 제품명, 날짜가 정확합니다.
- 스크린샷, 표, 차트, 캡션이 필요하고, 소개되어 있으며, 관련 본문 근처에 배치되어 있습니다.

## 출력 패턴

문서를 편집하거나 검토할 때는 개선된 문서 또는 구체적인 재작성문을 먼저 반환합니다. 그런 다음 유용하다면 구조, 명확성, 용어, 근거, 시각 자료 기준으로 가장 중요한 변경 사항을 간략히 요약합니다.
